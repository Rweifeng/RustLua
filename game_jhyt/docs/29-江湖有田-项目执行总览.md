# 《江湖有田》项目执行总览

- 文档版本：0.2
- 本版同步：总策划案 0.2、开发计划 0.2

## 1. 项目结论

当前 RustLua 引擎已经可以承载本项目的第一版“武侠农庄”垂直切片：已有 2D Tilemap、Lua 脚本、实体、输入、动画、物理查询、背包、商店、地图切换、基础 UI、音频、粒子、资源导入和键值存档，并已有农场 smoke 示例验证耕地、播种、浇水、睡觉、成长、收获和交易闭环。

但它还不是可以直接制作完整商业版的成熟农场 RPG 引擎。必须先补齐稳定实体 ID、World Snapshot、Tilemap 状态保存、A* 网格寻路、战斗 hitbox、战斗事件、建筑 footprint 和 Lua 事件总线，再扩展 NPC 日程、任务、对话、装备和编辑器生产工具。

因此推荐产品路线是：

```text
武侠农庄 MVP
→ 第一章垂直切片
→ PC Alpha
→ PC Beta/首发
→ WebGL 验证
→ 微信小游戏可行性评估
```

不建议当前直接承诺“完整星露谷规模”或“多平台同步发行”。

## 3. 当前引擎与项目的映射

| 需求 | 当前状态 | 处理方式 |
|---|---|---|
| 农田、播种、浇水、收获 | 已有原型能力 | 复用现有 Lua API，补正式数据表和存档 |
| 时间、四季、睡觉 | 已有基础能力 | 接入日结算顺序和事件总线 |
| 背包、快捷栏、商店 | 已有基础能力 | 扩充物品、价格和任务奖励 |
| 地图切换 | 已有能力 | 加强地图状态快照和入口校验 |
| NPC 移动 | 实体/物理已有，寻路不足 | Rust A* + Lua 日程 |
| 对话和任务 | Lua 可编排，schema 需补 | JSON 数据表 + P1 工具 |
| 战斗 | 物理、health、动画已有，战斗层缺失 | Rust hitbox/事件 + Lua 招式/AI |
| 建筑 | 场景和 Tilemap 可用，占用规则缺失 | Rust footprint + Lua 配方 |
| 中文 UI | 基础文本和字体已有 | 加入文本校验、布局和本地化基础 |
| 资源导入 | 图片、音频、字体等已有入口 | 建立资产登记和失败状态门 |
| PC 发布 | 已有流程 | 加入原子发布、干净目录验证 |
| WebGL | 有 WASM 入口，真实集成不足 | Beta 阶段浏览器实测 |
| 微信小游戏 | 仅有预留声明 | 暂不承诺，完成专用链路后再评估 |

## 4. 立即执行的首批任务

1. 锁定 MVP 设计和 32×32 Tile 规范；
2. 新建游戏数据目录和最小 `project.toml`；
3. 将现有农场 smoke 逻辑整理为正式 Lua 模块；
4. 实现 `PersistId`、`WorldSnapshot` 和 Tilemap 状态保存；
5. 实现 A* 网格寻路；
6. 实现最小战斗 hitbox、命中去重和 AttackHit 事件；
7. 制作山庄、村庄、山道灰盒；
8. 导入第一批 CC0/明确商用资源，并登记许可证；
9. 接入 3 个 NPC、1 条任务链和 1 个商店；
10. 通过 PC 干净目录运行验收后，再制作垂直切片美术。

## 5. 关键决策

- 游戏暂定名：《江湖有田》；
- 类型：生活模拟 + 轻动作 RPG；
- 首发：Windows PC；
- 视角：2D 俯视角；
- 视觉：32×32 逻辑网格的中国武侠像素风；
- 首发不做婚恋、联机、开放世界和微信小游戏；
- 游戏规则优先 Lua，稳定底座优先 Rust；
- 外部资源优先 CC0，其次明确允许商业使用的 CC-BY 或购买授权资源；
- 不能把未动态验证的 WebGL、微信小游戏和完整战斗描述为已支持。

## 6. 风险总表

| 风险 | 等级 | 应对 |
|---|---|---|
| 存档无法完整还原运行时状态 | P0 | 阶段 B 优先完成 Snapshot |
| NPC/敌人无可靠寻路 | P0 | 阶段 B 完成 A*，限制地图规模 |
| 战斗判定不稳定 | P0 | 固定时间步、显式 hitbox、事件日志 |
| 建筑覆盖作物或入口 | P0 | footprint、占用层和放置预览 |
| 资源授权不清 | P0 | 禁止使用，建立许可证登记和 Credits |
| 美术风格混杂 | P1 | MVP 先灰盒，垂直切片统一采购/委托 |
| 编辑器制作效率不足 | P1 | 先用数据和灰盒推进，Alpha 补工具 |
| 中文文本溢出或缺字 | P1 | 字符收集、字体子集化和文本检查 |
| 发布失败留下半成品 | P1 | 临时目录构建、校验、原子替换 |
| WebGL 运行差异 | P1 | Beta 真实浏览器测试，不以构建成功代替验收 |
| 微信小游戏适配成本失控 | P2 | 先隐藏平台选项，完成技术预研后决策 |

## 7. 验收原则

任何功能只有在以下条件同时满足时，才算完成：

- 有实现代码或数据；
- 有测试、Demo 或可复现手工步骤；
- Debug 和 Release 均可构建；
- 不引入新的 P0/P1 问题；
- 资源来源和许可证已记录；
- 存档和版本迁移影响已说明；
- 编辑器、运行器和发布包中的行为一致。

## 8. 文档同步规则

- 总策划案负责回答“做什么、给谁玩、做到什么范围”；开发计划负责回答“怎么做、依赖什么、如何验收”。
- 任何 MVP 范围、平台承诺、核心数值或公共数据字段变更，必须同时更新两份专项文档和本总览。
- 版本号只在内容发生实质变化并完成交叉检查后递增；资源方案的许可证变化需同步风险总表。
- 当前执行基线：Windows PC 首发、7 日 MVP 垂直切片、先补存档/寻路/战斗底座，再扩展内容。

本总览是执行入口，具体内容以三份专项文档为准。
