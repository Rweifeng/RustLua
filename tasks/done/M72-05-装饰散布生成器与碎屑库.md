- 任务 ID：M72-05

- 创建日期：2026-10-08

## 目标

解决"画面几乎没有东西"——这是观感差距的头号来源，比任何贴图质量都大。

## 现状（实测）

- `scenes/manor.scene` 全图 920 格，只放了 **15 个非幽灵 sprite**（另有 6 个 `build_*` 建造幽灵），
  其中**树/竹共 7 株**：`manor_tree.png` ×4 + `manor_bamboo.png` ×3。
  其余是 well / sign / rack / jar / haystack / fence 各 1、house / shed / gate 各 1、玩家 1。
- `assets/art/props/` 一共 **21 张**。
- 星露谷同尺寸农场图：数百株树 + 灌木 + 石头 + 杂草 + 枯枝，
  且"没有两块相邻地面完全相同"（`references/stardew/Standard_Farm.png` 可直接数）。
- 地面碎屑（杂草/枯枝/碎石）在星露谷里是**贴在地面的小 sprite 装饰层**，
  这正是 M72-02 的 4-bit autotile 做不到不规则岸线时的补偿通道。

## 影响文件

- 新增 `examples/game_jhyt/tools/gen_scatter_decor.py`（散布生成器）
- 新增 `examples/game_jhyt/assets/art/decor/`（碎屑/杂草/枯枝/落花…小 sprite 库，当前无此目录）
- `examples/game_jhyt/scenes/manor.scene`（写入散布结果）
- `examples/game_jhyt/scripts/world/`（若装饰要走运行期生成而非烘进 `.scene`）

## 设计要点

1. **确定性散布**：种子化泊松盘或网格抖动，**同一输入必出同一张图**。
   随机散布进 `.scene` 会让黄金表每帧红（同 M72-02 的哈希教训）。
2. **烘进 `.scene` 还是运行期生成**——本包要显式裁定并记录理由。
   倾向**烘进 `.scene`**：编辑器里看得见、可手工微调，且运行期零成本；
   代价是 `.scene` 体积涨（920 格按每 3 格一个装饰算 ≈300 实体，
   而现在整张图才 30 个实体 → **实体数要涨一个数量级**，得先看 ECS 侧扛不扛）。
3. **分层**：地面碎屑（不遮人）/ 中景道具（按 Y 排序遮人）/ 前景（M72-06 做）。
4. 密度指标要按**每屏**算而不是每图：相机 `zoom=2` → 一屏 20×11.25 格（`51` §2.2）≈ 225 格。
5. 碰撞：碎屑一律非实体，**不要给装饰加 collider**（否则玩家走不动，且 `solid` 语义被污染）。

## 风险

- **实体数涨一个数量级**是本轮最大的性能未知数。现在的性能读数全部基于 30 实体的场景测的。
  → 本包**第一件事**就是拿 300+ 实体的 `manor` 跑一次 `sprite_stress` 口径的计时，
  拿到数再决定要不要退到"装饰走 tilemap 第二层"而不是 sprite。
  若走 tilemap 层，则不受实体数影响，但会失去 Y 排序遮挡能力——这是真实的取舍。
- 装饰多了会挡视线/盖住交互点（农田格、采集点）。要定"交互半径内不散布"规则。
- 与并行会话撞 `manor.scene`（M72-01 也重存它）。

## 验收方式

- 量化判据：**每屏可见对象 ~2 → ≥40**（按相机矩形统计 sprite 数，从 mesh 取，不靠肉眼）。
- 确定性门：同种子跑两次生成器，产出的 `.scene` 装饰段**逐字节相同**。
- **反面对照**：把种子换掉，门必须识别出内容变了（证明它真在比内容而不是比长度）。
- 性能：300+ 实体下 `manor` 的帧计时读数，与 30 实体基线对比，数字进本文件「实现记录」。
  按 `feedback-doc-claims-need-evidence` 的口径：**要附复现命令与测量口径**。
- 目验：与 `Standard_Farm.png` 并排。

## 实现记录

### 1. 性能前置读数与载体裁定（本包第一件事，先于任何美术）

**读数 A — 批处理两阶段口径**（`cargo run --release -p engine --example sprite_stress -- --sprites N --cycles 200`，release，取 p50/p99，单位 µs）：

| sprites | push_p50 | build_p50 | build_p99 | vertices | draw_batches |
|---|---|---|---|---|---|
| 30（现状） | 1 | 3 | 7 | 180 | 4 |
| 300 | 13 | 35 | 82 | 1,800 | 4 |
| 600 | 29 | 69 | 146 | 3,600 | 8 |

拟合到 **每 sprite ≈ 0.10µs push + 0.115µs build**，300 个装饰相对 30 基线的每帧增量 ≈ **45µs**。
（同一行的 `sequential_build_p50` / `parallel_build_p50` 是**强制 A/B**，不是帧实际走的路：
300 sprite 时 32 vs 253µs——并行路径的固定开销在这个量级上是主项，读数只看 `build_p50`。）

**读数 B — 全帧口径**（`cargo run --release -p engine --example wp0_scene_frame -- --cycles 30`，
原始 JSON 存 `examples/game_jhyt/.temp/m72-05-wp0-scene-frame.txt`）：

- `manor` 现状 30 实体 / 64 typed_components：**load_p50 168µs**（一次性，切场景时付）。
- sprite 阶梯全帧：1,000 → **287µs p50**（p99 494）、10,000 → 2,138µs、50,000 → 10,488µs
  → 约 **0.2µs/sprite**，含 ECS 遍历与绘制提交，不只是批处理。
- ECS 阶梯：500 实体 → 214µs p50、5,000 → 2,009µs → 加了装饰的 manor（≈330 实体）落在 500 那一档以下。
- **tilemap 对照**：32×32=1,024 格 → 198µs p50，100×100=10,000 格 → **193µs**——几乎不随格数下降，
  说明第二层的代价是**固定的**上传/批次开销，在 300 这个量级上**并不比 sprite 便宜**（198 vs 45）。
- 裁剪 A/B：10,000 sprite 不裁剪 3,053µs vs 裁剪后 2,139µs（顶点 60,000 → 3,036）
  → 屏外 sprite 有真裁剪，装饰铺满 920 格不会按总数全额计价。

**裁定：装饰烘进 `.scene`，走独立 sprite，不退到 tilemap 第二层。** 三条理由：

1. **便宜的方面**：300 装饰的每帧增量 ≈45µs（批处理口径）到 ≈90µs（全帧 0.2µs/sprite 外推），
   占 16.67ms 预算的 **0.3–0.5%**；而 tilemap 第二层要付它那份 ≈198µs 的固定成本。
   性能不是选 tilemap 的理由——"实体数涨一个数量级"这个风险在本包目标量级（几十到几百）上是**假的**。
2. **代价是真的但不值钱**：tilemap 层丢掉亚格偏移（装饰必须贴着 32px 网格角对齐）、
   丢掉 Y 排序遮挡（`scripts/world/depth.lua` 的 层秩×1000+order 只作用于 sprite），
   还要为碎屑单开一张图集并占 `57` §1 的"每图 ≤4 张"额度（manor 现已用掉 ground+farm+moist 三张）。
3. **一次性成本可接受、但必须实测**：`.scene` 文本从 155 行/28KB 涨到约 1,600 行/120KB，
   load 解析按文本线性走。上面 168µs 是**无装饰**的读数，外推不算证据——
   **装饰写进 `manor.scene` 之后必须重跑读数 B 同一条命令**，拿到"manor 加装饰后的 load_p50 与实体数"
   回填本表；若这一条显著劣于预期（>3ms），退路是把纯地面碎屑（不需要 Y 排序的那批）改走 tilemap 层，
   而不是整体回滚。

**读数口径的诚实边界**：A 不加载 `.scene`（纯批处理），B 的 sprite/ECS 阶梯是合成场景，
两者都**不是**"manor + 300 个真装饰"。所以裁定附带第 3 条那个"改完必复测"的硬条件，见上方验收清单。

### 2. 复测（§1 裁定附带的硬条件）：装饰写进 manor 之后的读数 B

命令与读数 A/B 同一条：`cargo run --release -p engine --example wp0_scene_frame -- --cycles 30`
（原始 JSON 存 `examples/game_jhyt/.temp/m72-05-wp0-scene-frame-decorated.txt`）。

| | 装饰前 | 装饰后（175 件已写入） |
|---|---|---|
| manor entities | 30 | **205** |
| typed_components | 64 | **414** |
| load_p50 | 168µs | **778µs** |
| load_p95 / p99 | — | 1,294µs / 1,300µs |
| `.scene` 文本 | 155 行 / 28KB | 855 行 / 95,574 字节 |

**裁定成立，不退 tilemap 层。** 判据是 §1 第 3 条写的 3ms：实测 p50 778µs、p99 1.3ms，一次性
载入成本只有阈值的 1/4。折算下来每件装饰在 load 侧摊 ≈3.5µs（+610µs ÷ 175 件），比文本行数
线性外推的估计还低——因为 `role=decor` 那行是纯元数据、不进 ECS。帧侧不需要复测：§1 的
0.2µs/sprite 全帧口径给出 175 × 0.2 ≈ 35µs，占 16.67ms 的 0.2%，而 §3 的实测每屏只有 43 件
在帧内（其余被视口裁掉）。

### 3. 落地内容：碎屑库、散布规则、门

**库**：`assets/art/decor/` 24 张 PNG = 12 种形状 × 2（正/`_r` 镜像），另有一张 `_preview.png`
联络表（与 `buildings/`、`characters/` 的既有约定一致）。画它在
`tools/gen_decor_art.py`，颜色全部走 `terrain_ramp.json`（不在色阶表上的像素由它的 `check()` 判红）。
**镜像为什么是另一张图而不是 `flip_x`**：引擎的规范序列化 `Sprite::to_component_str` 不写 flip
字段，作者串带上 `flip_x` 就过不了"生成 == 引擎回写"的对拍，两个 web 宿主也没接这条。

**单一实现**：`tools/decor_kit.py`（plan 原写的是 `gen_scatter_decor.py`，实际拆成三件——
`decor_kit.py` 是散布本体、`gen_decor_art.py` 画库、`set_scatter_decor.py` 就地改盘上场景。
拆开的理由与 M72-04 的 `terrain_kit`/`set_terrain_autotile` 同一件事：从零生成与就地改写必须
共用一份实现，否则"重跑生成器"抹掉盘上场景，对拍就失去意义）。种子 `DECOR_SEED = 0x5C0713`。

四条规则，各自对应一个可复现的症状：

1. **每格独立哈希**（`hash_stream(质数混合)`），不是一条顺序流——顺序流里"多撒一格"会把后面
   所有格子整体重排，review 看不出改了什么。
2. **留白跟着遮挡力走**：`exclude`（药田矩形、`places.lua` 地点格、出生/出口、既有道具占格）
   两带都不许下；`mid_avoid`（半径 2 的环）**只挡中景带**。第一版给两带统一套半径 2，920 格里
   吃掉 180 格、每屏中位数只有 22 件——它防的症状（碎屑盖住交互点）其实不存在：碎屑 order -30
   画在所有物件之前，连玩家都永远在它上面。
3. **染色照抄脚下那格的地表 tint**（读 `tints=`/`tints_rgb=` 稀疏载荷），于是阴里的灌木和阴里的
   草地是同一档明度。
4. **生境偏置而不是小概率**：香蒲必须临水（4 邻域有水），全图只有池塘边 10 格满足，抽中概率
   2.6% 时**一次都不出**（等于白画一张图）；`EDGE_BONUS` 从 2 → 6 仍为 0，12（在那几格里占约 45%）
   才出 2 件。中景份额 `MID_SHARE` 从 0.20 → 1.0 是因为 175 件里只有 2 件中景——碎屑解决"地面
   有没有东西"，视线落点靠中景。

**结果**：175 件（碎屑 159 / 中景 16，镜像档 83），12 种形状全部至少被抽到一次。每屏
（640×360 世界单位，`zoom=2`）中位数 **43** 件，min 5 / max 71（最坏那一屏压在药田上，按契约必须
留白 → 判据取 median 而非 min）。前值 ~2。

**门**：`engine/crates/game/examples/jhyt_m72_scatter_decor.rs`（已登记进 `verify.ps1` MVP 清单）。
五节 + 四处对照，两处口径值得单独记：

- 每屏数量**两边各数一遍**：文件侧滑遍所有可停靠窗口取中位数，渲染侧用 mesh 的装饰 quad 数与
  文件件数对账（关剔除 175 == 175，开剔除 31 == 门按 `sprite_may_be_visible` 同判据数出的 31，
  且强制两数不同——相同即"剔除没生效，第二条断言是空的"）。
- **物理查询点必须从运行期取**：`physics.overlap` 走 Rapier 的碰撞体宽相，而刚体建在
  `Transform.position` 上（`scene_spawn.rs:544`）。第一版拿"文件里的 x/y + 半张贴图"当查询点，
  正向对照（打到带 collider 的实体上）取到 0 个命中——那个 0 与装饰有没有 collider 无关，只是
  门在测自己的坐标想象（贴图中心还要过 pivot 与 y 翻转）。改成 `entity.find` → `transform.get`
  之后：175 次查询命中装饰 0 次、命中别物 16 次（地表 tilemap 的实心格，这正好证明查询真的在
  跑），玩家自身那发取到 1 个命中且含其自身。

### 4. 路上修掉的两个工具缺陷（都不在本包计划内，都是一查就撞上的真 bug）

1. **`tools/preview_scene.py` 把 sprite 全画在 (0,0)**：它读 `transform.get("x")`，而 `.scene` 的
   规范串是 `position=x,y,z;rotation=…;scale=…`，**没有** `x=`/`y=` 两个字段，于是恒取默认 0。
   这个工具从写下那天起就是这样——之前所有"预览图目验"里，sprite 的相对位置都是假的（本包
   要靠预览目验装饰分布，第一条就撞上了）。修完的目验图在
   `.temp/m72-05-view-*.png` 与 `.temp/m72-05-decor-preview.png`。
2. **`gen_manor_scene.read_manor_place_cells` 的默认路径跟着 cwd 走，且文件不在时静默返回空表**：
   `os.path.join("scripts","data","places.lua")` 是相对 cwd 的，`os.path.exists` 为假就 `return []`。
   从 `engine/` 目录跑 `--check` 时实测与盘上差 24 行——不是散布不确定，而是**"玩法留白"这份输入
   整个消失了**，草被撒到 NPC 的地点格上。改成按 `__file__` 定位工程根 + 读不到就抛错。
   同类写法在 `gen_village_scene.py:327`、`gen_interior_scenes.py:265` 还各有一份（见「未完成项」）。

### 5. 对拍防呆与库门（Python 侧，事实源在的地方）

`python tools/set_scatter_decor.py scenes/manor.scene --check` 三段：同种子两次逐字节相同、
换种子内容必须变（否则散布根本没读 seed，"相同"是空的）、盘上装饰段 == 现算段。
三段全是**逐字节**比对（起点用盘上真实会用的 id，所以连实体名一起比）。
`python tools/gen_decor_art.py --check` 是库自己的门：24 张条目齐全、尺寸 == 目录、每个不透明像素
都在色阶表覆盖的色族里、alpha 只有 0/255——Rust 门只比尺寸与明度档，"手改过一张图的像素"只有
这里看得见。两条都已接进 `verify.ps1`（步骤名 `Decor scatter determinism (python)`，缺 python
时按本仓库口径打印原因后跳过、绝不写成通过）。修完 §4-2 与 `gen_decor_art.OUT_DIR` 的同类 cwd
问题后，从 `engine/`、`/tmp`、工程根三个 cwd 跑同样绿。
