# 任务：M34-01 关系与声望档位接线（把已算出来的档位变成玩法出口）

- 任务 ID：M34-01
- 状态：实现完成，待验收（2026-10-03）
- 关联里程碑：M34
- 创建日期：2026-10-03
- 前置：M34-00（要动存档语义，且需要长跑骨架做"跨天档位不漂"的断言）
- 预估：1.5–2 天（纯 Lua + 数据，不动 Rust）

## 目标

关系/声望原来**只有入口没有出口**：任务奖励在加（`scripts/data/quests/ending_*.lua`、
`mainline_*.lua` 的 `reputation`/`relationship` 奖励块都在），`relationship.tier()`
**全工程零调用方**，五档表算出来没人读。本任务把档位接进消费者：**对话分支、商店购买价、结局交付门槛**。

## 实现要点（原计划的四条约束与落实结果）

1. **先对齐两套口径，再写代码**：已按**实现口径**改写 docs/33 §8.1/§8.2（0–100 关系分五档、
   声望 `-100..100` 且档位表只覆盖 0–100），并让 `jhyt_m24_numeric_alignment` ⑩ 直接解析这两张表逐格比对
   （该套件本就有解析 markdown 表的先例：作物表、商店价表）。§8.2 另加一列"购买折扣"，
   让门比的是**数字**而不是散文。
2. **效果是查询不是写入**：只读查询函数 + 只读效果表，消费者每次交易自取；不新增引擎 API，不进存档。
   实测⑤章就是这条的验收（存读档只搬分数，折扣/门槛结论一起回来）。
3. **效果表为空时行为与改前逐字节一致**：陌生档 `effects = {}` → 折扣 0%，原价；
   第一刀因此能只接对话与结局而不动商店数值（实际同批做完，但折扣的可观测性只落在店主阵营上）。
4. **限次与幂等沿用既有形状**：一次性分支用对话节点的 `var` 锚点（`set_var` 已随存档持久化），
   没有新造"是否已解锁"的标量，也没有用 `relationship.reward_once`——分支的"只说一次"是对话语义，
   放在对话数据里更贴近。

## 实际落地的四个出口

- **声望 → 购买价折扣**：`scripts/data/relationships.lua` 的 `reputation_tiers[*].effects.price_off`
  （0/5/8/12/15）由 `scripts/systems/shop.lua` 的 `keeper_price_off` 读取——**按店主阵营**的档位算
  （`data/shops.lua` 的 `keeper` → `data/npcs.lua` 的 `faction`），只作用在购买价，
  出售价与限购不动；`M.price_off(shop_id)` 是只读查询，未知商店返回 0。
- **关系档位 → 对话分支**：`scripts/world/dialogue.lua` 新增条件键 `tier_npc` + `tier_gte`
  （成对出现，缺一即校验红），命中 `player/relationship.lua` 的 `affinity_met`（未知 NPC/档位一律返回 false，宁可挡住）。
  首个消费者是陆归藏的体己话分支（`scripts/data/dialogues/lu_guizang_truth.lua`：友善 45 分才出现，
  说完写锚点 `lu_guizang_secret`，选项收回，一次性奖励走 `effects.set_var`）。
- **声望档位 → 结局交付门槛**：`scripts/world/quest.lua` 新增目标 `kind = "reputation"`
  （`faction` + `tier` + `label`），进度行按 `0/1`、`1/1` 口径出，与 flag 目标同形；
  `ending_field` 挂 `village/known`、`ending_vengeance` 挂 `sect/trusted`、`ending_sect` 挂 `sect/esteemed`，
  `ending_renounce` **刻意不设门槛**（只用主线锚点 + 物品即可交付，保底第四条路）。
- **NPC 阵营归位**：`scripts/data/npcs.lua` 的 `faction` 字段把 9 位 NPC 归到 `village`/`sect`，
  玄冥会执事司徒魁留空（无阵营 = 不参与折扣，也不是敌对阵营）。

## 实测更正（与计划不一致处，逐条给依据）

1. **不需要新增 23 号校验器**：`scripts/validate_data.lua` 是按**路径**登记校验器的，
   `relationships` 早在表内，新增的档位结构校验（连续性、末档覆盖值域上界、`price_off` 白名单且非递减、
   NPC 引用未知阵营）直接挂进 `relationships.validate_all` 就已被 `game --check` 覆盖；
   `jhyt_m23_data_validation` 的校验器计数**没变**，实测仍绿。
2. **效果是"查询函数 + 数据表"，档位仍是派生值**：`affinity_met` / `reputation_tier` / `reputation_met` /
   `reputation_price_off` 全是只读查询，存档仍只写分数；关系档位在数据里只写 `min`（上限由下一档 `min - 1` 推出，
   末档取值域上界 100），声望档位写 `min`/`max` 成对——两套形状不同是有意的：关系分夹在 0..100、
   声望夹在 `-100..100`，负声望按第一档算（无惩罚），硬写 `max` 反而给"负数区间"留下可写错的位置。
3. **`effects` 只落了 `price_off` 一个键**（白名单同样只有一个）：计划里的 `order_tier` / `dialogue_flag` 没落地。
   订单池过滤今天没有可观测的消费方——三家店的店主全是云泽村阵营，**门派折扣连商店消费者都还没有**，
   更不会有"订单按门派档位扩容"的可断言行为；配方解锁要等 M34-05（茶棚）才有挂载点。
   与其造一个只能被自己的测试驱动的假效果，不如把白名单收窄，将来加键时再一起加消费方与用例。
4. **HUD 不改**：计划里要显示对话对象的档位中文名，并把新 `last_action` 键送进 `jhyt_m26_hud_feedback` 的中文映射。
   实际选了 `kind = "reputation"` 目标走任务日志的 `label`（"云泽村声望到熟识"），
   **没有引入新 reason 键**，因此 `ui/hud.lua` 一行未动（它在本工作区被并行的第二批改动占着，见"交接"）。
   验收④（新键要有中文映射）随之不适用。
5. **结局门槛必须钉在"内容真能到"的档位上**，这是实测出来的约束，不是设计选择：
   全仓只有任务奖励会加声望，逐笔相加——云泽村必得 8+15 = 23、可选 +6/+5（**上限 34**），
   青云门派 5+10+20+25 = **正好 60**。所以 `ending_sect` 挂 `esteemed` 是**刀刃**：
   差一分钱就交付不了，而且**今天没有任何负声望来源**能把它弄下去。这一条被显式钉成契约写进
   `ending_sect.lua` 的文件头与本门②/③章，将来加负声望或改奖励数额时必须先改这份账。
   `受信(40)` 对云泽村、`核心(80)` 对两阵营今天都到不了，仍是"预留"，在 docs/33 §8.2 里明写了。
