## 实现记录（2026-10-24）

### 已交付（`engine/crates/rustlua-ui/src/`）

- **虚拟列表**（`ui_virtual_list.rs`）：`VirtualList` 按固定行高算可见窗口
  （含过扫、钳制到总项数），`scroll_by` / `scroll_to_index` 返回实际位移；
  `SlotPool::bind` 只保留当前 key 的槽位、稳定 key 复用原槽、空槽优先复用，
  槽位池大小贴合窗口而不随总项数增长。`bind_window` 一帧给出
  `(index, key, slot, rect)`，1000 项单测验证窗口与池子上界。
- **富文本**（`ui_rich_text.rs`）：只解析 `<b>`、`<color=#rrggbb>`、`<icon=name>`、
  `<br/>`；未知标签按字面量保留并进 `unsupported`；未闭合标签不吞文本；
  非法颜色退化为无颜色。输出 spans + 纯文本 + 行数。
- **输入与 IME**（`ui_text_input.rs`）：光标/选区按**字符**下标（中文/emoji 不切半）；
  插入/退格/前删/移动/全选/选区替换；IME 预编辑 `begin/update/commit/cancel`，
  取消不改正文。`InputPolicy::for_host` 固化降级边界：桌面进程内组合、Web 浏览器
  composition、微信仅原生输入桥（无内部光标/选区），桥不可用则只读。
- **导航栈**（`ui_nav_stack.rs`）：`push`/`back`/`push_modal`/`close_modal`；
  返回键先关模态再弹页，根页返回 `AtRoot`；模态存在时底层页面不接收输入；
  弹出页携带 `restore_focus` 供调用方恢复焦点；关闭不存在的模态报错。
- **运行期接线**（`rustlua-ui/src/lua_advanced.rs` + `ui_state.rs` + scripting 的
  `api/mod.rs`）：四个命令表入口装进共享的 `ui` 表——
  `ui.virtual_list{op=open/close/scroll/scroll_to/window/bind}`、
  `ui.rich_text(text)`、`ui.text_input{op=open/close/state/edit/composition/policy}`、
  `ui.nav_stack{op=open/state/push/modal/back/close_modal}`。状态放在
  `UiState.advanced`（能力单元内），因此跨脚本调用存活、场景切换随
  `clear_for_scene_transition` 一并清空。参数错误在 Lua 边界当场报错（带可用 op 清单），
  读未登记的 id 返回 `nil` 而不是崩。

## 未完成项 / 已知限制

- **只接了 Lua 面，没接绘制**：`Capabilities::core()` 仍如实关闭 `rich_text` /
  `virtual_list`——富文本目前只解析成 spans，宿主文本排版仍按纯文本绘制（标签被去掉），
  虚拟列表的可见行也还没有生成 UI 网格/场景节点。`planned()` 的布尔位只表示目标能力面。
- **性能只有逻辑层读数**：`ui_virtual_list_1k` 量的是"算窗口 + 绑槽位 + 算矩形"，
  不含文本测量/绘制/上传；没有堆内存计数器，只有"槽位池 ≤ 40、不随总项数增长"的结构上界。
  debug 读数不能当发布结论；`verify.ps1` 目前只跑编辑器基线，没有单独的 UI 性能门。
- **富文本跨宿主未对拍**：没有固定字体/字号档位的 golden，三宿主排版一致性未测。
- **输入未接宿主事件循环**：桌面/Web 的 composition 事件、微信原生输入桥调用与
  焦点同步都还没有宿主侧实现；Lua 侧只能手动喂 `edit`/`composition` 命令。
- **三宿主终验矩阵未跑**：布局矩形、绘制顺序、交互序列、字体回退四类 golden
  全部未测；仓库当前没有 `builds/` 产物，Web/微信 harness 无法开跑；`verify.ps1`
  未新增 UI 矩阵门。微信真机未验。
- **场景切换清理只覆盖 `UiState.advanced`**：动态 UI 元素走既有清理通道；虚拟列表
  没有「窗口变化时重绑」的宿主循环，需调用方每帧自行 `bind`。

## 目标

补齐虚拟列表、富文本、输入控件、导航栈等高级能力，并把 PC/Web/微信三宿主的 UI golden 跑成终验矩阵。

## 影响文件

- `engine/crates/rustlua-ui/src/**`（虚拟列表、富文本、输入、导航）
- `engine/crates/rustlua-render/**`（文本排版/裁剪）
- `engine/crates/game_web/**` 与 `plugins/webgl/**`（宿主事件/字体）
- `scripts/verify/verify.ps1`（三宿主 UI 矩阵）

## 交付项

1. **虚拟列表**：可见窗口 + 回收池 + 稳定 key，`Capabilities::planned()` 的 `virtual_list` 转真。
2. **富文本**：有限标签集（粗体/颜色/图标/换行），三宿主同一排版结果。
3. **输入控件**：文本输入、IME 最小支持、焦点与光标；微信端降级策略明确。
4. **导航栈**：页面 push/pop、返回键、模态与遮罩、焦点恢复。
5. **三宿主终验**：布局矩形、绘制顺序、交互序列、字体回退四类 golden 全跑；未测项列清单。

## 验收方式

- `scripts/verify/verify.ps1` 全量门 + 三宿主 UI 矩阵脚本。
- 微信：真机按既有 #950 经验验 wasm 字节与画面；工具绿不作为真机结论。
- 性能：1000 项虚拟列表帧时间与内存读数进基线。

## 风险

- 微信字体/输入能力弱：输入控件可能只能做"唤起原生输入"的桥；提前写清降级边界。
- 富文本排版跨宿主差异：以固定字体与字号档位锁死，再逐步放宽。
- 三宿主矩阵耗时：按 nightly/手动档跑，PR 门只跑桌面 + Web 子集，矩阵读数入台账。
