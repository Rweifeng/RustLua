## UI 框架裁定（本期出文，内容先行）

**建议裁定：不迁移，保留 egui/eframe。** 论据：

- egui 是 Rust 独立编辑器生态事实标准（Bevy 生态编辑器均基于它），egui_dock 补齐
  docking 后，"更富表现力框架"（Slint/ImGui 完整版/Dear imgui Rust 绑定等）能提供的
  增量主要是动画与主题精致度，与编辑器工具属性错位；
- 迁移成本：31k 行编辑器代码 + 全部 `gui_evidence` 像素基线 + wgpu 管线接合点重写，
  量级 ≥ 一个整里程碑；立即重排现有全部架构约束（typed action 提交层与框架无关，是
  唯一保值资产，也应只保值这部分）。

**重估触发条件**（满足任一才重新评估，写进 ADR）：

- 需要矢量动画/富文本渲染级别的编辑器 UX（如内置过场编辑器时间轴预览）；
- egui/eframe 停止维护或 wgpu 主线断裂；
- Web 目标（`crates/game_web`）验证发现 egui 在 wasm 下不可接受的输入缺陷。

## 实现记录

### 1. 长会话 soak（负载机制 + ≥2h 实跑）

**机制**（`gui_evidence.rs`）：`RUSTLUA_EDITOR_SOAK` 之外新增三个环境变量把"本期改动的路径"塞进
soak 的每一轮——`_CHURN_SECONDS`（每轮间隔）、`_DROP_EVERY`（每几轮做一次拖放导入）、
`_DROP_SOURCE`（不填则自动在**工程外**找一个纹理当拖放源）。每轮做两件事：
① `dock::churn(state, step)` 按 6 步循环真的重排树（拆出浮动窗 → 并回 → 合并成组 → 拆回），
② 到点的那轮走 `ingest_and_spawn` 导入一个外部文件，**随后 Undo 掉建出的实体**，并在**下一轮开头**
删掉上一轮入库的副本——`assets/` 里的实体数与副本数因此**有界**（249 轮实测同时在飞 2 份，
不是设计值 1 份，见 §未完成项），工作集曲线量到的才是"同样的活重复 200 遍"，
不是"assets 目录长大了"。删除放在下一轮开头，是为了不打断后台导入。
每个采样点带 `churn_rounds` 计数，内存台阶可以逐轮归因；报告头与 `soak.json` 都带
`rounds / dock_churns / drop_imports / drop_cleanups / skipped`，`skipped>0` 说明有轮次在空转
（Play 锁定或树被借走），不能读成"重排过这么多遍"。
自动化半边：`dock::two_hundred_dock_churns_rearrange_the_tree_every_round`（200 轮每轮都必须改结构、
六标签不丢不重、重排后仍可序列化）、`gui_evidence` 的两条负载测试（30 轮负载不改变项目规模；
间隔未到就一律不做）。真实窗口 150 s 冒烟已过：计数逐条对得上、副本清理干净、源文件自动落在工程外。

**判据工具本身是坏的**（本期第一次有人运行它才暴露）：
`scripts/analyze-soak.ps1` 首行少了前括号（`CmdletBinding()]`），PowerShell 5.1 在解析阶段就报
"应为表达式"，退出码 1——`git log -1 --format=%h -- scripts/analyze-soak.ps1` 指到 `6bcdabd`
（2026-09-27，一个摇杆/作物批，与 soak 毫无关系：文件工具改写时把首行第一个字符吃掉了），
上一版 `908a478` 还是好的。**也就是说 docs/55 阶段 0 立下的 soak 判据坏了五天，而这段时间里
它的"结论"全靠人读 `soak.txt` 的表**。修了两处：
① 首行补回 `[CmdletBinding()]`；
② 第 14 行的 `Get-Content -Raw | ConvertFrom-Json` 补 `-Encoding UTF8`——
`soak.json` 的 `churn.recent_notes` 里全是中文面板标题，PS 5.1 默认按 ANSI 解码时
中文的 GBK 尾字节会落成 `0x5C`（反斜杠），`ConvertFrom-Json` 随即报非法转义（本仓库已知的坑，
`scripts/package.ps1:697` 的注释写的是同一件事）。同一处修法顺手给了 `scripts/compare-baseline.ps1:19`
（§2 帧预算对照用的那份 JSON 同样带中文场景名）。

**这类伤不能再等到验收当天**，两道门：
① `scripts/check-docs.ps1` 第 ⑦ 项原本只查 BOM（字节层），首行少一个字符在字节层看不出来；
新增第 ⑧ 项，用 `[Parser]::ParseFile` 把 `scripts/*.ps1` 全部**只解析不执行**地读一遍，
任一文件解析失败就判红并带行号与原始报错。负例已验证可拦截：临时造一个首行丢括号的文件 →
`[RED] check_docs_failed issues=1` `scripts\m27-parse-probe.ps1: PowerShell 解析失败（1 行：…应为表达式…）`、
退出码 1，删掉后 `check_docs_ok docs=55 game_docs=24 h1=81 links=282 ps1_bom_ok=28 ps1_parse_ok=28`
（28 是含下面第 ② 项新增自测脚本之后的数）。
② 判据本身新增自测 `scripts/test-analyze-soak.ps1`（`soak_analyze_tests_ok cases=5`，
已进 `verify.ps1` 的 "Soak analyzer self test" 阶段，紧跟 "Baseline comparison thresholds"）：
稳态负载（谷值 460 MiB ± 8 的锯齿 + 中文面板标题）必须退 0 且判定行可读；
每采样点 +4 MiB 的真泄漏必须退 2 且说 `sustained_growth`；
谷值不动、峰值一路摆 36 MiB 的锯齿**不得**误报；单采样点与文件缺失都必须非零退出。
fixture 写成**不带 BOM** 的 UTF-8，字节布局与编辑器侧 `soak.json` 一致——带 BOM 就测不到 ANSI 误解码。
负例同样验证过：把 `-Encoding UTF8` 摘掉再跑同一份 fixture，脚本当场 ParserError 退 1，
所以这一格是真的被门钉住的，不是"看起来绿"。判据行格式变了，命令矩阵同步登记在
[docs/34](../../docs/34-质量门与发布清单.md) §3。

**≥2 h 实跑（7500 s，2026-10-01 22:31:39 → 10-02 00:36:40 UTC，真实窗口 + 真实 Play/Stop 循环）**：
`RUSTLUA_EDITOR_SOAK=7500 _PLAY_SECONDS=10 _STEP_SECONDS=10 _CHURN_SECONDS=30 _DROP_EVERY=1`，
工程是 `%TEMP%\m27-soak-project\game_api`（22 实体、四精灵场景），拖放源由机制自己挑到**工程外**的
`examples/game_api/assets/models/kaykit-warrior.glb`（4 863 620 字节）。产物：
`soak.json` 748 个采样点、`complete=true`、`frames=257963`、`play_cycles=749`。
负载计数：`rounds=249 dock_churns=249 drop_imports=249 drop_cleanups=248 skipped=0`——
清单要求的"重排 + 导入 200 次"实到 249 次，且 **`skipped=0` 说明这 249 轮没有一轮在空转**
（每轮都真的改了树结构、真的导入了一次）。

判定（`scripts/analyze-soak.ps1 -Windows 8`，退出码 0）：


`tex_max` 全程 4.8 MiB 不动（egui 图集只有 2 张，随字符集微调在 3.7/4.8 之间摆），
这一列是专门用来排除"面板重排把纹理攒出来了"的：如果 dock 化漏放了纹理，
`egui_texture_bytes` 会随 `churn_rounds` 单调上去，而它没有。

分段线性回归（MiB/min，比窗口读数更直白）：预热段（0-60 s）**+6.82**；修剪前的长平台
（60 s～4837 s，476 点）**+0.224**（≈ 70 分钟涨 15.7 MiB）；t=4837 s 之后（266 点）**+0.061**
（≈ 3.7 MiB/h），最后四分之一（187 点）**+0.045**。也就是说：**斜率随时间往下走，不是往上走**，
清单第 1 条要的"无持续线性增长"成立。

**但结论不能拿 `tail_growth=-209.8` 这句话去读**：那个负数是那次外部 trim 白捡的，
它同时把 `tail_noise` 顶到 212.4 MiB（远大于 71.6 的阈值）——判定行"过"了，可它的信噪比是坏的。
真正站得住的是**修剪之后那 266 个点自己**：谷值 264.9 → 267.4（约 47 分钟 +2.5 MiB）、
p50 270.8 → 272.8、回归 +0.061 MiB/min、`egui_texture_bytes` 全程钉在 3.7/4.8 MiB 两档，
且期间又跑了 88 轮重排与 88 次导入。**"无持续线性增长"这条结论建立在这段稳态上，
不建立在那个负数上**；读判据的人若只抄 `soak_verdict` 那一行，就会把一次系统回收当成一小时的稳定。

**那一次 −214 MiB 必须归因，不能当"编辑器变好了"读**：单点从 483.9 掉到 269.9，而同一采样点的
每一项台账**都没动**——`egui_textures=2`、`egui_texture_bytes=3 874 400`、`entities=22`、
`undo_entries=0`、`console_lines=500`（上限）、`churn_rounds` 160→161 照常推进，每 10 s 的帧增量
340/338/353/352 连续无掉帧，编辑器日志在那个时刻没有任何事件（只有既有的 10 s Play/Stop 循环）。
一个进程不会在"什么都没释放"的前提下把驻留降掉 214 MiB，所以这是**操作系统回收工作集**
——同一件事 [docs/58](../../docs/58-编辑器重构阶段0-3收口与验收.md) §2.4 早就记过一笔
（"进程工作集是锯齿状的：缓存涨落、分配器保留页、**Windows 主动 trim working set**"，
那次 30 分钟档同时给出"均值 −258 MiB"与"谷值 +54.9 MiB"）。本节不是重新发现它，
而是把"台阶必须逐轮归因"变成读数纪律：报告里带着 `churn_rounds` 与全部台账，
才分得清"编辑器释放了"和"系统回收了"。
这条同时给判据划了边界：`WorkingSet64` 量的是**驻留**，不是提交量/私有字节，
所以本结论的正确读法是"驻留曲线没有向上外推"，而不是"堆没有增长"；反过来，真有持续泄漏时
被反复触碰的新页一定会把驻留顶上去（预热段那条 +6.82 的台阶就是这么来的），
所以这条门对"要判的故障"仍然有灵敏度——`test-analyze-soak.ps1` 的 ②③ 两格（每点 +4 MiB 判红、
谷值不动的大锯齿不误报）钉的就是这个灵敏度边界。

**负载是否真的"没把工程喂大"——落盘核对**：跑完 `%TEMP%\m27-soak-project` 共 21 MB，
`assets/models/` 里只有 **2 份** 4 863 620 字节的副本（与源文件同尺寸）。若机制失效、每轮真留一份，
这里会是 249×4.86 MB ≈ 1.17 GB。两点如实登记：① 设计是"同时在飞 1 份"，实测 2 份（诊断见
§未完成项第 9 条，有界且不影响本判据）；② `.cache/cache` 在 249 轮里长出 **56 个 blob / 9.87 MiB**
（约每 4 轮一个），这是**唯一随轮数增长的磁盘产物**——它落在磁盘上，不进工作集，
但"工程大小恒定"这句话对它不成立，只能说 `assets/` 有界。

**手感缺口照旧**：这 249 轮重排是 `dock::churn` 程序化改树，不是真鼠标；
清单第 1 条只主张"没有持续线性增长"，不主张"拖 200 次面板的手感没问题"（后者在 §未完成项）。

**原始产物留存**：`artifacts/baselines/m27-editor-soak-7500s.json`（222 736 字节，748 个采样点全量）、
同目录 `.txt`（报表正文）与 `artifacts/logs/quality/m27-editor-soak-7500s.log`（1 840 003 字节的运行日志）。
`artifacts/baselines/*` 除 README 与 `wp0-3d-stress.committed.json` 外被 gitignore 排除，
所以这三份**只在本机**——正是 §未完成项第 1 条说的存档缺口，本节把结论数字抄进文档就是为了不被它坑。

### 2. 帧预算对照（口径已改，见 §验收清单 2 的注）
