## 风险

- 对话/任务数据引用必须在加载阶段校验，不允许运行时静默失败。
- 任务奖励必须幂等，重复交付不能重复发奖。
- 变量副作用必须记录来源和事件，便于存档和调试。

## 实现记录

- **引擎能力零改动（验收项①）**：全部能力（`ui.text/text_at/panel/clear`、`input` 边沿键、`entity`/`npc.query`、`inv.*`、`state` 容器）在引擎侧已存在，本任务未修改任何 Rust 核心代码；新增一段对话或一条任务只需在 `data/dialogues/index.lua`、`data/quests/index.lua` 注册数据文件。
- **`state.lua` 变量与事件流水**：新增 `vars` 容器与 `get_var`/`set_var`/`add_var`/`clear_vars`；`set_var`/`add_var` 接受 `source`+`event` 参数并写入有界（`VAR_EVENT_LIMIT=32`）事件流水 `var_events`，每条含 `var/old/new/source/event`（硬风险③可回溯）；值类型限定 number/boolean/string 以保证 JSON 往返；`capture`/`restore`/`reset` 同步纳入 `vars` 与 `var_events`；`VALID_MODES` 含 `Dialogue`。
- **`quest.lua` 五态状态机（验收项③）**：`not_started`（无记录）→ `in_progress`（已接取）→ `deliverable`（目标全达成的**派生态，不落档**）→ `completed`（幂等锚点）/ `failed`（显式失败）。`state(id)` 按记录状态 + `objectives_met` 实时推导；目标支持 `item`（`inv.count` ≥ count）/`var`（数值 ≥ count）/`flag`（真值）三类。
- **幂等交付（硬风险②）**：`M.deliver` 顺序为「目标校验 → **先落 `status="completed"`** → 消耗目标物品 → 发奖 → `on_complete`」；重复交付在入口即返回 `already_completed`，奖励绝不重复发放。返回码覆盖 `unknown_quest`/`not_accepted`/`already_completed`/`quest_failed`/`objectives_unmet`。
- **副作用解释器**：`M.apply_effects(effects, source, event)` 被对话选项与任务 `on_complete` 共用，支持 `set_var`/`add_var`/`add_item`/`money`/`inner_power`/`accept_quest`/`deliver_quest`/`fail_quest`；变量写入统一携带来源（如 `dialogue:gu_changfeng_teach`、`quest:quest_spar`）与事件（如选项文本、`on_complete`）。
- **奖励字段规范**：item 奖励读 `count`，money/inner_power 读 `amount`（与数据 schema、`validate_all` 一致）。
- **`dialogue.lua` 运行时**：`get`/`ids`/`find_for_npc`/`start`/`close`/`choose`/`options`/`info`/`dialogue_id`/`node`/`is_open`/`reset`/`ensure_target`/`render`/`validate_all`；节点推进按选项 `next` 跳转或 `finish` 结束；选项 `cond` 支持 `quest`+`state`、`var`+`eq/gte/lte/lt/gt`、`var`+`truthy/falsy`、`item`+`count`，不满足即不渲染；`M.start` 进入 `Dialogue` 模式并渲染即时 UI 面板，`M.close` 复位 `Playing` 并 `ui.clear`。
- **加载期校验（硬风险①）**：`quest.validate_all` 校验注册表重复 id、定义可加载、`id`/`name`/`giver` 引用、目标 kind 与物品/var 引用、count 正数、奖励 kind 与引用、`on_complete` 字段白名单；`dialogue.validate_all` 校验节点 `text`/`options`、选项 `text`、`next` 节点存在或 `finish`、`cond`/`effects` 字段，并**交叉校验每条任务的 `giver` 至少有一段对话**（否则任务无法在游戏内接取）。两者由 `main.lua` 的 `validate_content()` 在 boot 时调用，issues 逐条 `log.warn`。
- **整合**：`main.lua` 注册 `save_manager.register("quest", ...)`；`new_game` 调 `quest.reset`/`dialogue.reset`；`enter_playable_map` 调 `dialogue.ensure_target`/`reset`；`input.lua` 在 `Dialogue` 模式下优先分发 `Esc`（关闭）与 `"1"..option_limit()`（选择），非 Playing 分支不再吞掉对话输入。
- **修复（headless 运行发现）**：对话选项原以 `end = true` 表示结束，`end` 是 Lua 保留字，`data/dialogues/*.lua` 与 `dialogue.lua` 均无法编译（`<name> expected near 'end'`）。统一改名为 `finish`（含 schema 头注释），语义不变。
