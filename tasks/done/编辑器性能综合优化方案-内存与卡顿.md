## 0. 结论先行

| 症状 | 证据核查结论 | 是否真问题 |
|---|---|---|
| 内存泄漏 | 未发现无界增长的经典泄漏。缩略图、Undo、日志、profiler、预览会话、字体图集均有明确的有界化与清理路径，且项目切换时成批作废 | **证据不足**：暂无可复现的持续增长；先补测量再定性 |
| 占用内存大 | `M83-07` 已归因：11-06 的 3D 特性批（屏幕空间/阴影/天空/地形/水面/风场）抬高固定开销，峰值 +18.7%~+51.6%；峰值随档位线性、无持续增长成分，已判定为**特性增长而非泄漏**并重签基线 | **是真实开销**，来源已定位，优化项已登记未做 |
| 操作卡顿 | 每实例约 1.0 次分配（10k 档约 1 万次/帧）+ 58 次/帧固定脚手架；此外有多条同步回读路径与观测盲区 | **是真实开销**，部分已量化、部分待 profile |

**一句话**：这不是"从零修起"的局面。真正的工作是——**P0 补上内存归属测量与编辑器视口 profile 缺口 → P1 把"看起来像泄漏"的缓存有界化并给出可证伪的门 → P2 削掉已定位的每帧分配 → P3 去掉同步阻塞与补齐面板盲区**。

## 1. 现状：已有的性能基础设施（不要重复造轮子）

编辑器已经具备相当完整的性能治理底座，任何方案都不应绕过它们：

- **帧循环**：`eframe`(Wgpu) + `egui` + `egui_dock`，无自写 winit 循环。帧入口 `editor/src/main.rs:2873 draw_frame`，面板绘制集中在 `:3071`, 帧末采样 `:3119-3145`。
- **有界 profiler**：`editor/src/profiler.rs`，`SampleRing` 固定容量 240，span 环形缓冲 8192，`MAX_BARS=512`，预热后无分配。
- **性能分析面板**：`docs/68` 所述能力已接入（帧/CPU/GPU、渲染账本、调度系统、Chrome trace 三档、采集/重放/差分、内存分项、240 帧趋势）。**内存分项是当前已知缺口**（不含 CPU 侧解码缓冲与字体轮廓缓存）。
- **每帧提交预算**：缩略图 `MAX_THUMBNAIL_SUBMITS_PER_FRAME=32` / `MAX_THUMBNAIL_UPLOADS_PER_FRAME=64`（`resource_browser.rs:1114-1117`）。
- **缓存失效纪律**：所有重计算缓存带明确失效键（revision / (长度,mtime) / 代际），统一收敛入口 `actions/transaction.rs:16-83 on_document_changed`。
- **历史压缩**：`rustlua-editor-core/src/history.rs` 的字段级 `EditPatch` + `CommandStorage` 双形态，连续 Transform 步合并；`1000 次编辑 398 MB → 216 KB`（`docs/60 §2`）。Undo 上限 `DEFAULT_MAX_ENTRIES=200`（`services.rs:320`）。
- **文件监视**：轮询式（非 OS 通知），元数据扫描 + diff 合并 + `WatchHandle::cancel/drop` 退出，`rustlua-editor-core/src/file_watcher.rs`。
- **质量门**：`verify.ps1` 含编辑器性能基线与 p95 毫秒预算门；`compare-baseline.ps1` 执行几何量 any-change 红线与 p95 +5% / p99 +10% / 内存 +10% 红线（`docs/70 §3.4`）。

## 2. 症状一：内存泄漏 —— 核查结论与残余风险

### 2.1 已确认完备的清理机制（逐条附证据）

| 资源 | 清理方式 | 证据位置 |
|---|---|---|
| 缩略图 `HashMap<String, TextureHandle>` | 项目切换 `thumbnails.clear()`；单资源删除 `thumbnails.remove()` | `import.rs:123`、`delete_guard.rs:295-305`、`resource_browser.rs:723-741` |
| 缩略图后台线程 | `Sender` drop → `recv()` 返回 Err → 线程自然退出 | `resource_browser.rs:1121-1129` |
| 缩略图请求集合 | 代际 `generation` 自增 + `requested.clear()` 丢弃旧结果 | `resource_browser.rs` `ThumbnailWorker::clear` |
| Undo 栈 | `enforce_undo_limit(200)` 每次编辑后执行 | `services.rs:383`、`history.rs:309` |
| 日志缓冲 | `LogSink::new(500)` 固定容量 | `main.rs:162` |
| profiler 采样/span | 固定容量环形缓冲 | `profiler.rs:20,203-218` |
| 预览会话纹理 | `impl Drop for PreviewSession` + `drop_managed_texture()` | `preview_session.rs:1055,1253` |
| Scene View 原生纹理 | `on_exit` + `release_scene_view_textures()` | `main.rs:2795-2801`、`render.rs:826` |
| 字体图集 | `Arc<Mutex<FontAtlas>>` 复用，项目切换清空 | `main.rs:610-620`、`import.rs:152-160` |
| 跨面板 Undo 账本 | `clear_undo_ledger()` 项目切换作废 | `undo_ledger.rs:304-306`、`import.rs:139` |
| 面板临时状态 | 项目切换成批 `clear()`（预览/源码/模型/导入草稿/断链/结构差异/徽标/搜索索引等） | `import.rs:125-137` |

**结论**：`EditorApp` 是单一巨型结构体（约 530 行字段，`main.rs:253-785`），且**没有实现 `Drop`**（`main.rs:2795-2801` 注释明确），归还在 `on_exit` 完成。这是有意取舍（进程退出时 OS 回收全部资源），不构成运行期泄漏，但意味着**关窗路径以外没有统一的资源归还钩子**——若有面板在会话中反复创建 GPU 纹理而不自行释放，只能靠各自的内部逻辑兜底。

### 2.2 残余风险点（假设，未证实；需在 P0/P1 用测量证伪）

这些是"如果…则…"的候选，**不是已确认的泄漏**。列出是为了让 P0 的测量有明确目标：

1. **UI Studio 画布纹理 `canvas_textures`**：`undo_ledger.rs:193-227` 在撤销后 `clear()`；正常编辑路径是否也有无界增长，未逐路径核对。
2. **`ctx.load_texture("thumb", ...)`**：每次缩略图更新都新建 `TextureHandle`，靠 `thumbnails.insert(key, handle)` 覆盖。`egui` 的 `TextureHandle` 基于 `Arc`，旧 handle drop 时释放纹理槽——理论上闭环，但 `thumbnail_cache_entries` gauge（`main.rs:2661`）当前无告警阈值，长期会话是否稳定无证据。
3. **`crash` 事件缓冲 / 后台任务结果**：需确认有界（profiler 与日志已确认，其余未逐一核对）。
4. **内存分项盲区**：`docs/68 §12` 明确面板内存分项**不含 CPU 侧资源解码缓冲与字体轮廓缓存**。这两块恰是"内存占用大"的常见来源，当前不可观测。

### 2.3 本症状的动作（并入 P0/P1）

- 建立五窗口内存账（启动峰值 / 稳定运行 / 场景切换 / 读档 / 退出），来源 `docs/66 §7.3`，当前**尚未建立**。
- 为 `thumbnail_cache_entries`、`canvas_textures` 长度加 gauge + 软阈值提示，让泄漏若发生可见。
- 补齐内存分项的 CPU 侧解码缓冲与字体轮廓缓存统计（或至少明确标注为估算并给出上界）。

## 3. 症状二：内存占用大 —— 已归因，优化项已登记未做

### 3.1 归因结论（来自 `tasks/plan/M83-07`，2026-11-16）

CI `WP0 benchmarks and semantic goldens` 曾因 `cpu_peak_bytes` 超 10% 红线而红。经干净 worktree 逐提交测量：

| 提交 | 日期 | peak(100) | peak(10000) |
|---|---|---|---|
| 本地基线快照 | 2026-11-02 | 386,467 | 5,903,771 |
| `ccea3429`（11-06 批前） | 11-06 | 486,375 | 5,903,955 |
| `7ee9a5d0`（11-06 批中） | 11-06 | **709,779** | 6,179,911 |
| `88d40478`~`44a27bf3` | 11-15/16 | 714,390 | 6,574,666 |

- 主体跳变（+45% 峰值、+68 次/帧分配）发生在 11-06 的 3D 特性批；三档同样多约 72 次/帧 ⇒ **固定每帧路径**，非数据规模放大。
- 峰值随档位线性、无持续增长成分 ⇒ **不是内存泄漏**，是特性增长。
- 已重签 `metrics/baselines/wp0-3d-stress.json`，几何量逐字段核对一致，`checks=12 regressions=0`。

### 3.2 已定位的分配结构（M83-07 §五-A/B，逐阶段分配计数）

`--profile` 的 `phase_allocs.vertices/extract/render` 读数（release，`--cycles 30`，每帧均值）：

| mesh | 总/帧 | vertices | extract | render |
|---|---|---|---|---|
| 100 | 629.4 | 125 | 206 | 295 |
| 1000 | 4318.4 | 1108 | 2009 | 1198 |
| 10000 | 41145.4 | 10927 | 20013 | 10202 |

A/B 排除法结论：
- `WP0_CULL=0` / `WP0_NO_LIGHT=1` 不改变 render 分配 ⇒ **cull 与阴影链不是来源**；
- `WP0_INSTANCING=0` → render 从 295 跳到 1521、draw 从 2 到 200 ⇒ 基线是"固定开销"型；
- `WP0_NO_MESHES=1` → render 降到 58、draw=0 ⇒ 渲染段**固定脚手架 = 58 次/帧**。

修正模型：`render ≈ 58（固定脚手架）+ ≈1.0 × instances（约 1 万次/帧 @10k）`。

### 3.3 待做（M83-07 §五-C，"下一刀"）

要在 `render_into_texture` 内做临时分段计数（pass 装配 / 绘制收集 / 实例缓冲 / 提交），测完即删，区分"我们的脚手架"与"wgpu 每帧记账"：

1. **每实例 1.0 次分配**（10k 档约 1 万次/帧，绝对量大头）：大概率是实例缓冲/批次暂存里每实例一次 `String`/`Arc`/`Vec` 分配；改为 `Arc<str>` 共享或复用缓冲，10k 档直接减约 1 万次。
2. **58 次/帧固定脚手架**（100 档红线成因，与 11-06 的 +68 同量级）：把固定 pass 的每帧临时集合改为复用字段。

判据：**几何量逐字节不变 + alloc/帧 ≤560（100 档）后再重签基线**。

### 3.4 编辑器侧对应的内存大对象（与卡顿共用，见第 4 节）

`EditorApp` 直接持有 `wgpu::Device/Queue`、`RenderState`、多个 `Renderer`、`RuntimeScene`、`PreviewSession`、`DockState`、`FontAtlas`（`main.rs:556-620`）。这些是必要的常驻对象，问题不在"持有"而在"重建频率"——分辨率切换已有 `PreviewSession::resize` 复用（`docs/28 §6 E18`），但 Scene View 的离屏渲染器与预览会话仍各持一套（`docs/66 §6.5.1`，尚未统一）。

## 4. 症状三：操作卡顿 —— 已定位开销与观测盲区

### 4.1 已量化：每帧分配

第 3.2/3.3 节的每实例分配与固定脚手架，既是内存问题也是卡顿来源——高频 `Vec`/`String` 分配带来的 allocator 争用与 cache miss 会直接反映在 p95/p99。这是当前**最有证据的卡顿根因**。

### 4.2 候选同步阻塞点（需 P0 profile 确认，不预设为瓶颈）

| 候选 | 位置 | 说明 |
|---|---|---|
| Shader Graph 预览同步回读 | `editor/src/panels/shader_graph_preview.rs` | 离屏渲染后用 `device.poll(Wait)` + `pollster::block_on` 同步读回（`Cargo.toml:26-28` 将 `pollster` 提为普通依赖）。同场景 `scene_view/render.rs:601-624` 已改为 `Ready/Pending/Failed` 三态非阻塞回读，这里有可直接借鉴的范式 |
| Shader 预览 golden 对比同步回读 | `editor/examples/editor_preview_golden.rs` | 同类同步回读，但属测试样例，不在交互帧路径 |
| 文件监视轮询 | `resource_browser.rs:780-864`，默认 500ms (`main.rs:644`) | 后台线程执行，不进 UI 帧；`poll_file_watcher` 仅非阻塞 `try_take`，设计正确 |
| typed 场景提取 | `scene_view_3d_typed`（revision 缓存，`main.rs:687-695`） | 已按 revision 失效，稳态不重算 |

**纪律**：以上除"每帧分配"外，均需先在 P0 用 Chrome trace(Fine 档) 或帧捕获确认再动手。

### 4.3 观测盲区（`docs/68 §12`，明确待办）

1. **非 Play 的 3D Scene View 离屏渲染器未混进同一组读数**——当前性能面板只采 Play 预览。这正是编辑器最常见的操作场景。
2. **没有逐 draw 的帧调试器**：面板给聚合账本，"哪一个 draw 慢"仍需 RenderDoc / 帧捕获。
3. **CPU 细分不完整**：Lua `update()`、UI layout、render encode 在编辑器内仍是整段读数。
4. **trace 不是完整 flame**：`SpanRecord` 只有 `depth` 无父子 id，无缩放/平移/搜索；8192 环形缓冲长捕获丢最旧；每帧只取尾部 512 条。

## 6. 验证体系与红线（沿用现有，不新造）

- **基线更新纪律**：只来自干净工作树，显式、可评审、逐字段核对几何量（`metrics/README.md §5`）。

### 2026-11-19（三）：P3 —— Shader 预览的同步回读改异步，UI 线程不再等 GPU

**问题**：`ShaderPreview::render` 在 UI 线程上 `device.poll(Wait) + rx.recv()`，等 GPU 画完才返回。
Shader 面板播放时**每帧一次**、属性面板特效预览播放时**每帧一次**，缩略图画廊连续 27 张各一次。
这是本方案 §2 列出的"操作卡顿"里最直接的一条：UI 帧率被 GPU 往返时间锁死。

**改法**：把 `render` 拆成"提交"与"取回"两步。

| API | 语义 |
|---|---|
| `submit(time, intensity)` | 编码 + 提交 + `map_async`，**立即返回**（不 poll、不 recv） |
| `try_take()` | `poll(Wait{timeout:ZERO})` 推进一次事件循环（不等待）+ `try_recv`；**只在回调已到达时**才读像素，否则返回 `None` |
| `has_inflight()` | 是否有一帧在途 |
| `render_take_blocking()` | 阻塞取出（只给同步包装与测试用） |
| `render()` | `submit` + `render_take_blocking`，**语义与 P3 之前完全一致**（保留给测试/一次性场景） |
| `AssetShaderPreview::render_async()` | 属性面板的异步版；`render()` 仍是同步版 |

调用方全部改走异步：
- `shader_graph.rs`：先 `try_take` 刷新画面，再按需 `submit` 下一帧；有在途帧时 `request_repaint()`。
- `inspector/panel.rs`：`render_async`。

**关键设计决定**：
1. **同一时刻只允许一帧在途**。再提交会被拒（否则 readback buffer 会被映射两次）。
   这比排队更合适——排队只会让画面越来越滞后于参数。
2. **映射失败不 panic**：`map_async` 回调的结果先判，失败返回空 Vec，UI 保持旧帧。
3. 用 `PollType::Wait{timeout: ZERO}` 而不是 `Poll`：两者都不阻塞，但前者在软件适配器等后端
   更可靠地推进映射回调（`Poll` 在某些后端只在"已有待处理事件"时才跑）。
4. **不改** `readback.rs` 的 `copy_texture_to_cpu`：它是诊断/截图路径（`procedural` 预览按签名变化触发，
   不是每帧）。`timestamp.rs` 本来就是 `timeout: ZERO`，非阻塞。

#### 新增的两条门

- `async_pipeline_returns_the_same_pixels_as_the_blocking_one`：异步与同步路径像素**逐字节相同**；
  在途期间重复提交被拒；取回后状态清空。
- `submit_returns_without_waiting_for_the_gpu`：`submit` 耗时显著小于一次阻塞往返 —— 直接钉住"不等待"这个承诺。

异步化后有两个既有测试从"一帧即有纹理"退化为"需要多帧"：

第一次只改成"跑 8 帧"时**间歇性失败**——软件适配器（WARP）上 GPU 完成时间不可预测，
并发跑多个 GPU 测试时更慢。最终改成最多 64 帧并配确定性兜底（仍有在途帧就阻塞收掉再跑一帧）。
这不是被测逻辑的问题，而是"用帧数猜 GPU 完成时间"这件事本身不可靠——**测试要等状态，不要等时间**。

### 2026-11-19（四）：P3 —— 两套离屏回读逻辑合并为一份

上一轮把 Shader 预览的 UI 等待改成了异步，但**实现仍有两份**：`Renderer` 里一套（环形槽 + 原子完成标志，
完善）、`ShaderPreview` 里一套（mpsc 通道 + 手写 buffer，功能更弱）。这一轮合并。

**新增** `rustlua-gpu/src/renderer/async_readback.rs`：不依赖 `Renderer` 的通用 `AsyncReadback`。

| API | 用途 |
|---|---|
| `readback_frame(tex, w, h)` | 提交本次拷贝 + 排空旧结果（Scene View 离屏，一帧一次） |
| `submit_copy(tex, w, h)` | **只提交**、不排空（Shader 预览，提交与取回分开） |
| `take_ready()` | 只排空，返回 `ReadbackStatus`（含 `Failed`） |
| `take_blocking()` | 阻塞取出（只给同步包装/测试） |
| `has_inflight()` / `metrics()` / `clear()` | 状态与诊断 |

**接入**：
- `Renderer`：删掉 `readback_slots` + 5 个计数器 + `ReadbackSlot` 结构，改持一个 `AsyncReadback`；
  `readback_frame` / `readback_metrics` / `readback_pending` / `readback_in_flight` 全部改为一行委托。
  `readback.rs` 从"实现"退化成"门面 + 同步截图函数"。
- `ShaderPreview`：删掉自建 staging buffer、`bytes_per_row`、mpsc 通道、`PendingReadback`；
  改持 `AsyncReadback`，`submit` → `submit_copy`，`try_take` → `take_ready`。

**对外路径不变**：`ReadbackStatus` / `ReadbackMetrics` 仍从 `renderer::readback` 导出，
`rustlua_gpu::readback::{...}` 的 import 无需改。

**这次合并抓到一个真 bug（新引入的）**：把渲染 encoder 改成 `drop(encoder)` 后，
`queue.submit([encoder.finish()])` 被漏掉了 —— 编码器直接丢弃等于**整帧绘制从未提交**，
回读拿到的是全零像素。测试立刻红了（`animated_templates_change_with_time` 断言"时间影响输出"失败）。
教训：把代码块搬进 `drop(...)` 之前要想清楚它原本是不是"提交"语义。

**没有动的**：`copy_texture_to_cpu` / `read_scene_color_to_cpu` / `read_planar_reflection_to_cpu`
仍是同步阻塞——它们的名字就写着"to CPU"，调用方（golden 示例、HDR 测试）明确要同步语义。
改成异步反而破坏契约。这类"显式同步 API"与"每帧 UI 路径"是两回事，不该一刀切。

这是**正确性所需**（undo/redo 必须有前后快照），但可以用**增量快照**替代全量深拷贝：
`History::execute` 已经能算出 `FieldEdit::Changed { path, payload }`，也就是说
"这次编辑改了哪个实体的哪个组件"是已知的——只需存 `(entity, component, 旧值)`，
而不是整份 `SceneDocument`。

改动面：`CommandStorage::Snapshots` → 增加一种 `Patch` 变体；`undo`/`redo` 走应用/回滚补丁。

**这是目前发现的、对"操作卡顿"影响最大的一项**，比之前 P2 那几轮分配优化更直接

### 2026-11-19（八）：P0-4 —— 字段编辑走定向补丁，941 µs → 12.9 µs

P0-3 指出 941 µs/次字段编辑几乎全花在 undo 快照上。这一刀把它切掉。

**先纠正一个前提**：补丁通道（`CommandStorage::Patch`）**早就存在且默认开启**。
`execute` 里已经会把字段级编辑压成补丁——但那只是**省内存**，
`document.clone()` × 2 + 全文档 `==` + 全文档 diff **一点没省**。
所以真正要改的不是"加补丁"，而是"让字段编辑根本不进入那条通用路径"。

#### 改法

**新增** `CommandHistory::execute_component_field`：定向写入。

```rust

let before = document.clone();        // ~830 µs @10k
edit(document)?;
if *document == before { return Ok(false); }   // 全文档比较
let after = document.clone();         // ~830 µs @10k
…scene_field_patch(&before.scene, &after.scene)  // 全文档 diff

// 定向路径（O(1)）：
读一个组件串 → 写一个组件串 → 存一条 FieldChange::Component
```

调用方 `apply_component_field_edit` 本来就知道 `entity + component + payload`
（`FieldEdit::Changed` 给的），no-op 判定只需比较两个组件串。

**配套**：
- `FieldChange::component(...)` 构造器（`patch_history.rs`）。
- `CommandService::execute_component_field`：**必须在这个类型上再包一层**，
  否则绕过 `enforce_budget()`。

#### 差分门抓到两个真问题（都是我自己引入的）

1. **`revision` 差一格**。通用路径是"先执行 edit（含 `mark_dirty` → revision+1）再判 no-op"，
   所以 no-op 也会推进 revision。定向路径若在比较前直接返回就少一格。
   修法：no-op 时仍补一次 `mark_dirty()`（不写组件，只补修订号）。
2. **undo 栈突破上限**。`CommandService::execute` 里会 `enforce_budget()`，
   而我加到 `CommandHistory` 上的方法通过 `Deref` 也能调到、却**不带裁剪**。
   基线 `schema_field_edit_1k` 立刻红了（期望 200/800，实际 1000/0）。
   修法：`CommandService` 上加同名包装。

**这两条都是先写差分门、再让门把问题逼出来的**——如果只跑既有测试，它们都不会露头。

#### P1-3 内存分项：补上 CPU 侧矢量缓冲

`RendererResourceStats` 之前只统计 **GPU 侧**字节，于是"资源面板显示很小、进程 RSS 不小"的
缺口里有一部分无处归因。新增：

```rust
pub cpu_vector_cache_bytes: u64,   // vector_glyph_cache.capacity() + vector_segment_cache.capacity()
```

一路接到 `RuntimePerfSnapshot.cpu_vector_cache_bytes` → 性能面板新增一行「CPU 矢量缓冲」。
这两块是"上一帧矢量文字数据"的 CPU 副本（避免每帧重传），进的是进程 RSS，不是显存。

#### P1-3 收尾：CPU 解码缓冲

`AsyncLoader::cpu_buffered_bytes()` —— **已解码、但主线程还没 `drain_ready()` 取走**的产物
（贴图像素 + 网格顶点/索引）。这是"资源加载相关内存"里之前完全没被记到的那一份：
`RendererResourceStats` 的 `texture_bytes` / `mesh_bytes` 只算**已上传**的那部分。

接到 `async_cpu_buffered_bytes` → 面板「待上传解码缓冲」，并设了 32 MiB 的黄色阈值
（正常主线程每帧 drain，队列应该在几 MB 内；远超说明取走侧卡住或异步加载在堆积）。

**配套门** `cpu_buffered_bytes_tracks_the_ready_queue`：Sync 模式请求一张 2×2 PNG →
断言读数 = **16**（精确到像素字节）→ `drain_ready()` 之后归零。

断言具体数字而不是"大于 0"，是因为这个读数要显示在内存面板上：**恒为 0 的面板就是在骗人**，
只有钉住精确值才能证明它真的在跟着队列走。

#### P1-4 资源释放：落地并加门

**`Renderer::release_cached_resources() -> u64`**：释放全部**可重建**的派生物 ——
网格缓存、网格身份表、材质缓存、纹理/贴图、字体图集、自定义字体、矢量字形缓冲。

**有意不释放**（各有理由，写进注释了）：
- 管线缓存：重编要几百毫秒，且体积稳定不随场景增长；
- `vertex_buffer`：容量复用正是它的价值，清掉反而要重新增长；
- `readback` 槽：两个小 staging buffer，清掉会打断在途帧。

**`EditorApp::release_all_resources()`**：先归还 egui 原生纹理 ID（它们指向 `scene_texture`
绑定组，底层资源一回收就成了悬空句柄），再调渲染器释放。挂在 `NewScene` 命令上——
换文档正是旧场景派生物失效的时刻，状态栏会报出释放量。

#### 新增的门（P1-4）

`release_cached_resources_frees_caches_and_keeps_pixels_identical`：
渲染两帧建立缓存并取稳定像素 → 释放 → 断言网格计数归零、释放字节数 > 0 →
**再画一帧，像素与释放前逐字节相同**。

第二条断言是关键：清 `textures` 会打乱按索引引用的材质槽位，写错就是黑图。
只断言"计数归零"是不够的。

**实测**：`save_scene` **36.03 → 31.78 ms（-11.8%）**。

#### 剩余：`Scene::load` 回读校验 24 ms（**需要你决策**）

`atomic_write_scene` 写完临时文件后会**重新 `Scene::load` 一遍**再替换正式文件：

```rust
fs::write(&temp, scene.to_text().as_bytes())?;
// 替换正式文件前重新加载临时文件，确保落盘内容可被引擎解析。
if let Err(error) = Scene::load(&temp) { … }
```

单独量（新 example `perf_scene_save_cost`）：

| 实体数 | `to_text` | **`Scene::load` 回读** |
|---|---|---|
| 100 | 0.04 ms | 0.18 ms |
| 1,000 | 0.42 ms | 2.52 ms |
| 10,000 | 6.93 ms | **24.28 ms** |

**这就是 27 ms 写盘段的主体**（序列化 6.9 + 回读 24.3 ≈ 31，与实测吻合）。

它防的是**序列化器 bug**（写出引擎自己都读不回来的文件），不是 IO 错误（那由 `fs::write` 返回）。
删掉它能把保存压到 ~8 ms，但等于放弃"写坏前拦住"这道防线。

**我没有删。** 这是一个正确性权衡，不该由我在性能任务里单方面决定。

#### 决策：**保持现状**（用户 2026-11-19 选定方案 1）

理由：保存是**低频**操作（用户按 Ctrl+S，不是每帧），32 ms 与 8 ms 在人的感知上没有区别；
而它拦的是"序列化器写出了引擎自己都读不回来的文件"——那一步若不拦，好文件已被 rename 覆盖。

已评估但不采用的替代：
- **加 `--skip-save-verify` 开关**：给防线开了默认以外的口子，实践中一定会被打开；
- **内容哈希相同才跳过**：哈希要遍历整棵场景，省不下多少，还多一份状态要维护。

未来若保存真变成高频路径（自动保存 + 数十万实体），正确方向是**让序列化器自身可证明正确**
（round-trip property test 覆盖所有组件类型），而不是每次保存现场验一遍。

#### 顺着这个决定，发现了一处"没门看着"的防线

为了给这个决定写注释，我去确认"删掉回读校验会不会被测试抓到"。**结果发现抓不到。**

我原本以为 `invalid_scene_does_not_modify_original_or_clear_dirty`
（它把 `scene.version` 改成 999，断言报 `unsupported scene version`）是在验回读校验。
**实测把校验改成 `if false`，那条测试仍然是绿的。**

原因：`version=999` 早在 `save_to` 开头的 `scene.validate()`（`document.rs:167`）就被拒了，
根本走不到回读那一步。**回读校验当时没有任何测试在守。**

补救：与其造一个人工失配去"测"那道防线（那测的是夹具能造错，不是序列化器正确），
不如把它依赖的**前提**钉死。新增 `rustlua-scene` 的门
`escape_roundtrip_preserves_separators_and_multibyte_text`：

- 载荷含 Tab（本格式的分隔符）、换行（记录分隔符）、反斜杠（转义前缀本身）、中文、emoji；
- `to_text` → `from_text` 后场景必须逐字段相等；
- 另断言实体行里 Tab **只作为字段分隔符**出现，载荷里的 Tab 必须被转义——否则记录结构早就坏了。

**这条门验证过不是空转**：故意把 `push_escaped` 里的 Tab 分支改成原样输出，测试立刻变红。
