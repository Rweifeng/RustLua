# 任务：ECS 并行调度（先把 `World` 变成 `Send`，再谈并行）

- 任务 ID：M74-02
- 状态：**已收口（2026-10-21，P0 实测判"不做"）**——交付物是度量工具、读数与结论，P1–P4 按判据不开工
- 关联里程碑：M74（能力补齐批，见[差距分析](../../docs/62-成熟引擎差距分析.md) §6 P1）
- 创建日期：2026-10-19

## 目标

让"同一 stage 内互不冲突的系统"能在多核上并发执行，且**结果与串行逐字节相同**、
随时可退回串行。这句话里真正的成本在括号外：今天 `World` 在类型层面就是 `!Send`，
所以先得动存储层的内部可变性设计——这正是[差距分析](../../docs/62-成熟引擎差距分析.md) §6
把它估成 3–4 周（而不是"加个 rayon"）的原因。

## 现状（实测）

| 事实 | 位置 / 读数 |
|---|---|
| 系统是 `System<C> { name, stage, dependencies, callback: Box<dyn FnMut(&mut C, f32)> }`；文档明写 **"runtime schedules on a single thread, callbacks are not required to be `Send`"**（因为脚本系统捕获非 `Send` 的 Lua 状态） | `rustlua-ecs/src/scheduler.rs` 模块头 + `System` |
| 帧序是固定的 **10 级 stage**（`Input → Script → Sync → Physics → Writeback → Simulation → Animation → Spatial → Transform → Render`，`rank()` 0..9），stage 内串行 | 同上 `ScheduleStage` |
| `World` 的组件存储是 `HashMap<TypeId, Box<dyn ComponentStorage>>`，而 `ComponentStorage: Any`（**没有** `Send`/`Sync` 约束） | `rustlua-ecs/src/world.rs:26-32` |
| `TypedStorage<T>` 内嵌 `order: RefCell<Vec<EntityId>>` + `order_dirty: Cell<bool>`（惰性重建有序索引）——这两个 `!Sync` 字段是并行的直接障碍 | `world.rs:60-64` |
| 今天真正在跑的并行只有 `rustlua-infra::par`：**切片**分块、确定性、可回滚；`MAX_THREADS = 8`、`MIN_PARALLEL_ITEMS = 20_000`；实测 10k 落在噪声内、50k −21%、100k −26% | `rustlua-infra/src/par.rs` |
| 它的两个消费者是渲染/模拟侧的批处理（`sprite_batch.rs`、`particle.rs::step_with_parallelism`），**不经过 `World`** | 同上 |
| 每帧系统数：`host/schedule.rs` 注册 18 处（全仓 24 处 `System::new`/`add_system` 调用点） | `engine/src/host/schedule.rs` |
| 帧成本的大头不在系统分发：WP0 实测 10k sprite 的 CPU 提取 11.5 ms p50（WP6 之后每帧分配已与精灵数几乎无关），瓶颈在 GPU 提交与 Lua；本任务 2026-10-21 复测整帧 10k 2.1 ms / 50k 10.9 ms，调度合计只占 16%（见 §实现记录 读数） | [docs/53](../../docs/53-WP0增量场景帧基准与每帧分配.md) §3.1、§3.11 |

## 判断：这件事的"收益"必须先量，不能照抄 Unity DOTS

- 24 个系统、stage 内串行 ⇒ 调度开销本身（微秒级）**不是**瓶颈；瓶颈是 stage 内**某几个**
  系统的实际工作量（提取、物理、粒子）。
- 而"某几个系统很慢"这件事，用 `infra::par` 在系统**内部**切片并行就能吃掉大部分收益，
  完全不用动 `World` 的 `Send`（今天的做法）。
- 所以并行**调度**真正换到的是"多个中等成本系统之间的重叠"。在 60 fps 的 2D 玩法里，
  这笔收益只有在系统数上到几十、且单系统都有毫秒级成本时才显现。

## 风险与回滚

- **`World: Send` 会波及所有宿主**：`RuntimeScene` 持有 `Rc<RefCell<Lua>>`（不在 `World` 里），
  但 `ScriptState`/组件里的非 `Send` 值（`Rc`、`RefCell`）会逐点暴露——P1 的验收就是"把这些
  一个个抖出来"，工作量不确定，这是本任务估时 1 周的底气来源也是风险来源。
- **脚本系统无法并行**（捕获 Lua 状态）：`Script` stage 永远串行，别在文档里写成"全面并行"。
- **确定性**：任何求和顺序变化都会让浮点结果不同 ⇒ 与 `par` 同口径按块切分、块内串行、
  块间不归约（或归约顺序固定），并对拍逐字节相等。
- **回滚档**：`set_parallelism(SEQUENTIAL)` 一行退回；P1 的存储层改造**不**能靠开关回滚，
  所以它必须单独一批提交、单独验收。

## 明确不做

- 任务图（task graph）+ 跨 stage 重排：固定 10 级 stage 是 WP7 的裁定，并行不改变帧序。
- 作业系统（fiber/工作窃取）：`infra::par` 的"分块 + 固定线程数"已经够用，不引入新运行时。
- 把 Lua 也并行：Lua 状态是单线程的，跨线程跑脚本是另一个量级的工程。

## 实现记录

### 2026-10-21 · P0 度量闸门：实测结论 = **不做**（P1–P4 不开工）

**做了什么（P0 的三件产物）**

1. **`engine/src/host/frame_profile.rs`（新）**：`FrameProfile` 跨帧累加器。
   - 每系统 p50/p95/p99（nearest-rank，与 `wp0_scene_frame::summarize_with` 同一条公式）、
     每 stage 合计、整帧墙钟（分母由调用方传入：调度器只知道自己那一段，拿它当分母会把占比算大几倍）。
   - **两套 stage 口径**：`share_pct`（全量）与 `parallel_share_pct`（去掉独占 stage）。
     独占清单由 `set_exclusive_stages` 显式给；P0 只标 `Script`，理由是本文件 §风险 已写明
     "脚本系统无法并行：`Script` stage 永远串行"。闸门判 `parallel_share_pct` 的最大值，
     全量口径照样写进报告作对照——只报一个数，下游没法复核"为什么 76% 的帧却判不做"。
   - 每个 stage 还给 `gain_ceiling_pct = (stage 合计 − 关键路径) / 帧`：并行调度的**理论上限**。
   - 输出：`m74-frame-profile-v1` JSON + 单行摘要（`verdict=skip|proceed`）。
   - 8 条单测：分位数口径、stage 分组与占帧比分母、20% 边界（严格 `<`）、多帧取分位数
     而非单帧、独占 stage 剔除、全独占为 0、空档 JSON 合法、JSON 与单行同一组读数。
2. **`game --frame-profile <file>`**：交互宿主每帧把 `last_schedule_report()` 喂给同一个累加器
   （整帧墙钟从 `redraw` 起算，含固定步 + 提取 + 提交），退出时落盘 JSON 并打印单行摘要。
   未开时 `Option::None`，每帧一次分支，零成本。`--trace-loads` 同一出口形态。
3. **`engine/examples/m74_ecs_frame_profile.rs`（新）**：无窗口可复现度量。帧的定义与
   `wp0_scene_frame` 一致（`run_script_steps` + `vertices` + `scene_3d`，含析构）。
   四个目标：`jhyt_title`（真实工程标题屏）、`jhyt_manor`（`BtnStart` 进山庄后的玩法主场景）、
   `sprite_10000` / `sprite_50000`（任务点名的 50k 档 + 对照档，经完整 `RuntimeScene` 帧路径，
   不是绕过 `World` 的 `sprite_stress`）。台账写入 `metrics/baselines/m74-frame-profile.json`。

**读数（2026-10-21，Release，本机 12 逻辑核；每档 300 帧 + 20 帧预热）**

| 目标 | 整帧 p50 | 调度合计 p50 | 全量最慢 stage | 可并行最慢 stage | 并行收益上限 |
|---|---|---|---|---|---|
| `jhyt_title` | 118.7 µs | 35.4 µs | Script **24.18%** | Physics **2.36%** | **1.18%** |
| `jhyt_manor` | 1,609.8 µs | 1,314.8 µs | Script **76.05%** | Physics **4.47%** | **0.24%** |
| `sprite_10000` | 2,117.1 µs | 346.7 µs | Spatial **11.96%** | Spatial **11.96%** | **0.00%** |
| `sprite_50000` | 10,872.5 µs | 1,750.4 µs | Spatial **11.56%** | Spatial **11.56%** | **0.00%** |

同一测量逻辑隔一轮复跑（`display_path` 修正前后各一次构建）：四档的闸门读数
2.28% / 4.37% / 10.77% / 11.13%，与上表同量级且都远低于 20%；差异来自机器噪声，不改变结论。

**判断：不做**

- 判据原文是"最慢 stage 的串行系统合计 < 帧的 20% ⇒ 不做"。按**可并行**口径，四档的最大值是
  `sprite_10000` 的 **11.96%**，低于 20%，结论成立。
- 全量口径在 `jhyt_manor` 上是 **76.05%**，但这 76% 全部是 `Script`（`lua_update` + 每实体脚本），
  而脚本系统在任务书 §风险 里就写明无法并行。把它算进"并行调度能吃到多少"，会得出与任务书
  自身分析相反的结论——所以报告同时留了两个数，判据用可并行口径。
- 即便只看可并行 stage，收益上限也很低：`jhyt_manor` 的 Physics 4.47% 里，
  `physics2d_step` 一条就占 62 µs（stage 合计 72 µs），并行上限 0.24%；
  标题屏的 1.18% 对应整帧只有 119 µs。**跨系统的重叠收益不足 1.2%**。
- 50k 档最慢 stage 是 `Spatial`（`spatial_propagate` 1,257 µs，占 11.56%），但它是**单个**系统：
  跨系统并行调度没有可重叠对象，收益上限 0%。真正的成本在调度之外——整帧 10.87 ms 里
  9.12 ms 是提取（`vertices`/`scene_3d`），与 `docs/53` §3.10 的"收集阶段才是大头"一致。
- 所以：并行调度换不到可测收益，**`World: Send` 化（1 周）+ 访问集（1 周）+ 并行执行（1 周）
  全部不开工**。要动的是单系统内部切片（`infra::par`）与提取阶段，那两件已有各自的量尺。
