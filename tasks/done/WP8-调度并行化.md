# 任务：WP8 调度并行化（数据并行已落地，系统级并行待裁定）

对应 [docs/40](../../docs/40-引擎全面重构计划.md) §3 WP8。状态：**执行器 + 合批并行完成；
系统回调级并行经核实不适用于当前架构，已上报为范围裁定项。**

## 1. 做了什么

### 1.1 `core/par.rs`：确定性数据并行执行器

`map_chunks_in_place(items, parallelism, output, worker)`：按同样块长切开输入与输出，
`items.chunks` 与 `output.chunks_mut` 顺序配对后逐块并行就地写入。

四条设计约束（都有测试）：

1. **就地写，不做二次拼接**。第一版是"每块返回 `Vec<O>` 再按序拼接"，实测（10k 精灵）
   无论起 2 个还是 8 个线程都稳定慢 ~700 µs，**且与线程数无关**——说明代价来自每块各自的
   分配与那份额外的整份拷贝，不是线程创建。改成 `chunks_mut` 就地写后该开销消失，并且
   全程安全代码（`chunks_mut` 天然给出互不重叠的 `&mut`）。
2. **确定性**：分块只改变"在哪个线程算"。串行与并行的输出逐字节相同，失败时报告的仍是
   **排序序中第一个**非法条目（取最小失败位置，否则错误信息会随调度变化）。
3. **可回滚**：`Parallelism::SEQUENTIAL` 等价于串行实现，不必改调用方代码。
4. **退化即串行**：线程创建失败（`spawn_scoped` 返回 `Err`）、规模低于阈值、只有一核时
   静默走串行，不 panic、不改变输出。

### 1.2 `SpriteBatch::build_with_parallelism`

只并行"每精灵顶点生成"这一段：它读一个只读条目、写自己的 6 个顶点，没有跨精灵状态。
排序、错误分类与 draw range 合并仍在调用线程上按原顺序做。`SpriteBatch::build` 保持
= `SEQUENTIAL`，因此旧行为就是默认值。

宿主侧：`RuntimeScene::set_sprite_parallelism(...)`，默认 `Parallelism::detected()`（8 线程
上限 + 规模阈值）。

## 2. 实测（Release，`sprite_stress` 的 `parallel_ab`）

同一批次、**同一进程内交替采样**（先串行后并行各一次，循环 N 轮），因此能抵消机器负载漂移。
多轮实测（本轮采样）：

| 精灵数 | 串行 build | 并行 build | 结果 |
|---:|---:|---:|---|
| 10,000 | ~1,210 µs | 1,082 µs（4 线程） | 落在噪声内，**不划算** |
| 50,000 | ~5,930 µs | 4,698 µs（8 线程） | **−21%** |
| 100,000 | ~13,200 µs | 9,727 µs（8 线程） | **−26%** |

两档并行/串行的**字节指纹相同**（`parallel_identical=true`，FNV-1a over 顶点与 draw range），
这是硬契约。

**阈值因此定为 `MIN_PARALLEL_ITEMS = 20_000`**，取在两档之间：小场景完全不受影响（走原有
串行路径，行为与 WP8 之前逐字节一致），重场景才启用。这正是 WP8 风险条要求的"默认单线程、
按白名单启用"。

### 端到端帧阶梯不可用于归因（如实记录）

`wp0_scene_frame --sprite-parallelism off|auto` 的跨进程对比**噪声过大**：1 万精灵档在
两种模式下都会走**同一条串行路径**（低于阈值），两次运行却相差 **−24%**。这等于一个天然
阴性对照，直接说明该量尺分辨不出这个量级的效果。因此本轮**不主张端到端帧时间收益**，
只主张上表的 build 级 A/B（同进程交替采样）。

## 3. 系统回调级并行：不适用于当前架构（待裁定）

WP8 原文要求"先为系统增加 Read/Write 组件与资源声明；冲突系统自动串行；把 Transform
propagation、动画采样、剔除、资源解码与 typed compile 并行"。

核实结果：`core/scheduler.rs` 的系统回调类型是

```rust
type SystemCallback<C> = Box<dyn FnMut(&mut C, f32) -> Result<(), SystemError> + 'static>;
```

**刻意没有 `Send` 约束**（注释写明原因：脚本驱动的系统捕获不可跨线程的 Lua 状态）。因此：

- 任何系统都无法与另一个系统并发执行——这不是调度器缺能力，而是回调签名不允许；
- 加一套"读写集声明 + 冲突自动串行"的规划器，产出的计划**没有任何执行器能消费**（所有系统
  必然串行），属于只增加复杂度不产生收益的改动；
- 真要系统级并行，就得把回调改成 `Send` 并配命令缓冲合并，那会波及全部 Lua 驱动系统，
  与"Lua 保持主线程"的要求正面冲突。

**本轮采纳的替代路径**：并行放在系统**内部**的纯数据子任务上（§1），这是同一目标下
当前架构唯一可落地、可测量、可回滚的形式。

## 4. 门与回滚

- `verify.ps1 -Benchmarks` 校验 `sprite_stress` 报告的 `parallel_ab`：`used == true`、
  `identical == true`（字节指纹相同）、两侧 p50 > 0、并行不得慢于串行 2 倍以上。
  **刻意不断言"并行更快"**——收益随规模变化，写成门会在负载波动时假红。
- 回滚：`RuntimeScene::set_sprite_parallelism(Parallelism::SEQUENTIAL)`，
  或基准 `--sprite-parallelism off`。两者都不改调用方代码，输出不变。
