## 设计要点

1. **树分两层画**：trunk 在地面层（不遮人）、canopy 在 `foreground`（遮人）。
   现在 `manor_tree.png` 是一整张，要拆。
2. 屋檐同理：墙不遮人、檐口遮人。
3. 阴影：所有 actor 脚下 1 个椭圆贴片；所有建筑右下 1 块投影。
   **光向必须全局唯一**，一批生成器出图，不许各画各的。
   → 实测修正（C 段）：角色那条**不是贴片**，脚下椭圆继续烘在帧里；建筑/树/道具那 16 条是新贴片。
4. Y 排序容差要显式定义（世界 +y 朝上，遮挡是 y 越小越靠前——
   这条口径在跨宿主绘制顺序门里踩过"写反了两边门都绿"的坑，见 `project-cross-host-draw-order-verification`）。
   → 落成数（C 段）：容差 = `depth.lua` 的 `STEP` 本身（2 单位），三条正文与"哪条是推断"写在
   `scripts/world/depth.lua` 头部，门 §⑧ 钉两侧（Δy=1 不许翻、Δy=2 必须翻）。
5. 被遮的地面用 tint 压暗，**不加新图层**。
   → 实测撤销（C 段）：Tilemap 恒在一切 sprite 之前画，压暗只从遮断物的透明缝隙漏出来；
   与投影贴片的覆盖交集实测 0 格，两条通道管的是不相交的两块地。理由与读数见 C 段。

## 风险

- **改绘制顺序会打断黄金表**：`jhyt_m63`（门面）、`jhyt_m65`（商店 116 行黄金表）
  以及 `67` 的门面黄金对账门都钉死了绘制序。前景层一加，覆盖判定（cover）会变。
  → 先跑一次看是否真红，红了按"为什么应当变"重刷。
- 前景压人若容差没定好，玩家会"凭空消失"在树后。要留一个可量判据（比如被遮面积 ≤40%）。
- 微信/web 宿主的绘制顺序与原生不同口径（原生读 `mesh.draws` 下标、微信读假 ctx 的 `drawImage` 序列），
  跨宿主遮挡门要两侧都跑。

## 验收方式

- `jhyt_m72_foreground_occlusion`：玩家走到树冠下，断言 canopy 的绘制下标**大于**玩家
  （即后画、盖在上面）。
- **反面对照**：把 canopy 的 `sorting_layer` 改回 `world`，门必须红。
- 阴影方向门：扫全图所有阴影贴片，断言偏移向量落在右下象限且**角度方差 ≤ 一个阈值**
  （证明"全局单一光向"这条真的被守住了，而不是靠肉眼）。
  → 口径收紧（C 段）：阈值给成 **恰好 0**（`2r+1` 的奇数尺寸让它是恒等式）；并且要说清这条
  不是独立守卫——写反的阴影会先在"落点复算"那条红，见 C 段末尾那段。
- **反面对照**：故意把一处阴影改成左下，门必须红。
- 跨宿主：原生 + 微信两侧各取一次绘制序列（口径见 `67` 与项目记忆）。
- 登记进 `verify.ps1` MVP 清单。

**两条改变了设计的实测**

1. 角色脚底那片影子**已经在盘上**（`player_male/static_s.png` 第 60–63 行 `#1f2328` a=70，
   64×64 帧里不透明像素一直铺到第 63 行）。所以角色不新开贴片实体：贴片要么逐帧配偏移
   （多一份会漂移的数据），要么固定偏移（走起来脱脚）；烘在帧里的椭圆天然跟脚、三个宿主
   同幅生效、零运行期开销。
2. 建筑/树/道具**一个半透明像素都没有**（manor_house 224×224、manor_tree 64×88、
   manor_well/gate/bamboo 实测全 0/255）⇒ 投影必须是**新贴片**，而贴片要保持 alpha 只有
   0/255（docs/57 §1.3 软边门）才能不新开"半透明例外"的口子——透明度走 `sprite tint 的 a`
   （`sprite_batch.rs` 的 `tint_is_opaque` 会把 tint 半透明的 quad 路由到混合通道）。

**接触阴影 ≠ 投影，门两码**（这条是量出来的，不是美学偏好）：脚下椭圆在任何光向下同形，
本身不携带光源信息，所以光向角度方差门**只采投影贴片的样本**；对脚下阴影只断言
"不往左上跑"（`shift ≥ 0`）。而且 64×64 帧底部只剩到第 63 行，投影本来占 60–63 行，
再往下挪就出框——所以 `actor_shadow` 取 `shift_x=2 / shift_rows=0`（纯右偏），
不是 sun 的 45°。若门硬要它等于光向角度，会把一个正确的画法判成错误。

**reach=0.12 的口径**：正房 224 单位高 → 偏移向量长 ≈26.9 单位（x/y 各 19.0，≈0.8 瓦格）。
**这条是推断**（相机接近俯视，影子过长会读成"房子在斜面上"；目测星露谷建筑影子 ≈0.5–1 格），
docs/57 回写时要标注，等实机参考再校。

**一条推翻本包 A 段措辞的实测**：`solid` **是**物理的。A 段与 `lighting.lua` 都写着"本项目
没把 solid 做成碰撞体（场景里唯一的 Collider 是玩家自己）"，凭的是只 grep 场景文件——而
`scene_spawn.rs:555` 的 `solid_cell_colliders` 会给**每个实心格**在 tilemap 实体的静态刚体上
挂一个 cuboid，运行期 `tilemap.set_solid` 还会 `refresh_tilemap_physics` 立刻重建。逐格探针
（920 发 r=4 圆）把这件事量成了读数：360/360 实心格恰好命中 GroundMap、560 空格 0 命中。
连带三处按事实改写：① §④ 末尾那条 teleport 落位断言**从此有了牙**（门按几何判的可达点，
物理求解器也必须让玩家待得住；门用"碰到格边即挡"，比物理只禁穿透更严 ⇒ 门的可达集是物理
允许位置的子集，方向安全）；② "全图理论上界 1.000"那列重新解释为"扫描没漏看"的证据而不是
"玩家真能穿墙"；③ `jhyt_m72_scatter_decor` §⑤ 里那句"命中别物 16 次（地表 tilemap 的实心格）"
本来是散文推断，现在按实体 id 认：16/16 全是 GroundMap，**认不出来源的必须为 0** 成了新断言
（helper `three_numbers` 泛化成 `numbers<const N>`）。

**0.40 那一档为什么没守住，以及为什么不是靠放宽守住的**：本计划"风险"一节写的判据是
"被遮面积 ≤40%"。第一次实现（树冠切顶 57 行）量出来最深 **0.861** —— 40% 在那档几何上做不到：
树冠块比角色主体（44 行不透明）还高，而树南缘那一格按 `solid` 是可走的，玩家必然能走到
"整人被树冠吞掉"的位置。**没有去放宽上界**（那等于把守卫改成迎合美术），而是改美术切点：
三档渲染对比的读法是 57 行 = 人没了一半（过了）、26 行 = 读成"人站在树前面"（**它最深处只有
0.357，数字上过得了 0.40，画面却是错读**——这正是"靠放宽数字来装没事"会奖励的结果）、
**40 行 = 露腿而头在树后**（对的一档），
而 40 行的最深处是 0.604（C 段重烘角色条带后的当前值，当时记的是 0.602）⇒ 上界取 0.65
（0.604 + ≈7.6% 余量）。要真守住 0.40，得把树干从 88
加长到 116 并整片树冠进前景，那要改 `manor_tree.png` 与三张生成器表、还要重存两张引用整图的
场景，代价与收益不成比例。**这条上界钉的是美术切点，不是运行期的宽容度。**

`0.861 / 0.357 / 0.602` 三个数记在角色条带重烘（C-1）之前，之后只复测了 40 行那一档（0.604）。
三档之间的相对结论——57 过、26 错读、40 对——差的量级是 0.2 以上，不随 0.00x 的漂移改变，
所以没有回去重跑那两档；要动切点时按上面「门读数」那条命令现测。
