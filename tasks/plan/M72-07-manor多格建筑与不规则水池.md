## 设计要点

1. **多格视觉 + 落地碰撞 + 门口留空**（本包对 `53` §3.5 第 5 条的建筑侧展开，
   与计划初稿"碰撞只占入口那一格"不同，理由见下）：
   - **solid = 本体（`world` 层那件）∪ 同名拆层屋顶件的"不透明像素紧包围盒"覆盖的格
     − 门口格**（同源于 `tools/building_kit.py`，读数由它现算，不是手抄表）；
   - 门口格必须可站、可走到（BFS 从出生点可达）。
   为什么不是"只留一格"：层秩是 `background −2 / world −1 / default 0 / actor +1 /
   foreground +2 / ui +3`，actor 恒在 world 之后 ⇒ **`world` 层的墙永远遮不住站在它后面的人**
   （玩家 key ≈ 1000−y/2，墙 = −1000）。所以本体 quad 覆盖的每一格都必须实心，否则玩家
   会走进墙里并被画在墙前面。
   **屋顶那几格反过来也必须实心**（这条是本包对计划初稿的口径修正，2026-10-09 裁定）：
   拆层只是把一张图按行切成两块、往上多挂一条遮带，**它的占地和整张原图一模一样**——
   正房的屋顶在图上就是压在墙身之上的同一座房子，留空等于"北半间能走进去"。
   M72-06 的前景遮断件负责的是**画面上压住人**，从来不负责"允许进入"；两者是正交的。
   这条按"并集"落地后还白送一条可断言的性质：**拆层前后占地逐格相同**（见 §验收方式），
   所以 #4 分件不会动摇 #2/#5 的碰撞读数。
   树才是"单格根碰撞"（本体只有干那一格落地）——`53` §3.5 那条的主语是
   "树/大型物件"，本包把它落到建筑上时按上面的展开执行，并在此登记这条口径修正。
2. 屋顶/墙/门窗分件，别合成一张死图（分件才能复用、才能换季、才能做 tier 升级）。
   M72-06 已经把正房拆成 body/roof 两件，本包把这套拆法推广到柴房与五座可建造建筑。
3. 建筑投影走 M72-06 的统一光向通道，不在建筑贴图里烤死阴影（否则换季/换光向要重画）。
   **实测这条已经成立**：16 件 `cast_shadow` 里 8 座建筑 + 2 件施工全在册，本包不重做，
   只在门里断言"每栋建筑有贴片且贴片走 lighting 的偏移公式"。
4. 左上光源在建筑侧的落点（`53` §3.5 第 4 条）：屋顶**左亮右暗**一条明度梯度、
   屋檐在墙顶压出一条暗带。现状是左右对称、无梯度——这是目验最大的差距。
5. 水池：岸线用 M72-04 的水族 autotile + M72-05 的石头/睡莲装饰压边，
   中心深度渐变走 per-tile tint。**顺带去掉 `gen_manor_scene.py:195-198` 给
   HOUSE/SHED/POND 整框刷 DIRT 的写法**——它在图上读成"棕色方盒套蓝方盒"，
   而且 DIRT 是 `farm.lua` 的"可开垦"判据，等于在房子底下留了一片能种地的地。
6. 生成器与盘上必须重新对齐：本包所有数据改动同时改 `gen_manor_scene.py`（从零生成）
   与一个就地改盘的工具（沿用 M72-06 `set_foreground_occluders.py` 的"生成器 import 它、
   两边共用同一份表"的做法），门读盘上场景并复算同一条表。

## 实现记录

**口径先于画面**（2026-10-09 两条裁定：solid = 本体∪屋顶并集；范围 = 分件 + 光向渐变 + 水池 + 门 + 回写）。
本包的产出不是一个更好看的山庄，而是**一条能抄的判据**：每一格 `solid` 都必须有可视依据。

### A. 判据落成一个工具 + 一门（两份独立实现）

- 新增 `tools/building_kit.py`：`visual_and_solid()` 按**不透明像素紧包围盒**算占地（不是 quad 框），
  建筑并上同名拆层件、减 `OPENINGS`；prop 走 `entity_meta cell` 单格根碰撞，`ManorFence`/`ManorRack`
  两件例外走框（它们本体就横着占两格）；`TILE_NATIVE_SOLID=(WALL,WATER)` 那两族天然实心。
  `--check` 已进 verify 的 Python 段。
- 新增门 `engine/crates/game/examples/jhyt_m72_building_footprint.rs` 五段，**不 import Python**，
  自己解 `.scene` 文本、自己解 PNG 的 alpha：
  - ① 逐格复算 vs 盘上 `solid`：地表天然实心 187 格 + sprite 依据 183 格 ⇒ 应实心 **359** 格 == 盘上
    359 格，缺 0 / 悬空 0。10 栋建筑的读数逐栋打印（视觉格数 / 实心格数 / 门洞 / 拆层件）。
  - ② 拆层不变量：7 栋拆层件在场、每栋本体∪屋顶 ≥4 格，**"整图算的格集 == 本体∪屋顶"逐格相同**
    （最大一栋 49 格）。
  - ③ 门洞三条反查：`(16,1)(16,2)` 在 ManorGate 视觉框内、盘上已挖开、每列最低格实测不透明占比
    **0.16** ≤ 0.35、从出生点 `(16,3)` 4 邻域 BFS 可达（可达集 550 格）。
  - ④ 投影贴片：9 栋够格建筑各有且仅有一件 `<Name>Shadow`，平地基的 `BuildFoundation` 必须没有。
  - ⑤ 运行期对拍：引擎读回的 40×23 `tilemap.is_solid` 位图逐格 == 盘上串（`solid` 就是物理）。
  - 反面对照三条，都走同一个 `footprint()`：竹子按 quad 框 ⇒ 悬空 **5** 格、摘掉拆层屋顶件 ⇒
    缺碰撞 **64** 格、把洞填实 ⇒ 出口当场断（550 → 548）。
- **反面对照 A 的落点换过一次**（登记的读数，不是松动）：计划原句是"把某建筑的 `solid` 扩到整个
  quad 框，门必须红"。盘上实测 **10 栋建筑的 quad 框与不透明紧包围盒逐格相同**——这几张贴图都铺满
  了自己的画框，拿建筑做这条对照**悬空格恒为 0**、门会绿在一条空转的对照上。落在道具上才有牙
  （竹子按框多出 5 格竹梢，那些格画的是能走过去的枝叶）。判别用的量也打在 §① 的读数行里
  （"按 quad 框与按不透明像素会算出不同占地的建筑：0 栋"），所以这条空转本身是可见的。

### E. 顺带修掉的三条会咬后来的包的东西

   web 按 id 升序排 tilemap 批次，两条约束都不破）。`scripts/systems/farm.lua` 那句"id 235"跟着改。

   正好贴在地图下边界（`position=(480,0)`）上，所以盘上从没撞过它。两侧同法改正，读数不变（0.16）。
