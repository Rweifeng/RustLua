## 动作拆分

1. **修 `url` 版本（最小改动）**
   ```powershell
   cd engine
   cargo update -p url --precise 2.5.9
   ```
   - 只允许 `url` 及其必要的传递依赖变化；用 `git diff engine/Cargo.lock` 逐条核对，
     出现无关 crate 升版必须回滚重做（不要跑不带 `-p` 的全量 `cargo update`）。
   - 验收：`cargo tree -i url` 显示 `url v2.5.9`；`git diff --stat engine/Cargo.lock` 只有 url 相关行。

2. **跑供应链门并留档**
   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify/check-security.ps1 -RequireTools
   ```
   - 判据：advisories / licenses / bans / sources 全过；**缺工具或网络失败是 BLOCKED（退出码 3），不是通过**。
   - 如 `cargo deny` 报新 advisory：只在确认"无修复版本"时按 docs/69 §4 的例外格式登记**带复核截止日**的理由；
     不允许扩大 allow-list 或静默 `ignore`。
   - 验收：日志里 `security_ok`（或等价成功行）；把日志路径写进实现记录。

## 风险

- **`cargo update` 的连带升级**：`url` 可能带 `idna`/`icu_*` 等传递依赖；必须 `--precise` + 逐条 review，
  出现非预期 diff 就 `git checkout -- engine/Cargo.lock` 重来。
- **安全门依赖外部工具与 advisory DB**：本机没有工具时只能 BLOCKED，不能写成"通过"；
  这类失败要如实进实现记录，并把它作为"本包未收口"登记，而不是放宽判据。
- **推送时机的耦合**：若 M85-01 尚未收口就推送，会让 CI 在红树上跑，浪费一轮并污染证据；
  若工作区还有其它会话的在制品，按仓库惯例先备份/隔离，不把别人的 WIP 推上去。
- **远端 CI 额度/并发**：CI 同 ref 质量门串行（`cancel-in-progress:false`），一轮约 80 min；
  推送后不要连续重推，等结论。
