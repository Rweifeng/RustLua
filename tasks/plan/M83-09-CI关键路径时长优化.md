# 任务：CI 关键路径时长优化（build-test 是唯一长杆）

- 任务 ID：M83-09
- 状态：待办（先测量、再动结构；本轮只落读数与方案）
- 关联里程碑：M83
- 创建日期：2026-11-16

## 目标

`Rust quality gate` 的墙钟时间由**最慢的 job** 决定。本轮实测：`build-test` 是唯一长杆
（~70–120 min），其余 job 都在一小时内。本任务先固化"每一轮各 job 用时"的读数口径，
再评估"拆分 / 并行 / 缓存"哪一项值得做，避免继续把时间花在非关键 job（例如 coverage 线程数）
上。

## 一、已观察到的读数（2026-11-16，本会话内多次 CI 轮次）

| job | 典型用时 | 说明 |
|---|---|---|
| **build-test** | **~70–120 min** | 关键路径：`cargo build --workspace --release` + `cargo test --workspace --all-features`（`RUST_TEST_THREADS=1`，见下）+ Debug build |
| coverage | <70 min（2 线程时） | `cargo llvm-cov` 插桩全量测试；1 线程会逼近/超过 build-test |
| gates | 33.5 min | 含 17 个基准示例的 release 运行 |
| web-evidence | ~14 min（BLOCKED 化后更短） | 能力预检 51 s 即 BLOCKED 时 |
| lint | 8.6 min | fmt / clippy / rustdoc / 若干 node 门 |
| security / release-closure | 2.4–2.6 min | 网络与工具受限时更快或 BLOCKED |

口径提醒：这些是"最近几轮"的观测，不含冷缓存构建；正式判据应取
`verify.ps1`/workflow 日志里的 `started_at → completed_at`，并记录 runner 与缓存命中状态。

## 二、build-test 为什么慢（读码结论 + 实测时长）

`4b68a60e` 一轮的 job 时长（CI API 实测，2026-11-16）：

```
build-test     89.4 min   ← 唯一关键路径
coverage       36.4 min
gates          23.2 min
web-evidence    7.8 min
lint            6.8 min
security        2.3 min
release-closure 2.1 min
```

耗时构成（读码）：

1. `cargo build --workspace --release`（发布 profile：opt-level=s、strip、16 CGU，冷缓存 ~15–25 min）；
2. `cargo test --workspace --all-features`，且 **`RUST_TEST_THREADS=1`**：这是 2026-10-21 为了
   规避 `engine --lib` 偶发 `0xC0000005` 而固定的（见 `quality.yml` 注释与 M83-02）；
   单线程让 workspace 全量测试串行跑——大头是 `rustlua-gpu` 的 308 条 GPU 测试（本机实测
   单线程约 47 min）与 `editor` bin 的 700+ 条面板测试；
3. `RUST_MIN_STACK=64MB` 只影响派生测试线程，不影响墙钟本身。

**结论**：墙钟主要被"单线程全量测试"占掉，而不是构建或缓存。要让 CI 明显变快，只有三条路：
拆分测试、恢复并行（需先解 AV 根因）、或缩小每次跑的测试集合；**缓存救不了测试运行时间**。

### 2.1 一个关键陷阱：不能按 target kind 拆

实测 `cargo test --tests` **包含 lib 单测**（`rustlua-math`：`--lib` 8 条、`--tests` 也是 8 条）。
所以"`--lib` 一组 + `--bins --tests` 另一组"会让 `rustlua-gpu` 那 47 分钟**在两组各跑一遍**，
等于没拆。可行的拆法是**按 crate 分组**，并用 `--exclude` 把边界写进配置：

```
cell gpu   : cargo test -p rustlua-gpu --all-features
cell editor: cargo test -p editor --all-features
cell rest  : cargo test --workspace --all-features --exclude rustlua-gpu --exclude editor
```

并集**构造性等于**全集（`--exclude` 是精确划分，不依赖 target-kind 语义）。
验证口径（比"本地跑一遍"更可核验）：**CI 首轮**把三个 cell 的日志里
`running N tests` / `test result: ok. N passed` 的 N 相加，与原 `build-test` 单 job 的总数对比，
差值必须为 0；同时 `cargo test --no-run --message-format=json` 的 compiler-artifact 清单
在本地抽查过三组 target 列表（`rustlua-gpu` 1 个、`editor` 3 个、rest 55 个，合计 59 == 全集 59）。

## 三、方案与当前选择

| # | 方案 | 预期收益 | 风险与依赖 |
|---|---|---|---|
| **A（已实现）** | **4 个并行 job**：`build-and-check`（Release+Debug 构建）+ `build-test-suites` 三 cell（gpu / editor / rest，matrix + `fail-fast: false`） | 墙钟从 89 min 降到 ≈ max(三 cell) + 各 cell 编译，目标 ≥30% | 只改 workflow；每个 cell 独立编译（rust-cache 共享但有并发写）；需"集合等价 + 三向反面对照" |
| B | 按 crate 进一步细拆（例如 `rustlua-render`/`rustlua-scripting` 单列） | 边际收益递减（细粒度 cell 的编译开销会吃掉收益） | 需再量；暂不做 |
| C | 恢复并行测试 | 可能 2–4× | **依赖 M83-02 的 AV 根因**；未定位前不做 |
| D | 缩小 `build-test` 集合（GPU 测试只在 nightly 跑） | 中等 | 与"每次 push 都要全绿"的门哲学冲突，需负责人裁定 |
| E | 缓存（rust-cache） | 只省构建 | 已在用；不是主要瓶颈 |

**当前选择 A**：这是唯一"纯调度、可逆、有反证"的方案。

## 三-B、首轮真实读数（2026-11-17，`99b1284e`，9/9 全绿）

| job | 时长 | 说明 |
|---|---|---|
| **build-test (gpu)** | **75.7 min** | **新关键路径**（单线程 308 条 GPU 测试） |
| coverage | 40.2 min | 2 线程；ECS 插桩假红修复后转绿 |
| gates | 23.0 min | 未变 |
| build-test (editor) | **10.0 min** | 原与 GPU 串在同一 job |
| build-test (rest) | **9.8 min** | 同上 |
| build-and-check | 9.6 min | Release + Debug 构建 |
| web-evidence | 5.4 min | BLOCKED 化后 |
| lint / release-closure / security | 5.0 / 3.0 / 2.8 min | — |

- **总墙钟：100.3 min → 80 min（−20.2%）**；
- 关键路径 job：97.7 min（旧 `ff327b04` 的 build-test）→ **75.7 min（−22.5%）**。

**结论：目标（总墙钟 ≥30% 下降）未达成，如实记录。**
拆分本身有效（editor/rest 两段各 ~10 min 已并行跑完），但 **GPU cell 独占 75.7 min**，
把收益吃掉了大半。下一步候选（按风险/收益）：

| 候选 | 预期 | 风险 |
|---|---|---|
| **G1：把 GPU cell 再拆两半**（按测试名过滤，例如 `renderer::tests::` 的两批） | 再 −20~30 min | 同一 lib binary 会被两个 cell 各编译一次（+5–8 min/格）；过滤表达式脆弱，需要"合起来全覆盖"的核对 |
| G2：GPU cell 改 2 线程 | 可能 −35 min | 历史 `0xC0000005` 未定位（M83-02）；但 coverage 以 2 线程跑全 workspace（含 GPU 测试）已连续绿，可作为一次受控实验 |
| G3：GPU 测试降级为 nightly | −75 min | 与"每次 push 全绿"的门哲学冲突，需负责人裁定 |
| G4：接受现状（80 min） | 0 | 已比旧拓扑好 20%，且关键路径从"全量"变成"单 crate" |

**建议顺序**：先做 G2 的一次受控实验（只改 gpu cell 的 `RUST_TEST_THREADS`，若红立刻回滚，
并记录是否复现 AV）；不可行再评估 G1。

## 四、验收方式

1. 记录改动前后的 `build-test` job 用时（`started_at`/`completed_at`，至少 2 轮）；
2. **集合等价反证**：在任意 commit 上故意弄红一个 `--lib` 用例和一个集成用例，确认拆出的两个
   job 分别变红（不是被汇总 job 吞掉）；
3. 总墙钟下降 ≥30% 才算达到目标；不足则记录"不做的结论"与原因（沿用仓库"先测后做"的惯例）。
