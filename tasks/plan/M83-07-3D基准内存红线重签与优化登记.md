## 四、重签基线（已执行）

依据 `metrics/README.md` §5：基线只来自**干净工作树**，更新必须显式、可评审；`verify.ps1:1815`
给出的流程是"在干净 HEAD 上跑一次 → 人工核对几何量 → 写入 `metrics/baselines/`"。

执行记录：

1. `git worktree add --detach <tmp> HEAD`（HEAD = `44a27bf3`，干净）；
2. `cargo run --quiet --release -p engine --example wp0_3d_stress -- --cycles 30 --output <tmp>.json`；
3. 几何量逐字段核对（三档 `draw_calls=2`、`instances=triangles=mesh_count` 全部一致）；
4. 写入 `metrics/baselines/wp0-3d-stress.json`；
5. 自比对 `compare-baseline -GeometryOnly`：**checks=12 regressions=0**（exit 0）。

**一个刻意的取舍：只更新分配/峰值字段，计时块保留上一次评审的读数。**

干净 HEAD 那次测量是在**本机**跑的，而本机的 GPU 计时读数是软件光栅产物（`gpu_frame_us`
只有 1 个样本、约 763 ms），与旧基线（真实 GPU，1–24 ms，count=2–3）根本不可比。
时间量本来就不进门（`-GeometryOnly` 只打印 INFO），把这种机器相关读数写进仓库基线只会让
后来人误读，所以：

- `cpu_alloc_count` / `cpu_alloc_bytes` / `cpu_live_bytes` / `cpu_peak_bytes` ← 本次干净 HEAD 实测；
- `samples` / `render.gpu_frame_us` ← 保留旧基线（作为"上次评审时的机器读数"参考）；
- `render.draw_calls/instances/triangles` ← 未变（逐字段核对一致）。

代价：这份 JSON 不再是"某一次运行的完整快照"，而是"结构性/分配参考点 + 历史计时参考"。
它的用途（`compare-baseline` 只读几何量与 `cpu_peak_bytes`）不受影响；`verify.ps1` 的 schema
断言读的是**当次报告**，不读基线。这一点写在这里，避免后人把它当完整 run 引用。

新旧数值（`cpu_peak_bytes`）：

| mesh | 旧基线（2026-10-21） | 新基线（2026-11-16） | 变化 |
|---|---|---|---|
| 100 | 471,271 | 714,390 | +51.6% |
| 1000 | 774,426 | 1,074,106 | +38.7% |
| 10000 | 5,538,246 | 6,574,666 | +18.7% |

**为什么重签是合理结论而不是掩盖**：几何红线（docs/54 的 any-change）仍然严格；`cpu_peak_bytes`
的红线本意是"相对上次评审认可的参考点报警"。旧参考点停在 2026-10-21，之后落了 11-06 整批
屏幕空间/地形/水面/风场特性——这些特性必然抬高固定开销。把参考点推进到"包含这批特性"的位置，
红线才对**下一次**增长有意义；否则它会永远红着，等于失效。

## 五、后续优化项（登记，不阻塞）

**每帧固定分配 +68 次（100→1000 档同为 +68）** 是真开销，值得单独一轮：

- 方向一：把 11-06 批次引入的每帧临时集合（pass 侧参数打包、阴影分级/cull 记账、天空 LUT 采样
  准备）改成**复用缓冲**（`&mut Vec` 清空复用 / smallvec / 预分配池），目标把 alloc/帧 压回 ~560；
- 方向二：`cpu_peak_bytes` 的三档若压不动，考虑给 `wp0_3d_stress` 增加"稳态帧峰值"与会话峰值
  两个读数，把"启动期一次性分配"和"每帧分配"分开判——但**先做方向一**，不靠改量尺回避数字。
- 判据：方向一完成后 alloc/帧回到 ~560（≤ 当前 −8%），且几何量逐字节不变；此时再按本流程重签一次。
