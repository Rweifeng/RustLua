## 四、"游戏侧不直接调可能缺失的引擎名字"这条门：**两种静态设计都试过，都不成立**

这是 B2 留下的欠账。我按两种设计各写了一版并**都跑了**，结论是：**静态名字匹配在这个仓库里做不出
可靠的门**，证据如下（这也是为什么坚持"新门必须先在一个已知坏例上变红"——不然交出去的就是一条
永远不会失败、或者满屏误报的门）。

### 设计一：扫"直接调用点" —— **不可判**

`main.lua` 里的 `audio` 是 `require("core.audio")`（游戏模块），而**引擎表也叫 `audio`**，于是
`audio.settings_path()` 这种调用**文本上与直接调引擎完全一样**，无法区分。这正是 B2 我记错的原因
（把它记成"无判据调用"，实际调的是包装）。

### 设计二：锚在"包装定义侧" —— **也不可判**（实测 40 条误报）

判据改成"对每个 dropped 名字 `<mod>.<fn>`，只要游戏侧用过，就必须存在一个带判据的包装
`function M.<fn>`"。在**当前这棵树上**跑出来是**红**的：43 个被引用，**40 个不合格**，而它们**全是误报** ——
例如：

- `animation3d.get` 被判成"有包装但判据被删了"，列了 **24 个文件**（`data/achievements.lua:291`、
  `data/animals.lua:75`…）——因为那些文件里各自有**自己的** `M.get`，与 `animation3d` 毫无关系；
- `animation3d.list` 同理（11 个文件）。

**根因**：引擎的名字空间与游戏模块的方法名空间**双重碰撞** —— 模块名会撞（`audio`），方法名也会撞
（`get`/`list`/`set`/`clear` 这类在一两百个模块里到处都是）。**没有类型信息或调用图，静态上判不出来。**

### 可成立的那条路：把判据挪到**运行时**

按本项目自己的原则（"不留静默 nil：要么可用、要么**显式报缺**（进控制台/进读数）"），正确做法**不是**
静态 lint，而是让"调了一个不存在的名字"**在运行时可见**：

- 对补丁层整表替换的那些模块，在表上挂一个 `__index` 元表：**未命中的 key 记进现有读数**
  （`data-rustlua-missing-api` 这条属性 JS 世界本来就在维护）并打一行控制台；
- 这样"某个名字在 web 上是 nil"从"静默"变成"可查"，而且**不需要任何白名单**；
- 对 `audio` 那三条，B8 之后**根本不需要它**：引擎侧 `audio.rs` 已经有 `settings_path`/`settings_text`/
  `apply_settings`（B2 查实），删掉 JS 世界后它们自动可用；
- 它对 **C 类（纯占位）**的名字仍有价值：那些名字删掉占位后"要么引擎真实现接管、要么显式报缺"，
  `__index` 报缺正好是后半句的实现。

**所以这一条从"B8 的前置"改判为"B8 之后的运行时收尾"**：静态门不做了（做不出），改成"引擎/补丁侧
对未命中名字报缺"。B8 因此**不必**再等这条门。

## 六、第 3、4、5 条的**结论**（已执行 / 已查实）

- **第 3 条 `wasm-lua/input-frame-abi-test.mjs`：不在本轮删，随 B8 一起删。**
  它的被测物**今天还在**（那个从出厂源码抽出来的打包器），所以现在删会**丢掉现有覆盖**。B8 删掉
  `web-runtime.js` 之后它才会以"anchor not found"的形式红 —— 那时它该整条删除，因为：
  它测的是"**批量二进制 ↔ 旧 Lua 源码序列化**逐字符等价"，而旧的那一套随旧世界一起消失（对拍的两套死了一套）；
  活下来的两件关切已有别的门守着：**布局与往返**由 `rustlua-frame-abi` 的 12 条用例（含
  `round_trip_preserves_every_field`、`offsets_do_not_overlap`）守，**键表一致性**由静态门
  `check-input-abi-parity.mjs` 守，**真帧**由两个平台门守。
- **第 4 条 `wasm-lua/measure-lua-boundary-wasm.mjs`：已改（本轮落地）。**
  不再从 `web-runtime.js` 抽打包器，改成**按 wasm 自己给的布局现搭一个合法帧**：被测物没变（仍是真
  wasm 的 `lua_input_frame` 跨界解码），而构造方式**不可能与布局漂移**（它就是照 `input_frame_layout_json()`
  写的）。这比原来更诚实：原来"测的是出厂打包器"，其实混进了被删文件的存活期。
- **第 5 条 `check-upload-ecma.mjs`：无需改动（查实）。**
  `files=N` 是**推导出来的**（`process.stdout.write(\`upload_ecma_ok files=${files.length} …\`)`），
  注释里那些 `files=6` 是**某次观测的历史记录**，不是期望值。B8 后计数自然变成 5，门照常工作。

## 七、第 1、2 条的**决策建议**（把权威来源搬去哪）

统一原则：**删掉一面镜子时，门的参照物必须落在"生产里真的还在跑的两侧"** —— 即**引擎（Rust）**
与**游戏自己的数据**（project.toml / 游戏 Lua）。**绝不能**把参照物留在脚本、构建产物、或另一份
只在旧形态里活着的前端代码里：那正是这两条门现在红的原因，也与"人工维护的说明会脱节"同源。

### 第 1 条 check-input-abi-parity.mjs：绑定的权威来源 → **project.toml 的 [input] 段**

- **为什么是它**：运行时**已经在读它**（引擎侧有 input.settings_path / input.load_settings，B2 查实时
  确认过），也就是说"玩家改键"的权威来源**本来就是工程文件**，JS 世界那张 bindings 表是**镜像**；
- **改成三方对拍**：Rust KEY_NAMES（键名表）↔ project.toml 的 [input] 绑定 ↔ **Rust 侧的 DOM 名映射**
  （空格键→space、ArrowX→x 这条规则今天在 JS 的 keyName 里；删旧世界后浏览器侧由 gpu_host 产输入，
  所以它必须先在 Rust 里落地 —— 这就是门前置）；
- **收益**：门不再依赖任何前端源码，"游戏绑了哪些键"变成**工程可读**的事实。

### 第 2 条 check-tile-hash-parity.mjs：改成 **Rust ↔ 游戏 Lua** 两侧对拍

- 账上记过瓦片哈希在 **Lua / JS / Rust 三份镜像**里逐位对齐；删旧世界后剩**两份**（Lua 与 Rust），
  而这两份**都还在生产里跑**（游戏侧算区块键、宿主侧算渲染/缓存键）⇒ 直接对拍它们；
- **不建议"作废"**：它守的是"翻土/浇水/出苗在 web 上整层不可见"那类**静默差异**，而两份镜像的真实
  风险（一边改了、另一边没改）依然存在；
- **前置**：先确认游戏 Lua 那份实现**真的在用**。若查实已无消费者，正确处置是**删门 + 记录理由**，
  而不是留一条只对着 Rust 自己空转的门。

> 两条都**不阻塞** B8 的机械部分（第 3、4、5 条已闭环）：它们是"门搬家"的设计题。搬家完成前，
> 这两条门会以"抽不出表 / 找不到暗号"的形式红 —— 那是**预期的红**，按上面两步处理。
