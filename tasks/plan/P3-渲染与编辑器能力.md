## 1. 要解决的问题

`docs/62` 把渲染判为全仓最大差距：单方向光 + Blinn-Phong、无 HDR、无 IBL、无 compute、
6 段内嵌 WGSL、8 条固定管线；视觉水平约在 Unity 5 / Godot 3。编辑器侧则缺动画时间线、
材质编辑、可视化脚本三件「效率倍增器」，插件系统只有生命周期，自动布局只到 E17 的最小集，
Profiler 有实时读数但没有 per-system / per-pass 的归因能力。

这不是「再加几个特性」的问题，而是四个具体断层：

1. **颜色管线断层**：场景颜色目标与后处理目标都是 8-bit（`targets.rs` 用 `config.format`，
   离屏用 `Rgba8UnormSrgb`），高光在进入 tonemap 之前已经被截断；没有 HDR，PBR 的能量守恒
   和 IBL 的高动态范围都无处落地。
2. **着色器断层**：WGSL 是 Rust `const` 字符串，改一行要重编译整个引擎；没有文件、没有变体、
   没有运行时校验。PBR 的 alpha mode / normal map / IBL / skinning 会把这个断层放大成
   「每加一个特性就多一条手写管线」。
3. **GPU 能力断层**：全仓 0 个 `create_compute_pipeline`、0 个 `@compute`；粒子是 CPU 系统，
   渲染侧逐粒子 push 成 sprite（`frame_data.rs:1078`），高粒子数时 CPU 与 draw 都先撞墙。
   WebGL2/微信没有 compute，这决定了任何 GPU 加速都必须有 CPU 回退。
4. **作者工作流断层**：动画只有 inspector 里的 clip 列表与 `UiAnimation` 编辑，没有时间线；
   材质没有资产，只能改 glTF 因子；可视化脚本不存在；插件只有 `on_load/on_unload`；
   自动布局缺 wrap/justify/约束/嵌套测量；Profiler 只有整帧 GPU 时间，不能按 pass/system 归因。

P3 的目标不是「把 13 项都写上」，而是把其中 **6 项变成画面与作者闭环**（HDR、PBR、材质编辑、
动画时间线、Profiler v1、Shader 变体），把 **4 项变成可复用的管线能力**（IBL、热重载、插件、
自动布局），把 **3 项高成本能力放在明确的决策门之后**（compute、GPU 粒子、可视化脚本）。

### 2.2 推荐的最小可交付集（P3-A）

先把「看得见的画面 + 能改画面的工具 + 能定位性能的工具」做成闭环：

1. `R01` HDR + Tonemap；
2. `R04` Shader 变体（PBR 的地基，先于 PBR）；
3. `R02` PBR + `.material`；
4. `E02` 材质编辑器；
5. `E01` 动画时间线（可与渲染并行，不阻塞）；
6. `E06` Profiler v1（CPU scope + per-system + trace 导出）。

**P3-A 的出口**：一个新 3D 场景能开 HDR、用 PBR 材质、在编辑器里改材质并保存；一个 2D 场景的
既有 golden 逐字节不变；Profiler 能导出一次可打开的 trace，并能说清一帧里 ECS/Lua/render
各占多少。A 档的 PBR 先接常数环境光，IBL 在 B 档紧接；不要为了 IBL 把 PBR 的验收拖后。
A 档没过，不启动 IBL / compute / 可视化脚本。

### 2.3 明确不做（批次级）

- **不做网络/多人、更多平台、VR/AR**：那是 `docs/62` §6 的 P3，按需启动，不在本批。
- **不做 Bloom / SSAO / SSR / DOF / Motion Blur / 自动曝光 / HDR 显示器输出**：先把 HDR 颜色
  管线与 tonemap 做对；这些是后续独立工作包。
- **不做多光源、级联阴影、点光/聚光灯阴影**：PBR v1 仍是「单方向光 + 阴影 + IBL 环境光」；
  多光源另立任务，避免把 light schema、shadow atlas、排序一次性搅进来。
- **不做 3D 骨骼关键帧编辑器 / 完整 cutscene 序列器**：时间线 v1 只编辑同实体属性轨与事件；
  glTF 骨骼 clip 只读预览。跨实体、root motion、IK、blend tree 都后置。
- **不做材质节点图 / Shader Graph**：材质编辑器只编辑 `.material` 的固定 PBR 字段与贴图槽；
  自定义着色器不在本批。
- **不做动态 Rust 插件 ABI / 插件市场**：进程内 Rust 插件是静态编译、受信的；外部扩展走
  Lua 或进程外协议，具体在 E04 的决策门里定。**不承诺 `cdylib` 稳定 ABI**。
- **不做 GPU 粒子碰撞、力场、拖尾、mesh 粒子、GPU→Lua 读回**：GPU 粒子是视觉层，不是
  gameplay 状态源；需要读粒子位置的玩法继续用 CPU 路径。
- **不做完整 Flexbox / CSS Grid / RTL / baseline / 容器查询**：E05 只补游戏 UI 真正需要的
  wrap、justify、min/max、aspect、嵌套测量与编辑器可视化。
- **不做 per-draw GPU 调试器 / 厂商计数器 / 远程 profiling**：E06 到 per-pass + per-system +
  capture 为止；逐 draw 的 frame debugger 另立。
- **不引入第二套运行时或第二套编辑器框架**：可视化脚本生成 Lua，复用现有 Lua VM；插件 UI
  复用 egui/egui_dock；不引 wasmtime/CEF/第二套 UI。

### 3.3 平台与门

| 能力 | Desktop（DX12/Vulkan/Metal） | WebGL2 / 微信 | 约束 |
|---|---|---|---|
| PBR | 可做 | 可做着色器数学，但受纹理单元/ALU 限制 | 2D 路径必须零变化 |
| HDR 浮点 RT | 通常可做 | **必须启动期探测**；`Rgba16Float` 渲染/线性过滤不保证 | 失败回退 `Rgba8` + LDR tonemap |
| IBL | 可做 | 可做 LDR/半浮点 cubemap 或 SH-only | 不支持时回退常数环境光，显式告警 |
| Compute | 可做 | **不支持**（`storage_capable=false`；M74-03 已裁） | 任何 compute 特性必须有 CPU 路径 |
| GPU 粒子 | 可做 | 不可做 | 默认 CPU；GPU 是可选视觉层 |
| Shader 热重载 | 编辑器/桌面 dev 可做 | 不可做 | wasm 用内嵌源，不暴露覆盖入口 |
| Shader 变体 | 可做 | 只编译实际用到的子集 | 变体上限 + 启动预算 |
| 编辑器能力 | 全部 | 不适用（编辑器不跑 wasm） | 运行时资产（`.anim`/`.material`）要能被 wasm 读 |

`engine/crates/engine/examples/` 19 个示例，已有 `wp0_3d_golden`、`wp0_2d_golden`、
`wp0_lighting_golden`、`wp0_mixed_golden`、`wp0_particle_parallel_golden` 等；`compare-golden.ps1`
做逐值/容差对账。P3 的新能力必须接进这套门，而不是只写单测。

### 3.4 这些读数说明什么

1. **PBR 不是只改写一个 fragment shader**：它同时要动顶点布局（tangent）、材质资产、glTF
   导入、bind group、shadow pass、alpha 排序、变体缓存。把它拆成 R02 的四个阶段，任何一个
   阶段失败都能退回上一阶段。
2. **HDR 是 PBR 的前置，不是 PBR 的装饰**：没有 >1 的颜色，金属高光只能被截到白色，
   metallic/roughness 的对比会被压平。先做 R01，再谈 PBR 的视觉收益。
3. **WebGL2 是硬约束，不是「优化目标」**：compute、浮点 RT、热重载在 web 上都不成立；
   每个 GPU 特性都要先写「不可用时怎么办」，否则就是在微信上制造黑屏。
4. **编辑器缺的不是 UI 控件，而是数据模型**：`.anim`、`.material`、`.vgraph` 三个资产格式
   不定，面板做得再漂亮也只是临时状态。P3 的顺序是「格式 → 运行时 → 面板 → golden」。

## 4. 跨包硬约束

1. **先探测，再启用**。所有 HDR/IBL/compute/变体能力在启动期产出
   `RendererCapabilities`（字段至少含 `hdr_color`、`float_linear_filter`、`compute`、
   `storage_buffers`、`timestamp`、`max_texture_dim`、`backend`）。没有探测结果就不允许
   静默假设。
2. **没有「静默降级」**。回退必须同时满足三件事：功能仍正确、日志/指标有记录、编辑器或
   Profiler 能看到当前档位。禁止「失败就当没这个特性」。
3. **默认路径不变**。2D 项目、旧 3D 场景、未开启 HDR/IBL 的场景，像素输出必须与今天一致；
   新能力默认关闭或按场景显式开启。每包至少一条「旧 golden 逐字节不变」。
4. **每个新能力至少两条门**：一条正向（像素/读回/采样值），一条负向（非法输入/不支持平台/
   超限/坏资源）。只编译通过不算通过。
5. **资产格式版本化**。`.material`/`.anim`/`.vgraph`/`.rlenv` 都带 `version`；解析器拒绝
   未知版本与未知字段（或按版本显式忽略），错误信息带文件与行/字段。导入器与运行时共用
   同一套校验，不允许「编辑器能存、运行时读不了」。
6. **单一事实源**。PBR 材质只认一个 `MaterialAsset`（glTF 导入与 `.material` 都落到它）；
   动画只认一个 `.anim` + `AnimationPlayer`（旧 `Animation` 保持兼容）；可视化脚本只认
   `.vgraph`，生成的 Lua 是产物不是源；布局只认 `ContainerStyle` + `LayoutItem`，编辑器
   不另存一份布局字段。
7. **架构红线**：`rustlua-ui` 不依赖 `rustlua-render`（文本测量走端口）；新增
   `rustlua-editor-api` 必须是叶子（插件不依赖 `editor`）；新增 `rustlua-visual-script`
   必须是叶子（只产 Lua 字符串，不依赖 `rustlua-scripting`）；`rustlua-infra` 不引入 egui。
   新边要进 `architecture_edges.rs` 的 `BUDGET`，并加叶子/成环测试。
8. **组件字段只改一处**：新字段必须同时更新 `component_schema.rs`、运行时解析/序列化、
   `schema_inspector` 与编辑器字段编辑；`MeshRenderer.material`、`ParticleEmitter.mode`、
   `Environment` 都是这条规则。
9. **渲染顺序可断言**：新增 `Tonemap`/`Particle` pass 必须进 `RenderPass::ALL` 与
   `RenderPlan::is_canonical` 测试；不允许在 `render_passes` 里写一个「就地 if」绕过计划。
10. **性能有预算**：PBR/HDR 对 2D 路径零成本；变体数量与编译时间有上限；Profiler 开销
    ≤2% 主线程（docs/55 目标）；GPU 粒子只有在实测优于 CPU 时才默认启用。
11. **测试证据可复跑**：每个门给出命令、输入场景/资产、期望读数或容差；GPU 不可用的环境
    返回 **exit 3（BLOCKED）并打印原因**，不伪装成 pass。仓库口径：**没跑 ≠ 通过**。
12. **不碰在途工作树**：本任务只新增/修改计划与相关索引；实施时每个子包只暂存自己的文件，
    不 revert 别人的改动。

## 5. 依赖、顺序与阶段

### 5.1 依赖图

```text
R01 HDR ──> R04 Shader 变体 ──> R02 PBR ──> R03 IBL
                                      │
                                      └──> E02 材质编辑器

R04 ──> R05 Shader 热重载（在 R02/R03 的 shader 集合稳定后收口）

R06 Compute（M74-03）──> R07 GPU 粒子

E04 插件 API ──> E03 可视化脚本
E01 动画时间线（独立，可与渲染并行）
E05 自动布局（独立，可与渲染并行）
E06 Profiler v1（地基）──> E06 v2/v3
```

关键依赖的理由：

- **R01 先于 R04**：变体缓存的 key 里含颜色目标格式（HDR/LDR）。先定 HDR 目标，再定变体 key，
  否则缓存 key 要改两次。
- **R04 先于 R02**：PBR 会引入 alpha mode、normal map、IBL、skinning 四类轴；先把预处理器、
  变体 key、管线缓存做出来，PBR 只“加轴”，不再手写第 9/10 条管线。反过来做会把 PBR 的
  管线代码写两遍。
- **R02 先于 R03**：IBL 是给 BRDF 提供环境辐射；PBR 的 `F0/kD/roughness` 没稳定前做 IBL，
  只会把两个问题混在一起调。
- **R05 在 R02/R03 之后收口**：热重载要重建“最终 shader 集合”的全部变体；如果 shader 还在
  大改，热重载的接口哈希门会天天误报。
- **R06 先于 R07**：GPU 粒子是 compute 的第一个真实消费者；M74-03 的 P0 探针若判无 compute，
  R07 直接走 CPU 路径，不硬上。
- **E02 在 R02 之后**：材质编辑器编辑的是 `.material`，不是临时 UI 状态。
- **E04 先于 E03**：可视化脚本作为内置插件使用同一套节点/面板注册 API，顺便证明插件 API
  不是“只给示例看的”。

### 5.2 推荐阶段

| 段 | 累计周（双轨粗算） | 渲染轨 | 编辑轨 | 段出口 |
|---|---|---|---|---|
| S0 观测与地基 | 0–3 | 能力探针；shader 源文件抽取（行为不变）；`.material/.anim/.vgraph` 格式草案 | Profiler v1（CPU scope + per-system + trace 导出） | 现有 golden 全绿；能力报告可在 3 个后端复跑 |
| S1 颜色与变体 | 3–8 | R01 HDR + Tonemap；R04 变体 | E01 时间线格式/运行时；E06 v1 收口 | `wp0_hdr_golden`；2D golden 不变；变体上限/编译预算达标 |
| S2 画面闭环 | 8–16 | R02 PBR；R03 IBL | E02 材质编辑器；E01 面板/撤销/预览 | PBR/IBL golden；材质保存往返；时间线采样 golden |
| S3 管线与工作流 | 16–24 | R05 热重载 | E04 插件 API；E05 自动布局；E06 per-pass GPU | 热重载负向门；示例插件；布局 3 分辨率 golden |
| S4 高成本能力 | 24–34 | R06 Compute → R07 GPU 粒子 | E03 可视化脚本（依赖 E04） | compute readback；10k/50k 基准；vgraph → Lua golden |

> 周数是**相对刻度**，不是承诺。S2 的 PBR 与 E01 可以并行；S4 的 GPU 粒子与 E03 可以并行。
> 每个段结束必须更新本文件的「实施台账」，没写证据就不算段完成。

### 5.3 并行与冲突规则

- **文件所有权按包划分**：R01/R04 都碰 `construct.rs`/`shader.rs`，串行；R02 碰
  `mesh3d.rs`/`gltf_asset.rs`/材质 bind group，和 R03 的 bind group 有交集，R02 先收口再开 R03。
- E01/E02/E03 各自新增 `panels/<name>.rs`，只改 `dock.rs`/`layout.rs`/`mod.rs` 的登记点；
  三个包同时开时要提前分配 `DockTab` 变体与面板顺序，避免互相改同一个 match。
- `component_schema.rs` 是热点：`MeshRenderer.material`（R02）、`Environment`（R03）、
  `ParticleEmitter.mode`（R07）、`AnimationPlayer`（E01）都改它；按阶段串行合并，或每个包
  只加自己的 schema 行并附带 roundtrip 测试。
- `verify.ps1` 的 golden 段是热点：新增示例先各自跑通，再由一个「P3 门接入」提交统一加；
  避免四个包同时改同一段脚本。

## 6. 工作包

> **小节按推荐执行顺序排**（R01 → R04 → R02 → R03 → R05 → R06 → R07 → E01…），不是按 ID
> 数字排；要找某个包直接搜 `P3-<ID>`。每包的「验收门」只写新增/关键项；所有包默认还要过
> §7 的总门。路径相对仓库根。

### 6.1 P3-R01 HDR 场景颜色 + Tonemap（2–3 人周）

**现状（实测）**：离屏 scene 目标 `Rgba8UnormSrgb`；后处理 scene 纹理用 `config.format`；
`PostProcess` 只有 exposure/tint/vignette；`MESH3D_SHADER` 的 `brightness` 直接写 8-bit 目标；
没有 tonemap 曲线，也没有 HDR 能力探测。

**交付**

- 新增 `RenderSettings`（工程/场景级；字段 `hdr = auto|off|on`、`pbr = on|off`、
  `ibl = auto|off|on`、`variants = on|off`），默认值全部保持今天的输出；后续 R02/R03/R04
  只往这里加开关，不再各自发明第二套配置。
- `RendererCapabilities` 增加 `hdr_color`/`float_linear_filter`：启动时创建 `Rgba16Float`
  纹理 + render pass + 读回探针；失败则 `hdr_color=false`，不 panic。
- `SceneColor` 目标：桌面/可用后端 `Rgba16Float`（linear）；回退 `Rgba8Unorm`（linear，
  非 sRGB），最终输出仍是 `Rgba8UnormSrgb` 表面。
- 新增 `Tonemap` pass（全屏三角形）：输入 HDR scene，输出 LDR；实现 ACES（默认）与
  Reinhard（可选），`exposure_ev` 换算成线性增益后乘，再曲线，再写 sRGB 目标。
- `PostProcess` 增加 `tonemap: Tonemap` 与 `exposure_ev`；旧 3 字段构造保持兼容；HDR 模式下
  `PostProcess.exposure` 必须为 1.0（校验/迁移），曝光只走 `exposure_ev`，避免双重曝光。
- 2D/UI 边界：HDR 只覆盖 3D 场景颜色；`Legacy2DOverlay`/`ScreenUI`/`VectorText` 在 Tonemap
  之后写 LDR（否则 ACES 会改 UI 颜色）。`RenderPass::ALL` 增加 `Tonemap`，并更新
  `RenderPlan::is_canonical` 测试。
- 默认：2D 场景 `hdr=false`；3D 场景 `hdr=auto`（本帧有 3D draw 且探针成功才开）；
  场景/相机可显式关。纯 2D 路径不创建 HDR 目标，保证旧 golden 逐字节不变。
- 尺寸变化：HDR/LDR 目标随 surface 重建，旧纹理释放；加 800×600 → 1280×720 的 resize 测试。
- 指标：`RenderFrameMetrics` 增加 `hdr_active`、`tonemap`、`scene_format`；Profiler 显示。

**阶段**

| 阶段 | 内容 | 出口 |
|---|---|---|
| R01-1 | 能力探针 + `SceneColor` 选择 + 读回测试 | 不支持时 `hdr=false`，旧路径零 diff |
| R01-2 | `Tonemap` pass + ACES/Reinhard + 曝光归属 | `wp0_hdr_golden`：8.0 线性值可读回，tonemap 后 ≤1 |
| R01-3 | UI/2D 分界 + mixed 场景排序 | `wp0_mixed_golden` 的 UI 颜色误差 ≤1/255；2D golden 逐字节不变 |
| R01-4 | 编辑器/Profiler 显示 + 文档 | 面板能看到 `hdr_active/format/tonemap`；docs/24 更新 |

**验收门**

- `cargo test -p engine hdr`：探针失败回退、曝光/曲线单元测试、格式选择。
- `cargo run -p engine --example wp0_hdr_golden -- --output artifacts/p3/hdr`；报告含
  `pre_tonemap_max`（应 >1）、`post_tonemap_max`（≤1）、`ui_delta`。
- 首次落地：`cargo run -p engine --example wp0_hdr_golden -- --output baselines/p3/hdr`，人工评审
  后入库；之后用 `powershell -File scripts\verify\compare-golden.ps1 -Current artifacts/p3/hdr
  -Previous baselines/p3/hdr` 对账。
- `wp0_2d_golden`/`wp0_hud_golden` 逐字节不变；`wp0_mixed_golden` 只允许 UI 容差内的差异。
- Web：`gpu-web-probe.ps1 -Stage render` 报告 `hdr_color`；不支持时 golden 走 LDR 分支并
  打印原因，不伪装 pass。

**风险 / 回滚**

- **UI 被 tonemap**：这是最大风险。若分界改动超过 2 周或 mixed 遮挡测不稳，降级为
  「HDR 只对纯 3D 场景开启；mixed 场景 `hdr=false` 并显式提示」，不硬改 UI 顺序。
- **浮点 RT 不可用/不可线性过滤**：`hdr=false` 回 LDR；IBL 也随之走 LDR 档。
- **双重 sRGB**：约定 scene 目标非 sRGB、输出目标 sRGB；加读回测试（0.5 线性值不应变成
  0.25）。
- **曝光归属混乱**：HDR 模式只认 `PostProcess.exposure_ev`，`PostProcess.exposure` 强制 1.0
  并在编辑器提示迁移；回滚删 `Tonemap` pass 即回旧路径。
- 回滚开关：`RenderSettings.hdr = off`（默认 2D）+ 删除新增 pass；旧 golden 必须仍绿。

**明确不做**：Bloom、自动曝光、颜色分级、HDR 显示器/EDR、MSAA、多相机 HDR 合成。

### 6.2 P3-R04 Shader 预处理 + 变体缓存（2–3 人周）

**现状（实测）**：6 个内嵌 WGSL 常量；8 条固定管线；没有 `.wgsl` 文件、没有 `#if`、没有
pipeline cache key，也没有变体统计。`construct.rs` 每条管线手写 vertex layout / bind group。

**交付**

- S0 先把 WGSL 抽到 `engine/shaders/*.wgsl`，Rust 侧用 `include_str!` 保持「无文件也能跑」；
  `ShaderSource { name, path, hash, source }`。这一步**行为不变**，只换存放位置。
- 轻量预处理器（只服务本仓库，不实现完整 C 预处理器）：
  - 指令：`//#if FEATURE`、`//#elif`、`//#else`、`//#endif`、`//#include "x.wgsl"`；
  - 未知 feature = 编译错误（防拼写漂移）；嵌套深度/包含深度上限；include 循环检测；
  - 行号映射：生成源保留 `//#line` 或 side table，wgpu 报错能回到原文件行。
- `ShaderVariantKey`（固定轴，不用字符串拼接）：
  - `skin: off|on`
  - `alpha: opaque|mask|blend`
  - `normal_map: off|on`
  - `ibl: off|diffuse|specular`
  - `shadow: off|on`（3D 默认 on；2D 不走这条）
  - key 里另含 `color_target: ldr|hdr`、`vertex_layout`、`depth`、`blend`、`cull`。
- `PipelineCache`：`HashMap<PipelineKey, Arc<RenderPipeline>>`；硬上限（mesh 家族 ≤32，
  全局 ≤64）；超限返回错误并打印 key，不静默淘汰；统计 hit/miss/compile_ms/variant_count。
- 预编译策略：启动/场景加载时预热常用变体（opaque+skin+shadow、opaque+normal+shadow、
  IBL specular）；WebGL2 只编译实际用到的子集。
- `RendererResourceStats`/Profiler 增加变体数量、编译耗时、缓存命中率。

**阶段**

| 阶段 | 内容 | 出口 |
|---|---|---|
| R04-1 | WGSL 文件化 + `include_str!` 回退 + hash | 现有 golden 零 diff；无文件构建仍可跑 |
| R04-2 | 预处理器 + 单测（嵌套/未知/循环/行号） | 预处理输出 golden；错误带原文件行 |
| R04-3 | 变体 key + pipeline cache + mesh shader 接入 | 变体矩阵编译通过；无重复管线 |
| R04-4 | 统计/上限/预热 + 文档 | 编译预算与上限门；Profiler 可见 |

**验收门**

- `cargo test -p engine shader_preprocess`：嵌套 `#if`、未知 feature、include 循环、行号映射。
- `cargo test -p engine shader_variants`：枚举 mesh 的合法轴，断言编译成功、key 唯一、
  超限报错、重复请求命中缓存。
- `wp0_variant_golden`：同一场景 normal/IBL 开关各渲染一次，读回差异符合预期（不是全黑/
  全白）；报告 `variant_count`、`compile_ms`、`cache_hits`。
- WebGL2：`verify-webgl` 场景只编译实际变体；启动/首帧编译时间不超预算（先定 250ms，
  实测后收紧）。
- 旧 `wp0_3d_golden`/`wp0_2d_golden` 零 diff。

**风险 / 回滚**

- **组合爆炸**：轴一多就 100+ 变体。固定轴 + 上限 + 预编译清单；若 demo 场景超 32，
  先砍 `shadow` 轴（阴影走独立管线）或把 `ibl` 合成一个 `on` 档。
- **编译卡顿**：pipeline 创建是同步的；启动预热 + 首帧预算 + Profiler 记录。超过预算就
  减少预热线，不把卡顿摊到每帧。
- **缓存 key 漏项**：颜色格式/混合/裁剪任一漏掉都会串管线；key 用结构体而非字符串，
  并加「同 key 只建一次」测试。
- **行号映射错误**：错误信息指错行比没有错误更糟；source map 单测必须覆盖 include。
- 回滚：`variants = off` 走静态 shader/固定管线；文件化本身可保留（行为不变）。

**明确不做**：运行时 shader graph、用户脚本动态 permutation、HLSL/GLSL 交叉编译、
SPIR-V 离线缓存（先不做，避免多一套产物）。

### 6.3 P3-R02 PBR 材质与 glTF 扩展（4–6 人周）

**现状（实测）**：`MESH3D_SHADER` 是 Blinn-Phong 式；法线没乘 model（184 行），高光视线
固定 `(0,0,1)`（198 行）；`MaterialAsset` 只有 base color/metallic/roughness；`MeshVertex`
无 tangent；`GltfMaterial` 只有 6 个字段；`MeshRenderer` 只有 `mesh`，没有材质入口。

**交付**

- 统一 `MaterialAsset`（`rustlua-render`）：
  - `base_color: [f32;4]`、`metallic`、`roughness`、`emissive: [f32;3]`、`emissive_strength`；
  - `base_color_texture`、`metallic_roughness_texture`（G=roughness，B=metallic）、
    `normal_texture`、`occlusion_texture`、`emissive_texture`（均可选）；
  - `normal_scale`、`occlusion_strength`、`alpha_mode`（Opaque/Mask/Blend）、`alpha_cutoff`、
    `double_sided`、`ibl_intensity`。
- `.material` 文本资产（示例）：
  ```text
  version=1
  name=rusted_metal
  base_color=0.8,0.7,0.6,1
  metallic=1.0
  roughness=0.35
  emissive=0,0,0
  base_color_texture=assets/textures/rust_albedo.png
  metallic_roughness_texture=assets/textures/rust_orm.png
  normal_texture=assets/textures/rust_normal.png
  alpha_mode=opaque
  double_sided=false
  ```
  解析器严格校验版本/字段/路径/数值；纹理依赖进入资产依赖图。
- glTF 导入扩展：`GltfMaterial` 增加上述字段与贴图索引；导入器解码 normal/ORM/emissive；
  有 `TANGENT` 用，没有则按三角形 + UV 生成（退化 UV 回退 `(1,0,0,0)` 并告警）。
- `MeshVertex` 增加 `tangent: [f32;4]`；顶点布局、shadow pass、skinned 路径同步。
- `MeshRenderer` 增加可选 `material=<path>`；为空时用 glTF 内嵌材质；schema/parse/serialize/
  inspector 同步。
- 着色器：Cook-Torrance GGX（NDF: Trowbridge-Reitz；可见性: Smith height-correlated；
  Fresnel: Schlick）；`F0 = mix(vec3(0.04), base, metallic)`；`kD = (1-F)*(1-metallic)`；
  方向光 + shadow + 环境项（先常数/IBL off）。法线矩阵在 **CPU 侧按实例算**
  `transpose(inverse(mat3(model)))` 再上传（WGSL 没有 `inverse` 内建，不能直接写在 shader 里）；
  uniform scale 可退化为 `normalize(mat3(model) * n)`，非均匀缩放必须用逆转置。相机视线
  `normalize(camera.position - world_position)`；skinned 法线也要过 skin 矩阵。
- 颜色空间：base color/emissive 贴图按 sRGB 解码到线性；ORM/normal 保持线性；
  `.material` 的颜色值按线性解析（与 glTF `baseColorFactor` 一致；编辑器取色器负责
  sRGB→线性转换），tonemap 前全线性。这条要有读回测试（0.5 sRGB 应约等于 0.214 线性，
  而不是 0.5）。
- GPU 材质缓存：`MaterialGpu`（uniform + 5 张纹理 + sampler）按资产 id/content hash 缓存；
  白纹理/平法线/黑 emissive 作为缺省，不在 draw 时临时建 bind group。
- Alpha：opaque/mask 进主 pass；blend 进透明队列并按深度排序；shadow pass 支持 mask；
  double-sided 用独立 cull 状态。`alpha` 轴进 R04 的变体 key；若 R04 因故未就绪，先用
  3 条固定管线兜底，不阻塞 PBR。

**阶段**

| 阶段 | 内容 | 出口 |
|---|---|---|
| R02-1 | BRDF + 法线/视线修复 + 固定因子 | `wp0_pbr_golden`；旋转模型光照不漂 |
| R02-2 | `.material` 资产 + glTF ORM/emissive + 材质缓存 | `wp0_pbr_material_golden`；往返/非法值门 |
| R02-3 | normal/occlusion + tangent 生成 | `wp0_pbr_normal_golden`；切线退化告警 |
| R02-4 | alpha mask/blend + double-sided + shadow | `wp0_pbr_alpha_golden`；透明排序稳定 |

**验收门**

- CPU BRDF 参考函数（Rust，纯函数）与 GPU 读回对拍：金属度/粗糙度网格各 5×5，容差先定
  `±2/255`；含 NaN/Inf 检查。
- **旋转不变性**：同一 mesh 绕 Y 旋转 90°，方向光相对模型不变时，读回差异在容差内；
  这条直接抓 184 行的法线 bug。
- **高光随相机**：相机绕物体转，金属高光位置变化；固定 `(0,0,1)` 的旧实现会失败。
- glTF fixture：含 normal/ORM/emissive/alpha 的材质，导入后字段/贴图/tangent 断言。
- `wp0_2d_golden` 逐字节不变；3D baseline 帧时间增幅先定 ≤25%，超过则先砍 normal map
  或降 BRDF 采样。
- 缺贴图/坏 `.material`：报错并回退白纹理/默认值，日志带路径；不静默。
- `check-silent-traces.ps1` 通过（不允许 `let _ =` 吞掉材质错误）。

**风险 / 回滚**

- **Tangent 生成质量**：UV 退化/镜像 UV 会产生错误切线；先告警并用平法线，不硬算法线贴图。
- **非均匀缩放**：逆转置在 CPU 侧算，注意奇异矩阵；CPU 侧校验 scale 非零。WGSL 没有
  `inverse` 内建，别把 GLSL 的写法直接搬过来。
- **Alpha 排序**：blend 与 3D 透明、world sprite 的顺序冲突；先只支持单材质透明，复杂
  场景用 mask；排序问题另立。
- **glTF 导入范围膨胀**：只做 metallic-roughness 工作流；specular-glossiness 不转，明确报
  unsupported。
- 回滚：`RenderSettings.pbr=off` 走旧 `MESH3D_SHADER`；`.material` 字段可缺省；旧 glTF
  路径保留到 R02-4 通过。

**明确不做**：多光源、PBR spec-gloss、clear coat、sheen、anisotropy、subsurface、parallax、
材质节点图、每像素阴影滤波升级（PCF 保持现状）。

### 6.4 P3-R03 环境资产与 IBL（3–4 人周）

**现状（实测）**：无 cubemap/环境资产；无 `.hdr`/`.exr` 导入（纹理只支持 png/jpg/jpeg）；
`MESH3D_SHADER` 只有 `0.15` 常数环境光；没有 SH、没有预过滤、没有 BRDF LUT。

**交付**

- `.hdr`（Radiance）导入：`rustlua-assets-import` 增加 HDR 解码（`image` 的 hdr feature 或
  自带 Radiance 解析），校验有限/非负/尺寸；生成 `.rlenv` 环境资产。
- `.rlenv`（版本化二进制）：
  - header：magic/version/source_hash/face_size/mip_count/format；
  - 漫反射：SH9（RGB，27 个 f32）；
  - 镜面：6 面 cubemap + mip 链（桌面 `Rgba16Float`；不支持浮点则 `Rgba8` + RGBM）；
  - 校验和；未知版本拒绝。
- 离线烘焙（assetc/导入器，不在运行时做）：
  - equirect → cubemap（固定采样方向，确定性）；
  - 漫反射：cosine convolution → SH9；
  - 镜面：GGX importance sampling 预过滤，按 roughness 分 mip；固定 RNG 序列；
  - BRDF：用 `EnvBRDFApprox`（Karis）解析近似，不烤 LUT，少一个资产。
  离线烘焙的理由：确定性、WebGL2 无 compute 也能用、不会在场景加载时卡帧；代价是导入耗时，
  先定预算（单 env ≤10s、≤8MB）。
- 运行时：`Environment` 组件/场景字段（`map=assets/env/studio.hdr;intensity=1.0`）；
  `MeshRenderer` 的 PBR shader 增加 group 2（env cubemap + SH + sampler）；`ibl` 变体轴
  控制 off/diffuse/specular。
- 能力分级：
  - Tier A：浮点 cubemap + 线性过滤 → 全质量；
  - Tier B：浮点但无线性过滤 → nearest + 手动双线性（或降 mip）；
  - Tier C：无浮点 → `Rgba8` + RGBM 或 **SH-only**；显式报告 `ibl_tier`。
- 编辑器：环境资产选择、强度、旋转（Y 轴）、预览；场景视图显示当前 tier。

**阶段**

| 阶段 | 内容 | 出口 |
|---|---|---|
| R03-1 | `.hdr` 解析 + equirect→cubemap + `.rlenv` 格式 | 解析/往返/坏文件门；确定性 hash |
| R03-2 | SH9 漫反射 + shader 采样 | SH 与 CPU 参考在容差内；无 IBL 时零变化 |
| R03-3 | 镜面预过滤 + `EnvBRDFApprox` + mip 选择 | 金属球 roughness 0/0.5/1 的 golden 稳定 |
| R03-4 | `Environment` 组件 + 编辑器 + tier/告警 | `wp0_ibl_golden`；不支持时回退并显示原因 |

**验收门**

- `cargo test -p rustlua-assets-import hdr`：合法/非法/超大/NaN；`.rlenv` 版本/校验和。
- 烘焙确定性：同一 HDR 两次烘焙 byte-identical；固定 seed；报告 `bake_ms`、`bytes`。
- SH 对拍：若干方向与 CPU cosine convolution 的误差 ≤ 容差；能量不为负。
- `wp0_ibl_golden`：金属球（metallic=1）在 env 下的反射随 roughness 变宽；报告
  `ibl_tier`、`env_bytes`、`bake_ms`；Tier C 走 SH-only 分支也要有 golden。
- 无 `Environment` 的旧 3D golden 零 diff；`ibl=off` 与 R02 的输出一致。
- WebGL2：`gpu-web-probe` 报告浮点 cubemap/线性过滤；不支持时 Tier C 可跑。

**风险 / 回滚**

- **HDR 色彩空间**：Radiance 是线性；decode 后不要再 sRGB；`Rgba16Float` 采样保持线性。
- **预过滤质量/耗时**：低分辨率 + mip 少会导致粗糙反射条带；先 128px、5 mip，超预算降 64px。
- **浮点纹理不可用**：Tier C 的 RGBM 编解码容易出误差；若误差大，直接 SH-only，不硬上
  镜面 IBL。
- **资产膨胀**：`.rlenv` 可能 >8MB；用 RGBM/降分辨率/共享环境，不把大文件塞进仓库。
- 回滚：删 `Environment` 组件即回常数环境光；`ibl=off` 变体保留。

**明确不做**：实时 GI、光照探针、反射探针、SSAO、天空大气、体积雾、HDRI 背景板
（背景板可后置）。

### 6.5 P3-R05 Shader 源文件 + 热重载（1–2 人周）

**现状（实测）**：WGSL 全部内嵌；`FileWatcher` 的 `WatchScope::default()` 只有
`assets/scripts/scenes/data`，没有 `shaders`；Lua 热重载已工作（`runtime.rs` 的
`reload_if_changed/reload/reload_entity_scripts`），shader 没有对应物。

**交付**

- `ShaderLibrary`：内置源（`include_str!`）+ 开发覆盖目录（项目 `shaders/`）；解析顺序
  覆盖 > 内置；内容 hash；`resolve(name)`。
- 开发模式：
  - 编辑器始终监听项目 `shaders/`（加入 `WatchScope`）；
  - 桌面运行时只在 `--shader-dir`/`RUSTLUA_SHADER_DIR` 显式开启时监听；
  - release/wasm 不暴露覆盖入口，始终用内置源。
- 校验与原子替换：
  - `naga` 解析 WGSL；检查入口点存在；
  - 计算 `BindingInterface` hash（group/binding/type/access/visibility）；**接口变了拒绝热重载**，
    提示「需要重启或重建布局」，绝不把新 shader 塞进旧 bind group；
  - 为该 shader 的所有变体重建 pipeline；全部成功才 swap；任一失败保留旧集合；
  - debounce 150ms；同一内容 hash 不重复编译；文件删除回退内置源并告警。
- 诊断：编辑器 Console/状态栏显示「reloaded <name> in Xms」「WGSL error at file:line」；
  旧 shader 继续工作；错误可复制。
- 测试：`wp0_shader_hot_reload`（离屏）写临时 shader → 渲染 → 改颜色 → 重新加载 → 读回；
  坏 WGSL → 读回不变 + 错误；接口变更 → 拒绝。

**阶段**

| 阶段 | 内容 | 出口 |
|---|---|---|
| R05-1 | `ShaderLibrary` + 文件化 + 覆盖路径 | 无覆盖时与内置逐字节一致 |
| R05-2 | watcher + naga 校验 + mesh shader 单条重载 | 改 fragment 画面变；坏源保留旧管线 |
| R05-3 | 全 shader + 变体原子重建 + 接口 hash | 接口变更负向门；部分失败不半替换 |
| R05-4 | 编辑器诊断 + 文档 | 错误可定位到原文件行；wasm 无入口 |

**验收门**

- `cargo test -p engine shader_hot_reload`：临时目录、有效/无效/接口变更/删除/无变化。
- `cargo run -p engine --example wp0_shader_hot_reload`：报告 `before/after` 像素、`reload_ms`、
  `rejected_reason`；退出码非 0 当负向门失败。
- `cargo check -p game_web --target wasm32-unknown-unknown`：wasm 编译通过，且没有文件监听
  分支被编入（用 cfg 断言/符号检查）。
- `check-silent-traces.ps1`：编译错误不能被吞。

**风险 / 回滚**

- **重编译卡顿**：pipeline 重建可能几十 ms；debounce + 只在保存时触发；Profiler 记录。
- **接口漂移**：bind group layout 是最容易“看起来能跑、实际读错”的地方；接口 hash 拒绝是
  硬门，不做自动重建布局（v1）。
- **watcher 循环**：编辑器保存 shader 触发重载，重载不写文件；确保不产生二次事件。
- **发布包误带覆盖**：release 只读内置源；`--shader-dir` 在 release 下拒绝并报错。
- 回滚：删 `shaders/` 覆盖即回内置；热重载是开发功能，关掉不影响运行。

**明确不做**：Rust 代码热重载、资产热重载、shader graph 实时编辑、跨进程 shader 调试。

### 6.6 P3-R06 Compute 接缝（认领 M74-03，3–4 人周）

**现状（实测）**：0 个 compute pipeline / `@compute` / dispatch；`storage_capable` 只看
storage buffer 数；[`M74-03`](M74-03-ComputeShader支持.md) 已有完整阶段表与 WebGL2 否决门。

**交付**

- **不复制 M74-03 的阶段表**。本包只做三件事：
  1. 把 M74-03 的 P0 探针并入统一 `RendererCapabilities`（compute/storage/workgroup limits）；
  2. 按 M74-03 的 P1 接缝落 `renderer/compute.rs`（pipeline cache、storage buffer pool、
     bind group cache、dispatch、readback）；
  3. 把首个消费者固定为 R07 GPU 粒子（M74-03 的 P2 选择项），不再另找 2D lighting。
- API 只对渲染器内部开放；v1 不暴露 Lua `gpu.dispatch`，避免把 GPU 生命周期交给脚本。
- 错误：无 compute/超限/绑定不匹配返回 `ComputeError`，日志带 backend/limits；不回退到
  「假装 dispatch 成功」。
- 指标：dispatch 次数、buffer 字节、pipeline 数、GPU 时间（若 timestamp 可用）。

**阶段**

| 阶段 | 内容 | 出口 |
|---|---|---|
| R06-0 | 探针 + 能力报告（1 天） | 桌面 true / WebGL2 false，有 JSON 证据 |
| R06-1 | 接缝 + storage buffer 往返 + 单测（1 周） | 读回与 CPU 参考一致；无 compute 返回 Unsupported |
| R06-2 | 首个消费者接线（与 R07 合并，1–1.5 周） | 10k 粒子 readback 不崩；CPU 路径不变 |
| R06-3 | 文档/门（2 天） | docs 更新；`verify.ps1 -Quick` 绿 |

**验收门**

- `wp0_compute_readback`：输入 buffer → dispatch → 读回，逐值/容差；报告 `backend`、
  `compute=true`、`workgroup_limits`。
- WebGL2：`gpu-web-probe -Stage backend` 报告 compute=false；尝试 dispatch 返回
  `Unsupported`，不 panic；2D/3D 旧 golden 零 diff。
- 与 R07 的 10k 粒子契约测试；没有 compute 时自动走 CPU（R07 门）。
- 若 P0 探针在目标桌面后端也 false：**停在 R06-1**，R07 只做 CPU 优化，不硬上 GPU；
  在台账写「compute 在本机不可用」而不是「已完成」。

**风险 / 回滚**

- **平台差异**：Vulkan/DX12/Metal 的 workgroup/storage 限制不同；用 `Limits` 查询，不写死。
- **与渲染 pass 的同步**：compute 必须在 render pass 之前提交；用 queue submit 顺序保证，
  不依赖隐式 barrier。
- **buffer 生命周期**：池化后不能跨帧复用未完成的 buffer；用 frame index/ring。
- **WebGL2 误判**：`storage_capable` 已有，但 compute 还要看 workgroup；统一探针。
- 回滚：删除 compute 模块与 R07 接线；CPU 粒子路径不受影响。

**明确不做**：通用 GPU 计算 API、GPU 骨骼动画、GPU culling、GPU 地形、compute 后处理、
GPU→Lua 同步读回。

### 6.7 P3-R07 GPU 粒子（首个 compute 消费者，3–4 人周）

**现状（实测）**：`ParticleSystem` 是 CPU 侧，`step_particle` 逐粒子更新；渲染在
`frame_data.rs:1078` 把每个粒子 push 成 white-texture quad；`wp0_particle_parallel_golden`
证明并行与串行逐字节一致；没有 GPU buffer，也没有粒子 render pass。

**交付**

- `ParticleEmitter` 增加 `mode=cpu|gpu`（默认 `cpu`）与可选 `seed`；schema/inspector/Lua
  同步；旧场景不带字段 = cpu。
- **语义写死**：GPU 粒子是**视觉层**，不进入 gameplay 状态；Lua 不读 GPU 粒子位置；
  需要读位置的玩法用 cpu。这样避免「GPU 读回卡帧」和「两套状态不一致」。
- GPU 路径（仅 compute 可用）：
  - storage buffer：粒子状态（pos/vel/age/life/seed）、spawn 环形队列、uniform；
  - compute：发射（rate/burst）、积分（gravity/drag/rotation）、寿命回收；
  - render：instanced quad（vertex shader 从 storage 读实例）或 compute 写顶点缓冲；
    2D 世界空间先做，3D billboard 后置；
  - pass：新增 `Particle`（在 3D/world sprite 之后、UI 之前），进 `RenderPass::ALL`；
  - 排序：粒子按 emitter 层/材质排序；透明混合固定 additive/alpha 两档，先不做逐粒子排序。
- CPU 回退：`mode=gpu` 但 compute 不可用 → 用同一 emitter 参数走 CPU，日志/Profiler 标
  `particle_fallback=cpu`；不丢粒子、不黑屏。
- 基准：10k/50k 粒子，固定 dt、固定相机；记录 CPU 帧时间、GPU 时间（若可用）、draw calls、
  buffer 字节；与 CPU 路径对比。
- 调试：`--debug-readback` 仅在测试/开发下把首帧状态读回，做不变性/首帧对拍；运行时默认
  不读回。

**阶段**

| 阶段 | 内容 | 出口 |
|---|---|---|
| R07-1 | emitter mode + CPU 回退 + schema | 旧粒子 golden 零 diff；`gpu` 无 compute 时回退 |
| R07-2 | compute 更新 + 调试读回 | 1k 粒子状态有限/寿命正确；首帧与 CPU 语义一致（容差） |
| R07-3 | instanced 渲染 + 10k | `wp0_gpu_particles_golden`；10k 可跑 |
| R07-4 | 50k 基准 + 3D billboard/文档 | 50k 有读数；未达 1.5× 收益则默认仍 cpu |

**验收门**

- `wp0_gpu_particles_golden`：固定 seed/dt，首帧/第 N 帧读回；报告 `mode/fallback/count/
  cpu_ms/gpu_ms/draw_calls`；无 NaN/越界。
- 性能门：50k 粒子时 GPU 路径的 CPU 帧时间 ≤ CPU 路径的 50%，或总帧时间 ≤ CPU 的 80%；
  达不到就**不默认启用**，保留 cpu 并在台账写结论。
- 回退门：强制 `compute=false`，同一场景仍出粒子（CPU），像素与旧粒子 golden 容差内。
- 内存门：50k 粒子 buffer 估算 ≤ 预定上限（先 16MB），不随帧增长。
- WebGL2/微信：`mode=gpu` 被拒绝并回退，工程可跑；`verify-wechat-minigame` 通过。

**风险 / 回滚**

- **视觉/gameplay 分叉**：这是设计选择，不是 bug；文档和编辑器必须写清「GPU 粒子不可读」。
- **compute 不可用**：回退 CPU；如果 CPU 也扛不住 50k，降发射率/粒子数，不假装 GPU 生效。
- **overdraw**：大量透明 quad 会先撞 fill rate；加最大粒子数/屏幕占比预算，Profiler 显示。
- **排序**：逐粒子排序成本高；v1 只按 emitter/材质，接受近似。
- **buffer 同步**：compute 与 render 之间用 submit 顺序；不要在同一帧读回。
- 回滚：`mode=cpu` 默认；删除 Particle pass 即回旧渲染。

**明确不做**：GPU 碰撞/力场、拖尾、mesh 粒子、粒子光照、GPU→Lua 读回、逐粒子排序、
3D 体积粒子。

### 6.11 P3-E04 插件接口（能力式编辑器 API，2–3 人周）

- 新叶子 crate `rustlua-editor-api`（只依赖 egui/eframe 与标准库，不依赖 `editor`）：
  - `PluginManifest { id, name, version, api_version, capabilities, permissions }`；
  - `EditorPlugin`：`manifest()`、`register(&mut PluginContext)`、`on_load`、`on_unload`；

    - `visual_script_node(NodeDescriptor)`（给 E03）；
    - `settings_page(SettingsPageDescriptor)`。
  - 宿主接口 `PluginHost`：只读项目/选中实体/资源，写操作走 typed command；插件不能直接拿

- 生命周期：`PluginRegistry` 扩展 enable/disable、依赖顺序、重复 id/版本不匹配拒绝；

- 加载方式（v1 明确）：
  - **静态编译插件**：`editor/src/plugins.rs` 维护构造器清单；manifest 校验 API 版本；

- 诊断：插件列表（id/version/status/error）、启用/禁用、重新加载（静态插件只重建 UI 状态）。

**阶段**

| 阶段 | 内容 | 出口 |
|---|---|---|
| E04-1 | 叶子 crate + manifest + 注册表/生命周期 | API 版本/重复 id/卸载单测 |
| E04-2 | 面板 + 菜单 + 命令 + 宿主 command 通道 | 示例插件面板可开关；0 直接写文档 |
| E04-3 | inspector section + importer + 节点注册 | 示例覆盖三类扩展；冲突报错 |
| E04-4 | panic 隔离/诊断/文档 + Lua 决策门 | Panic 插件不崩编辑器；决策记录 |

**验收门**

- `cargo test -p rustlua-editor-api`：manifest 解析/版本/能力；`cargo test -p editor plugins`：
  注册/加载/卸载/重复/panic。
- 示例插件：加面板、菜单、命令各一次；禁用后面板消失、命令不可用；重新启用恢复。
- panic 插件：在 `on_load`/draw/command 各 panic 一次，编辑器仍可交互，诊断有记录。
- 架构门：`rustlua-editor-api` 是叶子（不依赖 workspace crate）；`editor` 依赖它，反向无；
  `BUDGET`/成环测试绿。
- 安全负向：manifest 路径逃逸/未知能力/版本高 → 拒绝并打印原因。

**风险 / 回滚**

- **Rust ABI 陷阱**：不承诺动态 `.dll`；静态插件是 v1 的唯一稳定形态。需要动态扩展时走

- **安全边界**：进程内 Rust 插件是受信代码，permissions 只能约束 Lua/进程外；文档必须写清，

- **UI 质量/性能**：插件面板可能卡帧；Profiler 记录面板耗时，插件可禁用。
- **API 稳定性**：`api_version` 不匹配拒绝；每次破坏性改动升版本并写迁移说明。
- 回滚：禁用/删除插件；核心编辑器不依赖任何插件；`CoreEditorPlugin` 可退回内置。

**明确不做**：Rust 动态 ABI、插件市场/签名分发、热重载 Rust 插件、任意 egui 绘制沙箱、
完整 VS Code 扩展宿主。

### 6.12 P3-E05 自动布局 v2（3–4 人周）

**现状（实测）**：`ContainerKind` 只有 VBox/HBox/Grid/Margin/Center；`ChildLayout` 只有
`size/expand/fill`；`preferred_size` 缺省 64×64；`layout_container` 只排一层；
`resolve_node` 在容器分支给子节点写 rect 后没有递归子容器；没有 wrap/justify/min-max/
aspect/文本测量；Inspector 只能编辑容器样式，不能编辑子项约束。

**交付**

- 修嵌套：布局改为「自底向上测量 + 自顶向下摆放」两遍（或等价的递归带 available size），
  子容器先测 intrinsic 再被父容器摆放；避免指数重复测量，按子树 key 缓存。
- 新增能力：
  - `ContainerKind::Wrap`（按行/列换行）；
  - `Justify { Start, Center, End, SpaceBetween, SpaceAround, SpaceEvenly }`（主轴分布）；
  - 子项 `LayoutItem`：`min_size`、`max_size`、`preferred_size`、`grow`、`shrink`、
    `align_self`、`aspect_ratio`、`visible`；
  - 百分比/自动尺寸先只做「相对父容器」的百分比 + `Auto`，不做完整 CSS；
  - 文本/图片 intrinsic：通过 `TextMeasure`/`ImageMeasure` 端口由宿主提供，`rustlua-ui`
    不依赖 render；运行时与编辑器共用同一测量结果。
- 溢出诊断：容器内容超出时产出 `LayoutOverflow { entity, axis, needed, available }`；
  编辑器显示角标/日志一次；运行时 debug 日志；不静默裁剪。
- 缓存：布局缓存按子树/内容 hash 失效；Profiler 暴露 `layout_nodes/recomputed/cache_hits`；
  目标仍是叶子改动只重算受影响子树（docs/54 的差距）。
- 编辑器：
  - Inspector 的容器段增加 kind/justify/wrap/spacing；
  - 子项 `LayoutItem` 段（min/max/grow/shrink/align/aspect）；
  - 场景视图布局调试 overlay（bounds/padding/gap/overflow）；
  - 预设：Row/Column/Grid/Wrap；新增容器默认可用键盘/拖拽调整。
- 兼容：旧 `ContainerStyle` 字段缺省 = 今天的行为；旧场景不因新字段改变；新增字段全部可选。

**阶段**

| 阶段 | 内容 | 出口 |
|---|---|---|

### 6.13 P3-E06 更强 Profiler（CPU scope / per-pass GPU / 捕获，4–6 人周）

**现状（实测）**：`profiler.rs` 有编辑器 frame/panel/command 计时与 p50/p95/p99；
`runtime_perf.rs` 有 240 样本、fps/CPU/GPU/draw calls；`panels/performance.rs` 有文本报告/
冻结/清空/复制；`FrameScheduleReport` 已有 `steps/timings`（`runtime_scene/mod.rs:300–324`）
但没接面板；GPU timestamp 只有整帧（`renderer/timestamp.rs`），不是 per-pass；没有 trace/
flame/capture；docs/68 已列「不能按 panel/system 拆、GPU 依赖设备、无 per-draw debugger」。

**交付**

- **v1 CPU 归因（P3-A 必做）**：
  - 统一 scope：editor frame、panel、command、Lua update、ECS `FrameScheduleReport` 的每个
    system、physics、UI layout、render encode、asset import；
  - 有界环形缓冲（先 8k spans/帧，满了丢最旧并计数）；不能无界增长；
  - Chrome Trace Event JSON 导出（`traceEvents`，`ph:"X"`，`ts/dur`，`pid/tid`，`args`）；
  - 面板内 flame chart（egui 自绘）或至少 top-N 表 + 逐帧调用树；per-system 表直接读
    `FrameScheduleReport`，不再另算一套；
  - 开销预算：主线程 ≤2%（docs/55）；超过则默认关闭细粒度 scope，只保留系统级。
- **v2 GPU per-pass（P3-B）**：
  - 每个 render pass 的 timestamp（Shadow/DepthOpaque/WorldSprite/Legacy2DOverlay/
    ScreenUI/VectorText/Tonemap/PostProcess/Particle）；`QuerySet` + resolve/readback；
  - 不支持 timestamp 的后端显示 `unavailable`，不伪造 0；
  - 统计 pipeline/variant 数、shader 编译 ms、上传字节、queue submit 等待；
  - 整帧 GPU 时间与 per-pass 和做一致性检查（±5%），不一致标红。
- **v3 捕获/对比（P3-B/C）**：
  - Capture bundle：profile JSON + 场景快照 + RNG seed + 输入日志 + 引擎版本/提交 hash；
  - 重放：固定 dt/seed/输入，重跑并对比 per-system/per-pass/p50/p95；
  - 两次 capture diff（新增/删除/变慢 top-N）；阈值可配置；
  - 内存：Lua heap、资源解码缓冲、ECS/渲染估算、进程 RSS（Windows）；不做全局分配器
    插桩（release 开销不可接受）。
- 面板：Performance 增加 Capture/Export/Compare、per-system 表、per-pass 条形图、spike
  标记；保留现有冻结/清空/复制。

**阶段**

| 阶段 | 内容 | 出口 |
|---|---|---|
| E06-1 | CPU scope + FrameScheduleReport 接线 + per-system 表 | 一帧能按 system 拆；旧指标不变 |
| E06-2 | Chrome trace 导出 + flame/top-N + 开销门 | trace 能在 Chrome 打开；≤2% |
| E06-3 | per-pass GPU timestamp + cache/upload 指标 | per-pass 和 ≈ 整帧；不支持显式 |
| E06-4 | capture/replay/diff + 内存 + 文档 | 两次 capture 可对比；重放稳定 |

**验收门**

- `cargo test -p editor profiler`：环形缓冲上限、p50/p95、trace JSON 结构、spans 不丢字段。
- `wp0_profile_capture`：固定场景跑 120 帧，导出 trace；报告 `span_count/overhead_pct/
  systems/passes`；Chrome trace 至少能被 JSON 解析器 + `chrome://tracing`/Perfetto 打开
  （人工一次）。
- per-system：所有 `FrameScheduleReport.steps` 都出现在表中，时间和与 `total_elapsed` 一致；
  缺一个 system 判红。
- per-pass：支持 timestamp 时，各 pass 和与整帧差 ≤5%；不支持时 `gpu_pass_supported=false`。
- 开销：同一场景开/关 profiler，主线程 p50 差 ≤2%；超过则降级为系统级并记录。
- capture：同 seed/输入重放两次，per-system 时间在噪声容差内；场景状态 hash 一致。
- 内存有界：连续跑 10 分钟，span 缓冲/样本数不增长；面板不泄漏纹理。

**风险 / 回滚**

- **开销本身影响结果**：scope 太多会拖慢；默认只开系统级，细粒度按需开；始终报告开销。
- **GPU timestamp 不稳定**：不同后端/驱动可能抖动；用中位数/多次采样，不支持就明说。
- **per-pass 与整帧不一致**：query resolve 的时机/编码边界容易错；先做 3 个 pass，再扩。
- **Capture 重放不确定**：RNG/输入/物理步长都要冻结；不能保证 bit-identical 时，用容差并
  标「非确定」。
- 回滚：Profiler 是观测功能，关掉不影响渲染；per-pass 失败只隐藏该段。

**明确不做**：per-draw GPU debugger、厂商 GPU 计数器、远程/多进程 profiling、全局分配器
插桩、GPU 内存精确到字节、主机级 CPU 采样（perf/ETW）。

## 7. 总验收门与完成定义

### 7.1 每个包都必须过

```powershell
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features
cargo check -p game_web --target wasm32-unknown-unknown
powershell -NoProfile -File scripts\verify\check-silent-traces.ps1
powershell -NoProfile -File scripts\verify\check-docs.ps1
powershell -NoProfile -File scripts\verify\verify.ps1 -Quick
```

涉及 WebGL2/微信的包（R01/R03/R04/R07）再加：

```powershell
powershell -NoProfile -File scripts\verify\gpu-web-probe.ps1 -Stage backend
powershell -NoProfile -File scripts\verify\gpu-web-probe.ps1 -Stage render
powershell -NoProfile -File scripts\verify\verify.ps1 -Web
```

说明：`-Web` 依赖浏览器/Node/驱动，环境不满足时按仓库口径返回 **exit 3（BLOCKED）** 并打印
原因；不能把「没跑」写成「通过」。新增的 golden 必须接进 `verify.ps1` 的 golden 段（或独立
`-P3` 段）并提交 baseline；只在本地 `cargo run` 过一次不算进 CI。

### 7.2 完成定义（DoD）

一个包只有同时满足下面 8 条才算完成：

1. 代码 + 单测/集成测试进仓，`fmt/clippy/test` 绿；
2. 至少一条正向像素/读回/采样 golden，且报告可复跑；
3. 至少一条负向门（坏输入/不支持平台/超限/接口变更）；
4. 回退路径真实可用，并有回退测试；
5. Profiler/日志能看到当前档位与失败原因（无静默降级）；
6. 旧 golden（`wp0_2d_golden`/`wp0_3d_golden`/`wp0_mixed_golden` 等）零 diff 或有解释；
7. 文档更新：`docs/24` 或 `docs/25` + 对应新文档/本文件台账；
8. 架构门（新 crate/新边/组件 schema/面板）通过，未破坏 P1 的依赖预算。

### 7.3 批次出口

- **P3-A 出口**：HDR + 变体 + PBR + 材质编辑器 + 时间线 + Profiler v1 全部过；2D 旧 golden
  不变；一个 3D demo 能开 HDR/PBR 并在编辑器里改材质、存盘、重开。
- **P3-B 出口**：IBL + 热重载 + 插件 + 自动布局 + Profiler v2 全部过；WebGL2 上有明确 tier；
  示例插件与布局 golden 进 CI。
- **P3-C 出口**：compute + GPU 粒子 + 可视化脚本全部过；若 compute 探针否决，R06/R07 以
  「Unsupported + CPU 路径」收口，并在台账写「平台不支持」，不算失败、也不算 GPU 粒子完成。
