## 目标

`docs/30` §12 规划了 7 个节气事件（春分茶会 / 清明踏青 / 端午药集 / 夏至演武 / 中秋灯会 /
重阳登高 / 冬至封山），脚本里**零命中**；`scripts/world/calendar.lua` 全文 17 行，只算四季。
本任务把七条全部做成有入口、有消费方、可机器验收的内容：**节气 = `day` 的纯映射**，
效果走只读查询，四类消费方（采集 / 商店 / 出口 / 对话）各读一处，§12 的裁定照抄——不做完整农历算法。

## 实现要点（原计划的四条约束与落实结果）

1. **确定性是硬要求**：已落实。节气一律由 `day` 推导，全链路零 `math.random`；`world/festival.lua`
   无状态、无刷新钩子、无 provider，所以"读档/重进图/反复 `current()` 不能改变结果"这条是结构性的
   （没有可被改变的东西），实测见门 ⑧ 章。
2. **效果走查询函数，不走散落的 if**：已落实。运行时代码里**一次节气名都没出现**——
   `gather.lua`/`shop.lua`/`map_manager.lua` 只调 `festival.gather_rule` / `sell_bonus` / `exit_closed`，
   唯一的节气字面量在对话数据的 `cond.festival` 里（那是内容作者的意图表达，不是分支）。
3. **封山不能把玩家关死**：已落实并钉成断言。`exit_closed` 在数据里只点 `mountain_to_cave` 一个方向，
   且拒绝发生在**命中测试之后**（站在门口照常能按到 E，提示文案也不变），与 `42a565c` 的两个约束同批守住，
   实测见门 ⑦ 章（同一天：往洞里被拒 + 回村可用）。
4. **存档只存锚点不存派生值**：已落实，但锚点形状与计划猜的不同（见"实测更正"2）。

## 实际落地

- **`scripts/data/festivals.lua`（新，291 行）**：七条节气 = `(season, from..to)` 的闭区间 +
  `effects` 表。`validate_all` 守的是**时间轴与引用自洽**：窗口端点必须是整数且 `from <= to`；
  一张 `occupied` 表逐天查重（"同一天不能有两个节气事件"）；效果键白名单 `gather/sell_bonus/exit_closed`；
  `mult` 必须整数 ≥2、`one_time_daily` 只允许 `true` 或不填、`gather` 两个键至少给一个；
  `sell_bonus` 的每个物品必须存在**且有出售价**（+20% of 0 还是 0，那是一条假内容）、`bonus` 1..100；
  `exit_closed` 的出口 id 必须在 `data/maps.lua` 的 exits 里；每个季节至少一条事件。

## 实测更正（与计划不一致处，逐条给依据）

1. **reason 键名不是 `exit_closed_festival`**，实际是 `closed_festival`。计划里那个名字会撞上
   `jhyt_m26_hud_feedback` 的前缀表 `ACTION_PREFIX` 里的 `{ "exit_", "前往：", "map" }`：以 `exit_` 开头
   会被当成"前往：<地图>"动态拼接，独立中文映射永远读不到，负向用例还会把它判成"未登记的键"。
2. **`relationship.reward_once` 一次都没用**，节气也不是 `save_manager` provider。计划要点 4 猜
   "入档的只有本节气的一次性事件是否已触发"，实际一次性沿用了三种既有形状：对话 `set_var` 锚点
   （`teafair_started` / `xiazhi_drill_done` / `midautumn_lantern`）、任务状态（`order_tea` 的 completed）、
   采集记录自带的 `record.day`（重阳按日再刷）。**没有新的可入档字段**，所以 `main.lua` 一行未动
   （计划影响文件里那条不适用）。门 ⑧ 章把存档原文拿扫 `jieqi`/`festival`/`chongyang`/`qingming` 四根针，
   命中即红（`midautumn`/`teafair`/`xiazhi` 不能当针——它们是持久化 var 名的子串，会假红）。
3. **没复用 M34-00 的 30 天长跑骨架**，验收 ⑤ 章（"30 天长跑里节气/季节/天气互不漂移"）改写成门 ① 章的
   112 天逐日全扫 + 循环同余断言。理由：30 天只落在春分/清明两个窗口里（端午在 day 36），
   要真断言七条都不漂移必须跑到 112 天，那与全扫等价；把 112 天塞进 soak 会让那个门耗时翻倍却不带来新结论。
   现在 ① 章钉的是：事件日恰为 `8,9,10,15,16,17,36,37,38,43,44,45,64,65,66,71,72,73,99,100,101`
   （21 天 / 91 空天）、七条各命中 3 次、15 个边界日全空、`id(113) == ""`、`id(120) == id(8)`、`id(128) == id(16)`。
4. **`M.jieqi(day)` 返回条目表而不是"id 或 nil"**：消费方要的是 `effects`，`festival.id()` 才把 nil 折成 `""`。
5. **倍率按 `node.map`（节点所在图）查**，不是按调用方的当前图；一次性点的再刷判定同口径。
   写下来是免得后人当成笔误"改"回去——采集 API 没有传图的入参。
6. **docs/30 §12 的"中秋灯会 | 礼物、对话和结局变量"里"结局变量"没做**：M34-01 已把 `ending_sect`
   钉在 `sect/esteemed`（**正好 60 分的刀刃**），中秋再写 `ending` 变量会掀掉那份账，
   所以只给好感 +8 与莲子 ×3，并把这一偏离明写在 §12 的"实现落点"列里（表是机器读的，不能只改代码不改表）。
7. **风险 ① 说的两个常量一行未动**：`EXPECTED_REFERENCED=569 / DEV=47` 保持原样，本批不加对账条目，
   但实测确认这条红与本批无关（见"验收方式"末条）。
8. **新增一笔计划外的账**：`order_tea` 的云泽村声望 +8 把上限从 M34-01 记的 34 抬到 **42**，
   于是 `受信（40）` 第一次成为内容可达目标（村店 8% 折扣）。docs/33 §8.2 已改账、
   m24 ⑦ 的订单奖励表同步加 `order_tea 90`——**同一批交**，不留过期结论。
