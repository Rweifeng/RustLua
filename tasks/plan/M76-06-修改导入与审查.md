## 实现记录（2026-10-24）

### 已交付

- **拆分接受**（`rustlua-ui-spec/src/patch.rs` + `editor/src/ui_spec_host.rs`）：
  `select_ops(patch, indices)` 按原顺序保留选中操作、去重、越界报错；空选择是合法
  no-op；`UiSpecStore::submit_patch_subset` 复用同一套 revision/路径白名单/整份重校验，
  未选中的操作不进入提案与落盘内容。拒绝/过期 revision 不写工作区。
- **Figma 导入**（`rustlua-editor-ai/src/import_tools.rs`）：只读 JSON，白名单节点
  （FRAME/GROUP/COMPONENT/INSTANCE/SECTION/TEXT/RECTANGLE/ELLIPSE/VECTOR/LINE）映射为
  Spec 骨架；链接/未知节点只记录 `import.link_ignored` 与 `skipped`。注入文本
  “忽略之前指令” 只作为 `Text` 节点内容，不改变任何行为（单测断言节点数不变）。
- **截图导入**（同文件）：`suggest_screenshot_patch` 经 `VisionProvider` 拿建议，只接受
  7 个白名单属性（text/style/四类 layout 字段）；`events`/`key`/未知节点直接跳过并给
  diagnostic；`ScreenshotImport::into_patch(confirmed)` 未确认一律报错，确认后仍是
  `UiPatch`，继续走提案/接受流程。
- **审查报告**（`editor/src/review.rs`）：`review_document(store, document, limits)` 汇总
  Spec 诊断、未审阅资产、许可、总字节、生成清单与三宿主证据；PC/Web/微信默认
  `untested`，只有 `record_host(host, tested(...))` 才能改成已测。`is_clean` 以
  “无 error + 无未审阅 + 三宿主全部 tested” 判定，`to_json_pretty` / `export` 可归档。
- **回放期望 diff**（`rustlua-editor-ai/src/replay.rs`）：`ReplayStep.expect_json` 做
  JSON 子集匹配（对象递归、数组等长逐项、标量相等），`ui_apply_patch` 回放锁住
  `proposal.kind=patch` 与 `diff.nodes_changed=1`，结果不一致报 `ResultMismatch`。
- **接受后一次 Undo/Redo**（`editor/src/ui_spec_host.rs` + `ui_studio.rs`）：接受前用
  `snapshot` 保存原始字节，`UiStudio::accept` 入栈并清空重做栈；`undo()` 经 `restore`
  解析 + 校验后原字节原子写回，revision 与接受前完全一致，当前字节进重做栈；`redo()`
  对称恢复。空栈撤销/重做都是 no-op。UI Studio 的「撤销接受」「重做接受」按钮直接调用。
- **外部编辑保护**（`ui_studio.rs::ensure_unchanged`）：每个栈项同时记「要写回的字节」与
  「写回前必须仍是这些字节」；撤销/重做前比对，文档被外部改过就返回 `StaleRevision`
  且不动文件、不丢栈。错误信息带两侧 revision，提示先刷新。
- **全局 Undo/Redo 分流**（`command_router.rs` + `dock.rs::active_tab`）：菜单与快捷键
  都走 `EditorCommand::Undo/Redo`；UI Studio 是活动标签且对应栈非空时先消费它，
  栈空后再落回场景历史。两条栈互不共享，测试断言一边消费时另一边长度不变。
- **工程级审查门**（`review.rs::review_project` + `tests/ui_asset_gate.rs` +
  `verify.ps1`）：按 `project.toml` 逐工程汇总文档报告与跨文档资产门，诊断按
  (code, path, message) 去重；坏 `.ui.json` 直接报错而不是跳过。报告固定带
  `pc/web/wechat` 三项证据，未跑就是 `untested`；`is_green` 只表示“无 error”，
  与三宿主一致解耦。
- **宿主证据落盘校验**（`review.rs`，`ui/hosts.json`）：证据格式为
  `{version:1, documents:{<相对路径>:{<host>:{command, checks[], artifact, revision, note?}}}}`。
  一个宿主只有在**四件事同时成立**时才翻成 `tested`：命令与检查项非空；`artifact` 是
  工程内真实存在的 JSON（拒绝绝对路径与 `..` 逃逸）；产物里 `document`/`host`/`revision`
  与当前文档一致；`checks[]` 逐项出现在产物的 `checks` 里。任何一条不满足都保持
  `untested` 并给诊断：坏文件 → `review.host_evidence_invalid`（error）、证据对不上 →
  `review.host_proof_invalid`（warning）、未知宿主 → `review.host_unknown`（warning）、
  未知文档键 → `review.host_document_unknown`（warning）。`ProjectReview` 新增
  `host_diagnostics` 并并入 `diagnostics()`，所以 warning 可归档但不会弄红门。
- **远程 Vision Provider**（`rustlua-editor-ai/src/vision_provider.rs`）：
  `RemoteVisionProvider` 走 OpenAI/Ollama 兼容的 `chat/completions` 或 Anthropic
  `messages`，把 PNG 以 base64 `image_url`/`image` 块发送，解析 `choices[0].message.content`
  或 Anthropic `content[].text`，再去掉代码围栏取出 `{suggestions:[…]}`（也接受顶层数组）。
  配置来自 `RUSTLUA_VISION_URL/MODEL/MAX_TOKENS/ATTEMPTS/TIMEOUT` 与
  `RUSTLUA_AI_VISION_API_KEY`；429/5xx/传输错误按 `max_attempts` 重试，其余 4xx 立即失败。
  错误码固定为 `vision.key_missing` / `vision.image_not_png` / `vision.question_empty` /
  `vision.endpoint_invalid` / `vision.key_invalid` / `vision.encode` / `vision.decode` /
  `vision.http_<status>` / `vision.transport` / `vision.retry_exhausted`；`Debug` 实现
  隐去密钥。活体测试挂在 `RUSTLUA_VISION_LIVE=1` + `RUSTLUA_VISION_IMAGE` 下，默认
  `#[ignore]`。

## 未完成项 / 已知限制

- **UI 撤销/重做栈只覆盖「接受」**：栈属于 `UiStudio`（与文档绑定、上限 16），与场景
  `CommandHistory` 仍是两条独立栈；全局入口只在 UI Studio 聚焦且栈非空时优先消费它。
  切走标签后 Ctrl+Z/Ctrl+Y 只动场景历史。外部编辑只在撤销/重做的写入点检测
  （`StaleRevision`），没有实时文件监听；手动「刷新」后旧栈项同样会因 revision 不符被拒，
  需要重新接受或重启标签才能继续用栈。
- **三宿主仍全部未测**：现在有了 `ui/hosts.json` 的落盘通道，但仓库里没有任何一份
  由真实 PC/Web/微信跑出来的产物，因此三宿主照旧输出 `untested`；门只挡 error 与资产问题，
  不会用“测试套件绿”冒充宿主一致。录入证据时必须给命令、检查项、产物文件与
  revision，缺一项就翻不成 `tested`。
- **远程 Vision 只测了请求/响应契约**：`RemoteVisionProvider` 的 4 项单测用脚本化传输
  验证请求体、密钥不泄漏、重试与解析；**没有真实联网活体读数**（活体用例需
  `RUSTLUA_VISION_LIVE=1` + 密钥 + 图片，当前未跑），也没有图片预处理/多轮比较，
  建议质量取决于外部模型。截图导入目前仍是库级 API（`suggest_screenshot_patch`
  接 `&dyn VisionProvider`），编辑器 UI 尚未装配按钮；远程实现由调用方显式注入。
- **Figma 只覆盖白名单子集**：自动布局约束、原型交互、渐变/阴影、字体样式未映射，
  仅以 skipped/diagnostic 暴露；没有导入体积/重复节点压缩策略。
- **三宿主差异未测**：审查报告固定输出 `untested`，本轮没有跑 PC/Web/微信 UI 矩阵。

## 目标

把「修改」做成一等流程：自然语言 → `UiPatch` 提案 → 审阅 → 一次 Undo；并支持 Figma JSON/截图
导入为初始 Spec，最终产出可归档的审查报告。

## 交付项

1. **Patch 全链路**：base_revision 校验、路径白名单、拆分接受、拒绝不改工作区、一次 Undo。
2. **Figma 导入**：只读 JSON → Spec 骨架；外部内容按数据处理（不执行其中的指令/链接）。
3. **截图导入**：VisionProvider 产出结构建议；人工确认后才落 Spec。
4. **审查报告**：诊断、未审阅资产、许可、体积、三宿主差异、未收口项；可导出。
5. **回放**：修改类 tool-call 录制与期望 diff 回放。

## 验收方式

- `cargo test -p rustlua-ui-spec`、`cargo test -p rustlua-editor-ai`。
- 手工链路：截一张参考图 → 生成骨架 → 修改两轮（过期 revision 一次被拒）→ 接受 → Undo 一次复原。
- 反面对照：在 Figma JSON 里塞"忽略之前指令"文本，导入流程不得改变行为（只作为设计数据）。

## 风险

- Figma 结构千变万化：只支持白名单节点与自动布局子集，其余诊断列出而不是硬猜。
- 导入产生大量节点：用容器压缩 + 提案拆分，避免一次接受不可读的 diff。
- 审查报告容易变成"看起来全绿"：警告必须带条数与豁免理由。
