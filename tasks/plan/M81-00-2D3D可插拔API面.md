- 任务 ID：M81-00
- 状态：批 0/1/2/3 全部完成（2026-11-07/08，未提交）；批 4 = P2 不在本包
- 关联里程碑：M81（2026-11-07 新增；M80 已被 UI 子系统五星期收口占用，见 docs/76）

## 目标

让"做 2D 游戏时发布的 Lua API 只含 2D 面"成为可构建、可验证的形态：2D 基底 + 3D 可叠加
feature 包。**不做**对称的两个平行引擎（docs/54 的统一收敛不回退：相机/Transform/深度/资源身份
保持单一事实源）。

## 范围分档（先写清买不到什么）

- **P1（本包主体）：API 面裁剪**。2D 构建的 Lua `_G` 只有 2D 面（392 → 约 314 函数）。
  **二进制基本不变小**——3D 渲染/物理代码仍编译链接；收益是 API 契约清晰 + 为 P2 铺路。
- **P2（另立工作包，本包不开工）：代码级裁剪**。feature 下沉 render/gpu/physics/assets/
  animation 等 crate，真正减 wasm/微信包体。前置：先量 3D 代码在 wasm 里的占比，再裁定做不做。

## 盘点结论（2026-11-07，事实源 `lua_api_surface.json`：48 表 / 392 函数）

- **A 类：整表直接门控，9 表 / 58 函数**：`animation3d`(7)、`camera3d`(5)、`light`(4)、
  `mesh`(4)、`nav`(11)、`physics3d`(10)、`terrain3d`(7)、`transform3d`(7)、`water3d`(3)。
  注意 `nav` 名字不带 3d 但属 3D 包（`nav_lua.rs` 头注：格子对应 3D 战场 XZ 平面，
  返回值直接喂 `transform3d.set`）；`light` 是 3D 方向/点光（引擎没有 2D 光照系统）。
- **B 类：混合表，函数级门控**：`camera` 的 `set_clip_plane`（写 Camera3D 载荷；`get` 返回的
  `clip_*` 字段保留）；`particles` 的 7 个（burst3d/stream3d/stop_stream3d/clear_streams3d/
  wind3d/set_wind3d/set_wind_source）；`render` 的 12 个环境/后处理函数（留 stats/set_quality）。
  `audio` 的 play_at/set_listener/listener 是 3D 空间音频，**整表保留不门控**（2D 无害）。
- **C 类：基底保留，35 表**：2D 专属（animation/camera2d/physics/quad/sprite/tilemap/
  world_text）+ 维度无关设施与 gameplay 表。

## 方案（用户已批准，2026-11-07）

### Feature 设计

命名 `3d`，默认开；2D 发布 = `--no-default-features`（沿用 editor `ai-bridge`、game_web
`gpu2d` 先例）。**链上每条依赖边都必须 `default-features = false`**，漏一条 feature 统一就把
3D 悄悄开回来——批 0 的反面对照门防的就是这个。2D 验证只构建叶子包，不做 workspace 级
no-default。

| crate | features | 门控内容 |
|---|---|---|
| `rustlua-gameplay` | `default=["3d"]` | `input_lua::registry()` 里 nav 的 add（组合根） |
| `rustlua-scripting` | `default=["3d"]`, `3d=["rustlua-gameplay/3d"]` | `register_all` 的 3D installer 调用 + particles/render_tuning 函数级 cfg |
| `engine` | `default=["3d"]`, 透传 scripting/gameplay | 纯透传（host 不注册 API） |
| `game` / `game_web` | `default=["3d"]`, 透传 engine/scripting/gameplay | 叶子出口；game_web 与 `gpu2d` 并存 |
| `editor` | 不动 | 编辑器永远全量 |

### 注册层手法（P1 领域 crate 零 feature，除 gameplay）

`ui` 表三段式先例：表是引用语义，各 installer 拆出 `install_3d`（建 3D 专表 + 向共享表补
3D 函数），`register_all` 在调用点加 cfg：

- `renderable_lua`：install 留 sprite/quad；install_3d 装 mesh/light/terrain3d/water3d
- `camera_lua`：install 留 camera/camera2d；install_3d 装 camera3d + 补 camera.set_clip_plane
- `transform_lua` / `animation_lua` / `physics_lua`：install_3d 装 transform3d / animation3d / physics3d
- `particles` / `render_tuning`（scripting 本层）：函数级 cfg

### 门生态

- **快照门双基线**：全量 `lua_api_surface.json` 不动；新增 `lua_api_surface_2d.json`
  （`dump_lua_api --no-default-features` 生成）；测试按 cfg 各比各的。
- **覆盖率门**：事实源是运行期 `_G`，2D 构建自动只要求 2D 面 100%，零改动；自测要加
  "demo 调用了本构建面外 API 则静态扫描跳过并打印原因"（全量模式行为不变）。
- **文档桩/rustdoc 永远全量**（引擎文档不按维度残缺），gen-lua-api-docs.js 不动。
- **LuaLS**：生成器加 `--surface` 参数产 `rustlua_api_2d.d.lua`（批 3，可裁）。
- **cfg-inventory**：新 cfg 点登记 `metrics/inventory/cfg-sites.json`。
- **verify/CI**：新增 `scripts/verify/check-api-2d.ps1`（2D 快照测试 + game no-default
  `--check` + engine 样例门 no-default 段），CI 加一步；**不塞进 verify.ps1 默认串行段**。
- **产品接线（批 3）**：`project.toml` 加 `api = "2d"|"3d"`（默认 3d）；`package.ps1` 读到
  2d 给 game/game_web 构建加 `--no-default-features`，发布后跑 2D 面探针复核。

### 反面对照（每批必跑，证明门会红）

1. 2D 构建里故意注册一张 3D 表 → 2D 快照门必须红；
2. 删掉一个 2D 演示 → 2D 覆盖率门必须红（批 3 门改完后跑）。

## 风险

- **feature 边漏改 ⇒ 2D 构建静默变全量**：反面对照门 + 2D 基线逐项比对防住。
- workspace 继承依赖的 `default-features=false` 语义：以批 0 实测（2D 面里 nav 必须消失）
  为准，不以文档记忆为准。
- 既有坑规避：文档桩行数耦合（桩永远全量，行号漂移靠再生成吸收）；`-MvpOnly` 串行锁（2D 门独立脚本）；
  GPU 并发假红（2D 段不含 GPU 测试）。

## 决策点（2026-11-07 用户批准，按推荐项）

1. feature 名 `3d`；② audio 空间函数保留；③ 文档桩永远全量；④ P2 缓做、先量体积。

## P2 预研：3D WASM 增量实测（2026-11-08）

同一当前工作树、同一 wasm 发布优化链做 3D/2D A/B；2D 明确保留 `gpu2d`，避免把渲染宿主差异
混入 3D 维度差异。Rust 侧均用 `cargo +1.88.0 build -p game_web --release
--target wasm32-unknown-unknown`，分别默认 feature 与 `--no-default-features --features gpu2d`；
两边统一 `opt-level=z`、fat LTO、1 codegen unit、`strip=none`。再用 wasm-bindgen 0.2.129
（`--target web --no-typescript --remove-name-section`）及 Binaryen 133 `wasm-opt -Oz`。
两份优化后模块均通过 Node `WebAssembly.compile`。工具链固定记录：rustc 1.88.0、
zig 0.16.0、wasm-bindgen 0.2.129、Binaryen 133；Cargo 原始 wasm 用 Twiggy 0.8.0 做符号归因。
Twiggy 报告输入使用同一配置下 `strip=none` 的 `game_web.wasm`，保留函数名以便归因；它是分析
中间件，不是发布体积口径。

### 符号与依赖归因（同日）

`twiggy top` 的原始 wasm 符号表对齐后，3D 构建有 57 个 2D 构建中不存在的具名函数，共
35,118 bytes；反向仅 3 个函数 / 103 bytes。两者具名函数体积净差 173,137 bytes，与 Cargo
原始模块总差 211,948 bytes 不同，因为模块还包含函数名、数据、调试及其他自定义段，且部分
共享/泛型函数在两种 feature 组合中的代码尺寸变化。故不能将具名函数增量直接当成 3D 总占比。

2D 构建中仍可直接归属到 3D 的第三方具名函数体积（Twiggy 原始函数浅尺寸）：

| 2D 产物中的 3D 候选 | 函数数 | 原始函数浅尺寸 | 依赖树 / 代码归属 |
|---|---:|---:|---|
| `rapier3d` | 107 | 150,650 bytes | `rustlua-physics` 无条件依赖；还被 `rustlua-scene`、`rustlua-scripting` 直接纳入组合 |
| `parry3d` | 212 | 134,611 bytes | 随 `rapier3d` 引入 |
| `gltf` | 35 | 37,109 bytes | `rustlua-assets` 无条件依赖；由 3D 懒加载路径消费 |

`cargo tree -i gltf` 也确认当前 2D 组合没有切断这两条依赖链。

### 改造面与裁定

首批候选集中在 `rustlua-physics`（让 Rapier/Parry 3D 依赖和实现随 feature 门控）及
`rustlua-assets`（评估 glTF 解析 API 与动画 3D 消费者的门控）。之后还须检查 GPU/渲染器、
相机、ECS/变换、动画与场景组合根中混合 2D/3D 的代码，不能按 crate 整体移除。322,370 bytes
是当前 2D wasm 里可识别的原始第三方函数体积，不等于经 LTO、wasm-bindgen 和 `wasm-opt -Oz`
后的可回收发布字节；确切收益须在各候选 feature 实现后以同一发布链复测。

**裁定：P2 继续不立项。** `game_api` 2D/3D 实际发布对照显示微信主包约 3.49 MB 余量、总包约
11.1 MB 余量；3D 增量没有造成当前示例工程的配额压力。仍未证明 322 KB 候选经 feature 门控后
能回收多少优化后的发布体积，而跨 physics / assets 到 animation、scene、render、GPU 和 engine
组合根的改造及完整行为回归，不值得仅凭原始函数浅尺寸提前开工。这个结论只对当前示例工程成立；
若目标游戏实测接近平台预算，再以 Rapier/Parry 与 glTF 两条依赖链为小型验证切片，测优化后
净减量及行为回归成本，再决定是否扩到全量 P2。
