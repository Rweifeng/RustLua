## 目标

`scripts/data/buildings.lua:47-60` 的 `tea_shed` 自己写着"2x2 纯建筑（装饰/占位，验证多建筑共存与占用互斥）"，
`station = nil`（`:59`）——所以它永远进不了制作系统。而 `docs/33` §7.2 的建筑表早就定好了三档：
**解锁茶饮 / 社交收益 +10% / 解锁节气事件**。本任务把这三格填上，顺带补上"社交收益"这条零实现的循环
（目前送礼加分是固定值，`relationship.add` 没有任何乘子）。

**实测更正（认领时）**：茶叶这条链子已经存在，不是从零起。`data/items.lua` 有 `tea_leaf:217` 与 `tea_brew:275`；
`data/recipes.lua:69-76` 已有 `kitchen_brew_tea`（膳房 station、`tea_leaf×2 → tea_brew`、20 分钟）；
`data/gather.lua:120-123` 有 `wild_tea_1` 采集点产 `tea_leaf`；`data/shops.lua:68,70` 既卖 `tea_brew`（20 文/限 5）
又收 `tea_leaf`。真正缺的只有两格：**茶棚自己的 `station`（现在归膳房）与社交乘子**。
下面"影响文件"里的 items / gather 两条按此缩小：不新增物品，只把配方挂到 tea station 并做档位差异。

## 实现要点

1. **一次一杯的限次**沿用 `relationship.gifted_day` 的形状（`:32`、`:150-154`、`:209-212`）：
   当日第二杯不再加社交，返回同族 reason（如 `tea_today`），**不扣物品不加分**——
   与送礼那条"每日 1 次"是同一族语义，两条实现要贴在一起，别各写一套日期比较。
2. **社交乘子的合成规则要写在数据里**：茶棚等级 ×1.1（docs/33 §7.2 "社交收益 +10%"）与饮茶 buff 是加还是乘、
   上限多少，先在 `docs/33` §8.1 加一行口径再实现；用例断言具体新分数（"10 点 → 11 点"这种），
   不写"应该变多"的软断言。
3. **解锁节气事件 = 门，不是新机制**：M34-02 的 `festival.available()` 加一条"茶棚 ≥ 3 级"的条件；
   节气效果本身不读建筑。顺序上 02 先落地，本任务只做加法。
4. **茶叶要能被校验**：新物品/新配方进 `data/registry_check.lua` 与 `validate_data.lua` 的引用完整性
   （种子/收获物必须存在且分类正确那条对茶叶同样适用）。

## 风险

- ① 新物品会牵动 `jhyt_m24_numeric_alignment` ② 的商店价表比对（新增商品必须在表里有行，
  或显式进 `SHOP_ROWS_WITHOUT_DATA` 白名单，示例头注释 §3 就是为此设计的）。
- ② `relationship.add` 加乘子会改动 `jhyt_m18_stats`（M18-04 送礼限次那组）的期望分数。
  先跑它再提交；被改的每个期望值在实现记录里写明来自哪条口径。
- ③ 建筑 `levels` 从 2 档扩到 3 档涉及 `systems/building.lua` 的升级与存档 `min_level` 校验，
  与 M34-00 的版本门同期改动时**按文件切批**，不要同一笔。
