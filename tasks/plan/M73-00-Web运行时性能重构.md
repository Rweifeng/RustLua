**本轮踩到并记录的坑**：用 PowerShell 5.1 对 UTF-8 文件做 `Get-Content -Raw | Set-Content` 往返
会**不可逆损坏**内容——它按 ANSI(936) 解码 UTF-8 字节，GBK 前导字节会把后面的 `0x0A` 当尾字节吞掉，
于是既丢字符又丢换行（本台账被这样毁过一次，按反解骨架 + 上下文原文重建）。
改文本一律用 `edit`/`write` 工具；确需命令处理时显式指定编码（`[System.IO.File]::ReadAllText/WriteAllText`
配 `UTF8Encoding($false)`），绝不用 `Get-Content -Raw | Set-Content`。

## 实现与验证记录

### WP1（已完成）

按「正确性是性能优化硬约束」的口径，先修可证伪的缺陷，再做结构性替换。

1. **时间步与 Rust 权威对齐**（`plugins/webgl/web-runtime.js`）
   Web 侧原本按 rAF 回调次数当作步数，与 Rust 权威 `FixedTimeStep::new(60, 8)`
   （`engine/crates/rustlua-infra/src/time_step.rs`）不一致。现状改为同一套规则：60 Hz 固定步、
   `elapsed` 累积、最多 8 步追赶、超出丢弃并计数；`visibilitychange` 后重置时钟；
   每步注入输入并在 step 0 后清边沿（`__rustlua_finish_step_input`，对应 `InputSnapshot::finish_frame`）；
   帧阶段用 `delta * steps` 作为 `time.delta()`。诊断写 `data-rustlua-timing`（steps/dropped/acc）。
   新增 `lua_set_number`（`engine/crates/game_web/src/lua_bridge.rs`）供逐帧写 `__rustlua_dt`，
   不再为此每次编译一小段 Lua chunk。
   容忍度 `STEP_EPSILON` 是对 Rust 严格 `>=` 的**有意偏离**：那边 elapsed 是构造出来的
   （`1.0/60.0` 与 `1.0/60.0` 逐位相等），这边来自 `performance.now()` 差值，真机"正好一帧"
   常落在最后一个二进制位之下，严格比较会让步数在 0/1 之间抖动。
2. **WASM 兜底通道判定错误**（`plugins/wechat-minigame/wasm-bridge.js`）
   首选通道失败、兜底通道成功时，原实现无条件返回 `{failed:[first,second]}`，把"兜底成功"
   判成启动失败。现返回兜底结果并记 `fallbackFrom`。
3. **微信音频资源路由**（`wechat-adapter.js` 的 `assetSrcFor` + 运行时 `wechatAudioCandidates`）
   音频此前自己拼 `pack/...` 三种写法：分包形态下首屏音频在 `mainpack/`（构建期搬运），
   远端形态下资源根本不在包里——两种情况下都指向不存在的文件，表现为"有画面没声音"。
   现在统一问适配层（主体路由 + 改名 + 远端 URL），结果按音效名缓存。
4. **远端缓存的发布标识**（`wechat-adapter.js`）
   缓存键原本只有逻辑路径且命中即返回、只在新下载时校验，发新版本后旧缓存永久遮蔽新内容。
   现按清单文本指纹加发布级标识目录，并在换版时清掉上一版目录；清单自身恒走不带标识路径
   （否则先落盘清单再算标识会永远停在上一版）。
5. **染色瓦片缓存保留**（`web-runtime.js`）
   `tintedTileCache` 外层键是图集 `Image`，而 `loadImage` 每次新建 Image，每换一次场景就
   多一条永不使用的条目，各持有最多 512 张离屏画布。现加外层预算 + 换场景显式释放。
6. **诊断开销移出生产路径**（`web-runtime.js`）
   全画布 `getImageData`、`willReadFrequently: true` 以及每帧两次跨 wasm 边界的 Lua 调用
   （`__rustlua_world_summary` / `__rustlua_tilemap_layers`）此前无条件生效。现由 `DIAGNOSTICS_ON`
   （`?rustlua-diagnostics=1` / `__RUSTLUA_DIAGNOSTICS`）显式开启；两个验收入口
   （`verify-webgl-bundle.ps1`、`wechat-minigame-harness.js`）已显式打开，门不因此变红；
   微信适配层在开启渲染自证覆盖层时会替我们打开诊断（否则覆盖层会显示成"世界是空的"）。
   `data-rustlua-timing` 例外常驻：三个数字、无跨界调用，而刷新率无关性要在真机不开开关自证。
7. **启动链超时可观测**（`wechat-adapter.js`）
   看门狗原本在 wasm 兑现之后才 arm，且实例化本身无超时：分包挂载或
   `WXWebAssembly.instantiate` 半死时是黑屏 + 0 error + 无任何提示。现看门狗覆盖整条链并报
   阶段（`data-rustlua-boot-phase`），实例化按独立超时（默认 15s）结算为失败。
   `__RUSTLUA_DIAG()` 里诊断读数缺失时报 `off` 而不是 `0`——"没采样"不能长得像"世界是空的"。
8. **桥接门面白名单漏项**（`plugins/webgl/index.html`、`plugins/wechat-minigame/wechat-adapter.js`、
   `scripts/wasm-lua/verify-wasm-host.mjs`、`scripts/wasm-lua/verify-no-modules-bridge.mjs`）
   ——**这条是端到端跑出来才发现的，也是本轮最值得记的一条**：
   `window.__RUSTLUA_LUA_BRIDGE` 不是 wasm-bindgen 模块本身，而是各平台自己手写的一份
   **显式白名单**（webgl 在 `index.html`，微信在适配层）。我在 Rust 侧加了 `lua_set_number`
   导出、在运行时里调用它，却漏了这两份名单 → 真机/浏览器上表现为**启动即失败**，
   且原始报错只有一句 `is not a function`。
   修法：两处名单都补上；同时把 `lua_set_number` 加进两个 wasm 导出门的必需清单
   （`bridge_exports` 7 → 8），这样以后同类漏项会在**打包前**被拦住，而不是等到浏览器里。
   **教训**："新增一个宿主 API"在这套代码里是**四处**改动（Rust 导出、运行时调用、
   两份平台门面），漏任何一处都不是编译错误，而是运行期才炸。
9. **no-modules 胶水守卫误报**（`scripts/package.ps1:685-693`）
   微信打包在"wasm-bindgen call guard 补丁"那一步抛 `no-modules glue shape changed`。
   守卫本身是好东西（它防的是：胶水读 `__instance_terminated` 这个 Global 导出，而 iOS 分支
   会把全部 Global 剔掉 → 第一次跨 wasm 调用就 `Cannot read properties of undefined`，
   实测 2026-10-03 的微信包正是这么白屏的），但它只在**纯 try_table**（rustc 1.88）产物上不成立：
   当前 wasm-bindgen 0.2.129 的 no-modules 产物里 `call_guard` / `__instance_terminated` /
   `WebAssembly.Tag` **全是 0 处**。证据是仓库里**上一次成功打包**的发布产物
   （`builds/wechat-minigame/launcher/pkg/game_web.js`，2026-09-30）形态与今天一致——
   也就是说这个守卫自写下起就在误报，**微信打包从 10-03 起一直是断的**。
   修法：把二元判断改成三分支——命中就补；**胶水根本没引用 `__instance_terminated` 就跳过**
   （没有可补的东西）；引用了但写法不认识才 `throw`。保留"响亮失败"的那一面，只放过"确实没事"。
10. **出厂 JS 用了 ES2020 的 BigInt 字面量，微信上传器只到 ES2019**（`web-runtime.js` 原 119-159 行）
    ——**这条被上一条掩盖了**：守卫先抛，就永远走不到上传语法门。
   官方报 `Identifier directly after number`（`1n` 的 `n`），13 个 BigInt 字面量 + 5 处
   `BigInt()`，全在 64 位瓦片变体哈希里。`??=` 之类**不存在**（唯二的 `??` 在注释里，
   terser 会剥掉），所以违规面就是这一处。
   改法：把 64 位值一律表示成 **[hi, lo] 两个无符号 32 位**，手写乘法/右移/取模——
   BigInt 每次都分配，手写版在热路径上零分配，顺带更快（同一台机、同样入参 20000 次：
   19.4 ms vs 46.7 ms）。
   **正确性不靠"看着对"**：旧 BigInt 实现原样留作 oracle，新增
   `scripts/web-u64-hash-test.js` 对拍 **7203 例**（含负种子、±2^53、坐标到 2^31、
   12 种变体数）+ 20 万次乘法抽查 + JS↔Lua 一致性门（56 格金标、6/6 常数）。
   **写这个替换时真踩到一个坑，值得记**：64 位乘法按 16 位分段时，进位**不能**用
   `x >>> 16`——`c1`/`c2` 会超过 2^32，而 `>>>` 先做 ToUint32，会把高位进位丢掉
   （20 万次随机乘法里 7% 错一个字，而且**前 5 步 FNV 恰好都对**，只有 avalanche 露馅）。
   必须用 `Math.floor(x / 0x10000)`。fuzz 对拍就是这么抓到的。

### WP3（第一片：每帧输入批量 ABI，已完成）

WP3 的目标是"统一 Rust 模拟与帧接口"。第一片只做**帧接口里最贵的那条**：每帧输入。
（"统一模拟"本身还没开始，见"未完成项"。）

**动机是实测的，不是推断的**：现行每帧输入协议（`__rustlua_input = {…}` 拼源码 + `lua_do_string`
编译）在 wasm 上 **10.41–10.82 µs / 2,648 B Lua 垃圾每帧**，其中 **87–88% 是"编译 + 跨界编组"**
（见 WP0 续一节）。按 60 Hz 算，这是 ≈0.62 ms/秒 CPU 与 ≈155 KB/秒垃圾——垃圾那一项甚至比 CPU
更要紧，因为它以 GC 停顿的形式出现，而停顿落在帧中间就是掉帧。

**做法**（三个新文件 + 五处接线）：

1. **新 crate `engine/crates/rustlua-frame-abi`**：定义 `RLFI` 批量线格式，164 字节定长
   （`MAGIC`/`VERSION`/帧号/2×f64 轴/4×f64 双项表/128 键位图 + 64 鼠标位图，小端）。
   键表 128 槽、鼠标 64 槽，**顺序即位序**；偏移表由 const 断言钉住
   （`offsets::MOUSE_JUST_RELEASED + 8 == WIRE_LEN`），11 个单测覆盖往返、f64 逐位相等、
   头字段、长度/魔数/版本不合法、表外位、键表唯一性与大小写不敏感查找。
   轴与光标用 **f64**（不是 f32）：这两条是要与旧协议**逐位相等**的，压缩精度会变成
   "光标偶尔跳一个像素"这类只能靠眼睛发现的问题。
2. **`game_web` 两个导出**（`engine/crates/game_web/src/lua_bridge.rs`）：
   `input_frame_layout_json()` 把**布局与键表**交给 JS（JS 侧因此**不手写任何偏移**——
   偏移写错一个字在 JS 里不报错，只会让某个字段读到另一个字段的值）；
   `lua_input_frame(bytes)` 解码 → 校验 → **原地改常驻表**（差分只动变化的位）。
   差分语义与旧协议严格对齐：**按住集合消失写 `false`，边沿集合消失写 `nil`**，
   否则"松开方向键后角色还在走"或"点一次触发好几次"。
3. **运行时打包器**（`plugins/webgl/web-runtime.js`）：复用同一块 164 字节缓冲，
   每帧零分配；位图写成 4 个 u32 小端字，**不能用 `setBigUint64`**（要 BigInt = ES2020，
   而微信上传器只到 ES2019，M73-00 已经因此被拒过一次整包）。
   旧的"每帧拼源码"路径**整条删除**；缺导出时按 `lua_set_number` 同一口径**响亮失败**
   （"产物换了一半"属于发布故障，静默退回旧协议会把它降级成"手感有点怪"）。
   新增常驻读数 `data-rustlua-input`（`frames`/`bits`/`unmapped`，纯 JS 计数器、不额外跨界）：
   `bits` 恒为 0 就是"宿主与 wasm 对哪些位该变理解不一致"的第一手线索，`unmapped` 列出
   落不进键表的键名——"某个键按了没反应"要能一眼分辨是"宿主没送到"还是"线格式不认这个名"。
4. **门面白名单与导出门清单**：照 WP1 第 8 条的教训一次做全——两份平台门面
   （`plugins/webgl/index.html`、`plugins/wechat-minigame/wechat-adapter.js`）与两个 wasm 导出门
   的必需清单（`bridge_exports` 8 → 10）同步补齐。

**三条是"跑门跑出来的"，不是设计时想到的**（记在这里，因为它们各自代表一类缺陷）：

- **预置表漏了 `press_cursor`**。旧协议每帧**整份替换**表，第一帧就把它补上了，所以这个缺口
  七年都不会显形；改成原地改表之后，它立刻表现为 `lua input frame: error converting Lua nil to table`。
  修法：预置表补齐 11 项，并把应用器改成**报出缺的是哪张子表**（mlua 的原生报错指不出这一点，
  而修的地方在 Lua 预置表、不在调用点）。
- **线路键表漏了 `'+'` 和 `'_'`**，而游戏绑定表里就有
  （`volume_up = {'=', '+'}`、`volume_down = {'-', '_'}`）——症状是"Shift+= 调不了音量"，
  只在该按键、该平台出现，靠手感几乎不可能定位。修法：补齐 Shift 之后的**字符形式**
  （浏览器给的是 `event.key`，按住 Shift 时 `=` 就是 `'+'`），键表 84 → 105 项（余 23 槽）。
  并新增**静态门** `scripts/check-input-abi-parity.mjs`：把 Rust 键表、预置层 `bindings` 表、
  宿主 DOM 键名经 `keyName()` 归一后的结果三份来源对起来，构建前即可判红。
- **测试数据也必须"像出厂"**。第一版对拍每帧新建快照对象，于是"多键同时松开"那组冒出
  假差异（旧的少几个 `false` 项）——真实运行时 `state.keys` 是**常驻对象**、松开后保留 `false`
  且此后每帧都带它。快照构造已改为与 `createWebInput` 同构。**协议没问题，是"对拍的一方不像被测物"**。
  同一条门里还揪出我自己的两处测试 bug：位地址算成 `(slot-1)/8`（小数索引 → `|=` 静默 no-op，
  于是"应该抛错"的负例假通过）、以及内部字段名写成快照名导致 `mouse_just` 变 `nil`。

### WP3（第二片：每帧源码编译清零，已完成）

第一片把**输入快照**从"每帧编译一段 Lua 源码"换成批量二进制之后，热路径上还剩同类写法，这一片清零。

**先纠正一处此前的说法**：计划里写的是"把 `lua_call_global` 的 JSON 参数折进批量帧接口"。读代码发现
`lua_call_global` 在 Rust 侧**本来就没有编译源码**（`lua_bridge.rs`：取全局 → `Function::call`）；
它 1.25–1.40 µs 的开销来自**每次调用都解析一遍参数 JSON 并字符串化返回值**。所以这一片的目标是
"去掉每次调用的参数解析"，不是"折进批量接口"——后者的收益只有 0.16 µs/次，不值得为它加一个新协议。

**改动（语义不变；Lua 侧那两份实现仍是唯一事实源）**

1. **新增 `lua_call_global_void(name)`**：取全局函数直接调用，**不收参数 JSON、不字符串化返回值**。
   给"无参无返回"的钩子用——每步的 `__rustlua_apply_virtual_input` 与首步之后的
   `__rustlua_finish_step_input` 以前是 `doString(L, '__rustlua_apply_virtual_input()')`：
   **每个固定步为同一段永不变的源码编译一次**。全局不是函数时**报错**（旧写法也会报
   `attempt to call a nil value`），所以"预置层没跑到 / 宿主缓存了旧运行时"依旧当场可见，
   不会被降级成"虚拟按键偶尔不生效"。
2. **空参数快路径**：`parse_args_json` 把**空串**当成"没有参数"（`"[]"` 仍接受），JS 侧 `callGlobal`
   无参时传空串。每帧这样的调用有 4~5 次（`update`、`__rustlua_export_state`、`__rustlua_export_ui`、
   `__rustlua_export_scene_text_hidden`）。
3. JS 侧新增 `callLuaHook(name)`（与 `setLuaNumber` 同一口径：导出缺席时指明是哪一边旧，不做静默
   兜底），两处 `doString` 调用点改走它。

**读数**（新旧两条路**同一次运行内**并排；`scripts/wasm-lua/measure-lua-boundary-wasm.mjs`，
wasm 3,984,559 字节，5 轮 × 3000 次取中位数）

| 操作（同一件事的两种写法） | µs/次 | Lua 堆 B/次 |
| --- | --- | --- |
| 无参钩子：编译源码（旧） | 1.354 | 236 |
| 无参钩子：直接调用（**新**） | **0.421** | **0** |
| 全局调用：空 JSON 数组 | 0.735 | 0 |
| 全局调用：空串无参（**新**） | **0.575** | 0 |
| （参照）全局调用：带一个 JSON 参数 | 1.253 | 0 |

⇒ 钩子 **3.2×** 且分配清零；无参调用 1.28×。按每帧 `steps + 1` 次钩子 + 4 次无参调用算，每帧省约
**1.6 µs**（steps=1 时约 −24% 的 Lua 交互时间）。**CPU 仍不是重点**——重点是那 **236 B/步**的 Lua
垃圾归零（60 Hz 下约 14 KB/s 的分配变成 0），这是第一片之后剩下的最后一块。
（重复跑的中位数区间：旧 1.330–1.354 µs、新 0.390–0.421 µs，即新路径稳定在旧的 3 成左右；
落盘证据 `artifacts/logs/wasm-lua/boundary-wp3-second-slice-*.log`。）

**"每帧源码编译 = 0" 现在可核对**：`web-runtime.js` 里 `doString` 只剩 5 处，全在启动/场景绑定路径
（4722–4765 行），**帧循环（5266–5351）内一处都没有**；`lua_set_number`、`lua_input_frame`、
`lua_call_global_void` 三条热路径都不编译。方向也钉成机器判据（测量脚本新增三条断言：直接调用必须比
编译便宜、编译路径**必须**有分配而直接调用**必须**零分配、空串不比空数组慢）。

**验证**：`verify-wasm-lua.ps1` 全绿（`wasm_lua_ok spike=pass bridge=pass abi=pass`，桥面门新增
"`lua_call_global_void` 可调用"的硬断言）；测量脚本 8 条断言全过；`package.ps1` 发布成功
（`bridge_exports=11`，新导出进了产物）；真浏览器完整玩法剧本 **`drive_jhyt: done`**——M1 新游戏 →
**M2 按键移动**（528,112→528,131）→ M3 背包开合 → M4 任务开合 → M5 跨场景 → M5b 实体保留 → M6 回山庄，
另有 `drawn samples: 6171`、`tile_layers: 3/3`、`ui elements: 42`、`prefab_text: 9/9`。
移动与两个面板的开合都是**按键/虚拟键驱动**的——改动过的两个钩子正是这条链路的每步必经之处。

### WP3（第四片：引擎在 wasm 里画出**工程真场景**；已完成）

第三片留下的是一道卡点（跑工程 `main.lua` 会卡死）。本片**不掩盖它**，而是把两件事拆开：
"引擎能不能把工程的**场景文件**画出来"与"工程的 Lua 能不能在没有 JS 补丁层的 VM 里跑"
（前者本片证完，后者仍是第三片的读数）。

**关键改动是让宿主交字节，而不是让引擎的 loader 去猜**：`start()` 本来就有 `startup_scene`
与全部 manifest 资源，于是 `gpu_host_run(canvas_id, scene_path)` → `RustScene::boot(…, false, path)`
→ `lua_bridge::resource_raw(path)`（表里**原始**字节）→ `Scene::from_packed_bytes`（它内部才
`pack::decode`）→ `RuntimeScene::from_scene_edit(root, scene)`（实例化场景、不跑 `main.lua`）。
读表因此拆成两个入口并各自说明理由：`resource_raw`（原样，给场景）与 `resource_png`（解包，给贴图）——
解包责任在读它的人手上，先解一次会让场景被解两遍，症状是"文件读到了、解析出来是垃圾"。

**"换一个场景"不是凑数**：默认用工程启动场景时读到 `main entities=0 assets=0 vertices=0 draws=0`。
去产物里数了才确认 **`pack/scenes/main.scene` 本来就是空的**（809 B、14 行、0 个 `entity` 行，
只有 meta）——它是这个工程的"主入口门面"，画面内容全由 Lua 现造（同一次 dump 里 JS 那条路自报
`scene=main entities=18`，那 18 个实体是运行期造的）。所以 `entities=0` 是**如实读数**，
但拿它去验"引擎画得出工程真场景"，无论管线对错都会得到 0。于是加了只接受纯场景名（值做白名单校验）
的 URL 位 `rustlua-sim-scene=<名字>` 与驱动开关 `-SimScene`。

**读数**（`verify-webgl-bundle.ps1 -Gpu2d -SimScene village`，本机 `device_type=Cpu`）：

**验证**：`rustfmt --check`（edition 2024）对四个改动文件干净；`clippy -p game_web --target wasm32

**未完成**：模拟仍不是"一个"（本片跑的是**不执行 Lua** 的场景实例化，"显示的是当前游戏状态"还不成立）；
`rustlua-sim=script` 那条路仍卡死；GPU 帧仍是启动 3 帧、无输入/场景切换/像素比对；

### WP3（第六片：Web 上"脚本卡死"定性为 **std panic**，并修掉"脚本门"与数据根；已完成）

第四片留下的卡点被记成"跑工程 `main.lua` 会卡死"。本片以实验推翻了这个归因，并把真正的
两处缺陷修掉——**都不是脚本的问题**。

**怎么一步步排除的**（每一步都改一条可变因素，读数见
`artifacts/logs/gpu-web-probe/round13-wasm-boot-panic-20261008.md`）：

| 实验 | 做法 | 结果 | 排除项 |
| --- | --- | --- | --- |
| 长超时 | `-SimRoute script` + 5 分钟超时 | 仍未完成 | "只是慢" |
| 脚本截断 | 把 `scripts/main.lua` 换成前 1 行（0 字节） | 仍停住 | **脚本内容** |
| 指令预算 | Lua 全局钩子按 1e9 条指令兜底 | 未触发 | Lua 字节码里的死循环 |
| 无工程根 | 新档 `-SimRoute scene-script-noroot` | **跑满帧循环、31 个实体、`exit=0`** | `instantiate_scene`、场景来源；范围收敛到 `let Some(root)` 那一块 |
| 控制台 | CDP 采集 `Runtime.consoleAPICalled` / `exceptionThrown` | `panicked at …/sys/unsupported/os.rs:66:5` + `RuntimeError: unreachable` | 定性：**panic 后 wasm trap**，不是卡死 |

`os.rs:66` 是 std 的 `temp_dir()` → `panic!("no filesystem on this platform")`；wasm 上
`cfg!(windows)` 为假、`HOME`/`XDG_DATA_HOME` 都不存在，`user_dir::platform_data_dir()` 的最后一句
`env::temp_dir().join("rustlua-user")` 必然被执行。`panic=abort` 之下 wasm 当场 trap，宿主的状态属性
永远停在 `sim_boot_route=…`——**在 DOM 快照里与"死循环"完全同形**。这一片因此也补上了 CDP 的控制台采集：
不采它，这两类事故永远分不开。

**两处修复**：

| `rustlua-infra/src/user_dir.rs` | `platform_data_dir()` 在 wasm 上返回虚拟数据根 `/rustlua-user` | 不碰 `temp_dir()`；平台差异只留在这一个函数里，存档/设置的路径推导一字不改 |
| `engine/.../runtime_scene/scene.rs` | `scripts/main.lua` 的存在性改为 `is_file() \|\| vfs::read(...).is_ok()` | Web/微信上发布包在宿主资源表里，`std::fs::is_file()` 恒为 false——**"跑工程脚本"在 Web 上从未真正发生过**。桌面走前半句短路，行为不变 |

`-SimScriptLines N`（截断工程脚本，用于二分）、`lua_bridge::override_resource`。

### WP3（第七片：把**每帧推进**与**宿主输入**接进 wasm 模拟；已完成）

第六片证明"工程脚本在 Web 上确实会被执行"，但那只覆盖**起场景那一刻**：每帧该发生的逻辑一步都没发生
（`vertices`/`draws` 逐帧不变），也没有任何输入来源。本片把这条缝补上——**模拟开始真的往前走**。

**改了什么**（三个文件、一条链）：

| 位置 | 改动 | 为什么 |
| --- | --- | --- |
| `game_web/src/rust_scene.rs` | 新增 `step(steps, delta, &FrameInput)`，直接调 `RuntimeScene::run_script_steps` | 桌面运行器 / 编辑器预览 / headless 运行器用的是**同一个**入口；wasm 侧另起一套调度就等于第二个真相 |
| `game_web/src/frame_input.rs`（新） | `FrameInput` → 引擎 `InputSnapshot` 的换算（键/鼠标/光标/滚轮/摇杆轴）+ 4 条测试 | 此前**不存在**这条换算：Lua 那条链把线格式落进 Lua 表，GPU 模拟则完全没有输入 |
| `game_web/src/lua_bridge.rs` | `lua_input_frame` 解码后把这一帧存进 `LATEST_FRAME`，新增 `latest_frame_input()` | 两条链吃**同一份**输入，才谈得上是"一个模拟" |
| `game_web/src/gpu_host.rs` | 每帧**先 `step` 再取网格**（定长 1 步 / `1/60`） | 与桌面同序（先推进、后 `vertices()`）；反过来永远画上一帧，接上输入就是"操作慢半拍" |

**两条不变量**（由 `frame_input` 的测试守着，它们都对应过真实的错法）：

1. **快照跨帧保留、只改变化位**。整份重建会把"一直按住"变成"每帧都刚按下"，脚本里的
   `just_pressed` 分支于是每帧触发——这种错在画面上往往"看着还行"。
2. **线格式里每个名字都要有归宿**。这条测试当场抓到两个真缺陷：
   - `"shift"` / `"control"` / `"alt"` 在引擎侧**解析不出键位**（`KeyCode::from_text` 与
     `v1_key_code` 两条路都不认），而宿主按 `event.key` 送出的正是这三个名字——**这两个修饰键一直是
     静默失效的**。修法：按线格式的槽位定到左键，并把"线格式分不出左右"记成 ABI 下一版要拆的事
     （要改的就是这一处）。
   - 键名解析的**顺序**必须与脚本侧 `parse_key_strict` 一致（先物理名、再 v1 兼容名）：顺序反了，
     同一个按键在"脚本看到的输入"与"引擎模拟看到的输入"里会变成两个键。

**顺带拔掉一类 trap**：`wasm32-unknown-unknown` 的 std 把 `Instant::now()` 实现成
`sys/pal/unsupported/time.rs` 里的 `panic!`。这条路上有三处正好每帧都会踩：

| 位置 | 什么时候踩到 | 处置 |
| --- | --- | --- |
| `rustlua-ecs/src/scheduler.rs` | 调度器**给每个系统计时**——只要推进一帧就炸（浏览器实测就炸在这里） | 换 `web-time`（原生就是 `std::time::Instant` 的再导出） |
| `engine/src/host/gamepad.rs` | `expire_rumble` 每帧被 `poll_into` 调用（震动到期） | 同上；与渲染器 `passes.rs` 既有处理同源 |
| `rustlua-infra/src/performance.rs` | 性能采样器在主循环构造 | 同上 |

扫描还留了几处**同族但当前不在执行路径上**的调用，登记在案（不要在真机上再踩一次）：
`rustlua-assets/src/resource_db.rs` 的 `unix_seconds()`（资产库簿记，wasm 上文件系统本就不可用）、
`rustlua-assets/src/atlas_pack.rs` 与 `rustlua-scene/src/{asset_import,scene_migration}.rs`（导入/迁移路径，
不进 wasm 运行时）；`rustlua-infra/src/logging.rs` 与 `rustlua-scripting/src/script/runtime.rs`
已有 `cfg(not(target_arch = "wasm32"))` 守卫，`rustlua-render/src/texture.rs` 那处在 `#[cfg(test)]` 里。

**推进失败不再拆掉模拟**：脚本在 `update` 里抛错会让调度器返回 `SystemFailed`，此前 `gpu_host` 会把这个
错误当成"取网格失败"→ 丢掉 `RustScene` → 画面退回内建场景，现象与"根本没起场景"一模一样。现在失败记成
读数（`step_errors` / `last_step_error`）并继续推进，才看得到"从哪一帧起世界不动了"。

**验收读数**（同一份产物 `verify-webgl-bundle.ps1 -Gpu2d`，全部 `exit=0`）：

| 路 | 命令 | 模拟读数 |
| --- | --- | --- |
| A 对照（不跑脚本） | `-SimScene village` | `steps=240 script=false step_errors=0 input_edges=0 spawned=0`（步数与帧数逐帧对齐） |
| 输入链路 | `-SimScene village -DriveJhyt` | `data-rustlua-input="frames=97 bits=60"` → 模拟侧 **`input_edges=13`** |
| 脚本路 + 输入 | `-SimScene village -SimRoute scene-script -DriveJhyt` | `steps=240 spawned=135 input_edges=14 draws=43 vertices=4566` |

- `steps` 与 `frames` 逐帧对齐 = 每帧确实推进了一步（第六片时这里恒为"不推进"）。
- `input_edges=13` = 宿主键盘 → 线格式 → `InputSnapshot` → `run_script_steps` 这条链**在浏览器里通了**。
  没人按键时它是 0，与"接线断了"同形，所以证据必须来自真的按键（用仓库自带的 `-DriveJhyt` 剧本）。
- `spawned` 从 0 涨到 56/135 = 工程脚本按输入生成实体（A 对照为 0）。
- **`-DriveJhyt` 自身的判定是抖的**：同一个命令在本轮跑出过 `done`（exit 0）与 `failed`（exit 1）两态
  （剧本按帧/等待推进，与 GPU 模拟同帧争时间）。上面那条 `input_edges` 证据两次都成立（13 / 15），
  不依赖剧本终态；但拿它当门禁之前要先解决抖动。

**本片撞上的新阻塞（归 WP4）**：工程 `main.lua` 的 `update` 在 wasm 上**每步**都报
`ui.measure_text: project font unavailable (check project.toml 'font')`——`project.toml` 指到的工程字体
没进 wasm 资源管线。于是 `step_errors=240`（每步一次，不中断），而"模拟往前走"之后紧接着要解决的就是
**字体管线**。

**一条反向结论（省下后来人的时间）**：CDP 的 `Input.dispatchKeyEvent`、以及 `Runtime.evaluate` 里派发
`new KeyboardEvent('keydown', {key, bubbles})`，在这个 headless 配置下**都进不了页面的输入状态**
（宿主读数 `data-rustlua-input` 的 `bits` 恒为 0），而页面**内部**的剧本走同一条事件路径却有效
（`bits=60`）。试出来的 `-SimKeys` 开关因此删掉：留着一个"看着生效、其实没送"的杠杆，只会把
"注入没生效"误读成"链路断了"。**验输入只能用页面内剧本。**

**验证**：`cargo +stable test -p game_web --lib` 6 通过（`frame_input` 四条 + 既有两条）；
`rustlua-ecs` 151 / `rustlua-infra` 39 / `rustlua-scripting` 113 通过；`engine --lib` 179 通过；
`clippy`（host：engine/infra/scripting/ecs；wasm：`game_web --no-deps`）均 exit 0；
`rustfmt --check`（edition 2024）对全部改动文件干净；`cargo check -p game_web --target wasm32-unknown-unknown
--features gpu2d` 通过。**一处需要说明的偶发**：`engine --lib` 在本轮门禁首次跑出 `0xC0000005`
（访问冲突，测试进程直接死掉），之后单跑三次均 179 通过——按"偶发"记录，未归因到本片改动
（本片对 engine 的唯一改动是 `gamepad.rs` 的时钟类型，行为等价）。

### WP4（第一片：资源管线的第一块硬骨头——**工程字体进 wasm**；已完成）

第七片把每帧推进接上之后，`step_errors` 每步一条，全是同一句：

### WP4（第二片：把"读工程文件"收成**一条通道**，并让它可**原生验证**；已完成）

上一片把字体接上 wasm 时，三处各写了一份"先 `std::fs`、再 vfs"的私有助手，并留了一句

**先看一个只在宿主环境下才现形的分叉**：`vfs` 的模块契约是"provider 装了就当权威，读**先**问它；

| 改动 | 位置 |
| --- | --- |
| 新增 `vfs::read_resource(path)`：`read`（provider 优先）+ `pack::decode`；读不到/解码失败都返回 `Err` | `rustlua-infra/src/vfs.rs` |
| 工程配置读取改走它（原来自己 `fs::read_to_string` 再解码的那段删掉） | `rustlua-infra/src/project_config.rs` |
| 字体字节读取改走它；`project_font` 模块不再 `use std::fs` | `rustlua-render/src/font.rs` |
| 图集/自定义字体/`chars.txt` 读取与存在性判断改走它（`is_file` 同样 provider 优先） | `engine/src/host/runtime_scene/fonts.rs` |

### WP6-09（接入两平台·第九片）：**实体句柄的跨运行时歧义——把"旧存档的实体引用"钉成可见的决策项**（已完成）

WP6-05 顺带查出的架构事实：`entity`/`transform` 这套在 web 旧运行时里是**它自己用 Lua 预置表实现**的
（`web-runtime.js:2040-2098`，实体 id 从 1 开始发号，`web-runtime.js:2027`），遮蔽引擎同名表。
工程的持久化写法是 `map.state("buildings")` 里存 `rec.entity`（`building.lua:265`），读档时
`if rec.entity and entity.is_alive(rec.entity) then`（`building.lua:244/255`）。问题于是变成：
**旧运行时写下的实体 id 交给引擎会怎样？**

**一次被否证的推断（本片最该记的一笔）**：我先按"句柄是 `index << 32 | generation`、
`generation == 0` 即非法"推断小整数 id（1、2、3…）会抛 `invalid entity id`，并据此写了断言
`is_alive(1) == false` 的单测——它在**空世界**里顺利通过。真 wasm + 真工程脚本一跑就翻：
`is_alive(1)` 是 **`true`**。原因是 `generation` 只占低 32 位，而 `INITIAL_GENERATION = 1`
⇒ **引擎自己的第一个实体句柄恰好就是 1**，与旧运行时的小整数 id **逐位重合、无法区分**。
单测没抓到的，浏览器探针抓到了——这正是"读数要在真宿主里取"的价值。

**真正能修的部分（已做，只动谓词）**：

- `values.rs` 新增宽容解码 `entity_from_lua_lenient`：负数与 `generation == 0` 的整数返回 `None`。
- `entity.is_alive` / `entity.persist_id` 改用它 ⇒ 分别返回 `false` / `nil`。这些值**不是任何实体的
  句柄**，以前会抛 `invalid entity id`，把存档里的哨兵值（`0` / `-1`）变成脚本崩溃。
- **写操作继续严格**：`transform.set(0, 0, 0)` 仍然报错（改动一个不存在的实体是 bug，要当场报出来）。
- `entity.rs` 行号挪动让 5 个 Lua API 文档页漂移，按仓库既定做法跑 `scripts/gen-lua-api-docs.js`
  对齐（`--check` 转绿）。复核过生成结果：删掉的只有生成头/计数/绑定行，**正文未动**，
  `documented` 计数由 8 升到 15。

**不能在本片修的（决策项，需用户定夺）**：旧存档里的实体 id 与引擎 `index == 0` 的句柄**无法区分**，
所以"建筑恢复时 `is_alive` 返回 `true`"完全可能是**另一个实体**——比报错更隐蔽。两条出路都超出
引擎单方面能决定的范围：① 改句柄编码（让引擎 id 全部 ≥ 2³²）——会让**现有 Rust 侧存档**里已经写下的
句柄失去意义，属破坏性变更；② 工程侧把实体引用换成 `persist_id` 字符串（`entity.find_id` 已支持，
`building.lua` 是工程文件）。本片只把歧义变成**可见、可断言的读数**（读数里的 `alias1=`），不擅自改编码。

**验证**：单测 `entity_predicates_return_false_for_degenerate_handles_but_writers_still_error`
（退化值查询返回 `false`/`nil`、写操作仍报错）、`first_entity_handle_collides_with_foreign_small_ids`

（`spawn/find/find_id/persist_id/destroy` 往返与重复 `persist_id` 报错）。浏览器侧在**真 wasm + 真工程脚本**

### WP6-08（接入两平台·第八片）：**平台音频出口——让引擎在 wasm 上真的响**（已完成）

退休清单里的"音频"与"存档"是同一类缺口，而且更深：引擎的播放实现基于 rodio——
`sound_bytes` 先用 `std::fs::read` 把音频读成字节，再 `ensure_device()` 找输出设备。
**wasm 上两头都不成立**：没有可读文件系统，也没有 cpal 设备。于是 `audio.play()` / `audio.music()`
在 web/微信上恒失败，**游戏全程静音**（旧运行时自带 `new Audio()` / `wx.createInnerAudioContext`
两套通道绕过去，这也是它必须被退休的原因之一）。

**做法：把"声音交给谁放"从引擎里剥出来，做成平台出口。**

- `rustlua-audio::sink`（新模块）：`AudioSinkProvider::play(AudioRequest)`，请求里只有
  "引擎知道、平台需要"的东西——**名字、总线、已算好的有效音量、资源目录、是否循环**。
  路径解析与加载都归平台：引擎侧本来就不该知道 web 的 `pack/` 前缀。
- `AudioSystem::play_on` / `play_music` 在最前面分叉：**装了出口就整段交给平台**，
  不再读字节、不再找设备；`stop_music` / `pause_music` / `resume_music` 同样分叉
  （工程切图时会调 `stop_music`——只播不停会让旧 BGM 一直响，比"没声音"更难查）。
- `game_web::audio_sink`（新模块，wasm）：微信走 `wx.createInnerAudioContext()` + 适配层已暴露的
  `__RustLuaWechat.assetSrcFor()`；浏览器走 `document.createElement('audio')`。
  扩展名次序 `mp3 → wav → ogg` 与 URL 规则 `pack/<逻辑路径>` 都与旧运行时逐字一致。
- **存在性用引擎自己的资源表同步判**（`lua_bridge::resource_exists`）：平台加载是异步的，
  等 `error` 事件回来时 `audio.play()` 早就返回了；同步判一次才能把"缺文件"与"平台播放失败"分开。

**两个独立读数（一个来自 wasm，一个来自页面本身）**

- wasm 自报（状态属性）：`audio=<次数> last=<名字> src=<逻辑路径> err=<次数> via=<web|wx> music=<playing|stopped|none>`。
- 浏览器侧独立探针（CDP 直接读页面，`-AudioProbe any|none`）：`window.__rustluaAudioElements` /
  `__rustluaAudioErrors`。元素数组既是**保命引用**（`new Audio()` 被 GC 掉表现为"偶发没声音"），
  也是外部证据；自动播放策略的拒绝会记进错误数组——浏览器里最常见的"没声音"必须能被看见。
- 主张（Rust-only 路径 + 真播一个工程音效，`-WorldDo "audio.play('sfx_harvest')"`）：
  `audio probe (any): elements=2 errors=0`，其中一个是
  `.../pack/assets/audio/bgm_title.mp3|paused=false|loop=true|vol=1`——**工程自己的 BGM**，
  即 `core/audio.lua` 的播放请求经 Rust 引擎落到了浏览器；读数侧
  `match=<last=sfx_harvest src=assets/audio/sfx_harvest.mp3 err=0 via=web>`，`exit=0`。
- 引擎侧集成测试 `rustlua-audio/tests/sink_provider.rs`：资源目录**故意指向不存在的地方**，
  `play_on` / `play_music` 仍必须成功（只要还有代码偷偷读文件就会红），并钉住
  **有效音量 = 主音量 × 总线音量**（0.5×0.5=0.25）、总线与循环标记、资源目录。

**探针抓到的真实现象（本片最有用的一条）**：T4 第一次跑时页面错误数组里冒出
`AbortError: The play() request was interrupted by a call to pause()`——**我们主动停掉一个正在播放的元素**
时，浏览器会把那次未完成的 `play()` 拒掉。旧运行时为同一件事立过 `__rustlua_released` 标记
（"不挡掉它的话被淘汰的音效会被误记成文件不存在"），本片照做：释放前先立 `__rustluaReleased`，
回调里豁免带标记的元素。否则错误数组被噪声填满，**真正要看的自动播放策略拒绝（`NotAllowedError`）反被淹掉**。
微信侧同样补了 `onError` 挂载（不挂它，微信上"没声音"完全不可见）。

**未完成 / 已知限制**：① **"听得见听不见"无法在无头环境验证**（自动播放策略、音量、输出设备都取决于
真机），本片验的是"播放请求确实到了平台、元素在加载/播放且没有报错"；② 微信分支**没有环境验**
（`wx` 只在真机/开发者工具里存在），代码路径与适配层接口按现有 API 写，只做到"编译通过 + 浏览器分支实测"；
③ 引擎的 `audio.play` 仍不给 Lua 返回值（旧运行时会回 `(false, 原因)`），这是**行为对齐**的后续项；
④ wasm 上 BGM 循环由平台 `loop` 负责，引擎的 `maintain_music` 续播路在这条分支下不参与。

### WP6-07（接入两平台·第七片）：**平台存档槽——让引擎的存档在 wasm 上真的落盘**（已完成）

退休清单里的"存档"这一项，实际缺口比"少一个 API"深：引擎的存档是**内存表 + `commit`/`load` 落盘**
两段，落盘那段直接走 `std::fs`（`atomic_write` + `read_to_string`）。桌面没问题，**wasm 上没有可写的
文件系统**——于是 `save.commit()` 恒返回 `false`、`save.load()` 恒返回 `false,"missing"`，
**玩家进度永远存不下来**。（web 旧运行时的注释里写着同一件事，它自带了一套序列化 + 读写通道绕过去。）

**做法：把"存到哪儿"从引擎里剥出来，做成平台字符串槽。**

- `rustlua-infra::save_slot`（新模块）：`SaveSlotProvider` 两个方法——**读一个键、写一个键**；
  `commit`/`load` 在装了槽时走槽、没装时走文件系统（桌面**零行为变化**）。
  存储位置按平台分叉，写法与 `vfs` 一致（桌面 `OnceLock` + `Send + Sync`；wasm `thread_local`，
  因而可捕获 `web_sys::Storage` 这类非 `Send` 句柄）。
- `game_web` 装 `localStorage` 槽：微信侧由 `wechat-adapter` 把 `localStorage` 映射到 `wx.setStorageSync`，
  所以**一份代码覆盖两个平台**（与旧运行时一致）。
- **键名必须与旧运行时逐字相同**（`rustlua:save` / `rustlua:save_<slot>`，sanitizer 同
  `save_path_for_slot`）：不同就等于"换了通道，玩家浏览器里的旧档读不出来"。这条写了单测钉住。

**验证（三条串行，浏览器侧独立取证）**

新增两个验证通道，与只读读数**分开命名**（读数只读、动作显式）：

```
rustlua-world-do=<Lua>     驱动 -WorldDo      # 只跑一次的、允许有副作用的探针（等价一条控制台命令）
驱动 -StorageProbe                            # 落定后从浏览器侧读 localStorage（键 + 长度 + 格式头）
```

```
A 主张（Rust-only，无 JS 世界）：storage probe: rustlua:save=24hdr:ok
                              rust_input_ok match=<value&quot;:&quot;v1>      exit=0
B 对照（不 commit）            ：storage probe: (no rustlua:save entry) ⇒ 红 exit=1
C 产品路径（有 JS 世界）        ：storage probe: rustlua:save=24hdr:ok
                              rust_input_ok match=<value&quot;:&quot;v1>      exit=0
```

A 里那个 `value="v1"` 是关键：探针是 **write → commit → `save.clear()`（清内存）→ load → 读回**，
所以它只能来自"真的出过进程、又真的从平台槽读回来了"。`hdr:ok` 是另一层：payload 以
`save_version=` 开头 ⇒ 与旧运行时**同格式**，旧运行时的存档 Rust 读得懂（反之亦然）。

**这一片探针又抓到第二处缺口（值得记下来）**：装上槽之后第一次跑仍然红，读数写着
`do={"committed":false,"why":"no_save_path"}`——`commit` 在**到达槽之前**就因为"没配存档路径"被忽略。
原因是验证时用的 sim 路线没跑工程脚本，而引擎按既有语义只在"跑脚本 + 有工程根"时才配存档路径
（`runtime_scene/scene.rs` 的 `init`）。这不是 bug 而是既有语义（渲染-only 模式不该存档），
所以**没有改引擎**，而是把门改到真跑脚本的那一档（`-SimRoute script`）——顺带说明：
`save.commit` 的失败原因是**可读的**（`no_save_path` / `missing` / `corrupt:`），不用猜。

**未完成 / 限制**

- **微信侧未经真机验证**：`localStorage` 在该环境里由适配层提供，没有微信环境可跑（设备验证限制）。
- 键名是**域名/应用无关**的常量（与旧运行时一致）：同一域名下两个工程会共用 `rustlua:save`。
  要修得配迁移（旧档要能读出来），单独一轮。
- 只验到"引擎自己写的档读得回来"；**跨运行时互读**（Rust 写、旧运行时的 Lua 读）没有直接验，
  只验了 payload 格式头一致。
- `-WorldDo` 是**写通道**，靠调用方自觉只用于验证；若将来给微信侧复用需要加护栏。

### WP6-06（接入两平台·第六片）：**只读工程状态查询通道 + 交互门**（已完成）

WP6-05 的位移门只覆盖"按键 → 走路"一条通路；退休清单里还压着"玩家交互流程"（开背包、开任务、切图）。
这一片把"能问任意工程状态"做成基础设施，并把交互变成可断言的门。

**判据选工程自己的状态机**（`main.lua` 里本来就用 `state.is_mode("Inventory")` 分支）：

### WP6-05（接入两平台·第五片）：**Rust 侧世界读数 + "输入 → 世界改变"位移门**（已完成）

WP6-04 让 Rust 宿主收到 DOM 事件（`dom_events 0 -> 14 -> 20`），但那只证到"边沿进了快照"——
**证明不了游戏逻辑真的因此移动了主角**。这一片把这条链闭合，并把它变成可当门禁的确定性断言。

**读数从引擎自己的世界读**，不依赖 JS 预置的那套表：

| 步骤 | 用什么 |
| --- | --- |
| 主角是谁 | 场景文档里**名字含 `player`** 的实体（与渲染器 `entityColor` 同一套启发，不写死工程名） |
| 名字 → 实体 | `entity.find('<名字>')`（`rustlua-scripting` 的引擎 API） |
| 实体 → 坐标 | `transform.get(id)`，经 `RuntimeScene::with_script` + `LuaRuntime::eval_json`（只读求值） |

**顺带查出一件架构事实**：`transform`/`spawn`/`__rustlua_transforms` 这套实体 API 是
**`web-runtime.js` 用自己的 Lua 预置表实现的**（`web-runtime.js:2059-2100`）——即 **JS 世界在遮蔽
引擎同名 API**。所以"退休 JS 世界"的清单除了输入/音频/存档，还要加上"web 平台的实体 API 实现"。
Rust 侧本来就有引擎自己那套，本片读数正是用它读出来的。

**这一项的现状（WP6-09 实测）**：引擎侧**名字层面已经齐了**（`entity.find/is_alive/find_id/persist_id/
spawn/destroy`、`transform.get/set/move`、`map.goto/enter/state/state_clear/schema` 都有），所以缺口不在
函数，而在**边界语义**：旧运行时的实体 id 是从 1 开始的小整数，而引擎句柄是 `index << 32 | generation`、
`INITIAL_GENERATION = 1` ⇒ **两边的小整数逐位重合**（实测：首个实体句柄就是 `1`，`is_alive(1)` 为 `true`）。
退化句柄（`0` / `-1` / `generation == 0`）在谓词里已改成回答 `false`/`nil` 而不是抛错；
**旧存档实体引用可能指向别的实体**这一条超出引擎单方面能决定的范围，作为决策项记录在 WP6-09。

**确定性输入剧本**：URL `rustlua-input-script=<键>:<起帧>-<止帧>[,...]`（驱动侧 `-InputScript`）。
区间半开（`w:30-150` = 第 30 帧按下、第 150 帧松开）；逐帧按**集合差**发边沿，
所以 `w:30-150,a:150-180` 这种首尾相接不会多出一次"松一下再按住"的假边沿。
用它而不是探针按键，是因为探针的落点取决于事件循环调度，而位移读数要与帧号对齐才有可比性；
确定性之后它还能当性能基线（固定输入 = 固定负载）。

**验证**：

```
webgl_bundle_rust_input_ok script=w:30-150 world=JianghuPlayer@624,360 moved=0,280    # Rust-only，exit=0
[RED] webgl_bundle_rust_input_failed script=q:30-150 world=JianghuPlayer@624,80 moved=0,0   # 对照组，exit=1
```

三处自洽：`@624,80` 是出生点、`@624,360` 是终点，差正好 280 = `moved=0,280`；无效键 `q` 位移恒为 0
⇒ 门区分得开"输入驱动"与"世界自己在动"。正常产物（有 JS 世界）同一剧本读数**逐字相同**。
**全程没有 `web-runtime.js`。**

**一个被自己推翻的假设（写进计划，因为它差点变成错误结论）**：第一版把读数写成"`step()` 里每 30 步
自动刷一次"，随后 `-DriveJhyt` 从旧产物上的 2/2 通过变成连续 5/5 失败，我据此判断"读数抢了 JS 世界的
帧预算"。改成按需刷新后**仍然 2/2 失败**，而且 `-GpuFrames 30`（GPU 循环只跑 30 帧、几乎不执行新代码）
那次**也红**且相位换成预算更紧的 `quest-close`（70 帧）⇒ **归因错误**，不是这段代码。
"按需刷新"本身保留（观测不该在热路径上：读数现在只在宿主写状态属性那一帧之前刷一次）。

**本轮真结论（驱动剧本不稳）**：带 GPU 通道时今天 10 次运行 **2 绿 8 红**，失败相位两档
（`nav-exit` 预算 900 帧 ⇒ `frames=901`；`quest-close` 预算 70 帧 ⇒ `frames=71`）；
**不带 GPU 通道的同一剧本 2/2 绿**；同期本机 CPU 负载 57%（微信开发者工具等都在跑）。
即"GPU 通道与 JS 世界抢同一份 CPU/帧预算"时相位预算不够——对退休计划的意义反而更清楚：
**JS 世界在 GPU 模式下纯浪费**（抢帧 + 零像素贡献），越早退越好。**未修**，只做到定位 + 反证。

**测试**：`game_web --lib` **20 条**（本轮 +3：剧本解析的每类错误、半开区间、按集合差发边沿）。
写测试时抓到两次**我自己**的期望值错误（`keys_held` 是按**槽位**的位图，`w` 在第 22 位；
半开区间下"止帧"那一帧已经松开）——现在期望位图由 `rustlua_frame_abi::key_slot` 算，不手写常量。
门禁 10/10 绿；新增代码零警告。

**未完成**：① 剧本只有键盘，触摸/指针（微信侧主要输入）没有等价剧本；② `moved` 是相对量
（相对第一次写状态属性那一帧），要报绝对位移得在 boot 后立刻读一次；③ `EngineStartup` 档没有场景文档
⇒ 读数退化成 `world=no-player`（诚实读数，不是失败）；④ 相位预算与 GPU 通道共存时的稳定性未修。

### WP6-04（接入两平台·第四片）：**Rust 侧自己的输入采集**——退休清单第一项（已完成）

WP6-03 证明"没有 JS 世界，Rust 也能启动、跑脚本、出画面"，但那份证据有一处空白：
**玩家按不动它**。线格式输入此前**只有消费者**——`web-runtime.js` 采集 DOM 事件、编码成 `RLFI`、
经 `lua_input_frame` 写进常驻表，GPU 宿主读出来用。没有 JS 世界就没有输入，所以这是
"退休旧热路径"清单上的第一项，也是"能不能退"的功能判据之一。

**做法**：把输入的**逻辑**（归一、边沿、每帧量、两路合并）放进 `game_web` 里
**不依赖 wasm 的模块**，wasm 侧只留一层薄壳。

| 位置 | 内容 |
| --- | --- |
| `frame_input::wire_key_name` | DOM `KeyboardEvent.key` → 线格式键名，与 JS 宿主**逐条同规则**：小写；`" "`→`space`；`arrowX`→`X`；表外键返回 `None` |
| `frame_input::FrameInputProducer` | DOM 事件 → 每帧一份 `FrameInput`：按住集合跨帧保留、边沿只由状态**变化**产生、每帧取走即清空、表外键**计数**而不是静默丢弃 |
| `frame_input::merge_into` | 两路输入并集：位图按位或、滚轮相加、光标听"本帧真的动过"的那一路（JS 那路的摇杆轴原样保留） |
| `fit::css_to_design` | CSS 像素 → 设计坐标，与 `contain_box` **互逆**；触点映射与画面取景共用 `fit_now` 写下的同一个盒子 |
| `gpu_host::install_input_listeners` | window 上挂 keydown/keyup/pointermove/pointerdown/pointerup/wheel，只把事件攒进生产者，**不判任何逻辑**（逻辑在可测的那一层） |

**验证（Rust-only 宿主：`-StubJsRuntime -NoSceneVerify -KeyProbe -GpuFrames 0`）**：

```
[cdp] key probe: in-page delivery self-test hits=2
[cdp] key probe: frames 600 -> 750 -> 870 ; dom_events 0 -> 14 -> 20 ; input_edges 0 -> 2
webgl_bundle_gpu_fit_ok viewport=756x441 fit=756x425 ratio=1.7788      status=exit=0
```

三个数逐一对上：探针派了 12 次按下、页内自测 2 次、6 次抬起 ⇒ `dom_events` 精确为 14 与 20；
一次按下 + 一次抬起 ⇒ `input_edges=2`。而这一切发生在**没有 `web-runtime.js`** 的宿主里。

**这一片踩到的坑（各自都伪装成"链路坏了"，所以写进计划）**：

1. **`trim()` 会杀掉空格键**：`wire_key_name` 第一版先 `trim()` 再比 `" "`，空格键的名字变成空串、
   静默失效；JS 宿主也不 trim，两边必须逐条同规则。单测第一次跑就红了。
2. **PowerShell 向原生程序传参会丢掉空字符串**：`-KeyProbe` 的 `1` 落到了 shot 的位置，
   探针静默不跑而驱动照样 `exit=0`。改法：可选参数一律用 `-` 占位，waiter 把 `-` 当"未提供"。
3. **状态属性每 30 帧才刷、循环跑完就冻结**：探针读到 `frames 240 -> 240 -> 240`、`dom_events` 恒 0，
   看起来像"事件没到"，实际是**宿主已收工**（240 帧预算跑完循环就退出了）。于是加 URL 开关
   `rustlua-gpu-frames=<n>`（`0` = 不设上限），驱动侧是 `-GpuFrames`。
4. **驱动剧本在负载下偶发超时**：`-GpuFrames 0 -KeyProbe -DriveJhyt` 那次失败在 JS 侧的
   `phase=nav-exit timeout frames=901`；但**原样** `-DriveJhyt`（不带 `-GpuFrames`）也失败过一次、
   同一相位同样 901 帧，而在安静机器上连跑两次**都通过**（里程碑 M1–M6 齐全）⇒ 这是**负载相关的偶发**，
   `-GpuFrames 0` 只会加剧、不是根因。与输入改动**无关**且是结构性的：Rust 侧监听器只读事件
   （全文无 `prevent_default` / `stop_propagation`），线格式是 JS → Rust 单向，Rust 侧不可能反过来
   影响 JS 世界的 `data-rustlua-drive` 状态机。本轮同一命令 5 次里 3 次通过，通过的三次都在机器空闲时。

**测试**：`game_web --lib` **17 条**（本片 +8：6 条生产者/合并/归一 + 2 条光标换算），
其中 `producer_same_frame_tap_reaches_the_snapshot` 是端到端一条：生产者 → 线格式 →
`apply_frame` → 快照，同帧点按必须被认出来。门禁 10/10 绿；新增代码编译零警告
（`game_web` 只剩既有 4 条）。

**未完成**：① **接触输入**——本片只做浏览器 DOM，微信侧没有 DOM，触摸要走适配层；
但适配层本来就把输入编码成同一个线格式送进来（`merge_into` 正是为这个并集写的），两者可以并存。
② **"世界真的因此改变"**——`input_edges=2` 证明边沿落到了模拟，不等于游戏逻辑一定移动了主角；
正常产物那条路由既有 `-DriveJhyt` 的"位移非零"断言覆盖（页内剧本驱动同一份线格式），
Rust-only 那条路目前只证到"输入进了模拟"，缺一个"从读数里读世界状态"的口。

### WP6-03（接入两平台·第三片）：**Rust-only 宿主**——证明 Rust 侧自足，并拿到退休的**功能清单**判据（已完成）

上一片把退休判据改写成"先做到世界状态的单一来源"。那第一步做什么？最硬的一条是：
**Rust 那条路自己能不能把游戏跑全**——启动、跑工程脚本、读资源、出画面，**全程没有一个 JS 运行时**。
能，才谈得上退休；不能，退休就是砍功能。

**为什么不用改任何用户文件就能试出来**：产物 `index.html` 的启动链是显式两步——
`await start(...)`（Rust）之后 `await window.rustluaRunLuaGame(status)`（JS 世界）。而
GPU 宿主**不是** JS 启动的（Rust 的 `start()` 自己读 `?rustlua-gpu=1` 拉起），资源表也是 Rust 侧
自己预载的（读 `pack/manifest.txt`，`preloaded=1186`），`__rustluaSyncCanvasSize` 定义在
`index.html` 的内联脚本里。所以把 184 KB 的 `web-runtime.js` 换成一个只定义
`window.rustluaRunLuaGame = async () => {}` 的替身，`index.html`/wasm/pack **一行不改**，
跑起来就是"只有 Rust"的那条路。产物拷到临时目录再替换，不污染构建输出、不碰用户文件。

**读数（Rust-only：`-Gpu2d -SimScene village -SimRoute scene-script -StubJsRuntime -NoSceneVerify`）**：

**最硬的一条**：正常产物与 Rust-only 的截图 **逐字节相同**（同为 16060 字节，
SHA-256 都是 `BAF13A5C…E9B2205`），帧统计也逐项相同。⇒ **GPU 模式下玩家看到的那幅图，
已经是 100% Rust 那条路画的**；JS 世界（含 Canvas2D 层）一个像素都没贡献，它被压在不透明的
GPU 内容盒下面。顺带说明 Rust 侧两次运行世界状态稳定。

**代价那一面**：30 帧处 `avg_frame_ms=10.62`（JS 世界在跑）vs `10.07`（不启动）⇒ 差 **0.55 ms/帧**。
含 `yield_to_event_loop` 等待、且只有单次采样，只能作方向。方向很明确：**JS 世界在这条路上是纯浪费**
——画面不贡献，每帧还要跑一遍完整世界（Lua/JS 双份模拟 + Canvas2D 绘制）。

**踩到的坑（记一笔）**：`data-rustlua-scene-verify` 是 **JS 世界**写的门，Rust-only 跑法必须配
`-NoSceneVerify`，否则验的是"JS 世界有没有跑"而不是"Rust 侧行不行"。另外新增代码块一度放在
`Write-Log` 定义**之前**（PS 顺序执行）⇒ 报"无法识别的命令"，已挪到定义之后。

**结论 / 下一步**：① "Rust 侧自足"已被**证明**（不是推断）；② 因此退休在**渲染上**是安全的，
需要先搬走的是 JS 世界仍然**独占的功能**：真实输入事件源、音频、存档、玩家交互流程；
③ 下一步列"JS 世界仍独占的功能清单"并逐项确认 Rust 侧有无等价物——这才是退休判据（替代
上一片推翻的"画面一致"）；④ `avg_frame_ms` 的 A/B 要重复采样才能当性能读数。

### WP6-02（接入两平台·第二片）：**两层画面的客观对比**——以及"退休判据"必须改写（已完成）

WP6-01 让两层同框，但"同框"只说明几何一致，不说明**画面对得上**。本片把画面本身变成读数。

**取图方式（关键在"同一次运行、同一时刻"）**：分两次运行取图不可比——两层动画相位不同。
做法是一次运行取两张：① 等 `data-rustlua-gpu` 推到 `presented frames=240`（首帧含一次性建图集，
不能拍）后 `Page.captureScreenshot`；② JS 把 `#rustlua-gpu-canvas` 临时 `display:none`，等 600 ms，
再拍一张"只有 Canvas2D 层"；③ 恢复样式。**必须走 CDP 截图**：WebGL 画布默认
`preserveDrawingBuffer:false`，合成后用 JS 读是空白，只有合成器里还留着最后一帧。

**读数**（756×441 视口，`village` 场景、跑工程脚本）：

| 读数 | 值 |
| --- | --- |
| 内容盒包围盒（A 的非页面背景包围盒） | `(0,8)-(755,432)` = **756×425** |
| 视口上下边缘行（内容盒外） | A 与 B 都 = `(21,25,35)` = `#151923` |
| 整图差异 | 平均通道差 75.9/255；超阈值(32)像素 **89.56%** |
| 内容盒量化颜色种类数 | GPU+2D **47** / 2D-only **182** |

**像素独立证实了 WP6-01**：黑边色与内容盒尺寸与 `css=756x425+0+8` 完全对上——GPU 层确实只覆盖
内容盒、没铺满、没偏移。这条比上一片的属性读数更硬：它是真实像素。

**但这个 89.56% 差异不能读成"GPU 渲染器画错了"**，否则下一个人会去修错东西：
两层现在是**两套独立的模拟**——Rust 侧跑工程脚本、相机跟 Rust 侧的玩家实体
（`[camera] village 跟随玩家 entity=…`）；Canvas2D 侧是 `web-runtime.js` + 补丁层跑的**另一份**
工程状态、相机跟 JS 侧玩家。两者从未共享世界状态，"画面不同"是必然的。

**所以退休判据要改写**（这是本片最重要的产出）：原计划把"两层画面一致"当作退休
`web-runtime.js` 那条逐帧 JSON/源码编译路径的前置证据——**这个判据本身不成立**，
只要还有两套模拟，画面永远不会一致。正确的顺序是：

1. **状态单一来源**：Rust 侧成为唯一的世界状态持有者（输入批量 ABI + 运行时场景 + 逐帧循环
   已在 Rust 里跑，缺的是"JS 层不再自己推进世界"）；
2. 之后同一次运行里"藏掉 GPU 画布 vs 不藏"的两张图**才有**可比语义（本片的 `-ShotUnder`
   取图流程已经做好，届时直接复用）；
3. 到那时像素差异才可以当"渲染是否正确"的判据，并给门限。

**本片交付的工具（可复用）**：`webgl-cdp-wait.js` argv[6]/[7]（落定后截图；第二张藏掉 GPU 画布）、
`verify-webgl-bundle.ps1 -Shot/-ShotUnder`、`scripts/compare-shots.ps1`（包围盒、整图差异、
3×3 分区均值色、黑边色、量化颜色种类数、差异热图）。

**未完成（下一步）**：① 状态单一来源（本片改写后的主线）；② GPU 内容盒只有 47 种颜色这一点，
要在状态统一后重看——若仍近似单色，才说明 Rust 的 2D 通道（相机/视口/tint）确有渲染问题，
**现在下结论太早**；③ 微信侧仍无环境。

### WP6-01（接入两平台·第一片）：**两层同框**——GPU 画布改用 Canvas2D 层的等比适配盒（已完成）

**问题（此前不可见）**：Canvas2D 层每帧把 1280×720 设计空间 **contain** 进游戏画布
（`plugins/webgl/web-runtime.js`：`fitS = min(w/1280, h/720)` + 居中平移 + 黑边），
而 GPU 层是"**固定 1280×720 后备缓冲 + CSS 铺满视口**"（WP3 第五片留下的形状）。
两层因此是**两个不同的几何盒子**：实测无头窗口的游戏画布是 **756×441**（不是 16:9），
旧行为下 GPU 内容被浏览器**非等比拉伸**（纵向约 +7%），而 2D 层老老实实居中留了 8px 黑边。

**为什么一直没被发现**：画布属性、`frames=`、`draws=`、`avg_*_ms` **一个都不异常**。
这类"几何错"只能靠把两层几何都写进读数才抓得到——这正是本片加 `viewport= fit= css=` 的原因。

**做法**（只在宿主侧，不动渲染器/引擎公开面）：

| 步骤 | 说明 |
| --- | --- |
| 读盒子 | 每帧从**游戏画布**读后备缓冲尺寸（物理像素）与 `getBoundingClientRect()`（CSS 像素 + 原点） |
| 算适配盒 | `contain_box`：`scale = min(bw/1280, bh/720)`，取整到像素，居中 |
| 同步三件套 | 画布 `width/height` → `surface.configure`（复用同一份 `SurfaceConfiguration`，只改宽高）→ `RustScene::set_viewport` |
| 摆位置 | CSS `left/top/width/height` 按同一个比例换算（CSS 像素），只在变化时写 DOM |
| 读数 | `viewport=WxH fit=AxB css=WxH+x+y` 进 `data-rustlua-gpu` |

DPR / 页面缩放 / 画布被 CSS 挪过位置**都不需要单独处理**：像素数来自后备缓冲、位置来自
`getBoundingClientRect`，两者的比例就是真实的 CSS↔物理换算，不必假设它等于 `devicePixelRatio`。

**实测**（无头 756×441 窗口，两条路各 240 帧）：

```
viewport=756x441 fit=756x425 css=756x425+0+8
```

与 Canvas2D 层自己算出来的完全一致（`fitS = 756/1280 = 0.5906` ⇒ `1280×0.5906 = 756`、
`720×0.5906 = 425.25`，居中偏移 `(441-425.25)/2 = 7.9 ≈ 8`）。**两层现在画在同一个盒子里**。

**门禁怎么钉住它**（错法不可见 ⇒ 必须机器检查）：

1. `scripts/verify-webgl-bundle.ps1 -Gpu2d` 新增断言：从 `data-rustlua-gpu` 里解 `viewport= fit=`，
   要求**比例等于设计比例（1% 容差）**且不超出游戏画布，通过时打
   `webgl_bundle_gpu_fit_ok viewport=756x441 fit=756x425 ratio=1.7788`。
   不去钉死具体像素（无头窗口尺寸会变），只钉比例与包含关系。
2. `game_web/src/fit.rs` 三条**原生单测**（纯数学，不受 wasm 门控）：
   比例恒等（7 组盒子）、黑边出现在**不贴合的那个方向**（含"同比例时两边贴满"这个易错情形）、
   退化输入（0/1）不 panic 也不给 0（0×0 会让 `surface.configure` 直接失败）。
   **反向验证**：把 `scale` 改成 1.0（等价于旧的"铺满"）⇒ 立刻 2 条红；还原 ⇒ 9 条绿、文件字节一致。

**未完成（下一步）**：① 两层现在同框了，但**像素是否一致**还没比过（下一片：同一帧 CPU/GPU 取图对比）；
② 画布背景色（2D 层 `#151923`）与渲染器清屏色是否一致未断言；③ 微信侧 canvas 尺寸策略不同
（`wechat-adapter`），需要同样的适配盒复刻，但本机无微信环境。

### WP5（第五片：把渲染器接进**真宿主**——`game_web` 的 GPU 画布；已完成）

前四片都发生在探针里。本片把它接进**出货宿主**：`game_web` 里原本**连
`engine::host::Renderer` 都没有**（只有 `web_sys` 画布 + JS 的 Canvas2D），现在它有了
一条 GPU 通道——建 surface（画布）→ 适配器/设备 → 引擎渲染器 → 把 **Rust 侧产出的场景**
渲进画布纹理 → `present`，连渲 3 帧（第二帧才会暴露"上一帧没还回去"这类问题），
然后把结果写进 `data-rustlua-gpu`。

**开关的形状是刻意选的**：默认路径一行不动——Rust 侧读 `?rustlua-gpu=1` 才启用（因此
**不需要改** `plugins/webgl/` 下任何既有脚本），构建侧要 `package.ps1 -Gpu2d`
（`game_web --features gpu2d`，含 wgpu 的 WebGL2 后端），门是 `verify-webgl-bundle.ps1 -Gpu2d`
（断言 `data-rustlua-gpu=presented*`）。三处默认都是关的：GPU 路径还在逐片搭建，
一次误判就会让所有平台的画面一起变。

顺带把"从画布建 surface"那段带 `unsafe` 的边角料**收成引擎里的唯一实现**
（`host/web_surface.rs`）：探针与宿主都要走这一步，两份副本就是两个"只修好一份"的机会。
收编后探针读数逐项不变（本片第二天复跑确认）。

**踩到的坑（本片最值钱的产出）**：

- **一张画布只能有一个上下文**。第一版把 GPU 渲染器直接建在游戏画布上，`?rustlua-gpu=1`
  时页面立刻 `boot=failed … detail=2D canvas context is not available`：WebGL2 先被建起，
  随后 `web-runtime.js` 的 `getContext('2d')` 拿到 `null`（浏览器对这种请求只回 null、不抛错），
  **新通道把既有画面链路整条打死了**——比"GPU 没画面"严重得多，而且现场那句错误信息
  指向的是 2D 那一侧，不先弄清上下文互斥就会去改错文件。
  修法：GPU 用**自己的画布**（`#rustlua-gpu-canvas`，固定定位盖在上面，
  `pointer-events:none` 把输入留给游戏画布——输入链在 Lua 侧，不能被显示层抢走）。
  门的顺序也据此改了：GPU 自检放在场景切换门**之前**并互相带上对方读数，两条读数同框才判得清是谁弄死谁。
- **贴图的键只能在一处决定**。第一版 `upload_scene_texture()` 与 `scene_mesh()` 各自挑一次
  "第一张 PNG"：上传失败退回内建棋盘时，场景仍按资源键去查——渲染器查不到就静默退回
  **白兜底**，而"白兜底"与"贴图被采样到了"在画面上无法区分。现在键与来源说明一起由
  `prepare_texture()` 返回，场景只接收结果。

**证据边界（与第四片同一口径）**：本片画的是**手工场景**（两块内建白四边形 + 一块贴图四边形，
贴图优先取工程资源里第一张 PNG、拿不到才用内建棋盘），**不是游戏内容**——把场景换成
Rust 侧模拟产出的真场景属于 WP3；GPU 那一帧目前也只在启动时画 3 帧，还没有接进
JS/Lua 的每帧循环。这些都不是"顺手补一下"，是下一片的正式内容。

**本轮证据**：

| 判据 | 命令 | 结果 |

### WP5（第四片：真渲染器直接渲进**画布纹理**并 present——Web 宿主的接入形状已证；已完成）


前三片都停在**离屏纹理**上。但 web 宿主必须把这一帧送到画布上，而这条路从来没被跑过——
查下来根因比"没验过"更硬：`game_web` 里**连 `engine::host::Renderer` 都没有**（它只拿
`HtmlCanvasElement` 交给 JS 的 Canvas2D），所以"引擎渲染器 → 画布"这件事在两边都不存在。

**先要问清的问题是格式**：渲染器的颜色附件格式是构造时烘死的 `Rgba8UnormSrgb`，
管线与附件格式不匹配会被 wgpu 校验拒绝，而 wasm 是 `panic=abort`——**不能**抱着"试试看"
的心态往不匹配的 surface 上渲。探针实测（真浏览器 Edge 无头 + ANGLE/SwiftShader）：

| 读数 | 值 |
| --- | --- |
| 画布提供格式 | **`Rgba8UnormSrgb`, `Rgba8Unorm`, `Rgba16Float`** —— 烘死的那个**正好可用** |
| present 模式 | 只有 `Fifo` |
| 画布纹理可用用法 | **只有 `RENDER_ATTACHMENT`** |
| 配置 / 渲进画布纹理 / present | 全部成功，**零校验错误** |

于是接入形状被钉死成一句话：`surface.get_current_texture().texture` →
`render_into_texture(&mesh, None, &frame_view, w, h)` → `frame.present()`，
**不需要改引擎**（渲染器不必认识 surface，也没必要为 web 做格式参数化）。

**踩到并记下的坑（本片最大的实际收获）**：第一版按"读回画布纹理做逐像素对拍"来设计，
顺手在 `SurfaceConfiguration` 里申请了 `COPY_SRC`——结果 **wgpu 在未捕获的校验错误上直接 panic，
`panic=abort` 让整个 wasm 模块死掉**，探针连"哪一步被拒"都报不出来（现场只有一个
`Uncaught RuntimeError: unreachable`）。改成两件事后立刻拿到读数：① `usage` 只申请
`RENDER_ATTACHMENT`（能力问题不该由调用方替平台假设）；② **把配置与"渲染+present"整段放进
`push_error_scope(Validation)`**，让失败变成数据而不是 abort。这也解释清了为什么
`usages` 只有 `RENDER_ATTACHMENT`：**WebGL2 的画布纹理当不了 copy 源**。

**由此得到的证据边界（明确记录，不含糊）**：画布纹理读不回来 ⇒ "present 之后画布上到底是什么"
无法在页内逐像素对拍。所以本片的逐像素判据仍取自**离屏那一帧**（7 个采样点逐通道精确），
画布这一侧的证据是"按渲染器的格式配得起来、渲得进去、present 出去且零校验错误"。
要把画布像素也钉死，只能走页面外（CDP 截图）那条路——留给需要它的那一片。

**下一步（WP5 剩余 + WP7）**：`game_web` 现在有画布、有 `start()`，缺的正是这一步接线——
建 surface（它已经在用 `web_sys`）、把设备交给 `Renderer`、每帧把**Rust 侧产出的场景**
渲进画布纹理并 present；之后再拆 `plugins/webgl/web-runtime.js` 的 Canvas2D 热路径（WP8）。
`game_web` 目前的场景与逻辑仍在 JS/Lua 两侧，这也是 WP3「统一 Rust 模拟」必须先行的原因。

### WP5（第三片：2D 叠加通道保序合并——提交次数降到"同键连续段"数；已完成）

前两片解决的是"能不能画对"，本片第一次动**绘制效率**。原来 2D 主路径是**每个 `SceneDraw` 一次
`pass.draw`**：一千个相邻精灵就是一千次提交、一千次 `set_pipeline`/`set_bind_group`。

**做法（纯渲染器侧，宿主与场景格式都没改）**：相邻、**键相同**、且顶点在同一个缓冲里
**首尾相接**（`start + count == 下一个 draw 的 start`）的 draw 合成一次 `pass.draw`。
键 =（贴图下标, 是否 SDF, 是否位图）——它决定管线与绑定组，所以键相同才允许同批。

**为什么这不算"为了快牺牲正确性"**：合并后的三角形顺序、混合顺序与逐个画**完全一致**，
像素必须逐字节相同；而且合并不跨越层的边界（`layer_indices` 桶内保序），所以 2D 半透明叠加
依赖的画法顺序没有被改动。反过来，两条**不许合并**的边界各有一条测试钉着：键变了、
顶点不连续（中间那段没人引用的顶点一旦合进去就会被画出来）。

**安全性里最容易漏的一条：解析纪元**。键相同**不**等于内容相同——异步贴图完全可能在同一个
帧内完成上传，于是同一贴图键的第一次解析拿到"白兜底"、第二次拿到真贴图；把两次合成一批就会
把后者画成前者。`wgpu` 27 的 `BindGroup` 没有身份查询（`global_id` 要到更晚版本才有），
所以改用**纪元**做代理：贴图缓存长度、自定义字体图集数、内建字体图集是否已绑定——这三件事
覆盖了 `bind_group_for`/`sdf_bind_for` 的全部可变来源。纪元一变就先冲刷批次，
于是"批次内键相同 ⇒ 绑定的贴图内容相同"是**证明过的**，不是碰巧。

**读数**

| 场景 | 改造前 | 改造后 | 依据 |
| --- | --- | --- | --- |
| 探针 3 个 draw（前两块同贴图相邻） | `draw_calls=3` | **`draw_calls=2`**（`triangles` 仍 6） | 真浏览器 WebGL2 离屏出帧 |
| 1000 块同贴图相邻四边形 | 1000 次提交 | **1 次**（`instances=1000`、`triangles=2000`） | 原生测试（设备无关） |
| 200 块**交替**贴图 | 200 次 | 200 次（一次都合不了） | 原生测试——**局限也钉住** |

像素侧：探针 7 个采样点（含 4 个内存贴图纹素）仍**逐通道精确命中**，白色像素 5202/5202；
原生既有像素金标（tetris、编辑器预览、world sprite、frame views）全部照旧通过——合并没有改动
任何一个像素，这正是本片唯一可接受的形状。

**局限与下一步**：保序合并只吃"同键连续段"，交替贴图序列的收益是 0。要真正把提交次数压下来，
得让**产场景的一端**尽量按图集把同键 draw 排在一起（Tilemap/图集那一片的活）；**不能**在这里
按贴图重排——2D 半透明叠加靠的就是顺序，重排等于改画面。`draw_calls` 是设备无关的硬指标，
所以本片的收益可以在软件光栅上报；帧耗时仍然只能等真机。

### WP5（第二片：把内存里的贴图交给渲染器——web 上没有文件系统；已完成）

第一片证明"真渲染器能在 WebGL2 上出帧"，但那一帧只用了**内建白贴图**（`texture == 0`），
完全没碰资源解析。本片补的是第二片的前置条件：**在 web 上，贴图必须先能"交进来"**。

**为什么这是硬前置**：2D 贴图原本只有一条来路——`texture_paths` 里查不到就按路径
`std::fs::read`（`gpu_texture.rs::bind_group_for` 的末段）。web/微信上没有文件系统，那条路必然
落到白兜底；而"白"恰好也是"什么都没画"的样子——**图集/精灵画对没有，在浏览器里根本无从判断**。
所以本片不是"顺手加个 API"，而是把一条**不可验证**的路径变成可验证的路径。

**做法**：`Renderer` 新增两个公开入口（`gpu_texture.rs`）

- `upload_texture_rgba8(key, width, height, rgba)`：已在内存的 RGBA8 像素 → GPU 贴图 + 绑定组。
- `upload_texture_png(key, bytes)`：字节 → 解码 → 同上（web 端手里只有字节，没有文件可读）。
- 两者共用一个私有实现，按 `key` 登记槽位；**同一个 `key` 重复上传是原地替换**（槽位不变）——
  已经按资源身份缓存过该槽位的绘制仍然有效。流式图集靠这条：图集更新不该让所有身份失效。
- 解析路径**一行都没改**：宿主照旧把 `key` 放进 `SceneMesh::paths`、用 1-based 下标引用。

**怎么证明它真被用到了**（这一步的判据设计比实现重要）：探针上传一张 **2×2 四色棋盘**
（红/绿/蓝/黄，**没有白**），键取 `probe://checker2x2`——一个**不存在的路径**。于是上传若失败：
按路径解析必然落白兜底，两处同时露馅（① 四个纹素采样全白；② 白色像素面积超出解析值约 4%，
远超 2% 容差）。反过来，采样点**逐通道等于上传字节**只可能是"上传真的进了缓存并被采样到了"。

**读数（真浏览器 Edge 无头 + ANGLE/SwiftShader）**

| 项 | 读数 |
| --- | --- |
| 帧计数 | `draw_calls=3`、`triangles=6`、`dropped_draws=0`、`passes=2` |
| 采样点（7 个） | **全部逐通道精确命中**：2 个白四边形中心 `[255,255,255,255]`、背景 `[0,0,0,255]`、4 个纹素 = 上传的红/绿/蓝/黄 |
| 贴图不匹配 | `texture_mismatches=0`（本片的直接判据） |
| 贴图缓存 | `loaded_texture_count=1` |
| 白色像素 | 5202 / 期望 5202（贴图四色不含白 ⇒ 这条判据**独立地**盯住"退回白兜底") |
| 2D 上限 | 8192 → 8192 → 8192（存储缓冲 0，与第一片一致） |

**原生侧回归**：新增两条引擎测试（`tests/texture_upload.rs`）——四条纹素逐通道精确相等、
同 `key` 覆盖不新增槽位、非法输入（尺寸不符 / 0 尺寸 / 垃圾字节）在**进缓存之前**被拒且不留槽位。
原生 26 项渲染器测试全过。

**为什么先做这一片**：图集、Tilemap、文本 UI 三条路**都要**经过"内存像素 → GPU 贴图"这一步。
在它能被验证之前做图集，等于在一条不可验证的路径上盖三层楼。贴图格式按 WP2 的读数选
（POT 尺寸 + `Rgba8UnormSrgb` + `Filtering` 采样器，2×2 是最小 POT ✓）。

**下一片要接上的两件事**：① web 运行时的资源是**打包格式**（`rustlua_infra::pack::decode`），
所以还需要一个 `upload_texture_packed(bytes)` 入口（PNG 那条只覆盖了"原始字节"这一种情形，
且**尚未在 WebGL2 上端到端跑过**——原生只验了它的拒绝分支）；② 图集本身要能按需重传
（切片/流式加载），也就是同 `key` 原地替换这条语义要真的被用起来。

### WP5（第一片：真渲染器在 WebGL2 上可测、能建、能按期望值画对；已完成）

WP2 验的是"wgpu 的 GL 后端能不能用"，本片验的是 WP5 真正要回答的那件事：**本仓那台按 WebGPU 规格
写的渲染器，原样接到 WebGL2 上能不能把一帧画对**。两者的失败原因完全不同——能力探针过了不代表
渲染器过了（几十条管线的 WGSL→GLSL 翻译、绑定组布局、深度附件、顶点步长、帧计时用的时钟、构造期的
阻塞调用，坑都在后者），所以这一片**不做玩具渲染器**，直接在浏览器里把 `engine::host::Renderer`
跑起来，让像素和它自己的帧计数说话。

**先解决两个"跑不起来"的问题（都在引擎侧，语义不变）**

1. **时钟换 `web-time`**：`wasm32-unknown-unknown` 的 std 落在 `sys/time/unsupported.rs` 上，
   `Instant::now()` 直接 panic（"time not implemented on this platform"）。渲染器是第一个真在 wasm 上
   被调用的引擎子系统，帧计时（`cpu_frame_us`）必然踩到它。改的是渲染路径上仅有的两个文件：
   `renderer/passes.rs`（`render`/`render_into_texture` 的计时）与 `renderer/timestamp.rs`
   （`wait_for_gpu_timestamp` 的阻塞等待）。`web-time` 在原生上**就是** `std::time::Instant` 的再导出
   （同类型、零行为变化），在 wasm 上换成 `performance.now()`；它本来就在 `Cargo.lock` 里（winit 的
   wasm 依赖拉的），所以这次没有引入任何新下载。
2. **新增 `Renderer::new_offscreen_async`**：`new_offscreen` 用 `pollster::block_on` 驱动，而 wasm 上
   `Condvar::wait` 是 `panic!("condvar wait not supported")`——只要 `new_async` 里任何一个 await 点没有
   在首次 poll 就绪就会炸（GL 后端的 `request_adapter`/`request_device` 恰好是 `ready()`，所以这是
   "运气 + 契约"，不是安全边界）。新入口把等待方式交给调用方（wasm-bindgen 的 async 导出即 Promise），
   `new_offscreen` 一字未改。

**再做一把能量这件事的尺子**：`scripts/gpu-web-probe.ps1 -Stage render`

扩的是**已有的** `gpu-web-probe` 探针（不新建 crate）：探针依赖 `engine` 并开 `webgl` 特性，页面
`render.html` 手工合成一个最小 2D 场景（两个 NDC 四边形、内建白贴图 `texture = 0`、空 `path_handles`
走手写 mesh 回退），离屏渲到 `Rgba8UnormSrgb` 目标后读回像素，与**解析算出来的**期望值对拍
（四边形中心=白、背景=黑、白色像素面积≈两块四边形的面积）。驱动侧补了 `render-probe` 模式；
顺手修掉一个真 bug：`webgl-cdp-wait.js` 的 `findPage()` 把页面文件名硬编码成 `index.html`，新页面会被
判成"CDP 不可用"（exit 2），看起来像环境问题。

两处刻意设计，都是为了"失败也要有信息"：
- **构造期包在 error scope 里**：wgpu 对未被捕获的校验错误走默认 handler（panic），而探针的 wasm 是
  `panic=abort`——不包 scope 的话整个模块直接死，连"哪一条被拒"都报不出来。包了之后失败变成 JSON 字段。
- **阶段标记**：每一步把"最后到达的阶段"写进 `data-render-probe`（`surface_ok`/`adapter_ok`/`device_ok`/
  `constructing`/`rendered`/`readback_ok`），卡住时 dump 里最后那个值就是卡点。第一次跑还真用上了：
  页面停在 `pending` 时，正是靠它把范围缩到"构造期"。

**读数（真浏览器：Edge 无头 + ANGLE/SwiftShader，`device_type=Cpu`）**

| 项 | 读数 | 说明 |
| --- | --- | --- |
| 适配器后端 | `Gl` | 只有 WebGL2，符合预期 |
| 2D 贴图上限：适配器 → 请求 → 设备 | 8192 → **8192** → **8192** | WP2 硬约束 2 的现场复核：`downlevel_webgl2_defaults().using_resolution(adapter.limits())` 抬升**生效**，没有被压回 2048 地板 |
| 设备存储缓冲 | **0** | WebGL2 上没有存储缓冲 |
| `Renderer::new_offscreen_async`（修复前） | **被拒** | 见下面的原话；这是本片最重要的发现 |
| `Renderer::new_offscreen_async`（修复后） | **建成** | 见"修复后读数" |
| 像素/帧计数（修复后） | **精确命中** | 同上 |

被拒的**原话**（wgpu 校验错误，逐字）：

```
Validation Error
Caused by:
  In Device::create_bind_group_layout, label = 'rustlua-vector-text-bind-group-layout'
    Too many bindings of type StorageBuffers in Stage ShaderStages(FRAGMENT), limit is 0, count was 2.
    Check the limit `max_storage_buffers_per_shader_stage` passed to `Adapter::request_device`
```

⇒ **WP5 的第一个真阻塞点**：`construct.rs` 在**构造路径**上无条件建三处存储缓冲——
矢量文字的 `BindGroupLayout`（binding 0/1，就是上面这条）、3D 材质布局的 binding 2、
以及三个 `BufferUsages::STORAGE` 缓冲。WebGL2 上 `max_storage_buffers_per_shader_stage = 0`，
所以布局一建就被拒；构造是直线代码，校验错误 → panic → wasm 上 abort。**与 WP2 的结论一致，
只是这次落到具体那一行**。

**修法（已落地）**：按**设备能力**分叉，而不是按平台 `cfg`——这样原生桌面那条路完全不进新分支
（能力足够 ⇒ 到处都走原代码），而不是"给 wasm 另写一套"。

- `let storage_capable = device.limits().max_storage_buffers_per_shader_stage > 0;`，构造期定下后
  存进 `Renderer`（`storage_capable` 字段）。
- 全仓只有**两个** shader 用存储缓冲（`host/shader.rs`）：`VECTOR_TEXT_SHADER` 的
  `glyphs`/`segments`，以及 `MESH3D`/`SHADOW` 的 `instance_models`（`@group(1) @binding(2)`）。
  注意 **3D 蒙皮不在其中**——骨骼用的是 `joint_palette: array<mat4x4<f32>, 128>` **uniform** 数组，
  所以受影响的只有 GPU 实例化（`instancing_enabled` 也随之被强制关掉：同一件事的两种实现里选
  不需要存储缓冲的那种）。
- 能力不足时：矢量文字布局给空绑定表、材质布局去掉 binding 2、三个缓冲的 `STORAGE` 用法位去掉，
  三条管线（矢量文字 / 3D 网格 / 阴影）换成**占位管线**（一段只吐退化点、片元写全 0 的最小 WGSL），
  并把 `FrameFacts` 里对应的两个通道置假 ⇒ **计划里没有这两个通道，占位管线就不可能被绑上**。
  代价可见：丢弃的 draw 进 `dropped_draws`，构造期另有一条 `tracing::warn!`。
- 为什么不把字段 `Option` 化：那三个字段在 `passes.rs`/`gpu_texture.rs`/`arena.rs`/`world_sprite.rs`
  与全部原生测试里被引用一百多次，收益只是"少画一条本来就不该画的路径"。

**修复后读数**（同一条命令、同一台机器）

| 项 | 读数 |
| --- | --- |
| 构造 | 通过（`renderer_created=true`，无 `blocker`） |
| 帧计数 | `draw_calls=2`、`triangles=4`、`dropped_draws=0`、`passes=2` |
| 像素 | 白色像素 **5202 / 期望 5202**（精确相等），采样点不符 **0** 处 |
| `cpu_frame_us` | 9200（**只有"时钟在 wasm 上不再 panic"这一条信息量**；软件光栅的耗时不是性能读数） |
| 2D 上限 | 适配器 8192 → 请求 8192 → 设备 8192（存储缓冲 0） |

⇒ 真渲染器在 WebGL2 上**建得起来、画得对、读得回来**，`web-time` 时钟也确认在 wasm 上工作。
这一步只证明"管线能在这条后端上跑通且 2D 像素正确"，**不证明性能**——性能要等真机 GPU（WP0 的设备矩阵）。
门已接：`scripts/verify.ps1 -Web` 新增 `render-probe` 一步（0=通过 / 1=真回归 / 3=给不出 WebGL2 画布）。

**回归保护**：原生 `cargo test -p engine --lib host::renderer` 24 项全过（能力足够的路径逐字未变），
`cargo check/clippy -p engine --all-targets` 与 fmt 干净；`-Stage backend` 与完整玩法剧本门继续绿。

**顺带钉住的几条 wasm 事实**（下一片直接用，不必再踩）：目标纹理格式必须等于管线烘死的
`Rgba8UnormSrgb`；深度由 `render_into_texture` 自己管；`copy_texture_to_cpu`（mpsc + `recv()`）在 wasm 上
**会死等**，只能用 `readback_frame`（提交一次）+ `readback_pending`（只轮询，不重复提交——槽只有两个）
并每轮让出**宏任务**；世界精灵若不声明视图会用**单位矩阵**投影（不报错、也画不出来）；
非哨兵纹理路径在浏览器里必然走 `std::fs::read` 失败 → 白兜底，所以"带自定义贴图"需要先给渲染器
开一个公开上传入口。

**工作区与产物隔离**：探针依赖 `engine`（反向）不影响出货产物——`game_web` 不依赖 `gpu-web-probe`，
`cargo tree -p game_web` 里查不到它；探针自己的 wasm 8.5 MB（只存在于 `artifacts/gpu-web-probe`）。



这一片决定 WP5 的形态。结论：**搬得过去，但有 3 条硬约束**——而且三条都是**跑出来的**，不是读出来的。
证据分三层：编译层（特性与体积）、对照层（限制表）、真浏览器层（探针实跑）。

**证据 1（编译层）：wasm 上 wgpu 默认只有 WebGPU，没有 WebGL2**

`cargo tree -p game_web --target wasm32-unknown-unknown -e features -i wgpu` 的特性链是
`default → webgpu`，**没有 `webgl`**——也就是"什么都不做"的产物只会在 WebGPU 上跑，而**微信小游戏
没有 WebGPU**，现状等于"微信上起不来渲染"。

修法不是把那行 `features = ["webgl"]` 写死了事，而是做成 `engine` 的**按需特性**
`webgl = ["wgpu/webgl"]`：后端不该由"恰好依赖了 engine"的产物替所有人埋单（发布包体积是微信的硬
约束）。代价实测（同一次会话里的受控 A/B，除特性外输入完全相同）：

| 构建 | `game_web.wasm` |
| --- | --- |
| 默认（不开 `webgl`） | 8,711,933 B |
| `-F engine/webgl` | 8,851,119 B（**+139,186 B，+1.6%**） |

**更正留痕**：先前一度记下"5,519,459 → 8,851,126，+3.33 MB"——那是拿工作区里用户**在途改动之前**的
陈旧产物当基线。重做受控 A/B 后作废。凡体积/耗时对比，基线必须是同一次会话里紧接着造出来的。

原生侧两态 `cargo check -p engine`（默认 / `--features webgl`）都通过，桌面路径不受影响。

**证据 2（对照层）：WebGL2 的**保证值** vs 渲染器现在请求的 `Limits::default()`**

取自 `wgpu-types-27.0.1/src/lib.rs` 的 `downlevel_webgl2_defaults()` 与 `Limits::default()`
（`construct.rs:118` 现在请求的后者）：

| 维度 | `Limits::default()` | WebGL2 保证值 |
| --- | --- | --- |
| `max_storage_buffers_per_shader_stage` | 8 | **0** |
| `max_storage_textures_per_shader_stage` | 4 | **0** |
| `max_compute_workgroup_storage_size` | 16,384 | **0**（整组 compute 全 0） |
| `max_uniform_buffers_per_shader_stage` | 12 | 11 |
| `max_uniform_buffer_binding_size` | 65,536 | 16,384 |
| `max_color_attachments` | 8 | 4 |
| `max_vertex_buffer_array_stride` | 2,048 | 255 |
| `max_texture_dimension_2d` | 8,192 | 2,048 |
| `max_inter_stage_shader_components` | 60 | 31 |

渲染器里 WebGL2 **不支持**的用法一共 3 处（全在 `construct.rs`），且**都不在 2D 主路径上**：

- `rustlua-vector-text-bind-group-layout` 的 binding 0/1：**矢量文字**的两个只读存储缓冲（片元阶段取字形段）。
- 3D 蒙皮：binding 2 是骨骼矩阵的只读存储缓冲（顶点阶段）——web 用不到。

其余都过得去：**没有计算管线**（0 处）、`push_constant_ranges` 全是 `&[]`、
`MultisampleState::default()`（无 MSAA）、`Features` 只**条件**请求 `TIMESTAMP_QUERY`（WebGL2 上自动
退成 `Features::empty()`）、渲染通道只有一个 color attachment、顶点**全部** `step_mode = Vertex` 且
结构体 36 字节（离 255 的步长上限很远）。
=> **2D 主路径（精灵批次/图集/Tilemap/位图字/UI）不需要存储缓冲、不需要计算**：WP5 是"接过去"，
不是"重写"。

**证据 3（真浏览器层）：`crates/gpu-web-probe` + `scripts/gpu-web-probe.ps1`**

探针把 wgpu 的能力写成 `data-gpu-probe`/`data-gpu-probe-json`，由既有 CDP 轮询读回（新增
`gpu-probe` 模式）。本机实跑（Edge/Chrome 154 无头 + SwiftShader 软件光栅）：

| 事实 | 读数 |
| --- | --- |
| `Backends::GL` 建 surface | ✅ `create_surface_ok=true` |
| `Backends::GL` 拿适配器 | ✅ 后端 `Gl`；`ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero)), SwiftShader driver)`；`device_type=Cpu` |
| 适配器实际 2D 贴图上限 | 8,192（**远高于"保证值 2048"**） |
| `Limits::default()` 请求设备 | ❌ **被拒**：`Limit 'max_compute_workgroups_per_dimension' value 65535 is better than allowed 0` |
| `downlevel_webgl2_defaults()` 请求设备 | ✅ 成功 |
| 降级请求**之后**设备拿到的 2D 上限 | **2,048**（被降级请求**压低**了，而不是适配器的 8,192） |
| 只读存储缓冲绑定 | ❌ 校验拒绝：`Downlevel flags DownlevelFlags(VERTEX_STORAGE) are required but not supported on the device` |
| 真渲染 + 读回 | ✅ 清 `GREEN` 的 `Rgba8UnormSrgb` 贴图读回 `[0,255,0,255]` |
| `Backends::all()`（含 `default()`） | ❌ **一个适配器都拿不到**：`No suitable graphics adapter found; … gl support not compiled in, webgpu found no adapters` |
| downlevel flags | `NON_POWER_OF_TWO_MIPMAPPED_TEXTURES \| CUBE_ARRAY_TEXTURES \| COMPARISON_SAMPLERS \| ANISOTROPIC_FILTERING \| MULTISAMPLED_SHADING \| SHADER_F16_IN_F32`（**没有** COMPUTE_SHADERS / VERTEX_STORAGE / FRAGMENT_STORAGE / 纹理数组非一致索引） |
| shader model | `Sm5`（WGSL→GLSL 翻译没问题） |

**这三条是 WP5 必须照做的硬约束**（每条都是"不做就起不来"，不是风格偏好）：

1. **wasm 上必须 `Instance::new(&InstanceDescriptor { backends: Backends::GL, .. })`**，不能沿用
   现在的 `InstanceDescriptor::default()`：默认/all 那套在本机**连适配器都拿不到**（WebGPU 栈报
   `webgpu found no adapters`，并把 GL 记成 `not compiled in`）。wgpu 27 在 wasm 上按 `backends`
   位**选一族后端**，所以"WebGPU 优先、失败退 WebGL2"得自己写两段逻辑，别指望一个 instance 两种都给。
2. **`Limits` 按 `adapter.limits()` 夹取，不要直接写 `downlevel_webgl2_defaults()`**：后者会把
   `max_texture_dimension_2d` 从适配器实际支持的 8,192 **压到 2,048**，而字体图集（`font.rs`）是按
   **长到 4,096** 设计的——等于把一个已经支持的能力白白降级。正确形态是"请求 `adapter.limits()`，
   再把渲染器真正用不到的项（storage/compute）压到 0"。
3. **web 上不能走存储缓冲**：矢量文字那条路（两个只读存储缓冲）要么换 SDF/图集那条**已经存在**的
   文字路径，要么把字形段搬进贴图用 `texelFetch`；3D 蒙皮整条路径在 web 上不编。

另有两处 API 事实（本轮实测，写下来省下一次踩坑）：`Instance::create_surface(canvas)` 在 wgpu 27 的
wasm 上**编译不过**（`HtmlCanvasElement` 没实现 `HasWindowHandle`/`HasDisplayHandle`，
`SurfaceTargetUnsafe` 也没有 `WebCanvas` 变体），唯一通路是 `SurfaceTargetUnsafe::RawHandle` +
`WebCanvasWindowHandle`，并且必须自己管住那个 `JsValue` 的生命周期；`map_async` 是回调式，且
**`device.poll` 在 wasm 上是空操作**，等回调必须让出宏任务。

**这一片进门了**：`scripts/verify.ps1 -Web` 现在是 ① 页面级 WebGL2 能力（`verify-webgl.ps1`）→
①′ **wgpu 的 WebGL2 后端能力**（`scripts/gpu-web-probe.ps1`）→ ② 产物层 bundle → ③ 完整玩法剧本。
探针门自带红/绿/受限三分：surface 都建不出来 = 环境受限（exit 3，打印原因后跳过）；surface 建得出来
却拿不到适配器 = **判红**（这正是要抓的回归）；四条断言（后端必须是 `Gl`、降级 limits 必须能建设备、
清屏绿必须读回 `[0,255,0,255]`、只读存储缓冲绑定**必须**被拒）同时挡住"其实跑在 WebGPU 上"这种自欺。
探针是**独立 crate**（`cargo tree -p game_web … | Select-String gpu-web-probe` 无输出），发布包体积
一分不涨。

**限制（不得当作真机结论）**：这是**软件光栅（SwiftShader）**上的读数，不是真机 GPU，也不是微信
iOS/Android——真机矩阵仍属 WP0 的未验证项；`device_type=Cpu` 也意味着**性能读数不能从这个环境取**。

**留给 WP8 的一条**：`docs/32-webgl-浏览器平台验收.md` 里"wasm 实现、渲染走 wgpu 的 WebGL2 后端——
工作量最大，但**能力与桌面一致**"这句需要按上面的三条约束修正：WebGL2 上没有存储缓冲、没有计算、
uniform 绑定上限更小，**能力并不与桌面一致**；一致的只是"同一套 wgpu API 写法"。

### WP0（部分完成）：跨边界成本基线——**原生**读数

`engine/crates/rustlua-scripting/examples/lua_boundary_cost.rs`（新增，`cargo run --release -p
rustlua-scripting --example lua_boundary_cost`）。量的是"每帧编译一小段 Lua 源码"这条现行
协议的单价，输入快照按 `web-runtime.js` 的 `luaValue()` 规则生成（326 字节，形态取真实采样）。

| 操作（**同一份内容**，12 个字段） | µs/次 | 每调用 Lua 堆分配 |
| --- | --- | --- |
| 写 `__rustlua_dt`：编译源码（旧做法） | 1.78 | 375 B |
| 写 `__rustlua_dt`：直接写全局（本次已改） | 0.107 | 0 B |
| 注入输入快照：编译源码（**现行每帧协议**） | 8.41 | 3016 B |
| 注入输入快照：每帧新建表 | 4.74 | 1320 B |
| 注入输入快照：**原地复用常驻表（目标形态）** | **0.73** | **0 B** |
| 空 chunk 编译+执行（底价） | 1.45 | — |

换算到 60 Hz：现行协议每秒产生约 **199 KB** 的 Lua 垃圾，目标形态约 **0 KB/s**；
CPU 合计只省约 **0.56 ms/秒**。

**这三行数字改变了 WP2/WP3 的论证依据，必须记下来**：

- **CPU 不是理由**。0.56 ms/秒 ≈ 帧预算的 0.05%。此前"消除每帧源码协议"听起来像大优化，
  实测下来按 CPU 算它几乎不值得动。真正值钱的是**分配量**（199 KB/s → 0）——它影响的是
  GC 频率与停顿分布，也就是方案里排第 2 的"帧时间稳定性（P95/P99）"，而这一项
  **微秒读数完全看不见**。单帧看：3016 B ≈ 一个 11 KB 帧预算的 27% 被当成垃圾丢掉。
- **"每帧新建表"不够**。它仍有 1320 B/帧（6 张嵌套表的分配），比源码协议好 2.3×，
  但离目标差得远。**必须原地复用常驻表**：0.73 µs、0 B/帧，比现行协议快 11.6×。
  这条是给 WP3 的硬要求：输入表**只建一次**，每帧只改值，键集固定（不在热路径上扩容）。
- **名字不要每次重传字符串**。`lua_set_number(name, value)` 每次都要跨 wasm-bindgen 边界
  重新编组那个名字串；批量 ABI 应当一次性登记名字、之后只传数字句柄。
- **测法本身被证伪过两次，两次都值得记住**：
  ① 用"增量 GC 开着时的峰值增量"当分配量，把最昂贵的编译源码量成了 20 B/次
  （回收与分配同时在跑，只看到锯齿振幅）→ 必须**停用增量 GC** 再量堆增长；
  ② 对比用的"每帧新建表"只建了 5 个字段，而源码变体建 12 个，于是量出 544 B
  （真实值 1320 B，相差 2.4×）→ **对比变体必须逐字段等价**，否则是在偷着让结论好看。
  凡"分配/GC 类"读数都按这两条口径。

**限制（不得当作真机数字）**：这是 MSVC 原生读数，不是微信 iOS/Android，也不是 wasm 下的
读数。wasm 没有 JIT，编译占比通常**更高**，但没测就不能说；本基线只用于判断量级与方向，
**不用于宣称倍数**。wasm 侧读数见下一节。

### WP0 续：wasm 侧跨边界成本基线（**已补测**）

`scripts/wasm-lua/measure-lua-boundary-wasm.mjs`（新增；这是**测量**脚本，不是门）：
在 Node/V8 里加载**发布口径的真 wasm**（no-modules 胶水，与微信同形态；`wasm=3,958,017` 字节，
即 `verify-wasm-lua.ps1` 生成的那份），跑与原生基线**逐条对应**的操作；每项 5 轮 × 3000 次取
中位数，分配量用"停用增量 GC 后量 Lua 堆增长"（`collectgarbage("stop")`）。两次运行读数一致。

| 操作 | wasm µs/次 | wasm Lua 堆 B/次 | 原生 µs/次 | wasm/原生 |
| --- | --- | --- | --- | --- |
| 写 `__rustlua_dt`：编译源码（旧做法） | 2.59–2.71 | 271 | 1.78 | 1.5× |
| 写 `__rustlua_dt`：直接写全局（本次已改） | **0.31–0.34** | **0** | 0.107 | 2.9–3.2× |
| 注入输入快照：编译 326 B 源码（**现行每帧协议**） | **10.41–10.82** | **2648** | 8.41 | 1.2× |
| 空 chunk 编译（编译底价） | 0.91–1.02 | 186 | 1.45 | 0.7× |
| `lua_call_global` 走 JSON 参数（另一条逐帧协议） | 1.34–1.40 | 0 | — | — |
| （② 之内）Lua 侧自建同一张输入表 | 1.32 | — | — | — |

**换算出 WP3 要用的三条判断（这次是实测，不是外推）**：

- **现行每帧输入协议在 wasm 上是 10.4 µs + 2,648 B/帧**：60 Hz 下 ≈ **0.62 ms/秒** CPU 与
  ≈ **155 KB/秒** Lua 垃圾。分配量与原生同量级（3,016 B），CPU 反而更贵。
- **其中 87–88%（9.1–9.5 µs）是"编译 + 跨界编组"，建表本身只占 1.32 µs**。这条直接决定 WP3 的
  重心：要消除的是**每帧编译一小段源码**，而不是"少建一张表"——只优化建表，收益上限 1.3 µs。
- **固定跨界开销在 wasm 上占比更大**：最小的那次调用（直接写全局）是原生的 **2.9–3.2×**，
  而编译密集路径只有 1.2–1.5×；空转一次 `lua_call_global` 的 JSON 编组就要 1.4 µs。
  所以批量 ABI 必须摊到"**每帧一次调用**"；按字段各调一次的话，光固定开销就比现行整条协议还贵。

**范围与诚实边界**：host 是 Node/V8 的 wasm 执行器（Lua VM 在 wasm 里本来就没有 JIT，这一层与
浏览器同源），**不是**微信 iOS/Android 的 `WXWebAssembly`、也不是真机 CPU；V8 的 wasm 编译质量
与 JS 胶水 JIT 会影响最后一档，但**量级与方向**可用。本脚本**故意不挂进 `verify.ps1`**：
它是测量不是判据，计时类读数当门只会抖出假红。
复现：`node --experimental-wasm-exnref scripts/wasm-lua/measure-lua-boundary-wasm.mjs`
（需先跑一次**不带** `-SkipBuild` 的 `scripts/verify-wasm-lua.ps1` 生成胶水）。

> **改造后的复测读数**见 WP3 一节：同一条输入快照从 10.49 µs / 2,648 B 降到 2.22 µs / 0 B。
> 这一节保留**改造前**的基线，因为"省了多少"只有对着它才算得清；基线的三条结论
> （编译+编组占 87–88%、建表只占 1.32 µs、固定跨界开销 2.9–3.2×）依然成立于其余逐帧协议。

### WP0 续二：wasm **首帧与每帧**成本基线（含新增的 tracing 出口；已完成）

上一节量的是"跨边界一次调用多少钱"，这一节量的是**一次启动、一帧画面多少钱**——因为
"该优化谁"取决于这两笔钱各自的构成，而不是取决于哪段代码看起来慢。

**先补一个能力缺口**：引擎的诊断全走 `tracing`（`[render] font atlas ready` 这类现成结论），
而 wasm 宿主此前**没装订阅者**——那些行在桌面上有、在浏览器里被静默丢掉。上一轮查字体时就吃过这个
亏：只能靠 DOM 属性反推走到哪一步。本片加了一个极小的 `tracing::Subscriber`（`game_web/wasm_log.rs`，
不引新依赖 ≈90 行），装点与 panic hook 合并成**一个** `install_panic_hook()`：panic hook 管"炸了"、
它管"走到哪一步了"，两者必须同时在场才有用。两条约束写在代码里：**幂等**（与 vfs provider 同一套）、
**有上限**（400 条，到顶只报一次"已丢弃"，否则"日志刷屏"会变成新的性能问题）。

**分段计时落在哪**（都用 `web_time`，wasm 上 `std::time::Instant::now()` 是 panic 路径）：

| 读数 | 位置 | 含义 |
| --- | --- | --- |
| `sim_boot_ms` | `game_web::gpu_host` | 起场景 + 装载工程脚本（wasm 上唯一的长同步任务） |
| `first_frame_ms` | 同上 | **首帧**：首步（脚本 + `ui.measure_text` 首次读/解析字体）**加**首次取网格（首次文本图集 + 首次管线/贴图上传）。两段合报是因为它们在同一次 `next_mesh()` 里发生——拆开会把图集成本算到逻辑步头上 |
| `avg_frame_ms` / `fps` | 同上（帧循环） | 每帧均时。**只用于同机对比**：present 是 `Fifo`（跟随 rAF/vsync），且本机 GPU 是 SwiftShader |
| `elapsed_ms`（probe） | `rustlua-scripting::font_probe` | `ui.measure_text` 首次调用：读 + 解析工程字体 |
| `decode_ms` / `build_ms` / `primary_bytes` | `engine::host::runtime_scene::fonts` | 图集：读盘解包 / 解析建图集 |
| `elapsed_ms`（prewarm） | 同上 | `chars.txt` 字符集的光栅化预热 |

前两条同时进**控制台**（会被后续 `set_status` 覆盖，故必须另发一行）与**最终 note 属性**
（`boot_ms=… first_frame_ms=… startup_ms=…`，这句话活到最后一帧）。

**基线读数**（同一份产物、两条路各跑一遍，取多次运行的区间）：

| 读数 | 工程脚本路 | 对照路（不跑脚本） |
| --- | --- | --- |
| `sim_boot_ms` | 75.6 | 14.9 |
| `first_frame_ms` | 45.1 | 39.7 |
| 启动合计 | **≈121 ms** | **≈55 ms** |
| 字体：probe | 1.5–4.5 ms | 不触发（只有脚本调 `ui.measure_text`） |
| 字体：图集 decode / build | 0.6–0.8 / 2.0–4.5 ms | 同 |
| 字体：prewarm（1605 字） | 13.9–19.0 ms | 同 |
| **字体合计** | **≈17–24 ms（占启动 14–20%）** | 同 |
| `avg_frame_ms`（11 draws / 676 tris） | — | **6.6–7.6 ms**（fps 132–147） |
| `avg_frame_ms`（50 draws / 1422 tris） | 11.4 ms（fps 88） | — |

**三条结论（本片的意义就在这里）**：

1. **字体不是瓶颈**——整条字体链 ≈17–24 ms，其中**大头是 `chars.txt` 的 1605 字预热**（14–19 ms），
   读盘/解包/解析三项加起来不到 6 ms。⇒ 上一轮担心的"MB 级字体解析慢"**不成立**（该工程配的是
   597 KB 的点阵字体），**为字体做分包/按需加载没有收益**。真要动字体，动的是**字符集大小**。
2. **启动的大头在脚本装载**：脚本路比对照路多 ≈66 ms（`sim_boot_ms` 14.9 → 75.6）。
3. **每帧成本与画面规模线性相关**（11 draws ≈7 ms，50 draws ≈11 ms），且这台机器上 rAF 没被
   vsync 节流（fps > 60）⇒ 这个数是**纯 CPU/GPU 工作量**，可作为后续批处理优化的对比基线。

**未完成（下一步）**：① 这些数只覆盖本机 SwiftShader/headless，真机（微信）与真 GPU 仍无读数；
② `first_frame_ms` 把"首步"与"首次取网格"合在一起，若要再细分（脚本 vs 图集 vs 管线）需要更细的
打点；③ 启动那 ≈66 ms 的脚本成本还没拆到具体环节（`require` 链、编译、还是首帧 `update`）。

### WP0 续三：每帧成本**三分**与步内热点（已完成）

续二确认了"启动不是问题、钱花在每帧"，但每帧当时只有一个总数，于是"该优化渲染器还是逻辑"
仍然只能猜。本片把一帧拆开，并按引擎系统把**步内**再拆一层。

**拆法**（都不新增公开 API）：

| 读数 | 位置 | 口径 |
| --- | --- | --- |
| `avg_step_ms` | `game_web::gpu_host` | `RustScene::step()`：输入 + `run_script_steps`（逻辑与物理都在这里） |
| `avg_mesh_ms` | 同上 | `RustScene::mesh()`：从世界抽网格（提交前的 CPU 侧） |
| `avg_render_ms` | 同上 | `render_into_texture` + `present` + 一次显式 `poll` |
| `sched_frames` / `top_ms=[…]` | `game_web::rust_scene`（**常驻属性**） | 步内逐系统均值，前 4 名 |

两条口径上的讲究：① **首帧不计入**三个均值（那一帧含一次性建图集/建管线，已另有
`first_frame_ms` 承载，混进来会把三个均值一起抬高）；② 步内明细**不靠日志**——引擎本来就有
公开的 `RuntimeScene::last_schedule_report()`（编辑器与原生测试都在用），宿主累加取均值即可。
原来那条 DEBUG 级 `[schedule]` 是**每帧一行**，在浏览器里会吃光日志出口的上限：实测 400 条上限
下只剩 **28 行**样本，而且样本全落在最早的几十帧（最不具代表性的一段）。现在宿主聚合 +
订阅者挡掉该 target 的 DEBUG，限额留给真正一次性的事件。

**读数**（240 帧，两条路各一遍；本机 SwiftShader/headless，1280×720）：

| 读数 | 工程脚本路（50 draws/1422 tris） | 对照路（11 draws/676 tris） |
| --- | --- | --- |
| `avg_frame_ms` / `fps` | 9.06 / 110 | 6.33 / 158 |
| `avg_step_ms` | **2.21** | 0.39 |
| `avg_mesh_ms` | 0.35 | 0.20 |
| `avg_render_ms` | 0.36 | 0.26 |
| **每帧工作量合计** | **2.92 ms** | **0.85 ms** |
| 差值（空等/宿主） | ≈6.1 ms | ≈5.5 ms |

**关键读法**：`avg_frame_ms` 是**墙钟每帧**（含 `yield_to_event_loop` 等到下一次回调）；headless 下
rAF 不被 vsync 节流，所以其中 5.5–6.1 ms 是**空等**，不是工作量——"这台机器跑多快"要看工作量合计那一行。

**步内热点**（`sched_frames=240`）：

| 系统 | 脚本路均值 | 占步内 | 对照路 |
| --- | --- | --- | --- |
| **`lua_update`** | **1.88 ms** | **64%** | 0.07 ms |
| `physics2d_step` | 0.19 | 9% | 0.18 |
| `ui_click_dispatch` | 0.04 | 2% | 0.02 |
| 其余 16 个系统合计 | ≤0.08 | ≤3% | 同量级 |

**四条结论**：

1. **每帧的大头是工程脚本的 `lua_update`，不是渲染器**：脚本路每帧 2.92 ms 工作量里逻辑占 2.21 ms
   （`lua_update` 1.88 ms），抽网格 + 渲染合计只有 **0.71 ms**；对照路（不跑脚本）每帧工作量
   0.85 ms ⇒ **脚本带来约 2.1 ms/帧**。
2. **当前场景规模下 GPU 批渲染几乎没有可省空间**（50 个四边形 = 抽网格 0.35 + 渲染 0.36 ms）⇒
   下一步性能工作应**对准逻辑/脚本**这条线；批渲染的收益要等更大规模或真机 GPU 才体现。
   这条直接修正了"优化就是继续加码批渲染"的直觉。
3. 引擎自带系统都不是热点：除 `physics2d_step`（0.19 ms）外其余合计 < 0.1 ms。
4. **每帧的 DEBUG 日志不能当性能出口**（限额截断 + 样本偏差），累加进常驻属性才是能长期用的做法。

**未完成（下一步）**：`lua_update` 内部还没归因——它 = 工程脚本自己的逻辑 + 每次 Lua→Rust API
调用的桥接成本；要分开得给 API 入口加每帧调用计数（便宜）或做 Lua 侧采样（本机无工具）。

### WP0 续四：Lua **净耗时**进 Web 读数（**顺带修掉一个假读数**；已完成）

续三点名了"每帧 64% 在 `lua_update`"，但那还是**调度系统**的口径（含借出调度器、查全局、
错误包装）。要回答"是脚本自己贵，还是引擎围着它转的那些动作贵"，需要 Lua `update()` 前后卡表。

**引擎本来就在量**这件事（`last_update_micros` → `script_micros` → 公开出口
`RuntimeScene::take_script_micros()`），但**在 wasm 上被整段跳过**：

```rust
// 改前（rustlua-scripting/src/script/runtime.rs）
#[cfg(not(target_arch = "wasm32"))] let started = std::time::Instant::now();
#[cfg(target_arch = "wasm32")]     { self.state.borrow_mut().last_update_micros = 0; }
```

这是"std 时钟在 wasm 上会 panic"时代的权宜，而仓库后来已经有 `web_time`（ecs/infra/scripting
都换过，见第 14、17 轮）。它造成的不是"少一个数"，而是**同一份代码在两个平台给出相反结论**：
Web 上 Lua 永远显示 0 成本，而这一轮要问的恰恰是"每帧的钱是不是都在 Lua 上"。改成
`web_time::Instant` 后两边同一段代码 ⇒ 这条读数在 Web 上首次为真。这也正是"统一 Rust/WASM 状态"
要消除的那类分叉。

**三级归因**（读数：`avg_lua_ms` = Lua 净，`top_ms=[lua_update=…]` = 调度系统，
`avg_step_ms` = 整个逻辑步；三者相减给出"系统外围"与"步内其余"）：

| 读数（240 帧） | 工程脚本路（50 draws） | 对照路（不跑脚本） |
| --- | --- | --- |
| `avg_step_ms` | 2.45 | 0.38 |
| 其中 `avg_lua_ms`（**Lua 净**） | **1.97（占 step 80.4%）** | **0**（没有 `update` 函数，正确） |
| 其中 `lua_update`（调度系统） | 2.07 | 0.08 |
| 系统外围 = 系统 − Lua 净 | **0.10（占 step 4%）** | 0.08 |
| 步内其余（输入/物理/点击派发/空间传播…） | 0.38 | 0.30 |
| `avg_mesh_ms` / `avg_render_ms` | 0.41 / 0.43 | 0.21 / 0.25 |
| 每帧工作量合计 | 3.29 ms（Lua 占 **59.9%**） | 0.84 ms |

三条交叉验证都对上：对照路 `avg_lua_ms=0` 而 `lua_update=0.08`（纯外围）⇒ 没把"不跑脚本"
算成成本；系统外围 0.10 与对照路 0.08 同量级；各项之和与总量在采样噪声内一致。

**结论**：**帧循环里已经没有"引擎侧热路径"可摘**——每帧 60% 的工作量就是工程脚本自己的
`update()`，引擎围着它的全部动作只有 0.10 ms（5%）。要再压这条线，对象是**游戏脚本自身**
或**每次 Lua→Rust 调用的桥接成本**。

**未完成（下一步）**：桥接 vs 游戏逻辑仍未分开。工程每帧入口是 `main.lua::update()` →
`npc.tick()`/`combat.tick()`/`enemy.tick()`/`effects.update()`/`input.update()`/`player.tick()`/
`depth.tick()`，其中若干按**实体数**逐个调 API（本场景 31 个实体），所以 1.97 ms 既可能"逻辑重"
也可能"调用次数多"。分开的办法：在每个 API 注册处加计数（`create_function` 有几百处，机械改动）
或在 Lua 侧包一层 shim（需要引擎提供一个"跑 Lua 片段"的入口）。两者都还没做。

### WP0 附：工具链接线（本轮核实，避免下次白等）

- `scripts/zig-toolchain.ps1` 固定 `$ZigVersion = "0.16.0"`，缓存于 `engine/.tools/zig/`，
  解压目录 `zig-x86_64-windows-0.16.0/`，可用 `$env:ZIG` 覆盖。
- **`Install-ZigToolchain` 只认解压后的 `zig.exe`，不复用已下载的 zip**：把 zip 放进去再调
  `package.ps1` 会触发一次**全新下载**（本机实测会白等一次）。正确做法是先把 zip 解压到
  `engine/.tools/zig/zig-x86_64-windows-0.16.0/`，脚本里的提前返回就会命中。
- `package.ps1 -Platform webgl` **不跑 wasm-opt**（WP10 起有意保留纯 `try_table`，binaryen 的
  任意 pass 会把它改回 legacy EH），所以 webgl 只需要 zig + wasm-bindgen（本机 0.2.129 已在）。
  微信侧仍需要 **binaryen 133**（`minify-toolchain.ps1`）与 terser；terser 缺失只告警。
- 结论：本机 `webgl` 端到端可达（zig 到位即可）；微信端到端还需再下一个 binaryen，
  本窗口内很可能不可达。
- **更省的一条路（本轮实际走通的）**：`package.ps1 … -SkipBuild` **完全绕开 zig**——它只要求
  `target` 里已有 `assetc.exe` 与 `game_web.wasm`。而 mlua-sys 的构建脚本产物若命中缓存，
  `cargo build -p game_web --release --target wasm32-unknown-unknown`（**默认 profile**，
  不动 profile 环境变量）可以**不触发 C 重编**、也就不需要 zig。
  关键差别：**一旦改动 `CARGO_PROFILE_RELEASE_*`（打包分支要改 strip/opt-level/lto/codegen-units），
  构建脚本指纹变化会重跑 mlua-sys 的 build.rs，那时必然报 "cannot locate zig"**（本轮实测）。
  所以"缺 zig 也能验证"成立的前提是**沿用默认 profile 的既有产物**，代价是产物 profile 不等于
  发布口径（见"未验证"一节）。
- **临时 `.ps1` 必须带 BOM**（仓库约定，本轮又踩了一次）：PS 5.1 对**无 BOM** 的脚本按系统 ANSI
  解码，脚本里的中文会在解析期就变成乱码——后果不是脚本报错，而是它**照常跑完、只是写进日志的
  中文全坏**（本轮 `round17-gates.log` 的首行与"用时="就是被这么毁掉的）。同一段中文放在
  `pwsh -Command` 内联命令里没问题。⇒ 生成临时脚本要么带 BOM，要么干脆别在脚本里写中文。
- **诊断开关与剧本脚本的耦合（改动引入的隐性依赖，必须记住）**：`-DriveJhyt` 的导航读
  `data-rustlua-world` 拿玩家坐标，而我把该属性移到了 `DIAGNOSTICS_ON` 之后。两者目前靠
  `verify-webgl-bundle.ps1` **无条件加 `rustlua-diagnostics=1`** 才成立——谁哪天去掉那个 query
  bit，剧本就会以 `no-player` 失败，而读起来像是"运行时坏了"。已经在
  `plugins/webgl/README.md` 的画面自检一节写明这条前提。
