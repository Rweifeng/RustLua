## 0. 一句话风格定义

**国风武侠 × 星露谷式 cozy 像素**：硬边无抗锯齿、32×32 世界格、64×64 导出角色帧、左上统一光源、有限墨色描边、低饱和宣纸/竹青/旧金色板、三层场景渲染、少半透明。玩家一眼能从剪影认出"这是武侠农家的山庄"，而不是任何别的游戏。

## 1. 全局像素总纲（可验收硬指标）

| 维度 | 可验收基准（量化） | 不合格判据 |
|---|---|---|
| 世界格 | **固定 32×32 px tile**，全项目地表/墙/物件统一 | 同图混用 16 与 32、或导出做了双线性模糊放大 |
| 角色导出帧 | **64×64 px/帧**（绘制 32×32，导出 ×2 最近邻，`ART_SCALE=2`），相机 zoom=2 时角色在屏上 128px | 帧高 ≠ 64、存在半透明缩放 |
| 描边 | **1 px 硬轮廓**，墨色 `#1F2328`（ink/900），4 邻域 | 描边 >1px、灰色描边、无描边 |
| 抗锯齿 | **全程关闭**，`FilterMode::Nearest`、不生成 mipmap、RGBA8/sRGB | 出现软边、ALIAS 模糊 |
| 光源 | **全局左上**，阴影落在右下方；统一方向，禁止同一批资产出现 2 种光源 | 角色脚下阴影方向与场景光源相反 |
| 调色板色数 | 单场景主色 ≤ **1 主色 + 1 强调色**；角色单帧色数 ≤ **12 色**（含描边与阴影） | 同一场景出现 ≥3 套互不协调色系 |
| 透明背景 | PNG-24 透明通道；禁止 JPG 源素材 | 白底/黑底、不透明背景 |
| 动画帧间隔 | 项目统一默认 **200 ms**（5 FPS 待机类）；快动作刀光可 **100 ms**（10 FPS）；同一动作全方向帧间隔一致 | 同 clip 不同方向帧数/FPS 漂移 |
| 渲染分层 | 背景（地面）/中景（作物·道具·建筑·NPC·敌人）/前景（树冠·屋檐遮挡玩家）三层 | 前景不遮挡角色、Z 序混乱 |
| 半透明 | 仅雨雪粒子与受击闪白允许；UI/角色/sprite 主体**禁止大面积半透明模糊** | 道具/面板用了高斯模糊或 <40% 不透明压字 |
| 性能预算 | 每地图 ≤ **4 张 atlas**，单张 ≤ **1024×1024**；贴图尺寸必须正好等于组件声明的 `atlas_cols × atlas_rows × tile`，未用到的槽位全透明；字体子集**实测 1,612 码位（目标 ≥2,000 尚未达成，见 §6 字体行）**；音频实测 MP3 96 kbps / 22050 Hz（规格曾写 OGG，口径见 §7.2） | 单图 >4 atlas、尺寸与声明不符（切 UV 错位）、空槽留残留像素、字体超包 |

**图集预算为什么从 1 张放宽到 4 张**（M72-04 定，回写自 `51` 的旧口径"每图 ≤1 张
1024×1024"）：一张图按**角色**分，而不是一律合进一张——

1. `ground`：地表逻辑瓦（`manor` 现为 12 列 × 9 行 = 384×288，六族满块档 + 每族 16 格过渡）；
2. `farm`：农田 overlay（恒等寻址，6 列 × 1 行）；
3. `moist`：湿度 overlay，画在 farm 之上，只占第 1 列；
4. `crop`：作物图集，29 种 × 5 阶段 = 145 格，本身就要 12×13 以上。

合成一张的代价不是像素（145 + 108 + 12 格远小于 1024²），而是**批次与寻址**：引擎按 ECS
插入序排 tilemap 批次、web 端按 entity id 排，四层各自的 `atlas_rows` 不同，合并就得让
四个组件共享同一套行列声明，任何一层加格子都会挪动另外三层的条目号——四季换色（只换
`texture=`）与 M72-08 接作物线都会撞在这条上。分层之后每层独立扩，预算按层计。

上限仍是硬的：**每张 ≤1024×1024、每图 ≤4 张**。第 5 张必须先改这条口径再动手。

## 1.2 色阶与可读性契约（M72 补充，规范层，不宣称素材已完成）

锁定色板 token 是色相方向，**不是只允许八个 RGB 值**。下表按深→浅列出明确 sRGB hex；不使用含糊的“亮度 ±百分比”，也不宣称这些色值均已用于每张真实贴图。每族四档的 sRGB 相对亮度递增；这只是材质层次，不等于图集变体/可读性验收。

**这张表从 M72-04 起是机器可读的**：唯一口径在 `tools/terrain_ramp.json`，生成器
（`gen_terrain_tiles.py` 画地表、`gen_manor_art.py` 画建筑/道具、`gen_season_variants.py`
出四季）一律从表里取色，**不再在代码里现写 hex**。表与本文不一致时以表为准并回写本文；
`gen_terrain_tiles.check()` 会断言每族"深→浅"相对亮度单调递增、图集每个不透明像素都出自
本表，所以"改了文档忘了改生成器"这种分叉会被门拦下。

| 材质 | 深档（接触/缝隙） | 暗档（背光） | 中档（主体） | 亮档（左上受光） | 表里的族名 / 生成器常量 |
|---|---|---|---|---|---|
| 草 | `#4A6636` | `#5E7C46` | `#6F8F52` | `#7FA35E` | `grass` / GRASS_DARK / GRASS / GRASS_LIGHT / GRASS_HI |
| 土 | `#4E3A26` | `#63482F` | `#7C5C3E` | `#8F6E4A` | `dirt` / DIRT_WET / DIRT_DARK / DIRT / DIRT_LIGHT |

**同一格内的第三档明度可以来自顶点色**：`Tilemap` 组件的稀疏 `tints=`/`tints_rgb=` 把整格
乘上 `#F2F5FF`（阴面，0.96/0.98/1.0）或 `#FFFCFC`（阳面，1.03/1.02/0.99）一类的系数。
顶点色是**乘法**而不是新色相，所以它能在"族只有四档"的前提下把大面积同材质地块读出

### 1.3 像素单位、锚点与可读性硬门

1. **像素单位**：`1 px` 描边/纹理指 **32×32 绘制空间的 1 像素**；角色导出 `ART_SCALE=2` 后显示为连续 `2×2` 像素块，不能把导出 PNG 的 2px 边误判为 2px 绘制描边。角色单帧仍为 64×64；生成器绘制空间脚底基线是 `y=29`，导出帧对应像素行 `58–59`；旧 §3.1 的 `y=52` 与此不一致，本轮登记为锚点契约漂移，需后续按 sprite pivot、世界脚位与碰撞体联合核定，不能声称已对齐。
2. **剪影门**：角色、建筑、交互道具在 100% 与 50% 缩略预览下都能与相邻地面分离；主体边缘为绘制空间 1px `ink/900`，不得以半透明描边补救。
3. **对比门**：主体与其直接背景至少保持一个明度层级差；UI 文字使用 `paper/50` 或 `ink/900`，禁止低于 40% alpha 的正文。
4. **锚点门**：建筑/道具底边与 32px 世界格对齐；审计工具只能确认文件规格，锚点仍需预览或人工验收。
5. **遮挡门**：背景→中景→前景顺序必须显式登记；树冠、屋檐等前景可压角色，但不可覆盖交互提示与 HUD。**M72-06 已落地，机制与判据同源于 `scripts/data/lighting.lua`**（唯一的层带事实源，工具与门都只读它，不再各自写数）：
   - 前景遮断物 = `sorting_layer=foreground` + `order=-100`；特效 = 同一个 foreground 桶、`order=0` ⇒ **刀光永远压在树冠之上**（前景可压角色，不可压交互提示这条就是靠这个分带成立的）。投影贴片 = `world` + `order=-20`（在角色之前画）。
   - 树干/树冠、墙身/屋顶**分别登记**（`tools/gen_manor_art.py` 的 `LAYER_SPLITS`），两块按行拼回去逐字节 == 整张原图。
   - 量化判据：玩家可达位置上被前景盖住的角色像素占比 ≤ `occlusion.max_cover_ratio`，且全图最深 ≥ `min_cover_ratio`（否则前景层是白加的）。**`0.65` 这一档钉的是美术切点，不是运行期的宽容度**：树冠切顶 40 行实测最深 0.604、顶 57 行 0.861（人在树冠里只剩一条边）、顶 26 行 0.357（数字过得上旧判据 0.40，画面却读成"人站在树前面"——正是"靠放宽数字装没事"会奖励的结果）。取的是中间那档：露腿、头在树后。
   - 门：`cargo run --quiet -p game --example jhyt_m72_foreground_occlusion` §③④⑤（读原生 `mesh.draws` 提交序 + 运行期 `sprite.set` 反面对照）。工具（`preview_scene.py`）不验证绘制序。
   - 同一判据的第二份实现（web/微信的排序键与绘制循环是另写的两份，见下面第 9 款）：`node scripts/wechat-minigame-harness.js <发布目录>/launcher --remote auto --remote-root <发布目录>/assets --frames 90 --drive-new-game --check-foreground-order`——它看的是假 ctx 记下的**真实 `drawImage` 先后**，三段（正序 / 只改 `sorting_layer` 的反面对照 / 还原）读数在 `tasks/done/M72-06` 的 D 段。
6. **软边门**：PNG 必须 RGBA8；主体 alpha 仅允许 0/255，雨雪与受击闪白另行登记例外。尺寸正确或目录存在，均不等于接线完成。
7. **色阶审计边界**：工具可检查 PNG IHDR、明确 `icon=`/`texture=`/`sheet=` 路径和注册表枚举；不能从文件名、目录或启发式"看起来像"推断场景已接线、素材已被运行时使用。
8. **投影门（光向全局唯一，M72-06）**：一批图只能有一个光向，这条现在是**算出来的**，不是目测的。
   - 事实源 `data/lighting.lua` 的 `sun = { dir_x = 1, dir_y = -1 }`（左上光源 ⇒ 影子落右下），Python 侧由 `tools/light_kit.py` 按文本解析同一份，不执行 Lua、也不许生成器自己写偏移。
   - 贴片形状由 **sun 与本体接触椭圆**唯一决定：贴片 = 接触椭圆沿光向扫出的那一段（Minkowski 和），尺寸一律 `2r+1`（奇数）⇒ "贴片中心"就是中间那个 texel，从接触点量的偏移恰为 `(±hx, ∓hy)`，于是 `atan2` **精确**等于光向角，门实测 16 件最大偏离 0.000000°。
   - 取整两边同法：`.5` 一律进位（Python 侧 `half_up()`，Rust 侧 `(x+0.5).floor()`）。内建 `round()` 是银行家舍入、`f64::round()` 是远离零取整，两边各用各的会让门红在 1 像素上，而看起来像"光向算错了"。
   - 贴片是**纯白** RGBA8、alpha 只有 0/255（§1.3 第 6 条软边门的延伸）：暗与透全交给 `sprite tint`，于是"影子多暗"在盘上只有 `shadow_tint` 一处，改它三个宿主同时生效，贴片自己永远不需要重出图。
   - **接触阴影 ≠ 投影**：脚下椭圆在任何光向下同形，本身不携带光源信息 ⇒ 角度方差门只采投影贴片；对脚下阴影只断言"不往左上跑"（`actor_shadow.shift_x=2`、`shift_rows=0` 纯右偏，因为 64×64 帧的不透明像素已经铺到第 63 行，再往下挪就出框）。
   - **推断项（等实机参考再校，别当已证）**：`shadow_reach = 0.12`（正房 224 单位高 ⇒ 偏移 ≈26.9 单位 ≈0.8 瓦格；星露谷建筑影子目测 0.5–1 格，相机接近俯视时影子过长会读成"房子在斜面上"）与 §1.3 第 5 条的 `max_cover_ratio = 0.65` 同一性质。`docs/53` §5 早就记过这三条推不出来，需要实机参考。
   - **城门那一片有 17/27 行落在图外（已知限制，登记不修）**：`ManorGate` 本体底边正好压在地图下边界（`position=(480,0)`、96×96），贴片沿 sun 往右下扫 ⇒ `ManorGateShadow` 占 `y ∈ [−17, +10)`（`blob_95x27.png` @`position=(485,−17)`），27 行里 17 行在 `y<0` 之外。视野 1280×720、地图 1280×736 ⇒ 相机中心被夹死（`jhyt_m32_camera` 实测 `map=1280x736 view=1280x720 clamp_x=[320,960]`，纵向只剩 736−720=16 单位可动），可见带最低就是 `y=0` ⇒ 那 17 行玩家永远看不到，门口只留 10 行可见影子。这是"本体贴边 ⇒ 贴片必然出图"的几何后果，不是落点算错（§⑥ 对它的逐件复算同样通过，其余 15 片全在图内，最北一片到 `y=644`；M72-07 把南门本体重画后贴片从 `blob_91x25` 换成 `blob_95x27`，这条限制的形态没变、行数跟着长了 2 行）；要补全得把城门挪进图内或把地图下沿外扩一行，两者都动布局，本批不动。
   - 门：同一个 `jhyt_m72_foreground_occlusion` 的 §⑥⑦（逐件独立复算落点 + 够格而未挂影的反向清点 + 脚下阴影 8 朝向 × 4 帧质心同侧）。
9. **Y 排序容差（M72-06）**：`scripts/world/depth.lua` 只对 **actor 层**按脚位折 `order = -floor(y / STEP)`、`STEP = 2`、夹 ±999。三条口径写死在该文件头部，跨宿主同一份：
   - **容差 = STEP**：Δy < 2 世界单位落同一桶 ⇒ 谁先谁后不许被依赖（门实测 Δy=1 order 不变、Δy=2 恰好翻一桶）。M72-13 在 HEAD 副本上复跑取到两侧读数：同一 actor 脚位 Δy=1 时 `order` 仍是 −279，Δy=2 时恰好翻一桶（−279 → −280），方向是 **y 越大越靠后**；门输出里那行 `桶宽=STEP` 就是"容差不是别的常数"的断言，复现命令见本节末。
   - **静态物件不参与 Y 折**：层秩是主键，人恒在所有 `world` 物件之后 ⇒ "主角站在房子北边不被房子盖住"是设计，不是 bug。
   - **foreground 恒压角色、不看 y**：这就是前景层只放"悬空的上半张"的原因，也是 `max_cover_ratio` 存在的理由。
   - 禁止以实体 ID 当空间深度。`jhyt_m35_depth_sort` + 本门 §⑧ 两侧读数；微信/web 那条 (`scripts/wechat-minigame-harness.js --check-depth-order`) 见 M72-12 的宿主收口。上面那组 −279/−280 的复现：`cd engine && cargo run --quiet -p game --example jhyt_m72_foreground_occlusion -- <工程根>`（M72-13 在 HEAD 副本根实跑 rc=0，同一行还给出 `occluders=11 worst=0.604 bound=0.65 shadows=16 角度方差=0.000000° 脚下阴影=32帧 桶宽=STEP`）。
10. **碰撞门（每一格 `solid` 都必须有可视依据，M72-07）**：`solid` 串不是装饰性元数据——`scene_spawn.rs` 的 `solid_cell_colliders` 给**每一个实心格挂一个静态 cuboid**，所以多标一格就是"在屋外两步远的地方撞空气"，少标一格就是"走进墙里并被画在墙前面"。口径：
   - 一格可以实心的**唯一两种理由**：那一格的地表本身就是墙/水（`building_kit.TILE_NATIVE_SOLID = (WALL, WATER)`，瓦自己画的），或有一个 sprite 的**不透明像素**压在那一格上。按 sprite 的 **quad 矩形**标是错的：建筑贴图的 quad 四角几乎总是全透明（屋顶是梯形、檐口是斜的）。
   - **建筑**（`role=building`/`building_site`，本体在 `world` 层）= 本体不透明紧包围盒 ∪ 同名拆层屋顶件 − 门洞。层秩 `world(−1) < actor(+1)` ⇒ 墙永远遮不住身后的人，所以墙身那几格必须实心；拆层只是把一张图按行切两块往上多挂一条遮带，**占地与整张原图一模一样**，所以屋顶并进并集（等价形式：拆层前后占地逐格相同，门 §② 在守）。
   - **树/竹/单件道具**（`role=prop`）= **单格根碰撞**，只实心 `entity_meta cell` 那一格；树冠/竹梢那几格由第 5 款的前景遮断件负责盖人，不该挡人。**装饰**（`role=decor`）不参与碰撞（M72-05）。
   - **门洞**是唯一一处手填的数据，所以它自带三条反查：声明的洞格必须在自己的视觉框内（洞挪了位置而表没跟着改就红）、盘上那一格必须真的空着、贴图在"人站着穿过的那一格"（每列最低格）上实测不透明占比 ≤ 0.35，且从出生点按 4 邻域 BFS 走得到。
   - 事实源 `tools/building_kit.py`（`python tools/building_kit.py scenes/manor.scene --check`），门 `jhyt_m72_building_footprint` 是它的**第二份独立实现**（自己解 `.scene` 文本、自己解 PNG 的 alpha），两份都说"缺 0 / 悬空 0"才算成立。manor 实测：地表天然实心 187 格 + sprite 依据 183 格 ⇒ 应实心 **359** 格 == 盘上 359 格，缺 0 / 悬空 0；运行期 `tilemap.is_solid` 位图逐格相同（§⑤）。
   - 反面对照三条，都走同一个函数：竹子按 quad 框标实心 ⇒ 悬空 5 格、摘掉拆层屋顶件 ⇒ 缺碰撞 64 格、把南门洞填实 ⇒ 出口当场断。**为什么"按框"那条落在道具而不是建筑**：盘上 10 栋建筑的 quad 框与不透明紧包围盒逐格相同（贴图都铺满了画框），拿建筑做这条对照是空转——这条已按实测登记，不是口径松动。

> 运行 `python tools/audit_art_assets.py` 得到确定性事实；`FAIL missing_asset` 表示注册/规范要求的文件不存在，`FAIL missing_wiring` 表示已有或声明应有的接线指向不存在/缺失字段。两者必须分开处理，`INFO` 仅为事实计数，不是通过门。
