# 66-江湖有田-门面画面的黄金对账门：动手之前先把画面钉死（M63a）

64 号交的是"预设能进活世界"（`prefab.spawn`：画得出、点得中），65 号交的是"进去之后改得动"
（`prefab.set_rect` / `set_visible`）。这一批**一行门面代码都不改**，交的是动手之前必须先立起来的那道门：
`engine/crates/game/examples/jhyt_m63_title_prefab.rs` + 一张 68 行的迁移前黄金表。

为什么门在迁移前面：门面（`title_menu`）的画面上今天由**两层合成**，而"门面长什么样"没有单一真源——
挪一块木牌要同时改 `scenes/main.scene` 与 `scripts/ui/title_menu.lua`。这种结构下"迁进 `.prefab` 之后
画面没变"是一句无法验证的话，除非先把"现在到底画了什么"逐 id 记成一张表。所以 M63a 只钉表，
M63b 才动数据与脚本，动完拿同一张表对账。

里程碑号取 M63：M62 之后内容门没有再占号。

门跑的是真宿主（`engine::host::RuntimeScene` 起 `examples/game_jhyt`，固定 4 个步帧，1280×720），

```

```

## 2. 读数怎么做到与"载体是谁"无关

迁移会把块从一层搬到另一层，所以门读的数**不能来自某一层的私有接口**，否则搬完就读不到了。
三条读数通道：

| 通道 | 接口 | 为什么迁移前后同源 |
| ---- | ---- | ------------------ |
| 宿主本帧真正用于绘制的矩形 | 新增 `RuntimeScene::ui_rects_by_name(viewport)` → `名字 → UiRect` | 它 `ensure_scene_ui_layout(viewport)` 之后，把 `ui_layout_rects`（键 = 活实体槽位号）用新增的 `LuaRuntime::entity_names_by_slot()` 换成**名字**。名字这张表是 `entity.find` 查的那一张，**场景实体与 spawn 实例共用** ⇒ 今天从 `main.scene` 读到的 `BtnStart`，迁移后从预设实例读到的还是同一个 `BtnStart` |
| 节点的版面数据 | `entity.find(name)` → `EntityId::from_raw(index<<32 \| generation)` → 一次 `with_script(with_world)` 借完 17 个节点的 `UiRectLayout` / `UiText` / `UiImage` / `UiEvents` | 组件挂在实体上，实体来自场景还是预设不影响字段 |
| 动态层 | `ui.text_get` / `ui.image_get` / `ui.panel_get`（nil ⇒ `missing`，`visible == false` ⇒ `hidden`） | 与实体层无关，正好用来抓"两边都在画" |

两个没用成的口径，记下来免得下次再试：

- **`prefab_ui_rects` 不够**——它只含 spawn 实例，不含场景实体，而迁移前门面上 14 块全在场景侧。
- **键不能是实体句柄**——`prefab_spawn_names` 那份表只覆盖 spawn 实例，场景实体反查不出名字；
  而槽位号本身缺 generation，还原不成 `EntityId`（65 号 §3 同一个坑）。所以 `entity_names_by_slot`
  直接给名字，不让宿主反查。

绘制与命中共用链末端的同一张 `ui_layout_rects`（`push_scene_ui` 与 `compute_click_targets` 都从它读），
所以"矩形读到了"就等于"这块画得出来、也点得中"——门不需要再单独问命中。

## 3. 黄金表 68 行的形状

`engine/crates/game/examples/support/jhyt_m63_title_menu_golden.tsv`，`层 \t 角色/节点 \t 种类 \t 读数`：

```
31 行 shown   —— 逐块画面：矩形/贴图/字号/字/九宫格
37 行 authored —— 逐节点版面：layout 17 + text 7 + image 10 + events 3
```

三个格式化决定都是为了让两边可直接比：

- 位置统一 `%.2f`；字号统一 `%g` 口径（Rust 侧 `g()`：整数值不带小数点），否则 Lua 的 `24` 对上 Rust 的 `24.00` 就成了一行假红。
- **九宫格边同时进 shown 与 authored**：它是"这块板子怎么拉伸"的数据，丢了不改矩形、只改画面，光比对矩形抓不到。
- **高亮框只取几何、不取 alpha**：`title_menu.M.anim()` 的呼吸项让它的透明度每帧不同，把 `a` 写进表就等于钉了一张"每帧都在动"的黄金表。
- 文字读数不含颜色——动态层这条通道压根没有颜色参数（`ui.text_at(id, x, y, text, scale, font_size)`），这是 §4 第二条的来源。

```
cd engine && cargo run -q -p game --example jhyt_m63_title_prefab -- --capture   # 打印 68 行读数表后退出
cd engine && cargo run -q -p game --example jhyt_m63_title_prefab                 # 与黄金表逐行对账
```

`--capture` 是这批能成立的前提：**表是从迁移前的树上跑出来的**，不是新实现自己吐的数。

## 5. M63b 怎么用这张表（一张表、两种契约）

迁移之后必然出现两类差异，只有第一类算破画面：

1. **`shown` 31 行逐字节不许变**。块数、位置、字号、字、贴图、九宫格全同 ⇒ "一像素没动"。
   载体换了而名字没换，所以同一块的读数字符串本就该相同；标签三行会从"动态画的 578"变成
   "实体画的 578"，字符串一致，对账不红——这正是 ② 那格存在的理由：它提前告诉你**要抄哪一份**。
2. **`authored` 会长、也会少**，这是搬家的正常代价，不是破画面：今天 7 块静态装饰（hover、四角、
   竹分隔、印章）与三行标签只有动态层读数、没有节点 ⇒ 迁进实体层后**多出** layout/image 行；
   同时 `main.scene` 里那三份从未显示的 `Text` 数据**消失**。所以 M63b 的操作规程是：
   `--capture` 重导一次，人工核对 diff **只允许落在预期清单上**（三行标签的 offsets 与颜色、
   装饰节点的新增行、场景旧 Text 行的删除），其余一行不许变；新表落库后由它继续守后面每一屏。

这就是为什么两张表打在同一个文件里、由同一个门比较：读的人一眼能看出"这条是画面契约、那条是搬家契约"。

三道盲区，写清楚免得被当成"门绿了就没事"：

1. **文字颜色不在账上**（§4 第 2 条）——迁移时那三行字的颜色是必须由人决定的，门不会替你决定。
2. **每帧变化的视觉属性不在账上**——高亮框的 alpha、hover 的贴图切换、`title:hint` 的文案随选中态变，
   黄金表钉的是"选中项 = 第一项、新档、4 帧"这一个确定起点。换选中态的对账要另跑一次读数。
3. **只量 1280×720 一档视口**——门面项目的 `meta ui_reference_width/height` 就是 1280×720；
   参考分辨率之外的等比缩放行为这条门看不见（它守的是搬运无损，不是响应式正确）。
