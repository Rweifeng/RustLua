## 3. 面板与按键

模式机（`state.lua`）新增 `Quest`：`Playing / Dialogue / Inventory / Shop / Pause / Quest / Transition`。
`input.update()` 在 `not Playing` 早退**之前**分发各面板（M16-01 语义：UI 输入不落到世界），
并带**自愈**：mode 停在某个 UI 态但面板未打开（读档/切图残留）时复位 `Playing`。

> 引擎输入层当前只暴露字母键 / `Space` / `Escape`（无方向键、无 Enter），故面板用
> `W/S/A/D` 代替方向键，`空格` 代替确认，`Esc` 代替取消。

| 面板 | 打开 | 选择 | 操作 | 关闭 |
|---|---|---|---|---|
| 背包 `inventory_ui` | `I` | `W/S` 上下、`A/D` 跨列(±10)、`1-9` 定位 | `U`/`空格` 使用（`inventory.use`）、`E` 装备到 tool/weapon 槽、`C` 设为当前种子 | `I` / `Esc` |
| 任务日志 `quest_ui` | `L` | `W/S`、`A/D` 翻页、`1-9` | 只读（显示五态 + 目标进度） | `L` / `Q` / `Esc` |
| 暂停 `pause_menu` | `P` | `W/S`、`1-9` | `空格` 确认（继续/保存/读取/返回标题）、`+/-` 音量 ±10% | `Esc` / `P` |
| 对话 `dialogue` | 面向 NPC 按 `E` | `W/S` 或数字键 | 数字键/空格选择 | `Esc` |
| 商店 `shop` | 面向店主按 `E` | `W/S` 或数字键 | `F` 买卖切换、`+/-` 数量、`空格` 确认 | `Esc` |

- 背包：显示名称/数量/分类、容量 `占用/上限` 与负重；选中项详情含「可使用/可装备/可设为种子」提示；
  失败原因（`not_enough`/`no_effect`/`not_equippable`/`not_seed`）就地显示并播取消音。
- 任务日志：**只读**，交付仍走对话/交互单一入口（M17-03），避免第二条交付路径。
- 暂停菜单：保存/读取走 `save_manager.save()/load()`；读取后由 `main.lua` 暴露的
  `jianghu_reload_map()` 重放本图 overlay 并**自动回到玩法态**（`enter_playable_map` 复位面板与模式），
  保存则停留在菜单并显示「已保存」；返回标题走 `jianghu_return_to_title()`
  （复位一次性引导标志，下次从标题进入重新走 boot 判定）。

## 4. 音频

- 生成：`py -3 tools/gen_audio.py` → `examples/game_jhyt/assets/audio/*.wav`
  （16-bit / 22050 Hz / 单声道；BGM 14–16s 可无缝循环且 ≤2 MB；音效 ≤0.6s；
  纯 Python 标准库、确定性输出、脚本自带自检。清单与许可证见 `docs/THIRD_PARTY.md`）。
- 运行时 `scripts/audio.lua`：
  - `play_bgm(map_id)` 按地图选曲（`MAP_BGM`），**同一曲目不重启**，切图才换曲，
    未登记地图回落 `bgm_wilds`；标题走 `play_title()`。
  - `sfx(name)` 包装 `audio.play`；`set_volume(v)` / `adjust_volume(±)`（0..1）。
  - 缺失文件 / 无输出设备 / 无 asset 目录：`pcall` 静默降级 + 一次性 debug 日志，
    **绝不中断玩法逻辑**（引擎侧本身只 `warn`）。
  - 音量随存档持久化：provider `"audio"` → `{ volume }`。
- 接入点（只在成功路径播放）：翻土/播种/浇水/收获、命中/受击、交付、买卖、对话开闭与选择、
  面板开闭与确认/取消、睡觉、建造放置/升级、制作开工/收取。

## 5. 新手引导

- `data/tutorial.lua`（纯数据，`version=1` + `validate_all`，已登记进 `scripts/validate_data.lua`）
  声明 10 步：`till → plant → water → sleep → goto_village → talk_npc → accept_quest → deliver → craft → done`；
  每步 `prompt`（HUD 单行）+ `detail`（文档）+ `match`（`action` / `action_prefix` / `day_start` /
  `enter_map` / `quest_accepted` / `quest_delivered` / `finish`）。
- `scripts/tutorial.lua`：
  - 进度写 `state.vars["tutorial_step"]`（= 已完成步数），随 `state` provider 存档恢复，无需新 provider。
  - **幂等**：每次事件最多推进一步，重复触发同一步不重复推进；奖励锚点
    `state.vars["tutorial_rewarded"]` 保证一次性奖励（回复药 ×1）不重复发放。
  - **非新档不打扰**：`tutorial_step` 缺失（功能上线前的老档）→ `prompt()` 返回 `nil`、事件零写入。
  - 事件源：`input.update`（Playing 每帧 `on_action`）、`main.on_day_start`、`main.enter_playable_map`。
  - `new_game` 调 `tutorial.reset()` 从第 0 步开始。
- HUD 左下显示 `引导 N/10：<prompt>`；`L` 面板可查任务进度。

## 6. 决策点与坑（实现记录）

1. **标题场景布局**：`project.toml` 的 `startup_scene` 当前是 `scenes/main.scene`（并行场景批次把门面从
   历史上的 `scenes/title.scene` 收敛到 `main.scene`，`title.scene` 已从工作区移除）。任务书举例
   `scene.load('title')`，实现改为**优先尝试 `title`、缺失回落 `main`**（`main.lua` 的
   `jianghu_return_to_title()`），两种布局都可用；标题 BGM 与时钟冻结在任意非玩法场景的 `on_create` 生效。
2. **水壶此前不可获得（MVP 闭环硬缺口）**：`farm.act` 浇水要求 tool 槽装备 `watering_can`，
   但商店不售工具、也没有任务奖励，且 `weather` 永远不会变 `rainy`（无天气调度）——
   作物永远无法成长，「播种→浇水→睡觉→收获→交付→制作」不可完成。M19-02 在新档
   `inventory.setup()` 直接发放 1 把水壶，并把「打开背包 → 选中 → `E` 装备」写进引导第 3 步。
   （天气随机的排程属内容项，本任务不改，避免破坏 headless 确定性。）
3. **模式机新增 `Quest`**：任务面板需要一个 UI 模式才能继承 M16-01 的「UI 输入不落到世界」；
   同时在 `input.update` 加了模式自愈，修掉「存档时正开着面板 → 读档后 mode 残留导致输入被永久吞掉」
   的既有隐患。
4. **输入层限制**：无方向键/Enter/Tab，面板选择统一 `W/S/A/D` + 数字键 + `空格`/`Esc`。
5. **音量单一事实来源**：`audio.lua` 持有音量，直接调用引擎 `audio.volume()` 会让模块状态失真；
   面板/存档一律走 `audio.set_volume/adjust_volume`。
6. **UI 面板用 `ui.text_at/panel/hide` 每帧整体重绘**（沿用 `shop.lua` 范式），因为场景切换会清空动态 UI；
   背包「网格」用两列 × 10 行的文本槽位实现（品质框省略），不依赖 `ui.grid` 命中测试。
7. 音效不改变任何玩法结果：所有 `audio.sfx` 调用点都在状态写入之后，且 `pcall` 保护。
8. **`inv.equip` 只是标签，工具必须真实发放（2026-10-04）**：引擎侧
   `inv.equip(id, slot, item_id)` 是 M16-07 留的装备骨架
   （`engine/crates/rustlua-scripting/src/script/api/inventory.rs`）——**不校验数量、不消耗堆叠、
   也不把上一件退回背包**。而背包面板的行只来自槽位（`ui/inventory_ui.lua` 的 `snapshot()`
   只收 `item ~= ""`）。两条规则叠起来意味着：**只写标签、不发放堆叠的工具，玩家一次换装就永久失去它**。
   锄头正是这种形状（`inventory.setup()` 原先只有 `inv.equip(..., "tool", "hoe")`），
   于是「装备水壶后无法切回锄头」→ 翻土永久不可用（水壶/斧/镐是同一个坑的三次前科，见上面第 2 条）。
   修法是一张 `STARTER_TOOLS` 表（`inventory.lua`，锄头/水壶/伐木斧/矿镐）：`setup()` 按它发放，
   `restore()` 按它补发背包里计数为 0 的件。**补发成立的前提**是这四件工具没有第二条获取途径
   （商店不卖、`data/tools.lua` 里没有 `sell` 字段可卖、无任务奖励、也不会被消耗），缺件即死档；
   正因为发放与补发共用同一张表，以后加工具只改一处不会再漏。老档两种坏形状都能自愈：
   槽上还指着锄头（只写标签）与槽已被水壶顶掉（连引用都不剩，就是玩家报的那一种）。
   - 复现与读数：`cargo run -q -p game --example jhyt_m19_ui`（`M19-02c` 新增「面板里选中锄头 → `E` →
     `equip_list().tool == "hoe"`」，横幅 `inventory_rows=8`，比修前多一行锄头）；
     `cargo run -q -p game --example jhyt_m19_slice`（`①` 在原有 `equip_list().tool == "hoe"` 前加
     `inv.count(...,'hoe') == 1`）；`cargo run -q -p game --example jhyt_m22_save_isolation`（新增 `⑨`
     两条：`{ slots 全空, equipment.tool = "hoe" }` 读档后断 `1/hoe`，
     `{ slots 只有 1 把水壶, equipment.tool = "watering_can" }` 读档后断锄头/水壶 `1/1`）。
     两处机制各自跑过反向对照（同一份用例、只把补丁关掉），退出码均 1：发放去掉后
     `jhyt_m19_ui` 红在 `ui.inventory_ui: no row for hoe`、`jhyt_m19_slice` 红在
     `inv.count(...'hoe') = 0, want 1`；补发去掉后 `jhyt_m22` 红在 `= "0/hoe", want "1/hoe"`。
     其余 jhyt 用例全跑一遍无连带损伤（`m21_appearance`/`m29_season_weather`/`m32_camera` 三条是
     修前既有红，红点分别是主角 clip 数、docs/48 资源表计数、进图首帧相机）。
   - 它买不到的部分：装备语义本身没变——`inv.equip` 仍不占用/消耗堆叠，同一件工具可以同时
     出现在行上和槽里，换装时旧件也不会「退回」背包（它本来就没被拿走）；补发只覆盖
     `STARTER_TOOLS` 里那四件没有获取途径的工具，将来若给某件**可消耗或可卖**的物品打槽标签，
     这条自愈帮不上，得按那件物品的获取途径另想补给的口子。

10. **招式快捷栏按画布宽度换行，越界改成可机器验收（2026-10-05）**：玩家报两件事——
    「HUD 左边那个空心方块是什么、点不动」和「快捷栏最右那张只露半张」。
    - 空心方块 = `hud:avatar_frame`（`ui/hud.lua` 的 `skin.icon("hud:avatar_frame", x - 56, y + 8, 48, 48)`，
      贴在状态面板左侧）。它是**涂装不是控件**：HUD 没有任何点击通道，所以点了没反应是有意的；
      看着空是因为框里没画头像（见下面"买不到的部分"）。
    - 半张卡的根因是**单行排法**：8 招 × (48 卡 + 4 间隔) 从设计 x=992 排到 **1404**，而
      `layout.DESIGN_W` 只有 1280 ⇒ 第 6 张右半被窗口切掉、第 7/8 张完全不在屏上（招式从 5 扩到
      8 那天起就是这样）。为什么没有一门门红：`layout.audit()` 只查 `M.PANEL` 注册过的面板矩形，
      招式卡是 `ui.image`；而 `TOUCH_KEEP_CLEAR.hud_skill_bar` 抄的还是 5 张时代的 `260×48`。
    - 修法三处：每行列数由画布宽度推导（`floor((1280-992+4)/(48+4)) = 5` 张一行，新增招式只往下

      （`entitySortKey`），于是两个宿主各排各的。修复：`sprite.set` 与场景加载同批写排序层，
      并给 `sprite.get` 补上 `sorting_layer` / `order` 回读（web 的 shim 此前也没有这两个键，
      一并补齐，键名与默认值 `default`/`0` 与原生一致）。
    - ② **游戏**：两个宿主的**主排序键都是 `层秩 × 1000 + order`**，而玩法里没有任何一处把 Y
      写进 order ⇒ 同层角色的先后落在"实体 id / 纹理下标"的巧合上。修复：新增
      `scripts/world/depth.lua`（`attach` = `sprite.set` + 立刻按 Y 落一次 order，`tick`
      每帧只在**桶位变化**时重写），主角 / NPC / 敌人三条挂形象路径一律改走 `depth.attach`
      （`enemy_art.apply` 是生成器产物，不动它，改为在 `activate` 里把同一张串交给 depth）。
    - ③ **方向**（第一版就栽在这条上，用户肉眼看出来的）：`order` 该随 y **递增还是递减**
      不是靠直觉定的。这台引擎的世界 **+y 朝上**——`world_to_screen` 写的是
      `screen.y = h/2 - view.y*zoom`（`rustlua-camera/src/camera/component.rs:138`、
      `bake.rs:89` 各一份），web 的 `toCanvas` 是同一条（`web-runtime.js` 的
      `y: 360 - (wy - camera.y)*zoom`，注释里就写着"世界朝上 ↔ 画布朝下"）。
      于是"越靠画面下方 = 越近"对应的是 **y 越小越近**，画家顺序要求越近的越后画
      ⇒ **`order = -floor(y / 2)`**。第一版按屏幕坐标的直觉写成 `+floor(y/2)`，
      排序键、合批、回读全都对，唯独方向反了 ⇒ 主角站在 NPC 下方时被盖住，而**两个宿主的门都是绿的**
      （那时门断言的是"我以为是哪个方向"）。现在 §② 断的是**名次方向**而不只是"排过序"。

    为什么是 `order` 而不是 `z`：带 z 的那条世界深度通道只有原生渲染器有、web 完全不认，
    且原生 overlay 通道的排序是 `layer → 纹理 → 插入序`、**显式忽略 z**。order 是唯一一份
    "两边都读"的深度杠杆。为什么不把 Y 直接插进引擎的排序键：那会压碎"同层同纹理合批"
    （每个角色一个 draw call）。代价是 Y 被量化成 **2 世界单位**的桶、且 order 夹在 ±999
    （角色贴图 64 单位高，2 单位的错位肉眼看不出；夹取上限的意义是"不溢进相邻层桶"）。
    顺带一条必须跟着改的：特效原先借 `actor` 层堆 `order=50`，Y 排序上线后 actor 的 order
    最高到 +999，远处角色会把刀光盖掉 ⇒ 特效改挂 `foreground`（层秩 2 = 2000，恒在所有
    actor 之后；方向翻转后 actor 桶落在 -999..0，同样不会越过 foreground）。

    - 读数：`cargo run -q -p game --example jhyt_m35_depth_sort` →
      `y=[120, 180, 240] order=[-60, -90, -120] 绘制序=3→2→1（y 最小的最后画）` / 倒过来 →
      `y=[240, 180, 120] order=[-120, -90, -60] 绘制序=1→2→3`、
      `场上 actor 实体 5 个：player(y=112)=-56 npc_gu_changfeng(y=208)=-104 npc_lu_guizang(y=336)=-168 …`
      （主角 y 最小 ⇒ order 最大 ⇒ 最后画 ⇒ 盖在 NPC 之上）、
      `夹取：order=[-999, -999, -999]（y→+∞ 钉在 -999）；特效 draw #18 在全部 actor（最靠后 #15）之后`、
      末行 `jhyt_m35_depth_sort_ok … clamp=-999 effect_after_actor=true`；
      活体宿主那半 `node scripts/verify/wechat-minigame-harness.js <发布目录> --frames 420
      --drive-new-game --check-depth-order` →
      `depth_order="ok,forward=[950,949,947],flipped=[947,949,950]"`（`--check-api-contract`
      同跑仍 `api_contract=ok,cases=33`，新回读键没有破坏两侧契约对拍）。
    - **像素级目验**（门读的是提交序，不是像素，所以这一半单独看过一次）：`py -m http.server
      8199 --bind 127.0.0.1` 起 `builds/webgl`，浏览器开 `index.html?rustlua-drive=auto`
      （自动走完标题→进山庄），再用活体桥 `__RUSTLUA_LUA_BRIDGE.lua_call_global('__eyeball','[0]')`
      把顾长风搬到主角的 `y+40` / `y-40` 各截一张图。读数：主角 (528,114) `order=-57`；
      NPC 在 `y=154`（画面上方、更远）时 `order=-104` ⇒ **主角盖住 NPC**；搬到 `y=74`（画面下方、
      更近）时 `order=-37` ⇒ **NPC 盖住主角**。两张图里都是"屏幕上靠下的那个在前"，与
      「y 越小越靠前」一致。（`lua_do_string` 只执行不回值，取读数必须走 `lua_call_global`
      那条带返回的口子；搬完要等一两帧，`depth.tick()` 才会把新 order 写下去。）
    - 反向对照（六处各自跑红过，改回即绿）：① 拿掉 `renderable.rs` 里那句 `SpriteSorting`
      写入 → 原生 §① 报 `sprite.get(...).order 不是数字（读回 "nil"）`；② 让 `depth.lua`
      只写组件串不追 `;order=` → 原生 §② 报 `probe1 (y=120.0) 的 order=0，应为 -60`；
      ③ 把特效改回 `sorting_layer=actor;order=50` → 原生 §④ 报
      `特效 draw #9 没有排在最靠下的 actor (draw #15) 之后`；④ **只改发布包里**那份
      `mainpack/scripts/world/depth.lua.txt`（不动仓库源码）→ 活体门报
      `正序 探针 1：order=0 与脚位 y=48 的桶不一致`；⑤⑥ **方向**两处各钉一次：把
      `depth.lua` 的 `-math.floor` 改回 `math.floor`（就是第一版的写法）→ 原生 §② 报
      `probe1 (y=120.0) 的 order=60，应为 -60`；只把发布包里那份副本改成同样的写法 →
      活体门报 `正序 探针 1：order=24 与脚位 y=48 的桶不一致` + `反序 探针 1：order=88
      与脚位 y=176 的桶不一致`。④⑥ 证的正是"web 的排序键是另写的一份，
      原生全绿不代表这边也绿"这件事只有活体门拦得住；⑤⑥ 证的是这两条门真的在断**方向**，
      不只是"排过序"。
    - 它买不到的部分：① 门里读的是**提交顺序**（原生 `mesh.draws` 的下标 / 微信假 ctx 的
      `drawImage` src 序列），不是像素——"画面上真的谁盖住谁"仍要目验；② 桶位量化意味着
      2 单位以内的两个角色谁在前仍由 id/纹理决定（同层同纹理本来就合批，无法再分先后）；
      ③ 位置是宿主侧积分的，`depth.tick()` 读的是"本帧将被画出的那个位置"，两个宿主同样
      有一帧滞后，门不证这一帧的视觉误差；④ 建筑/道具在 `world` 层（层秩 −1），角色永远
      盖在它们之上——这条本轮没改，也不归这条门管。
