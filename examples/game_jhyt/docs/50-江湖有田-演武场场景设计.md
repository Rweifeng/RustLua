## 1. 定位与约束

演武场是山庄的练武场（总策划 §10.1"玩家山庄：住宅、药田、工坊、练功场"），
同时承担 M18-01 战斗系统的 headless 验收场。因此重设计遵循两条铁律：

1. **验收锚点不可动**：`jhyt_m18_combat` 硬编码了战斗几何（见 §5），
   布局围绕锚点做，锚点本身一格不移——这次改的是**坪外那一圈**（石板→草地），坪内没动；
2. **farm.lua 防误垦**：`farm.lua` 的 FARM 矩形（x14..33, y4..13）没有场景门禁，
   "可开垦"只看 GroundMap tile==2（夯土）。演武场全场**禁止夯土 tile**，
   否则玩家能在演武坪里锄地。生成器把"无 tile 2"作为硬性自检，而且现在测在
   **抖动之后**的载荷上（`JITTER_TARGETS=(1,2)` 只改写草/土，这张图一格 kind 2 都没有 ⇒
   没有可当供体的夯土，抖完长不出夯土；71 格被抖，直方图仍无 2）。

引擎硬约束与 docs/37 §1 相同：无 Y 排序（遮挡靠 solid 占位）、sprite 不能选 UV 区域
（一件道具一张图）、碰撞只看 tilemap solid。**列语义固定 6 个 kind**
（1=草地 2=夯土 3=石板路 4=院墙 5=青瓦 6=水），`terrain_ramp.json` 硬校验同名同序。

**演武坪为什么缩到 x2..18 × y2..11**（旧版 x1..19 × y1..12）：金标读数门判的是任意 20×12
窗口里**最坏**那一屏的可见外观种数（`scene_readings.MIN_SCREEN_TILES=24`）。19×12 的坪放得进
一整屏纯坪——那一片全是 mask=15 的内部格，三档 tint 最多撑 3 种。缩一格之后任何窗口都必须
跨出坪外，一定吃到石↔草犬牙、院墙带与（东半屏）池塘岸线。实测最坏窗口 27 种（见 §6）。

**南门与院墙打架这件事**（旧版靠把坪画到 y1 绕开、没写下来）：`building_kit.TILE_NATIVE_SOLID`
含 WALL，门洞压在墙行上就**永远实心**。现在 `GATE_ROW=(8,1,10,2)` 显式把门洞所在那一列刷成石板
⇒ 门洞 (9,1)(9,2) 地表是石、非实心、可站可达；立柱 (8,1)(8,2)(10,1)(10,2) 由 `manor_gate` 的
不透明像素实心；门楼压在 row0 墙上的那三格两侧都实心，不存在悬空碰撞。

## 2. 地表 tileset

`assets/art/tilesets/combat_arena/combat_arena_ground.png`（**384×288 = 12 列 ×9 行 ×32px**，
18,745 B）。M72-11 ④ 之前这张图**借用山庄的** `manor/manor_ground.png` 并按恒等寻址只取六族
满块档——两笔账本包才还：

| 旧形态（借图 + 恒等寻址） | 本包（自有图集 + autotile） | 还掉的账 |
|---|---|---|
| 草/石板/院墙用的是**山庄的 hex**，改山庄调色会顺手改演武场 | `terrain_ramp.json` 里 `combat_arena` 档自取色（`courtyard_turf` / `worn_flagstone` / `grey_brick` / `drill_loam` / `water`） | 调色解耦 |
| 恒等寻址拿不到 autotile ⇒ 坪与草的交界是**按格子对齐的直线**（docs/71 §1 点名的"像 demo"头号成因） | `tile_kinds=6;autotile=1`，交界按 4-bit 邻居掩码选过渡块，再叠 `jitter` 犬牙 | 交界犬牙 |
| 隐式依赖"新图集前 6 个条目仍等于旧的 6 种实心瓦" | 图集归自己，manor 布局再变也不漂 | 寻址耦合 |

寻址公式与四张金标图同一条：`1 + kinds*span + (kind-1)*16 + mask`，6 族 ×17 档 = 102 槽 ≤ 108；
`autotile=1` 由引擎 `resolve_atlas_index` 与 `tools/terrain_kit.py`、`tools/preview_scene.py`、
`plugins/webgl/web-runtime.js` 四处同解。**kind 5（青瓦）地面不用但图集照画满 6 族**——
布局不许按"用了哪几族"裁剪图集。

载荷读数（`scene_readings.py scenes/combat_arena.scene` 首三行）：kind 直方图
`{4: 160, 1: 450, 3: 290, 6: 20}`（= 40×23 = 920 格）、`solid` 239 格、
稀疏 `tints` **616 格**（id1 阴面 341 / id2 阳面 275）。

池塘是**按行手填的不规则岸线**（`POND_ROWS`，对齐山庄 `POND_ROWS` / 山道 `STREAM_ROWS`）：
岸线形状 23 格、外接框 7×4=28 ⇒ 填充率 0.821（旧版是完美方盒 28/28=1.000）；其中栈桥桥面 3 格
的地表刷成石板（见 §4 的 `ArenaPier`），所以**盘上 kind 6 = 20 格**、生成器打印的填充率 0.714。
两条读数是同一个池子的两个口径，不是两个池子。

base 在 y19 时树冠（顶 40 行切点）落在 y20 上半 + y21，而 y21/y22 是院墙（天然实心）、
y20 下半又被树干那 24px 覆盖 ⇒ 摘掉遮断件后**一格碰撞都不少**，
`jhyt_m72_building_footprint` 的反面对照 B 当场报"屋顶并进并集这条其实没在参与计算"。
挪到 y18 后树冠独占 y20 那 24px，拆层第一次真的在决定玩法；代价只是北墙前多出一条能走过去
的草地，而这条读数比"树与墙叠成一面"更好读。

**道具全部复用** `gen_manor_art.py` / `gen_village_art.py` 既有贴图：本场景零新美术，
唯一新增的像素是那张 12×9 地表图集。

## 4. 建筑、道具与碰撞占地

M72-11 ④ 起这张图**不再有手填 `solid_cells`**（它是七张里最后一张手填的）。占地只认
`building_kit` 一条规则，`SCENES["combat_arena"]` 点名声明例外：

- **建筑**（`role=building`）= 本体 ∪ 同名拆层件的不透明像素覆盖格 − 门洞；
- **道具**（`role=prop`）默认只在 `cell` 那一格实心；横着占两格的按表走 `box`：
  `ArenaRackA/B`（兵器架 64×46）、`ArenaRockA/B/C/D/N`（山石 64×40）、`ArenaStall`（茶水棚 64×40）；
- `ArenaPier`（木栈桥 96×32）走 **`walk`**：桥面三格的地表在 `build_tiles` 里刷成石板，
  于是"桥"是真能踩的。旧版写 `solid_cells=[]` 而底下三格仍是水 ⇒ 画面上是一座走不进去的桥；
  `walk` 说不挡人，地表就得真让人走过去；
- 门洞 `openings = {"ArenaGate": ((9,1),(9,2))}`，两侧都有反查（生成器自检 + `building_kit`）。

| 栋 | 贴图 | 尺寸 | cell | 视觉格 | solid 格 |
|---|---|---|---|---|---|
| `ArenaGate`（南门，复用山庄门楼） | `buildings/manor_gate.png` | 96×96 | (8,0) | 9 | 7（挖 2 个门洞） |
| `ArenaArmory`（军械棚，**本包新增**） | `buildings/manor_shed.png` | 160×128 | (2,14) | 20 | 20 |

`ArenaArmory` 为什么必须存在（这是本包最贵的一条发现）：这张图原来只有南门一件
`role=building`、而它不拆层 ⇒ 四棵树的遮断件（树冠）在碰撞上**一格都不参与**——道具走
"单格根碰撞"，树冠那几格本来就不实心。也就是说"摘掉拆层件应当缺碰撞"这条反面对照在本图
永远是空转。补一件拆层的建筑（本体 + `ArenaArmoryRoof`）之后反面对照 B 才真的红过、
才真的绿回来（读数见 §6）。追加位置在 `ENTITIES` **表尾** ⇒ 盘上 id 2..28 一个都不动
（挪 id 会让 Lua 侧 `entity.find` 与黄金表全部重排），它拿 29、玩家顺延到 30。

拆层件 5 件（id 5001..5005）：`ArenaTreeA/B/C/DCanopy` + `ArenaArmoryRoof`，全部由
`set_foreground_occluders.py` 按 `layer_kit.LAYER_SPLITS` 生成；竹丛不拆（`LAYER_SPLITS`
里没有 `manor_bamboo`，山道六丛竹同判）。

改动锚点必须三处同步：`tools/gen_arena_scene.py`、`scripts/data/maps.lua`、
`engine/crates/game/examples/jhyt_m18_combat.rs`。生成器解析 `data/maps.lua` 与

散布那边也有一条对应账：`set_scatter_decor.py` 的 `RESERVED_BY_SCENE` 现在给 `combat_arena`
登记 `gen_arena_scene` 为留白事实源——那六个锚点格与门洞/桥面是生成器说了算的留白，
装饰不许撒上去。

## 6. 生成与验收

出图与装配（顺序即依赖顺序，与山庄/村庄/山道同一条管线）：

```powershell
cd examples/game_jhyt
python tools/gen_terrain_tiles.py --scene combat_arena   # 12×9 图集（只从色阶表取色）+ 预览 + 自检
python tools/gen_arena_scene.py                          # 装配 combat_arena.scene（含契约自检）
python tools/set_terrain_autotile.py scenes/combat_arena.scene --apply   # 抖动 + 撒 tint（冻集为空，理由见生成器 FREEZE）
python tools/set_foreground_occluders.py scenes/combat_arena.scene --apply   # 5 件遮断件上前景层
python tools/set_cast_shadows.py scenes/combat_arena.scene --apply          # 9 件投影贴片
python tools/set_scatter_decor.py scenes/combat_arena.scene --apply        # 340 件装饰散布
```

盘上对拍（不改写字节的那一组，`verify.ps1` 的 Python 段对四张金标图各跑一轮）：

```powershell
python tools/gen_terrain_tiles.py --scene combat_arena --check   # 色阶 / alpha / 16 过渡块 / 四边收口 / 空槽
python tools/building_kit.py scenes/combat_arena.scene --check   # 每格 solid 都有可视依据：239 == 239，缺 0 悬空 0
python tools/set_foreground_occluders.py scenes/combat_arena.scene --check
python tools/set_cast_shadows.py scenes/combat_arena.scene --check
python tools/set_scatter_decor.py scenes/combat_arena.scene --check
python tools/scene_readings.py scenes/combat_arena.scene --gate  # 逐图量化读数
python tools/check_scene_refs.py                                # references/ 零泄漏
```

## 7. 已知限制与后续

1. **训练木人/灰狼仍是 `__white__` 色块占位**：敌人美术属 docs/40 #2（另一批次）；
2. **演武旗复用 village_banner（商铺招幌）**：专用旗幡贴图待有场景专属美术批次；
3. **无 Y 排序**：树/竹压墙是贴图技巧，人物走到树后仍会被树盖住（引擎层限制）；
4. **遮断上限没有本图读数**：`jhyt_m72_foreground_occlusion` 目前只读 `scenes/manor.scene`
   （`const SCENE: &str`），所以演武场那 5 件遮断件没有 `max_cover_ratio` 数——与 village /
   mountain_path 同档，是既有缺口不是本包新引入，登记在 `tasks/plan/M72-11` §combat_arena 的未测账；
5. **+18,745 B 一张新图集进包**：旧形态共用 manor 那张、零增量；发布门 `-Gpu2d` 的包体积读数
   要在下一次打包时复核（台账 docs/58 §1.3 同条已登记）；
6. **军械棚用的是山庄柴房贴图**（`manor_shed.png`）：演武场专属兵器房美术待外部委托；
