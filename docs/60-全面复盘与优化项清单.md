## 3. P0 — 性能关键问题

### 3.1 渲染器每帧每 Draw Call 分配 6 个 GPU Buffer

**位置**：`engine/crates/engine/src/host/renderer.rs`，`material_bind_group()` 函数

**问题**：每次调用 `material_bind_group()` 创建 3 个新 GPU buffer（`create_buffer_init`）：
- `material_buffer`
- `palette_buffer`（蒙皮网格）
- `instance_buffer`

该函数在 shadow pass 和 mesh pass 各调用一次，即 **每 Draw Call 每帧 6 次 GPU buffer 分配**。GPU buffer 分配涉及驱动级内存映射，开销远大于实际绘制。

**建议**：
1. 预分配 buffer 池，或用单大 buffer + bump allocator 子分配
2. Pass 开始前统一构建所有 bind group
3. 用 `write_buffer` 更新内容而非重新分配

**预期收益**：draw call 开销降低 10–100×。

---

### 3.2 每帧 O(n log n) 实体脚本同步

**位置**：`engine/crates/engine/src/core/script/runtime.rs:163-181, 222-234`

**问题**：`call_entity_scripts` 每帧调用 `sync_entity_scripts`，后者分配 `Vec<(EntityId, String)>`、遍历所有实体、排序——即使没有任何新实体生成。

**建议**：缓存排序结果，仅在 `EntityScript` 组件变化时失效重建。

---

### 3.3 纹理查找线性扫描

**位置**：`engine/crates/engine/src/host/renderer.rs`，纹理上传路径

**问题**：
```rust
self.textures.iter().position(|entry| entry.path == *path)
```
O(n) 线性扫描所有已加载纹理。

**建议**：维护 `HashMap<PathBuf, usize>` 做 O(1) 查找。

## 4. P1 — 架构与正确性

### 4.1 ScriptState 上帝对象（~45 字段）

**位置**：`engine/crates/engine/src/core/script/mod.rs:88-230`

**问题**：所有游戏状态集中在一个巨型 struct 中，涵盖 12+ 个领域：

| 领域 | 字段举例 |
|---|---|
| 输入 | `input_diagnostics`, `action_map` |
| 物理 2D/3D | `physics_world`, `physics3d_world`, `rigid_bodies`… |
| UI | `ui_texts`, `ui_bars`, `ui_panels`, `ui_images`, `ui_grids`, `ui_drag`, `ui_focus`, `ui_scroll`… |
| 音频 | `audio_handles`, `audio_params` |
| 存档 | `save_data` |
| 背包/商店 | `inventories`, `shops` |
| 相机 | `camera_2d`, `camera_3d` |
| 粒子 | `particles` |
| 动画 | `animations` |
| 标签 | `tags`, `names`, `health` |
| 时钟 | `game_clock` |
| 场景 | `scene_text_hidden`, `scene_parent_issues`… |

**连锁问题**：
- 场景切换需手动清理 17+ 字段（`transition.rs:37-63`），新增字段忘清理就泄漏状态
- 任何子系统修改导致整个 struct 的所有消费者重编译
- `Rc<RefCell<ScriptState>>` 是全局单点竞争

**建议**：按领域拆分子结构体（`UiState`、`PhysicsState`、`InputState`、`SaveState`、`InventoryState`），各自有 `Default` + `clear()` 方法，场景切换变成 `state.ui.clear()`。

---

### 4.2 热重载非原子操作

**位置**：`engine/crates/engine/src/core/script/runtime.rs:80-91`

**问题**：热重载先执行旧 VM 的 `on_destroy`，再尝试新 VM 的 `on_create`。如果 `on_create` 失败，旧状态已被销毁但新状态未建立——脚本处于半撕裂状态。同样的问题存在于 `reload()`（100-110 行）。

**建议**：先在候选 VM 上运行 `on_create`，成功后再调用旧 VM 的 `on_destroy`，最后交换。

---

### 4.3 RefCell 运行时 Panic 风险

**位置**：`engine/crates/engine/src/core/script/mod.rs` 及所有 `api/*.rs`

**问题**：整个 Lua API 层的每个回调都做 `s.borrow_mut()`。如果 mlua 通过 `__index` 元方法重入 Rust，第二次 borrow 会 panic。当前代码依赖"mlua 不会在 callback 中重入"的隐式假设。

**具体风险点**：
- `mod.rs:503-507`：两次连续 `borrow_mut()` 应合并为一个 borrow scope
- 所有 API 闭包中的 `Rc::clone` + `borrow_mut` 模式在重入场景下不安全

**建议**：
1. 合并相邻的 borrow scope
2. 考虑用 `RefCell::try_borrow` + 友好错误替代 panic
3. 长期可评估是否需要 `UnsafeCell` + 手动不变量

---

### 4.4 `parse_mouse_button` 静默吞掉未知按钮

**位置**：`engine/crates/engine/src/core/script/mod.rs:1167-1174`

**问题**：未知鼠标按钮静默映射为 `MouseButton::Other(0)`。同一文件中的 `parse_key_strict`（1144-1160）已修复为报错模式（注释 1142 行记录了旧 bug），但鼠标按钮未同步更新。

**建议**：与 `parse_key_strict` 对齐，对未知鼠标按钮返回错误。

### 5.3 Lua API 绑定样板代码

**位置**：所有 `engine/crates/engine/src/core/script/api/*.rs`

**问题**：`let s = Rc::clone(&state)` 出现 ~150 次。每个函数遵循完全相同的模式：

```rust
let s = Rc::clone(&state);
some_table.set(
    "function_name",
    lua.create_function(move |_, args| {
        let mut state = s.borrow_mut();
        // ... 业务逻辑 ...
    })?,
)?;
```

**建议**：声明宏 `lua_fn!` 消除样板，预期减少 20–25% 代码量：

```rust
macro_rules! lua_fn {
    ($lua:expr, $table:expr, $name:expr, $state:expr, |$arg:ident| $body:expr) => {
        let s = Rc::clone(&$state);
        $table.set($name, $lua.create_function(move |lua, args| {
            let mut $arg = s.borrow_mut();
            $body
        })?)?;
    };
}
```

## 6. P3 — 内存与分配优化

### 6.1 BTreeMap 用于热路径查找

**位置**：`engine/crates/engine/src/core/script/mod.rs` 多处

**问题**：`ScriptState` 中几乎所有映射都用 `BTreeMap`（`tags`、`health`、`names`、`inventories` 等约 15 处），O(log n) 且缓存不友好。对于每帧查找的热路径，`HashMap` 或 `FnvHashMap` 的 O(1) 更合适。

`BTreeMap` 的有序性仅在确定性序列化时需要，运行时查找是性能税。

---

### 6.2 Host 端访问器每帧 clone 集合

**位置**：`engine/crates/engine/src/core/script/mod.rs:533, 623, 629, 408`

**问题**：
- `self.state.borrow().scene_text_hidden.clone()` — clone 整个 `BTreeSet`
- `self.state.borrow().scene_parent_issues.clone()` — clone `Vec<String>`
- `self.state.borrow().scene_renderable_conflicts.clone()`
- `self.state.borrow().input_diagnostics.clone()`

这些每帧被 host 调用。已有 `with_world`、`with_ui`、`with_particles` 等闭包模式可复用。

**建议**：统一改为 `with_*` 闭包模式，避免 clone。

---

### 6.3 物理引擎 query_pipeline 每次 add/remove 都重建

**位置**：`engine/crates/engine/src/core/physics.rs:482, 501`

**问题**：每次 `add_body()` / `remove_body()` 后立即调用 `query_pipeline.update()`。场景加载时批量添加/删除物体会触发 O(n) 的冗余全量重建。

**建议**：添加 `dirty` 标志，延迟到下一次 `step()` 时统一更新：

```rust
if self.query_dirty {
    self.query_pipeline.update(&self.rigid_body_set, &self.collider_set);
    self.query_dirty = false;
}
```

---

### 6.4 场景序列化中的字符串分配

**位置**：`engine/crates/engine/src/core/scene.rs`

**问题**：

| 函数 | 行号 | 问题 |
|---|---|---|
| `escape()` | 310-314 | 连续 3 次 `.replace()` 产生 3 个临时 String |
| `to_text()` | 133-178 | 多次 `format!` + `push_str` 创建中间 String |
| `from_text()` | 187 | 每行 `.split('\t').collect()` 分配 Vec |
| `is_entity_hidden_with_ancestors` | 69 | 每个祖先 `format!` 分配 String |

**建议**：
- `escape()` → 单次遍历构建输出
- `to_text()` → `write!(&mut output, ...)` 直接写入
- `from_text()` → iterator indexing 替代 `collect::<Vec>`
- `is_entity_hidden_with_ancestors` → 复用预分配 buffer

### 6.5 `despawn()` 遍历所有组件类型

**位置**：`engine/crates/engine/src/core/world.rs:145-153`

**问题**：反生成实体时遍历所有已注册组件类型的 storage（`HashMap<TypeId, Box<dyn ComponentStorage>>`），即使大多数不含该实体。

**建议**：维护 per-entity 的组件 TypeId 集合，despawn 只触及相关 storage。

## 7. 项目治理

### 7.1 大文件直接入库

**工作区现状**（2026-10 实测，`git ls-files "*.ttf"` + `git cat-file -s`）：

| 大小 | 文件 |
|---|---|
| 17.0 MB | `engine/crates/editor/fonts/NotoSansSC-VF.ttf` |
| 17.0 MB | `examples/game_jhyt/assets/fonts/NotoSansSC-VF.ttf`（**与上一行同一个 blob** `cc79aef4`） |
| 74 KB | `examples/game_api/assets/fonts/NotoSansSC-VF.ttf`（`subset_project_font` 按工程用字子集化） |
| 4.6 MB | `examples/game_api/assets/models/kaykit-warrior.glb`（第三方 CC0，不可再生） |

三条结论，都是量出来的、不是推断的：

1. **两份 NotoSansSC 不是冗余副本，而是同一 blob 的两个路径**。Git 按内容寻址，对象库里只存一份，
   所以"合并字体"在仓库侧的收益是 **0**，收益只有工作区的 17 MB。
2. **两份各自有独立的加载代码路径，不能合成一份**：editor 那份由 `editor/src/util.rs` 按
   "exe 同目录 `fonts/`"查找，同时是 ≥8 处文字测试 fixture 的字源；jhyt 那份被
   `game_jhyt/project.toml` 加载、`tools/cjk_text.py` 要它的完整 advance 表、
   `jhyt_m31_pc_release.rs` 断言发布包内必须存在 `pack/assets/fonts/NotoSansSC-VF.ttf`。
   把它改成派生产物等于让全新检出必须先跑再生成步，否则这批 CJK 门全红——**本项关闭**。
3. `SourceHanSerifSC-Regular.ttf`（57 MB）、`SourceHanSerifSC-Regular.otf`、
   `LXGWWenKaiGB-Regular.ttf`（7.3 MB）已在 `1cd624b`（"内嵌字体出库"）从工作区移除，
   **但历史 blob 仍在 `.git` 里**——这是 `.git` 203 MB 的主要构成。工作区已经不持有它们，
   要真正收回只能重写历史（`git filter-repo`），代价是所有远端与同事的克隆失效，
   因此单列为"只在明确决策后执行"的一项，不做无痕处理。

**建议**：
1. ~~检查两份 `NotoSansSC-VF.ttf` 是否为同一文件的冗余副本~~ → 已确认同一 blob，且两侧各有加载路径，不合并（见上）
2. Git LFS 只对**将来**新增的大资产有意义；已入库的历史 blob 用 LFS 迁移同样要重写历史，与第 3 条是同一个决策

### 10.1 那条完全没动的债（§4.3 已在复核当天收口）

**§4.3 重入借用：从「机制在、没转完」收口到「全部转完」** —— ✅ **复核当天完成**

- 原状：`lua_borrow(_mut)` 这套"把 RefCell panic 降级为 Lua 可捕获错误"的机制早就写好了，但只转了一部分
  （调用点 173 处已转 / **104** 处未转，真实数字见下面的账目更正）。而 `mod.rs` 的原注释写着
  "**统一**用 `try_borrow(_mut)`"——**注释比代码承诺得多**。本次先把注释改成实测口径，再把差的补上。
- 为什么值得做：wasm32 上 `panic = abort`，重入触发的是**硬 abort**（浏览器/微信里表现为裸 `unreachable`，
  连行号都拿不到），而这条路径是**已知可达**的——机制本身就是因为 mlua 会经 `__index` 等元方法重入 Rust 才建的。
- 做法：`s.borrow_mut()` → `s.lua_borrow_mut()?`、`s.borrow()` → `s.lua_borrow()?`，**两个方向都转**
  （只转外层等于没转：外层转了、内层没转，内层照样 panic）。18 个 `api/*.rs` **本来就都
  `use crate::script::LuaStateBorrow;`**，所以这是纯机械改动。编译器把两类特例指了出来：
  ① 11 处 `?` 打断 deref coercion（`&s.lua_borrow()?` → `&*s.lua_borrow()?`）；
  ② 5 处**我自己的子串替换误伤**——`subs.borrow_mut()` 里含 `s.borrow_mut()`，被改成了 `subs.lua_borrow_mut()?`，已撤回。
- **账目更正**：原记的"109 处"里有 5 处其实是 `subs.borrow*()`（**另一个 RefCell**，与 state 重入无关），
  是被 `s.` 的子串匹配算进来的。真实要转的是 **104 处**；转换后全仓 `lua_borrow*` 调用点 **277 = 173 + 104** ✓ 对得上。
- **验收（两条方向相反的用例）**：新增 `script/tests/reentrancy.rs`——
  ① 持住 `runtime.state.borrow_mut()` 再调 Lua API，必须收到带 `already borrowed` 的 **Lua error**（而不是 panic）；
  ② 非重入路径必须照常工作（少了这条，"把所有 API 改成永远报错"也能让 ① 变绿）。
  **反面对照**：把 `health.get` 一处改回 `s.borrow()` → ① 立刻在 `api/entity.rs:110` **panic**（正是改造前的行为），② 仍绿。
- **残留的 70 处 panic 版 state 借用为什么不改**：它们都在 `impl LuaRuntime` 的 `&self` / `&mut self` 方法里
  （`mod.rs` 44 / `step.rs` 10 / `runtime.rs` 9 / `transition.rs` 3 / `hot_reload.rs` 3 / `scene_spawn.rs` 2），
  是**宿主侧的外层借用**——也就是重入的**来源**，不是受害者。它们**从 Lua 回调里不可达**，这是结构性的：
  API 闭包捕获的只有 `Rc<RefCell<ScriptState>>`，拿不到 `&LuaRuntime`（`api/*.rs` 里 `runtime.` 出现 **0** 次；
  那 4 处 `LuaRuntime::` 全是**关联函数**调用，收的是已借出的 `&mut ScriptState`，例如
  `LuaRuntime::instantiate_prefab_state(&mut state, &prefab)`）。`require.rs` / `values.rs` / `guard.rs` / `error.rs` 一个借用都不持有（实测）。
- 读数：`rustlua-scripting` **109 通过 0 失败**（107 → 109）；`engine --lib` **159 通过**；fmt（仅本次改过的文件）与
  clippy `--all-targets -D warnings` 干净；**五个 prefab 门 + `game --check` 全通过**（`jhyt_m59/m61/m62/m63/m65_*_ok`、`game_check_ok`）。
- 诚实边界：**没有做逐调用点的可达性证明**，只有上面那条结构论证；也**没跑 wasm 目标**（本机不做那种重构建），
  所以"panic → Lua error"是在 native 测试里验的，wasm 上的收益按"panic 即 abort"推。

**§5.3 是唯一整体未动的（见下）**

**§5.3 `Rc::clone(&state)` 样板：已评估，决定不做** —— ❌ **不做（附实测与理由，可推翻）**

- 实测（2026-10-06）：`api/` 合计 **5,638 行**，其中 `let s = Rc::clone(&state);` 独占 **260 行 = 4.6%**；

- 代价一（最要紧）：**宏体不再被 rustfmt 覆盖**——本仓没有 `rustfmt.toml`，默认行为就是不格式化宏调用体，
  于是几百行绑定会**掉出 `cargo fmt --check` 这道门的覆盖范围**。在一个以"门不说谎"为身份的仓库里，
  主动把代码移出格式门是净损失。
- 代价二：逐处的借用与绑定形态**不再可 grep**。这不是空谈——**§4.3 那 104 处审计正是靠"每处借用都写在

- **可推翻条件**：若将来这些绑定不再需要 `'static`（例如换掉 mlua 的回调生命周期约束），或本仓引入
  `rustfmt.toml` 并启用 `format_macro_bodies`，这条结论要重算。届时用同一把尺（行数占比 + 是否掉出格式门）。

### 10.3 本次复核**新发现**的（原清单里没有，两条都在帧路径上）

原清单的 §6.1/§6.2 关心的是"BTreeMap 该不该换"和"访问器该不该 clone"，本次顺着热路径读下去，
发现了两个**当时的清单没列、也没被后续批次修掉**的逐帧缺陷。它们比清单里剩下的多数条目更值得先动，
因为代价落在每一帧上且随实体数增长：

1. **`names` 的反向查找是线性扫 → 每帧 O(n²)** —— ✅ **复核当天已修**
   - 原状：`mod.rs` 的 `entity_name(id)` 是 `by_name.iter().find(...)`（O(n)），而
     `host/runtime_scene/mesh_ui.rs:68` 在**遍历实体的循环里**调它；叠加
     `is_entity_scene_text_hidden` 对每个文字线性扫同一张表 → 实体数 n 时每帧 O(n²)。
   - 修法：把「名字 → 实体」与「实体 → 名字们」合成一个类型 `EntityNames`（`mod.rs`）。正向 `by_name`
     仍是唯一真源、也是有序性的来源（`entity_names_by_slot` 这类**确定性输出**靠它），反向 `by_entity`
     是**惰性派生 + 脏标记**——与 `rustlua-ecs` 的 `TypedStorage::ensure_order` 同一惯用法。
     **关键不是"再加一张表"**：两张表各自维护必然漂移（而漂移的后果是名字张冠李戴，比慢一点严重得多），
     所以改名的入口只有该类型的方法，脏标记在方法里置位。`entity_name` 与 `is_entity_scene_text_hidden`
     都改走反查（后者从"扫全表"变成"只扫该实体的名字"）；两个 getter 仍走 `&self` + 内部可变性，
     **没有给 Lua 重入多开一个可变借用的口子**。
   - 语义**逐字保留**：`entity_name` 在"同一实体挂多个名字"时取 `by_name` 键序里的第一个——与旧
     `iter().find` 同结果；`insert`/`remove_entity` 的既有语义（同名改指向、旧名字仍指向同一实体）一字未动。
   - 防回归：`script/tests/entity.rs` 新增 `entity_name_reverse_index_is_stale_free_and_rebuilds_only_on_change`，
     钉**方向相反**的两条契约——① 改动必须让缓存失效（否则反查返回过期名字）；② 稳态 64 次反查

     改成每次反查都重建 → 断言 ② 红（`left: 2` vs `right: 1`）。探针已回退，`grep 'RC 探针'` = 0。
