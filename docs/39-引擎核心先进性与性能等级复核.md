# RustLua 引擎核心设计先进性与性能等级复核

## 结论

当前引擎属于**工程化较好的原型/小型独立游戏级引擎**，综合建议评级为 **C+ 到 B-**：质量工程和基础架构达到 B/B+，但 ECS 存储、字符串组件热路径、2D/3D 空间统一、并行调度和大规模渲染仍明显低于成熟通用引擎。

| 维度 | 评级 | 结论 |
|---|---:|---|
| Core/Host 分层 | B | 边界清晰，core 有防止依赖 host 的回归测试 |
| 调度与确定性 | B | 有阶段、依赖拓扑缓存、异常诊断和系统计时；目前单线程 |
| ECS 吞吐潜力 | C | HashMap + 有序实体 Vec，类型擦除和查询复制不适合高密度实体 |
| 场景/数据管线 | C+ | 可读性和诊断好，但运行时依赖字符串组件解析 |
| 2D/3D 空间架构 | C+ | 两套 Transform，缺少通用 GlobalTransform 与父子传播 |
| 3D 渲染基础 | C+ / B- | 有深度、阴影、缓存、实例化、CPU 剔除；缺少大规模可见性和 LOD |
| 质量与发布工程 | B+ | 有确定性、长跑、读档、发布隔离和质量门 |
| 当前性能定位 | 小型项目级 | 适合当前 game_jhyt 与中小场景，无大型场景证据 |

## 复核依据

- `engine/crates/engine/src/core/world.rs`：每种组件是 HashMap 加有序实体 Vec，TypeId 类型擦除；entities_with2 会复制实体列表后做 membership 检查。
- `engine/crates/engine/src/core/scheduler.rs`：Input → Script → Physics → Simulation → Animation → Transform → Render；支持依赖校验、拓扑缓存、异常诊断和系统计时，但回调是单线程 FnMut。
- `engine/crates/engine/src/core/scene.rs`：版本 2，组件为 BTreeMap<String,String>，版本严格校验。
- `transform.rs`/`transform3d.rs`：2D 为 Vec2+角度，3D 为 Vec3+Quat；尚无统一 GlobalTransform 和父子传播。
- `math2d.rs`/`camera3d.rs`：2D 的像素 zoom/bounds 与 3D 的透视/look-at 语义不同。
- `host/renderer.rs`/`frame.rs`：已有 mesh pipeline、深度、阴影、缓存、实例化、CPU bounds/culling 和 skinned palette；render pass 仍是 3D depth 后画 2D 无深度 overlay。
- `docs/34-质量门与发布清单.md`、`docs/36-游戏级回归与性能基线.md`：已有 30/60/120 FPS 一致性、31 天长跑、100 次磁盘往返、20 次真实 runtime load、3000 次快照恢复等证据。

## 已经比较先进的部分

Core/Host 分层对 headless、编辑器和平台扩展是正确方向。调度器支持命名依赖、拓扑排序、循环检测、阶段约束、panic 捕获和耗时报告。质量工程包括规则回归、固定步一致性、长跑、读档、发布隔离及 WebGL 限制标注。3D 基础包含深度、阴影、mesh/材质/纹理缓存、静态实例化、bounds 和 skinned palette。

## 主要短板与性能风险

### ECS

HashMap 节点分散，TypeId/trait object/downcast 增加访问成本，查询可能复制 Vec，有序插入/删除可能 O(n)，despawn 遍历全部 storage。小规模简单稳定，规模上升会受 cache miss、哈希和分配影响。建议先 benchmark，再只迁移 Transform、Sprite、Velocity、PhysicsProxy 到 dense/sparse-set 或 archetype/chunk。

### 字符串热路径

BTreeMap<String,String> 适合磁盘和编辑器，不适合作为每帧渲染/查询输入。应加载时编译成 typed scene/render snapshot，运行帧只使用 typed ECS 和稳定 ID。

### 世界变换

场景有 parent/children，但提取器按单实体 TRS 构造 model matrix。缺少统一 Transform、GlobalTransform、dirty/version 和父优先传播，会导致编辑器、渲染、物理各自解释空间。

### 调度与渲染

当前单线程无法利用多核；3D 有 CPU culling/实例化但没有层级 BVH/空间索引、LOD/HLOD、遮挡剔除、GPU indirect 或多线程 render extraction。2D 无深度 overlay，Sprite 无法自然遮挡 Mesh。

### 校验

Transform3D 字符串入口检查单位四元数，但直接构造进入 model matrix 的路径需要统一 finite/单位性校验，非法状态不能传播到 GPU。

## 性能证据边界

已有固定步基线约 `0.15–0.41 ms/step`，近期约 `0.4098 ms/step`，并通过长跑及大量读档/快照。这说明当前玩法逻辑/Lua 在小规模场景下性能很好，但不能证明 GPU 帧时间、复杂 3D、编辑器大场景、WebGL 或十万/百万实体能力。

缺少 CPU/GPU frame breakdown、draw call/instance/三角形、内存峰值、分配次数、ECS/Transform 微基准、2D/3D 阶梯场景和编辑器大场景数据。

## 相对成熟引擎的位置

相比手写小型框架明显更完整；相比 Bevy/Flecs，在 archetype/sparse-set、并行调度、零拷贝查询和生态上明显落后；相比 Godot/Unity，资产管线、编辑器、渲染变体、profiling 和平台规模明显较小；与 Unreal 不在同一性能/功能等级。相比轻量 Rust 专用引擎，Rust 安全性、可控性和领域聚焦有竞争力。

## 优先改进路线

### P0：真实性能画像

新增 benchmark，区分规则固定步和渲染帧，记录 p50/p95/p99、分配次数、CPU/GPU frame、draw calls、实例数和资源字节：ECS 操作；1/10/100 层级 Transform；1k/10k/50k/100k Sprite；100/1k/10k Mesh（实例化、阴影、骨骼、透明）；Lua；场景加载、typed compile、首帧和内存峰值。

### P1：运行时 typed 化并统一空间

字符串只留在磁盘/编辑器边界；加载时编译 typed scene。统一 Transform/Camera/RenderView，增加 GlobalTransform，修复矩阵入口校验。

### P2：局部优化 ECS 热点

Transform/Sprite/Velocity 使用 dense/sparse-set；查询返回迭代器而非复制 Vec；引入 generation/version dirty 标记；只在需要确定性的边界排序。

### P3：渲染提取和可见性

RuntimeScene 生成 typed render snapshot；增加层级 bounds、空间索引、增量剔除；保留独立 mesh/sprite shader，随后评估世界 Sprite、透明排序、LOD 和 indirect draw。

### P4：有证据后并行化

声明系统读写集，建立并行 DAG；Transform、动画采样、剔除和资源准备并行；Lua 保持确定性边界；异步 IO/解码/shader 准备不阻塞主线程。

## 最终建议

不要全面重写。先建立 profiling 和规模基线，再限制字符串数据在加载边界，统一 Transform/Camera/RenderView，之后只对 profile 证明的 ECS 热点 dense 化，最后决定空间索引、并行调度、LOD 或 GPU indirect。最值得保留的是 core/host 分层、确定性调度、严格诊断和质量门；最需要改变的是 ECS 存储、字符串热路径、世界变换缺失以及 2D/3D 渲染隔离。
