# RustLua 引擎核心设计先进性与性能等级复核

> 文档版本：1.1 · 复核日期：2026-10-29（初版为拆分前的 2026-09 复核）
> 1.1 版按当前代码重判：ECS 已换 `DenseStorage`、Transform/Camera 已统一并有 `GlobalTransform` 传播、
> 3D 已有 PBR/IBL/HDR、并行调度已有实测结论（判"不做"）。旧表的 C 档多数是按"HashMap + 两套 Transform + 无 PBR"打的，
> 继续沿用会把已完成的改造重复排期。

## 结论

当前引擎属于**工程化良好的小型独立游戏级引擎**，综合建议评级为 **B-/B**：质量工程与基础架构达到 B/B+，ECS 存储与空间架构已追上主流轻量 ECS 的及格线；仍明显落后的是**大规模渲染**（跨帧 VSM/ESM、完整 SSAO/SSR、可见性剔除）与**并行调度**（已有实测结论：当前不划算）。

| 维度 | 评级 | 结论 |
|---|---:|---|
| Core/Host 分层 | B | 边界清晰，core 有防止依赖 host 的回归测试；36 crate 无真实依赖环 |

| 场景/数据管线 | B- | 磁盘/编辑器仍是字符串组件（v2，`BTreeMap<String,String>`），加载时编译成 typed 组件；30 个运行时组件有 schema 驱动序列化 |

| 当前性能定位 | 小型项目级 | 适合当前 game_jhyt 与中小场景，无大型场景证据 |

## 复核依据

- `engine/crates/rustlua-ecs/src/world.rs`：组件存储已整体换成 `DenseStorage`（文件头即 WP3 裁定），类型擦除仍在（`TypeId` 表 + downcast）；`entities_with` / `entities_with2` 仍返回新建 `Vec`，稳态遍历零分配，但查询本身有复制。
- `engine/crates/rustlua-ecs/src/scheduler.rs`：`ScheduleStage` 10 个类型化阶段（含 `Sync`/`Writeback`/`Spatial`，旧的"同步/回写/世界变换传播只存在于注释里"已收敛成类型）；支持依赖校验、拓扑缓存、异常诊断和系统计时，回调是单线程 `FnMut`。
- `engine/crates/rustlua-ecs/src/hierarchy.rs` + `spatial_transform.rs`：`propagate_spatial` 沿父链组合局部变换写进 `GlobalTransform`，挂在 `Spatial` 阶段；父子传播不再需要"显式启用"。
- `engine/crates/rustlua-ecs/src/transform.rs`：`Transform3D` 的校验路径拒绝非有限位置/缩放与非单位四元数，字符串入口先过 finite 再构造。
- `engine/crates/rustlua-scene/src/typed_scene.rs`：场景侧**唯一**变换组件名 `Transform`，载荷 `position/rotation/scale`（`LocalTransform::from_unified_component_str` 解析后装进 `Transform3D` 变体）；ECS 内部仍保留 2D `Transform`（Vec2 + 角度）与 3D `Transform3D`（Vec3 + Quat）两种载荷，统一发生在加载边界。
- `engine/crates/rustlua-scene/src/scene.rs` / `typed_scene.rs`：磁盘格式仍是版本 2 的 `BTreeMap<String,String>`（严格版本校验），`TypedScene::compile_v2` 在加载边界编译成 typed 组件；表现层 12 个组件经 `component-codec` 注册表编解码，未注册即硬错误。
- `engine/crates/rustlua-gpu/src/renderer/`：`RenderPass` 11 条规范通道（Clear / WorldSpriteOpaque / Shadow / DepthOpaque / WorldSprite / Particle / Tonemap / Legacy2DOverlay / ScreenUI / VectorText / PostProcess），PBR/IBL/HDR/变体/热重载各有独立模块与 golden；阴影是方向光四级 CSM（2048² × 4 层，级联边界 smoothstep 混合）加全部 8 盏点光的六面阴影（1024² × 48 深度数组）。
- `engine/crates/rustlua-render/src/render_plan.rs`：渲染计划把"这一帧有哪些通道"变成显式列表；空间索引（`spatial_index`）与 `LodGroup` 已接入运行时提取。
- `docs/34-质量门与发布清单.md`、`docs/36-游戏级回归与性能基线.md`：已有 30/60/120 FPS 一致性、31 天长跑、100 次磁盘往返、20 次真实 runtime load、3000 次快照恢复等证据。

## 已经比较先进的部分

Core/Host 分层对 headless、编辑器和平台扩展是正确方向。调度器支持命名依赖、拓扑排序、循环检测、阶段约束、panic 捕获和耗时报告，并把帧序术语类型化。质量工程包括规则回归、固定步一致性、长跑、读档、发布隔离及 WebGL 限制标注。3D 基础已从"深度 + 阴影"扩到 PBR/IBL/HDR、mesh/材质/纹理缓存、静态实例化、bounds、skinned palette、LOD 与 compute 粒子。

## 主要短板与性能风险

### ECS

`DenseStorage` 解决了"每种组件一次 HashMap 查找 + 删除 O(n) memmove"的问题，但**查询仍然返回 `Vec`**（`entities_with*` 每次新建并复制实体列表），没有 archetype/chunk 的连续遍历，也没有并行。大规模实体下仍会受分配与 cache miss 影响。建议先 benchmark，再决定是否改成迭代器/视图并只对 Transform、Sprite、Velocity 这些热点做 archetype 化。

### 字符串热路径

`BTreeMap<String,String>` 仍留在磁盘与编辑器边界，这是对的；运行帧已经吃 typed 组件（`RuntimeScene` 持 typed 实体，`scene_extract` 产出渲染快照），但 `Opaque` 载荷与少数组件（如 `Environment`）仍会回读原文。残项是"把回读点清空"，不是重做管线。

### 世界变换

统一 `Transform` + `GlobalTransform` 传播已落地（`Spatial` 阶段，父优先组合）。仍需注意的是：2D 的像素语义（zoom/bounds）与 3D 透视语义没有合并成同一个 RenderView，编辑器/渲染/物理对空间的解释靠约定而不是同一个类型。

### 调度与渲染

单线程调度已有实测结论：可并行 stage 的最大占帧比 11.96%，跨系统并行收益上限 ≤1.18%（`metrics/baselines/m74-frame-profile.json`），因此**不并行是决定，不是欠债**；瓶颈在单系统内部与提取阶段。渲染侧已有 CPU 视口预筛、LOD、实例化，但**没有层级 BVH、遮挡剔除、GPU indirect、跨帧 VSM；已有 2048² × 4 全分辨率 ESM、CSM 平移纹素 snap/2 m 缩放量化/PCSS-lite；后处理只有 Tonemap+泛光/AA+SSAO-lite+SSR-lite，没有完整 SSAO/SSR 栈**；2D overlay 仍无深度，Sprite 不能自然遮挡 Mesh。

### 校验

`Transform` 入口已校验 finite 与单位四元数；直接构造进入 model matrix 的路径仍需保持同一套校验，非法状态不能传播到 GPU。

## 性能证据边界

已有固定步基线约 `0.15–0.41 ms/step`，近期约 `0.4098 ms/step`，并通过长跑及大量读档/快照。2026-10-21 又补了逐系统 `FrameProfile`（p50/p95/p99 + 每 stage 合计 + 整帧墙钟）与 `game --frame-profile`。这些能证明玩法逻辑/Lua 在小规模场景下性能很好，但不能证明 GPU 帧时间、复杂 3D、编辑器大场景、WebGL 或十万/百万实体能力。

缺少 draw call/instance/三角形计数、内存峰值、分配次数、ECS 查询/调度微基准、2D/3D 阶梯场景和编辑器大场景数据。Lua 脚本与 `transform` 表的调用成本已补微基准（见 [78](78-Lua脚本性能分析与优化.md)），不再属于空白。

## 相对成熟引擎的位置

相比手写小型框架明显更完整；相比 Bevy/Flecs，在 archetype/sparse-set、并行调度、零拷贝查询和生态上明显落后；相比 Godot/Unity，资产管线、编辑器、渲染变体、profiling 和平台规模明显较小；与 Unreal 不在同一性能/功能等级。相比轻量 Rust 专用引擎，Rust 安全性、可控性和领域聚焦有竞争力。

## 优先改进路线

### P0：真实性能画像（部分交付）

已交付：逐系统 `FrameProfile`（p50/p95/p99、每 stage 合计、整帧墙钟）与 `game --frame-profile`，读数落 `metrics/baselines/m74-frame-profile.json`（`jhyt_title` 2.36% / `jhyt_manor` 4.47% / `sprite_10000` 11.96% / `sprite_50000` 11.56%）。
仍缺：draw call/instance/三角形计数、内存峰值、分配次数、ECS 查询/调度微基准、2D/3D 阶梯场景与编辑器大场景数据。Lua 侧已补纯 Lua、Lua→Rust 与返回 table 的微基准（见 [78](78-Lua脚本性能分析与优化.md)）。

### P1：运行时 typed 化并统一空间（已交付）

字符串留在磁盘/编辑器边界；加载时经 `TypedScene::compile_v2` 编译成 typed 组件。场景侧 `Transform` 统一成 `position/rotation/scale` 载荷（合法入口校验 finite 与单位四元数），`Camera` 用 `projection` 判别字段统一，`GlobalTransform` 由 `Spatial` 阶段父链传播。

### P2：局部优化 ECS 热点（存储已交付）

组件存储已整体换 `DenseStorage`（`world.rs` 文件头即裁定），稳态遍历零分配、删除不再是排序 `Vec` 的 O(n) memmove。
未做：`entities_with*` 仍返回 `Vec`（未改迭代器/视图）、未上 archetype、未引入 generation/version dirty 标记。

### P3：渲染提取和可见性（部分交付）

已交付：RuntimeScene 产出 typed 渲染快照（`scene_extract`）、渲染级空间索引（uniform grid 视口预筛，静态收集 O(N) → O(视口内)）、3D `LodGroup` 距离切模、独立 mesh/sprite shader、11 条规范渲染通道。
未做：层级 BVH、遮挡剔除、透明排序策略升级、indirect draw。

> **P3 证据**（2026-09，`wp0_lod_golden`）：`examples/wp0_lod_golden.rs` 注入 `LodGroup`
> （`mesh=<基础>;lod=<距离>|<低模>`）后，近/远相机各渲染一帧：近相机用基础网格（warrior）、
> 远相机切低模（triangle），两帧像素差异非零（pixels_differ=9907）且远帧有内容（content=72）——
> 「距离驱动切换真的发生在像素层」，报告落 `baselines/wp0_lod_golden.json`。

### P4：有证据后并行化（已判定不做）

2026-10-21 的 P0 度量走完闸门：可并行 stage 的最大占帧比 11.96%，跨系统并行收益上限 ≤1.18%；`jhyt_manor` 的 76% 全在 `Script`（Lua 单线程），50k sprite 的 10.9 ms 里 9.1 ms 在提取阶段。结论是**并行调度换不到可测收益**，要动的是单系统内部切片与提取；`World` 的 `!Send` 结构（`RefCell`/`Cell` 内嵌）因此不必改造。

## 最终建议

不要全面重写。P1（typed 化 + 空间统一）与 P2 的存储改造已经完成，P4 已用实测关闭；剩余的性价比排序是：**先把 P0 缺的那半张画像补齐**（draw call/内存/微基准/大场景），再决定是否改写查询接口与上 archetype，然后才是 P3 剩下的 BVH/遮挡剔除与 P0 级别的跨帧 VSM、后处理栈。最值得保留的是 core/host 分层、确定性调度、严格诊断和质量门。
