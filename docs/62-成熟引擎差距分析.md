### 1.1 代码规模与分层实测

**每 crate `src/` 行数**（2026-10-02 实测，两次采样间有并发改动，取近似值）：

| 层 | crate | src 行数 |
|---|---|---|
| 宿主 | editor | 59.7K |
| 宿主 | engine（host） | 20.8K |
| 宿主 | assetc / game / game_web / wasm-lua-spike | 1.6K / 1.5K / 1.1K / 0.2K |
| 聚合 | rustlua-scripting | 13.6K |
| 核心 | rustlua-ecs | 11.2K |
| 渲染 | rustlua-render | 9.3K |
| 资源 | rustlua-assets | 5.4K |
| 聚合 | rustlua-scene | 5.2K |
| 其余 9 个 core crate | ui / camera / physics / infra / input / gameplay / animation / math / audio | 3.9K ~ 0.45K |

14 个 `rustlua-*` crate 合计 ~65.3K 行，5 个宿主 crate + spike 合计 ~84.8K 行 —— 即**近 56% 的引擎代码仍在宿主侧**，拆分只覆盖了 core 那一半。

**依赖拓扑**（读各 crate 的 `[dependencies]` / `[dev-dependencies]`）：

- 14 crate **无真实依赖环**；反向边只出现在 `[dev-dependencies]`：`ecs` 的测试需要 animation/scene/ui/physics/render/camera 六个 crate 才能跑（它自己正向只依赖 math + infra）。
- 另两条反向边是 `render → ui` 与 `ui → scene`，成因完全不同。`ui → scene` 是常规的"测试拿上层当夹具"（`rustlua-ui/src/ui.rs:690` 起用 `Scene` 构造 UI 序列化往返用例）。`render → ui` 不是——它曾经只为一条 `#[cfg(test)]` 断言存在：要求 render 的 `EM_PX` 等于 `rustlua_ui::ui::UI_TEXT_BASE_PX`，而这两个字号基准是各自 crate 里重复写的同一个字面量 `12.0`，靠断言维持同步。所以这条边的真实债不是"渲染依赖 UI"，而是**字号基准缺单一事实源**（拆分期就挂着的 EM_PX 待定项）。**已于 2026-10-03 消除**：字面量收进 `rustlua_math::text_metrics::TEXT_BASE_PX`（math 是 render 与 ui 共同的零依赖基座，两边都已直接依赖它），`text::EM_PX` 与 `ui::UI_TEXT_BASE_PX` 保留原公开名指过去、既有引用路径一字不变；那条同步断言没有删掉而是**挪了地方**（`engine/crates/engine/tests/text_metrics_source_of_truth.rs`——engine 同时依赖三个 crate 且只有一份类型，看得见两侧又不必让 render 反向依赖 ui），`render` 的 `dev-dependencies rustlua-ui` 随之删除。反向边现在只剩 `ui → scene` 这一条测试夹具。
- `scene`、`animation` 的 dev-dep 只指向基座 `infra`，那是正向边不是环——把它们和 ecs 那六个混在一起读会高估反向耦合的面。真正需要处理的只有 `render → ui` 这一条。
- 真正的耦合瓶颈不是 ecs，而是两个全知聚合层：`rustlua-scene` 正向依赖 **9 个** crate（含 render/ui/physics），`rustlua-scripting` 正向依赖**全部 13 个**兄弟 crate。scripting 的改动半径等于拆分前的整个 core，增量编译红利在它的下游拿不到。
- 无内部依赖的基座：`rustlua-math`、`rustlua-input`（两者只带 `thiserror`）；`rustlua-audio` 仅依赖 infra。这几层是干净的。
- `engine` crate 的 20.8K 行里 `host/` 占 20.4K（**98%**），`core.rs` 只有 70 行纯 `pub use`——门面再导出本身没有承载逻辑，符合预期。

## 2. 核心差距矩阵

### 2.1 渲染管线 — 差距最大

| 能力 | RustLua | Unity / Unreal | Godot 4 |
|---|---|---|---|
| 光照模型 | 单方向光 + Blinn-Phong | 全 PBR + IBL + 光照探针 + 光照贴图 | Full PBR + IBL + SDFGI + VoxelGI |
| 后处理 | exposure / tint / vignette 三项 | 完整 tonemap（ACES/Filmic）、Bloom、SSAO、SSR、DOF、Motion Blur | 完整后处理栈 |
| HDR | 无 | 标配 | 标配 |
| 阴影 | 基础 shadow map + PCF | CSM + VSM + 级联 + GPU-driven | 多光源阴影 |
| Compute Shader | 不支持 | 全面支持 | GDExtension + Vulkan compute |
| 粒子系统 | ECS 有组件，渲染侧不成熟 | VFX Graph / Niagara | GPUParticles3D/2D |
| Shader 系统 | 6 个内嵌 WGSL 字符串，无热重载 | Shader Graph / HLSL + 热重载 | VisualShader + GLSL + 热重载 |
| GPU Instancing | 静态 mesh 分组 | 全场景自动 | 自动 |

**核心差距**：没有 PBR IBL 环境光照、没有 HDR 管线、没有 compute shader、没有 shader 变体/permutation 系统。视觉表现力约处于 **Unity 5 / Godot 3** 水平。

### 2.2 ECS 架构 — 差距较小

| 能力 | RustLua | Unity DOTS | Godot 4 |
|---|---|---|---|
| 存储模型 | Dense sparse-set | Archetype-based | 传统 OOP（无原生 ECS） |
| 系统调度 | 10 级固定 stage，顺序执行 | 并行 job system | 信号/节点树 |
| 并行 | 无（stage 内串行） | 全面并行 | 有限 |
| 序列化 | 完整 schema 驱动 | 有 | 有 |

**亮点**：ECS 设计合理（generational index + dense storage + schema 驱动序列化），2D 游戏完全够用。差距主要在**系统并行调度**——Unity DOTS 的 job system 可以多核并行跑数千个 system，RustLua 的 stage 内串行。

### 2.3 脚本系统 — 定位独特，差距中等

| 能力 | RustLua | Unity | Godot |
|---|---|---|---|
| 语言 | Lua 5.4 (mlua) | C# | GDScript / C# |
| API 规模 | 41 模块 / 275 函数 | 数千个类 | 数千个类 |
| 热重载 | 完整实现 | 不支持（需编辑器重编译） | 部分支持 |
| 调试 | 有基础支持 | Visual Studio / Rider | 内置调试器 |
| IDE 支持 | 无 Language Server | 完整 LSP | 完整 LSP |

**亮点**：Lua 热重载是真正的竞争优势，Unity 做不到。但 API 覆盖面（275 函数 vs 数千个类）和缺少 Lua Language Server 是明显短板。

### 2.4 编辑器 — 差距大

| 能力 | RustLua | Unity | Godot |
|---|---|---|---|
| 技术栈 | egui (immediate mode) | 自研 IMGUI + UI Toolkit | 自研 Qt-like |
| 可视化脚本 | 无 | Visual Scripting (Bolt) | VisualShader |
| 动画编辑 | 无编辑器内动画时间线 | Animation Window / Timeline | Animation Editor |
| 材质编辑 | 无 | Shader Graph / Material Inspector | VisualShader |
| 性能分析 | 基础 profiler | Profiler + Frame Debugger | Built-in Profiler |
| 地形编辑 | 无 | Terrain System | 无原生（有插件） |
| 导航网格 | 无 | NavMesh | NavigationServer |
| 插件系统 | 无 | 完整 Package/Plugin | EditorPlugin |

**核心差距**：egui 作为编辑器 UI 框架在**复杂交互、自定义控件、视觉品质**上远不及 Unity/Godot 的自研编辑器。缺少动画时间线编辑、材质编辑器、可视化脚本是最致命的三个缺失。

### 2.5 资源管线 — 差距中等

| 能力 | RustLua | Unity | Godot |
|---|---|---|---|
| 增量导入 | 有（ImportCache） | Asset Database v2 | ResourceImporter |
| 格式支持 | PNG/JPG/WAV/MP3/OGG/glTF/TTF/Lua/Atlas | 数十种 | 数十种 |
| Atlas 打包 | 已落地（`.atlas` 源格式 + 导入校验 + shelf 打包器 + 运行时加载，`docs/63`） | Sprite Atlas | AtlasTexture |
| 资产压缩 | 基础 | ASTC/ETC2/BC 多格式 | VRAM 压缩 |
| 热更新 | 无 | Addressables / Asset Bundle | PCK 导出 |

### 2.6 完全缺失的系统 — 差距极大

| 系统 | Unity/Unreal 状态 | RustLua |
|---|---|---|
| **网络/多人** | Netcode / Unreal Networking | 完全无 |
| **导航系统** | NavMesh + NavAgent | 无 |
| **动画混合/IK** | Mecanim 状态机 + IK | 基础状态机，无混合/IK |
| **音频空间化** | 3D 空间音频 + HRTF | 仅 2D 总线 |
| **UI 自动布局** | UXML/FlexBox | 锚点手动布局 |
| **跨平台** | 20+ 平台 | 3 个（Win/Web/微信） |
| **VR/AR** | OpenXR | 无 |
| **物理载具** | PhysX Vehicle | 无 |
| **世界构建** | Terrain / World Partition | 无 |

## 3. RustLua 的独特优势

差距不等于劣势。以下是成熟引擎反而做不到的点：

1. **极致轻量**：整个引擎 ~178.8K 行 Rust（含 `src/` 与示例/测试），Unity 编辑器本身千万行级别。启动快、打包小、嵌入容易。
2. **Lua 热重载**：改脚本即生效，不需要重编译或重启，Unity/Godot 都做不到原生支持。
3. **WebGPU-native + 微信小游戏**：直接面向 Web 和微信生态，Unity WebGL 打包体积大且性能差。
4. **Rust 内存安全**：没有 GC 暂停，没有 C++ 内存错误，引擎层面的可靠性天然更高。
5. **工程执行力**：ECS + 渲染 + 物理 + 脚本 + 编辑器 + 资产管线 + 两个完整示例游戏 + 质量门 + CI，6 周内由一人完成。

## 4. 定位对标

RustLua 当前最接近的对标是 **Bevy 0.14** 或 **Defold**：

| 对比维度 | vs Bevy 0.14 | vs Defold | vs Godot 4 |
|---|---|---|---|
| 编辑器 | 领先（有完整编辑器） | 领先 | 落后 |
| 脚本热重载 | 领先 | 领先 | 持平 |
| 渲染表现力 | 持平 | 领先（2D）/ 落后（3D） | 落后 |
| 工具链成熟度 | 持平 | 落后 | 落后 |
| 生态/社区 | 落后 | 落后 | 落后 |
| 包体/启动速度 | 领先 | 持平 | 领先 |

- 比 **Bevy** 更完整：有编辑器、有 Lua 脚本、有完整示例游戏、有资产管线
- 比 **Defold** 更现代：Rust + wgpu + ECS，但缺少 Defold 的成熟工具链和多平台支持
- 离 **Godot 4** 还有 2-3 年的功能差距（主要在渲染和编辑器）
- 离 **Unity** 有 5+ 年的生态差距

## 6. 优先级建议

按投入产出比排序。表里有两条是**架构债**（不是新增能力，而是让后续能力做得动的地基），它们的理由与工作量直接引 1.1 的实测数据（正向依赖数、文件行数），不是主观感受：

### P0 — 视觉表现力分水岭

| 方向 | 理由 | 预估工作量 |
|---|---|---|
| PBR + HDR + Tonemapping | 从"能用"到"能商用"的分水岭 | 4-6 周 |
| Sprite Atlas 打包 ✅ 已完成（`docs/63`） | 2D 项目刚需：`.atlas` 源格式 + 导入校验 + 打包器 + 运行时加载 + 依赖边 | 原估 1-2 周 |

### P1 — 能力补齐

| 方向 | 理由 | 预估工作量 |
|---|---|---|
| Compute Shader 支持 | 粒子、GPU 动画、后处理都依赖它 | 3-4 周 |
| 3D 空间音频 | 实现成本低（rapier 有位置数据，rodio 支持空间化） | 1 周 |
| ECS 并行调度 | 当前串行够用，规模上去后是瓶颈 | 3-4 周 |
| 拆上帝文件（架构债）：`host/renderer.rs`（6,089 行） | 1.1 实测宿主侧第二大单文件，且 §2.1 的四项差距（PBR/IBL、HDR+tonemap、阴影、shader 变体）全都落在这一个文件里——P0 的 PBR + HDR 那 4-6 周若不先拆它，就是往 6,089 行里继续加代码。现状是把 GPU 资源缓存（`LoadedTexture`/`GpuMaterial`/`CachedMesh`/`CachedPrimitive`）、draw call 与 metrics 记录、viewport/depth-stencil pass 设置、2D sprite 视图解析四类逻辑混在同一个 `impl Renderer`（该 `impl Renderer` 块从 574 行一直铺到 4,137 行）。按这四条缝切是机械搬迁；**次序上应在 P0 的 PBR 项之前启动** | 1 周 |
| 依赖倒置（架构债）：削掉 `rustlua-scripting` 的 13 条正向依赖 | 1.1 实测的耦合瓶颈就在这里——它正向依赖全部 13 个兄弟 crate，改动半径等于拆分前的整个 core，14-crate 拆分买到的增量编译红利在它的下游一点都拿不到。做法是把各模块的 Lua 绑定注册下沉回 owning crate（`rustlua-assets` 已经带 mlua 依赖，是可落地的先例），scripting 只认注册表不认具体 crate。代价要说清：mlua 依赖跟着下沉，编译量只是换了位置，真正买到的是**改动半径** | 2-3 周 |

### P2 — 效率倍增器

| 方向 | 理由 | 预估工作量 |
|---|---|---|
| 动画编辑器 | 目前只能代码创建 clip，时间线编辑是效率倍增器 | 4-6 周 |
| Lua Language Server | 275 个 API 没有 IDE 补全，开发体验差 | 2-3 周 |
| 导航网格 | 任何需要 AI 寻路的游戏都需要 | 3-4 周 |
| 拆上帝文件（架构债）：`host/runtime_scene.rs` | 全仓最大单文件，1.1 实测 10,267 行，本次补录时（2026-10-03）复核已到 10,458 行——它还在长。也是"近 56% 引擎代码仍在宿主侧"的代表作（engine crate 20.8K 行里 `host/` 占 98%）。按场景生命周期 / 渲染提交 / 输入分发 / 脚本桥切开是机械搬迁、风险低；不先做它会挡住上面的 ECS 并行调度与依赖倒置 | 1-2 周 |

### P3 — 按需启动

| 方向 | 理由 |
|---|---|
| 网络/多人 | 看目标用户群，单机游戏不需要 |
| 更多平台（macOS/Linux/iOS/Android） | 看目标市场 |
| VR/AR | 需要硬件和市场需求驱动 |

## 7. 总结

RustLua 是一个架构优秀、执行力惊人的引擎，在 **2D + Lua 热重载 + Web 小游戏**这个细分赛道上有真实竞争力。

最大的短板不是代码质量，而是**渲染表现力**和**编辑器工具链**——这两项恰恰是成熟引擎投入了十几年团队积累的结果。

建议策略：**不追求全面对标，聚焦细分赛道做到极致**。在 2D 游戏 + Web/微信小游戏这个定位上，RustLua 的轻量、热重载和 Rust 安全性是成熟引擎无法轻易复制的优势。
