## 5. 续跑方法（怎么在这个仓库里干活）

- **Rust 工作区在 `engine/`**：`cargo` 必须在 `engine/` 下跑（或 `--manifest-path engine/Cargo.toml`）。
- **改完就跑 §2 的命令组**；涉及引擎 schema 的改动还要跑 `cargo test -p engine --lib`
  与两个真实工程 `--check`（审计是真实工程证据的来源）。
- **门在哪**：`scripts/verify.ps1`（完整）、`scripts/check-docs.ps1`（文档编号/H1/索引/链接/替换字符/脚本 BOM）、
  `--perf-baseline` 的 30 个场景（每个都带不变量，失败退出码 2）。
- **负向对照要求**：新增门/不变量时必须**证明它能判红**（临时破坏生产代码 → 看到判红 → 还原），
  这一点在 docs/56 里每轮都留了记录，续跑时保持同样标准。

## 6. 未提交状态：怎么带到另一台机器

当前工作区有 **32 个已跟踪文件被修改 + 20 个新文件未跟踪**（HEAD = `2ed147d`，分支 `main`）。
其中 `docs/55`、`docs/56`、`docs/57`、`engine/crates/editor/src/{command_router,services,schema_fields,
schema_inspector,scene_drag,menu,play_control,layout,file_watcher,perf_*,profiler,resource_refresh,
schema_audit,diagnostics}.rs`、`engine/crates/engine/src/core/{component_schema,property_path,
component_migration}.rs` 等**都在未跟踪/已修改状态**，`git pull` 到另一台机器**拿不到这些文件**。

带走的两种做法（任选）：

```powershell
# A) 提交后推分支（推荐）
git add -A
git commit -m "编辑器重构：阶段 0/1 收口 + 阶段 2（typed action / 交互状态机 / schema 编辑器 + 4 组件迁移）"
git push origin main

# B) 打包成一个 git bundle（不想动远端时）
git bundle create editor-refactor.bundle HEAD
# 另一台机器： git clone editor-refactor.bundle RustLua
```

**注意**：`git add -A` 会把本会话开始前就存在的改动（`docs/README.md`、`engine/crates/editor/src/history.rs`
等）一并提交；如果那些属于别的在途工作，先 `git status` 看清楚再决定。

## 7. 工程注意事项（踩过的坑，别重复踩）

1. **不要用 PowerShell 文本 cmdlet 批量改源码**（`Get-Content -Raw` + `Set-Content` 在 PS 5.1 下按 ANSI
   读写，会毁掉 UTF-8 源码；第 11 轮出过事故）。只用文件读写工具。
2. **改 `.ps1` 之后确认 UTF-8 BOM 还在**：文件工具写回**不带 BOM**，而 PS 5.1 在中文区域按 ANSI 读无 BOM
   脚本 → 整条质量门无法解析（第 21 轮出过事故，现在 `check-docs.ps1` 的第 ⑦ 项会判红）。
3. `editor` 包同时有 **lib 与 bin**：bin 的测试把 lib 当外部依赖编译（不带 `cfg(test)`），
   lib 里的测试辅助函数要么 `#[doc(hidden)] pub`，要么在 bin 侧另写一份。
4. 面板文件里**不要直接写文档**（架构棘轮会判红）；视图只发 typed action，提交边界留在 shell。
5. 引擎 schema 的字段规则要**与引擎解析器对拍**（`field_rules_match_engine_validators`）；
   刻意比引擎更严的规则（如 `.lua` 扩展名、负九宫格）必须写成显式分歧并加注释，别"顺手对齐"。
6. 门的**计数/清单**类断言（`PINNED_WRITES`、`HANDWRITTEN_PANEL_COMPONENTS`、缺 schema 清单）
   变化时会红——这是有意的：迁移进度必须显式记录，而不是悄悄漂移。
