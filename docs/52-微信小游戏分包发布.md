# 微信小游戏分包发布（主包 + 单分包）

本文定义微信小游戏的**默认发布形态**：主包 + 单分包。它是
[docs/51 平台插件适配](51-平台插件适配.md) 里"微信小游戏特有约束"一节的展开，
并被 [docs/34 质量门与发布清单](34-质量门与发布清单.md) 的微信两条用例引用。

## 1. 为什么换形态

之前的默认形态是**瘦首包 + CDN 远端回落**：主包只留 ~391 KB 骨架，4 MB 重资源上传 CDN。
这条路能跑通，但代价是三个**发布前必须办完的外部前提**：

| 前提 | 代价 |
|---|---|
| 公网 HTTPS 服务器 | 有成本，且是运行时依赖（服务器挂了游戏就进不去玩法） |
| ICP 备案 | 国内域名必须备案才能上线 |
| 公众平台 `downloadFile` 域名白名单 | 漏配一项就是"真机贴图全丢"，而本机测不出来 |

分包形态把这三点一次性去掉：

* **零服务器、零备案、零域名白名单**：资源随代码包上传，微信自带 CDN 分发；
* **分包下载后落在本地沙箱**，运行时是本地文件读取，比走 HTTPS 回源快；
* **版本统一**：一次上传、一次审核，不存在"CDN 上是旧资源、包内是新代码"的不一致。

## 2. 微信规则（决定了整个设计的形状）

1. **`subpackages[i].root` 目录下的文件全部进分包，主包里一个都不能留。**
   所以"主包保留启动场景及其贴图"**不能**表现为"在 `pack/` 里留一部分"——留在 `pack/` 里的
   首屏资源在真机上仍然属于分包、仍然要等下载。主包侧首屏资源必须放**兄弟目录 `mainpack/`**。
2. **`root` 目录下必须有 `game.js`，它是分包入口文件，挂载后会被宿主执行**（不只是存在性占位）。
   缺了开发者工具报「未找到 `["subpackages"][0]["root"]` 对应的 `/pack/game.js` 文件」并拒绝打开工程
   ——这正是历史上取消分包的直接原因。
3. 上限：主包 ≤ 4 MB、**单个普通分包不限制大小**、总计 ≤ 20 MB（官方《分包加载》2023-10 起；
   开通虚拟支付的小游戏可到 30 MB，本脚本按无内购口径保守取 20 MB）。
4. 资源路径由 `plugins/webgl/web-runtime.js` 硬编码为 `'pack/' + path`，而这份运行时**由
   webgl 与微信两个平台共用同一份**（刻意的，防止游戏逻辑各自漂移）。因此分包形态
   **不改 `web-runtime.js`**：所有路由都落在适配层（`plugins/wechat-minigame/wechat-adapter.js`）。
5. **代码包只上传后缀在白名单内的文件**（官方《代码包》文档，69 个后缀）。`lua` / `toml` / `md`
   都不在白名单里 → 传不上去 → 真机上读它是 `permission denied`。构建期按此改名，见 R9。
6. **`*.js` 与 `game.json` 会被编译**，上传后无法用 `FileSystemManager` 直接读
   （`require` 走的是编译产物，那是另一条通道）→ 适配层不得把它们当运行期判据，见 R9b。

    ├── game.json             # 含 subpackages: [{ name: "pack", root: "pack" }]
    ├── code-package.json     # 改名映射：逻辑路径 → 会随代码包上传的宿主文件名（R9）
    ├── mainpack.json         # 首屏清单（构建/运行时/harness 三方共用的路由依据）
    ├── mainpack\             # 首屏资源：在**主包**里，启动即用
    │   ├── manifest.txt / chars.txt（原名）/ project.toml.txt / settings.toml.txt（按白名单改名）
    │   ├── scripts\**        # 全部 Lua（require 是同步的，无法懒加载）；逐个改名为 *.lua.txt
    │   ├── assets\fonts\**   # 子集字体（boot 之前就要用）
    │   ├── assets\art\title\** + assets\art\ui\** + 启动场景引用的贴图
    │   └── scenes\main.scene
    └── pack\                 # 分包 root（有 game.js 入口）
        ├── game.js           # 分包入口（发布脚本生成，挂载后由宿主执行）
        ├── assets\**         # 音频 + 非首屏贴图
        └── scenes\**         # 除启动场景外的场景

### 三种资源形态

| 形态 | `-AssetPack` | 主包 | 资源位置 | 外部前提 |
|---|---|---|---|---|
| **分包（默认）** | `subpackage` | ≤ 4 MB | 首屏 `mainpack/`，其余 `pack/` 分包 | **无** |
| 瘦首包 | `remote` | ≤ 4 MB | `pack/` 只剩骨架，重资源在 CDN | HTTPS + 备案 + 域名白名单 |
| 全量随包 | `full` | ≤ 4 MB | 整个 `pack/` 都在主包 | 无（但本工程 4.4 MB 必然超限） |

三者**互斥**：`subpackage` 与 `-RemotePackBaseUrl` / `-CdnPackDir` 相互拒绝。两套资源来源同时存在
只会让"包内读到了"掩盖"分包根本没挂载上"。

## 4. 切分机制：首屏清单

切分的唯一依据是 `scripts/first-screen-pack.js` 从 `pack/` 的**实际磁盘内容**推导出的
`mainpack.json`（零依赖 Node，不写死工程名或目录层级）。

```powershell
node scripts/first-screen-pack.js examples\game_jhyt\builds\wechat-minigame\launcher\pack --json
# first_screen_pack_ok entries=126 bytes=1102502 startup=scenes/main.scene scripts=105 textures=7 fonts=1 scenes=8 renamed=107 warnings=0
```

* **种子**（缺一启动即失败）：`manifest.txt` / `project.toml` / `settings.toml` / `chars.txt`；
  `project.toml` 声明的 `startup_scene` 与 `main_script`；全部 `scripts/**`；全部 `assets/fonts/**`。
* **`scripts/` 与 `fonts/` 必须全部进主包**，这不是保守而是硬约束：`web-runtime.js` 启动时遍历
  manifest 把所有 `scripts/**.lua` 塞进 `package.preload`，而 Lua 的 `require` 是**同步**的、
  无法懒加载；`loadGameFont` 也在 boot **之前**执行。
* **场景贴图闭包**：解析 `startup_scene` 的 `texture=` 与 `clip:` 引用。引用了但**不在**
  manifest 里 → 其出现在启动场景中即**致命退出（码 1）**；只出现在别的场景里则只警告。
* **保守前缀**：默认只把 `assets/art/ui/menu/**` 纳入（13 张）。启动场景的贴图闭包只能拿到
  `main.scene` 里的静态 `texture=`，而 `ui/title_menu.lua` 是按 `ui/skin.lua` 的注册表**键名**画装饰
  （四角 ornaments、bamboo divider、seal、hover 态，还有从未被静态引用到的 pressed 态），静态推不出来，
  所以整目录收 `menu/`。其余 10 个 UI 子目录（common 24 / hud 19 / skills 6 / backpack 5 / dialogue 3 /
  save 2 / build 2 / settings 2 / shop 2 / quest 2）只被局内面板引用（`shop.lua` / `inventory_ui.lua` /
  `pause_menu.lua` / `quest_ui.lua` / `hud.lua`），标题画面一张都不画，留在分包侧。
  此前这里是"整收 `assets/art/ui/**`"，多带 67 张 = **11,096 B**（主包内 art 实测 69,367 B / 82 文件
  → 58,271 B / 15 文件，逐文件 `stat` 求和，别用 `du`）—— 相对 3,729 KB 的主包只占 0.3%，收窄**不是**为了过线，
  是为了让首屏清单回到"入口界面要用的"这个语义。需要临时多带别的目录用 `--include <前缀>`，
  它与默认前缀并列生效、不改这里的取舍。
* **拒绝项**：`game.js` 一律不得入清单——它与分包入口 `pack/game.js`、主包入口 `game.js` 三重同名，
  且 `subpackage-relative` 方言会把 `pack/game.js` 读成主包入口。
* **退出码**：`0` 通过 / `1` 清单不可靠 / `3` 未找到 pack 根。

### 推论的方向（2026-10-03 更新）

原话"**首屏清单越大，分包越安全**"来自资源大头决定主包的年代（那时主包只用 37%，被 4 MB 卡住的是
分包那一侧）。**现在被卡住的是主包**：wasm 核心 2,347 KB 进了主包（R11/R12），实测 88.7%（第 6 节）。
两个方向因此相反，但结论仍然成立、只是要分开说：

* **正确性优先**：清单「宁可多列、不可漏列」不变——漏列的文件被路由到分包，而首屏读分包在挂载前读不到，
  症状是标题一片 `Image.onerror`。这条永远赢过体积考虑。
* **体积侧**：主包超限时，方向是**收窄**清单（把非启动必需的条目挪回 `pack/` 分包 ⇒ 主包变小、分包变大），
  而不是扩大它。`package.ps1` 超限报错里的"出路 ①"就是这个方向；它此前写反成"把更多资源列进首屏清单"，
  照着做只会更超（两侧配额下同一句话含义相反，2026-10-03 已改正）。

### 切分是真搬运，不是复制

发布脚本按清单 `Move-Item` 到 `mainpack/`（保持同构相对路径），并立刻断言：

* **搬运守恒**：`mainpack/` 的文件数与字节数 == 清单条目数与字节和；
* **整体守恒**：`mainpack/` + 裁完的 `pack/` == 切分前的 `pack/`（文件数与字节数都要对得上）；
* **两侧互斥**：清单项必须在 `mainpack/` 下存在、且在 `pack/` 下**不存在**。

漏列的文件会被路由到分包，而首屏读分包在挂载前是读不到的——症状是标题一片
`Image.onerror`。上面的断言把这种漏列挡在**发布期**，而不是等真机白屏。

## 5. 运行时路由

适配层是唯一知道"某个逻辑路径该从主包还是从分包读"的地方。实现是**主体 × 方言**两层正交组合：

* **主体**（`mainpack/` 还是 `pack/`）是**包内布局**属性，由 `mainpack.json` 静态决定：
  清单内 → `mainpack/<x>`，清单外 → `pack/<x>`；不回落（清单项构建期已被搬走，
  在 `pack/` 再找一次只会把"切分没搬干净"掩盖成"分包还没挂载"）。
* **方言**（根相对 / 前导斜杠 / `./` 前缀 / 分包根相对…）是**宿主**属性，5 条候选逐个试、记住成功的。
  主体里的**文件名**还要再套一层改名映射（`hostFileFor`，R9）：`scripts/main.lua` 在真机上叫
  `main.lua.txt`。映射对两个主体用同一张表、同一个键域（pack 相对逻辑路径）。
  注意 **`user-data` 那条方言必须作用在逻辑路径上**：改名只存在于代码包里，而用户目录缓存的键
  与远端 URL 都按逻辑路径算——两者混用会让"下载成功了却永远读不到"（瘦首包形态实测踩到）。

**必须这样拆**：把 `mainpack/` 当成策略表里的一条别名，在 `slash` / `sub-root` 这类宿主上会被拼成
`/mainpack/...` 或 `mainpack/...` 而读不到——两个正交的维度必须正交地组合。
方言记忆按**主体**分键（`mainpack/` 与 `game.json` 同级共用 `main` 键，`pack/` 单独一键），
因为 `sub-root` 形态下这两类路径的合法形式**真的不同**（实测
`read_strategies=main:root-relative/pack:subpackage-relative`）。

其余关键行为：

* **首屏不等分包**：`fetchShim` 对清单内路径直接读主包，不等 `loadSubpackage`；`start()` 里分包
  是**后台发起、不 await** 的，boot 立即用主包资源渲染标题。
* **非首屏等分包**：清单外的 `fetch` 先 `await ensurePack()`；`Image.src` 是同步通道，
  未挂载时**延迟到分包结算再交给宿主**（先交一个读不到的路径，宿主立刻 `onerror`，
  而运行时的 `loadImage` 以第一次 `onerror` 为准，之后补挂载也救不回来）。
* **失败降级而非掀翻启动**：`ensurePack()` 永不 reject。失败走三重可见通道——
  `console.error` + `data-rustlua-pack=failed` + 画布红横幅；同时有 10 秒重试冷却
  （否则每次 `pack/` 读取都会重新下一次包 = 重试风暴），以及 20 秒兜底超时
  （宿主既不 `success` 也不 `fail` 时不能让等待它的读取永远悬着）。
* **进度条**：微信端**没有** loading UI（`statusElement` 是个 no-op 对象），分包却是几十 MB 量级的
  下载。适配层消费 `onProgressUpdate` 并自绘进度条，每帧的 z 序固定为
  `loadingBar → failureBand → packFailure → drawOverlay`；`boot=failed` 时不画进度条
  （那一刻整屏属于启动错误页）。

**口径只能是 `wechat_minigame_package_ok` 那行**（它按文件**字节和**统计）。用 `du -sk` 估包体会虚高数百 KB
（本仓 700 个小文件、4 KB 块对齐），曾据此误判"主包超 173 KB"而实际根本没超——`scripts/first-screen-pack.js --json`
给出的也是字节和，两处一起看才对得上。**量体积的门必须先确认量的是字节。**

主包构成（逐棵子树量的字节和，三项相加正好等于 3,635）：`pkg/game_web_bg.wasm` **2,347 KB** +
`mainpack/` 首屏 **1,010 KB** + launcher 根 **227 KB**（根里是 `web-runtime.js` 108 KB、
`wechat-adapter.js` 64 KB、`wasm-bridge.js` 15 KB、`pkg/game_web.js` 之外的 game.js/game.json 等入口）。
**wasm 一项就占主包 64%**——真要再腾空间，方向在 wasm 侧（内嵌资源、feature 裁剪），不在内容侧。

新增的体积杠杆（构建期、零运行时行为改动）：**产物 Lua 剥注释**。

```bash
# 只读体检（同时验证"清单能逐条复现"这条动手前提）；对**未剥过**的 pack 跑，savedKb 就是这一项的额度
node scripts/strip-lua-comments.mjs examples/game_jhyt/builds/webgl/pack --json
# 落盘（发布链路里由 package.ps1 自动执行，不需要手工跑）
node scripts/strip-lua-comments.mjs <packRoot> --write
```

实测 **283 KB**（Lua 862 KB → 579 KB；104 个文件里 102 个有可剥内容）。为什么它是安全的：

* 只动 `pack/` 里的**产物副本**，源工程 `examples/<game>/scripts/**.lua` 一个字节都不改；PC 平台不剥
  （桌面包没有体积门，而"pack 与源文件逐字节相同"在排查时有用）。
* **保留行数**（剥文字留换行）：发布包里的 Lua 栈回溯行号仍对得上仓库源码。工具对此有断言，
  行数变了就整批拒绝写出。
* **逐字符词法**（不是正则）：`print("a -- b")` 的串内 `--`、`--[[]]`、`[=[ ]=]` 都按 Lua 的规则处理。
* 同步重写 `manifest.txt` 的字节数与 FNV-1a-64：适配层运行时逐条校验清单，"改文件不改清单"等于首屏
  每个脚本都校验失败。所以工具把"整份 684 条能逐条复现"当成**动手前的硬条件**（FNV 实现从
  `plugins/wechat-minigame/wechat-adapter.js` 同段算法复制，复现不了就拒绝改动）。

端到端验证（同一份发布产物）：跨 `mainpack/` + `pack/` 两棵树、按 `code-package.json` 的改名映射查宿主文件名，

### 6.2 2026-10-06 实测：把 wasm 内核搬进分包（主包第一次真被 4 MB 门挡下）

触发这一改动的读数（同一份产物，`scripts/verify-wechat-minigame.ps1` 的静态段）：

```
wechat_minigame_static_ok main=4,547KB … main_of_limit=111.0%   ← 超 451 KB，发布被拒
```

复现（不需要重建 Rust 产物）：

```powershell
powershell -NoProfile -File scripts\package.ps1 -Platform wechat-minigame -SkipBuild
powershell -NoProfile -File scripts\verify-wechat-minigame.ps1 -SkipRuntime
```

搬完之后同一道门：

```
wechat_minigame_static_ok main=2,087KB subpackage=4,689KB total=6,776KB subpackages=pack
  asset_pack=subpackage upload_rules=ok main_of_limit=51.0% subpackage_of_limit=22.9% total_of_limit=33.1%
主包 2,087KB（含首屏 mainpack/ 1,736KB）/ 上限 4,096KB（51.0%）
```

**两份读数不能直接相减**：内核实测 2,580,513 字节 = 2,520 KB，而 4,547 − 2,087 = 2,460 KB，差
60 KB 来自两次构建之间别的内容漂移（在途的 prefab 批往 `pack/` 里加了东西）。要按字节核对只能
在同一份产物上量：`node scripts/first-screen-pack.js <launcher>/pack --json` 给的是分包的字节和。

为什么搬内核而不是"收窄首屏清单"：首屏清单是**把资源从分包挪进主包**的那张表，主包已经超限的
时候列进清单是反方向（验收脚本里那句修法提示因此被改掉了）。内核一个文件就占主包 55%，而它是
唯一"能整块搬走、又不需要重写路由"的东西。剩下的候选（feature 裁剪、`--disable-optimizations`
之外的 wasm 瘦身）都动的是引擎本体，代价比这一条大得多。

**形状**（这一条是整个改动里唯一有设计含量的部分）：

* 内核 `game_web_bg.wasm` → `pack/game_web_bg.wasm`；胶水 `pkg/game_web.js` **留在主包**。
  胶水是 `require()` **同步**加载的，`WXWebAssembly` 只给异步的 `instantiate(路径, imports)`——
  分包没挂载时那句 require 无从等待。于是"搬内核、留胶水"不是可选项而是唯一可行的切法。
* 启动次序跟着变：`start()` 先 `await` 分包挂载，**挂载成功后**才实例化，然后才出标题画面
  （原先是"标题不等分包"）。等待期间进度条由**适配层自己**用 `setTimeout` 链驱动并自绘——
  运行时一帧都还没跑，`wx.requestAnimationFrame` 那条队列属于运行时，占它等于偷游戏帧
  （实测踩过：`data-rustlua-boot=booted / 未执行任何帧 / raf 队列为空`）。
* 挂载失败在实例化前自动重试 1 次（`ensurePackForBoot`；每次尝试自带 20 s 无回调超时，所以
  重试次数刻意压到 1）。仍失败才判 boot 失败，屏上句子点名是哪一个包：
  「分包（pack）加载失败：游戏内核就在这个分包里…」。

**新增的门**（都是"这条改动要是没生效，输出必须红"的形状）：

| 门 | 在哪 | 反面对照（实测会红的读数） |
|---|---|---|
| 分包形态下 `pkg/game_web_bg.wasm` **不得存在** | `package.ps1` + `verify-wechat-minigame.ps1` 各一条 throw | 手工把内核复制回 `pkg/` 立刻红；取其一而不是两份并存（两份同名内核迟早漂移） |
| `wasm_denied_before_mount=0` | harness 证据行 + 成功用例断言 | 把 `start()` 里那句 `await ensurePackForBoot(...)` 换成 `Promise.resolve(true)`（只改产物副本，验完还原，md5 核对一致）→ 红：`分包挂载前有 2 次 wasm 内核读取被挡下`+`boot=failed`+0 帧 |
| 失败用例下 wasm 失败原因必须**点名** `pack/game_web_bg.wasm` | harness `WP10` 段换向分支 | 旧版内核在主包时同一条用例报 `no such file … pkg/…`，换向前后各红一次 |
| `--subpackage delay` 下适配层挂载帧必须为 **0 游戏帧** | harness delay 段（内核在分包时不再与宿主的 tick 对等） | 币种不同：宿主记的是驱动 tick（实测 `mount_frame=6`），适配层记 `frameCount`；硬要相等必然假红 |

harness 侧还补了一条结构性的东西：boot 悬着的那段由 `pumpSubpackageDuringBoot` 按 16 ms 一 tick
顶上挂载驱动。没有它，`--subpackage delay` 直接死锁（挂载等帧，帧等 boot，boot 等挂载），实测
表现是 30 s 不 settle 后撞 20 s 无回调超时。

**本机证明不了的（不要写成"已验证"）**：

1. **2.5 MB 单文件上传上限**。内核搬进分包后是 2,520 KB 的**单个文件**，官方对单文件大小没有
   可本机复现的门；只有上传器/开发者工具的"代码包大小"面板能给数。这一条是本次改动剩下的
   最大未知，真机/上传前必须先看它一眼。
2. **真机 `WXWebAssembly.instantiate` 能不能读分包路径**。harness 的复刻按代码包根解析路径、
   并按挂载状态放行，它证的是"适配层没在读错地方"，证不了宿主的分包路径语义。
3. **重试救回的概率**。真实网络抖动下"1 次重试能不能救回来"本机无从测量；这条降级只是把
   "一次失败必死"改成"两次机会 + 三重可见"。
4. **首屏时序代价**。冷下载时标题画面现在要等分包（以前不等）。分包 4,689 KB 里 2,520 KB 是
   内核，玩家第一眼看到的是进度条而不是标题——这是形态选择的必然结果，不是可以调优掉的细节。

**这一批跑完的用例矩阵**（产物同上，逐条手跑）：

```
subpackage-delay / subpackage-delay-move / subpackage-never / subpackage-fail-once  → exit 0
subpackage-ok / no-game-json-dependency                                             → 各剩 1 条红：
  data-rustlua-drawn=0（期望 > 0，即画面上确有内容）
```

那一条红**不属于这次搬迁**，当时三条实测：① 同一份产物加 `--drive-new-game` 进 `manor` 后
`drawn=4720`，也就是取样机制在跑、只有**标题屏**采不到非背景像素；② 用 `git show HEAD` 的适配层
与 harness 分别回退跑（把内核复制回 `pkg/` 复刻旧形态），读数一样是 `drawn=0`；③ 搬迁后的启动
日志里没有任何贴图/读取失败警告，而每帧绘制调用严格递增（`perFrame=[5,23,41,…]`）。当时把它记成
"标题门面搬进 `.prefab` 之后画面只剩背景色"，归给 prefab 那摊——**那个归因是错的**，2026-10-07
查清后写在下节：红的是量具，不是画面（见 §6.3）。
**代价要写清楚**：这条红卡在 `drawn>0` 这道通用断言上，所以整个微信运行时门（不只分包用例）
在它修好之前跑不绿——本批只能做到"除这一条之外全绿"。

### 6.3 2026-10-07 实测：标题屏 `drawn=0` 是量具瞎，不是画面坏（假 ctx 补了仿射变换栈）

**症状**：`node scripts/wechat-minigame-harness.js <发布根>/launcher --frames 30 --subpackage ok`
红在 `data-rustlua-drawn=0`，且 30/60/120 帧三种预算读数一样是 0（排除"贴图还没加载完"）。

**三条实测把责任钉在 harness 自己身上**：

1. `--dump-diag` 同一次跑里给 `frames=30 ui_elements=13 images: ok=7 fail=0`，而 `draw_ops>0`
   与"每帧严格递增"两条断言都是过的——**游戏确实在画，7 张贴图一张没失败**。
   复现：`node scripts/wechat-minigame-harness.js examples/game_jhyt/builds/wechat-minigame/launcher --frames 30 --subpackage ok --dump-diag`
2. **同一份产物**在真浏览器里过 `verify-webgl-bundle.ps1`：
   `powershell -NoProfile -ExecutionPolicy Bypass -File scripts\verify-webgl-bundle.ps1 -BundleRoot examples\game_jhyt\builds\webgl -NoSceneVerify`
   → `drawn samples: 251 ui elements: 13`，`data-rustlua-ui-summary` 与微信 harness 里逐字一致
   （`P:title:hl:BtnStart,I:title:btn_hover:…ui_menu_*.png`×6）。两侧 `ui_elements` 同为 13
   而一侧 251、一侧 0 ⇒ 差的不是内容，是**取样口径**。
3. 口径差在哪：`plugins/webgl/web-runtime.js:850-858` 每帧做 contain 适配
   `translate(fitOx,fitOy); scale(fitS,fitS)`，`fitS = min(canvas.width/1280, canvas.height/720)`；
   harness 的假 2D 上下文把 `save/restore/translate/scale/setTransform/transform` 一律设成 `noop`。
   于是 `painted` 记的是**设计坐标**（标题屏元素全在 x=378…1240），而 `sampleDrawnPixels` 按
   **设备坐标**（`wx.getSystemInfoSync()` 给 375×667 ⇒ `fitS=0.293`）开窗口读 ⇒ 采样点一个都碰不到
   UI，恒 0。manor 能读到几千，是因为瓦片从设计 x=0 铺起、恰好有一条没被缩放的窄带落进窗口里。

**为什么现在才红**：门面进 `.prefab`（`164fa0a`）后标题屏最左的元素从设计 x<375 挪到了 x=378，
原来那份"歪打正着的覆盖"没了。所以 prefab 那摊没有回归，**这条门的两种错读数都归量具**：真机被
letterbox 裁掉的内容它可以算成"有画面"（假绿），有内容的标题屏它读 0（假红）。

**改法**：给假 ctx 补一条真仿射矩阵（`a,b,c,d,e,f` + `save/restore` 压栈，`transform` 按
`new = current ∘ arg` 复合，`setTransform` 直接替换），`fillRect`/`drawImage` 入 `painted` 前把
矩形四角落过矩阵、取轴对齐包围盒。`getImageData` 不过矩阵——真 canvas 的像素回读本来就在设备空间。

**这条读数对得上账吗**（不是"改绿就算"）：把标题屏那 17 个绘制矩形按同一套 contain 数学
（`fitS=0.29297 / fitOx=0 / fitOy=228.03`）独立重算一遍采样，脚本给出的期望值与 harness 的读数
**逐位相同**：

```
$ node -e '<按 53 像素步长、光栅序、后画者覆盖重算>'
{"fitS":0.29297,"fitOx":0,"fitOy":228.03,"samples":4720,"expected_drawn":60}
→ harness: drawn=60
```

另一路对照是比例：真浏览器 251/17389 = 1.44%，修好后 harness 60/4720 = 1.27%（修之前是 0%）。
manor 侧同一条断言的数从 4625 变成 3050 —— 换的是口径不是阈值，设备面积本就只是设计面积的
`fitS² = 8.6%`。

**修完的矩阵**（`verify-wechat-minigame.ps1 -BundleRoot examples/game_jhyt/builds/wechat-minigame`
跑到 case 5 之前共 19 组 `harness_ok/harness_negative_ok`；case 5 之后被下面那条既有红挡住，
其用例逐个手跑，全部 exit 0）：`image-src-prototype`、`image-callback-bridge`、
`boot-stall-watchdog`、`host-globals`(stub/separate)、`host-globals-locked`、`host-globals-frozen`、
`canvas-provenance`、`render-overlay`、`render-overlay-no-frames`、`play-path-move`、
`play-path-touchstick`、`save-persist`。

**买不到的部分**（别把这条门读成"画面验过了"）：

1. **文字仍然不产像素**。假 ctx 不栅格化字形，`fillText` 只进 `drawnTexts` 不进 `painted`——
   一个纯文字画面在微信 harness 里依旧读 0（真浏览器给 251 里的大部分正是字形）。标题屏现在能读到
   60 靠的是那 6 张菜单贴图和一条面板。
2. **贴图色是写死的**。`drawImage` 一律记 `[200,120,60]`，不看位图真实内容，所以 `drawn` 只回答
   "有没有东西画进可视区"，不回答"画得对不对、颜色对不对"。
3. **单文件 2.5 MB 上传上限仍未测**（§6.2 那条未知没被这次改动动到）。

**这次解锁后新撞上的红（归下一摊，已证明与本修无关）**：gate case 5
`--image-src-frozen`（subpackage 形态）期望"宿主不让改写 `Image.src` ⇒ 响亮失败"，实测
`boot=running`、`接管方式=own-accessor`、`images ok=7`，适配层没报告"不允许改写"。用
`git show HEAD:scripts/wechat-minigame-harness.js` 的版本复跑同一条命令，红字一字不差 ⇒
它不是仿射变换栈带出来的，是 19 组用例之前从没被跑到过（case 3 的 `drawn=0` 一直把门挡在
case 5 前面）。


## 7. 验收

```bash
# 1) 清单工具（不需要重新构建：现有导出资源包就是一份完整 pack/）
node scripts/first-screen-pack.js <...>/launcher/pack --json
# 期望：first_screen_pack_ok entries=178 bytes=1098178 startup=scenes/main.scene scripts=89 textures=7 fonts=1 scenes=8 renamed=91 warnings=0

# 2) 发布 + 隔离自测（隔离副本里逐条复核切分，再跑一次完整验收）
powershell -NoProfile -File scripts\package.ps1 -Platform wechat-minigame -SelfTest
# 期望：wechat_minigame_split_ok mainpack_files=178 …
#       已按白名单改名 91 个文件；code_package_whitelist_ok dirs=2 (rules_verified_on=2026-09-16/2.32.3)
#       wechat_minigame_package_ok files=11 … asset_pack=subpackage split=mainpack+pack
#       Directory-isolation self test passed (WeChat launcher + runtime OK; asset_pack=subpackage)

# 3) 平台验收（布局 + 配额 + 全部用例）
powershell -NoProfile -File scripts\verify-wechat-minigame.ps1 -BundleRoot <...>\launcher
# 期望：wechat_minigame_static_ok main=1,534KB subpackage=3,011KB total=4,545KB subpackages=pack asset_pack=subpackage upload_rules=ok …
#       wechat_minigame_package_ok … asset_pack=subpackage … subpackage_case=ok,delay,delay-move,never,fail-once
```

分包专属的 5 条 harness 用例（`--subpackage …`）：

| 用例 | 钉住的事实 |
|---|---|
| `ok` | 声明有且仅有 1 个 `root=pack`；入口 `pack/game.js` 存在且可被 `require` |
| `delay --subpackage-delay-frames 6` | 首屏不等分包（启动完成时分包尚未挂载）；进度条消费了进度并画到画布上 |
| `delay + --drive-new-game --drive-move` | 进 manor（非首屏）才需要分包，且世界里主角真的在走 |
| `never --expect-pack-failure` | 分包永远挂不上时首屏照常启动 + 失败三重可见 + 无未处理 Promise 拒绝 |
| `fail-once --drive-new-game` | 首次失败后冷却重试能自愈（冷却经存储注入压到 0） |

`--subpackage auto|off|ok|never|delay|fail-once` 与 `--wx-path-style` 是**正交的两轴**：
前者是"分包挂载行为"（宿主侧强制），后者是"路径方言"。4 档方言用例在分包形态下都额外带
`--subpackage ok`，否则"哪一档方言配哪一种分包行为"说不清、用例之间会互相掩盖。

## 8. 风险与已知边界

* **R1 开发者工具 vs 本机（最高）**：harness 是 Node 伪造 `wx`，**无法模拟微信 IDE 的打包器**。
  "root 目录整体进分包"这条规则是方案的支点，本机证明不了。缓解：切成 `mainpack/` 兄弟目录后，
  两种可能的打包语义**都**能得到正确产物；验收脚本的"清单项在 `pack/` 下不得存在"断言
  把本机产物形态锁死。**首次在开发者工具里必须核对「详情 → 代码包大小」面板的主包/分包两块
  数值与输出行一致**，并真机跑一次「标题 → 开始新游戏」。
* **R2 分包余量**：预计 73.5%，安全。真正会顶到墙上的是"清单过小（< 300 KB）"或资源总量增长。
  杠杆按优先级：① 把资源列进清单（清单变大反而更安全）→ ② 拆第二个分包 → ③ `-AssetPack remote`。
* **R3 `pack/game.js` 三重同名**：分包入口 / 主包入口 `game.js` / `subpackage-relative` 方言把它读成
  `game.js`。缓解：清单工具拒绝把 `game.js` 列进清单；`probePackReadability` 继续不拿它当探针
  （分包形态下这一点更强：它现在**真的存在**，误读会更隐蔽）。
* **R4 分包不可用**：标题照常显示（首屏全在主包），进玩法场景失败，但**失败是响的**。
* **R5 音频接入（已落地，MP3 统一格式）**：微信小游戏音频后端已接入 `plugins/webgl/web-runtime.js`
  （`installLuaAudioBridge` → `wx.createInnerAudioContext`，Lua 侧 `audio.play_on/music/stop_music/`
  `set_bus_volume/volume` 全部走真实播放）。格式策略：**统一 MP3**——InnerAudioContext 官方格式矩阵里
  MP3 在 iOS 和 Android **均支持**（ogg 仅 Android 支持、wav 体积过大），因此源文件直接使用 `.mp3`
  （96kbps、22050Hz、单声道），运行时不再做格式转换或备用格式生成。`assets/audio/**` 从
  "OGG+WAV 双格式各占一半体积"（6.9 MB）缩减为"单一 MP3 格式"（1.5 MB），分包体积省约 5.4 MB。
  文件不存在时返回 false（游戏侧静默降级）。2026-10-03 起**浏览器侧也接了真实后端**（同一份
  `installLuaAudioBridge`，改用 `new Audio()`），"一律失败"只保留在桥没接上的情况；两侧对外语义
  逐条对齐（含缺文件返回 false），实现与实测见 [docs/51](51-平台插件适配.md) 的"浏览器音频后端"。
* **R11 wasm 核心即 Lua 执行层（2026-09-30 起，取代此前"只到装进来为止"）**：微信分支现在
  构建 `--target no-modules` 胶水 + wasm 核心，适配层实例化后把 6 个 `lua_*` 桥导出挂到
  `window.__RUSTLUA_LUA_BRIDGE`，`web-runtime.js` 的全部 Lua 交互经它完成——**游戏逻辑真的在 wasm 里跑**
  （实测 `wasm=ok:ok`、`boot=running`、进 manor 后 33 实体、主角随摇杆位移）。
  由此带来两条硬约束：
  1. **wasm 必须用 rustc 1.88（LLVM 18）构建，两个 web 平台都是**。此前 `package.ps1` 只给
     webgl 用 1.88、给微信留默认 toolchain，理由是"WXWebAssembly 对混合 EH 的接受度沿用阶段二
     发布基线"——那个前提来自 42 KB 的旧 wasm（只有 `start`/`memory`）。换成 mlua 之后，1.97 产物
     **在 wasm-opt 之前**就被本机 V8 拒绝（`Invalid opcode 0x1f`，错误落在 mlua 的函数里），
     症状却只有一句 `wasm lua bridge not loaded` + 0 帧。发布链路现在强制跑
     `node scripts/wasm-lua/verify-wasm-host.mjs <wasm>`，加载不了就直接失败。
  2. **没有 wasm 就没有 Lua**：fengari 时代"wasm 失败不影响 Lua 启动（clock 走 Lua 兜底、boot
     照常成功）"的降级契约已不存在。`--no-wasm` 用例现在要求的是**响亮失败**：
     `boot=failed` + 拒绝原因指名 wasm 桥 + 控制台有启动失败行 + 诊断 `no-webassembly`。
  体积口径随之改变：核心从 42 KB 涨到 **2,371 KB**（1.88 未优化 3,150 KB，`wasm-opt -Oz` 后
  2,428 KB；binaryen 133 **会保留**纯 try_table，实测产物仍可被 V8 加载），
  主包因此从文档旧基线 40.1% 涨到 **96.5%（3,954 KB / 4,096 KB）**，只剩约 140 KB 余量。

* **R12 `WXWebAssembly` 只认代码包路径（2026-09-30 开发者工具实测，已修）**：R11 之后 wasm 就是
  Lua 执行层，而桥接层当时用的是**字节通道**（`readBytes` → 胶水 `initSync(bytes)` →
  `new WebAssembly.Module(bytes)`）。官方 API 面里 `WXWebAssembly` 只有
  `instantiate(path, imports) -> Promise`，且"第一个参数只接受一个字符串类型的代码包路径"，
  **没有** `Module`/`Instance` 构造器、也没有流式版本；iOS 上还不支持导出 `Global`。
  开发者工具里的表现就是那句看不出层次的报错：
  `[wasm=instantiate-failed/WXWebAssembly detail=WebAssembly.instantiate: first argument must be a string]`
  ——宿主把我们的字节数组转发给它那份路径型实现，报的是"必须是字符串"。
  修法与配套守卫（三层都要，少一层就会再次"本机全绿、工具里起不来"）：
  1. `wasm-bridge.js` 排两条通道并**跟着宿主能力定优先级**：宿主是 `WXWebAssembly` 时先走
     `path-instantiate`（异步），字节通道只作为有 `Module`/`Instance` 的宿主的兜底。
     `imports` 拿不到是这里的真正难点（它是胶水闭包私有的）——做法是临时把全局 `WebAssembly`
     换成一个 shim，丢弃胶水传给 `instantiate` 的第一参数、把第二参数（胶水自己造好的 imports）
     原样转发给宿主，宿主返回的 `{module, instance}` 再交回胶水的 `__wbg_finalize_init`。
     顺带省掉把 2.3 MB wasm 读进 JS 堆。
  2. `loadWasmCoreOnce()` 因此返回 **Promise**，`start()` 必须把 boot 排在它之后
     （`wasmReady → loadGameFont() → boot()`）——路径通道天生异步，同步挂载这个假设不成立。
  3. **harness 复刻宿主的受限形态**：以前它写的是 `globalThis.WXWebAssembly = globalThis.WebAssembly`
     （完整能力面），等于用一条真机上不存在的通道验证成功。现在它只给
     `instantiate(path, imports)`（按代码包根解析路径，非字符串入参按宿主的方式拒绝），
     并断言实际通道必须是 `path-instantiate`（证据行 `wasm=ok:ok:path-instantiate`）。
  4. **发布前剔除 Export 段的 Global 条目（必须与胶水里的读取补丁成对）**：当前 wasm-bindgen 会把
     `__abort_handler`/`__instance_terminated` 两条内部 global 塞进 Export 段，而 iOS 的
     WXWebAssembly 不支持 Global 导出（带 Global 的模块整块被拒）。
     `scripts/wasm-lua/strip-wasm-globals.mjs` 从 Export 段按 `kind=3` 过滤重写（Global 段本身留着，
     模块仍自洽），`scripts/package.ps1` 在微信分支的 `wasm-opt -Oz` 之后就地跑一遍；
     `verify-wasm-host.mjs --platform=wechat-minigame` 兜底：Export 段里若还有 Global，发布失败。
     **本项当时的口径是错的，2026-10-03 纠正**：这里曾写"实测 JS 胶水完全不引用它们
     （`__wbg_call_guard` 一条也没落进 `game_web.js`）"——那是那版胶水的形状。当前 wasm-bindgen 给
     **每个导出函数**开头都插了 `__wbg_call_guard()`，它无条件读 `wasm.__instance_terminated.value / 4`。
     于是"剔掉死导出"变成"剔掉一个有人读的导出"：微信包在实例化成功（111 项导出）之后的
     **第一次跨 wasm 调用**就抛 `TypeError: Cannot read properties of undefined (reading 'value')`，
     表现为 `hostApi=error:…` + `boot=failed` + 一帧不跑（本机 harness 实测，与 iOS 无关）。
     修法成对：`package.ps1` 的微信分支在构建期把那句改成
     `if (!wasm.__instance_terminated) return; <原句>`——global 缺席时守卫直接跳过。它答的是
     "实例已终止就别再调了"，读不到标记时本来也无从判断；同份胶水的 abort hook 自己就包在
     `try/catch` 里，可见 wasm-bindgen 也把这类读取当可选路径。**剔除步骤与守卫补丁只留一个就是死包**，
     补丁写法变了会响亮失败（与 `script_src`、`module.exports` 两条同一套构建期补丁）。
     本机端到端复测（2026-10-03，同时带着 Lua 注释剥离的发布包）：
     `wasm=ok:ok:path-instantiate`、`boot=running`、120 帧 `drawn=4720`、运行时清单 684 条逐条对上。
  仍然证明不了的：前导斜杠容忍度、`.wasm.br`——本产物 Export 段的 Global 已剔除，
  iOS WXWebAssembly 那条已知硬约束不再触发；但**真机是否对别的 aspect 仍有 Global 依赖**
  只能等 iOS 真机跑一次才算完（R1 同一口径）。
  失败信息现在带 `attempts`（每条通道/每个路径写法的原始原因），屏幕与 `console.error` 都有。
* **R13 胶水在**求值期**就要标准 `WebAssembly` 域名（2026-10-03 开发者工具实测，已修）**：R12 落地后
  工具里报的是 `[wasm=glue-missing/WXWebAssembly detail=WebAssembly is not defined]`。这句话是撒谎的：
  `pkg/game_web.js` 就在包里（本次产物 52,225 字节），死的是 `require` 胶水那一步。真正的原因在
  `--target no-modules` 产物把 JS 异常桥的 tag 放在了 IIFE **顶层**求值：
  `const __wbindgen_jstag_polyfill = new WebAssembly.Tag({ parameters: ['externref'] });`
  这两条 tag 同时是 wasm 的**导入**（复现：
  `node -e "const fs=require('fs');const m=new WebAssembly.Module(fs.readFileSync('…/game_web_bg.wasm'));const im=WebAssembly.Module.imports(m);console.log(im.length, im.filter(i=>i.kind==='tag').map(i=>i.name))"`
  ⇒ 56 条导入 = 54 function + 2 tag，名字 `__wbindgen_jstag` / `__wbindgen_wrapped_jstag`）。
  小游戏宿主只注入 `WXWebAssembly` 域名、没有标准全局，而 `wasm-bridge.js` 原先只在**实例化阶段**
  才碰 `WebAssembly`（路径通道的 shim），require 胶水时读的是空气 → ReferenceError → 被判成
  `glue-missing`。本机 Node 有真全局，所以缺口在本机永远不响——与 R12 同一类"本机全绿、工具里起不来"。
  修的是四层，缺一层就会再漏一次：
  1. `wasm-bridge.js` 在 `requireGlue` **之前**装标准域名 facade，**只转发宿主真有的构造器**
     （`GLUE_EVAL_CTORS` = Tag/Exception/Memory/Table/Global）。tag 是 wasm 的导入，伪造一个 JS 对象
     会在 instantiate 时被宿主拒，所以 `WXWebAssembly` 没有 `Tag` 时直接判
     `webassembly-api-incomplete`，detail 带 `facade missing=…｜host keys=…｜求值期全局读数
     （WebAssembly/TextEncoder/TextDecoder 各 present/absent）`——不再冒充成"发布形态问题"。
     路径通道的 shim 现在转发整张构造器表：`__wbg_finalize_init` 会跑 `wasm.__wbindgen_start()`，
     Rust 侧一抛 JS 异常就进 `wrapError` → `new WebAssembly.Exception(...)`，那时读的正是这个被换掉的全局。
  2. 标准域名的来源进证据：`__RUSTLUA_DIAG().wasm.facade`（转发时是构造器清单，宿主自带时是
     `host-standard`）。
  3. **harness 复刻这个宿主形态**：假 `WXWebAssembly` 给出 `Tag`/`Exception`（V8 真实现，
     摘全局之前抓下来），装完之后 `delete globalThis.WebAssembly`；判据钉两条——通道必须
     `path-instantiate`、facade 必须是转发的而不是 `host-standard`。当前本机端到端读数：
     `wasm=ok:ok:path-instantiate:Tag+Exception+Memory+Table+Global`、`boot=running`、60 帧 `drawn=4720`。
  4. 发布期漂移守卫：`scripts/package.ps1` 微信分支扫胶水里的 `WebAssembly.<名字>`，任一不在
     "facade 转发的 + 通道逻辑覆盖的"清单里就**发布失败**（当前产物读数：
     `used=Exception,Instance,instantiate,instantiateStreaming,Module,Tag`、`uncovered=` 空）。
  **开发者工具这一份的域名实面已测到（2026-10-03，修完 facade 之后的第二轮读数）**：
  `[wasm=webassembly-api-incomplete/WXWebAssembly detail=… facade missing=Tag,Exception
  ｜host keys=Global,Instance,Memory,Module,Table,compile,instantiate
  ｜WebAssembly=absent TextEncoder=present TextDecoder=present]`
  两条结论：① 工具的 `WXWebAssembly` **没有** `Tag`/`Exception`，所以 facade 在这份宿主上救不了
  求值期那一行 `new WebAssembly.Tag(...)`；② R12 那句"官方 API 面里 `WXWebAssembly` 只有
  `instantiate`"在开发者工具上**偏保守**——它其实还有 `compile`/`Module`/`Instance`/`Memory`/`Table`/
  `Global`（没有 `instantiateStreaming`）。这不改变通道优先级（路径通道仍是首选，顺带省掉 2.3 MB
  进 JS 堆），但"字节通道在微信上根本不存在"这句口径要改成"可能存在，只是被 tag 这条更硬的限制盖住"。
  为了让下一次启动**自己**给出分叉判据，facade 缺 `Tag` 时曾计划再问一句宿主 `compile(代码包路径)`
  并把结果写进同一行 detail（`probe=compile-ok` / `probe=compile-fail`，带 3 秒超时）。

  是 `.txt`、另两个是 `.toml`）：
  `manifest.txt=ok@mainpack project.toml=FAIL settings.toml=FAIL` → 障碍只在后缀（本方案即充分）；
  `manifest.txt=FAIL` → 嵌套目录也被限制，需要改形态（把首屏资源打成白名单后缀的单个容器，
  运行时在内存解出）。**首次在真机上跑通之前，这一条要一直记着。**
* **R8 开发者工具开着时发布会被"另一个程序正在使用此文件"顶掉（实测踩到）**：只要微信开发者工具
  导入过该产物，`wxfilewatcher_x64.exe` 就会**递归监视发布根并持有目录句柄**，
  于是原子交换里 `Move-Item` 把旧 `launcher/` 挪到 `.backup-*` 这一步失败（Windows 不允许移动
  被持有句柄的目录），发布以 `release swap failed (old release restored at …)` 收场——
  报错文案指向"文件被占用"，与代码/产物问题长得一模一样。
  **判据**：`[IO.Directory]::Move` 改名发布目录失败，而逐个文件都能独占打开 → 是目录句柄被占用。
  **出路**：发布前关掉开发者工具，或在另一个发布名/目录下发布后再导入。
  注意 `release-atomic.ps1` 的回滚用的是 `-ErrorAction SilentlyContinue`，恢复失败也会打印
  "old release restored"——那句话说出口时并没有被校验过（既有实现，本次未改）。
