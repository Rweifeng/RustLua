# 微信小游戏分包发布（主包 + 单分包）

本文定义微信小游戏的**默认发布形态**：主包 + 单分包。它是
[docs/51 平台插件适配](51-平台插件适配.md) 里"微信小游戏特有约束"一节的展开，
并被 [docs/34 质量门与发布清单](34-质量门与发布清单.md) 的微信两条用例引用。

## 1. 为什么换形态

之前的默认形态是**瘦首包 + CDN 远端回落**：主包只留 ~391 KB 骨架，4 MB 重资源上传 CDN。
这条路能跑通，但代价是三个**发布前必须办完的外部前提**：

| 前提 | 代价 |
|---|---|
| 公网 HTTPS 服务器 | 有成本，且是运行时依赖（服务器挂了游戏就进不去玩法） |
| ICP 备案 | 国内域名必须备案才能上线 |
| 公众平台 `downloadFile` 域名白名单 | 漏配一项就是"真机贴图全丢"，而本机测不出来 |

分包形态把这三点一次性去掉：

* **零服务器、零备案、零域名白名单**：资源随代码包上传，微信自带 CDN 分发；
* **分包下载后落在本地沙箱**，运行时是本地文件读取，比走 HTTPS 回源快；
* **版本统一**：一次上传、一次审核，不存在"CDN 上是旧资源、包内是新代码"的不一致。

## 2. 微信规则（决定了整个设计的形状）

1. **`subpackages[i].root` 目录下的文件全部进分包，主包里一个都不能留。**
   所以"主包保留启动场景及其贴图"**不能**表现为"在 `pack/` 里留一部分"——留在 `pack/` 里的
   首屏资源在真机上仍然属于分包、仍然要等下载。主包侧首屏资源必须放**兄弟目录 `mainpack/`**。
2. **`root` 目录下必须有 `game.js`，它是分包入口文件，挂载后会被宿主执行**（不只是存在性占位）。
   缺了开发者工具报「未找到 `["subpackages"][0]["root"]` 对应的 `/pack/game.js` 文件」并拒绝打开工程
   ——这正是历史上取消分包的直接原因。
3. 上限：主包 ≤ 4 MB、**单个普通分包不限制大小**、总计 ≤ 20 MB（官方《分包加载》2023-10 起；
   开通虚拟支付的小游戏可到 30 MB，本脚本按无内购口径保守取 20 MB）。
4. 资源路径由 `plugins/webgl/web-runtime.js` 硬编码为 `'pack/' + path`，而这份运行时**由
   webgl 与微信两个平台共用同一份**（刻意的，防止游戏逻辑各自漂移）。因此分包形态
   **不改 `web-runtime.js`**：所有路由都落在适配层（`plugins/wechat-minigame/wechat-adapter.js`）。
5. **代码包只上传后缀在白名单内的文件**（官方《代码包》文档，69 个后缀）。`lua` / `toml` / `md`
   都不在白名单里 → 传不上去 → 真机上读它是 `permission denied`。构建期按此改名，见 R9。
6. **`*.js` 与 `game.json` 会被编译**，上传后无法用 `FileSystemManager` 直接读
   （`require` 走的是编译产物，那是另一条通道）→ 适配层不得把它们当运行期判据，见 R9b。

## 3. 产物形态

```powershell
# 默认形态就是分包；零额外参数、零外部依赖
powershell -NoProfile -File scripts\package.ps1 -Platform wechat-minigame -SelfTest
```

```
examples\<game>\builds\wechat-minigame\<PublishName>\
└── launcher\                 # 代码包：整目录一次上传微信
    ├── game.js               # 主包入口
    ├── game.json             # 含 subpackages: [{ name: "pack", root: "pack" }]
    ├── code-package.json     # 改名映射：逻辑路径 → 会随代码包上传的宿主文件名（R9）
    ├── mainpack.json         # 首屏清单（构建/运行时/harness 三方共用的路由依据）
    ├── mainpack\             # 首屏资源：在**主包**里，启动即用
    │   ├── manifest.txt / chars.txt（原名）/ project.toml.txt / settings.toml.txt（按白名单改名）
    │   ├── scripts\**        # 全部 Lua（require 是同步的，无法懒加载）；逐个改名为 *.lua.txt
    │   ├── assets\fonts\**   # 子集字体（boot 之前就要用）
    │   ├── assets\art\title\** + assets\art\ui\** + 启动场景引用的贴图
    │   └── scenes\main.scene
    └── pack\                 # 分包 root（有 game.js 入口）
        ├── game.js           # 分包入口（发布脚本生成，挂载后由宿主执行）
        ├── assets\**         # 音频 + 非首屏贴图
        └── scenes\**         # 除启动场景外的场景
```

### 三种资源形态

| 形态 | `-AssetPack` | 主包 | 资源位置 | 外部前提 |
|---|---|---|---|---|
| **分包（默认）** | `subpackage` | ≤ 4 MB | 首屏 `mainpack/`，其余 `pack/` 分包 | **无** |
| 瘦首包 | `remote` | ≤ 4 MB | `pack/` 只剩骨架，重资源在 CDN | HTTPS + 备案 + 域名白名单 |
| 全量随包 | `full` | ≤ 4 MB | 整个 `pack/` 都在主包 | 无（但本工程 4.4 MB 必然超限） |

三者**互斥**：`subpackage` 与 `-RemotePackBaseUrl` / `-CdnPackDir` 相互拒绝。两套资源来源同时存在
只会让"包内读到了"掩盖"分包根本没挂载上"。

## 4. 切分机制：首屏清单

切分的唯一依据是 `scripts/first-screen-pack.js` 从 `pack/` 的**实际磁盘内容**推导出的
`mainpack.json`（零依赖 Node，不写死工程名或目录层级）。

```powershell
node scripts/first-screen-pack.js examples\game_jhyt\builds\wechat-minigame\launcher\pack --json
# first_screen_pack_ok entries=178 bytes=1098178 startup=scenes/main.scene scripts=89 textures=7 fonts=1 scenes=8 warnings=0
```

* **种子**（缺一启动即失败）：`manifest.txt` / `project.toml` / `settings.toml` / `chars.txt`；
  `project.toml` 声明的 `startup_scene` 与 `main_script`；全部 `scripts/**`；全部 `assets/fonts/**`。
* **`scripts/` 与 `fonts/` 必须全部进主包**，这不是保守而是硬约束：`web-runtime.js` 启动时遍历
  manifest 把所有 `scripts/**.lua` 塞进 `package.preload`，而 Lua 的 `require` 是**同步**的、
  无法懒加载；`loadGameFont` 也在 boot **之前**执行。
* **场景贴图闭包**：解析 `startup_scene` 的 `texture=` 与 `clip:` 引用。引用了但**不在**
  manifest 里 → 其出现在启动场景中即**致命退出（码 1）**；只出现在别的场景里则只警告。
* **保守前缀**：默认把 `assets/art/ui/**` 全量纳入（启动场景的一部分 UI 由 `main.lua` 通过
  `ui.*` 运行时绘制，静态推不出来；该目录约 55 KB，属"便宜且必要"的过度包含）。
* **拒绝项**：`game.js` 一律不得入清单——它与分包入口 `pack/game.js`、主包入口 `game.js` 三重同名，
  且 `subpackage-relative` 方言会把 `pack/game.js` 读成主包入口。
* **退出码**：`0` 通过 / `1` 清单不可靠 / `3` 未找到 pack 根。

### 反直觉但正确的推论

**首屏清单越大，分包越安全。** 两者此消彼长，而被 4 MB 卡住的是**分包**那一侧（主包只用了 37%）。
所以清单「宁可多列、不可漏列」的保守性原则与体积上限方向一致。

### 切分是真搬运，不是复制

发布脚本按清单 `Move-Item` 到 `mainpack/`（保持同构相对路径），并立刻断言：

* **搬运守恒**：`mainpack/` 的文件数与字节数 == 清单条目数与字节和；
* **整体守恒**：`mainpack/` + 裁完的 `pack/` == 切分前的 `pack/`（文件数与字节数都要对得上）；
* **两侧互斥**：清单项必须在 `mainpack/` 下存在、且在 `pack/` 下**不存在**。

漏列的文件会被路由到分包，而首屏读分包在挂载前是读不到的——症状是标题一片
`Image.onerror`。上面的断言把这种漏列挡在**发布期**，而不是等真机白屏。

## 5. 运行时路由

适配层是唯一知道"某个逻辑路径该从主包还是从分包读"的地方。实现是**主体 × 方言**两层正交组合：

* **主体**（`mainpack/` 还是 `pack/`）是**包内布局**属性，由 `mainpack.json` 静态决定：
  清单内 → `mainpack/<x>`，清单外 → `pack/<x>`；不回落（清单项构建期已被搬走，
  在 `pack/` 再找一次只会把"切分没搬干净"掩盖成"分包还没挂载"）。
* **方言**（根相对 / 前导斜杠 / `./` 前缀 / 分包根相对…）是**宿主**属性，5 条候选逐个试、记住成功的。
  主体里的**文件名**还要再套一层改名映射（`hostFileFor`，R9）：`scripts/main.lua` 在真机上叫
  `main.lua.txt`。映射对两个主体用同一张表、同一个键域（pack 相对逻辑路径）。
  注意 **`user-data` 那条方言必须作用在逻辑路径上**：改名只存在于代码包里，而用户目录缓存的键
  与远端 URL 都按逻辑路径算——两者混用会让"下载成功了却永远读不到"（瘦首包形态实测踩到）。

**必须这样拆**：把 `mainpack/` 当成策略表里的一条别名，在 `slash` / `sub-root` 这类宿主上会被拼成
`/mainpack/...` 或 `mainpack/...` 而读不到——两个正交的维度必须正交地组合。
方言记忆按**主体**分键（`mainpack/` 与 `game.json` 同级共用 `main` 键，`pack/` 单独一键），
因为 `sub-root` 形态下这两类路径的合法形式**真的不同**（实测
`read_strategies=main:root-relative/pack:subpackage-relative`）。

其余关键行为：

* **首屏不等分包**：`fetchShim` 对清单内路径直接读主包，不等 `loadSubpackage`；`start()` 里分包
  是**后台发起、不 await** 的，boot 立即用主包资源渲染标题。
* **非首屏等分包**：清单外的 `fetch` 先 `await ensurePack()`；`Image.src` 是同步通道，
  未挂载时**延迟到分包结算再交给宿主**（先交一个读不到的路径，宿主立刻 `onerror`，
  而运行时的 `loadImage` 以第一次 `onerror` 为准，之后补挂载也救不回来）。
* **失败降级而非掀翻启动**：`ensurePack()` 永不 reject。失败走三重可见通道——
  `console.error` + `data-rustlua-pack=failed` + 画布红横幅；同时有 10 秒重试冷却
  （否则每次 `pack/` 读取都会重新下一次包 = 重试风暴），以及 20 秒兜底超时
  （宿主既不 `success` 也不 `fail` 时不能让等待它的读取永远悬着）。
* **进度条**：微信端**没有** loading UI（`statusElement` 是个 no-op 对象），分包却是几十 MB 量级的
  下载。适配层消费 `onProgressUpdate` 并自绘进度条，每帧的 z 序固定为
  `loadingBar → failureBand → packFailure → drawOverlay`；`boot=failed` 时不画进度条
  （那一刻整屏属于启动错误页）。

## 7. 验收

```bash
# 1) 清单工具（不需要重新构建：现有导出资源包就是一份完整 pack/）
node scripts/first-screen-pack.js <...>/launcher/pack --json
# 期望：first_screen_pack_ok entries=178 bytes=1098178 startup=scenes/main.scene scripts=89 textures=7 fonts=1 scenes=8 renamed=91 warnings=0

# 2) 发布 + 隔离自测（隔离副本里逐条复核切分，再跑一次完整验收）
powershell -NoProfile -File scripts\package.ps1 -Platform wechat-minigame -SelfTest
# 期望：wechat_minigame_split_ok mainpack_files=178 …
#       已按白名单改名 91 个文件；code_package_whitelist_ok dirs=2 (rules_verified_on=2026-09-16/2.32.3)
#       wechat_minigame_package_ok files=11 … asset_pack=subpackage split=mainpack+pack
#       Directory-isolation self test passed (WeChat launcher + runtime OK; asset_pack=subpackage)

# 3) 平台验收（布局 + 配额 + 全部用例）
powershell -NoProfile -File scripts\verify-wechat-minigame.ps1 -BundleRoot <...>\launcher
# 期望：wechat_minigame_static_ok main=1,534KB subpackage=3,011KB total=4,545KB subpackages=pack asset_pack=subpackage upload_rules=ok …
#       wechat_minigame_package_ok … asset_pack=subpackage … subpackage_case=ok,delay,delay-move,never,fail-once
```

分包专属的 5 条 harness 用例（`--subpackage …`）：

| 用例 | 钉住的事实 |
|---|---|
| `ok` | 声明有且仅有 1 个 `root=pack`；入口 `pack/game.js` 存在且可被 `require` |
| `delay --subpackage-delay-frames 6` | 首屏不等分包（启动完成时分包尚未挂载）；进度条消费了进度并画到画布上 |
| `delay + --drive-new-game --drive-move` | 进 manor（非首屏）才需要分包，且世界里主角真的在走 |
| `never --expect-pack-failure` | 分包永远挂不上时首屏照常启动 + 失败三重可见 + 无未处理 Promise 拒绝 |
| `fail-once --drive-new-game` | 首次失败后冷却重试能自愈（冷却经存储注入压到 0） |

`--subpackage auto|off|ok|never|delay|fail-once` 与 `--wx-path-style` 是**正交的两轴**：
前者是"分包挂载行为"（宿主侧强制），后者是"路径方言"。4 档方言用例在分包形态下都额外带
`--subpackage ok`，否则"哪一档方言配哪一种分包行为"说不清、用例之间会互相掩盖。

## 8. 风险与已知边界

* **R1 开发者工具 vs 本机（最高）**：harness 是 Node 伪造 `wx`，**无法模拟微信 IDE 的打包器**。
  "root 目录整体进分包"这条规则是方案的支点，本机证明不了。缓解：切成 `mainpack/` 兄弟目录后，
  两种可能的打包语义**都**能得到正确产物；验收脚本的"清单项在 `pack/` 下不得存在"断言
  把本机产物形态锁死。**首次在开发者工具里必须核对「详情 → 代码包大小」面板的主包/分包两块
  数值与输出行一致**，并真机跑一次「标题 → 开始新游戏」。
* **R2 分包余量**：预计 73.5%，安全。真正会顶到墙上的是"清单过小（< 300 KB）"或资源总量增长。
  杠杆按优先级：① 把资源列进清单（清单变大反而更安全）→ ② 拆第二个分包 → ③ `-AssetPack remote`。
* **R3 `pack/game.js` 三重同名**：分包入口 / 主包入口 `game.js` / `subpackage-relative` 方言把它读成
  `game.js`。缓解：清单工具拒绝把 `game.js` 列进清单；`probePackReadability` 继续不拿它当探针
  （分包形态下这一点更强：它现在**真的存在**，误读会更隐蔽）。
* **R4 分包不可用**：标题照常显示（首屏全在主包），进玩法场景失败，但**失败是响的**。
* **R5 音频接入（已落地，MP3 统一格式）**：微信小游戏音频后端已接入 `plugins/webgl/web-runtime.js`
  （`installLuaAudioBridge` → `wx.createInnerAudioContext`，Lua 侧 `audio.play_on/music/stop_music/`
  `set_bus_volume/volume` 全部走真实播放）。格式策略：**统一 MP3**——InnerAudioContext 官方格式矩阵里
  MP3 在 iOS 和 Android **均支持**（ogg 仅 Android 支持、wav 体积过大），因此源文件直接使用 `.mp3`
  （96kbps、22050Hz、单声道），运行时不再做格式转换或备用格式生成。`assets/audio/**` 从
  "OGG+WAV 双格式各占一半体积"（6.9 MB）缩减为"单一 MP3 格式"（1.5 MB），分包体积省约 5.4 MB。
  文件不存在时返回 false（游戏侧静默降级）。
* **R11 wasm 核心即 Lua 执行层（2026-09-30 起，取代此前"只到装进来为止"）**：微信分支现在
  构建 `--target no-modules` 胶水 + wasm 核心，适配层实例化后把 6 个 `lua_*` 桥导出挂到
  `window.__RUSTLUA_LUA_BRIDGE`，`web-runtime.js` 的全部 Lua 交互经它完成——**游戏逻辑真的在 wasm 里跑**
  （实测 `wasm=ok:ok`、`boot=running`、进 manor 后 33 实体、主角随摇杆位移）。
  由此带来两条硬约束：
  1. **wasm 必须用 rustc 1.88（LLVM 18）构建，两个 web 平台都是**。此前 `package.ps1` 只给
     webgl 用 1.88、给微信留默认 toolchain，理由是"WXWebAssembly 对混合 EH 的接受度沿用阶段二
     发布基线"——那个前提来自 42 KB 的旧 wasm（只有 `start`/`memory`）。换成 mlua 之后，1.97 产物
     **在 wasm-opt 之前**就被本机 V8 拒绝（`Invalid opcode 0x1f`，错误落在 mlua 的函数里），
     症状却只有一句 `wasm lua bridge not loaded` + 0 帧。发布链路现在强制跑
     `node scripts/wasm-lua/verify-wasm-host.mjs <wasm>`，加载不了就直接失败。
  2. **没有 wasm 就没有 Lua**：fengari 时代"wasm 失败不影响 Lua 启动（clock 走 Lua 兜底、boot
     照常成功）"的降级契约已不存在。`--no-wasm` 用例现在要求的是**响亮失败**：
     `boot=failed` + 拒绝原因指名 wasm 桥 + 控制台有启动失败行 + 诊断 `no-webassembly`。
  体积口径随之改变：核心从 42 KB 涨到 **2,371 KB**（1.88 未优化 3,150 KB，`wasm-opt -Oz` 后
  2,428 KB；binaryen 133 **会保留**纯 try_table，实测产物仍可被 V8 加载），
  主包因此从文档旧基线 40.1% 涨到 **96.5%（3,954 KB / 4,096 KB）**，只剩约 140 KB 余量。
  短期杠杆：terser 压缩 `web-runtime.js`(133 KB) + `wechat-adapter.js`(143 KB)，约回收 180 KB。
  两个压缩工具（`wasm-opt`、terser）现在由 `scripts/minify-toolchain.ps1` **按需取到
  `engine\.tools\`**（仓库只留脚本、不留二进制）：binaryen 锁 **`version_133`**——非 133 的 pass
  可能把纯 `try_table` 改回 legacy `try`，所以解析时按 `wasm-opt --version` 复核、版本不符就当没找到，
  下载还带一份写死在脚本里的官方 sha256。两者缺席时 `package.ps1` 只警告不阻断，但**主包体积门会
  阻断**：实测 2026-10-01 因两者未安装产出的主包 4,660 KB > 4,096 KB。
  两者就位后**同一份代码**实测：`wasm-opt -Oz` 出 **2,679 KB**（未优化 3,150 KB；再加
  `--converge`、`--strip-debug/--strip-producers` 一共只多省 4 KB，binaryen 这边已经见底），
  terser 后 `web-runtime.js` 100 KB、`wechat-adapter.js` 63 KB，**主包 4,143 KB**——比上面的旧基线
  3,954 KB 还高，因为核心 wasm 比那个口径大了约 250 KB。缺的 47 KB 出在**编译期**而不是压缩期：
  workspace 的 release profile 是 `opt-level = "s"`，`package.ps1` 现在只给 wasm 构建临时覆盖成
  `"z"`（`CARGO_PROFILE_RELEASE_OPT_LEVEL`，pc/editor 不受影响），同一份代码 `-Oz` 后
  **2,853,068 → 2,424,558 字节（省 418 KB）**，`wasm_host_ok … exports=121 globals=0
  bridge_exports=7` 照旧，主包落到 **3,843 KB / 4,096 KB（93.8%）**（2026-10-01 实测）。
  主包构成：wasm 2,368 KB + `mainpack/` 首屏资源 1,211 KB + 两个 JS 163 KB + 入口/配置。
  再往下要腾空间只剩内容侧的三条路：瘦首屏清单（非启动必需的条目挪回分包）、字体子集
  （247 KB）再小、或 `-AssetPack remote` 把整包资源搬出代码包。
  `start_wechat()` 在 Rust 侧保留为**备选直启路径**，发布链路走的是 `lua_boot_with_reader` 桥。
  构建期还有两处**必需**的胶水补丁（`script_src` 那句在小游戏里必抛错、no-modules 只有顶层
  `let` 不是 `module.exports`），都在 `scripts/package.ps1` 里并且**写法变了会响亮失败**。
* **R12 `WXWebAssembly` 只认代码包路径（2026-09-30 开发者工具实测，已修）**：R11 之后 wasm 就是
  Lua 执行层，而桥接层当时用的是**字节通道**（`readBytes` → 胶水 `initSync(bytes)` →
  `new WebAssembly.Module(bytes)`）。官方 API 面里 `WXWebAssembly` 只有
  `instantiate(path, imports) -> Promise`，且"第一个参数只接受一个字符串类型的代码包路径"，
  **没有** `Module`/`Instance` 构造器、也没有流式版本；iOS 上还不支持导出 `Global`。
  开发者工具里的表现就是那句看不出层次的报错：
  `[wasm=instantiate-failed/WXWebAssembly detail=WebAssembly.instantiate: first argument must be a string]`
  ——宿主把我们的字节数组转发给它那份路径型实现，报的是"必须是字符串"。
  修法与配套守卫（三层都要，少一层就会再次"本机全绿、工具里起不来"）：
  1. `wasm-bridge.js` 排两条通道并**跟着宿主能力定优先级**：宿主是 `WXWebAssembly` 时先走
     `path-instantiate`（异步），字节通道只作为有 `Module`/`Instance` 的宿主的兜底。
     `imports` 拿不到是这里的真正难点（它是胶水闭包私有的）——做法是临时把全局 `WebAssembly`
     换成一个 shim，丢弃胶水传给 `instantiate` 的第一参数、把第二参数（胶水自己造好的 imports）
     原样转发给宿主，宿主返回的 `{module, instance}` 再交回胶水的 `__wbg_finalize_init`。
     顺带省掉把 2.3 MB wasm 读进 JS 堆。
  2. `loadWasmCoreOnce()` 因此返回 **Promise**，`start()` 必须把 boot 排在它之后
     （`wasmReady → loadGameFont() → boot()`）——路径通道天生异步，同步挂载这个假设不成立。
  3. **harness 复刻宿主的受限形态**：以前它写的是 `globalThis.WXWebAssembly = globalThis.WebAssembly`
     （完整能力面），等于用一条真机上不存在的通道验证成功。现在它只给
     `instantiate(path, imports)`（按代码包根解析路径，非字符串入参按宿主的方式拒绝），
     并断言实际通道必须是 `path-instantiate`（证据行 `wasm=ok:ok:path-instantiate`）。
  4. **发布前剔除 Export 段的 Global 条目**：当前 wasm-bindgen 会把
     `__abort_handler`/`__instance_terminated` 两条内部 global 塞进 Export 段，实测 JS 胶水
     完全不引用（`__wbg_call_guard` 一条也没落进 `game_web.js`）。iOS 的 WXWebAssembly 不支持
     Global 导出，这两条是"死导出但会撞硬约束"。新增 `scripts/wasm-lua/strip-wasm-globals.mjs`
     从 Export 段按 `kind=3` 过滤重写（Global 段本身留着，模块仍自洽），`scripts/package.ps1`
     在微信分支的 `wasm-opt -Oz` 之后就地跑一遍；`verify-wasm-host.mjs --platform=wechat-minigame`
     兜底：Export 段里若还有 Global，发布失败。本机 harness 端到端实测：剥掉 2 条 global 之后
     `wasm=ok:ok:path-instantiate`、boot=running、场景切换正常（`[lua] 切换场景: manor 实体 33`）。
  仍然证明不了的：前导斜杠容忍度、`.wasm.br`——本产物 Export 段的 Global 已剔除，
  iOS WXWebAssembly 那条已知硬约束不再触发；但**真机是否对别的 aspect 仍有 Global 依赖**
  只能等 iOS 真机跑一次才算完（R1 同一口径）。
  失败信息现在带 `attempts`（每条通道/每个路径写法的原始原因），屏幕与 `console.error` 都有。
* **R6 文档过时项（既有隐患，本次未修）**：
  [docs/32-webgl-浏览器平台验收.md](32-webgl-浏览器平台验收.md) 里"缺 17 个宿主 API / boot=failed"
  的描述已与当前工作区不符（实测 `boot=running`、`drawn=15820`）；且那条 "missing host API" 诊断
  分支因 `hostCompat` 先填代理而**已是死代码**，`missingCount` 恒为 0，所以它的"绿灯"是假的。
  **不得**据此声称"宿主 API 已补齐"。
* **R7 `full` 形态对本工程不可用**：4,507 KB 顶死 4 MB。发布脚本会在超限时明确报错并给出
  `subpackage` / `remote` 两条出路，而不是发出一个传不上去的包。
* **R9 代码包只上传白名单后缀的文件（真机实测，已修）**：官方《代码包》文档规定，只有后缀在
  白名单内的文件会被上传（69 个：`png/json/txt/scene/ttf/wav/js/wasm/zip/...`）。
  **`lua` / `toml` / `md` 不在白名单里** → 传不上去 → 真机上 `readFileSync` 得到 `permission denied`
  （文件在项目里、但不在上传结果里）。本游戏的全部 Lua 逻辑都靠逐文件读取，于是真机启动直接失败：
  `pack/project.toml HTTP 404` → `rustluaRunLuaGame` 抛错 → 启动失败。**这不是回归，是从未在真机上
  验证过的前提被推翻**（过去的 remote/full 形态的 `pack/project.toml` 也是 `.toml`，同样传不上去）。
  修法：构建期把名称追加 `.txt`（`x.lua` → `x.lua.txt`，末位后缀入白名单、原名可追溯），
  映射落在产物根的 `code-package.json`；**运行时只查表、不重算规则**。
  规则与白名单收在 [scripts/code-package-rules.js](../scripts/code-package-rules.js)，
  构建期（`first-screen-pack.js` / `package.ps1`）、无头验证（harness）共用同一份。
  实测：需要改名的是 91 个文件（88 个 `scripts/**.lua` + `scripts/README.md` + `project.toml`
  + `settings.toml`），**分包 `pack/` 里一个都不需要**（音频/贴图/场景的后缀全在白名单内），
  所以改名不动分包、也不动 CDN 导出路径。
* **R9b 适配层不得依赖 `game.json`（同一个坑的另一半，已修 + 已加回归守卫）**：真机上
  `readFileSync('game.json')` 也**一律失败**——因为**规则 ②**：`*.js` 与 `game.json` 会被**编译**，
  上传后无法直接访问。而"`pack/` 是不是分包"原本**只看** `game.json`，于是分包形态会在真机上
  **静默退化**：判成"没声明分包" → 一次 `wx.loadSubpackage` 都不调 → `pack/` 永远读不到，
  且屏幕上**任何提示都没有**（失败通道只挂在"挂载失败"上，这里根本没去挂载；
  `diag` 里 `declared=true` 而 `attempted=false` 就是它的指纹）。现在判据是首屏清单自己的
  `layout.subpackage_root`。守卫：harness 的 `--expect-no-read game.json`（**要求一次都没读过它**）。
* **R10 无头验证必须模拟真机的上传规则（本轮最大的教训，已修）**：harness 的假 `wx` 以前
  **直接从磁盘读**，于是"真机上根本不存在的文件"在本机全部读得到——91 个文件的问题一路全绿，
  直到真机启动失败。现在 harness **默认常开**这套模型：先按磁盘算出"会被上传且读得到"的文件集合
  （后缀在白名单内 且 不是被编译的 `*.js`/`game.json`，再减去产物里 `project.config.json` 的
  `packOptions.ignore`），此后所有代码包路径的读取都必须落在这个集合内，否则按真机语义拒绝
  （**不在集合但磁盘上有 → `permission denied`；磁盘上也没有 → `not found`**——两种报错分开，
  与实测日志一致；早期把两者混成一句 `no such file or directory`，正是它掩盖了根因）。
  集合用**精确大小写**的相对路径匹配，因为 Windows 的 `fs.existsSync` 不区分大小写而真机区分。
  另外 `wx.loadFont` 现在真去读文件并校验 TTF 魔数（以前直接返回常量，字体读不到也永远绿）。
  **反证**：拿改名前的旧产物跑一次，harness 报出的正是真机那句 `pack/project.toml HTTP 404`
  外加"91 个文件后缀不在白名单内"，与现场一致。
* **R10b 已知的观测边界**：真机日志里 `mainpack/project.toml` 是 `permission denied` 而
  `mainpack.json` 读得到，这两条**同时变了两个变量**（目录 + 后缀），所以**不能**据此断定
  "障碍只在后缀"。白名单是官方文档事实（改名是**必需**的），但**嵌套目录本身是否也被限制**
  仍未证。判据在适配层启动自检那一行（分包形态下三个探针都路由到 `mainpack/`，其中 `manifest.txt`
  是 `.txt`、另两个是 `.toml`）：
  `manifest.txt=ok@mainpack project.toml=FAIL settings.toml=FAIL` → 障碍只在后缀（本方案即充分）；
  `manifest.txt=FAIL` → 嵌套目录也被限制，需要改形态（把首屏资源打成白名单后缀的单个容器，
  运行时在内存解出）。**首次在真机上跑通之前，这一条要一直记着。**
* **R8 开发者工具开着时发布会被"另一个程序正在使用此文件"顶掉（实测踩到）**：只要微信开发者工具
  导入过该产物，`wxfilewatcher_x64.exe` 就会**递归监视发布根并持有目录句柄**，
  于是原子交换里 `Move-Item` 把旧 `launcher/` 挪到 `.backup-*` 这一步失败（Windows 不允许移动
  被持有句柄的目录），发布以 `release swap failed (old release restored at …)` 收场——
  报错文案指向"文件被占用"，与代码/产物问题长得一模一样。
  **判据**：`[IO.Directory]::Move` 改名发布目录失败，而逐个文件都能独占打开 → 是目录句柄被占用。
  **出路**：发布前关掉开发者工具，或在另一个发布名/目录下发布后再导入。
  注意 `release-atomic.ps1` 的回滚用的是 `-ErrorAction SilentlyContinue`，恢复失败也会打印
  "old release restored"——那句话说出口时并没有被校验过（既有实现，本次未改）。
