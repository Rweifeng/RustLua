# AI 驱动 Rust + Lua 游戏引擎开发实施计划

> 项目依据：`E:\Codex\p2\docs\AI驱动RustLua游戏引擎实施计划.md`
>
> 版本：2026-08-20
>
> 目标：在独立开发者主要负责目标确认与结果验收、AI 负责调研、设计、编码、测试、文档和迭代的工作模式下，完成一个 Windows 优先、Rust 引擎核心、Lua 游戏脚本、2D 优先并逐步支持轻量 3D 的可发布游戏引擎和样板游戏。

## 0. 执行总则

### 0.1 项目不是“先做引擎，再做游戏”

采用“双轨交付”：

```text
引擎能力轨：核心运行时、渲染、资源、编辑器、脚本、工具链
游戏验证轨：用一款小型 2D 游戏持续验证引擎是否真的可用
```

任何引擎功能必须至少绑定一个游戏需求、一个可运行 Demo 和一项验收标准。没有实际用户场景的功能不进入当前版本。

### 0.2 AI 的主要职责

AI 负责：

- 阅读现有计划、代码和文档；
- 查询官方文档和依赖 API；
- 设计模块、接口和数据结构；
- 创建和修改代码；
- 编写单元测试、集成测试和示例；
- 执行格式检查、静态检查、测试和构建；
- 分析错误日志和性能数据；
- 维护技术决策、变更记录和用户文档；
- 在每个里程碑生成验收报告。

独立开发者负责：

- 确认游戏方向和优先级；
- 接受或拒绝技术方案；
- 提供无法由 AI 自动获得的美术、声音、产品和发行决策；
- 在需要视觉判断时检查实际窗口、编辑器和游戏画面；
- 进行最终里程碑验收。

### 0.3 AI 不得自行做出的高风险变更

以下操作必须先说明影响，再等待确认：

- 删除或覆盖用户资产；
- 修改项目整体技术路线；
- 更换核心图形 API、脚本 VM 或 ECS；
- 大规模重写公共 API；
- 升级可能破坏兼容性的依赖；
- 修改场景格式且没有迁移方案；
- 引入网络、在线服务、商业 SDK 或许可证风险；
- 进行不可逆的 Git、文件和发布操作。

### 0.4 单任务原则

每个实施条目必须满足：

- 可由 AI 在一次或几次连续工作中完成；
- 有明确输入和输出；
- 修改范围可预测；
- 可以独立测试；
- 有明确验收命令或验收动作；
- 不同时跨越多个未稳定模块。

建议单任务规模：0.5–2 个工作日，最多不超过 5 个工作日。超过范围必须拆分。

## 1. 版本、里程碑与完成定义

### 1.1 版本路线

| 版本 | 目标 | 预计 AI 实施周期 |
|---|---|---:|
| M0 | 项目基线和 AI 协作规范 | 1 周 |
| M1 | 窗口、wgpu、Lua、日志和固定时间步 | 2 周 |
| M2 | ECS、实体句柄、事件和调度器 | 4 周 |
| M3 | 2D 渲染、纹理、精灵和摄像机 | 6 周 |
| M4 | 场景、资源库、序列化和 Lua 游戏 API | 8 周 |
| M5 | 编辑器 MVP | 10 周 |
| M6 | 2D 游戏完整能力和样板游戏 | 12–16 周 |
| M7 | 打包、性能、质量和发布 | 6–8 周 |
| M8 | 轻量 3D | 12–20 周 |

时间是工作量参考，不是硬性日历承诺。任何阶段都以验收门为准，而不是以日期强行结束。

### 1.2 Definition of Ready：任务开始条件

任务只有满足以下条件才能开始：

- 已有任务编号和目标；
- 已说明涉及模块；
- 已说明不包含的内容；
- 已写出验收标准；
- 已确定测试方式；
- 已确认依赖和风险；
- 已确认使用的 API 版本。

### 1.3 Definition of Done：任务完成条件

每个任务完成时必须具备：

- 代码实现；
- 必要的单元测试或集成测试；
- `cargo fmt --check` 通过；
- `cargo clippy` 无新增高优先级问题；
- 相关 Demo 可以运行；
- 文档或 API 示例已更新；
- 已记录已知限制；
- 已生成验收证据；
- 未破坏已有里程碑。

### 1.4 里程碑通过条件

里程碑必须同时满足：

1. 功能验收通过；
2. 回归测试通过；
3. Debug 构建通过；
4. Release 构建通过；
5. 文档完整；
6. 至少一个可运行 Demo；
7. 已知问题已分级；
8. 用户确认继续下一阶段。

### 2.1 任务文件格式

每个任务使用一个 Markdown 文件，例如：

```text
tasks/active/M1-03-lua-bridge.md
```

内容固定为：

```markdown
# M1-03 Lua Bridge

## 目标

## 背景

## 修改范围

```

### 2.2 任务状态

```text
BACKLOG -> READY -> IN_PROGRESS -> REVIEW -> ACCEPTED
                                  └-> REWORK
                                  └-> BLOCKED
```

状态含义：

- `BACKLOG`：只有需求；
- `READY`：可以交给 AI 执行；
- `IN_PROGRESS`：AI 正在实现；
- `REVIEW`：代码和测试完成，等待验收；
- `ACCEPTED`：验收通过；
- `REWORK`：未通过，需要带着失败证据修复；
- `BLOCKED`：存在外部阻塞，不允许用猜测掩盖。

## 3. AI 协作工作流

### 3.1 每个任务的标准流程

```text
1. 读取项目总计划和相关任务
2. 检查当前工作区和已有实现
3. 查询官方文档/锁定版本 API
4. 输出简短实施方案
5. 修改代码
6. 添加测试和 Demo
7. 执行格式、静态检查、测试、构建
8. 分析失败并修复
9. 更新文档和任务状态
10. 生成验收报告
```

### 3.2 AI 每次开始工作时必须先回答

- 当前项目版本是什么？
- 本任务要解决什么用户问题？
- 哪些模块会被修改？
- 哪些行为不会改变？
- 如何证明任务完成？
- 如果失败，最小回退点在哪里？

### 3.3 AI 每次交付时必须报告

```text
已完成：
- ...

修改文件：
- ...

验证结果：
- 格式检查：通过/失败
- 静态检查：通过/失败
- 单元测试：通过/失败
- 集成测试：通过/失败
- Debug 构建：通过/失败
- Release 构建：通过/失败
- 手工/视觉验收：通过/待验收

已知问题：
- ...

建议下一步：
- ...
```

### 3.4 失败处理规则

- 第一次失败：读取错误、定位原因、修复；
- 第二次失败：缩小问题范围，创建最小复现；
- 第三次仍失败：停止继续堆代码，提交阻塞报告；
- 不允许删除测试来“修复”失败；
- 不允许通过放宽验收标准来“通过”；
- 不允许在未理解生命周期的情况下增加 `unsafe`、全局变量或线程锁。

# 5. 具体实施条目与验收方案

## M0：项目基线

### M0-01 项目章程与范围锁定

实施内容：

- 创建 `docs/00-project-charter.md`；
- 写明目标平台、目标用户、第一款游戏类型；
- 固定第一版不做事项；
- 写明性能目标、目录结构和版本策略；
- 建立决策变更流程。

验收：

- 章程包含目标、非目标、成功标准、风险和里程碑；
- 任意新需求都能判断属于当前版本或延期；
- AI 能根据章程拒绝范围外需求。

### M0-02 Cargo workspace 基线

实施内容：

- 创建 `engine` workspace；
- 创建 `engine_core`、`game_runner`、`examples`；
- 配置 Debug/Release；
- 固定 Rust toolchain；
- 添加基础依赖并记录版本。

验收命令：

```powershell
cargo metadata --no-deps
cargo fmt --all -- --check
cargo test --workspace
cargo build --workspace
cargo build --workspace --release
```

通过标准：全部命令返回 0，且干净目录可以按 README 重建。

### M0-03 质量门和自动化检查

实施内容：

- 添加格式检查；
- 添加 Clippy；
- 添加单元测试和集成测试入口；
- 添加最小 CI 配置；
- 规定提交前检查清单。

验收：

- 故意引入格式错误能够被检查发现；
- 故意让测试失败能够阻止通过；
- CI 或本地脚本能输出清晰失败原因。

### M0-04 文档和任务系统

实施内容：

- 建立任务模板；
- 建立验收矩阵；
- 建立风险登记表；
- 建立技术决策记录；
- 建立每个里程碑的报告模板。

验收：

- 新任务可以在 5 分钟内按模板创建；
- 每个任务至少具备目标、范围、验收、测试和风险字段。

### M0-05 最小 Demo 规范

实施内容：

定义所有 Demo 必须包含：

- 启动方式；
- 输入方式；
- 预期画面/行为；
- 退出方式；
- 日志位置；
- 验收截图或录屏位置。

验收：

- 一个陌生 AI 会话只看 Demo README 就能运行和验证 Demo。

## M1：基础运行时

### M1-01 窗口与应用生命周期

实施内容：

- 创建窗口；
- 处理关闭、最小化、恢复和缩放；
- 定义初始化、运行、暂停、退出状态；
- 处理窗口大小为 0 的情况。

验收：

- 窗口正常启动和关闭；
- 拖动缩放不崩溃；
- 最小化后恢复画面正确；
- 关闭窗口后进程退出；
- 生命周期日志顺序正确。

### M1-02 wgpu 初始化与清屏

实施内容：

- 创建 Instance、Adapter、Device、Queue、Surface；
- 配置 Surface；
- 处理 SurfaceLost、Outdated、Timeout、OutOfMemory；
- 实现清屏。

验收：

- Debug/Release 均能清屏；
- 调整窗口尺寸后仍能渲染；
- 设备初始化失败时输出可理解错误；
- 无未处理 panic。

### M1-03 Lua VM 桥接

实施内容：

- 接入 `mlua`；
- 创建和销毁 Lua VM；
- 注册 `log.info`、`time.delta`、`app.quit`；
- 加载项目脚本；
- 将 Lua 错误转换为项目错误。

验收：

- Lua 可调用 Rust API；
- Rust 可调用 Lua 函数；
- 语法错误包含文件名和行号；
- 脚本错误不会让引擎无日志退出；
- VM 退出后无资源泄漏报告。

### M1-04 日志与错误系统

实施内容：

- 配置 `tracing`；
- 区分 engine、editor、game、script、asset 日志；
- 实现文件日志和控制台日志；
- 为错误补充上下文。

验收：

- 可以按模块过滤日志；
- 每条错误包含时间、模块、上下文；
- Lua、资源和渲染错误可分别检索；
- 关键错误有用户可理解的解决建议。

### M1-05 固定时间步

实施内容：

- 逻辑更新默认 60Hz；
- 渲染使用实际帧率；
- 设置最大补偿步数；
- 防止螺旋死亡；
- 输出 dt、accumulator 和跳步统计。

验收：

- 低帧率时逻辑不会无限追赶；
- 同样输入和相同初始状态下，逻辑结果可重复；
- 暂停/恢复行为明确；
- 时间统计可在控制台查看。

### M1-06 输入快照

实施内容：

- 键盘、鼠标、窗口事件；
- 按下、持续、释放三类状态；
- 逻辑层读取快照而非直接读取平台事件；
- 预留手柄抽象。

验收：

- WASD、空格、鼠标点击可验证；
- 快速按键不会丢失释放状态；
- 游戏暂停时输入策略符合文档；
- Lua 可读取动作和轴值。

### M1-07 基础性能埋点与性能 overlay

实施内容：

- 帧耗时；
- 固定更新耗时；
- Lua 调用耗时；
- 系统耗时；
- 实体数和资源数；
- Debug overlay。

验收：

- 运行时能显示 FPS、Frame ms、Update ms；
- 每项统计来源清晰；
- 开关关闭后对 Release 性能影响可接受；
- 有一份基准记录。

## M2：ECS 与核心数据

### M2-01 EntityId 和 generation 句柄

验收：

- 删除实体后旧句柄访问失败；
- 新实体不会误用旧句柄；
- 句柄可以序列化和日志化；
- 100 万次创建/销毁测试通过。

### M2-02 World 与组件存储

实施内容：

- 创建/销毁实体；
- 添加、读取、修改和删除组件；
- 查询组件组合；
- 明确借用边界。

验收：

- Transform/Velocity 查询可运行；
- 组件缺失有明确结果；
- 删除实体不会残留组件；
- 组件查询测试和基准测试通过。

### M2-03 系统调度器

实施内容：

- 系统注册；
- 明确执行顺序；
- 阶段：Input、Script、Physics、Animation、Transform、Render；
- 记录依赖和耗时。

验收：

- 系统顺序符合设计；
- 循环依赖能报错；
- 系统 panic 或错误有模块信息；
- 10000 实体场景可稳定运行。

### M2-04 Command 与事件队列

实施内容：


- 资源导入测试；
- 场景序列化往返测试；
- 旧版本迁移测试；
- Lua API 测试；
- EntityId 失效句柄测试；
- ECS 创建/销毁压力测试；
- 发布包启动测试；
- 关键 Demo smoke test。

### 6.3 手工和视觉验收

AI 可以生成测试步骤和截图，但以下内容必须查看实际结果：

- 窗口是否正确显示；
- 精灵、文本、UI 是否变形或错位；
- 编辑器布局是否可用；
- Gizmo 是否跟随选择对象；
- Play/Stop 是否符合预期；
- 热重载是否造成明显状态污染；
- 发布包是否能正常启动和游玩。

每次手工验收保存：

```text
artifacts/screenshots/<milestone>/<task>.png
artifacts/logs/<milestone>/<task>.log
artifacts/builds/<milestone>/...
```

### 6.4 验收矩阵

建立 `docs/04-acceptance-matrix.md`，每行至少包含：

| 字段 | 内容 |
|---|---|
| ID | 例如 M3-02-A01 |
| 功能 | 精灵透明混合 |
| 前置条件 | 资源已导入 |
| 操作 | 运行 Demo，加载纹理 |
| 预期结果 | 透明区域不显示黑底 |
| 自动化测试 | 测试名或命令 |
| 手工证据 | 截图/录屏路径 |
| 状态 | PASS/FAIL/BLOCKED |
| 版本 | 通过时的版本号 |

### 6.5 Bug 分级

- P0：无法启动、数据损坏、发布包不可运行；立即修复；
- P1：核心玩法或核心编辑流程不可用；当前里程碑必须修复；
- P2：重要功能异常但有替代方案；排入近期任务；
- P3：体验、性能或文档问题；按时间处理。

任何 P0/P1 未解决时，不得通过里程碑。

# 8. AI 自主开发的质量控制

## 8.1 代码质量红线

禁止：

- 为了通过编译删除功能；
- 为了通过测试修改测试预期；
- 用 `unwrap`/`expect` 掩盖用户可触发错误；
- 通过全局单例解决所有模块通信；
- 未记录原因就新增 `unsafe`；
- 未经测试引入多线程；
- 将路径字符串作为唯一资源引用；
- 让 Lua 直接修改 Rust 内部存储；
- 一次性生成无法审查的大型重构。

允许但必须说明：

- 原型阶段的临时代码；
- 为第三方 API 编写的适配层；
- 性能测试中的特殊数据结构；
- 经过安全不变量说明的 `unsafe`；
- 暂不完整的占位模块。

## 8.2 每日 AI 工作循环

```text
读取状态 -> 选择一个任务 -> 方案 -> 实现 -> 测试
-> 失败修复 -> 文档 -> 生成证据 -> 更新状态
```

每天结束时生成：

- 今日完成；
- 测试结果；
- 剩余问题；
- 下一任务；
- 是否有需要用户决策的事项。

## 8.3 每周 AI 工作循环

## 8.4 每月里程碑审查

审查问题：

1. 引擎是否更接近第一款游戏？
2. 是否引入了不必要的抽象？
3. 哪些模块需要冻结 API？
4. 哪些功能应该删除或延期？
5. 是否出现性能、内存或资源泄漏趋势？
6. AI 是否反复修改同一个模块却没有解决根因？

# 12. 项目完成的客观判断

项目达到以下条件，才可称为“第一版完成”：

1. 不依赖 AI 临时记忆，新的 AI 会话只读取项目文档即可继续；
2. 引擎有稳定的运行时、资源、场景和脚本边界；
3. 编辑器至少能完成创建、修改、保存和运行场景；
4. Lua 能完成完整游戏玩法；
5. 有自动化检查、回归测试和性能基线；
6. 有可以独立运行的 Release 游戏包；
7. 有完整文档和已知问题清单；
8. 第一款样板游戏能够被实际玩通。

> AI 负责提高执行速度，但不能替代验收标准。每一个“完成”都必须由代码、测试、运行结果、日志或截图证明。
