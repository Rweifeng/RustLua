边界规则（docs/55 §4.1）的当前状态：

1. **View 只发 typed action**：`EditorCommand` 有唯一编排点 `EditorApp::dispatch`。已迁移：快捷键（Ctrl+S/Z/Y/D）、工具栏 Play/Stop、菜单保存、Hierarchy 右键菜单的创建/删除/移动到根节点。剩余：Inspector 属性提交、Scene View 拖拽落点与 Gizmo 提交仍在面板内直接调用既有方法（见 §5）。
2. **持久数据修改经 `CommandService`**：`EditorApp.history` 已是 `CommandService`，撤销预算在其中强制生效。
3. **选择唯一事实源**：`EditorApp.selection` 已是 `SelectionService`；Hierarchy/Scene/Inspector 共享同一实例。
4. **预览资源归 `PreviewService`**：未变（既有 `PreviewSession` 继续独占 GPU/readback/字体资源）。
5. **后台任务只返回不可变结果**：资源刷新已完全满足；缩略图 worker 既有实现不变。
6. **稳定 ID**：未变（`AssetId`/`SceneEntityId` 既有设计）。
7. **取消/失败/恢复/telemetry 契约**：`CancellationToken`+`JobError`+`JobReport` 已定义并被刷新任务使用。

### 1.1 性能止血（阶段 1 明确项）

| 阶段 1 要求 | 落地方式 |
|---|---|
| 后台资源刷新/校验 | 递归扫描、`ResourceDatabase` 协调、依赖重算、DB 落盘全部移出 UI 线程；UI 线程只做「发起」与「提交」，代际号保证旧结果不覆盖新结果 |

| Hierarchy 搜索热点 | 过滤匹配改为一次遍历的 `HierarchyMatchIndex`（O(n)，哈希表 O(1) 查询）+ 按修订缓存的小写化名称表（`HierarchyNameCache`）；改过滤词不再重算 10k 个名字，命中计数复用同一次遍历 |
| Console 有界 + **虚拟滚动** | 行存储有界（Lua 输出 10k / 通知 500 / `LogSink` 500）；新增 `ConsoleRowCache` 行索引（按分类/过滤/级别/来源代数失效）+ 固定行高 16 px `show_rows`，只绘制视口内的行；多行输出按物理行拆行以保持固定行高 |
| Inspector dirty 驱动 | 既有 E08 直写 + 提交点收敛机制保持（本次未改动其语义） |
| 历史内存预算 | 撤销条目上限 200，超出丢弃最旧并计入 `dropped_entries`，暴露到 HUD 与 profiler gauge |
| Editor Profiler | 帧 p50/p95/p99 + 超预算帧数、面板耗时、命令耗时（含 `dispatch`）、扫描/导入队列、缓存命中率（`hierarchy_cache_hit/miss`、`console_index_cache_hit/miss`）、实际绘制行数（`hierarchy_rows_drawn`）、`console_rows_indexed`、历史深度等 gauge |

结论（对照 docs/55 §3.2 预算）：

- **10k 实体 Hierarchy 的"扁平化"本身不是瓶颈**（Release p95 1.1 ms，缓存命中 2 µs）；
- **10k 实体面板每帧只绘制 26 行**（视口 720 px / 22 px 行高），Release 面板帧耗时 p95 0.22 ms、
  Debug p95 2.9 ms —— 相对"最低 30 FPS（33 ms）"的门槛有一个数量级余量，且这是**无窗口真实
  egui 帧**测出来的，不是估算；
- **10 万行日志的控制台面板帧 p95 0.48 ms**（Release）：存储有界（保留 1 万行）+ 行索引按
  来源代数/过滤/级别缓存，稳态 30 帧内 0 次重建，因此"滚动/过滤不冻结主线程"是结构性成立的；
- **10k 实体按名搜索 P95 2.46 ms**（预算 100 ms，达标；比优化前 14.16 ms 快 5.8×）：
  一次遍历的匹配索引 + 按修订缓存的小写化名称表；
- **撤销/重做单步 Release p95 < 1 ms**，100 步往返内容逐字段一致；
- **资源扫描已彻底离开 UI 线程**：发起 0.034 ms，worker 侧 2k 文件约 75 ms；
- **外部文件变化 2 秒内被反映**（docs/55 §3.2 预算 2000 ms）：实测端到端 **225 ms**，
  其中 UI 线程每帧只付一次 `try_recv`（p95 **0.0001 ms**），2k 文件的元数据扫描（worker 侧 p95 8 ms）完全不在主线程；
- **长会话内存有界**：日志 100k→保留 1 万行、`LogSink` 100k→保留 500 行、历史 500 编辑→保留 200 条。

### 3.1 漂移门抓到的问题（真实缺陷，已修）

组件 schema 是"逐字段"的，写错就会在真实内容上暴露。本轮三道门（编码器对拍 / 再序列化 / 真实工程审计）
一共抓出 3 个问题，全部已修：

| # | 问题 | 谁抓到 | 修法 |
|---|---|---|---|
| 1 | `Sprite.sorting_layer` / `Quad.layer` 被当成整数，实际是**分层名字符串**（`default`/`world`/`actor`） | 引擎编码器对拍门 | 字段类型改 `Text`，并在 schema 注释里写明由 `sorting_layer_rank` 解析 |
| 2 | `FieldKind::Size`（`宽x高`）经 `serialize` 后变成 `128,128`，再解析失败 | 「解析→序列化→解析」稳定性检查 | `ComponentSchema::serialize` 改为**按字段类型**编码（`Size` 写回 `x`），并补 `serialize_values` 作为无 schema 的兼容入口 |
3 | `Sprite.pivot`/`order` 被标为 required，而**仓库里的真实旧场景没有这两个字段**（解析器取默认值） | 真实工程审计（`examples/game_jhyt`） | 改为可选；这条正是 docs/55「旧项目可无损打开」的前置条件 |

另外两条与 Prefab 逐字段覆盖相关的**语义收紧**（不是缺陷，而是把"整串覆盖"升级为"逐字段覆盖"后必然变化的契约）：

- `diff_prefab_entity` 现在对**有 schema 的组件**输出 `property:<Component>.<field>` 而不是 `component:<Component>`；
  未注册组件、组件新增/删除仍走整串覆盖。两个既有测试相应更新（它们原本断言整串覆盖）。
- 覆盖值取**实例字段的原始文本**（`read_field_text`），因此"保留 77"不会把它写成 `77.000000`；
  Apply 因此变成幂等操作（同一覆盖重复应用结果完全一致），这条由 `property_overrides_rewrite_one_field_only` 锁定。

### 3.4 Schema 驱动 Inspector 过程中抓出的问题（第 12 轮，全部已修/已钉住）

**A. `CommandService::default()` 的 Undo 预算是 0（真实缺陷，已修）**

`CommandService` 原本 `#[derive(Default)]`，派生值 `max_entries = 0`，而 `enforce_budget()`
会照此在**每次编辑后把整条历史丢光**——"默认构造 = 没有 Undo"。生产路径用的是
`CommandService::new(DEFAULT_MAX_ENTRIES)`，所以此前没人碰到；这正是新基线场景
`schema_field_edit_1k` 的报告行把它暴露出来的（`budget=0` 与 `undo_entries=200` 自相矛盾）。

修法：手写 `impl Default`（= `new(DEFAULT_MAX_ENTRIES)`），并加单测
`default_command_service_keeps_the_documented_undo_budget` 钉住这个陷阱。

**B. 数字字段按"字段类型"归一化，与各引擎编码器的精度不同（行为记录，非缺陷）**

schema 写路径（`FieldValue::to_component_value`）把数字写成 `{:.6}`，而引擎各组件编码器各写各的
（`QuadComponent` 写 `size={},{}` → `128,64`；`SpriteComponent` 写 `tint={:.3}`）。
因此**被编辑过的那个字段**文本会变成 6 位小数（`size=128.000000,64.000000`），语义与解析完全等价，
且"归一化后的文本再提交一次"仍是**无变化**（幂等，不会持续增长历史）。
影响面：编辑过的场景文件在该字段上会有一段"精度样式"变化，直到引擎再次保存整串。

不改的理由：schema 层刻意只保证**类型级**契约（漂移门比对的是解析后的语义，不是逐字节文本），
强行让 schema 输出等于每个编码器的私有精度不可行；Prefab 覆盖路径同样依赖这条契约。
证据：`editing_writes_one_field_and_leaves_the_rest_byte_identical` 明确断言
"只有被编辑的字段变、其余字段逐字节不变"与"归一化后再提交 = 无变化"。

**C. 组件串本身不满足 schema 时，报错不能指向用户正在改的字段（已修）**

逐字段写入要先整串解析以比较当前值，因此缺必填字段的旧串会以
`字段 center 取值非法：required field is missing` 冒出来——用户改的是 `zoom`，
这条消息会把人带到错误的字段上。新增 `SchemaFieldError::PayloadUnparsable`，
把这类问题翻译成"组件 X 的现有串无法按 schema 解析（字段 Y：…）；请先用整串修正后再按字段编辑"，
由 `unparsable_payload_is_reported_as_a_payload_problem` 锁定。

**D. 测试写法上的一个坑（记录给后续写测试的人）**

`Undo` 命令会先走帧末收敛边界（`finish_inspector_edits_if_dirty`）。测试里如果**从不调用**
`sync_inspector`，Inspector 缓冲与文档不一致，这条边界会先把"从未同步过的缓冲"提交成一条历史，
于是单次 `Undo` 撤销的是那条而不是被测的字段编辑（现象：`status=Undo: Inspector`）。
真实 UI 每帧都会同步，所以这不是产品缺陷；测试里必须像 UI 一样先 `sync_inspector`。

### 3.5 实体级脚本组件有**三个名字**（真实缺陷，已修；第 13 轮）

发现过程：为了给"缺 schema 的组件"补 schema，我先把运行时真正读取的组件名列了一遍
（`Select-String 'components\.(get|contains_key|remove)\("…"'`）。结果运行时读的是 `Script`：

| 位置 | 用的名字 | 载荷形式 |
|---|---|---|
| 运行时 `core::script` + 场景加载器 `typed_scene` | `Script` | `file=scripts/x.lua` |
| 编辑器 Inspector（`inspector_state::set_lua_script`） | `LuaScript` | **裸路径** `scripts/x.lua` |
| 引擎 schema 注册表 | `EntityScript` | `file=…` |

后果：**在 Inspector 里给实体填了 Lua 路径，运行时永远不会加载它**（运行时只找 `Script`，
而没有任何迁移代码把 `LuaScript` 翻译过去）；同时 schema 描述的是一个没人消费的组件名，
真实场景里的 `Script` 反而会被审计报成"没有 schema"。

修法（一处权威名字 + 一条迁移 + 三个守卫测试）：

1. **唯一权威名字**：引擎新增 `core::entity_script::SCRIPT_COMPONENT = "Script"`，
   运行时读取点（`core/script.rs`）改用它；schema 注册表的键也从 `EntityScript` 改成
   `SCRIPT_COMPONENT`（字段表重命名 `SCRIPT_FIELDS`）。
2. **迁移**：新增 `core::component_migration`（幂等、不写盘、不猜）：
   `LuaScript`（裸路径**或** `file=` 形式）→ `Script` + `file=<路径>`；
   新组件已在场时保留新值、丢弃旧键（`conflicts`）；旧负载解析不出来则**原样保留**
   （`untouched`，绝不为了报告好看而丢数据）。与 `scene_migration`（空间迁移，会写盘/备份）
   分工明确。
3. **编辑器**：`SceneDocument::open` 统一做迁移；发生过迁移就**标记未保存**并在状态栏说明
   ——独立游戏读的是场景文件，不保存等于运行时仍看不到脚本。Inspector 的 Lua 输入现在写
   `Script` + `file=`，显示仍是裸路径（用户关心的是文件）。
4. **守卫**：
   - `component_schema::script_schema_uses_the_runtime_component_name`：schema 键 == 运行时常量、
     旧键名不得复活、引擎编码器输出可解析；
   - `typed_scene::script_component_name_matches_the_shared_constant`：加载器认得这个名字；
   - `component_migration::migrated_scene_compiles_into_the_runtime_component_set`：
     旧场景 → 迁移 → 加载器真的编成 `ComponentId::Script`（把"改名"和"运行时读得到"连起来）。

诚实边界：`examples/game_jhyt` 以及仓库里**任何** `.scene/.prefab/.widget` 数据文件都不含
`LuaScript`（命中 0），所以这条修复的"真实工程证据"同样不存在——证据是引擎/编辑器测试 +
新的基线场景 `legacy_script_migration_1k`。

顺带记录（不是缺陷）：`ComponentSchema::serialize` 按字段名字典序输出（`ComponentData` 是
`BTreeMap`），与引擎编码器的书写顺序不同（`Script` 是 `file=…;enabled=false`，schema 写
`enabled=false;file=…`）。该函数目前**没有任何生产消费者**（只有漂移门与守卫测试用它），
编辑器写字段走的是 `property_path::write_field` 的"最小改动"路径，因此不会重排组件串。

### 3.6 字段级语义规则（第 14 轮）：把"类型正确但语义错"的洞堵上

第 12/13 轮反复记录过同一个缺口：`FieldKind::Text` 只表示"任意文本"，于是
`Script.file`（必须落在工程根内）这类规则只存在于编辑器的输入校验与引擎解析器里，
schema 与审计表达不了。本轮把规则**声明式**地放进 schema：

- 新增 `FieldRule{ NonEmpty, ProjectPath{ extensions }, NonNegative }` +
  `FieldSchema::with_rules(...)`/`describe()`；规则是纯数据（无闭包），
  `FieldSchema` 仍是 `const`/`Eq`，schema 表照旧是静态常量表。
- 校验顺序固定"先类型、后语义"：类型错报到类型上，语义错报到规则上；错误信息同时被
  引擎审计、`property_path::write_field` 与通用字段编辑器复用。
- `Script.file` 挂上 `NonEmpty + ProjectPath{extensions: &[]}`——**刻意不限扩展名**：
  运行时是 `root.join(file)` 后直接当 Lua 源码编译，`.lua` 只是**编辑器输入层**的项目约定
  （更严）。两边差异写进了两侧测试，避免"以为一样"。

**过程中抓到的真实缺陷**：我在实现 `ProjectPath` 时先用 `Path::is_absolute()` 判定绝对路径，
结果 schema **放行** `/etc/passwd`——Windows 上根相对路径没有盘符，`is_absolute()` 返回 `false`。
这正是"同一规则两处实现"的典型后果：引擎原来用的是组件式检查（`RootDir | ParentDir | Prefix`），
编辑器用的也是有同样洞的 `is_absolute() + 手写 .. 扫描`。修法：
把判定收敛到 `core::paths::{is_absolute_path, escapes_project_root}`（带自己的单测），
`EntityScript::validate` 与 schema 规则**共用同一份实现**，编辑器也改为复用引擎校验器。
反漂移守卫：`field_rules_match_engine_validators` 对 10 组样本逐条断言
"引擎解析器与 schema 规则的接受/拒绝完全一致"，`paths` 自己的单测覆盖 Windows 根相对形式。

同类"假样本"清理：漂移门原来用 `EntityScript::default().to_component_str()`（= `file=` 空路径）
当 `Script` 的样本，而引擎自己的解析器根本不接受它——换成合法载荷，否则门在自欺。

### 3.8 Scene Interaction 首批接线（第 16 轮，docs/55 `ER-07`）

### 3.10 菜单栏按 Unity 结构重组（第 18 轮）

原来只有「项目 / 编辑 / 视图 / 帮助」四个自造菜单，条目散落在 `header.rs` 的 170 行内联代码里。

- [`MENU_BAR`] 声明表：顶级菜单顺序、子菜单、条目、快捷键提示、可用条件（`MenuGate`）；

### 3.14 我自己造成的第二起编码事故：`verify.ps1` 的 BOM 被剥掉（第 21 轮，已修 + 已加门）

**现象**：本轮按需求给 `scripts/verify.ps1` 追加"审计第二个示例工程"的步骤（用文件编辑工具），
之后用 PowerShell 解析该脚本时，它在**中文注释处**报一串语法错误
（`意外的标记"-NoProfile"`、"字符串缺少终止符"…）——也就是说**整条质量门脚本当时无法运行**。

**根因**：脚本在 git 里是 **UTF-8 with BOM**；文件编辑工具写回的是 **UTF-8 without BOM**。
Windows PowerShell 5.1 在中文区域设置下按 ANSI 读**无 BOM** 的 `.ps1`，中文注释被误解码 → 解析失败。
逐字节对比确认：`HEAD` 版本前三字节 `EF BB BF`，改动后的工作区版本是 `[Cm`（BOM 已丢）。
这与第 11 轮那次"PowerShell 文本 cmdlet 改源码"是同一类事故（**编码**），但这次是**工具默认行为**造成的，
而且受害文件是质量门本身——比业务代码坏了更危险。

**修法**：

1. 用 .NET 读写（`ReadAllText` + `WriteAllText(..., UTF8Encoding($true))`）把 BOM 补回去，
   内容逐字节不变（改前先确认正文是合法 UTF-8：解析**文本**通过、解析**文件**失败，即编码而非内容问题）；
2. 逐个核对 `scripts/*.ps1` 的 BOM 状态与 `HEAD` 是否一致 —— 只有 `verify.ps1` 被剥掉，其余 14 个正常；
3. **加机械化守卫**：`scripts/check-docs.ps1` 新增第 ⑦ 项检查——`scripts/*.ps1` 必须带 UTF-8 BOM，
   缺一个就判红并说明后果。负向对照已验证：临时剥掉 `run-demo.ps1` 的 BOM →
   `[RED] check_docs_failed issues=1`（指到具体文件）、退出码 1；补回后 `check_docs_ok ... ps1_bom_ok=15`。
4. 同一轮确认 `verify.ps1` 重新可解析（`verify_parses_ok`）。

**教训（追加到项目约定）**：改 `.ps1` 之后必须确认 BOM 还在；文件工具不会保留它。
现在这条由 `check-docs.ps1` 盯着，不再依赖人记得。

### 3.15 第三个迁走的组件 `Image` + 迁移"卡点清单"（第 22 轮）

**1）`Image` 迁移**（同一份样板）：删掉 `ImageFields` + `set_image`/`clear_image` +
`encode/decode/validate_image` + 快照字段 + `EditorApp.image` 字段 + 面板（含"九宫格四条边框"
与"移除 Image"按钮所在的那一整块）。迁移后由通用编辑器生成：`texture` 文本框、**`color` 取色器**
（比手写的 3 个 DragValue 更好用）、`nine_slice` 四个 DragValue。

**2）迁移前必须先补的一条规则能力：向量非负。** `Image` 的两个既有测试暴露了手写面板比 schema
更严的地方——旧 `validate_image` 拒绝负的九宫格边框。为此把 `FieldRule::NonNegative` 从"标量"
扩展到**向量要求每个分量非负**，并挂到 `Image.nine_slice` 上，于是**审计也获得了这条校验**
（原来只有编辑器拦）。同时用真实数据确认了"全零 = 省略"这一等价性：
渲染侧是 `image.nine_slice.filter(|s| s.iter().any(|v| *v > 0.0))`，全零与省略都回退单四边形，
所以通用编辑器把 `nine_slice=0,0,0,0` 写出来**语义无变化**（引擎再保存时会自然收敛回省略）。

**3）刻意更严的分歧要写进测试**：引擎解析器**接受** `nine_slice=-1,0,0,0`（渲染侧会过滤掉它），
schema 拒绝它。这与 `Script.file` 的 `.lua` 约定是同一类"编辑器比运行时严"的分歧，
在 `field_rules_match_engine_validators` 里用一段显式注释 + 三行断言写清楚，避免以后有人
"顺手对齐"把编辑器守卫删掉。

**4）迁移卡点清单（诚实边界，也是下一步的输入）**：接下来要迁的组件各缺一样 schema 表达能力，
所以**没有**在本轮硬迁——迁了就是体验或校验降级：

| 组件 | 缺的能力 | 具体表现 |
|---|---|---|
| `Camera3D` | **显示单位** | 面板 FOV 用**角度**，组件串存**弧度**；通用编辑器只会显示弧度。另外面板还带"姿态来自 Transform3D""已禁用"等说明与只读投影摘要 |
| `WorldText` / `Text` | **动态选项源** | 字体是下拉框（项目可用字体列表），schema 只能给文本框 |
| `Sprite` / `Transform` / `Transform3D` / `UiLayout` | 字段多 + 面板有复合语义 | 例如 Transform 的等比锁、UiLayout 的锚点/预设、Sprite 的纹理下拉 |
| `Collider3d` / `Tilemap` / `Animation` / `Container` / `UiEvents` / `UiBindings` / `ButtonStates` / `UiAnimation` | **没有 schema** | 先补 schema 才能谈迁移 |

也就是说：迁移这三轮（Light/MeshRenderer/Image）已经把"控件级等价"打通；
**下一层要补的是"字段元数据"**——显示单位、动态选项源、以及"零值等于省略"这类格式约定。

### 3.16 字段元数据层 + 第四个迁移组件 `WorldText` + 暂停按钮图标（第 23 轮）

**1）字段元数据层：显示单位与动态选项源。** 上一轮把迁移卡点归成两类，本轮先补上：

- `FieldUnit { Raw, Degrees }`：`Camera3D.fov` 在编辑器里用**角度**显示与输入，写回组件串时
  换算成**弧度**（`to_display`/`from_display` 一对纯函数，往返精度有测试）。组件串格式一个字没改。
- `ChoiceSource { Static, ProjectFonts }`：`font` 字段的候选来自**项目字体列表**
  （`project_font_paths()`），不是 schema 的静态 choices；通用编辑器因此画出与手写面板同款的下拉
  （"默认字体（不指定）" + 项目字体路径）。
- 两者都挂在 `SchemaFieldRow` 上由编辑器消费；`hint` 会自动带上单位说明
  （如 `number（编辑器用角度，组件串存弧度）`）。

放在编辑器而不是引擎 schema 是刻意的：schema 描述**字符串契约**，"人看着是多少度"是界面问题，
塞进引擎会让审计/序列化也背上界面语义（将来 SDK 需要插件声明自定义显示时再升级成 schema 元数据）。

**2）第四个组件迁移：`WorldText`。** 它是上一轮列出的"卡在动态选项源"的那个；本轮补齐后按样板迁移：

| 位置 | 删除内容 |
|---|---|
| `panels/inspector.rs` | `has("WorldText")` 面板（文本/字号/字体下拉/颜色/偏移/居中 + "移除 WorldText"） |
| `inspector_state.rs` | `WorldTextFields` + `Default`、`set_world_text`/`clear_world_text`、`encode/decode/validate_world_text`、快照字段与 apply 分支、`InvalidWorldText`、2 个旧测试 |
| `actions.rs`/`main.rs`/`lib.rs` | 快照构造与回读、`EditorApp.world_text`、`inspector_world_text_open`、`WorldTextFields` 导出 |
| `schema_fields.rs` | `HANDWRITTEN_PANEL_COMPONENTS` 里的 `"WorldText"`（通用编辑器自动接管） |

迁移后的控件：文本=文本框、字号=DragValue、**字体=项目字体下拉**、颜色=**取色器**（原来是 3 个
DragValue，属于升级）、偏移=两个 DragValue、居中=勾选框。`add_component("WorldText")` 的默认值改成
引擎类型编码（原默认 `offset=0,-20;centered=true` 一字不差）。迁移测试
`migrated_world_text_uses_project_font_choices` 断言：字体字段拿到下拉（`ChoiceSource::ProjectFonts`）、

**3）用户截图反馈的图标缺陷（真实缺陷，已修）。** 截图上"暂停"按钮渲染成两个"豆腐块"：

## 6. 回滚说明

- 所有新增能力都是**新增类型与新入口**，没有替换既有实现：`services.rs`、`profiler.rs`、`perf_fixture.rs`、`resource_refresh.rs`、`perf_baseline.rs`、`command_router.rs`、`diagnostics.rs`、`schema_audit.rs` 全为新文件。
- 唯一改动的既有行为：
  1. `EditorApp.history` 类型由 `CommandHistory` 改为 `CommandService`（通过 `Deref/DerefMut` 保持旧调用点语义不变）；
  2. 资源刷新从**同步**改为**后台代际任务**（状态文案与提交点改变，但 `ResourceBrowserState` 的对外读 API 未变）；
  3. Lua 控制台输出由无界 `Vec` 改为 10k 上限的有界缓冲（超出丢弃最旧）；
  4. `EditorCommand` 新增实体级变体，服务层 `WorkspaceController` 对它们**显式拒绝**（shell-only）；
     运行控制变体 `PausePlay/ResumePlay/StepPlay/RestartPlay` 与字段提交变体
     `SetComponentField` 同样只由 shell 处理、服务层显式拒绝；
  5. `ComponentSchema::serialize` 改为按字段类型编码，原行为保留在 `serialize_values`；
  6. `editor --check` 输出新增 `schema_audit`／`schema_error`／`component_no_schema` 行（只增行，不改既有行）。
  7. `CommandService::default()` 从"派生 = 预算 0"改为"= `new(DEFAULT_MAX_ENTRIES)`"（**修正**，
     此前默认构造会把历史全丢）；`panels/inspector.rs` 只在末尾多了一行调用
     `draw_schema_driven_components`，手写面板一行未动。
  8. **实体级脚本组件的名字与载荷**（第 13 轮）：运行时/加载器/schema/编辑器统一到
     `SCRIPT_COMPONENT = "Script"`；schema 注册表键 `EntityScript` → `Script`；
     编辑器 Inspector 写 `Script` + `file=<路径>`（不再写 `LuaScript` + 裸路径）；
     `SceneDocument::open` 增加旧写法迁移并在有迁移时标记未保存。
     回滚：删掉 `component_migration` 的调用、把 `SCRIPT_COMPONENT` 的用点换回字面量即可
     回到旧行为（**不建议**：旧行为下 Inspector 设的脚本运行时读不到）。
