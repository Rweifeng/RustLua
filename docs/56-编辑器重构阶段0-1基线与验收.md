边界规则（docs/55 §4.1）的当前状态：

1. **View 只发 typed action**：`EditorCommand` 有唯一编排点 `EditorApp::dispatch`。已迁移：快捷键（Ctrl+S/Z/Y/D）、工具栏 Play/Stop、菜单保存、Hierarchy 右键菜单的创建/删除/移动到根节点。剩余：Inspector 属性提交、Scene View 拖拽落点与 Gizmo 提交仍在面板内直接调用既有方法（见 §5）。
2. **持久数据修改经 `CommandService`**：`EditorApp.history` 已是 `CommandService`，撤销预算在其中强制生效。
3. **选择唯一事实源**：`EditorApp.selection` 已是 `SelectionService`；Hierarchy/Scene/Inspector 共享同一实例。
4. **预览资源归 `PreviewService`**：未变（既有 `PreviewSession` 继续独占 GPU/readback/字体资源）。
5. **后台任务只返回不可变结果**：资源刷新已完全满足；缩略图 worker 既有实现不变。
6. **稳定 ID**：未变（`AssetId`/`SceneEntityId` 既有设计）。
7. **取消/失败/恢复/telemetry 契约**：`CancellationToken`+`JobError`+`JobReport` 已定义并被刷新任务使用。

### 1.1 性能止血（阶段 1 明确项）

| 阶段 1 要求 | 落地方式 |
|---|---|
| 后台资源刷新/校验 | 递归扫描、`ResourceDatabase` 协调、依赖重算、DB 落盘全部移出 UI 线程；UI 线程只做「发起」与「提交」，代际号保证旧结果不覆盖新结果 |
| Hierarchy 扁平化 + **虚拟滚动** | 行模型（`HierarchyRow{id, depth, effective_collapsed, has_children}`）按 `(文档修订, 实体数, 过滤词, 折叠集合)` 缓存；面板用固定行高 22 px + `ScrollArea::show_rows` **只绘制视口内的行**；绘制不再递归、不再逐行克隆文档 |
| Hierarchy 搜索热点 | 过滤匹配改为一次遍历的 `HierarchyMatchIndex`（O(n)，哈希表 O(1) 查询）+ 按修订缓存的小写化名称表（`HierarchyNameCache`）；改过滤词不再重算 10k 个名字，命中计数复用同一次遍历 |
| Console 有界 + **虚拟滚动** | 行存储有界（Lua 输出 10k / 通知 500 / `LogSink` 500）；新增 `ConsoleRowCache` 行索引（按分类/过滤/级别/来源代数失效）+ 固定行高 16 px `show_rows`，只绘制视口内的行；多行输出按物理行拆行以保持固定行高 |
| Inspector dirty 驱动 | 既有 E08 直写 + 提交点收敛机制保持（本次未改动其语义） |
| Inspector **搜索 + 引用选择器**（P1） | **已完成**（第 42 轮） | `filter_field_rows` 多词 AND（含当前值，可按资源路径反查字段）+ `picker_candidates` 按 `FieldRule` 扩展名白名单列工程资源（选中即一条 Undo，可选字段可写空）。缺口：不做正则/排除词，不做跨实体全局搜索；**真人在真实工程里的手感未被确认**（属人眼清单） |
| 历史内存预算 | 撤销条目上限 200，超出丢弃最旧并计入 `dropped_entries`，暴露到 HUD 与 profiler gauge |
| Editor Profiler | 帧 p50/p95/p99 + 超预算帧数、面板耗时、命令耗时（含 `dispatch`）、扫描/导入队列、缓存命中率（`hierarchy_cache_hit/miss`、`console_index_cache_hit/miss`）、实际绘制行数（`hierarchy_rows_drawn`）、`console_rows_indexed`、历史深度等 gauge |

## 2. 可重复基线

### 2.1 怎么跑

```powershell
# 归档到版本库内的基线目录（质量门走的就是这条命令）
cargo run --quiet --manifest-path engine/Cargo.toml -p editor -- --perf-baseline --perf-report artifacts/baselines/editor-baseline.txt

# Release 口径（对外引用性能数字时用这个）
cargo build --release -p editor
cargo run --quiet --release --manifest-path engine/Cargo.toml -p editor -- --perf-baseline --perf-report artifacts/baselines/editor-baseline-release.txt
```

**判定语义**：每个场景自带不变量，任一不达标即 `failed>0`、`result=FAILED`、退出码 2。
`scripts/verify.ps1` 已接入（`Editor performance baseline` 步骤），因此"数字好看但代码是坏的"无法通过质量门。

结论（对照 docs/55 §3.2 预算）：

- **10k 实体 Hierarchy 的"扁平化"本身不是瓶颈**（Release p95 1.1 ms，缓存命中 2 µs）；
- **10k 实体面板每帧只绘制 26 行**（视口 720 px / 22 px 行高），Release 面板帧耗时 p95 0.22 ms、
  Debug p95 2.9 ms —— 相对"最低 30 FPS（33 ms）"的门槛有一个数量级余量，且这是**无窗口真实
  egui 帧**测出来的，不是估算；
- **10 万行日志的控制台面板帧 p95 0.48 ms**（Release）：存储有界（保留 1 万行）+ 行索引按
  来源代数/过滤/级别缓存，稳态 30 帧内 0 次重建，因此"滚动/过滤不冻结主线程"是结构性成立的；
- **10k 实体按名搜索 P95 2.46 ms**（预算 100 ms，达标；比优化前 14.16 ms 快 5.8×）：
  一次遍历的匹配索引 + 按修订缓存的小写化名称表；
- **撤销/重做单步 Release p95 < 1 ms**，100 步往返内容逐字段一致；
- **资源扫描已彻底离开 UI 线程**：发起 0.034 ms，worker 侧 2k 文件约 75 ms；
- **外部文件变化 2 秒内被反映**（docs/55 §3.2 预算 2000 ms）：实测端到端 **225 ms**，
  其中 UI 线程每帧只付一次 `try_recv`（p95 **0.0001 ms**），2k 文件的元数据扫描（worker 侧 p95 8 ms）完全不在主线程；
- **长会话内存有界**：日志 100k→保留 1 万行、`LogSink` 100k→保留 500 行、历史 500 编辑→保留 200 条。

### 3.1 漂移门抓到的问题（真实缺陷，已修）

组件 schema 是"逐字段"的，写错就会在真实内容上暴露。本轮三道门（编码器对拍 / 再序列化 / 真实工程审计）
一共抓出 3 个问题，全部已修：

| # | 问题 | 谁抓到 | 修法 |
|---|---|---|---|
| 1 | `Sprite.sorting_layer` / `Quad.layer` 被当成整数，实际是**分层名字符串**（`default`/`world`/`actor`） | 引擎编码器对拍门 | 字段类型改 `Text`，并在 schema 注释里写明由 `sorting_layer_rank` 解析 |
| 2 | `FieldKind::Size`（`宽x高`）经 `serialize` 后变成 `128,128`，再解析失败 | 「解析→序列化→解析」稳定性检查 | `ComponentSchema::serialize` 改为**按字段类型**编码（`Size` 写回 `x`），并补 `serialize_values` 作为无 schema 的兼容入口 |
3 | `Sprite.pivot`/`order` 被标为 required，而**仓库里的真实旧场景没有这两个字段**（解析器取默认值） | 真实工程审计（`examples/game_jhyt`） | 改为可选；这条正是 docs/55「旧项目可无损打开」的前置条件 |

- `diff_prefab_entity` 现在对**有 schema 的组件**输出 `property:<Component>.<field>` 而不是 `component:<Component>`；
  未注册组件、组件新增/删除仍走整串覆盖。两个既有测试相应更新（它们原本断言整串覆盖）。

  Apply 因此变成幂等操作（同一覆盖重复应用结果完全一致），这条由 `property_overrides_rewrite_one_field_only` 锁定。

### 3.4 Schema 驱动 Inspector 过程中抓出的问题（第 12 轮，全部已修/已钉住）

**A. `CommandService::default()` 的 Undo 预算是 0（真实缺陷，已修）**

`CommandService` 原本 `#[derive(Default)]`，派生值 `max_entries = 0`，而 `enforce_budget()`
会照此在**每次编辑后把整条历史丢光**——"默认构造 = 没有 Undo"。生产路径用的是
`CommandService::new(DEFAULT_MAX_ENTRIES)`，所以此前没人碰到；这正是新基线场景
`schema_field_edit_1k` 的报告行把它暴露出来的（`budget=0` 与 `undo_entries=200` 自相矛盾）。

修法：手写 `impl Default`（= `new(DEFAULT_MAX_ENTRIES)`），并加单测
`default_command_service_keeps_the_documented_undo_budget` 钉住这个陷阱。

**B. 数字字段按"字段类型"归一化，与各引擎编码器的精度不同（行为记录，非缺陷）**

schema 写路径（`FieldValue::to_component_value`）把数字写成 `{:.6}`，而引擎各组件编码器各写各的
（`QuadComponent` 写 `size={},{}` → `128,64`；`SpriteComponent` 写 `tint={:.3}`）。
因此**被编辑过的那个字段**文本会变成 6 位小数（`size=128.000000,64.000000`），语义与解析完全等价，
且"归一化后的文本再提交一次"仍是**无变化**（幂等，不会持续增长历史）。
影响面：编辑过的场景文件在该字段上会有一段"精度样式"变化，直到引擎再次保存整串。

不改的理由：schema 层刻意只保证**类型级**契约（漂移门比对的是解析后的语义，不是逐字节文本），
强行让 schema 输出等于每个编码器的私有精度不可行；Prefab 覆盖路径同样依赖这条契约。
证据：`editing_writes_one_field_and_leaves_the_rest_byte_identical` 明确断言
"只有被编辑的字段变、其余字段逐字节不变"与"归一化后再提交 = 无变化"。

**C. 组件串本身不满足 schema 时，报错不能指向用户正在改的字段（已修）**

逐字段写入要先整串解析以比较当前值，因此缺必填字段的旧串会以
`字段 center 取值非法：required field is missing` 冒出来——用户改的是 `zoom`，
这条消息会把人带到错误的字段上。新增 `SchemaFieldError::PayloadUnparsable`，
把这类问题翻译成"组件 X 的现有串无法按 schema 解析（字段 Y：…）；请先用整串修正后再按字段编辑"，
由 `unparsable_payload_is_reported_as_a_payload_problem` 锁定。

**D. 测试写法上的一个坑（记录给后续写测试的人）**

`Undo` 命令会先走帧末收敛边界（`finish_inspector_edits_if_dirty`）。测试里如果**从不调用**
`sync_inspector`，Inspector 缓冲与文档不一致，这条边界会先把"从未同步过的缓冲"提交成一条历史，
于是单次 `Undo` 撤销的是那条而不是被测的字段编辑（现象：`status=Undo: Inspector`）。
真实 UI 每帧都会同步，所以这不是产品缺陷；测试里必须像 UI 一样先 `sync_inspector`。

### 3.5 实体级脚本组件有**三个名字**（真实缺陷，已修；第 13 轮）

发现过程：为了给"缺 schema 的组件"补 schema，我先把运行时真正读取的组件名列了一遍
（`Select-String 'components\.(get|contains_key|remove)\("…"'`）。结果运行时读的是 `Script`：

| 位置 | 用的名字 | 载荷形式 |
|---|---|---|
| 运行时 `core::script` + 场景加载器 `typed_scene` | `Script` | `file=scripts/x.lua` |
| 编辑器 Inspector（`inspector_state::set_lua_script`） | `LuaScript` | **裸路径** `scripts/x.lua` |
| 引擎 schema 注册表 | `EntityScript` | `file=…` |

后果：**在 Inspector 里给实体填了 Lua 路径，运行时永远不会加载它**（运行时只找 `Script`，
而没有任何迁移代码把 `LuaScript` 翻译过去）；同时 schema 描述的是一个没人消费的组件名，
真实场景里的 `Script` 反而会被审计报成"没有 schema"。

修法（一处权威名字 + 一条迁移 + 三个守卫测试）：

1. **唯一权威名字**：引擎新增 `core::entity_script::SCRIPT_COMPONENT = "Script"`，
   运行时读取点（`core/script.rs`）改用它；schema 注册表的键也从 `EntityScript` 改成
   `SCRIPT_COMPONENT`（字段表重命名 `SCRIPT_FIELDS`）。
2. **迁移**：新增 `core::component_migration`（幂等、不写盘、不猜）：
   `LuaScript`（裸路径**或** `file=` 形式）→ `Script` + `file=<路径>`；
   新组件已在场时保留新值、丢弃旧键（`conflicts`）；旧负载解析不出来则**原样保留**
   （`untouched`，绝不为了报告好看而丢数据）。与 `scene_migration`（空间迁移，会写盘/备份）
   分工明确。
3. **编辑器**：`SceneDocument::open` 统一做迁移；发生过迁移就**标记未保存**并在状态栏说明
   ——独立游戏读的是场景文件，不保存等于运行时仍看不到脚本。Inspector 的 Lua 输入现在写
   `Script` + `file=`，显示仍是裸路径（用户关心的是文件）。
4. **守卫**：
   - `component_schema::script_schema_uses_the_runtime_component_name`：schema 键 == 运行时常量、
     旧键名不得复活、引擎编码器输出可解析；
   - `typed_scene::script_component_name_matches_the_shared_constant`：加载器认得这个名字；
   - `component_migration::migrated_scene_compiles_into_the_runtime_component_set`：
     旧场景 → 迁移 → 加载器真的编成 `ComponentId::Script`（把"改名"和"运行时读得到"连起来）。

诚实边界：`examples/game_jhyt` 以及仓库里**任何** `.scene/.prefab/.widget` 数据文件都不含
`LuaScript`（命中 0），所以这条修复的"真实工程证据"同样不存在——证据是引擎/编辑器测试 +
新的基线场景 `legacy_script_migration_1k`。

顺带记录（不是缺陷）：`ComponentSchema::serialize` 按字段名字典序输出（`ComponentData` 是
`BTreeMap`），与引擎编码器的书写顺序不同（`Script` 是 `file=…;enabled=false`，schema 写
`enabled=false;file=…`）。该函数目前**没有任何生产消费者**（只有漂移门与守卫测试用它），
编辑器写字段走的是 `property_path::write_field` 的"最小改动"路径，因此不会重排组件串。

### 3.6 字段级语义规则（第 14 轮）：把"类型正确但语义错"的洞堵上

第 12/13 轮反复记录过同一个缺口：`FieldKind::Text` 只表示"任意文本"，于是
`Script.file`（必须落在工程根内）这类规则只存在于编辑器的输入校验与引擎解析器里，
schema 与审计表达不了。本轮把规则**声明式**地放进 schema：

- 新增 `FieldRule{ NonEmpty, ProjectPath{ extensions }, NonNegative }` +
  `FieldSchema::with_rules(...)`/`describe()`；规则是纯数据（无闭包），
  `FieldSchema` 仍是 `const`/`Eq`，schema 表照旧是静态常量表。
- 校验顺序固定"先类型、后语义"：类型错报到类型上，语义错报到规则上；错误信息同时被
  引擎审计、`property_path::write_field` 与通用字段编辑器复用。
- `Script.file` 挂上 `NonEmpty + ProjectPath{extensions: &[]}`——**刻意不限扩展名**：
  运行时是 `root.join(file)` 后直接当 Lua 源码编译，`.lua` 只是**编辑器输入层**的项目约定
  （更严）。两边差异写进了两侧测试，避免"以为一样"。

**过程中抓到的真实缺陷**：我在实现 `ProjectPath` 时先用 `Path::is_absolute()` 判定绝对路径，
结果 schema **放行** `/etc/passwd`——Windows 上根相对路径没有盘符，`is_absolute()` 返回 `false`。
这正是"同一规则两处实现"的典型后果：引擎原来用的是组件式检查（`RootDir | ParentDir | Prefix`），
编辑器用的也是有同样洞的 `is_absolute() + 手写 .. 扫描`。修法：
把判定收敛到 `core::paths::{is_absolute_path, escapes_project_root}`（带自己的单测），
`EntityScript::validate` 与 schema 规则**共用同一份实现**，编辑器也改为复用引擎校验器。
反漂移守卫：`field_rules_match_engine_validators` 对 10 组样本逐条断言
"引擎解析器与 schema 规则的接受/拒绝完全一致"，`paths` 自己的单测覆盖 Windows 根相对形式。

同类"假样本"清理：漂移门原来用 `EntityScript::default().to_component_str()`（= `file=` 空路径）
当 `Script` 的样本，而引擎自己的解析器根本不接受它——换成合法载荷，否则门在自欺。

   `#![allow(dead_code)]` 被删除——这个文件从"待接线"变成"在线上"。
5. **相位规则与生产行为对齐**（这是接线时必须解决的真实分歧）：原状态机把修饰键编进事件，

   现在规则改为：TilePaint → `Painting`；命中实体 → `Dragging`；否则 → `Marquee`，
   修饰键**不**参与相位判定（它只决定选择是"加入"还是"替换"，属于选择语义）。
   旧测试 `modifier_click_select_starts_marquee` 相应改写为
   `empty_space_click_starts_marquee_for_every_tool`（4 种工具全覆盖）。
6. **新增 3 个 app 级测试**：切换工具取消交互、Escape（`clear_active_scene_drag`）把相位
   打回 `Idle`、命中/空白决定相位。

**当时的诚实边界（第 17 轮已补掉一部分，见 §3.9）**：3D 视口的 Gizmo 拖拽当时仍走它自己的
`gizmo_drag` 状态；`draw_scene_2d` 里那串指针分支**没有**被"合成指针拖动"的帧级测试覆盖
（现有证据是状态机单测 + app 级状态测试 + 编译期强制"面板只能读相位"）。

### 3.10 菜单栏按 Unity 结构重组（第 18 轮）

原来只有「项目 / 编辑 / 视图 / 帮助」四个自造菜单，条目散落在 `header.rs` 的 170 行内联代码里。
现在改成 **Unity 的七个顶级菜单**：文件 / 编辑 / 资源 / 游戏对象 / 组件 / 窗口 / 帮助。

**做法：菜单结构是数据。** 新增 `engine/crates/editor/src/menu.rs`：

- [`MENU_BAR`] 声明表：顶级菜单顺序、子菜单、条目、快捷键提示、可用条件（`MenuGate`）；
- 渲染层只走这棵树，动作统一进 `EditorApp::run_menu_action`；
- 能走 typed command 的一律走 `dispatch`（撤销/重做/复制/删除/播放控制/保存），
  其余走既有入口方法——菜单**不直接改文档**，架构棘轮继续守住面板文件；
- 「组件」菜单直接由 `COMPONENT_REGISTRY` 的类别分组生成（`component_menu_groups()`），
  所以"新增组件不改菜单"与"新增组件不改巨型 match"是同一件事；
- 「最近项目」「工作台」「视图模式」「布局信息」是运行时分组（`MenuRow` 的专门变体）。

Unity 的 Preferences / Build Settings 窗口 / Open Scene 文件选择器**不存在**，因此不列空条目。
不可用条目一律**灰置 + 悬停说明原因**（`MenuGate::reason()`），不假装可用。

**这一轮的 7 条菜单测试**（`menu.rs` 内）：顶级菜单顺序 == Unity；结构卫生（非空、无连续

### 3.14 我自己造成的第二起编码事故：`verify.ps1` 的 BOM 被剥掉（第 21 轮，已修 + 已加门）

**现象**：本轮按需求给 `scripts/verify.ps1` 追加"审计第二个示例工程"的步骤（用文件编辑工具），
之后用 PowerShell 解析该脚本时，它在**中文注释处**报一串语法错误
（`意外的标记"-NoProfile"`、"字符串缺少终止符"…）——也就是说**整条质量门脚本当时无法运行**。

**根因**：脚本在 git 里是 **UTF-8 with BOM**；文件编辑工具写回的是 **UTF-8 without BOM**。
Windows PowerShell 5.1 在中文区域设置下按 ANSI 读**无 BOM** 的 `.ps1`，中文注释被误解码 → 解析失败。
逐字节对比确认：`HEAD` 版本前三字节 `EF BB BF`，改动后的工作区版本是 `[Cm`（BOM 已丢）。
这与第 11 轮那次"PowerShell 文本 cmdlet 改源码"是同一类事故（**编码**），但这次是**工具默认行为**造成的，
而且受害文件是质量门本身——比业务代码坏了更危险。

**修法**：

1. 用 .NET 读写（`ReadAllText` + `WriteAllText(..., UTF8Encoding($true))`）把 BOM 补回去，
   内容逐字节不变（改前先确认正文是合法 UTF-8：解析**文本**通过、解析**文件**失败，即编码而非内容问题）；
2. 逐个核对 `scripts/*.ps1` 的 BOM 状态与 `HEAD` 是否一致 —— 只有 `verify.ps1` 被剥掉，其余 14 个正常；
3. **加机械化守卫**：`scripts/check-docs.ps1` 新增第 ⑦ 项检查——`scripts/*.ps1` 必须带 UTF-8 BOM，
   缺一个就判红并说明后果。负向对照已验证：临时剥掉 `run-demo.ps1` 的 BOM →
   `[RED] check_docs_failed issues=1`（指到具体文件）、退出码 1；补回后 `check_docs_ok ... ps1_bom_ok=15`。
4. 同一轮确认 `verify.ps1` 重新可解析（`verify_parses_ok`）。

**教训（追加到项目约定）**：改 `.ps1` 之后必须确认 BOM 还在；文件工具不会保留它。
现在这条由 `check-docs.ps1` 盯着，不再依赖人记得。

**2）迁移前必须先补的一条规则能力：向量非负。** `Image` 的两个既有测试暴露了手写面板比 schema
更严的地方——旧 `validate_image` 拒绝负的九宫格边框。为此把 `FieldRule::NonNegative` 从"标量"
扩展到**向量要求每个分量非负**，并挂到 `Image.nine_slice` 上，于是**审计也获得了这条校验**
（原来只有编辑器拦）。同时用真实数据确认了"全零 = 省略"这一等价性：
渲染侧是 `image.nine_slice.filter(|s| s.iter().any(|v| *v > 0.0))`，全零与省略都回退单四边形，
所以通用编辑器把 `nine_slice=0,0,0,0` 写出来**语义无变化**（引擎再保存时会自然收敛回省略）。

**3）刻意更严的分歧要写进测试**：引擎解析器**接受** `nine_slice=-1,0,0,0`（渲染侧会过滤掉它），
schema 拒绝它。这与 `Script.file` 的 `.lua` 约定是同一类"编辑器比运行时严"的分歧，
在 `field_rules_match_engine_validators` 里用一段显式注释 + 三行断言写清楚，避免以后有人
"顺手对齐"把编辑器守卫删掉。

**4）迁移卡点清单（诚实边界，也是下一步的输入）**：接下来要迁的组件各缺一样 schema 表达能力，
所以**没有**在本轮硬迁——迁了就是体验或校验降级：

| 组件 | 缺的能力 | 具体表现 |
|---|---|---|
| `Camera3D` | **显示单位** | 面板 FOV 用**角度**，组件串存**弧度**；通用编辑器只会显示弧度。另外面板还带"姿态来自 Transform3D""已禁用"等说明与只读投影摘要 |
| `WorldText` / `Text` | **动态选项源** | 字体是下拉框（项目可用字体列表），schema 只能给文本框 |
| `Sprite` / `Transform` / `Transform3D` / `UiLayout` | 字段多 + 面板有复合语义 | 例如 Transform 的等比锁、UiLayout 的锚点/预设、Sprite 的纹理下拉 |
| `Collider3d` / `Tilemap` / `Animation` / `Container` / `UiEvents` / `UiBindings` / `ButtonStates` / `UiAnimation` | **没有 schema** | 先补 schema 才能谈迁移 |

也就是说：迁移这三轮（Light/MeshRenderer/Image）已经把"控件级等价"打通；
**下一层要补的是"字段元数据"**——显示单位、动态选项源、以及"零值等于省略"这类格式约定。

### 3.16 字段元数据层 + 第四个迁移组件 `WorldText` + 暂停按钮图标（第 23 轮）

**1）字段元数据层：显示单位与动态选项源。** 上一轮把迁移卡点归成两类，本轮先补上：

- `FieldUnit { Raw, Degrees }`：`Camera3D.fov` 在编辑器里用**角度**显示与输入，写回组件串时
  换算成**弧度**（`to_display`/`from_display` 一对纯函数，往返精度有测试）。组件串格式一个字没改。
- `ChoiceSource { Static, ProjectFonts }`：`font` 字段的候选来自**项目字体列表**
  （`project_font_paths()`），不是 schema 的静态 choices；通用编辑器因此画出与手写面板同款的下拉
  （"默认字体（不指定）" + 项目字体路径）。
- 两者都挂在 `SchemaFieldRow` 上由编辑器消费；`hint` 会自动带上单位说明
  （如 `number（编辑器用角度，组件串存弧度）`）。

放在编辑器而不是引擎 schema 是刻意的：schema 描述**字符串契约**，"人看着是多少度"是界面问题，
塞进引擎会让审计/序列化也背上界面语义（将来 SDK 需要插件声明自定义显示时再升级成 schema 元数据）。

**2）第四个组件迁移：`WorldText`。** 它是上一轮列出的"卡在动态选项源"的那个；本轮补齐后按样板迁移：

| 位置 | 删除内容 |
|---|---|
| `panels/inspector.rs` | `has("WorldText")` 面板（文本/字号/字体下拉/颜色/偏移/居中 + "移除 WorldText"） |
| `inspector_state.rs` | `WorldTextFields` + `Default`、`set_world_text`/`clear_world_text`、`encode/decode/validate_world_text`、快照字段与 apply 分支、`InvalidWorldText`、2 个旧测试 |
| `actions.rs`/`main.rs`/`lib.rs` | 快照构造与回读、`EditorApp.world_text`、`inspector_world_text_open`、`WorldTextFields` 导出 |
| `schema_fields.rs` | `HANDWRITTEN_PANEL_COMPONENTS` 里的 `"WorldText"`（通用编辑器自动接管） |

迁移后的控件：文本=文本框、字号=DragValue、**字体=项目字体下拉**、颜色=**取色器**（原来是 3 个
DragValue，属于升级）、偏移=两个 DragValue、居中=勾选框。`add_component("WorldText")` 的默认值改成
引擎类型编码（原默认 `offset=0,-20;centered=true` 一字不差）。迁移测试
`migrated_world_text_uses_project_font_choices` 断言：字体字段拿到下拉（`ChoiceSource::ProjectFonts`）、
颜色字段拿到取色器、提交一条 Undo、引擎解析器能把**中文文本**与改后的颜色一起读回；
`world_text_is_edited_through_the_schema_path` 断言存盘往返无损、非有限 offset 仍被 schema 拒绝。

**3）用户截图反馈的图标缺陷（真实缺陷，已修）。** 截图上"暂停"按钮渲染成两个"豆腐块"：
我用的是 `❚❚`（U+275A），**编辑器配置的字体里没有这个字形**，于是渲染为缺字方框。
修法：**图标改用 `ui.painter()` 绘制**（运行中画两条竖杠、暂停中画三角形），尺寸/配色仍走
egui 自己的按钮视觉，因此与字体无关；`pause_resume_icon(paused)` 这个纯函数被单测钉住，
保证"按钮显示的是下一步动作的反向图标"。同屏的 `▶/■/⏭/⟲` 渲染正常（截图可见），暂不改。

**4）当前迁移进度**：已迁 `Light`(20) / `MeshRenderer`(21) / `Image`(22) / `WorldText`(23)；
还剩 `Transform`/`Transform3D`/`Camera3D`/`Text`/`Sprite`/`UiLayout` + 刻意例外的 `Script`。

### 3.17 第五个迁移组件 `Camera3D` + 迁移当场抓出的三个真实缺陷（第 24 轮）

前四轮的迁移都是"控件级等价"，相机这一轮不一样：它的手写面板里有两样**不是字段**的东西
（统一 `Projection` 的只读投影摘要、`pose=transform` 时的生效姿态），还有一条**跨字段**不变量
（`near < far`、look-at 非退化）。迁移它把这两类缺口都逼了出来，也顺带抓出上一轮留下的一个
"看起来对、其实反了"的字段单位。

**1）字段单位写反了（真实缺陷，已修）。** 第 23 轮把 `Camera3D.fov` 登记为
`FieldUnit::Degrees`，理由写的是"编辑器用角度，组件串存弧度"。本轮迁移前先核对引擎：
`Camera3D::from_component_str` 读 `fov` 时 `parse_camera_number(raw)?.to_radians()`、
`to_component_str` 写出 `fov_y.to_degrees()`（`core/camera.rs`）——**组件串里存的就是角度**。
若照旧表迁移，手写面板里的 60° 会在通用编辑器里显示成 **3437.75°**，而且一编辑就把
`60` 当成弧度再乘一次 π/180。

修法：`FieldUnit` 改成显式区分**存储单位**与**显示单位**——`Degrees`（组件串就是角度，
不做换算，只补提示"（单位：角度）"）/ `Radians`（组件串存弧度、编辑器显示角度，才做换算）；
`Camera3D.fov` 归 `Degrees`。**门**：新增 `field_units_agree_with_the_engine_encoder`
直接拿**引擎编码器**对拍——编码一台 60° 相机、读出 `fov` 原文、经
`field_unit(..).to_display` 得到的数必须等于引擎内部的 `fov_y.to_degrees()`。
这与第 21/22 轮的"规则与引擎解析器对拍"是同一类守卫，只是对象换成了显示单位。
负向对照见 §4 第 8 条：把 `Degrees` 改回旧写法，测试立刻报
`编辑器显示 3437.746770784939°，引擎里是 60.0…°`。

**2）跨字段不变量：加一道"引擎解析器兜底门"（新能力）。**
手写面板的 `validate_camera3d` 是直接调 `Camera3D::from_component_str`，因此它拦下的不只是
类型：`near < far`、`fov ∈ (0°,180°)`、`near > 0`、look-at 非退化（position ≠ target）。
声明式 `FieldRule` 是**按字段**的，表达不了这些关系。与其再造一套跨字段规则词汇（还会与
引擎漂移），不如让**引擎解析器**当唯一事实源：

- 引擎新增 `core::typed_scene::validate_component_payload(name, value)`，三态返回：
  `None` = 组件名不在引擎已知集合里（Lua/自定义组件，引擎刻意不解释）、`Some(Ok)` = 引擎
  自己的 typed 解析器能读、`Some(Err(reason))` = 已知组件但载荷非法（带解析器原文）。
  实现直接复用加载边界的 `compile_component`——**没有第二份校验**。
- 编辑器在 `edit_component_field` 产出新串后调用它，失败返回
  `SchemaFieldError::EngineRejected`（`Rejected` → 不改文档、不产生历史）。

收益是**通用**的：所有走 schema 的组件写入都获得"引擎读得了"这条底线（`Transform` 的缩放
非零、`Sprite`/`UiLayout` 的既有约束、`Text` 的 `font_size > 0` 等同样被覆盖），而编辑器里
一份校验都没有重写。负向对照见 §4 第 9 条。

**3）只读说明层：迁移后保留"不是字段"的信息（新能力）。**
相机面板里的投影摘要与生效姿态不属于任何字段，因此新增 `SchemaComponentNote`（`text` +
`warning`）与**只读说明提供者表** `NOTE_PROVIDERS`（组件名 → 纯函数），由通用编辑器在该组件
字段行**下方**呈现；`warning` 用醒目色（与旧面板同一个颜色 `220,150,60`）。
`camera3d_notes` 仍全部用引擎自己的解析器（`Projection::from_camera3d`、
`Camera3D::with_pose`），内容包括：`enabled=false` 的"不参与相机选帧"警告、
`pose=transform` 时"位置/目标仅在实体没有 Transform3D 时生效"的说明、统一投影行、
以及生效姿态（缺 `Transform3D` / `Transform3D` 非法都给警告）。原
`panels/inspector.rs` 的 `camera_panel_summary` 与其测试整体搬到 `schema_fields`。
负向对照见 §4 第 10 条。

**4）`pose` 下拉必须能"改回去"（迁移当场抓出的可用性缺口）。**
引擎解析器认 `pose=transform` 与 `pose=look_at`（后者与**省略**同义：编码器在
`pose_from_transform=false` 时根本不写这个字段），而 schema 的候选只有 `transform`。
手写面板用勾选框（取消勾选 = 省略），下拉框没有"清空"动作——照旧候选迁移，
`pose=transform` 就成了**单行道**。修法：候选补 `look_at`，并把它纳入对拍门
（`field_rules_match_engine_validators` 新增相机样本组：base / `pose=transform` /
`pose=look_at` / `pose=bogus` 拒绝 / `enabled=false`）。审计口径不变（两个真实工程仍 0 漂移）。
负向对照见 §4 第 11 条。

**5）删除清单**（与前四轮同构，一次删干净）：

| 位置 | 删除内容 |
|---|---|
| `panels/inspector.rs` | `has("Camera3D")` 面板（位置/目标/DragValue、FOV、近远、pose 勾选框、enabled 勾选框、禁用与姿态提示、摘要块）+ `camera3d_panel_summary()` + 面板级摘要类型与函数 + 1 个面板测试 |
| `inspector_state.rs` | `Camera3DFields` + `Default`、`set_camera3d`、`validate/encode/decode_camera3d`、`InspectorSnapshot.camera3d` 与两处 apply 分支（含多选相机批量写入）、`InvalidCamera3d`、3 个旧测试 |
| `actions.rs`/`main.rs`/`lib.rs` | 快照构造与回读、`EditorApp.camera3d`、`Camera3DFields` 导出 |
| `schema_fields.rs` | `HANDWRITTEN_PANEL_COMPONENTS` 里的 `"Camera3D"`（通用编辑器自动接管） |

**6）保留/新增**：

- `add_component("Camera3D")` 的默认值改为**引擎类型**（新增 `impl Default for Camera3D`：
  位置 `(0,0,5)` 看向原点、FOV 90°、near 0.1、far 100——与旧面板默认值一字不差），
  编辑器里不再有这份默认值。
- 迁移后的控件：position/target = DragValue×3、`fov` = **以角度显示**的 DragValue、
  near/far = DragValue、`pose` = 下拉、`enabled` = 勾选框，下方是只读摘要。
- 迁移测试 `migrated_camera3d_keeps_units_notes_and_engine_invariants`：`fov` 显示 `60`
  （不是 3437.75）、position 是 `Vector{3}`、`pose` 是下拉且候选含 `look_at`、提交
  `fov=75` 后**恰好一条 Undo** 且引擎读回 75°、`near=200` 被**引擎解析器**拒绝且不产生历史、
  只读说明给出"透视 75.0°"与"已禁用 → 不参与相机选帧"的警告。
- **数据格式未变**：组件串仍是引擎编码器的形式（`fov` 角度、位置 9 位小数、near/far 9 位小数）。

**7）当前迁移进度**：已迁 `Light`(20) / `MeshRenderer`(21) / `Image`(22) / `WorldText`(23) /

### 3.18 第六个迁移组件 `Text` + 自由文本转义（第 25 轮）

**1）迁移前先补的一条真实能力：自由文本转义（真实缺陷，已修）。**
旧 `Text` 面板有两个测试专门盯"字体路径里带 `;`/`=`"（`font=assets/fonts/a\;b\=数字.ttf`）。
而通用字段编辑器的 schema 层当时只会**朴素按 `;` 切分**、写入也不转义——照那样迁移会丢掉这个
属性；更糟的是第 23 轮迁移 `WorldText` 时**已经静默丢了**（它的老测试只用了不含特殊字符的中文，
没抓到）。第 24 轮新加的"引擎解析器兜底门"只是把"写坏串"从**数据损坏**变成**被拒绝**，
并没有真正支持这类文字。

修法（转义口径只有一份实现）：

- `FieldSchema` 新增 `escaped: bool` + `with_escaped()`：**显式标注**哪些字段是自由文本；
- `TEXT_FIELDS.text/font` 与 `WORLD_TEXT_FIELDS.text/font` 标上；
- `ComponentSchema::parse/serialize` 与 `property_path` 的按字段读写共用
  `ui::{escape_text, unescape_text, split_fields}`（原来只有 `UiText` 自己用）；
  **只有"有转义字段的组件"**才用转义感知切分——`MeshRenderer.mesh` 这类字段的引擎解析器是
  朴素切分，替它转义会让审计比运行时更松（反向漂移）；
- `read_field_text` 保留**原样文本**（Prefab 覆盖记录用），新增
  `read_field_display_text`（编辑器输入框用，返回反转义后的真实文字）；
- `write_field` 对转义字段"先反转义入参、再转义写出"，于是编辑器输入（真实文字）与
  Prefab 回退（`read_field_text` 的原样文本）两条路径都正确，且不会二次转义；
  "无变化"判定比较的是反转义后的值（含转义字符的文字不再每次失焦都产生一条历史）。

门：引擎 `escaped_text_fields_match_the_engine_encoder`（`Text`/`WorldText` 与
`UiText::to_component_str` 双向对拍 + `MeshRenderer` 明确**不**转义）与编辑器
`escaped_text_fields_survive_the_generic_edit_path`（显示文本 = 真实文字 → 提交 → 引擎读回 →
再提交是"无变化" → 写一个字段不动其它字段）。负向对照见 §4 第 13 条。

**2）`Text` 迁移**（同一份样板）：删面板（文本/字号/字体下拉/颜色/"移除 Text"）+
`TextFields` + `set_text`/`clear_text` + `encode|decode|validate_text` + `InvalidText` +
快照字段与 apply 分支（含多选批量）+ `EditorApp.text` + `inspector_text_open` + `lib.rs` 导出；
`add_component("Text")` 默认值取**引擎类型**（新增 `impl Default for UiText`：空文本 +

**字体 = 项目字体下拉**、颜色 = **取色器**（原来是 3 个 DragValue，属升级）。
迁移测试 `migrated_text_keeps_font_choices_and_escaped_text`；bin 侧

### 3.19 Scene Interaction 收尾：帧级合成拖动 + 抓到"2D 拖动不落盘"的真实缺陷（第 26 轮）

**1）把拖动序列做成可合成的帧级测试。** 上一轮遗留的 `ER-07` 缺口是"指针拖动只有状态机单测 +
app 级状态测试，没有帧级测试"。本轮把 `draw_scene_2d` 里内联的**预览推进**抽成
`scene_pointer_drag_apply(pos, scale)`（与已有的 `scene_pointer_down/drag/up` 同一层），
于是"按下 → 拖动（含预览）→ 拖动 → 松手"整条生产序列可以在**没有 egui 帧、没有 GPU** 的
情况下合成出来：`synthetic_pointer_drag_commits_exactly_one_undo` 断言
① 拖动全程不写历史、不改文档（只推进运行时预览）；② 松手恰好一条 Undo、文档真的落到
`(124, 88)`（面板 +(24,12)、Y 轴取反）；③ Undo 精确回到拖动前的**原文**；④ 相位回 Idle、
预览清空。

**2）这条测试当场抓到一个真实缺陷（已修）：2D 拖动松手从不写入文档。**
`scene_drag::apply_drag_preview_to_document` 先 `std::mem::take(&mut scene_state.preview)`
**再**调用 `scene_drag_locals()`——而后者读的正是 `scene_state.preview`，于是 `locals` 恒为空，
写入循环每次都走 `continue`（"无法无损反解就拒绝写回"分支），文档一字未改；事务照旧提交，
所以用户看到的历史里有记录、画面却在松手后弹回原处。
修法：把 `scene_drag_locals()` 挪到 take **之前**（顺序错误，不是换算逻辑错误）。
负向对照就是这条测试本身：把顺序改回去，它立刻报
`assertion left != right failed: 文档必须真的被改动`（拖动中预览正常、松手后原文未变）。

**3）诚实边界**：这条是**合成输入**（直接调生产入口），不是真实窗口的指针事件；
真实窗口的点击/拖放/停靠仍在 §5 的 GUI smoke 缺口里。`scene_view.rs` 剩余的 8 处直接写入
（Tile 绘制、拖放生成实体）仍未迁移——它们需要新的 typed 命令，排在棘轮清零里。

### 3.21 补齐 4 个组件的 schema + 4 个按模型能力跳过（第 26 轮，与 §3.19 并行）

**补齐的 4 个**（编码器为唯一事实源，required 逐条对着解析器的 `ok_or("missing …")` 与
`Self::default()` 核对）：`Collider3d`（`shape` required，其余 optional——形状尺寸缺席各自默认
`0.0`，由"对应形状尺寸必须为正"这条**跨字段**校验兜底）、`Tilemap`（`tile_size/width/height/
tiles/solid` required、`texture` optional；挂了 `NonNegative`/`NonEmpty`）、`Container`（全
optional，空串就是合法默认样式）、`ButtonStates`（全 optional；**刻意不挂 `NonEmpty`**——空值
`normal=` 在引擎里是"无覆盖"而不是错误）。

**跳过的 4 个（诚实缺口：当前 schema 模型是"键→值"映射，表达不了这些编码）**：

| 组件 | 编码形态 | 缺口 |
|---|---|---|
| `Animation` | `default=<名>;clip:<名>:<sheet>:<cols>:<fps>:<looped>` | `clip:` 段**没有 `=`**（位置式）且可**重复多次** |
| `UiEvents` | `event=..;target=..;function=..;arg.<名>=..` 用 `\|` 连接多条 | 重复键 + 动态键（`arg.<名>`） |
| `UiBindings` | `property=..;target=..;source=..` 用 `\|` 连接多条 | 重复键 |
| `UiAnimation` | `track.<属性名>=<time>:<value>:<easing>` 用 `\|` 连接 | 动态键名（键来自作者写的属性名） |

新增引擎测试 `components_with_positional_or_repeated_fields_stay_unregistered` 把"跳过"机械化
钉住（断言未注册，并用朴素 schema 展示失败形态：`clip:` 无 `=`、重复键被 BTreeMap 静默折叠、
`track.*` 动态键被拒）。**要做完这 4 个，需要给 schema 加一种"列表/重复字段"模型
（如 `FieldKind::List{ item }` 或 `FieldSchema::repeated`），并在 `property_path` 里支持
`Component.field[index]` 之外的"带名字的条目"寻址**——这是阶段 2 的下一步立项，不是本轮能顺手带过的。

**真实工程影响面**（只读清点两个示例工程、排除 `builds/`）：这 4 个组件共 28 个实例
（Tilemap 13、Collider3d 13、Container 1、ButtonStates 1），键集合全部落在新 schema 内；
真实样本已进对拍门（`arena.scene` / `game3d.scene` / `physics3d.scene` / `ui_layout.scene`）。
审计结果与预期一致：两个工程 `schema_errors=0`，`unknown_components` 从 4/9 降到 3/5。
偏松（只漏报不误报）：Collider3d 的形状条件必填与 `layer/mask` 范围、Tilemap 的
`tiles.len()==width*height` 与 `tile_size>0`——都是当前 `FieldRule` 表达不了的跨字段/范围规则。

### 3.24 组件级动作 + 原子多字段提交（第 30 轮，为 `UiLayout` 迁移铺路）

手写面板里有一类**不是字段**的东西：`UiLayout` 的"锚点预设"下拉——它一次改**两个**字段
（`anchors` + `pivot`）。通用编辑器此前只会逐字段提交，直接迁移就会把"一次操作一条 Undo"
变成两条。本轮先把这条能力补上：

1. **编辑器 lib**：`editor::edit_component_payload(component, payload, field, value)` ——
   在**组件串**上按字段编辑（不碰场景）；`edit_component_field` 改为它的薄包装（行为不变）。
   多字段原子编辑与预演共用这条路径，校验顺序仍是"整串 schema → 按字段写 → 引擎解析器兜底门"。
2. **typed action**：新增 `EditorCommand::SetComponentFields { entity, component, fields }`
   （服务层显式拒绝，与 `SetComponentField` 同一条 shell-only 规则）。shell 侧
   `apply_component_fields_edit` 逐字段滚动计算、**任一步失败整体不写**、全无变化 `NoOp`、
   有变化**恰好一条** Undo。
3. **组件级动作层**：`SchemaComponentAction { label, selected, fields }` + `ACTION_PROVIDERS`
   数据表（与 `NOTE_PROVIDERS` 同一思路）。`UiLayout` 的 12 个预设直接来自引擎
   `UiLayoutPreset::ALL`，写入值是引擎编码，选中态由"字段值与预设一致"**推导**（不另存
   "当前预设"状态，因此外部改动会立刻反映；不匹配时显示"自定义"——与手写面板一致）。
4. **视图**：通用编辑器在组件标题下方渲染动作下拉，选中即发一条 `SetComponentFields`。

门与负向对照：`component_actions_come_from_the_engine_presets`（12 个动作、每个写
`anchors`+`pivot`、选中态推导、写回后仍等于该预设）与
`multi_field_action_edit_is_one_undo_and_atomic`（一条 Undo / 未涉及字段原样保留 /
任一步非法整体不写 / 幂等 NoOp）。负向对照见 §4 第 16 条：把"任一步失败整体不写"改成
"出错也提交已算出的部分取值"，测试立刻报 `非法多字段提交必须被拒绝，实际 Applied`。

**下一步**（同一目标的收尾）：`UiLayout` 本身的迁移可以做了——删面板与
`UiLayoutFields`/`set_ui_layout` 缓冲管线、从 `HANDWRITTEN_PANEL_COMPONENTS` 移除，
字段由 schema 生成、预设由本轮的动作下拉接管。

### 3.25 修掉"跑测试时资源管理器自己弹出 docs 目录"（第 30 轮附带修复）

### 3.27 字段级语义规则铺开：纹理引用（第 32 轮）

docs/55 §P0 第 4 条要求"字段级语义校验"从首个个例铺开。本轮把**纹理引用**这条铺到四个组件：

- **共用规则**：`TEXTURE_RULE`（`FieldRule::OptionalProjectPath`，扩展名
  `png/jpg/jpeg/webp`，哨兵 `__white__`）挂到 `Sprite.texture`、`Image.texture`；
  `REQUIRED_TEXTURE_RULE`（`FieldRule::ProjectPath`，同扩展名/哨兵，**空值也拒绝**）挂到
  `Quad.texture`、`Tilemap.texture`。
- **为什么分两种**：引擎解析器口径不同——`Sprite`/`Image` 接受空纹理（`SpriteComponent::default()`
  的编码就是 `texture=`），而 `Quad`/`Tilemap` 明确拒绝空纹理
  （`quad texture must not be empty`）。为此新增 `FieldRule::OptionalProjectPath`
  （与 `ProjectPath` 同一实现，空值放行）。这条差异是"编码器对拍门"**当场逼出来**的：
  先统一要求非空，`builtin_schemas_match_engine_encoders` 立刻报
  `Sprite: schema 无法解析引擎编码 "texture=;size=128x128;…"：不能为空`。
- **刻意更严的显式分歧**：引擎解析器对 `.bmp`/绝对路径/穿越路径**照收**，schema 拒绝——
  与旧手写 Sprite 面板的 `validate_asset_reference` 同一口径，运行时行为不变；分歧写在
  `field_rules_match_engine_validators` 的显式断言＋注释里，别"顺手对齐"。
- **真实工程证据**（关键）：先只读清点了两个示例工程全部 **245** 个 `texture=` 取值——
  199 个 `.png`、28 个 `__white__` 哨兵、其余为省略形态，**没有一个**会被新规则误伤；
  改完后两个工程审计仍是 `schema_errors=0`（8/396、22/402）。

编辑器侧门：`texture_reference_rule_is_enforced_through_the_generic_editor`
（合法值一次 Undo + 引擎读回；hint 里带规则说明；`.bmp`/穿越/绝对/`.lua` 四种非法值全部
`Rejected` 且不产生历史；`Quad` 的空纹理也被拒绝——与引擎同口径）。
负向对照见 §4 第 17 条。

**仍缺的规则形态**：`Sprite/Quad/Image.texture` 之外的资源引用（如 `Tilemap.tiles` 之外的
自定义资源字段）、以及"**引用必须存在**"（需要资源库查询，超出纯字段规则的范围）——
这条留在 §5 的缺口表里。

### 3.28 多选批量 + 混合值：通用编辑器补齐"批量语义"（第 33 轮）

`Sprite`/`Transform`/`Transform3D` 三个组件一直迁不动的真正卡点，是手写面板的**多选批量**：
在面板里改一个字段会写到**所有选中且拥有该组件**的实体上，并且取值不同的字段显示"混合"。
通用编辑器此前只编辑主选中实体——直接迁移就会把批量编辑能力弄丢。

本轮把这一层补上：

- **编辑器 lib**：`SchemaFieldRow.mixed` + `rows_for_selection(&[&SceneEntity])`——以主选中为基准，
  其它选中实体同一字段取值不同就标 `mixed`；**缺少该组件的实体不参与**（它本来就不会被写）。
- **typed action**：新增 `SetComponentFieldOnSelection { component, field, value }` 与
  `SetComponentFieldsOnSelection { component, fields }`（服务层与其它实体级命令一样显式拒绝）。
  这是**唯一一对"读选区"**的命令：批量改写本身就是选区语义，目标集合仍由 `SelectionService`
  决定（选择的唯一事实源），面板不自己算。
- **shell**：`apply_component_edit_on_selection` —— 目标 = 选中 ∩ 拥有该组件；
  每个目标独立走 schema/PropertyPath 校验（`edit_component_payload`），
  **任一目标失败整体不写**；全部无净变化 `NoOp`；否则**一条**历史（多选一次操作 = 一条 Undo）。
- **视图**：多选时字段值仍以主选中为基准显示，混合字段补一个"混合"提示；提交时按目标数
  自动选单实体命令还是批量命令。

门与负向对照：`multi_selection_edit_writes_all_targets_in_one_undo` —— 混合值判定
（`size` 不同 → mixed、`color` 相同 → 非 mixed、没有组件的实体不参与）、批量写两个目标
**一条 Undo**、无变化 `NoOp`、非法值整体不写、**Undo 一步把所有目标一起回滚**。
负向对照 §4 第 18 条：把 shell 改成"只写主选中"，测试立刻报
`实体 2 必须被写入：size=8,8;color=1,1,1,1`；恢复后回到通过。

### 3.32 "引用必须存在"：上下文诊断（第 37 轮）

§5 里长期挂着的一条缺口是"引用必须存在（资源库查询）还没有规则形式"。本轮补上**编辑器侧**的
上下文校验，并明确它的边界：

- `SchemaFieldRow` 新增 `path_rule`（该字段带 `ProjectPath`/`OptionalProjectPath` 规则）与
  `missing_asset`；纯函数 `mark_missing_assets(rows, assets)` 把"带路径规则、取值非空、
  资源索引里找不到"的行标成缺失。
- 视图在字段行右侧给琥珀色 `⚠ 工程内找不到该资源`。**诊断，不是拒绝**——作者经常
  "先写引用、后补资源"（新建场景 → 连资源），拒绝会让这条正常流程走不通；`FieldRule`
  本身仍是纯字段规则，查不了资源库。
- **资源索引为空时不做判断**（例如刚打开工程、索引还没建立），避免整屏假警告。
- 输入刻意是 `BTreeSet<String>` 而不是 `ResourceBrowserState`：这条逻辑与编辑器状态解耦、
  可单测（门 `missing_asset_paths_are_flagged_not_rejected`：只有路径规则的字段参与、
  空索引不判、命中索引不判、缺失判、**缺失仍可编辑**）。负向对照见 §4 第 21 条。
- 真实工程证据：两个示例工程的 `--check` 仍 `schema_errors=0`（这条诊断不改审计口径）。

### 3.33 列表/重复字段模型：`Animation`/`UiEvents`/`UiBindings` 补上 schema（第 38 轮）

第 26 轮留下的模型缺口（docs/57 §4 第 1 条）本轮解决。旧模型是
`ComponentData = BTreeMap<键,值>`，表达不了三种真实编码：位置式段（没有 `=`）、
`|` 分隔导致**同一个键出现多次**、动态键名（`arg.<名>`/`track.<属性>`）。

**引擎侧新增（`core/component_schema.rs`）**：

| 新增 | 作用 |
|---|---|
| `PositionalField { prefix, parts, required }` | 位置式段：`prefix`（`"clip:"`）+ 冒号分隔的参数表；最后一段**吃掉剩余文本**，与引擎的 `splitn(6, ':')` 同口径（`events=2:step` 里的冒号不会被误切） |
| `DynamicField { prefix, field }` | 动态键：键名由作者决定，只有值的类型可声明 |
| `ListModel { separator, positional, dynamic }` | `None` = 一条记录内的重复段（`Animation`）；`Some('\|')` = 多条记录（`UiEvents`/`UiBindings`/`UiAnimation`） |
| `ComponentPayload { Fields, Entries }` / `ComponentEntry` | 解析结果：单条记录仍是扁平映射，列表模型是多条记录（每条 = 字段 + 按顺序的位置式段原文） |
| `parse_payload` / `serialize_payload` | 列表模型的解析/写回；`validate_component`（审计入口）改走 `parse_payload`，单条记录组件行为不变 |
| `serialize` 抽出 `encode_field` | 单条与列表共用一份编码（`Size` 的 `宽x高`、自由文本转义不再有两份实现） |

**三个组件的字段表逐条对着引擎解析器（不是对着旧手写面板）核**：

- `Animation`：`default=<名>` 必填；`clip:<名>:<sheet>:<cols>:<fps>:<looped>[:events=..]` 可重复。
  `looped` 用 `FieldKind::Enum{["true","false"]}` 而不是 `Bool`——引擎只认这两个字面量，
  `Bool` 会多接受 `1`/`0`（比引擎松）。
- `UiEvents`：`|` 多条记录；`event` 的 9 个候选与 `UiEventType::parse` 一一对应，
  `function` 必填（引擎 `MissingFunction`），`arg.<名>` 走动态键。
- `UiBindings`：`|` 多条记录；`property` 的三个候选与 `BoundProperty::parse` 一一对应，
  `target` 必填且**不得为空**（引擎 `MissingTargetOrProperty`），`source` 必填。

**为什么不重新格式化位置式段**：第 2 个 `clip:` 就是第 2 个状态，顺序本身携信息；schema 保留段原文，
于是"引擎写什么、schema 就写回什么"这条**逐字节**断言成立（`serialize` 的字段顺序也按声明顺序 =
引擎编码器的书写顺序）。门 `repeated_field_schemas_round_trip_like_their_engines` 用三条**引擎编码器
自己写出来的串**对拍：解析 → 写回逐字节相等 → 再解析不变 → 审计放行，并附三组否定样本
（缺 `default`、`looped=maybe`、位置参数不够 / 缺 `function`、未知事件名、未知键 /
未知 `property`、缺 `target`、空 `target`）。

**保留的否定对照**：旧测试 `components_with_positional_or_repeated_fields_stay_unregistered`
改名为 `flat_model_cannot_express_positional_or_repeated_fields`——它仍用临时朴素 schema 演示
"扁平模型会静默折叠重复键"（`left: naive_serialize` ≠ `right: 引擎编码`），防止有人把
`ListModel` 又改回按 `;` 切 `key=value`。

**仍然不注册的 1 个：`UiAnimation`**，理由**不是**模型能力：它的串
（`track.<属性>=<t>:<v>:<easing>|…`）目前只有编辑器写过
（`ui_editor::apply_ui_animation_editor`），引擎里**没有任何解析器**（`ui_animation.rs` 只有纯数据与
轨道类型）。给引擎 schema 注册一份"没人消费的格式"就是 `Script`/`EntityScript` 那类缺陷的翻版，
因此这一条留作诚实缺口：**要先把格式落到引擎（解析器 + 往返测试），再补 schema**。

**真实工程证据**：`game_jhyt` / `game_api` 的 `--check` 仍 `schema_errors=0`（新 schema 对
245 个 texture、13 个 Tilemap/ButtonStates 之外的全部实例零误伤），
`unknown_components` 从 3/5 降到 **1/3**。

**顺带查到的下一批缺口（第 39 轮立项）**：审计打印的 `component_no_schema` 明细显示，
剩下"没有 schema"的**不是** `UiAnimation`，而是
`Collider`（2D，31+7 个实例）、`Animation3D`（4 个）、**`ParticleEmitter`**——
最后一个正是 `Script`/`EntityScript` 那类**键名漂移**：注册表里写的是 `Particle`，
而运行时（`typed_scene.rs` 的编译表、`script.rs`、`renderable.rs`）读的是 `ParticleEmitter`。
也就是说真实工程里的粒子组件一直被报"没有 schema"，而注册表里那份 `Particle` schema
描述的是**没人消费的组件名**。这条已写进 docs/57 §4。

### 3.34 键名漂移（第 2 例）+ 两个漏掉的组件 + 机械化守卫（第 39 轮）

第 38 轮把审计的 `component_no_schema` 明细当成一份清单，本轮照着它收口。结果里藏着一个
**真实缺陷**，而且是第 3 轮 `EntityScript`/`Script` 那一类：

**① `Particle` → `ParticleEmitter`（键名漂移）**：注册表里写的是 `Particle`，而运行时
（`typed_scene` 的编译表、`script.rs`、`renderable.rs`）读的是 `ParticleEmitter`。后果与当年
一模一样且更隐蔽：真实工程里的粒子组件**一直被审计报"没有 schema"**，而注册表里那份 schema
描述的是一个**没人消费的组件名**（既没校验真实实例，也没让编辑器接管它）。
修法是把注册表的键改成运行时那个名字；编辑器也因此第一次接管了粒子组件
（`game_api` 里有真实实例，此前在 Inspector 里没有任何字段行）。

**② 补 `Collider`（2D）与 `Animation3D`**：审计明细里剩下的真实缺口，字段表逐条对着引擎解析器核
——`Collider.shape` 是 `Enum{ball,cuboid}`（引擎只认这两个）、`radius`/`half_width`/`half_height`
保持 optional（"`radius` 只跟 `shape=ball` 搭配"是**跨字段**规则，标 required 会对真实串误报，
与 `Collider3d` 同一处理）；`Animation3D` 的 `mesh`（工程内相对路径 + glb/gltf 规则）与 `clip`
required、`looped` 是 `Enum{true,false}`。2D `Collider` 没有编码器，因此走 `Collider3d` 那条
"真实串 + 引擎解析器确认"的半证据；`Animation3D` 有 from/to，进**逐字节**对拍门。

**③ 机械化守卫（本轮最重要的一条）**：给 `typed_scene::ComponentId` 加 `ALL` + `as_str()`
（运行时名字的唯一出处），新增测试 `every_component_id_the_runtime_knows_has_a_schema` 遍历它，
断言"运行时认识的每个组件名都在 schema 注册表里"，并额外钉住 `Particle` 旧键名不得复活。
**为什么必须机械化**：前两例漂移都是靠人偶然发现的，逐个写断言挡不住第三例。

**④ 编辑器侧的新能力（注册 schema 即自动接管）**：`Collider`/`Animation3D`/`ParticleEmitter`
都不在 `HANDWRITTEN_PANEL_COMPONENTS` 里，所以注册后通用编辑器**一行 match 都没改**就接管了它们。
新增 bin 侧测试 `newly_registered_components_are_editable_through_the_generic_editor` 验证：
`shape`/`looped` 拿到候选下拉、`SetComponentField` 改半径与片段名各一条 Undo、引擎解析器能读回
（`Ball(20.0)` / `clip=Running_A`）、**跨字段**不变量（`shape=ball` 的半径必须为正）由引擎兜底门
拒绝、**路径**规则（绝对路径 `C:/models/hero.glb`）由 schema 在写入前拒绝，且两种拒绝都不产生历史。

**真实工程结果**：两个示例工程的 `--check` 首次同时达到 `schema_errors=0` 与
**`unknown_components=0`**（`game_jyht` 396 个、`game_api` 402 个组件实例全部被 typed schema 覆盖；
本轮之前是 3 / 5）。仍未注册的只剩编辑器专属的 `UiAnimation`（引擎里没有它的解析器，见 §3.33），
而它不出现在任何场景文件里。

### 3.35 `UiAnimation`：把格式搬进引擎，最后一格 schema 补齐（第 40 轮）

第 38/39 轮之后唯一"没有 schema"的组件是 `UiAnimation`，而它的障碍**不是模型能力**：
`track.<属性>=<时间>:<值>:<缓动>` 这份格式此前**只有编辑器实现**
（`ui_editor::parse_ui_animation_component` / `apply_ui_animation_editor`），引擎里
`ui_animation.rs` 只有纯数据与轨道类型。给引擎 schema 注册一份没人消费的格式，
正是 `Script`/`EntityScript`、`Particle`/`ParticleEmitter` 两代键名漂移的同类问题——
于是本轮先把**格式搬进引擎**，再补 schema：

- 引擎新增 `UiAnimationClip::tracks_from_component_str` / `tracks_to_component_str`：
  `|` 分隔多条轨道、每条是动态键 `track.<属性名>`、关键帧三元组用 `,` 分隔；
  数字定长 3 位小数（**磁盘上既有数据的形态**，编辑器一直这么写），
  轨道顺序 = `BTreeMap` 字典序（与 `UiEvents`/`UiBindings` 的多记录格式一致）。
  解析沿用原有的全部校验（`track.` 前缀、三元组、缓动白名单、时间严格递增且有限）。
- 编辑器改为**只调用引擎**：`parse_ui_animation_component` 变成薄包装（只负责把轨道装进
  预览用的 clip，`name = "preview"` 是预览概念、不属于组件契约），
  `apply_ui_animation_editor` 直接用引擎编码器——**两份事实源合并成一份**。
- schema 注册 `UiAnimation`（列表模型：`separator = Some('|')`、动态键 `track.`）。
  **边界（偏松，只漏报不误报）**：schema 这层只校验"值非空"，
  键帧三元组语法与"时间严格递增"由引擎解析器负责——写入路径上的
  `typed_scene::validate_component_payload` 会跑它，所以编辑器写不出非法串；
  不为它加 `FieldRule` 是刻意的：那会把三元组语法复制成第二份实现，
  正是本轮要消除的东西。这条边界在测试里被**同时钉住两侧**
  （同一个非法串：schema 放行、引擎解析器拒绝）。

**门与证据**：`component_str_round_trips_and_rejects_malformed_input`（引擎：多轨道/多关键帧/
三种缓动逐字节往返 + 6 类非法串拒绝）、`repeated_field_schemas_round_trip_like_their_engines`
新增第 ④ 组（引擎编码 → schema 读 → schema 写回逐字节相等 + 动态键各自成一条记录）。
编辑器侧 `handwritten_panels_are_disjoint_from_the_generic_editor` 的"有面板却缺 schema"
清单**现在是空的**（并补了反向断言：有手写面板的组件必须都有 schema）。

### 3.36 Hierarchy 类型过滤：`type:`/`component:` 查询（第 41 轮）

docs/55 §5 的 P1 里 Hierarchy 有"类型过滤"，此前过滤框只做**名称子串**。本轮把它做成一个
最小的查询语言（`HierarchyFilter`），不动面板写入棘轮、不动文档数据：

| 词 | 语义 |
|---|---|
| 自由文本 | 实体**名称**必须包含它（与既有行为一致，大小写不敏感） |
| `type:<模式>` / `component:<模式>` | 实体必须有**至少一个组件名**包含该模式（子串、大小写不敏感） |
| 多个词 | **全部 AND**（`leaf type:sprite` = 名字像 leaf 且有 Sprite） |

三条刻意行为（都写进了测试）：① `type:` 后为空（刚输入到一半）**不算过滤**——否则每敲一个
前缀就会瞬间清空整棵树；② 类型词用的是**子串**而不是精确名，`type:ui` 一次找出
`UiLayout`/`UiEvents`/`UiAnimation`/`UiBindings`；③ 祖先行的可见性语义不变
（命中者与它的祖先路径可见，计数只算**自身**命中的实体）。

**实现与性能**：`HierarchyMatchIndex` 的匹配入口从"小写化查询串"改成 `HierarchyFilter`，
小写化缓存 `HierarchyNameCache` 升级为 `HierarchyLowerCache`（名称 + 组件名，仍按文档修订缓存，
改过滤词只做 `contains`，不重算 10k 条）；解析结果随扁平化缓存一起存下，绘制时不再逐行解析。
2D/3D Scene View 的过滤只吃**名称词**（`matches_name`）——类型词管 Hierarchy 的行可见性，
不该让视口里的对象凭空消失。

**门与证据**：
- `type_filter_matches_components_and_combines_with_name_terms`：`type:sprite` 的可见行与计数、
  `type:ui` 的子串多命中、`component:SPRITE` 的别名与大小写、名称词 AND、
  只输入一半的 `type:`、以及不认识的 `type:nope`（空结果 ≠ 没有过滤）。
- `match_index_is_equivalent_to_recursive_reference` **扩容**：样本树的每个实体都插了两种组件，
  查询表新增 6 个（含类型词、类型词+名称词、大小写、`type:`），索引与"逐行递归"参考实现
  逐实体等价——优化不得改变可见性语义这条继续由它守。
- 过滤框的占位文本直接写语法提示（`type:Sprite` / `component:ui`），
  这样 UI 变化与文档一致，不需要另写一段用户手册。

### 3.37 Inspector 字段搜索 + 引用选择器（第 42 轮）

docs/55 P1 的 Inspector 一条："搜索、引用选择器"。两者都建立在**已有的字段行**上，
不动文档、不动棘轮：

**① 字段搜索（`filter_field_rows`，纯函数）**：查询词按空白切分，**每个词**都必须在
"组件名 / 字段名 / 路径 / 当前值"里出现（大小写不敏感子串）才保留该行。
- 为什么是"全部词 AND"：Inspector 的用法几乎都是"把某类字段找出来"
  （`texture`、`sprite texture`、`camera fov`），AND 是唯一不会越搜越多的语义；空查询原样返回。
- **搜索覆盖当前值**，所以可以"按资源路径反查哪个字段引用了它"
  （`player.png` → `Sprite.texture`）。这条也意味着 `nope` 这种词会命中
  `MeshRenderer.mesh = assets/models/nope.glb`——测试里专门留了注释说明这个语义。
- 视图：搜索框 + 命中计数（`匹配 N / M 行字段`），只影响呈现。

**② 引用选择器（`picker_candidates`，纯函数 + 视图下拉）**：带路径规则的字段
（`Sprite.texture`/`Image.texture`/`MeshRenderer.mesh`/`Animation3D.mesh` …）旁边多一个
**"资源…"下拉**，列出工程资源索引里**扩展名匹配**的路径，选中即提交（一条 Undo）；
可选字段还提供"（不指定）"（写空串）。
- 候选规则（扩展名白名单）与 `FieldRule::ProjectPath` **同一份事实源**：
  `SchemaFieldRow` 新增 `path_extensions`，由字段规则直接取出——不另写一张表，否则必然漂移。
- 当前值不在候选里也会被放进列表（否则下拉显示不出当前选中的东西），反斜杠写法按组件串的
  约定归一成正斜杠。资源索引为空时不画选择器（作者仍可手打路径）。

**门与证据**：`field_search_is_and_over_component_field_path_and_value`（空查询/单词/
多词 AND/词序与大小写/按值搜索/不存在的词）、`picker_candidates_follow_the_extension_whitelist`
（扩展名过滤 + 排序去重 + 空白名单 = 全部 + 当前值兜底 + 大小写不敏感）、
bin 侧 `field_search_and_reference_picker_are_driven_by_the_schema`（视图侧证据：
`Sprite.texture` 行确实带 `["png","jpg","jpeg","webp"]`、颜色字段不长选择器、搜索框状态真的
驱动 `schema_field_rows`、候选来自资源索引）。负向对照见 §4 第 26/27 条。

### 3.38 Gizmo 变换空间：World / Local（第 43 轮）

docs/55 P1 的 Gizmo 一条里，"吸附"早已有（`snap_enabled`/`snap_step`，见 §5 的场景交互行），
缺的是**变换空间**。本轮补 `GizmoSpace { World, Local }`：

- **它是独立类型，不进 `ToolStateMachine`**：状态机管"现在在做什么"（工具/相位），空间管
  "沿着什么方向做"。两者正交，混在一起会让状态机的转移表凭空多一倍。
- **默认 `World` = 既有行为一字不改**（这一条本身就是兼容性门：默认值必须与迁移前一致）。
- **拖拽语义**（真正的功能）：`gizmo_axis_world(space, rotation, axis)` 决定 Move 用哪根轴
  （局部模式 = 实体自身的旋转作用在世界单位轴上）；`gizmo_rotate(space, rotation, angle)`
  决定 Rotate 是**左乘**（绕世界 Y 公转）还是**右乘**（只改自身朝向、自己的 Y 轴保持不动）。
- **健壮性**：四元数非法（零长度/非有限）时退回世界轴并保持原姿态——一个坏旋转不该让手柄
  整根消失、连修都修不了。这条写在函数注释里，并有断言。
- **持久化**：随布局保存（`gizmo_space: "world"|"local"`），未知值/缺失字段收敛回 `world`
  （前向兼容：旧布局文件照常加载）；`EditorContextSnapshot` 也带上它，Play/Stop 能恢复。
- **UI**：场景右上角工具条在需要方向的工具（选择/移动/旋转/缩放）下多一个"世界/局部"切换。
  刻意不做快捷键：W/E/R/Q 已被工具占用，`X`/`Z` 之类的猜测键位不如显式按钮诚实。

**边界（诚实缺口）**：Gizmo 的**绘制**仍是固定屏幕方向的三根臂（不随相机投影/实体旋转改向），
所以局部模式在视觉上只有工具条上的"局部"标签与其拖拽结果能看出来——按相机投影画真实轴
（并让命中检测跟着走）是下一步，已记进 docs/57 §4。

**门与证据**：`gizmo_local_axes_follow_the_entity_rotation`（绕 Y 转 90° 后局部 X → 世界 -Z、
局部 Z → 世界 +X；世界模式与旋转无关；单位旋转下两空间一致；坏四元数退回世界轴；
Free/Scale 没有方向）、`gizmo_rotation_space_picks_world_or_own_axis`（局部右乘保持实体自己的 Y，
世界左乘带动朝向，且等于把初始朝向整体绕世界 Y 转 angle；角度 0 与 NaN 都不改姿态）、
`gizmo_space_round_trips_and_toggles`（默认/字符串/未知值/切换/标签）、
`gizmo_space_persists_and_converges`（布局往返 + 损坏值收敛 + 缺字段前向兼容）。
负向对照见 §4 第 28 条。

### 3.39 资源重命名/移动 + 引用保持（第 44 轮）

docs/55 P1 的 Project Browser 一条里，"文件监听/增量导入/收藏/依赖视图"此前已有，
缺的是**移动/重命名时的引用保持**。本轮补上，并把它做成**可单测的纯层 + 一层薄 shell**：

**① 纯层（新模块 `editor::resource_ops`）**

| 函数 | 职责 |
|---|---|
| `rewrite_component_reference(payload, from, to)` | 改**一个组件串**里的引用，`Option<新串>` |
| `rewrite_scene_references(scene, from, to)` | 改一份场景，返回改动的组件数 |
| `rewrite_project_references(root, from, to, skip)` | 遍历工程里的 `.scene`/`.prefab`，**解析成功才写回**，坏文件原样保留并进 `RewriteReport.failures` |
| `normalize_relative` / `paths_match` | 工程内相对路径闸门（拒绝绝对路径与 `..`）与同文件判定 |

**两条安全纪律**（都在测试里钉住）：
1. **只替换整段取值**：`texture=assets/a.png` 里的 `assets/a.png` 会换，但
   `texture=assets/a.png.backup`（更长路径）和 `texture=a.png`（更短）**不动**。
   子串替换是这类功能最经典的静默数据损坏——负向对照 §4 第 29 条就是把它演示出来。
   位置式段（`Animation` 的 `clip:<名>:<sheet>:…`）按冒号参数逐个做**相等**比较；
   没有"这是路径"标记，因此调用方必须传资源路径（已在注释与测试里写明）。
2. **解析失败不覆盖**：`Scene::load` 失败的文件一律跳过；测试里那个坏文件在整次操作后
   逐字节不变。

**② shell 层（`actions.rs::perform_resource_move`）**：顺序刻意是
**先校验 → 再搬文件 → 最后改引用**：
- 目标已存在 / 越出工程根 / 正在 Play / 目标是当前打开的文档 → 直接拒绝（不做半截操作）；
- 文件搬完再改引用：即使改引用失败，磁盘上也只可能是"文件已改名 + 部分文档仍指向旧路径"，
  这是**可诊断**的状态（审计会报断链），而不是"文档指向不存在的文件却没人知道"；
- **当前打开的文档不写磁盘**（保住未保存的编辑），而是在内存里改写并进 history
  （一条 Undo 可回退引用改写；文件改名本身不回退，与 Unity 的取舍一致），改完标记未保存；
- 最后刷新资源索引、迁移缩略图键、选中新路径，并把"改了哪些文件/多少处引用/哪些文件没改"
  汇总进状态栏。

**③ 视图**：资源面板右键 →「重命名…」出现内联输入行（确定/取消/回车），确认走 shell 方法；
被拒绝时保留输入并显示原因（作者改个名字就能重试）。

**门与证据**：`rewrites_only_whole_reference_values`（整段替换、子串不动、反斜杠归一化、
空 `from` 无效）、`rewrites_positional_clip_sheet_and_multiple_records`（位置式 `clip:` 的
`sheet`、`|`/`;` 分隔符原样保留）、`project_rewrite_updates_documents_and_skips_broken_files`
（只改引用了资源的文档、坏文件逐字节不变、`skip` 的当前文档不碰磁盘）、
bin 侧 `rename_resource_keeps_references_and_refuses_unsafe_targets`
（端到端：文件真的改名、其它文档磁盘上已改写、当前文档内存改写且**多一条 Undo**、
`C:/…` 与"已存在的目标"被拒绝且文件未动、选区跟到新路径）。

**边界（诚实缺口）**：只处理 `.scene`/`.prefab`；不改 `.lua` 脚本里的字符串引用、
不改资源内部的相互引用（例如材质指向的纹理）、不改 `project.toml` 的
`startup_scene`；重命名**当前打开的文档本身**被拒绝（尚未实现）；跨工程移动不支持。

### 3.40 Gizmo 手柄按相机投影绘制 + 命中检测跟随（第 45 轮）

第 43 轮留下的缺口：手柄画的是**固定屏幕方向**的三根臂，于是"局部"模式在画面上完全看不出来。
本轮把方向改成**真实世界轴的投影**（`gizmo_screen_axes`）：

- 每条臂 = `project(position + world_axis) - screen` 归一化到臂长；`world_axis` 由
  `gizmo_axis_world(space, rotation, axis)` 给出（第 43 轮的局部/世界语义原样复用），
  因此**实体转多少、手柄就转多少**，相机绕转时手柄也跟着走；
- **命中检测用同一份方向**（`pick_gizmo_axis` 的参数从"臂长"换成"三条臂向量"），
  "看到哪里就点哪里"成立——不再是"看起来在左上、实际要按旧的固定位置点"；
- **退化保护**：轴几乎与视线平行（投影长度 <1px）或投影失败时，那根臂退回固定方向
  （X 右 / Y 上 / Z 斜向左上，与旧版观感一致）。没有这层保护，正俯视时 Z 臂会缩成一个点、
  既看不见也抓不到。
- 旋转/缩放手柄跟随投影：旋转手柄挂在 X 臂方向、"等比缩放"手柄沿 X+Y 臂的对角方向。

**门与证据**：`gizmo_axes_follow_the_camera_projection`（假投影下世界 X→屏幕右、世界 Y→屏幕上、
世界 Z 与视线平行→**退回固定方向**；局部模式绕 Y 转 90° 后局部 Z 朝世界 +X；
投影完全失败时三条臂都退回固定方向；同一屏幕位置在不同方向表下命中不同的轴）、
`gizmo_hit_testing_respects_tool_and_lock_state`（扩成三条臂逐一命中 + 中心 Free +
锁定时不给 Free + Scale/ TilePaint）。负向对照见 §4 第 30 条。
**边界**：手柄仍画在实体自身位置（**轴心模式 Pivot/Center 未做**）；命中仍按**端点圆**判定，
没有做"点到线段距离"的细判定。

### 3.41 Gizmo 轴心模式：Pivot / Center（第 46 轮）

docs/55 P1 的 Gizmo 一条最后一块：**轴心**。与第 43 轮的变换空间正交——空间管"沿哪个方向"，
轴心管"绕哪一点"，因此同样是独立类型 `GizmoPivot { Pivot, Center }`（**默认 `Pivot` = 迁移前行为**）。

两处语义，都在纯函数里：

| 位置 | `Pivot`（默认） | `Center` |
|---|---|---|
| 3D 手柄原点（`gizmo_origin`） | 实体自身原点 | 实体 **AABB 中心**（原点在脚下/左上角的模型、九宫格 UI 会明显不同） |
| 2D 旋转/缩放的轴心（`scene_drag_pivot`） | **主选中实体**自身位置 | 拖动集合的位置平均（多选时才是"绕整体中心转"） |

- 2D 这条改的是既有的 `pivot` 参数：**原来永远是集合平均**，所以多选旋转/缩放一直绕整体中心；
  现在"轴心"模式改为绕主选中实体自己——单选时两种模式完全等价（这正是默认模式下行为不变的原因，
  测试里专门断言了这一点）。
- 主选中不在拖动集合里（选区刚变化等）时 `Pivot` 退回平均，**不退化成 (0,0)**（否则旋转会跳到
  世界原点）。
- 手柄命中检测用的仍是同一份原点（`screen` 由 `gizmo_origin` 投影而来），所以"看到哪里点哪里"
  这条在第 45 轮建立的纪律继续成立。

**UI/持久化**：工具条上与"世界/局部"并排的"轴心/中心"开关；随布局持久化
（`gizmo_pivot: "pivot"|"center"`），未知值/缺失字段收敛回 `pivot`（前向兼容），
`EditorContextSnapshot` 也带上它，Play/Stop 能恢复。

**门与证据**：`gizmo_pivot_mode_moves_the_origin_and_the_2d_center`（AABB 中心 = 高度一半处；
2D 多选下 `Pivot`=(10,4) vs `Center`=(5,2)；主选中不在集合里时退回平均；单选时两种模式等价）、
`gizmo_pivot_round_trips_and_toggles`（默认/字符串/未知值/切换/标签）、
`gizmo_space_persists_and_converges` 扩成同时覆盖两个字段（往返、损坏值收敛、缺字段前向兼容）。
负向对照见 §4 第 31 条。

**边界**：3D 的旋转/缩放仍作用在实体自身（`Center` 只改手柄原点）——"绕选区中心公转"需要把
旋转增量同时作用到位置上，且与局部空间叠加时语义需要另行定义；多选时 3D 手柄仍只作用于
首个选中实体。这两条都写在 docs/57 §4。

### 3.42 嵌套 Prefab：检测、环检测与创建边界（第 47 轮）

docs/55 P1 的 Prefab 一条里，"嵌套/变体"是最大的一块。编辑器**不支持嵌套**这一条一直写在 §5
的缺口清单里；本轮把"不支持"从注释变成**可查、可测、会在边界上拒绝**的事实——不支持的下一步
不该是"悄悄生成一份坏数据"。

**① 引擎侧事实源**：`Prefab::nested_sources()` 返回这份 Prefab 内部所有
`prefab.source` 元数据（去重排序）。非空即"嵌套"，而且是**唯一**的判定口径
（编辑器与引擎不再各写一份）。`PREFAB_SOURCE_META_KEY` 常量同时把 `"prefab.source"`
这个字符串约定固定下来。

**② 编辑器侧扫描器**（新模块 `editor::prefab_graph`，纯函数）：
`scan_prefab_nesting(root_source, load)` 做 DFS，返回
`PrefabNesting { nested, transitive, cycles, max_depth, truncated_at }`：
- **环检测**（A→B→A、自环）：把环记进 `cycles`，而不是递归到栈溢出——这正是"嵌套数据
  写坏之后"最先炸的地方；
- **菱形依赖不是环**（A→(B,C)→D 只报一次、深度 3）：用"每个源见过的最大深度"做去重，
  错误地把它判成环会让正常资源图被误报；
- **深度上限 16**，超限的源进 `truncated_at` 并出现在诊断文本里；
- 用**加载闭包**当输入，扫描逻辑与文件系统无关（没有工程的单测就能把环、菱形、超深链跑完）。

### 3.43 3D 旋转/缩放绕轴心公转（第 48 轮）

第 46 轮留下的缺口：3D 里 `Center` 模式只改手柄原点，旋转/缩放仍作用在实体自身。
本轮把两条工具都接上轴心：

- **旋转**：`gizmo_rotation_delta(space, rotation, angle)` 给出**世界空间增量**
  （世界模式绕世界 Y；局部模式绕实体**自己的 Y**，即 `rotation.rotate(Y)`）。
  实体朝向 = `delta * rotation`；`pivot = Some(中心)` 时位置 = `pivot + delta.rotate(offset)`，
  即**绕轴心公转**，到轴心的距离不变。`pivot = None`（默认 `Pivot`）时位置不动。
- **缩放**：`gizmo_scale_about(initial, pivot, factor)`：等比缩放；`Some(中心)` 时位置按同一比例
  远离/靠近轴心（与 2D 的 `scene_drag_transform` 同语义），系数下限 0.05 不变。
- **公转中心在拖动开始时记下**（`GizmoDrag.pivot`，来自 `gizmo_origin`）：拖动过程中实体在动，
  如果每帧重算中心就会漂移。
- **实现只有一份**：原来的 `gizmo_rotate`（左乘/右乘两个分支）被删除，统一成
  "增量 + 组合"（`gizmo_rotation_delta` × `gizmo_rotate_about`），
  旧的局部/世界语义测试改为走生产路径断言——不会出现"两条实现慢慢分叉"。
  世界/局部两种空间下 `delta * rotation` 与旧实现数学等价（浮点末位有差，测试按分量容差比较）。

**门与证据**：`gizmo_rotate_and_scale_about_the_pivot`（原地旋转位置不动、绕原点转 90° 到
`(0,0,-1)` 且距离不变、轴心=自身时与原地等价、增量与生产路径一致、局部增量绕自身 Y、
缩放的推离/系数下限），`gizmo_rotation_space_picks_world_or_own_axis` 改为走
`gizmo_rotate_about` 的 `Pivot` 分支（保留原有语义断言）。负向对照见 §4 第 33 条。

**剩余缺口**：多选时 3D 手柄只作用于首个选中实体（"多选整体绕中心"要等 3D 多选手柄本身）；
命中仍按端点圆判定。

### 3.45 修掉"导入资源弹窗无限重开"（第 49 轮，用户报障）

**症状**：打开编辑器后「导入资源」进度弹窗不停重开（每帧一次），并伴随每轮一个新的后台导入线程。

**根因**（`resource_browser_state.rs` + `import.rs` 的组合）：
`start_resource_import` 是**每帧**调用的——只要 `pending_imports` 非空就再起一次导入、重开弹窗。
而 `pending_imports` 对 `Discovered`/`Stale`/`Missing` 三种状态**无条件**重新排队，
"已尝试"记录 `import_attempted` 只在 `ImportFailed` 分支被查询。于是只要工程里存在**一个
永远到不了 `Ready` 的资源**（该类型没有真正注册、文件已缺失、导入跑完状态不变……），
每次刷新它都回到待导入队列 → 弹窗和线程无限重复。修前那段注释写着"避免失败项在每次刷新后
无限重试"——意图是对的，只是漏了另外三种状态。

**修法**（`resource_browser_state.rs`）：把 `import_attempted` 从 `HashSet<PathBuf>` 升级为
`HashMap<PathBuf, u64>`，存**尝试时该文件的签名（mtime；缺失记 0）**，判据统一成
"状态未完成 **且** 签名与尝试时不同"：
- 内容没变 → 不再自动重试（弹窗停下）；
- 内容变了（签名变）→ 自动再试一次（保留原有 `staled_files_are_pending_even_after_attempt` 语义）；
- 文件缺失（签名 0）→ 尝试一次后停止；文件后来出现（签名非 0）→ 自动重新排队。
另外新增 `clear_import_attempts()`，接在**用户显式刷新**的两条路径上（资源面板「刷新」按钮、
菜单「资源 ▸ 刷新资源」）：显式刷新就是"再试一次"的明确意图，不该被去重守卫挡住。

**顺带**：新增的 `current_signatures` 让 `ResourceBrowserState` 变大，触发了 clippy 的
`large_enum_variant`（`RefreshPoll::Ready(RefreshResult)` 内联了它）。按 clippy 建议把载荷
改成 `Box<RefreshResult>`——`Pending`/`Stale` 是热路径，这个枚举不该每个值都背几百字节。

**门与证据**：`unchanged_assets_are_not_retried_after_attempt`（尝试后同内容不再排队 →
再刷新仍为空 → 显式刷新能强制重排 → 内容变化自动重排）；既有的
`failed_imports_are_not_automatically_retried_after_attempt` 与
`staled_files_are_pending_even_after_attempt` 保持通过，证明语义只收紧"同一内容"这一条。
负向对照见 §4 第 34 条。

### 3.46 变换组件统一（阶段 1）：迁移引擎（第 50 轮，用户需求）

**需求**：编辑器里只保留**一个** `Transform` 组件，不再区分 2D/3D。选定的路线是
**统一到引擎的单一组件**（3D 表示）+ **打开时在内存里迁移、标记未保存**（磁盘文件在用户保存前
一字不动，与 `LuaScript`→`Script` 的既有纪律一致）。

这是一次破坏性改动的**阶段 1**，只做"迁移引擎"本身，不动任何消费者（因此本阶段结束后
验证组与既有行为一字不变）：

- 新增 `engine::core::transform_migration`：
  - `TRANSFORM_COMPONENT = "Transform"`（统一后的唯一组件名）、
    `LEGACY_TRANSFORM_3D_COMPONENT = "Transform3D"`（旧名）；

    （`position/rotation/scale`）只需**改名 + 规范化数字格式**；2D 旧串
    （`x=..;y=..;rotation=..;scale_x=..;scale_y=..`）升级为 `position=(x,y,0)`、
    绕 Z 的四元数、`scale=(sx,sy,1)`；
  - `migrate_scene_transforms(&mut Scene)`：场景级入口，返回
    `TransformMigrationOutcome { changed_entities, skipped }`。
- **换算复用渲染路径的 `LocalTransform::from_2d`**，不另写一份——否则"2D 旋转是绕哪个轴、
  什么方向"迟早分叉（这正是本仓库反复吃过的亏）。
- **幂等**：统一写法读进来返回 `None`，迁移跑第二遍是 0 改动（否则文档会永远 dirty）。
- **合并策略明写**：同一实体两种写法并存时**以显式 3D 为准**，2D 旧键丢弃（测试钉住）。
- **坏数据原样保留**：解析失败既不删也不改写，进 `skipped` 并带上实体与原因——宁可让作者在
  审计里看见一个坏组件，也不猜着造一份"看起来能跑"的数据。

**门与证据**（`transform_migration` 模块 5 条）：2D 升级的数值与"与 `LocalTransform::from_2d`
同源"逐项相等、统一写法幂等 + 改名算一次改动、两种写法并存时 3D 优先、坏串原样保留并进
`skipped`、非变换组件与无变换实体的实体不受影响。负向对照见 §4 第 35 条。

### 3.47 相机组件统一（阶段 1 续）：迁移引擎（第 51 轮，与 §3.46 同一需求）

用户追加"camera 组件同理"，因此相机走同一套纪律（内存迁移、幂等、坏数据不猜），
但**映射按语义定**——相机不像变换那样同构，这一步不能照搬：

| | 2D 相机 | 3D 相机 |
|---|---|---|
| 本质 | **正交视口** | **透视相机** |
| 字段 | `center` / `rotation` / `zoom` / `bounds` | `position` / `target` / `fov` / `near` / `far` / `pose` |
| 共用 | `enabled` | 同左 |

**不做"把 2D 相机改造成透视相机"这种会改变画面的映射**，而是让统一组件用一个显式的
**投影判别字段**承载两种语义（判别字段写在最前，便于检索与人工核对）：

```text
projection=orthographic;center=..,..;rotation=..;zoom=..[;bounds=..][;enabled=false]
projection=perspective;position=..,..,..;target=..,..,..;fov=..;near=..;far=..[;pose=transform][;enabled=false]
```

- 迁移只做三件事：**改名**（`Camera2D`/`Camera3D` → `Camera`）、**补判别字段**、
  **规范化数字格式**（数字格式交给各自既有的编码器，不重写）。
- 判别字段**不参与**各自解析器的语义：`split_projection` 先把它摘出来，剩余字段仍交给
  `Camera2D::from_component_str` / `Camera3D::from_component_str` 校验——**旧解析器可以原样读回
  去掉判别字段的串**，这条在测试里直接断言。
- 手写/早期数据里的 `Camera` 若没写判别字段：按**字段集合**判定（出现 `center`/`zoom`/`bounds`
  → 正交；出现 `position`/`target`/`fov`/`near`/`far` → 透视）。判据是"哪套字段存在"，
  不是对数值的猜测；**两套都出现或都没有 → 不猜**，进 `skipped` 并原样保留。
- 两个旧名并存时以 `Camera3D` 为准（与变换统一同一策略），另一个键丢弃。

**门与证据**（`camera_migration` 模块 6 条）：2D 迁移的串与"2D 编码器自己写出的串 + 判别前缀"
逐字节相等且去掉判别字段后旧解析器能读回、3D 迁移后 `fov` 仍是角度且 `pose=transform` 保留、
场景级改名 + 幂等（第二遍 0 改动）、两个旧名并存 3D 优先、缺判别字段按字段集合判定（含歧义
与空载荷报错）、坏数据原样保留且非相机组件不受影响。负向对照见 §4 第 36 条。

**后续阶段**：与 §3.46 合并推进（阶段 2 编辑器接迁移 → 阶段 3 编辑器 2D 路径切统一字段 →
阶段 4 typed_scene / 运行时 / Lua / schema 注册表 / 审计别名 / 示例与 docs 收口）。

### 3.48 统一组件的**读侧**（阶段 2）：两个读取器（第 52 轮）

阶段 1 只做了"把旧写法改写成统一写法"的迁移引擎。真要让编辑器**开始写出**统一写法，
必须先把**读侧**补齐——否则用户一保存，运行时就读不懂自己的场景了。所以阶段 2 先做读取器：

- **`LocalTransform::from_unified_component_str` / `to_unified_component_str`**
  （`core/spatial_transform.rs`，与 2D↔3D 换算的 `from_2d`/`from_3d` 同处一地）：
  同一份实现吃两种历史写法——统一/3D 写法（`position/rotation/scale`）与 2D 旧写法
  （`x/y/rotation/scale_x/scale_y`，按 `from_2d` 映射）。两种写法的键集合不相交
  （`position` vs `x`），所以判定顺序不影响结果；真正畸形的串两边都失败，**返回底层解析器的
  原文**。写出侧委托 `Transform3D::to_component_str`，数字格式只有那一份实现。
- **`CameraComponent { Orthographic(Camera2D), Perspective(Camera3D) }`**
  （`core/camera_migration.rs`）：统一 Camera 的**取值类型**。消费方拿到它之后**按投影分支**
  处理，而不是按组件名——这正是"不再区分 2D/3D 组件"要表达的语义。`from_component_str(name, payload)`
  同时接受 `Camera2D`/`Camera3D`/`Camera`（含缺判别字段的兼容路径），并提供
  `projection()`/`enabled()`/`as_orthographic()`/`as_perspective()`/`to_component_str()`。
- **顺带去重**：两个迁移引擎改为调用读取器（`unified_transform_payload` → `LocalTransform` 读取器；
  `unified_camera_payload` → `CameraComponent`），因此"迁移怎么理解旧数据"与"运行时怎么理解
  新旧数据"**共用一份实现**，不会各自漂移。

**门与证据**：`unified_transform_reader_accepts_both_historical_shapes`（3D 写法读入与
`from_3d` 逐项相等且规范化后逐字节相同、2D 旧写法与 `from_2d` 逐项相等、读→写→读稳定、
畸形串被拒且给出底层文案）；`unified_camera_reader_branches_on_projection_not_on_component_name`
（旧名照读并落到正确分支、`enabled` 透传、统一写法读→写→读稳定、**判别字段与字段体不匹配时报错

### 3.49 统一组件读侧接线 + 编辑器取消 3D 重复项（阶段 3，第 53 轮）

阶段 2 做出了读取器，这一轮把它**接到真正的读路径**上，并按要求把编辑器里的 3D 重复项撤掉。

**① 引擎读侧（`typed_scene` + Lua 桥接）**
- `typed_scene::compile_component` 的 `Transform` 分支改为**按形态分流**：能按 2D 旧写法解析
  就落到 `ComponentId::Transform2D`（既有行为一字不改），否则按统一读取器解析并落到
  `Transform3D`。`Camera` 分支同理：按 `projection` 判别字段（含缺字段的兼容判定）
  落到 `Camera2D`/`Camera3D`。**消费方（2D 渲染 / 3D 渲染 / Lua）一行都没改**——
  统一只发生在"名字 → 类型化变体"这一层，这正是把风险压到最小的做法。
- `script.rs` 的 Lua 桥接：`Transform` 按形态分流到既有的 2D/3D 插入路径（`Transform3D` 旧名照旧），
  `Camera` 按投影落回 `Camera2D`/`Camera3D` 两条既有路径。**两种形态都读不了时仍然报错**
  （不因为"现在支持两种形态"就把解析失败静默吞掉）。

**② 编辑器：取消 `Transform3D` / `Camera3D` 作为可添加组件**（用户要求）
- 从 `COMPONENT_REGISTRY`（Add Component 菜单 + 菜单栏「组件」菜单的唯一来源）移除这两项；
  `Camera2D` 本来就不在表里，也不加回去（相机不分 2D/3D）。
- 这两个旧名**仍然可以加载与显示**，旧场景不会因此变得不能编辑；只是不再作为"新加一个组件"
  的入口。统一名 `Transform`/`Camera` 要等 schema 注册表跟上（阶段 4）再进这张表——
  提前放进去会写出运行时读得懂、但**审计与通用编辑器不认识**的组件。

**门与证据**：`unified_transform_and_camera_compile_to_the_existing_typed_variants`
（2D/3D 两种 `Transform` 形态与两种投影的 `Camera` 各自编译到既有的 `ComponentId`、
统一 3D 取值真的读进来、缺判别字段的兼容路径、判别字段与字段体不匹配时**编译报错**）；
`lua_bridge_accepts_unified_transform_and_camera_components`（四种写法都能实例化且落进世界的
是 `Transform3D`/`Camera3D`/`Camera2D` 的正确分支、坏串仍然报错）；
`component_menu_comes_from_the_registry` 扩为**断言三个重复项都不在菜单里**。
负向对照见 §4 第 38 条。

**顺序说明（重要）**：写侧（编辑器保存统一写法）必须晚于读侧，而 schema 注册表与审计别名
必须与写侧同一批落地，否则 `--check` 会把示例工程里的旧名报成未知组件。

### 3.50 统一组件的 schema 化：一次**回退**的尝试（第 54 轮，诚实记录）

阶段 4a 的目标是"让 schema 认识统一写法，并让编辑器在打开文档时迁移"。这一轮**全部写出并跑通了
引擎侧**（`engine --lib` 844 全绿、两个工程审计仍 0），但**编辑器侧塌了 11 个 bin 测试 + 1 个
perf 场景**，因此**整体回退到 `ba5632d`**（回退后重新验证：engine 842 / editor lib 173 + bin 256 /
perf 30 场景 ok / 审计 0）。这一节记录"做对了什么、为什么不能半途落地、下一步该按什么顺序做"。

**做出来的东西（补丁留在 `%TEMP%\unify-transform-wip.patch`，86 KB；磁盘上是易失的，设计记在这里）**：
- `ComponentSchema` 新增 `legacy_fields`（历史写法的备用字段表）+ `parse` 的主表/备用表回退；
  `Transform` 改成统一形态（`position/rotation/scale`）并挂上 2D 旧表，新增 `Transform3D` 别名与
  统一 `Camera`（`projection` 判别字段 + 两套字段并集）。
- `property_path` 的 `read_field`/`write_field` 改成**按字段名选表**（`table_for_field`）：
  旧 Prefab 覆盖键 `property:Transform.x` 在旧形态载荷上继续可用，且**整条读写留在旧形态**，
  不会写出两种形态混在一起的串（这一条让 4 个 Prefab 覆盖/回退测试原地转绿，是这轮真正的收获）。

  打包），迁移发生即标记未保存；配套新增门 `open_unifies_transform_and_camera_in_memory_only`
  （内存归一、**磁盘一字未动**、保存后重开干净）通过。
- `perf_fixture` 的夹具改成统一 `Transform`（否则 `scene_save_load_1k` 会因为"打开即归一化"
  而判 `roundtrip_identical=false`）。

**为什么不能半途落地（关键结论，下轮必须先解决）**：
1. **schema 一改，编辑器就必须同时接迁移**。`Transform` 的字段变成 `position/rotation/scale` 后，
   2D 旧载荷在 Inspector 里会显示成三个**空行**（行按主字段表生成），而且编辑它们会报
   "字段不存在" → 用户打开自己的 2D 场景就没法改变换了。所以"改 schema"和"打开时迁移"
   **必须同一批**（回退前我正是先改了 schema、再补迁移，中间的绿状态只对测试成立、对用户不成立）。
2. 打开即迁移会改变**既有测试的期望**，共 11 个 bin 测试（`actions` 的打开/脏标记/状态文本/
   选择清理、`header` 的恢复快照、`inspector` 的 Prefab 覆盖链），不是"顺手改数字"而是
   要把"打开一个旧文档会标脏并改内存"这条新事实写进这些测试的语义里。
3. Prefab 覆盖链还有一个**没查清的点**：`apply_prefab_override_field` /
   `sample_project_reapply_prefab...` 在迁移后失败（inspector.rs:2469、actions.rs:3669）。
   怀疑是"实例已被归一化成 `Transform`，而源 Prefab 仍是旧写法/旧名"导致的比对口径不一致——
   需要在下一轮用一个小实验确定，再决定是"源也要迁移"还是"比对时两侧都归一化"。

**下一轮的执行顺序（建议）**：
① 先只做引擎侧的 schema + `property_path` 选表（补丁里已验证过，风险最低），单独提交；
② 再单独做"打开时迁移"，并把那 11 个测试的期望逐条改成新语义（含 Prefab 链的那个疑问）；
③ 最后才把编辑器 2D 写入路径（`scene_view` 拖拽、`encode_transform`、Add Component 里的
   `Transform`/`Camera` 默认值）切到统一写法，并复跑完整验证组。
期间任何一步红着，都不进入下一步——这正是本轮回退所依据的纪律。

## 6. 回滚说明

- 所有新增能力都是**新增类型与新入口**，没有替换既有实现：`services.rs`、`profiler.rs`、`perf_fixture.rs`、`resource_refresh.rs`、`perf_baseline.rs`、`command_router.rs`、`diagnostics.rs`、`schema_audit.rs` 全为新文件。

  1. `EditorApp.history` 类型由 `CommandHistory` 改为 `CommandService`（通过 `Deref/DerefMut` 保持旧调用点语义不变）；
