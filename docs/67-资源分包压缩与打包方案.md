## 0. 摘要

现在的 `assetc package` 产出的是**原格式文件的镜像**：`scenes/ scripts/ assets/` 一个文件对一份拷贝，
`--compress` 只是把 `assets/` 下部分后缀**逐文件**套一层 gzip 容器，`--encrypt` 只碰 `.lua`/`.scene`。
没有容器、没有分组、没有图集参与发布。

本方案要把它换成 **cook → bundle → mount** 三段流水线：

| 指标（`examples/game_jhyt`，本文实测） | 现在 | 方案后 | 变化 |
|---|---|---|---|
| 包内文件数 | **1,372** | **约 12**（1 个计划表 + 若干 bundle） | −99% |
| 包体积 | **6.00 MB** | **3.49 MB**（容器 3.48 + 骨架/清单/报告 0.01） | **−42%** |
| 文本（lua/scene/prefab/json，占包 41%） | 2.63 MB，**零压缩** | 0.54 MB（块内 zstd） | −79% |
| 逐文件 gzip 的收益 | 6.00 → 5.93 MB（−1.2%） | 不再逐文件压，改块压缩 | 去掉伪优化 |
| `manifest.txt` 自身 | 84,882 B / 1,372 行 | 约 1 KB / 14 行 | −99% |
| Web 首屏请求数 | 1,372 次 | 与 bundle 数同阶（本次约 12） | −99% |
| 微信主包占用 | 3,736 / 4,096 KB = **91.2%** | 由分组表压到限额的一半量级 | 喘息空间 |

四条**实测反直觉结论**（§1.3 逐条给数据），方案的取舍全部由它们决定：

1. **逐文件压缩基本无效，块压缩有效**：逐文件 gzip 在 1,180 张 PNG 上只省 0.7%（`assetc benchmark`
   实测 0.993）；但把这批 PNG **连续拼进 256 KB 块**再用 zstd 压，PNG 语料降到 **0.840**——
   PNG 之间共享的调色板、帧间重复、九宫格同形**只有跨文件才看得到**。
2. **包里最该压的是文本**（块内 zstd 0.209；`.scene` 单类到 0.054），而现在 `--compress` 明确避开它。
3. **图集的问题不在图集，在"页 → PNG"**：同一角色 64 帧打成 2048×1024 一页，页 PNG 从 46 KB 涨到
   153 KB（换编码器也只到 82 KB），而**裸 RGBA + zstd L19 只要 14.7 KB**——比散图还小 3 倍。
4. **"按场景分包"在本引擎的现有依赖图上跑不通**：1,180 张 PNG 里只有 **197 张**能从场景静态可达，
   `opaque=0` 说明索引自己认为"没说不知道"，但它其实漏掉了 Lua 里 `texture=…;size=…` 这种组件串写法。

> 上一版本文写作时构建机离线（`cargo add` 被 ustc 镜像 403 拒绝），压缩只能用 deflate、VRAM 压缩被排除。
> 2026-10-19 该约束已解除：镜像配置修好后 crates.io 直连可用，`zstd`/`ruzstd`/`lz4_flex` 均可引入，
> 全文数值已改为 **zstd 实测**（§1.5）。wasm 侧的解码器可达性另有一条硬约束，见 §4.3.1。

## 1. 现状：`assetc package` 到底做了什么

### 1.1 代码事实

`engine/crates/assetc/src/lib.rs` 的 `package()`（[lib.rs](../engine/crates/assetc/src/lib.rs)）：

- `copy_file(project.toml)`；
- `scenes/`、`scripts/`：`copy_dir_encoded(compress=false, encrypt=encrypt)`，`is_encryptable_data` 只认 `.lua`/`.scene`；
- `assets/`：`copy_dir_encoded(compress=compress, encrypt=false)`，`is_compressible_asset` 认
  `png/jpg/jpeg/wav/ogg/mp3/ttf/otf/glb` 九种后缀；
- 字体子集化 → 剔除未声明字体 → `write_dependency_index(dependencies.json)`；
- 遍历输出目录写 `manifest.txt`（`路径 \t 大小 \t fnv1a`）。

编码容器在 `rustlua-infra/src/pack.rs`：`RustLua <flags> [nonce] <payload>`，先 gzip 再 ChaCha20Poly1305。
`decode` 对非 `RustLua` 文件原样返回，所以开发明文与发布包共用一套读路径。

**结论**：这是"文件搬运 + 可选单文件封装"。文件边界=资源边界，所以文件数、请求数、主包配额、
图集、去重、依赖分组全部无从谈起——这正是 Unity 在有 AssetBundle 之前、Godot 在有 PCK 之前的状态。

### 1.3 四条反直觉结论

#### 结论 1：逐文件压缩基本无效，块压缩有效

逐文件 gzip 在 1,180 张 PNG 上只省 0.7%（`assetc benchmark` 的 0.993），16 个 mp3 省 3.8%（0.962），
代价是 5.7 s 构建时间 + 每次加载一次 `flate2` 解压 + 每个文件多 8 字节 `RustLua` 头。

但**把这批 PNG 连续拼进流里再压，结论完全不同**（同一份 1,876,595 B 的 PNG 语料）：

| 压缩方式 | 字节 | 比值 |
|---|---|---|
| 逐文件 gzip（现状 `--compress`） | 1,864,226 | 0.993 |
| solid zstd L9（1.8 MB 一次压完） | **1,575,491** | **0.840** |
| solid flate2 L9 | 1,585,686 | 0.845 |

省下的 16% 来自**跨文件冗余**：同一套 UI 九宫格切片的同形区域、动画帧之间的近似重复、
共享的调色板与 chunk 布局——**逐文件压缩在物理上不可能看到这些**。
所以教训不是"PNG 不可压"，而是"**压缩单位太小**"：容器 + 块 > 逐文件容器。

#### 结论 2：包里 41% 是文本，一分钱没压

`lua` + `scene` + `prefab` + `json` = 2.63 MB / 6.29 MB。按后缀成组、整组 solid 压（本案实测）：

| 类别 | 原始 | zstd L9 | flate2 L9 | zstd 比值 |
|---|---|---|---|---|
| `.scene` | 657,437 | **35,558** | 55,442 | **0.054** |
| `.json`（`dependencies.json`） | 78,592 | 5,861 | 6,350 | 0.075 |
| `.prefab` | 157,449 | 16,633 | 19,225 | 0.106 |
| `.lua` | 1,638,166 | **407,950** | 476,114 | **0.249** |
| `.ttf`（已子集化） | 288,364 | 80,210 | 83,386 | 0.278 |
| `.txt`（`chars.txt` + `manifest.txt`） | 89,523 | 27,370 | 28,263 | 0.306 |
| `.toml` | 4,479 | 2,745 | 2,602 | 0.613 |

`--compress` 之所以没吃到这块，是因为 `is_compressible_asset` 只列二进制后缀，而 `--encrypt` 只碰
`lua`/`scene` 且加密前不压缩。按"256 KB 块 + zstd L9"折算，**这块能省 1.9 MB**。

#### 结论 3：图集的问题不在图集，在"页 → PNG"

用现成打包器（`atlas_pack`，shelf、padding=2、POT、max 2048）实测
`assets/art/characters/player_male` 的 64 帧（散图合计 46,045 B）：

```
atlas_pack_ok page=0 size=2048x1024 regions=64
hero_male-0.png   153,012 B     ← 合成页
hero_male-0.atlas   2,000 B
```

- 帧尺寸实测 **256×64**（不是 Lua 里那个 64×64——那是显示尺寸），64 帧 = 1,048,576 像素；
- 磁盘：46,045 B（散图）→ **153,012 B**（页），**涨 3.3 倍**；
- VRAM：散图 1,048,576 px = 4.2 MB → 页 2,097,152 px = **8.4 MB（2 倍）**。原因不是"稀疏"，
  而是 **padding=2 + POT 的耦合**：8 帧一行会到 2064 > 2048，于是只能 7 帧一行 → 10 行 × 66 = 660 px 高，
  POT 向上取整成 1024 → 页面积是理论下界的 2 倍（占用率 50%）。
- 附带发现：同目录的 `preview.png`（435×3778）会让打包器**直接报错**
  （`源图 435×3778 超过单页上限 2048`），即当前 `atlas_pack` 没有"超限源图降级/单列"的处理。

页的 8,388,608 B 裸像素换四种封装（§1.5 的同一台机器实测）：

| 封装 | 字节 | 相对页 PNG | 相对散图 |
|---|---|---|---|
| `image` 写出 PNG（当前 `atlas_pack` 路径，`Adaptive` 滤波 + flate2 L6） | 153,012 | 1.00× | 3.32× |
| 另一编码器（GDI+）写出的 PNG | 82,388 | 0.54× | 1.79× |
| 裸 RGBA + flate2 L9 | 38,688 | 0.25× | 0.84× |
| 裸 RGBA + zstd L9 | 31,035 | 0.20× | 0.67× |
| **裸 RGBA + zstd L19** | **14,711** | **0.096×** | **0.32×** |
| 裸 RGBA + lz4 | 234,212 | 1.53× | 5.09× |

页里 88%（1,848,604 / 2,097,152）的像素是纯零（`a=0` 且 RGB 全零，已逐像素核对）。对这种内容
**"按行滤波 + zlib 分块"反而在制造熵**，而 zstd 的长匹配 + 大窗口能把它压到 9.6%——**页比散图还小 3 倍**。
所以图集不但不涨字节，配上正确封装还降 3 倍。（具体是滤波启发式还是 zlib 逐行 flush 造成的，
未逐项归因；本方案的取舍不依赖这个归因，因为 zstd 已经同时赢过三种 PNG 封装。）

另外，这 64 帧**按角色打包也换不到合批**：`characters.lua` 是按朝向挑一张 256×64（内含 4 帧
64×64），同一时刻每个角色只用 1 张，把同一角色的 64 张打成页，draw call 不变。
合批机会在**跨角色**（一屏多个角色共用一个 actor 页，朝向切换不再换纹理），要按"共绘"而不是
按"同类"切页（§6.2）。图集真正稳的收益在"同时上屏的不同区域"（瓦片、UI、地面物品、建筑），
与 `SpriteBatch` 的"按 纹理 ID + 图层 合并 draw range"（[09-sprite-batch](09-sprite-batch.md)）
才咬合得上。

#### 结论 4：现有依赖图不够切分包

`dependencies.json`（format 1）实测：`edges` 106 个源，`opaque` **空**。以 8 个场景为根求闭包：

- 1,180 张 PNG 中**只有 197 张可达**，983 张不在任何场景闭包内；
- 每场景"独占集"极小（manor 77 KB、village 26 KB、其余 ≤ 20 KB）——因为美术是**跨场景共享**的。

为什么不达？`scripts/data/characters.lua` 里写的是组件串：

```lua
s = "texture=assets/art/characters/player_male/static_s.png;size=64x64;tint=…;sorting_layer=actor"
```

`assetc` 的 `normalize_asset_path` 从 `assets/` 起截取后按整串匹配已知文件，而这里有 `;size=…` 尾巴，
匹配不上 → 丢边。**这是提取缺口，不是"动态引用"**；`opaque=0` 说明索引没意识到自己漏了。
按场景切分包在本项目上因此不可行；按**内容域**切可行（见 §5.3）。

### 1.5 编解码器实测与跨端可达性

探针工程（`%TEMP%\rlzprobe`，`flate2` / `zstd 0.13` / `ruzstd 0.8` / `lz4_flex 0.11`）在本机对

**(a) 文本语料 2,625,646 B**

| 方案 | 字节 | 比值 | 编码耗时 | 解码（C） | 解码（ruzstd） |
|---|---|---|---|---|---|
| 逐条目 flate2 L9 | 674,015 | 0.257 | — | — | — |
| 逐条目 zstd L9 | 678,079 | 0.258 | — | — | — |
| 256 KB 块 flate2 L9 | 598,329 | 0.228 | 107 ms | — | — |
| **256 KB 块 zstd L9** | **548,592** | **0.209** | 55 ms | — | — |
| solid flate2 L9 | 591,021 | 0.225 | 112 ms | — | — |
| solid zstd L9 | 486,801 | 0.185 | 43 ms | 2.7 ms | 11.3 ms |

**(b) 整包模拟**（1,372 条目按路径序、条目不出块、块 256 KB、逐块自选 store/compress）

|---|---|---|---|---|
| **zstd L9** | **3,650,673** | **0.581** | 116 ms | 23 / 24 |
| zstd L19 | 3,575,526 | 0.569 | 1640 ms | 23 / 24 |
| zstd L3 | 3,740,916 | 0.595 | 30 ms | 23 / 24 |
| flate2 L9 | 3,707,377 | 0.590 | 244 ms | 23 / 24 |
| lz4 | 4,172,298 | 0.664 | 5 ms | 23 / 24 |

索引开销约 **87 KB**（54,255 B 条目名 + 24 B × 1,372；索引本身可再压到约 25 KB）。
所以"原包 6,287,820 B → **3,652,689 B（0.581×）**"是这条流水线的端到端预期值——**索引已经算在里面**
（索引是容器的一部分，不是额外开销）。批 A 实测落地值 3,652,689 B，与模拟差 5 KB。

**(c) 可达性（这才是选型的硬门槛）**

| 问题 | 实测 | 结论 |
|---|---|---|
| 能不能拉新 crate | 修掉 `~/.cargo/config.toml` 的 ustc 镜像替换后 `cargo build` 直接拉到 zstd/ruzstd/lz4_flex | ✅ 可以 |

于是压缩分层被 wasm 逼出来，而不是偏好：
**编码用 C 版 `zstd`（只在 `assetc` 里，native），解码用纯 Rust `ruzstd`（进引擎与 wasm）**。
`rustlua-infra` 今天已经编进 wasm 的 `flate2` 继续服务旧 `RustLua` 单文件格式（loose/开发形态），
两条解码器并存，wasm 体积增量在批 A 用 `wasm-opt`/产物大小实测（门槛：≤ 100 KB）。

## 2. 对标：三家各自解决的是哪一格

| 维度 | Unity（AssetBundle / Addressables） | Unreal（.pak / IoStore） | Godot（.pck） |
|---|---|---|---|
| 容器 | 每 bundle 一个文件（偏 LZMA/LZ4） | `.pak`（头+索引在尾）；`.utoc`+`.ucas`（IoStore，分块、可 mmap） | 单 `.pck`，文件顺序拼接 + 尾部索引 |
| 边界 | **显式**（按文件夹/标签声明） | **显式**（Primary/Chunk 0..N/DLC 补丁层） | **过滤器**（export preset 的 include/exclude glob） |
| 压缩 | 整个 bundle 级 LZ4/LZMA | **按块**（默认 64 KB~128 KB）压缩，块内条目共享上下文 | 默认不压；导入期把资源换成 `.ctex`/`.ogg` 等压缩形态 |
| 随机访问 | bundle 内可寻址 | 块表 + 块内偏移，O(1) | 尾部索引 + 偏移，可寻址 |
| 依赖 | bundle 间依赖表 + 引用计数加载/卸载 | 资产注册表 + 软引用 | 无 bundle 级依赖（靠路径） |
| 热更 | 远端 bundle + 版本目录（catalog） | 补丁 pak 叠加 | 整体替换 pck |
| 读的入口 | 资产系统统一 API | `FPakPlatformFile` 挂在文件系统栈上 | `res://` 虚拟文件系统 |

我们的选型（**zstd + 块 + 尾部索引**）落在 UE/IoStore 那一格：块大小与 zstd 家族一致，
而 Godot 的"默认不压"不适用本引擎（文本占 41%，实测可压到 0.21）。

**提炼出的 7 条原理**

1. **容器先于压缩**：把"一个文件一份资源"换成"一个容器一份清单"，收益来自文件数/请求数/配额，
   压缩是容器内的事。
2. **块压缩是随访问与压缩率的最佳折中**：整包 solid 压得最狠但等于全量解压；逐条目压得最松但零浪费；
   按块（几十~几百 KB）两头都占。
3. **索引放尾部**：写出时流式追加、读完时一次定位；对 HTTP Range 与"没有 mmap 的宿主"（微信）都友好。
4. **边界必须显式且可审计**：Unity 的教训是"自动按依赖切"会切出上千个碎 bundle；UE 的教训是
   chunk 必须人工可控。三家最终都靠**声明**而不是靠算法。
5. **去重靠内容哈希**：同一张图被多个入口引用时只存一份，这是"字节级"收益里唯一稳定的一块。
6. **分组粒度受分发约束反向限制**：微信 4 MB 主包/分包上限、CDN 单文件上限，决定了
   bundle 该切多大——不是美学问题。
7. **改的是"读的入口"而不是"每个读点"**：UE 把 pak 挂进文件系统栈，Godot 用 `res://`。
   本引擎对应物已经存在：`vfs::read_resource`。

**抄什么 / 不抄什么（本引擎裁定）**

| 抄 | 不抄 | 理由 |
|---|---|---|
| 单文件容器 + 尾部索引 + 块压缩（UE IoStore） | `.utoc`/`.ucas` 双文件拆分 | 我们没有 mmap 依赖与分区容器需求，单文件足够 |
| 内容哈希去重（UE/Unity 共有） | Unity 的运行时 bundle 引用计数与卸载 | 本项目资源总量 MB 级，卸载收益 < 复杂度 |
| 显式分组声明 + 构建期审计（Unity/UE） | Godot 的 glob include/exclude 当唯一手段 | 单独 glob 表达不了"依赖闭包"与"首屏" |
| 尾部索引 + 定位读（三家共有） | Godot 的"默认不压" | 我们文本占 41%，不压白丢 1.84 MB |
| 版本目录 / 内容寻址命名（Addressables） | 完整的 CDN 差分补丁系统 | 本方案只预留命名与目录，不实现差分 |

## 3. 方案总览

### 3.1 三段流水线

```
源工程                          构建期 (assetc)                                 运行期
project.toml          ┌──────────────────────────────┐
scenes/ scripts/      │ 1. cook  图集/纹理 → .rltex    │
assets/  ──────────▶  │          图集重定向表          │ ──▶ bundles/ ──▶ ① 桌面: 定位读 + 块缓存
   │                  │ 2. split 分组计划 bundle_plan │      *.rlb       ② WebGL: 按 bundle fetch
   │ 导入缓存          │          覆盖审计(每文件一次)  │      plan.json    ③ 微信: pack/分包/CDN
   └── .cache/ ─────▶  │ 3. pack  分块压缩 → RLB v1    │                        │
      dependencies.json│          manifest.txt(仅bundle)│                       ▼
                       └──────────────────────────────┘              vfs::read_resource / read
```

- **cook**：把"能算出更好形态"的资源在构建期定型（图集页、字体子集、可能的纹理重排），
  产出物一律落在 `assets/` 的**发布副本**里，不动工程源。
- **split**：把 `assets/ + scenes/ + scripts/` 切成若干 bundle，边界由**规则 + 依赖 + 声明**三方决定，
  构建期审计"每个文件恰好属于一个 bundle"。
- **pack**：每个 bundle 写成 RLB v1 容器（块压缩、块级可选 AEAD、尾部索引），再产出
  `manifest.txt`（bundle 级清单）与 `bundle_plan.json`（分组计划，供三宿主与工具消费）。

### 3.2 关键决策

| # | 决策 | 取值 | 理由 | 被否决的选项 |
|---|---|---|---|---|
| D1 | 容器形态 | **单个 bundle 文件 = 多个条目 + 块压缩 + 尾部索引** | UE IoStore 的折中；微信无 mmap 也能定位读 | 整包 solid（≈全量解压）；逐条目压缩（块内冗余吃不掉，实测差 19%） |
| D2 | 压缩算法 | **zstd**：编码用 C 版 `zstd`（只在 assetc/native），解码用纯 Rust `ruzstd`（进 wasm） | wasm 逼出来的分工，不是偏好；块级比 flate2 好 8.3%，页级好 25%~2.6× | 只用 flate2（块级 0.590 vs 0.581，仅差 1.6%，但页面差 2.6 倍）；lz4（0.664，明显更差） |
| D3 | 压缩单位 | **块（默认 256 KB 解压后）+ 逐块自选 store/compress** | 块内跨文件共享上下文；单次 miss ≤ 256 KB；压不动的块原样存 | 逐条目（实测差 19%）/整包 solid（不可随机访问） |
| D4 | 分组依据 | **显式声明 > 目录规则 > 依赖闭包**，三者都记录来源 | 依赖图目前只覆盖 17% 的 PNG，不能单独承担 | 纯依赖自动切（碎 bundle + 漏切） |
| D5 | 图集 | **只打"共绘集"**，产出 `.atlas` + `.rltex`，运行期用重定向表 | "同类集"（角色 64 帧）零合批收益 | 全量自动图集 |
| D6 | 纹理 cook 格式 | **`.rltex` = 头部 + 裸像素**，压缩交给容器块 | 页 PNG 153 KB → 裸像素块 zstd L19 **14.7 KB**（散图 46 KB）；且省掉 PNG unfilter 与解码器分派 | 自产 PNG（3.3 倍）；`.rltex` 内再压一层（双压，无收益） |
| D7 | 加密 | **块级 AEAD**，闸门在 `--encrypt` | 随机访问 + 逐块完整性；现在只有 lua/scene 加密，贴图裸奔 | 整包 AEAD（必须全量解密） |
| D8 | 兼容 | **bundle 与 loose 双读**，`--keep-loose` 保留目录形态 | 编辑器/热重载/回归脚本都靠 loose | 直接改签所有读者 |
| D9 | 命名 | 逻辑名 `bundles/<组名>.rlb`，名称内嵌内容哈希（`…-<hash8>.rlb`） | 远端可做不可变缓存与差分 | 固定名 + 版本号目录（多做一层） |

## 4. 容器格式 RLB v1

放置：`engine/crates/rustlua-infra/src/bundle.rs`（与 `pack.rs` 同层）。依赖分工见 §4.3.1：
`chacha20poly1305` + `ruzstd` 进 wasm 构建，`zstd`（C）只出现在 `assetc`。

### 4.1 字节布局

```
┌─────────────────────────────── 偏移 0，32 B 定长头 ───────────────────────────────┐
│ "RLBU" (4) │ ver u16 │ flags u16 │ block_size u32 │ index_offset u64 │ index_len u32 │
│ header_fnv u32                                                                      │
├────────────────────────────── payload：块 0 │ 块 1 │ … │ 块 N-1（紧排，无填充）───────┤
├────────────────────────────── index：条目表 + 块表（可整体 zstd 压）────────────────┤
└────────────────────────────── 无尾标：长度由 index_offset + index_len 确定 ───────────┘
```

- **头在头、表在尾**：读出 32 字节即可判版本/规模；写完再回填 `index_offset`/`index_len`（单次 seek）。
- 索引放尾部是三家共同做法：写出流式、读入一次定位、对 `wx` 的定位读与 HTTP `Range` 都友好。
- `header_fnv` 覆盖前 28 字节：坏头（截断/改版本）立刻报错，不进解码器。

### 4.2 条目表

每个条目（名字升序，`/` 分隔，相对工程根，UTF-8）：

| 字段 | 宽度 | 含义 |
|---|---|---|
| `name_len` | u16 | 名字字节数 |
| `name` | … | 如 `assets/art/ui/hud/ui_icon_hp.png` |
| `flags` | u8 | bit0=`.rltex` 纹理、bit1=条目已在 cook 期压过（容器不再压）、bit2=预留（VRAM 压缩） |
| `raw_len` | u32 | 条目长度（块解压后） |
| `block` | u32 | 所在块号 |
| `offset_in_block` | u32 | 块解压后的字节偏移 |
| `fnv1a` | u64 | 原文校验和（`--check`/远端校验用，与现清单同一算法） |

**条目自身不带压缩标志**：压缩是块级的事（§4.3），条目在块内一律是裸字节。`bit1` 只给
"已经压过的条目"（例如将来引入的预压纹理）留口子，让容器别再压一遍。

条目名与 `vfs` 的 key 完全一致（工程相对路径），**所以分组表、`dependencies.json`、`pack.json`
的路径字符串不需要任何换算**——这是选"路径即 key"而不是"资产 ID"的原因。

### 4.3 块表与压缩

| 字段 | 宽度 | 含义 |
|---|---|---|
| `flags` | u8 | bit0=已压缩、bit1=档位 L19（大像素块）、bit2=已加密 |
| `stored_len` | u32 | 该块压缩（+加密）后长度 |
| `raw_len` | u32 | 该块解压后长度（目标 ≤ `block_size`） |

块偏移由 `stored_len` 前缀和推出（首块紧接 32 字节头），不需要逐块存 offset。

- **为什么按块而不逐条目**：同一份语料实测，逐条目 zstd 0.258 vs 256 KB 块 zstd **0.209**（差 19%）；
  整包 solid 又能到 0.185，但要求"读一个字也得全量解压"。256 KB 块把两者折中：
  块内享受跨文件共享上下文，miss 成本有上界（解一个块）。
- **逐块自选 store / compress**：压缩后不比原始短（阈值默认 1%）就原样存并置 `flags.bit0=0`。
  实测整包 24 块里只有 1 块选择 store——这条规则不是为了省字节，是为了**不给已经压不动的数据
  白付解码成本**（音频块、随机噪声块）。
- **档位**：默认 zstd L9；**原始 > 1 MB 的像素块（`.rltex` 页）用 L19**——同一张页 L19 = 14,711 B
  vs L9 = 31,035 B（2.1 倍），而解码速度与档位无关（实测 L3/L9/L19 解压均 15~18 ms）。
  开发构建 `--fast` 用 L3（整包 30 ms vs L9 的 116 ms）。
- **块内布局**：条目按**名字字典序**装入块，顺序 = 条目表顺序 → 同一目录的资源在物理上相邻，
  块缓存命中率高（UI 一屏 20 个图标通常落在同一块）。
- **大条目**：条目大于 `block_size` 时独占一个（或多个）块，`raw_len` 可超 `block_size`——
  否则 8.4 MB 的图集页无处安放（§4.7）。
- **块缓存**：运行时保留最近 N=8 个解压块。页块会达到 8 MB 级，缓存对页面块只保留 1 块
  （"大块降级"策略），避免 8 块 × 8 MB 的峰值。

### 4.3.1 编解码器的跨端分工（wasm 是硬门槛）

| | 编码 | 解码 |
|---|---|---|
| 用什么 | `zstd` 0.13（C，libzstd） | `ruzstd` 0.8（**纯 Rust**） |
| 在哪 | 只在 `assetc`（native） | `rustlua-infra`（进 wasm32-unknown-unknown） |
| 为什么 | 编码只在构建机跑，C 实现最快最省事（整包 L9 116 ms / L19 1.6 s） | wasm 里不能编 C：`zstd` crate 依赖 `libzstd`+`cc`，浏览器/微信产物不接受 |
| 实测 | 见 §1.5 | 8.4 MB 页面 L19 帧往返一致，解压 14.9 ms（原生，预计 wasm 3~5 倍慢） |

对应到 `Cargo.toml`：`assetc` 加 `zstd = "0.13"`；`rustlua-infra` 加 `ruzstd = "0.8"`。
**不要让 `zstd` 出现在引擎 crate 的依赖图里**——`cargo tree -p rustlua-infra --target wasm32-unknown-unknown`
必须是干净门之一（批 A）。

`flate2` 继续留在 `rustlua-infra` 里服务旧 `RustLua` 单文件格式（loose/开发形态，§4.6）；
两个解码器并存，wasm 体积增量在批 A 实测（门槛 ≤ 100 KB）。

### 4.4 块级加密（`--encrypt` 时）

- 每块独立 `ChaCha20Poly1305`：
  - `nonce[0..4] = header.salt`（构建期取 `index_fnv` 低 4 字节，**确定性**，不引入随机）；
  - `nonce[4..12] = 块号 u64`（小端）；
  - `AAD = ver ‖ flags ‖ block_size ‖ 块号 ‖ raw_len`——防止换块/换包重放。
- 密钥沿用 `pack.rs` 的固定 32 字节（内嵌可执行文件，定位仍是"防随意读取"，不是强加密，与现文档口径一致）。
- **收益**：贴图/音频/字体现在也能进加密域（今天只有 `lua`/`scene` 有），且**Web/微信也可开**——
  bundle 解析在 wasm/Rust 侧做，`package.ps1` 今天对 web 平台直接拒绝 `-Encrypt` 的理由（JS 只读明文）
  在这里不成立。这条单独成批（批 F），不影响其它批。

### 4.5 确定性

同一份输入必须产出逐字节相同的 bundle（否则 golden 门、`manifest` 比对、CDN 缓存全部抖动）：

1. 条目按**名字字典序**（不是文件系统枚举序）装入；
2. 块边界只由 `block_size`、逐块 store/compress 判定与累积 `raw_len` 决定；
3. 档位固定（默认 L9、像素块 L19、`--fast` L3），不写时间戳（zstd 帧头无 mtime 字段）；
4. `salt` 取自 `index_fnv`（内容决定），不取随机数；
5. 不并行写同一 block（并行只允许在"块之间"，且块号与内容一一对应）。

**一个必须写进文档的坑**：zstd 的输出**不保证跨版本逐字节一致**（匹配查找/启发式会变）。
所以"确定性"要按下述口径钉：

- `Cargo.lock` 锁死 `zstd` 版本，且改用 `[patch]`/vendor 也在锁里；
- bundle 头里记 `zstd_version: u32`（`ZSTD_versionNumber()`），解包端只校验"能解"，不校验版本相同；
- golden 门钉的是**同一构建机、同一锁文件下的两次产物 FNV 相等**；升级 zstd crate 时 golden 值
  会变，属于**预期变更**，要与 `PACKAGE_VERSION` 一起在提交里说明。

门：`bundle_determinism_golden`——同目录连打两次，两组文件的 FNV 全等。

### 4.6 与现有 `RustLua` 单文件容器的关系

| | `RustLua` 容器（现在） | RLB v1（新增） |
|---|---|---|
| 粒度 | 一个文件 | 一个组（多条目） |
| 压缩 | gzip（带 18 B 头 + CRC，逐文件） | **zstd（块级，无逐条目头）** |
| 加密 | 整文件 AEAD | 块级 AEAD（批 F） |
| 随机访问 | 天然（本来就一个文件） | 块表 + 块内偏移 |
| 谁还在用 | **loose 形态与开发期单文件**（保留，gzip 不变） | 发布包形态（批 A 起可显式产出） |

两者**不叠加**：bundle 内条目一律**裸字节**。这一条是硬约束，理由是 `vfs` 的契约：

> provider 返回**未解码**字节，压缩/加密由 `pack::decode` 统一处理（`vfs.rs` 模块头）。

bundle provider 返回的条目已经是解压后的明文，`pack::decode` 对明文原样透传 → `read` 与
`read_resource` 两条路径**都不需要改**。反过来，若 bundle 内再套 `RustLua` 头，`decode` 会二次解压，
或者明文分支被误判——所以格式层面禁止。

**新增一条硬规则**：`pack::decode` 遇到 `RLBU` 魔数必须**报错**（"bundle 被当普通资源读取"），
而不是当明文透传。否则 `lua` 加载器会把 bundle 二进制当脚本执行，症状是"语法错误在某二进制行"。
批 A 已落地并有门（`bundle_magic_is_rejected_not_passed_through`）。

### 4.7 边界与上限

- **单 bundle ≤ 4 MB**（微信单分包口径）；超过则构建期**拒绝并报错**，不做静默拆分（静默拆分会破坏
  分组表的"一个文件恰好一处"不变量）。
  > 实测（`game_jhyt`，批 A 单包）：**3.57 MB**——已经到 4 MB 的 87%，和今天主包 91.2% 是同一个病。
  > 也就是说"单包"只是把问题从"文件数"换成"单包上限"，**真正的解药是批 C 的分组**，不是更大的容器。
- **条目跨块**：v1 的实现取"大条目独占自己的块"（`raw_len` 可超 `block_size`），不做多块链。
  已落地：8.4 MB 的图集页会独占一个块，`raw_len` 记 8,388,608、`stored_len` 记压缩后的几十 KB。
- 条目名 ≤ `u16::MAX` 字节（写入端拒绝更长），路径不许为空或含 NUL。
- `u32` 长度字段 → 单条目 ≤ 4 GB。

## 5. 分组（分包）策略

### 5.1 三个归组来源与判定顺序

| 优先级 | 来源 | 表达方式 | 谁消费 | 覆盖 |
|---|---|---|---|---|
| 1 | **显式声明** | `bundles.json` 的 `assign` 表（`路径或前缀 → 组名`，最长前缀优先） | assetc split | 人工要控制的一切（首屏、章节、DLC） |
| 2 | **目录规则** | `bundles.json` 的 `groups[].include`（顺序即优先级） | assetc split | 本项目 83% 的"索引不可达"资源 |
| 3 | **依赖闭包** | `dependencies.json` 的 `edges`，按"被几个入口引用"归入独占/共享 | assetc split | 场景/预制体/图集链，197/1180 张 PNG；**本批未启用**（见下） |

> **配置为什么是 `bundles.json` 而不是 `project.toml` 的 `[bundles]` 表**：`assetc` 解析
> `project.toml` 用的是逐行 `key = value` 扫描（`project_font_key` 那一族），撑不住"数组表 + 嵌套"，
> 而工作区没有 `toml` 依赖。`bundles.json` 与 `dependencies.json`、`pack.json` 同族
> （构建期配置/产物），`serde_json` 已在依赖里，不新增 crate。格式见 §5.6。

判定顺序即优先级：显式 > 目录规则 > 依赖闭包；未命中的落 `unowned` 组并**在报告里列前 20 条**。
文件不存在时用内置默认规则（§5.3 那张表），所以"不写配置也能分组"。

### 5.2 覆盖不变量（构建期硬门）

1. **每个文件恰好属于一个 bundle**（重复=报错，遗漏=报错）；
2. **每个 bundle 整体属于一个分发单元**（主包 / 某分包 / CDN）——一个 bundle 不许横跨，
   否则微信"主包/分包互斥"的字节守恒断言会在搬运时炸；
3. **core 组必须自足**：`scripts/main.lua` + 其 `require` 闭包 + 启动场景 + `project.toml` + 字体
   全部在 core（Web 上 `require` 是同步的，这一点不可协商）；
4. **`dependencies.json` 里 `opaque` 非空时**，构建期在报告里显式标注"该组可能欠载"，
   并且该组的消费方只允许在"已挂载全部 bundle"的形态下运行（Web 全量、桌面默认）。

### 5.3 本项目实测分组表（`examples/game_jhyt`）

逐组跑"256 KB 块 + zstd L9 + 逐块 store/compress"的实测（与批 A 的容器同算法）：

| 组 | 内容 | 文件数 | 原始 | 落盘 | 比值 | 块数 | 分发单元 |
|---|---|---|---|---|---|---|---|

| `audio` | `assets/audio/**`（16 个 mp3） | 16 | 1,497,215 | 1,446,660 | 0.966 | 5 | 分包 |
| `art:world` | `art/**` 除 characters/enemies/ui/items/portraits（建筑/道具/装饰/瓦片…） | 301 | 1,258,791 | 1,199,773 | 0.953 | 4 | 分包 |

要点：

- **`core` 只占 630 KB** 是微信主包的关键数字：`scripts/` 1.6 MB、字体 0.28 MB、启动场景必然在首屏，
  光这三项今天就占主包 2 MB 量级；压成块内 zstd 后同一批内容 0.63 MB。再叠加首屏要用的
  `art:ui` 子集，主包可从 91.2% 降到 40~55% 区间。
- **角色/敌人帧的压缩率好得意外（0.53 / 0.42）**：同一角色的相邻帧几乎只差一两个像素，
  块内跨文件匹配把 64 张 256×64 帧压到原来的四成——**这是"容器该做而图集不该做"的教科书例子**：
  文件数占 33%、字节占 4%，收进容器降到 0.42~0.53，而打图集只会涨（§1.3 结论 3）。
- `audio` 0.966、`art:world` 0.953：已经是压缩域/内容丰富的数据，容器只能拿到个位数收益——
  它们的价值在**文件数**（16 / 301 个文件收成 5 / 4 块）与**可校验**，不在字节。
- 分组是**目录规则**产物，不依赖依赖图；依赖图只用来做"跨组引用的合法性检查"，
  以及把 `art:world` 里确实只被一个场景用的部分下钻成更细的组（可选优化，不是 v1 必须）。

### 5.4 与微信三形态的映射

`first-screen-pack.js` 现在按 `pack.json` 把 `pack-sub/` 下的首屏文件**搬**到 `pack/`，判定依据是
扫描场景文本算首屏闭包 + 字节守恒断言。bundle 之后：

| 形态 | 映射 | 关键约束 |
|---|---|---|
| 主包+单分包（默认） | `bundles/core.rlb`、`bundles/art-ui.rlb` → `pack/bundles/`；其余 → `pack-sub/bundles/`（subpackage root） | **bundle 边界必须细于首屏切分**：主包里出现的 bundle 只能整体在 `pack/` |
| 瘦首包 + CDN | 全部 bundle 导出到 `<发布根>/assets/pack-sub/bundles/`，包内留 `bundle_plan.json` 骨架 | 远端按 bundle 粒度下载 + 校验，替代今天 1,372 次 `downloadFile` |
| 全量 | 全放 `pack/bundles/` | 与今天行为等价，仅文件数变少 |

- **`first-screen-pack.js` 的正文扫描会失效**（场景文本进了 bundle）。两条路：
  (a) 迁移期：assetc 额外产出 `bundle_plan.json` 与**每 bundle 的条目列表**，JS 改读计划表而不扫正文；
  (b) 收敛期：把首屏闭包计算整体搬进 assetc（Rust），JS 只消费结果——与 `dependencies.json`
  同源，消除"两套提取器必然漂移"的隐患（`first-screen-pack.js` 头部已经为此写了 40 行一致性说明）。
  **推荐 (a) 先行、(b) 收口**，两者都不改变字节守恒断言。
- **后缀**：`.rlb` 不在微信 69 个白名单内。既有改名机制（`code-package-rules.js`，`.lua`→`.lua.txt`）
  对任意后缀都成立，所以 `.rlb` → `.rlb.txt` 自动可用，**不需要动白名单**。代价是运行时按
  `code-package.json` 查表（这条通道今天已经在跑）。

**分发布局的唯一契约**：`bundle_plan::distribution_layout(plan)` 把计划表折算成「单元 → 包内根」：
`main` → `pack`、`sub` → `pack`、`sub:<name>` → `pack-<name>`、`cdn` 不进布局；
同时校验主包 ≤4 MB、总量 ≤20 MB。发布器与适配层都应消费这一份结果，而不是各自按 `unit` 字符串拼目录。
（函数与两条校验有单测钉住；`first-screen-pack.js` 迁移到多根时直接照它搬文件。）
命令行入口：`assetc layout <包目录|bundle_plan.json>` 打印同一份结果
（`mainpack unit=main …` / `pack unit=sub …` / `assetc_layout_ok roots=… entries=… kb=…`），
`--json` 输出机器可读的 `{schema, entries, total_bytes, roots[{unit, root, bundles, entries, bytes}]}`
（`first-screen-pack.js` 迁移多根时直接消费它），脚本可以先用它对账再搬文件。
实测 `game_jhyt`：`mainpack=760 KB / pack=2,024 KB / 合计 2,785 KB`（cdn 不计）。

发布侧的解析已单独成模块：[`scripts/build/bundle-layout.js`](../scripts/build/bundle-layout.js)。
`parseLayout`（吃 BOM、校验 schema/unit/容器路径、核对 entries/total_bytes）→
`distributionPlan`（生成 `bundles/x.rlb → mainpack|pack|pack-<name>/...` 的搬运表与
`game.json` 的 `subpackages`）→ `assertConservation`（字节守恒）。
`node scripts/build/bundle-layout.js --self-test` 是零依赖单测；`--file <layout.json>` 直接看搬运表。
`first-screen-pack.js` 迁移多根时只负责 IO，目录规则不再写第二遍。
`--apply <发布根>` 直接执行：搬容器到 `pack/`、`pack-<name>/`，写 `game.json` 的
`subpackages`（保留其它字段），并为每个分包根补 `game.js` 入口；
输出 `bundle_layout_applied moved=… roots=… subpackages=…`，`--self-test` 里含一个临时目录的搬运用例。
`--verify <发布根>` 校验产物形状：每个分包根有 `game.js`、`pack/` 存在、
并数出主包/分包容器（`bundle_layout_verify_ok subpackages=… main_bundles=… sub_bundles=…`）。

### 5.5 命名与缓存
- 产物名：`bundles/<组名>-<index_fnv 前 8 位 hex>.rlb`（组名里的 `:` 等字符换成 `-`）。
  内容变 → 名变 → CDN/微信缓存天然失效，不需要 `?v=` 或版本目录。
- `bundle_plan.json`（放包根，与 `manifest.txt` 同级）记录：
  `{ schema, format, block_size, groups: [{ name, unit, bundle, entries, raw_bytes, bundle_bytes, paths }] }`。
  三个消费者共用：构建搬运、Web 预载、运行时的缺件归因（`BundleSet::declare_pending`）。
  **代价**：本工程 1,371 条路径 → **70.4 KB**。它进主包会占 4 MB 的 1.7%，批 E 可以按需
  只保留"未在 main 单元里的组"或整体 zstd 压（运行时已有 `ruzstd`）。

### 5.6 `bundles.json` 格式

```json
{
  "schema": 1,
  "default_group": "unowned",
  "default_unit": "sub",
  "allow_unowned": false,
  "groups": [
    { "name": "core", "unit": "main", "include": ["project.toml", "scripts/", "scenes/", "assets/prefabs/", "assets/fonts/"] },
    { "name": "art:ui", "unit": "main", "include": ["assets/art/ui/", "assets/art/items/", "assets/art/portraits/"] },
    { "name": "audio", "unit": "sub", "include": ["assets/audio/"] },
    { "name": "art:world", "unit": "sub", "include": ["assets/"] },
    { "name": "brand", "unit": "cdn", "include": ["splash/", "branding/"] }
  ],
  "assign": { "assets/art/ui/hud/ui_icon_hp.png": "art:ui" }
}
```

- `include` 项以 `/` 结尾按**前缀**匹配，否则按**精确路径**；`groups` 的**声明顺序即优先级**。
- `unit ∈ {main, sub, sub:<name>, cdn}`：`main` 是启动即挂（主包/首屏），`sub` 是默认分包，
  `sub:<name>` 是**具名分包**（计划表与面板按名字分别统计），`cdn` 不参与包内配额。
  `sub:<name>` 的名字只允许字母/数字/`-`/`_`，长度 ≤32；语法错在**读配置**时就报错。
- **`cdn` 组不进本地微信包**：`assetc package --bundle grouped --exclude-cdn` 会把 cdn 组从
  计划/清单/产物里一起剔掉（`-AssetPack remote` 例外，那时它们正是要导出到 `assets/` 的内容）。
  `splash/` 这种启动器品牌图曾经因此在 `pack/` 里留了一份 1,225 KB 的重复；本地包只保留
  `branding/splash.jpg`，CDN 组由远程资源另行分发。
- `allow_unowned`：默认 `false`。`default_group` 非空时发布期**直接拒绝**（未归组 = 首屏可能白图，
  且 `async_loader` 失败后不重试）；确认要放行才显式打开。
- `assign` 优先于 `groups`，同一路径多个前缀命中时**最长前缀赢**；指向未声明的组 = 读配置即报错
  （防拼写错误静默把文件丢进默认组）。
- 不写 `bundles.json` = 用**引擎级通用默认** `BundleConfig::generic_domains()`：
  只依赖本引擎的目录约定（`project.toml` / `scripts/` / `scenes/` / `assets/prefabs/` /
  `assets/fonts/` / `assets/` / `splash/` / `branding/`），任何 RustLua 工程可直接用，
  不含任何具体游戏的路径。
- `BundleConfig::default_domains()` 保留为**示例工程预设**（§5.3 的实测内容域分组，
  含 `art:ui` / `title_bg_pixel.png` 这类工程约定），不再是引擎默认；
  `examples/game_jhyt/bundles.json` 就是工程级配置，不依赖它也能跑。

**配置与预览在编辑器里**：**资源 ▸ 分包 ▸ 分包配置与预览…**（`editor/src/panels/bundles.rs`）。

- 面板编辑的就是 `<工程>/bundles.json`，只在你点「保存 bundles.json」时落盘；
- 「扫描并预估」按同一份 `rustlua_infra::bundle_plan` 归组，并**用发布同款 zstd 编码器**
  （`BundleBuilder`，256 KB 块）逐组算出真实落盘字节 —— 所以 4 MB / 20 MB 的判断不是按原始字节拍的；
- 面板给出：按单元的合计与配额条（主包 4 MB、总量 20 MB）、每组原始/落盘/条目数、
  未归组/脚本不在 main/单元语法/具名分包未拆分等**全部问题清单**（`check_plan` 一次列全）。
- 预估是"未 cook"口径：不含图集页、字体子集与生成清单，所以是**下界量级**的准确值，
  与最终发布包的差异只来自这几步。


### 5.7 加载集观测（实测代替推断）

静态依赖图在本工程上只覆盖 55%~61%（§1.3 结论 4），所以分组不再靠"猜引用"，改为**观测真实读取**：

- 引擎在 `vfs`（所有工程资源读取的唯一入口）记录 `(上下文, 工程相对路径, 次数)`；
  **上下文由场景切换打点**（启动场景 + Lua `scene.load`），只有真正读字节的 `read` 才记，
  工程根之外的读取不记；
- 采集：`game --project <工程> --trace-loads <file>`（玩一段后关窗）；`--check` 也能产出 boot
  上下文。输出行契约：`game_load_trace_ok path=… entries=… contexts=…`；
- 编辑器：分包面板「读取观测」读同一份 JSON，给出
  ① **boot 读到但不在 main 单元**的路径清单（首屏白图的直接证据），
  ② 每个上下文的条目/字节/组归属与主导组占比（判断"按场景拆包值不值"）；
- **分组建议（可一键应用）**：按观测生成两类确定性建议——某个 `sub` 组只在一个场景上下文里被读到
  → 建议改成 `sub:<场景名>`；boot 读到但不在 main 的路径按组聚合 → 建议把该组设为 `main`。
  建议只改 `unit`，应用后配置标记为未保存，需重新扫描/读取观测；
- 语义边界：观测是**采样**，回答"实际读到了什么"，不回答"可能读到什么"；
  它替代的是"按依赖图推断加载边界"，不是完备性校验。

### 5.8 通用接入（任意 RustLua 工程）

分包方案是**引擎能力**，不绑定 `examples/game_jhyt`。任意工程的最小接入：

1. **零配置也能用**：不写 `bundles.json` 时用 `BundleConfig::generic_domains()`
   （`core` / `assets` / `brand` 三组，只依赖 `project.toml`、`scripts/`、`scenes/`、
   `assets/`、`splash/`、`branding/`）。
2. **要更细的加载边界**时，在工程根写 `bundles.json`（§5.6）：可先用
   `assetc bundles init <工程>` 生成通用草稿（`--force` 才覆盖），再由编辑器细化；编辑器
   **资源 ▸ 分包** 可直接编辑并预估落盘字节。
3. **构建**：`assetc package <工程> -o <包> --bundle grouped` → `bundle_plan.json`。
4. **分发**：`assetc layout <包> --json` 得到「单元 → 根」；
   `node scripts/build/bundle-layout.js --file layout.json --apply <发布根>` 搬文件并写
   `game.json` 的 `subpackages`；`--verify` 校验形状。
   一步到位：`powershell -File scripts/build/apply-bundle-layout.ps1 -Launcher <发布根>`
   （`-Assetc` 指定 assetc.exe，`-SkipVerify` 只搬运）。
   `package.ps1 -MultiSub`（opt-in，仅微信 `subpackage` 形态）会在**原子交换前的 staging 内**
   自动调用它（apply 失败不会碰最终发布目录），拆完再按"launcher − 全部 pack*/"重测 4 MB/20 MB
   配额；默认关闭，默认产物逐字节不变。
   **适配层已接线（2026-10-18）**：`wechat-adapter.js` 启动时读 launcher 根的
   `bundle_plan.json`（`bundle-layout --apply` 从 `pack/` 复制一份到主包可读的位置），用
   `bundle-roots.js` 把逻辑路径 `pack/<相对路径>` 以及**容器路径** `pack/bundles/<x>.rlb`
   一起路由到 `pack/`、`pack/` 或 `pack-<name>/`。
   **boot 只等主包 + wasm 根**：`mount_from_reader_partial` 只挂当前可读根里的容器，缺的记
   `pending`；具名根在 preinstall 之后后台 `loadSubpackage`，root ready 后用
   `mount_bundles_from_reader` 把该根容器补进 `BundleSet`。老内核没有这两个导出时回退到
   "boot 前全量预挂"（保证旧产物仍能起）。
   计划外路径回落旧单根规则，并计入 `__RUSTLUA_DIAG().bundle.plan_misses`；
   没有计划表时完全走旧单根路径（默认产物行为不变）；计划表读不到/解析失败会
   响亮记一次（`bundle.error`）后继续，不会掀翻启动。
   适配层的路由表已单独成模块：`plugins/wechat-minigame/bundle-roots.js`
   （`rootOfUnit` / `planRootIndex` / `rootsForPaths` / `rootForPath` / `missingRoots`，
   `--self-test` 可跑；模块本身不依赖 Node `fs`，微信侧可直接 `require`，发布脚本
   已把它列入必带文件），与发布侧共用同一套根命名；适配层接线只调它，不再自己拼目录。
   挂载编排也在同模块：`mountRoots`（按顺序、幂等、`load` 失败上抛）与
   `ensurePathsMounted`（读一组路径前只挂它们所在的分包根）；适配层按单路径调用，
   每个根各自有状态（`bundle.roots.<root>.state`）。
   产物与计划的一致性由 `scripts/build/check-bundle-mounts.js --launcher <发布根>` 检查：
   以计划表为准（优先 launcher 根，回落 `pack/bundle_plan.json`），要求每个根有目录、
   分包根有 `game.js`、声明的容器齐全（缺件 exit 1）。`apply-bundle-layout.ps1` 在 apply 后
   自动跑这条检查；它的临时 layout 文件写在系统临时目录，不落进发布包。
   **boot 元数据**：launcher 根计划表另有 `boot = { roots, groups, wasm, entries }`，
   `package.ps1` 在首屏切分后写入并调用 `check-boot-closure.js`：boot roots 必须包含
   `pack` 与 `wasm_root`，boot groups 必须恰好是 `unit = "main"` 的组，
   `pack.json.entries` 必须与 `boot.entries` 完全一致，main 容器/boot entry/wasm 必须
   真实存在；`-BootTrace <load-trace.json>` 时 boot 上下文读到的任何非 main 路径直接失败。
   `apply-bundle-layout.ps1` 与 `verify-wechat-minigame.ps1` 也跑这条门，所以 lazy 不是
   "大概安全"，而是有计划表 + 首屏清单 + 真实文件三方对账。
   实测（2026-10-19，`game_jhyt` 用 1.88 重打、并把 wasm 拆到 `pack-wasm/` 的微信产物）：
   `bundle_mounts_ok roots=4 paths=1375`、`subpackages=3`；boot 只等 `pack + pack-wasm`，
   `pack-sub/` 的非启动容器在后台挂载（harness 报 `补挂 pack-sub 容器 981 个`、`补挂 pack-audio 容器 16 个`）。
   具名根端到端：`scripts/test/test-wechat-multisub.ps1` →
   `wechat_multisub_test_ok roots=3 subpackage_loads=3`（boot 根 `pack-wasm` + 后台 `pack-sub`/`pack-audio`）。
   `verify-wechat-minigame.ps1` 现在也认 launcher 根的 `bundle_plan.json`：多根时按全部
   `pack*` 根算主包/总量，逐根要求 `game.js`，并先跑 `check-bundle-mounts` 对账；
   单根产物仍走原来的"有且仅有 1 个 pack"断言。两者同一夹具实测 `verify_exit=0`。
   **主包瘦身（2026-10-19）**：确认 `branding/splash.png` 与 `brand:cdn` 容器里的
   `splash/splash.png` **逐字节相同**（`assetc verify` → `assetc_verify_ok entries=1`）。
   微信启动图改为 `branding/splash.jpg`（960×540、q80，83,968 B；原 PNG 1,254,162 B），
   `assetc package --exclude-cdn` 把 `brand` 组从本地包剔除；实测主包 **1,527 KB**
   （4 MB 的 37.3%，≤1.5 MB）、`pack` **2,124 KB**、`pack-wasm` **5,400 KB**、总量
   **9,051 KB**。`launcher` 根的 `bundle_plan.json` 带 `launcher_root: true` 标记：
   `sub-root` 宿主把根路径回落到 `pack/` 时，适配层不会把单分包产物误判成多根。
5. **调优**：`game --project <工程> --trace-loads <文件>` 采一次加载集，
   编辑器面板「读取观测」给出 boot 缺口与可一键应用的分组建议。

引擎侧不出现具体游戏的路径：`title_bg_pixel.png`、`art:ui` 这类约定属于**工程配置**
（`examples/game_jhyt/bundles.json`），`default_domains()` 只是示例预设。

## 6. 压缩与纹理 cook 策略

### 6.1 压缩策略：**没有按类型表，只有逐块判定**

早期草案按后缀列了"文本 deflate / png store / mp3 store"，**实测把这个表推翻了**（§1.5(a)(b)）：

- 逐文件压缩看不到跨文件冗余，所以 `png` 看起来"不可压"（0.993）；
- 但同一批 png 进 256 KB 块后是 **0.840**，收进容器后整包 **0.580**；
- 反过来，`mp3`（0.966）与 `art:world`（0.953）确实压不动——**但它们只是"不值得压"，不是"必须 store"**。

所以策略收敛成一条规则：

> **每个块都试压，压完如果没变小就原样存**（`Block.flags.bit0 = 0`）。
> 实测整包 23 个块里 22 个选择压缩、1 个 store；这条规则的作用不是省字节，而是
> **不给已经压不动的数据白付解码成本**（音频块的首选路径就是直读）。

例外只有两类，都不是"按后缀"而是"按内容已经压过"：

| 情形 | 处理 | 理由 |
|---|---|---|
| `.rltex`（cook 后的图集页/大纹理） | 条目标志 `ENTRY_FLAG_RLTEX`，容器照常压（裸像素本身可压） | 页的正确形态是**裸像素**，压缩交给容器统一做；不要在 `.rltex` 内部再压一层（双压无收益、还挡住块级复用） |
| 将来引入的预压资产 | 条目标志 `ENTRY_FLAG_PRECOMPRESSED`，容器跳过 | 给 VRAM 压缩纹理留口子（§11） |

逐文件 gzip 的旧路径在 bundle 形态下退役；loose 形态保留（供编辑器与热重载）。

### 6.2 图集：打"共绘集"，不打"同类集"

判定"共绘"的三条证据（按可信度）：

1. **同一预制体/场景同时引用**（`dependencies.json` 的边：`hud.prefab → 15 张 ui png`）——最硬；
2. **同一屏 UI 的九宫格/图标**（`assets/art/ui/**`，99 文件 62 KB，一屏全上）；
3. **瓦片集**（已是单张 sheet，`atlas_cols/rows` 语义，不进图集流程）。

**v1 不打，但留触发条件**：角色/敌人帧（`characters` 448 + `enemies` 219 文件）——按角色打页换不到合批，
页还比散图大 3.3 倍，所以这一批"文件多"的问题交给容器解决。若 profiling 显示一屏多角色时纹理切换成为
瓶颈，再按**跨角色共绘**打一张 actor 页（触发条件：某场景每帧纹理切换 > 8 次，且 draw call 是瓶颈）。

图集配置写在资源旁 `assets/art/ui/atlas.json`（或 `project.toml` 的 `[atlas]` 表）：

```toml
[[atlas]]
name = "ui_hud"
include = ["assets/art/ui/hud/**", "assets/art/ui/common/**"]
max_size = 2048
padding = 2
format = "rltex"        # 或 png（仅在编码器修正后）
```

### 6.2.1 组织策略：目录默认聚合（2026-10-18 落地）

`atlas.json` 现在**优先按目录聚合**，不再需要逐条维护 include：

```json
{
  "schema": 1,
  "auto": { "enabled": true, "root": "assets/art/ui", "max_size": 1024,
            "padding": 1, "format": "rltex", "single_min_pixels": 65536 },
  "separate": ["assets/art/ui/title/ui3.png"]
}
```

- `assets/art/ui/title/` 下的小图自动并进 **`title_default`**；
- `separate` 里点名的图（编辑器属性面板勾选后写进这里）单独成 **`title_ui3`**；
- 像素面积 ≥ `single_min_pixels`（默认 256²）的图**自动**单独成集——"大图成为单图集"；
- 目录里只剩一张可合并的图时也按单图集处理（没有合并收益）。

**自动跳过三类图**（都不报错，只打一行 `atlas_cook: 跳过 …`）：

1. `Tilemap` 纹理——UV 按整张图算，换页地形整体错位；
2. 动画表（`sheet=`）——`AnimationStateMachine::current_frame_uv` 按整张表算 UV，**不查重定向**；
3. 九宫格（`_9s`）——边框按整张纹理算，换页会取错位置。

显式 `atlases` 与 `auto` 可并存；**显式配置里点名要打的图**撞上上面三类是硬错误
（作者意图与规则冲突必须让人看见），`auto` 扫描撞上是跳过。

**实测（`root=assets/art/ui`，1024）**：生成 14 个 `*_default` 页 / 28 个条目；
`draws 16 → 11`、`first_frame_ms 8.8 → 64.8`、首帧内存 10.7 → 26.7 MB。
与 §6.2 的结论一致：**页总像素决定成本**，所以示例工程默认仍不启用
（`atlas.sample.json` 里是可直接拷用的配置）。

### 6.3 `.rltex`：图集页的编码形态

实测（§1.3 结论 3 那张页，四组对照）：

| 形态 | 字节 | 相对页 PNG | 相对散图 |
|---|---|---|---|
| 64 张散图 PNG（现状） | 46,045 | 0.30× | 1.00× |
| 页 → `image` 写出的 PNG（`Adaptive` 滤波 + flate2 L6，当前 `atlas_pack` 走的就是这条路） | 153,012 | 1.00× | 3.32× |
| 页 → 另一编码器（GDI+）写出的 PNG | 82,388 | 0.54× | 1.79× |
| 页 → 裸 RGBA + flate2 L9 | 38,688 | 0.25× | 0.84× |
| 页 → 裸 RGBA + zstd L9 | 31,035 | 0.20× | 0.67× |
| **页 → `.rltex` + 容器块 zstd L19** | **14,711** | **0.096×** | **0.32×** |
| 页 → 裸 RGBA + lz4 | 234,212 | 1.53× | 5.09× |

结论：**图集页不走 PNG，走 `.rltex`（裸像素，压缩交给容器）**——页比散图还小 3 倍，
于是"打图集涨字节"这个顾虑在正确封装下**不存在**。

`.rltex` v1 布局：

```
"RTX1" (4) │ w u32 │ h u32 │ fmt u8 (0=RGBA8, 1=RGB565, 2=RGBA4444) │ reserved u8[3] │
raw pixels（不压；压缩由容器块负责）
```

- 只在**图集页**与**大纹理**上启用；散图小 PNG 继续原样（省不了多少，还多一层风险）；
- 页的 `raw_len` 会是 8.4 MB 级 → 触发容器"大条目独占一块 + L19 档"那条规则（§4.3/§4.7）；
  解压 8.4 MB 原生 15 ms，wasm 预计 50~70 ms，发生在页面加载时（不是每帧）；
- 读侧收益：省掉 PNG 的 unfilter + 不必进 `image` 解码器分派（wasm 体积收益需实测，未当既成事实）；
- **不做 VRAM 压缩（ASTC/BC/ETC2）**：依赖现在能拉了，但真正的阻碍是**平台格式支持不一致**
  （WebGL2 无 BC/ETC2-全档、微信侧更差），留 `ENTRY_FLAG_PRECOMPRESSED` 位不实现（§11）。

#### 6.3.1 打包器现有两个缺口（批 D 必须顺手修）

1. **padding 与 POT 耦合**：`padding=2` 让 256 宽的帧一行只放得下 7 张（8 张到 2064 > 2048），
   10 行 660 px 高被 POT 抬到 1024 → 页面积翻倍、VRAM 翻倍（§1.3 实测）。
   修法二选一：`pot = false`（wgpu 不要求 POT），或 padding 只在同 row 内计入、页尺寸按
   实际占用而非 POT。
2. **超限源图直接报错**：`preview.png`（435×3778）会让整个打包失败，没有"降级/单列/跳过并告警"
   的第三态。批 D 的配置里需要 `oversize = "skip" | "split" | "error"`。

### 6.4 图集重定向表（不改工程源）

工程源里写的是 `texture=assets/art/ui/hud/ui_icon_hp.png`。打完图集后这张图不再作为独立文件存在，
而工程源**不应该**被改写成 `ui_hud.atlas#ui_icon_hp`（会污染所有场景/Lua，且让"关掉图集"变成大手术）。

做法：`bundle_plan.json` 旁产出一张 `atlas_redirect` 表（`原路径 → {atlas, region, w, h}`），
运行期在**装配期**查它：

```rust
// rustlua-render/src/atlas.rs 已有 resolve_atlas_reference；新增一层重定向：
pub fn resolve_redirect(root, raw) -> Option<(atlas_path, region)>
```

因为 `#区域名` 解析本来就发生在装配期（`script/scene_spawn.rs` 的 Sprite `texture=` 与
Lua `sprite.set`），重定向挂在这一个点上，**运行期抠图/合批代码零改动**——与 `docs/63` 批 B 的
同一处设计延续。

启用条件：`bundle_plan.json` 里有该表；没有则完全不生效（loose/编辑器形态天然走原路径）。

## 7. 运行时挂载

### 7.1 为什么能"只改一个入口"——证据

`rustlua-infra/src/vfs.rs` 的 `read` / `is_file` / `metadata` 先问 provider，再回落 `std::fs`；
`read_resource` = `read` + `pack::decode`。全引擎的工程资源读取**基本都已收敛到这里**：

| 资源 | 读点 | 走 vfs |
|---|---|---|
| 纹理 | `rustlua-render/src/texture.rs` | ✅ `vfs::read` |
| 图集 | `rustlua-render/src/atlas.rs` | ✅ `vfs::read` |
| 字体 | `rustlua-render/src/font.rs`、`host/runtime_scene/fonts.rs` | ✅ `read_resource` |
| Lua `require` / 脚本 | `rustlua-scripting/src/script/require.rs` | ✅ `vfs::read` |
| 音频 | `rustlua-scripting/src/script/api/audio.rs` | ✅ `read_resource`（宿主侧 `rustlua-audio` 另有 `fs::read`，见 §8） |
| 场景切换 | `rustlua-scripting/src/script/transition.rs` | ✅ `vfs::read` |
| 预制体 | `rustlua-scripting/src/script/api/prefab.rs` | ✅ `vfs::read` |
| 瓦片尺寸探测 | `host/runtime_scene/tilemap.rs` | ✅ `vfs::read` |
| 项目清单 | `rustlua-infra/src/project_config.rs` | ✅ `read_resource` |
| **发布完整性校验** | `crates/game/src/cli.rs` `verify_project_inner` | ❌ **`fs::read` + `path.is_file()` + 目录遍历** |

最后一行是全方案唯一必须动调用点的地方，见 §8。

### 7.2 API 形态（`rustlua-infra::bundle`）

```rust
// —— 批 A 已实现（rustlua-infra/src/bundle.rs）——
pub const BUNDLE_MAGIC: &[u8; 4] = b"RLBU";
pub struct BundleIndex { /* 条目表 + 块表 + 块偏移前缀和，由 bytes 解析，只读 */ }
impl BundleIndex {
    pub fn parse(bytes: &[u8]) -> Result<Self, BundleError>;
    pub fn paths(&self) -> impl Iterator<Item = &str>;      // 审核/枚举用（替代目录遍历）
    pub fn contains(&self, path: &str) -> bool;
    pub fn entry(&self, path: &str) -> Option<&Entry>;
    pub fn blocks(&self) -> &[Block];
    pub fn salt(&self) -> u32;                              // 批 F 的 nonce 前缀
}

pub trait BlockSource {                                    // 桌面 = File+seek（批 B）；wasm = 内存切片
    fn read_range(&mut self, offset: u64, len: usize) -> Result<Vec<u8>, BundleError>;
}
pub struct MemSource { /* 整包驻留内存：批 A 唯一实现，也是 Web 宿主最终形态 */ }

pub struct BundleReader<S: BlockSource> { /* 单块缓存 + 逐条目 FNV 校验 */ }
impl<S: BlockSource> BundleReader<S> {
    pub fn read(&mut self, path: &str) -> Result<Option<Vec<u8>>, BundleError>;
    pub fn read_unchecked(&mut self, path: &str) -> Result<Option<Vec<u8>>, BundleError>;
    pub fn verify_all(&mut self) -> Result<(), BundleError>;   // --check 用（批 B 接）
    pub fn decoded_blocks(&self) -> u64;                        // 诊断：解压过几次
}

// —— 批 A 已实现，但挂在 `bundle-write` feature（C 版 zstd，只在 assetc 打开）——
pub struct BundleBuilder { /* 逐条目 add → build */ }
pub struct BundleBuild { /* bytes + raw_len + stored_len + blocks + index_len + checksum */ }

// —— 批 B 才落地（挂载多个包 + 接 vfs provider）——
pub struct BundleSet { /* 已挂载的多个 bundle */ }
impl BundleSet {
    pub fn mount<S: BlockSource + 'static>(&mut self, reader: BundleReader<S>) -> Result<(), BundleError>;
    pub fn read(&self, path: &str) -> Option<Vec<u8>>;
    pub fn paths(&self) -> impl Iterator<Item = &str>;
}
```

- `BundleSet` 作为 vfs provider 的**第一优先级**，provider 内部顺序：bundle → 平台表/文件系统（批 B）。
- 桌面 provider 用 `Mutex<BundleSet>`（`Send + Sync` 要求已有先例）；wasm 用 `thread_local`（同 `vfs` 现状）。
- 块缓存：批 A 是**单块**（`RefCell<Option<(u32, Rc<Vec<u8>>)>>`，命中不重复解压，有门钉住）；
  批 B 视实测决定是否升到 N 块 LRU，大块（页面）永远只留 1 块。

### 7.3 三平台接线

| 平台 | 挂载方式 | 请求数/IO | 预载策略 |
|---|---|---|---|
| 桌面 | `game --pack pack` 启动时按 `bundle_plan.json` 把 `unit=main` 的 bundle 挂上；其余按需 `mount_file` | 1,372 次 `open` → 约 12 次；块读 256 KB 粒度 | 首帧只挂 `core`，进场景再挂对应组 |
| WebGL | `preload_all` 从"逐个条目 fetch"改为"逐个 bundle fetch"：`fetch("pack/bundles/core-xxxx.rlb")` → `BundleSet::mount(bytes)` | **1,372 次 request → 与 bundle 数同阶**；并发仍 8 | 启动期挂 `core` + 启动场景所在组；切场景前 `request_bundle(组名)` 异步预取 |
| 微信 | bundle 就是普通文件：`pack/bundles/*.rlb`（物理名 `*.rlb.txt`），沿用现有 `pack.json` 路由；`readFileSync` 定位读（`position`/`length` 参数，**真机待验**，见 §12 风险 4；不成立时退化为整文件读 + 内存切片） | 同上；另外**分包粒度 = 组粒度**，4 MB 限额由组大小直接满足 | `wx.loadSubpackage` 后挂该分包内全部 bundle |

WebGL 侧的关键点：**wasm 侧不需要 JS 懂格式**。现在浏览器路径已经有 Rust 侧资源表
（`lua_bridge::LUA_RESOURCES` + `provider_from_resources`），bundle 解析完全在 Rust 做，
JS 只负责"把某个 URL 的字节给我"；微信路径靠 `wechat-adapter` 的字节通道（0.7.11 起返回
`ArrayBuffer`/`Uint8Array`），同样是"给字节"，不解析。

### 7.4 缺件必须响亮

今天的静默失败点：纹理读不到时回退成内建白贴图（`texture.rs` 注释里记着"玩法画面成了一张白屏"）。
bundle 之后多了一种新的缺件形态——**文件在包里，但不在已挂载的 bundle 里**。判定与提示必须分开：

| 情形 | 判定 | 行为 |
|---|---|---|
| 不在任何 bundle 条目里 | `BundleSet::paths()` 无此路径 | 与今天"文件不存在"同义 → 明确错误 |
| 在 bundle 里但该 bundle 未挂载 | `bundle_plan` 有该路径、`BundleSet` 无 | **响亮错误 + 打印所属组名 + 提示先 `request_bundle`**；Web 上给可读诊断（不静默白贴图） |
| 挂在已挂载 bundle 里但解压/校验失败 | `fnv1a` 不符 | 立即错误（数据损坏，不许继续） |

三条都要有回归门；第二条是 bundle 化引入的**新**失效模式，必须最显眼。

### 7.5 预载闭包与 bundle 计划

今天是"入口闭包预载，遇 `opaque`/缺文件则全量预载"（`docs/26` §2 的两条换算）。bundle 之后：

- Web 启动预载集 = `core` + 启动场景组的 bundle（不再逐条目）；
- `opaque` 非空的工程 → 仍然全量挂载（退化成今天的行为，不新增风险）；
- 切场景：`bundle_plan.json` 里 `scene → 组` 的映射给出需要预取的组，`request_bundle` 后同步可用。

### 批 E — 内容哈希命名 + 增量分发 ✅ 2026-10-19 落地（引擎侧）

- 命名：`bundles/<组>-<hash8>.rlb`（批 C 已完成，hash8 = 整包 FNV 的低 32 位）。
- **计划表加 `hash`（16 位十六进制整包 FNV）**：增量对比只比它。文件名里那 8 位是截断值，
  而且名字一改就没人记得住当初的语义。
- **增量对比 `BundlePlan::diff(local, remote)`**（`rustlua-infra`，纯函数、可单测）：
  ① 远端有且 hash 相同 → `unchanged`（复用，不下载）；
  ② 远端有但本地没有/hash 不同 → `download`（含新增组）；
  ③ 本地有、远端没有 → `remove`（旧组残留，留着白占配额）。
  **按组名配对而不是按文件名**：文件名带 hash，按名配会把"改名"当成"删旧增新"，
  每个版本都重下没变的包（缓存全废）。空 hash（旧计划）一律视为"不同"，不猜。
- 门：`plan_diff_compares_by_group_name_and_hash`（相同/变更/新增/删除/旧计划五条断言）；
  实测 `game_jhyt` 六组的计划 hash 低 32 位与文件名逐一相符。

**没做**：宿主侧的下载器接线（Web 的 `fetch` 与微信适配层的远端包）仍按整包/整文件工作，
`diff()` 目前只有库与门、没有生产调用者；差分 patch（bsdiff）仍不做（触发条件：单 bundle
> 4 MB 或月更频繁）。接线需要改适配层 JS 并跑一次微信 harness——与批 C2 同一批更安全。

但它**仍在被打包**（1.2 MB 进容器）——它本该由发布器单独放到放行根、不随 pack 发布。
`unowned` 组把这件事暴露成一行数字（`brand:cdn=1224KB`），是否彻底剔除要在打包输入侧改。

**顺带发现的真问题（`unowned` 组第一次派上用场）**：重建后的计划表里出现
`unowned:sub=2288 KB`，条目是 `splash/splash.png`——启动器品牌图被当成**游戏资源**打进了包。
它不该随 pack 发布（`package.ps1` 会单独把 branding 放进放行根）。这正是"未归组要显式列出来"
这条设计的价值：2.2 MB 死重在一个字段里露头，而不是悄悄进包。
**顺带回答"合批为什么不降"**：`SpriteBatch` 的排序键是
`layer → texture_id → 提交序`（`sprite_batch.rs:279`，layer-major、texture-minor）。
所以图集只能在**同一层内**合并；标题画面那 16 个 draw 分布在十几层上（背景/暗角/墨带/
logo/按钮/装饰/印章…），跨层不可能合并——那是**画家顺序**，合并就错画。
要真降 draw，只有两条路：① 同层多纹理进阶到图集（需先修上面的 GPU 路径）；
② 允许相邻且不重叠的层合并（要真做重叠检测，复杂度高、收益取决于美术层次）。

顺带修掉一个真问题：`atlas_redirect.json` 原本落在 `unowned`（sub 单元）会被延迟挂载，
而装配期**启动就要查它**；已把它并入 `core` 组默认 include。

**② 启动闭包优先的块排序** ✅ 已落地并**实测到读数**

先记一个坑：第一版是在 assetc 侧把 `group.paths` 排好序再 `add`——**完全无效**，因为
`BundleBuilder::build` 内部会按名字重排条目。实测 blocks 分布一动不动（`boot_blocks=5`）。
正确做法是让 builder 参与排序：新增 `add_ranked(path, bytes, rank)`，`build()` 的排序键改成
`(rank, name)`（两档都由内容决定，仍然逐字节确定）。

分档：
- **0 档**（引擎确定在 boot 期读的四个文件）：`project.toml`、`atlas_redirect.json`、
  `scenes/main.scene`、`scripts/main.lua`，合计约 75 KB；
- **1 档**：其余 `scripts/**`（`require` 同步，boot 会连带读到）；
- **2 档**：场景、预制体等按需条目。

新增 `assetc inspect <包目录|.rlb>`（索引是 zstd 压缩的，外部脚本解不了，只能由 Rust 侧给读数）：

| 产物 | boot 条目所在块 | `boot_blocks` |
|---|---|---|
| 排序前（旧 pc 产物） | `project.toml`=0、`scenes/main.scene`=1、`scripts/main.lua`=6 | **3** |
| 排序后 | 四个锚点**全在 block 0** | **1** |

判定口径要小心：**不能**把 `scenes/*` 全算进"启动闭包"——那样会得到 3 个块的假读数
（其余场景启动根本不读）。门：`boot_closure_sorts_first`；读数工具：`assetc inspect`。

**实测 `sim_boot_ms`（`scripts/test/test-webgl.bat`，各 2 次）**

| 时间点 | 读数 |
|---|---|
| 排序前 | 145.7 / 146.7 ms |
| 排序后 | **141.4 / 133.8 ms**（均值 146.2 → 137.6，**−8.6 ms / −5.9%**） |

单次抖动约 ±8 ms，所以这个改善"方向明确、幅度不大"：确定性证据是 `boot_blocks 3 → 1`，
毫秒读数只是它的外化。**没有**像最初预估的省 50–60 ms——因为 boot 真正的大头是
`scripts/**`（1600 KB / 155 文件，`require` 同步会摸到），换排序动不了它。

**块大小扫描（`assetc package --block-size <KB>`，WebGL 实测）**

| 块大小 | 容器总落盘 | 块数 | `sim_boot_ms` | 首帧内存 |
|---|---|---|---|---|
| 64 KB | 3,644 KB（0.256） | 71 | 未测 | — |
| 128 KB | 3,558 KB 量级 | 约 44 | 144.1 | 10.2 MB |
| **256 KB（默认）** | **3,549 KB（0.249）** | 26 | **133.8 / 141.4** | 10.6 MB |
| 1024 KB | 3,513 KB（0.247） | 11 | **280.7** | 13.6 MB |

**结论：256 KB 保持默认，别再往大调。** "块大 ⇒ 启动少解几次 ⇒ 更快"这个直觉被实测否定：
1 MB 块省了 36 KB 落盘，却让启动慢了一倍（+140 ms）、首帧内存 +3 MB——因为启动期每次
miss 都要解一整块，boot 要摸的脚本本来就有 1.6 MB，粗粒度只会把"按需解"变成"整块解"。
128 KB 与 256 KB 在噪声范围内持平，落盘还更大，没有理由换。

**harness 放宽 `branding/**` 的贴图探针** ✅

`scripts/verify/wechat-minigame-harness.js` 原来把**任何** `Image.src` 解析失败都记成
"引擎贴图读取失败"。但 `branding/icon.png` / `branding/splash.png` 是启动器 DOM 图
（index.html 的 `<img>`、启动画面），**不走引擎纹理管线**；假宿主的路径模型只覆盖
代码包/用户目录方言，于是它解析不到就报红。判定为"与资源形态无关"的依据：容器形态与
`-BundleMode none` 散文件形态**都**报同一条。

改法：`branding/**` 的失败**单独计数**（`stats.brandingImageFailures`，ok 行里是
`branding_images=N`），仍照常调用 `onerror`——**放宽统计归属，不是让它静默消失**。

验证：把 `launcher/branding/splash.png` 移到发布目录外再跑 →
`branding_images=1`、`image_failures=0`、`exit=0`（改之前这一条会把整轮判红）。
实验口保留：`assetc package --bundle grouped --block-size <KB>` 与
`package.ps1 -BlockSizeKb <KB>`（`0` = 默认）。

**④ 一次 BOM 事故（值得单列，因为症状离原因很远）** ⚠️ 已修

我用行级重写改 `scripts/build/package.ps1` 之后，**文件丢了 UTF-8 BOM**。PowerShell 5.1 便按

它把排查带偏了两轮：我先后怀疑适配层缓存改动、以及对照 `-BundleMode none`——**两种形态报

（`wechat_exit=0`、4 种 path_style 全 `harness_ok`）。

顺带发现仓库重排后另有 2 个 `.ps1` 也没有 BOM（`scripts/lib/bundle-discovery.ps1`、

**③ `-AssetPack remote` 远端缓存** ⚠️ 已诊断，修复回退

真因：`cachePathFor` 写侧在清单落地前只能写**不带发布标识**的路径，读侧却只查带标识的路径
⇒ 永远 miss、每次重下（`cache=0`、`main.lua` 读不到）。加 `user-data-unversioned` 读候选后
**远端 + 散文件**形态通过；但同一改动让**分包 + 容器**形态出现"启动期间 6 次 pack/ 读取被未挂载分包挡下"，

### P2 债务清理（2026-10-19）

1. **计划表自校验** ✅：`bundle_plan.json` 增加 `checksum`（对 `groups` 的规范化 JSON 取 FNV-1a 64），
   写盘前签、`BundlePlan::parse` 时核。空串表示旧计划（仍可读，向后兼容）。
   **同时修掉一个真问题**：`game::bundle_boot::read_plan` 原来把解析失败降级成"没有计划"，
   于是"计划表坏了"和"没有计划表"无法区分——现在存在但解析失败是**硬错误**，启动当场中止并点名文件。
   实测：把计划表里某个组的 `entries` 改一个数字 → `挂载资源包失败：… 自校验失败：记录 47a75cca… 实际 c85dd8c7…`。
2. **解压成本实测**（替代"wasm 体积"这个没法直接量的指标）：
   `game --check`（会解压并逐条目校验全部块）在 `examples/game_jhyt` 上，
   容器形态 **736 / 722 ms**，目录形态 **447 ms** ⇒ **解压+全量校验整包（6 容器 / 3.5 MB 落盘 / 25 块）≈ 282 ms**。
   折算约 **12.4 MB/s 原始字节**（含 FNV 校验与块缓存开销）。这是"发布前全量校验"的成本，
   启动期只解被读到的块，不摊这份钱。
3. **`diff()` 接宿主下载器** ✅ 已接线（`wechat-adapter.js`），用的是**内容寻址缓存**这条更省的路：

   - 容器的**文件名自带内容哈希**（`bundles/<组>-<hash8>.rlb`），所以缓存键直接用文件名：
     `user-data/bundle-cache/<组>-<hash8>.rlb`，**不**再挂在发布级目录 `v-<清单哈希>/` 下。
     发布级键是"改一个字节整批重下"——散文件时代没得选（单文件看不出内容），容器有内容寻址就不必再付。
   - 与 `BundlePlan::diff` 的三条语义一一对应：远端有且内容相同 → 复用（命中同名缓存）；
     内容不同 → 下载（文件名变）；远端没有 → 清理（`stale_removed`）。
   - 启动日志新增一行：`容器增量缓存 bundles=6 hit=N miss=M stale_removed=K`。

   **实测前提成立**：改一个属于 `art:world` 的素材后重新打包，6 个容器里**只有 `art-world` 的文件名变**
   （`art-world-02fa6603.rlb` → `art-world-8cfc3ab5.rlb`），其余 5 个逐字节同名 ⇒ 下一版只重下 1 个容器。
   harness 实测首轮 `bundles=6 hit=0 miss=6`（冷缓存），与预期一致。

   **顺带发现两个坑（都已处理/记录）**：
   - harness 有一条硬门"适配层用到了 harness 未实现的 `FileSystemManager` 方法就判失败"，
     新增的 `readdirSync` 当场被它抓到；已在 harness 的 FS 垫片里实现（返回名字数组，与微信一致）。
   - **`-AssetPack remote` 形态当前是坏的，且与本次改动无关**：先用**散文件**（`-BundleMode none`）
     打一份 remote 包复验，同样是 `cache=0` + `failed to load /project/scripts/main.lua`。
     也就是说远端回落"每次读都重新下载、且缓存从不命中"是既有问题。这条单独记成待办，
     不与容器混在一起修（两边都改会让归因失效）。

**没做**：密钥仍是内嵌固定值（"防随意读取"，不是强加密；密钥分发是产品决策，不在本批范围）。

## 11. 明确不做（与触发条件）

| 不做 | 理由 | 重新考虑的触发条件 |
|---|---|---|
| lz4 / brotli 压缩 | 实测 lz4 整包 0.664、页面 1.53×——明显更差；brotli 缺 wasm 侧纯 Rust 解码的成熟对照 | 出现"解压延迟敏感、体积不敏感"的场景 |
| zstd **字典**（dictionary） | 块压缩已经吃掉跨文件冗余（0.580），字典再挤空间有限，却要多维护一个版本化文件 | 出现大量 < 4 KB 散资源且块压缩后仍 > 0.8 |
| ASTC/BC/ETC2 VRAM 压缩 | 编码器 crate 现在能拉，但**平台格式支持不一致**（WebGL2 无 BC、微信侧更弱），且要按平台各烘一份 | 出现 3D 大纹理为主的商业项目，且能接受按平台分别烘焙 |
| 运行时 bundle 引用计数与卸载 | 本项目全程资源 < 10 MB，卸载收益 < 复杂度 | 单项目资源 > 200 MB 或移动端内存卡死 |
| 差分 patch（bsdiff 类） | 内容哈希命名已解决缓存失效 | 单 bundle 频繁超 4 MB |
| 边下边播的音频流（Range 流式解码） | 音频总计 1.4 MB，整包更省事 | 出现 > 50 MB 的语音包 |
| 编辑器读 bundle | 编辑器必须能改资源；bundle 是只读发布形态 | 不做（这是设计而非缺失） |
| 图集 MaxRects / 旋转排布 | shelf 的 golden 门更稳；本方案的实测浪费来自 **POT+padding**（§6.3.1），换装箱算法治不了 | 修完 `pot=false` 后占用率仍 < 60% |
