# 技术决策记录

## 使用说明

所有会影响架构、公共 API、资源格式、依赖或发布平台的决策都写入本文件。旧决策不删除，通过状态标记为 Accepted、Superseded 或 Rejected。

## ADR-0001：采用 Rust 作为引擎核心

- 状态：Accepted
- 日期：2026-08-20
- 原因：需要接近 C++ 的性能、无垃圾回收运行时、较强的内存和并发安全性。
- 代价：游戏行业生态和主机平台支持不如 C++，需要更多自行建设。
- 回滚：保留 C ABI/插件边界，避免未来接入主机或特定 C++ SDK 时重写全部引擎。

## ADR-0002：采用 Lua 作为游戏脚本

- 状态：Accepted
- 日期：2026-08-20
- 原因：运行时轻量、嵌入简单、适合玩法热重载和快速迭代。
- 代价：静态类型和 IDE 能力弱于 C#，需要 API 封装和类型提示。
- 回滚：脚本边界以稳定句柄和命令 API 为中心，未来可增加另一种脚本语言。

## ADR-0003：Windows 优先，2D 优先

- 状态：Accepted
- 日期：2026-08-20
- 原因：降低独立开发者的首发复杂度，先用垂直切片验证引擎价值。
- 代价：早期不覆盖主机、移动和完整跨平台需求。

## ADR-0004：先使用成熟第三方库

- 状态：Accepted
- 日期：2026-08-20
- 范围：wgpu、Rapier、mlua、egui、Serde、tracing 等。
- 原因：独立开发者不应重复实现图形后端、物理、音频和序列化基础设施。
- 约束：通过适配层接入，锁定版本并记录许可证。

## ADR-0005：编辑器采用独立 crate，egui/eframe 起步

- 状态：Accepted
- 日期：2026-08-20
- 范围：M5 编辑器 MVP
- 决定：编辑器作为独立 `editor` crate，第一版采用 `egui` + `eframe`；编辑器通过 `engine_core` 公共 API 访问场景、资源和脚本。
- 原因：独立 crate 可以隔离编辑器依赖和运行时发布包；egui/eframe 适合独立开发者快速完成 Windows 优先的工具界面，并可复用现有 Rust 代码。
- 代价：需要处理 eframe 与现有 wgpu/winit 版本兼容；GUI 自动化能力弱于无窗口测试。
- 约束：先实现无窗口项目检查和状态模型，再接入复杂 GUI；依赖版本锁定在 Cargo.lock；若依赖冲突，回滚为独立 winit + engine_core 状态模型，不修改 M4 场景格式。
- 重新评估条件：M5-01 最小窗口无法构建、启动稳定性不达标，或编辑器与运行时依赖无法共存。

## ADR-0006：M8 采用 glTF 2.0 作为 3D 交换格式

- 状态：Accepted
- 日期：2026-08-22
- 范围：M8 轻量 3D 的 Mesh、材质、纹理、节点和动画导入。
- 决定：首版支持 `.gltf` 和 `.glb`，使用成熟的 glTF 解析库；导入结果先转换为 `engine_core` 自有的 CPU 资源模型，再由渲染层上传 GPU 资源。
- 原因：glTF 2.0 适合运行时分发，`.glb` 可将测试资产和二进制数据封装为单文件，成熟解析库能降低 accessor、buffer、材质和动画边界错误。
- 支持范围：静态 Mesh 的 POSITION/NORMAL/TEXCOORD_0、索引、基础材质纹理、节点层级；后续增加一个 skin 和动画状态。
- 非目标：首版不支持任意 glTF 扩展、 morph target、复杂材质扩展、压缩 Mesh 和自研解析器。
- 格式：assetc 以导入器版本控制缓存；场景、资源库和存档只接受当前版本，
  不保留旧格式迁移层；不支持的扩展必须报告文件、节点或 primitive 上下文并返回失败。
- 重新评估条件：目标资产无法由标准 glTF 2.0 表达，或解析库无法在当前许可证和 Windows 发布约束下使用。

## ADR-0007：M8 3D 坐标、单位和深度约定

- 状态：Accepted
- 日期：2026-08-22
- 范围：Math3D、Transform3D、Camera3D、Mesh 和光照。
- 决定：世界坐标使用右手系，+Y 向上、+Z 指向观察者；长度单位为米；矩阵按列向量语义组合，渲染使用 `clip = projection * view * model * position`；透视相机使用弧度 FOV 和正的 near/far 平面。
- 决定：深度纹理使用 `Depth32Float`，清除值为 1.0，比较函数为 `LessEqual`；3D pass 使用深度测试和写入，2D pass 保持现有无深度行为。
- 决定：颜色纹理按 sRGB 采样，法线/金属度/粗糙度和深度数据按线性数据处理；near 必须大于 0，far 必须大于 near。
- 原因：约定简单、适合 wgpu 默认坐标转换和常见 glTF 资产，且可用纯 CPU 数学测试验证，不依赖 GPU 截图才能发现基本错误。
- 代价：glTF 的节点坐标需在导入边界明确转换；阴影和后续反向深度不在首版范围。
- 重新评估条件：实测资产坐标转换普遍需要特殊例外，或 wgpu 后端验证显示深度范围与该约定不兼容。

## ADR-0008：M9 采用 rapier3d 作为 3D 物理后端

- 状态：Accepted
- 日期：2026-08-22
- 范围：M9 3D 可玩垂直切片的刚体、碰撞体、触发器和射线查询。
- 决定：在 `engine_core` 引入 `rapier3d`，与现有 `rapier2d` 在同一 workspace 统一版本锁定；3D 物理复用 2D 物理的 API 形态（`ColliderDesc`、layer/mask、sensor、碰撞事件进 Lua），固定时间步推进，与 Transform3D 双向同步。
- 原因：与现有 2D 物理同一生态，减少适配成本；不自研碰撞求解器（章程原则）。
- 代价：`rapier3d` 与 `rapier2d` 存在 API/特性差异，需要在 `engine_core` 内隔离 2D/3D 物理模块边界。
- 非目标：不做连续碰撞检测、软体、角色控制器内置组件等高级物理能力。
- 重新评估条件：2D/3D 物理共用边界导致维护复杂度过高，或版本冲突无法在 workspace 内解决。

## ADR-0009：M9 拆分 game_runner 渲染边界

- 状态：Accepted
- 日期：2026-08-22
- 范围：M9-01 渲染边界重构。
- 决定：将 `game_runner/src/main.rs` 中渲染相关职责抽出为独立模块，建立明确边界：GPU 资源（buffer/texture/pipeline 创建与生命周期）、RenderPass（2D/3D pass 与 depth 管理）、实例化与剔除数据缓冲、Camera/Depth 生命周期。重构只移动与组织代码，不改变渲染行为。
- 原因：M8 风险登记将「3D 改造堆积在 game_runner 单文件」标记为 P1；重构是继续扩展 3D 能力的前提。
- 代价：重构期间有回归风险，需要每个重构提交独立可编译并跑质量门。
- 非目标：本次重构不引入渲染图（render graph）、多线程渲染或 GPU-driven indirect。
- 重新评估条件：模块边界仍随功能膨胀，或重构导致 2D/3D 渲染行为回归。

## ADR-0010：M9 编辑器 3D Gizmo 首版只做平移

- 状态：Accepted
- 日期：2026-08-22
- 范围：M9-03 编辑器 3D Gizmo 与组件编辑。
- 决定：编辑器支持选中 3D 实体并拖动平移 Gizmo；Inspector 可查看/编辑 Transform3D、MeshRenderer、Camera3D、Light、碰撞体组件；旋转/缩放 Gizmo 后置。
- 原因：平移 Gizmo 足以支撑 3D 关卡搭建的核心需求，复杂度可控；旋转/缩放涉及轴向手柄与投影算法，推迟到有实际需求时再实现。
- 代价：搭建含旋转的场景需要手写旋转值。
- 非目标：不做 3D Gizmo 旋转/缩放、不做地形编辑器。
- 重新评估条件：3D 关卡搭建明显受限于无法可视化旋转/缩放。

## ADR-0011：M9 3D 样板游戏玩法锁定

- 状态：Accepted
- 日期：2026-08-22
- 范围：M9-04 3D 样板游戏垂直切片。
- 决定：3D 样板游戏范围锁定为：玩家角色（碰撞移动）、至少一种敌人（AI 追击）与攻击判定、拾取物、血条 HUD（复用 `ui.text`）、音效（复用现有音频）、胜负条件与重开一局；玩法逻辑全部由 Lua 驱动（参照 2D 样板游戏的模块化结构）。
- 原因：用一款小游戏验证「3D 引擎能力绑定游戏需求」的双轨原则，控制范围防止膨胀。
- 代价：不做复杂关卡设计、Boss、成长系统等，首版仅验证 3D 玩法链路。
- 非目标：不做 3D 音效空间化、不做多关卡/存档（按需）、不做联网。
- 重新评估条件：核心玩法验证通过后，由负责人决定是否扩展为正式 3D 游戏。

## ADR-0012：编辑器引擎内嵌采用单一 wgpu 设备 + offscreen 渲染目标

- 状态：Accepted
- 日期：2026-08-22
- 范围：M10 编辑器强化阶段的引擎内嵌游戏预览与 3D 透视视口。
- 决定：编辑器从 eframe 的 wgpu render_state 取 Device/Queue；改造 `Renderer` 支持「窗口 surface」与「offscreen 纹理目标」两种模式；游戏预览与 3D 场景视口用同一 wgpu 设备渲染到 offscreen 纹理，直接注册为 egui 纹理显示。
- 原因：单一设备避免跨设备 GPU 拷贝（方案 B）与 CPU readback 的每帧同步开销（方案 C）；offscreen 纹理可直接作为 egui 纹理，性能与集成度最好。
- 代价：`Renderer` 需重构为接受外部设备并支持非 surface 渲染目标，改造量较大但一次到位；需要把 game_runner 的运行时抽为可复用 crate。
- 非目标：不做跨设备渲染、不做编辑器内多适配器。
- 重新评估条件：单一设备导致 egui 与游戏渲染相互阻塞无法满足交互帧率，或 offscreen 纹理在目标 GPU 上不可用。

## ADR-0013：编辑器 3D 透视视口相机约定

- 状态：Accepted
- 日期：2026-08-22
- 范围：M10-04 编辑器 3D 透视视口导航。
- 决定：编辑器使用独立于游戏相机的轨道相机：右键拖拽轨道（yaw/pitch）、中键平移、滚轮缩放（与游戏内相机分离，编辑时观察用）。坐标系沿用 ADR-0007（右手 +Y 向上）。透视视口渲染复用内嵌渲染器的 3D pass，将场景渲染到 egui 纹理显示。
- 原因：编辑器相机与游戏相机分离是 Unity/Godot 惯例，编辑视角不影响游戏运行；轨道导航直观易用。
- 代价：编辑器需要维护相机状态与输入映射；透视视口与俯视模式共存需可切换。
- 非目标：不做编辑器相机书签、多视口。
- 重新评估条件：轨道导航在编辑场景中明显不便，或透视视口性能不可接受。

## ADR-0014：资源系统状态机与依赖图

- 状态：Accepted
- 日期：2026-08-25
- 范围：M12 资源系统闭环（ResourceDatabase、ImporterRegistry、依赖图与失效传播）。
- 决定：资源生命周期用显式状态机建模（`ResourceState`：`Discovered/Ready/ImportFailed/Stale/Missing/Orphaned/Invalid/ImportQueued/Importing/Removed`），数据库以 TSV v2 schema 持久化（只接受当前 schema，支持损坏库隔离）；导入走 `ImporterRegistry` 注册表按 `ResourceKind` 增量导入；依赖图（`dependency.rs`）由引用扫描得到边，任一被引用资产失效会把依赖方标记为 `Invalid`（仅重导入该资产无法修复）。
- 原因：M11 暴露「资源注册版本双源漂移」与「失效传播缺失」问题；显式状态机 + 依赖边使编辑器与 assetc 共享同一套状态判定。
- 代价：状态数多，校验与迁移逻辑增加；依赖提取器需覆盖文本（scene/script/prefab/toml）引用语法。
- 非目标：不做增量上传/流式加载、不做远程资源。
- 重新评估条件：状态机与依赖图在编辑器中导致维护复杂度过高，或失效传播产生误报影响生产。

## ADR-0015：发布资源编码（P2PK1）与打包清单

- 状态：Accepted
- 日期：2026-08-27
- 范围：assetc `package` 输出编码与清单。
- 决定：发布包编码文件带 `P2PK1` 魔数 + 标志字节 +（加密时）12 字节 nonce + payload；载荷按需 gzip 压缩（`assets/`）与 ChaCha20Poly1305 加密（`scenes/`、`scripts/`）。解码自动检测：非 `P2PK1` 文件（开发明文）原样返回，同一运行时代码同时支持明文开发与加密发布。打包清单 `manifest.txt` 以 `assetc_manifest=1\t{版本}` 为头、每文件一行 `{相对路径}\t{大小}\t{fnv1a 校验和}`。
- 原因：客户端加密的固有局限（密钥可提取）可接受，目标是提高门槛、防止随意读取；单文件自动检测保持运行时加载路径统一。
- 代价：加密密钥内嵌于可执行文件，属于混淆而非强加密；压缩/加密增加 CPU 开销。
- 非目标：不做服务端密钥管理、不做签名验证（`--check` 用校验和验证完整性）。
- 重新评估条件：发布资产被实际破解导致泄露不可接受，或性能损耗显著。

## ADR-0016：运行时动态 UI 数据模型（panel/grid/image）

- 状态：Accepted
- 日期：2026-08-29
- 范围：引擎动态 UI（运行时由 Lua 驱动的面板/背包网格/图片/tooltip/模态层）。
- 决定：动态 UI 用数据模型描述（`UiImage`/`UiPanel`/`UiGridCell`/`UiGrid`），以组件字符串往返（编辑场景组件与 Lua 运行时共用同一解析器）；布局空间（`UiLayoutSpace`）区分作者空间与视口空间，锚点（anchor）定位，`resolve_ui_rect` 统一解析到像素矩形；Lua 通过 `ui` 表（`panel/image/grid/grid_cell/.../drag_begin/drag_end`）创建与更新，拖拽回调 `on_drag` 由脚本定义。
- 原因：把「编辑场景组件」与「运行时动态 UI」收敛到同一数据模型，避免两套 UI 状态；数据驱动使背包网格/tooltip 等生产需求可无硬编码实现。
- 代价：动态 UI 为即时模式之上的保留数据模型，需与既有 `ui.text_at` 即时 API 共存。
- 非目标：不做复杂布局引擎（Flex/Grid 自动布局）、不做字体富文本。
- 重新评估条件：动态 UI 与即时 UI 共存导致心智负担过大，或布局空间抽象不满足生产需求。

## ADR-0017：农场玩法数据模型下沉为 Lua API

- 状态：Accepted
- 日期：2026-08-29
- 范围：引擎农场玩法数据模型（游戏时钟、物品定义、背包/装备、网格工具）与对应 Lua API。
- 决定：把农场循环需要的数据结构（`GameClock`、`ItemStack`、`Inventory`、网格坐标工具）作为引擎核心数据模型实现，并通过 Lua 全局表暴露为稳定 API（`clock/calendar/day/grid/tilemap/item/inv/container/shop/map/data/save.blob_*` 等）；所有接口运行在主线程共享状态，错误转换为 Lua 错误而非 panic。
- 原因：玩法逻辑全部由 Lua 驱动（章程原则）；把状态模型放引擎侧保证编辑器/运行时/headless 一致性，且可单元测试。
- 代价：引擎需要维护一组玩法语义的数据结构，扩大了 core 表面积。
- 非目标：不在引擎侧实现具体玩法规则（交易资金、任务、剧情）。
- 重新评估条件：玩法数据模型与通用引擎职责冲突，或 Lua 层使用率低导致抽象过度。

## ADR-0018：编辑器 Play/Stop 快照隔离

- 状态：Accepted
- 日期：2026-08-24
- 范围：编辑器 PlaySession（运行态隔离）。
- 决定：Play 在场景文档的副本上实例化运行时，Play 期间运行时修改只作用于副本；Stop 后恢复 Play 前的编辑态，不污染场景文件和 dirty 状态。编辑器顶部 Play/Stop 单按钮切换，Play 期间禁止新建/删除/重命名/Inspector 编辑（[M5-07](22-使用手册.md) 验收）。
- 原因：防止运行时代码污染作者场景，是编辑器安全工作的基础（M11 收口主题之一）。
- 代价：需要维护快照/恢复逻辑与 100 次 Play-Stop 循环不漂移的回归测试。
- 非目标：不做多 VM 并行预览、不做断点单步（后续可加）。
- 重新评估条件：快照恢复在真实工程中出现状态漂移无法修复。

## ADR-0019：编辑器导入/发布后台任务与确定进度

- 状态：Accepted
- 日期：2026-08-29
- 范围：编辑器资源导入与发布打包的后台执行与进度面板。
- 决定：资源导入走 `run_import_batch` 非阻塞执行，pending 列表驱动；发布打包后台启动 `scripts/package.ps1`（不弹终端窗），解析其 `==>` 阶段标记映射为确定进度 `0..=1`；顶部用单按钮切换 Play/Stop（[37d3e61](../CHANGELOG.md)）。
- 原因：大工程导入/发布耗时长，阻塞主线程导致编辑器不可用；确定进度替代未知等待，改善 Windows 体验。
- 代价：后台任务与编辑器状态同步需要消息/轮询桥接；脚本输出解析依赖发布脚本的稳定标记。
- 非目标：不做任务取消恢复、不做多工程并行发布。
- 重新评估条件：进度映射随发布脚本漂移失准，或后台任务与编辑器状态不一致导致竞态。

## ADR-0020：运行时固定阶段统一接入 Scheduler

- 状态：Accepted
- 日期：2026-09-10
- 范围：`core/scheduler.rs`（泛型化）与 `host/runtime_scene.rs`（帧调度管线）。
- 决定：`RuntimeScene::run_script_steps` 内部的手工固定阶段（输入 → Lua update → UI 点击 → 2D/3D 物理 → 粒子 → 时钟 → 场景切换，调用尾部的速度积分与动画推进）改为注册进 `Scheduler<RuntimeScene>` 执行；Scheduler 的系统上下文从硬编码 `&mut World` 泛型化为 `&mut C`（默认仍为 `World`），并新增 `Simulation` 阶段承载粒子/时钟/场景切换。游戏壳（`game_app.rs`）、编辑器 Play 预览（`preview_session.rs`）与 headless 执行共用这一调度入口；新增玩法系统经 `add_step_system`/`add_frame_system` 按阶段注册，不再扩大手工编排函数。
- 原因：正式运行时、编辑器预览和 headless 三条路径必须共享一致的系统顺序、依赖/循环/panic 诊断（含 panic payload）与逐系统性能统计（`last_schedule_report`）；顺序不变是硬约束（每步管线与帧级管线的阶段/注册顺序与旧实现逐项对齐）。
- 代价：Scheduler 回调不再要求 `Send`（运行时单线程，脚本系统捕获非 Send 的 Lua 状态）；每次 `run_script_steps` 重建调度器并做依赖校验（系统数量为个位数，开销可忽略）；系统所有权在调用期间移入调度器、结束后按注册顺序放回。
- 非目标：不引入并行执行、不改 ECS 存储结构、不引入 archetype ECS。
- 重新评估条件：出现需要并行调度的负载，或注册系统数量增长到逐帧重建调度器成为可测量开销。

## ADR-0021：命名动作输入映射与设置持久化

- 状态：Accepted
- 日期：2026-09-13
- 范围：`core/input.rs`（`ActionMap`/`Binding`）、`core/script.rs`（Lua `input.action*`/`input.pad*`）、
  `host/runtime_scene.rs` 与 `host/gamepad.rs`（设备帧 → 动作）、设置文件（`<project>/settings.toml`）。
- 决定：输入分三层——**物理输入**（键盘/鼠标/手柄设备帧）、**命名动作映射**（`ActionMap`，一份实例随
  `ScriptState` 走，宿主经 setter 注入，保证脚本重绑定与宿主查询同源）、**动作消费**（Lua `input.action*`
  与游戏脚本）。`Binding::to_text`/`parse` 是绑定的稳定文本形式，设置文件带版本头
  `rustlua-actions-v1`；方向键序列化为**可读名字** `key:up`/`key:down`/`key:left`/`key:right`
  （与 Lua 侧 `input.is_down("up")` 同名，便于设置文件阅读与重绑定面板展示；旧的内部码位写法
  `key:other:1048577`…`1048580` 仍可解析并在重新保存时归一化）；读取失败/版本不符时回退默认映射并记录诊断（不崩溃、不静默丢弃用户绑定），
  写入采用保序读改写；`ActionMap::merge_missing` 只补缺失动作，用户重绑定不被默认值覆盖。
  旧物理键 API（`input.is_down`/`just_pressed`/`axis`）语义不变并继续可用。
  **后续修订（M22/W1，见 `docs/35` §8 与 `docs/18`「物理键身份」）**：
  上面「方向键用可读名字」「版本头 v1」两条**已被取代**——键的身份改为与 winit 0.30 逐项对齐的
  **物理键**（194 项），文本形式 = 变体名小写（`key:arrowup`、`key:keye`、`key:digit1`），
  版本头升为 `rustlua-actions-v2`（读 v1 写 v2，`key:up` 一类旧写法按 US-QWERTY 换算并归一化）。
  原因：字符身份让 `Shift+1` 与 `1` 变成两个键、`Tab`/`Enter`/`F5` 无法表达，且按键位置随
  玩家键盘布局漂移。
- 原因：手柄、键盘与未来重绑定必须共用一套命名动作，否则每加一种设备就要改全部玩法脚本；
  设置文件与存档分离（`settings.toml` 是工程/玩家偏好，不进存档、不随存档回滚）。
- 代价：脚本层多一层间接（动作名→绑定）；需要一次性把 `game_jhyt` 从物理键直读迁移到动作名，
  并保持 headless 用例喂物理键时的等价行为（默认绑定必须让它等价通过）。
- 备选：把映射只放在宿主（Lua 不可见）——被否，编辑器重绑定面板与脚本调试都需要读绑定；
  把映射塞进存档——被否，存档回滚会连带回滚键位。
- 非目标：不做触屏输入、输入录制/回放、多语言原生按键图标；手柄设备轮询见 M20-06（XInput，
  gilrs 因离线依赖不可解析未落地）。
- 重新评估条件：绑定文本格式需要破坏性变更（届时升版本头 + 迁移），或手柄型号差异导致固定编号
  契约不可用（改为按设备映射表）。
