# 技术决策记录

## 使用说明

所有会影响架构、公共 API、资源格式、依赖或发布平台的决策都写入本文件。旧决策不删除，通过状态标记为 Accepted、Superseded 或 Rejected。

## ADR-0001：采用 Rust 作为引擎核心

- 状态：Accepted
- 日期：2026-08-20
- 原因：需要接近 C++ 的性能、无垃圾回收运行时、较强的内存和并发安全性。
- 代价：游戏行业生态和主机平台支持不如 C++，需要更多自行建设。
- 回滚：保留 C ABI/插件边界，避免未来接入主机或特定 C++ SDK 时重写全部引擎。

## ADR-0002：采用 Lua 作为游戏脚本

- 状态：Accepted
- 日期：2026-08-20
- 原因：运行时轻量、嵌入简单、适合玩法热重载和快速迭代。
- 代价：静态类型和 IDE 能力弱于 C#，需要 API 封装和类型提示。
- 回滚：脚本边界以稳定句柄和命令 API 为中心，未来可增加另一种脚本语言。

## ADR-0003：Windows 优先，2D 优先

- 状态：Accepted
- 日期：2026-08-20
- 原因：降低独立开发者的首发复杂度，先用垂直切片验证引擎价值。
- 代价：早期不覆盖主机、移动和完整跨平台需求。

## ADR-0004：先使用成熟第三方库

- 状态：Accepted
- 日期：2026-08-20
- 范围：wgpu、Rapier、mlua、egui、Serde、tracing 等。
- 原因：独立开发者不应重复实现图形后端、物理、音频和序列化基础设施。
- 约束：通过适配层接入，锁定版本并记录许可证。

## ADR-0005：编辑器采用独立 crate，egui/eframe 起步

- 状态：Accepted
- 日期：2026-08-20
- 范围：M5 编辑器 MVP
- 决定：编辑器作为独立 `editor` crate，第一版采用 `egui` + `eframe`；编辑器通过 `engine_core` 公共 API 访问场景、资源和脚本。
- 原因：独立 crate 可以隔离编辑器依赖和运行时发布包；egui/eframe 适合独立开发者快速完成 Windows 优先的工具界面，并可复用现有 Rust 代码。
- 代价：需要处理 eframe 与现有 wgpu/winit 版本兼容；GUI 自动化能力弱于无窗口测试。
- 约束：先实现无窗口项目检查和状态模型，再接入复杂 GUI；依赖版本锁定在 Cargo.lock；若依赖冲突，回滚为独立 winit + engine_core 状态模型，不修改 M4 场景格式。
- 重新评估条件：M5-01 最小窗口无法构建、启动稳定性不达标，或编辑器与运行时依赖无法共存。

## ADR-0006：M8 采用 glTF 2.0 作为 3D 交换格式

- 状态：Accepted
- 日期：2026-08-22
- 范围：M8 轻量 3D 的 Mesh、材质、纹理、节点和动画导入。
- 决定：首版支持 `.gltf` 和 `.glb`，使用成熟的 glTF 解析库；导入结果先转换为 `engine_core` 自有的 CPU 资源模型，再由渲染层上传 GPU 资源。
- 原因：glTF 2.0 适合运行时分发，`.glb` 可将测试资产和二进制数据封装为单文件，成熟解析库能降低 accessor、buffer、材质和动画边界错误。
- 支持范围：静态 Mesh 的 POSITION/NORMAL/TEXCOORD_0、索引、基础材质纹理、节点层级；后续增加一个 skin 和动画状态。
- 非目标：首版不支持任意 glTF 扩展、 morph target、复杂材质扩展、压缩 Mesh 和自研解析器。
- 兼容：assetc 以导入器版本控制缓存；场景格式通过版本号和迁移保持 `v0.7` 旧 2D 场景可加载；不支持的扩展必须报告文件、节点或 primitive 上下文并返回失败。
- 重新评估条件：目标资产无法由标准 glTF 2.0 表达，或解析库无法在当前许可证和 Windows 发布约束下使用。

## ADR-0007：M8 3D 坐标、单位和深度约定

- 状态：Accepted
- 日期：2026-08-22
- 范围：Math3D、Transform3D、Camera3D、Mesh 和光照。
- 决定：世界坐标使用右手系，+Y 向上、+Z 指向观察者；长度单位为米；矩阵按列向量语义组合，渲染使用 `clip = projection * view * model * position`；透视相机使用弧度 FOV 和正的 near/far 平面。
- 决定：深度纹理使用 `Depth32Float`，清除值为 1.0，比较函数为 `LessEqual`；3D pass 使用深度测试和写入，2D pass 保持现有无深度行为。
- 决定：颜色纹理按 sRGB 采样，法线/金属度/粗糙度和深度数据按线性数据处理；near 必须大于 0，far 必须大于 near。
- 原因：约定简单、适合 wgpu 默认坐标转换和常见 glTF 资产，且可用纯 CPU 数学测试验证，不依赖 GPU 截图才能发现基本错误。
- 代价：glTF 的节点坐标需在导入边界明确转换；阴影和后续反向深度不在首版范围。
- 重新评估条件：实测资产坐标转换普遍需要特殊例外，或 wgpu 后端验证显示深度范围与该约定不兼容。

## ADR-0008：M9 采用 rapier3d 作为 3D 物理后端

- 状态：Accepted
- 日期：2026-08-22
- 范围：M9 3D 可玩垂直切片的刚体、碰撞体、触发器和射线查询。
- 决定：在 `engine_core` 引入 `rapier3d`，与现有 `rapier2d` 在同一 workspace 统一版本锁定；3D 物理复用 2D 物理的 API 形态（`ColliderDesc`、layer/mask、sensor、碰撞事件进 Lua），固定时间步推进，与 Transform3D 双向同步。
- 原因：与现有 2D 物理同一生态，减少适配成本；不自研碰撞求解器（章程原则）。
- 代价：`rapier3d` 与 `rapier2d` 存在 API/特性差异，需要在 `engine_core` 内隔离 2D/3D 物理模块边界。
- 非目标：不做连续碰撞检测、软体、角色控制器内置组件等高级物理能力。
- 重新评估条件：2D/3D 物理共用边界导致维护复杂度过高，或版本冲突无法在 workspace 内解决。

## ADR-0009：M9 拆分 game_runner 渲染边界

- 状态：Accepted
- 日期：2026-08-22
- 范围：M9-01 渲染边界重构。
- 决定：将 `game_runner/src/main.rs` 中渲染相关职责抽出为独立模块，建立明确边界：GPU 资源（buffer/texture/pipeline 创建与生命周期）、RenderPass（2D/3D pass 与 depth 管理）、实例化与剔除数据缓冲、Camera/Depth 生命周期。重构只移动与组织代码，不改变渲染行为。
- 原因：M8 风险登记将「3D 改造堆积在 game_runner 单文件」标记为 P1；重构是继续扩展 3D 能力的前提。
- 代价：重构期间有回归风险，需要每个重构提交独立可编译并跑质量门。
- 非目标：本次重构不引入渲染图（render graph）、多线程渲染或 GPU-driven indirect。
- 重新评估条件：模块边界仍随功能膨胀，或重构导致 2D/3D 渲染行为回归。

## ADR-0010：M9 编辑器 3D Gizmo 首版只做平移

- 状态：Accepted
- 日期：2026-08-22
- 范围：M9-03 编辑器 3D Gizmo 与组件编辑。
- 决定：编辑器支持选中 3D 实体并拖动平移 Gizmo；Inspector 可查看/编辑 Transform3D、MeshRenderer、Camera3D、Light、碰撞体组件；旋转/缩放 Gizmo 后置。
- 原因：平移 Gizmo 足以支撑 3D 关卡搭建的核心需求，复杂度可控；旋转/缩放涉及轴向手柄与投影算法，推迟到有实际需求时再实现。
- 代价：搭建含旋转的场景需要手写旋转值。
- 非目标：不做 3D Gizmo 旋转/缩放、不做地形编辑器。
- 重新评估条件：3D 关卡搭建明显受限于无法可视化旋转/缩放。

## ADR-0011：M9 3D 样板游戏玩法锁定

- 状态：Accepted
- 日期：2026-08-22
- 范围：M9-04 3D 样板游戏垂直切片。
- 决定：3D 样板游戏范围锁定为：玩家角色（碰撞移动）、至少一种敌人（AI 追击）与攻击判定、拾取物、血条 HUD（复用 `ui.text`）、音效（复用现有音频）、胜负条件与重开一局；玩法逻辑全部由 Lua 驱动（参照 2D 样板游戏的模块化结构）。
- 原因：用一款小游戏验证「3D 引擎能力绑定游戏需求」的双轨原则，控制范围防止膨胀。
- 代价：不做复杂关卡设计、Boss、成长系统等，首版仅验证 3D 玩法链路。
- 非目标：不做 3D 音效空间化、不做多关卡/存档（按需）、不做联网。
- 重新评估条件：核心玩法验证通过后，由负责人决定是否扩展为正式 3D 游戏。

## ADR-0012：编辑器引擎内嵌采用单一 wgpu 设备 + offscreen 渲染目标

- 状态：Accepted
- 日期：2026-08-22
- 范围：M10 编辑器强化阶段的引擎内嵌游戏预览与 3D 透视视口。
- 决定：编辑器从 eframe 的 wgpu render_state 取 Device/Queue；改造 `Renderer` 支持「窗口 surface」与「offscreen 纹理目标」两种模式；游戏预览与 3D 场景视口用同一 wgpu 设备渲染到 offscreen 纹理，直接注册为 egui 纹理显示。
- 原因：单一设备避免跨设备 GPU 拷贝（方案 B）与 CPU readback 的每帧同步开销（方案 C）；offscreen 纹理可直接作为 egui 纹理，性能与集成度最好。
- 代价：`Renderer` 需重构为接受外部设备并支持非 surface 渲染目标，改造量较大但一次到位；需要把 game_runner 的运行时抽为可复用 crate。
- 非目标：不做跨设备渲染、不做编辑器内多适配器。
- 重新评估条件：单一设备导致 egui 与游戏渲染相互阻塞无法满足交互帧率，或 offscreen 纹理在目标 GPU 上不可用。

## ADR-0013：编辑器 3D 透视视口相机约定

- 状态：Accepted
- 日期：2026-08-22
- 范围：M10-04 编辑器 3D 透视视口导航。
- 决定：编辑器使用独立于游戏相机的轨道相机：右键拖拽轨道（yaw/pitch）、中键平移、滚轮缩放（与游戏内相机分离，编辑时观察用）。坐标系沿用 ADR-0007（右手 +Y 向上）。透视视口渲染复用内嵌渲染器的 3D pass，将场景渲染到 egui 纹理显示。
- 原因：编辑器相机与游戏相机分离是 Unity/Godot 惯例，编辑视角不影响游戏运行；轨道导航直观易用。
- 代价：编辑器需要维护相机状态与输入映射；透视视口与俯视模式共存需可切换。
- 非目标：不做编辑器相机书签、多视口。
- 重新评估条件：轨道导航在编辑场景中明显不便，或透视视口性能不可接受。
