# 编辑器运行时性能分析面板

本文记录编辑器性能分析面板的**运行时层**：数据从哪来、每个数字怎么算、哪些是估算值、
以及当前做不到什么。编辑器层的帧/面板/命令耗时不在这里重复，见
[编辑器使用指南](25-editor-guide.md) 第 18 节。

## 1. 目标与入口

Play 预览跑起来以后，面板要能直接回答下面几类问题，而不是让人去翻日志：

- 现在多少帧？帧时间花在 CPU 还是 GPU？
- 这一帧提交了多少 draw call / set pass？顶点、三角形、实例各多少？有没有 draw 被丢弃？
- 贴图/网格缓存有多大？加载队列里还有多少没到？命中率如何？
- 进程占了多少内存？GPU 侧已知缓存占了多少？
- 场景里有多少实体、多少运行时资源？

入口：工具栏 `性能` 勾选框、菜单 **窗口 → 性能分析面板**。
面板是独立 `egui::Window`，默认落在工作区右下角，不覆盖 Scene 右上角工具条。

## 2. 数据来源

| 数据 | 来源 | 口径 |
|---|---|---|
| 帧率 / 帧间隔 | `runtime_perf::PreviewPerfMeter` | 只在 `PreviewSession` **到期并提交了一帧**时记账；一秒滚动窗口，未满一秒用最近帧间隔兜底 |
| 运行时更新 / Lua 耗时 | `PreviewPerfMeter` + `RuntimeScene::take_script_micros` | 更新 = 一次预览 tick 的 CPU 总耗时；Lua = 脚本 `update()` 净耗时（不含 ECS/物理/渲染） |
| CPU 渲染 | `Renderer::last_frame_metrics().cpu_frame_us` | 渲染器内部从开始建命令到 `queue.submit` 的耗时 |
| GPU 渲染 | `Renderer::last_frame_metrics().gpu_frame_us` | wgpu timestamp query 异步回读；设备未启用时间戳时为 `None`，面板显示原因而不是 0 |
| 逐通道 GPU 时间 | `Renderer::gpu_pass_report()` | 与整帧**同一次提交**的 `QuerySet`；每对起点/终点包住一条通道，异步回读后解析；见 §7 |
| draw call / set pass / 实例 / 顶点 / 三角形 / 丢弃 draw | `RenderFrameMetrics` | 见 §3 |
| 渲染通道 | `Renderer::last_frame_passes()` | 本帧实际进入的通道，按执行顺序 |
| 贴图/网格缓存、加载队列、顶点缓冲、回读 | `Renderer::resource_stats()` | 见 §4 |
| 进程工作集 | `gui_evidence::working_set_mib()` | Windows `GetProcessMemoryInfo` 的真实 RSS；非 Windows 为不可用 |
| Lua 堆 | `RuntimeScene::lua_memory_bytes()` | mlua `Lua::used_memory` 的真实 VM 堆字节（E06-4） |
| 资源身份条目 / 场景实体 / 运行时实体 | `RuntimeScene` | `AssetStore::len`、场景声明实体数、ECS 世界实体数 |
| 调度系统逐项耗时 | `RuntimeScene::last_schedule_report()` + `registered_system_names()` | 最近一次 `run_script_steps` 的 `steps` / `total_elapsed` / `timings`；见 §5 |
| span 时间线 / top-N | `host::profile_trace::SpanTrace` | 有界环形缓冲（8192），只保留最近一段；捕获档位与开销门见 §6 |
| 采集包 / 差分 | `host::profile_capture::CaptureBundle` + `RuntimePerfTracker` 的采集窗口 | 有版本 JSON（`p3-capture-v1` / `p3-capture-diff-v1`）；见 §8 |

采样点在 `EditorApp::draw_frame` 的**帧末**（`sample_runtime_performance`）：此时 Game 视图的
`PreviewSession::update`（或帧末补步）已经跑完，`last_frame_metrics()` 是这一帧而不是上一帧。
面板本身在帧中绘制，读到的是同一帧稍早的快照，差一帧以内。

## 3. 渲染指标的统计边界

### 3.1 Draw call

- 2D 只统计**实际成功编码**的 draw；绑定组造不出来时计入 `dropped_draws`，不虚增 draw call。
- 3D 的 shadow pass 与 main mesh pass 分别计入 draw call（`record_indexed_draw` 的
  `pass_count = 2`）。
- 矢量文字计入 draw call 与三角形，但不计为 Sprite 实例。

### 3.2 Set Pass

`RenderFrameMetrics::set_pass_calls` 计的是 **shader pipeline 状态设置次数**：

- 阴影 pass、主网格 pass、世界 Sprite 的每个深度分段、2D overlay、矢量文字、后处理各计一次；
- 2D overlay 内部只在**普通管线 ↔ SDF 管线**真的切换时计一次；贴图变化但管线不变不算；
- 清屏是附件操作，不计入。

它是 Unity `SetPass Calls` 的对应量，不是 draw call 的别名：同一管线连续画很多批时，
set pass 应显著少于 draw call。若两者接近，说明批次/材质切换是下一个优化点。

### 3.3 顶点与三角形

- 2D overlay / 世界 Sprite / 矢量文字 / 后处理：按实际提交的顶点数计，三角形 = 顶点数 / 3。
- 3D：`顶点 = 网格顶点数 × 实例数`，`三角形 = index_count / 3 × 实例数`；两者都只按逻辑几何
  统计一次，不因 shadow + main 两条 pass 重复。
- 顶点数是"提交给 GPU 的顶点"，不是"去重后的唯一位置数"。

## 4. 资源加载与缓存

`RendererResourceStats` 每帧汇总（只读，不触发 GPU 查询）：

| 字段 | 含义 |
|---|---|
| `loaded_textures` | 已上传的 2D 贴图 + 3D albedo 贴图条数 |
| `texture_bytes` | 上述贴图 + 字体图集的 RGBA8 面积估算 |
| `font_atlas_textures` | 默认字体图集 + 自定义字体图集条数 |
| `texture_identity_hits/misses` | 2D 贴图按**资源句柄**解析的命中/未命中次数（按 draw 累计） |
| `cached_meshes` / `mesh_bytes` | 3D 网格缓存条数与顶点+索引缓冲字节 |
| `mesh_identity_hits/misses` | 网格按资源句柄解析的命中/未命中 |
| `async_pending/completed/workers/mode` | 异步加载队列的待取走数、已取走数、后台线程数与模式 |
| `vertex_buffer_capacity/growths/peak` | 2D 顶点缓冲容量、扩容次数、单帧峰值 |
| `readback` | 非阻塞回读槽数、busy、提交/完成/丢弃、CPU 缓冲字节 |

注意：

- 编辑器 Play 预览走 `Renderer::new_offscreen`，加载器是 **Sync**（确定性输出），因此
  `async_workers = 0`、`async_pending` 通常为 0；面板显示"同步（编辑器预览 / 确定性输出）"。
  独立 `game` 宿主才是异步模式，同样的分组会显示 worker 数与队列长度。
- **身份命中率不是磁盘缓存命中率**：第一次见到某句柄记未命中，之后同一句柄 O(1) 命中；
  它衡量的是"资源身份这条路有没有被走到"，不是"图片有没有重新解码"。
- 贴图/网格字节是**上传时记录的估算值**，不含驱动对齐、绑定组、管线等不可见开销。

## 5. 调度系统拆分（E06-1）

Play 预览每帧调用 `RuntimeScene::run_script_steps`，`FrameScheduleReport` 已记录：

- `steps`：这次调用实际执行的固定步数（慢帧补步时会 >1）；
- `total_elapsed`：整次调度（含每步 + 帧级系统）的墙钟时间；
- `timings`：每个 system 的累计耗时（跨步累加）与阶段，按首次执行顺序。

面板新增「运行时 · 调度系统」分组，直接读这份报告，不再另算一套：

- 系统行按耗时降序，最多列 12 个；完整清单写进「复制报告」的 `运行时调度系统` 段。
- **缺失系统判红**：把 `registered_system_names()`（每步系统 + 帧级系统）与报告里的
  `timings` 逐名比对，注册了却没计时的系统会以红行列出。`steps=0` 时不做该判定。
- **口径一致性**：系统合计超过 `total_elapsed` 的 5% 判红（计时账本自相矛盾）；
  反向差值（总耗时更大）是调度器自身开销，单列「调度开销」行，不判红。
- 未 Play 或还没产生报告时不出这一组，不保留上一局的过期系统表。

## 6. Chrome trace 捕获（E06-2）

调度系统表回答"这一帧哪个 system 慢"，但回答不了"面板、Lua、提取各自占多少、谁套在谁里面"。
E06-2 在引擎侧加了一条统一 span 时间线（`engine::host::profile_trace::SpanTrace`），编辑器只做
开关、展示与导出。

### 6.1 存储与档位

- **有界环形缓冲**：容量 `DEFAULT_SPAN_CAPACITY = 8192`，满了丢最旧并累计 `dropped`；
  长会话不会无界增长。捕获的是**最近一段**，不是整局历史。
- **三个档位**（`CaptureLevel`）：
  - `Off`：不记录任何 span（默认，启动时就是 Off）；
  - `System`：只记帧根 + 每个调度 system；
  - `Fine`：在 `System` 之上再记 panel / command 等细粒度 scope。
- span 字段：`name`、`category`（`frame` / `script` / `system` / `extract` / `panel` / `command`）、
  相对起点 `start_ns`、时长 `dur_ns`、嵌套深度 `depth`、`args`（键值文本）。
- 帧开始会中止上一帧遗留的未闭合 span；`Off` 或清空时同样清掉，避免导出一棵断掉的调用树。

### 6.2 运行时系统的接入方式

编辑器没有在 `run_script_steps` 内部插桩，而是在帧末（`record_schedule_trace`）把
`FrameScheduleReport.timings` **合成为顺序 span**：以"现在 − total_elapsed"为起点，按报告顺序
依次排开，每个 system 一条，`args` 带 `stage` 与 `synthetic=true`。

- 好处：不侵入调度器热路径，报告与面板 §5 是同一份数据；
- 代价：这是**合成时间线**，不是每个 system 的真实起止时刻。system 之间的空隙归入
  「调度开销」，不会被摊到某个 system 上。
- 暂停时报告不会更新，用 `(steps, total_ns, timings.len())` 签名去重，避免同一帧被反复追加。

### 6.3 面板交互

性能面板工具栏在「复制报告」旁：

- **开始 / 停止 trace**：开始即切到 `Fine` 并清空旧记录；停止回到 `Off`（已记录的内容保留到清空）；
- **导出 trace**：把当前记录写成 Chrome Trace Event JSON，路径固定为
  `<工程根>/target/reports/editor-profile-trace.json`（自动建目录，状态栏给成功/失败）；
- 活跃时显示 `trace N spans（丢 M）` 徽标。

面板新增「trace 捕获」折叠分组：档位、`span n/容量`、丢弃数、覆盖时长，以及按合计耗时排序的
top 8（span / 合计 / p95）。「复制报告」在 span 非空时追加同一份 top-N 文本。
「清空采样」会同时清空 span 记录与去重签名。

### 6.4 导出格式与可视化

JSON 顶层是 `traceEvents` + `metadata`：

- 每个 span 一个完整事件：`ph:"X"`、`ts`/`dur`（微秒）、`pid:1`、`tid:1`、`name`、`cat`、`args`；
- `metadata` 记录 `report_version = "p3-profile-trace-v1"`、容量、档位与丢弃计数；
- 事件按起点、深度、名字排序，保证同一份记录导出的字节稳定；名字与 args 做 JSON 转义。

Chrome `chrome://tracing`、Perfetto 与 `chrome://tracing` 的继任者都吃这个格式。
**人工打开验证尚未做**（见 §11）：自动化侧只证明了 JSON 能被解析器逐字段读出。

### 6.5 开销门（≤2%）

docs/55 的预算是细粒度 scope 的**主线程 p50 开销 ≤2%**。证据由无头例子
`wp0_profile_capture` 给出：同一进程内**交替**跑"基线帧 → 带捕获帧"，5000 个 Sprite 的
`RuntimeScene`、预热 5 帧、120 帧采样，用两组的帧 p50 算 `overhead_pct`：

```text
cargo run -p engine --example wp0_profile_capture -- --frames 120 \
  --output target/reports/p3/profile-capture
```

最近一次读数：

| 项 | 读数 |
|---|---|
| `span_count` / `dropped_spans` | 2760 / 0 |
| `systems` / `passes` | 19 / 0（该例子不读 GPU 通道报告；E06-3 见 §7） |
| Fine 开销 | **0.484%**（`system_overhead_pct=0.262`） |
| 预算 / 结论 | 2.0% / `verdict=pass`、`recommended_level=fine` |
| trace JSON 校验 / 字节 | `true` / 434319 |

报告同时给出 `top_spans`；该次的 top 是 `frame`（p50 12493.6 µs）、`extract2d`（9454.0 µs）、
`script`（3027.3 µs）、`spatial_propagate`（1057.2 µs）、`integrate_velocity`（759.0 µs）。
`passes=0` 与 `passes_available=false` 是如实记录：这个无头例子只采 CPU span，不读 GPU 通道
报告（E06-3 的逐通道数据接在渲染器与面板，见 §7）。

## 7. 逐通道 GPU 时间（E06-3）

整帧 GPU 时间只能回答"这一帧 GPU 花了多久"；E06-3 把同一个 `QuerySet` 扩展成
**帧起点（索引 0）+ 每通道起点/终点 + 帧终点**，一次提交里同时拿到整帧与各通道：

- 通道必须**先 `drop` 渲染通道对象再写结束时间戳**（pass 还活着时写是校验错误）；
- 通道中途没执行（例如粒子通道没有可画的派发）时**放弃这一对**：显式记录
  `(RenderPass, begin, end)`，放弃留下的索引空洞不参与解析，后面的通道不会错位；
- 2D overlay 与 ScreenUI 共用一次 `begin_render_pass`（同管线、同附件），没有 inside-pass
  时间戳就拆不开；整段记在 `legacy_2d_overlay` 上，`screen_ui` 不单列，通道和不会重复计这一段；
- 设备没有 `TIMESTAMP_QUERY | TIMESTAMP_QUERY_INSIDE_ENCODERS` 时报告是
  `supported=false, reason="unsupported"`，`frame_us=None`、通道表为空——**不拿 0 µs 冒充**；
- 一致性门：`|pass_sum - frame| / frame ≤ 5%`；面板把越界标红。

面板新增「运行时 · GPU 通道耗时（E06-3）」：整帧/通道和、偏差（预算 ±5%）、逐通道一行；
不可用时只有一行原因。复制报告里是 `gpu_passes:` 汇总行 + `gpu_pass <name>=<us>us` 明细。

真实回读读数（`RUSTLUA_REQUIRE_GPU=1 cargo test -p engine --lib gpu_pass_timings -- --nocapture`，
WARP、64×64、一个清屏 + 一个 UI 四边形）：

| 项 | 读数 |
|---|---|
| 整帧 / 通道和 | 1144 µs / 1143 µs |
| 偏差 / 结论 | **-0.09%** / `consistent` |
| `clear` | 59 µs |
| `legacy_2d_overlay` | 1084 µs |

不支持设备的用例在同文件：`supported=false`、`reason="unsupported"`、`frame_us=None`、
`passes=[]`，且 `wait_for_gpu_timestamp` 返回 `None`。这些读数是**真实 GPU 提交**的回读，
不是估算，也不是 CPU 时间代理。

## 8. 采集、重放与对比（E06-4）

### 8.1 采集包

`host::profile_capture::CaptureBundle` 是**有版本的 JSON**（`p3-capture-v1`），一份包包含：

| 字段 | 内容 |
|---|---|
| `engine_version` / `engine_commit` / `captured_at_unix_ms` | 引擎版本、采集时的提交号（取不到时 `"unknown"`，不编造）、时间戳 |
| `scenario` | 场景名/路径/内容指纹、视口、固定 dt、随机种子、预热帧数、帧数、逐帧 `input_log` |
| `state_hash` | 采集结束时的最终状态指纹（无头例子对 2D 顶点/UV/颜色、世界 Sprite、3D drawable 矩阵做 FNV-1a） |
| `frames` | 帧时间的 p50 / p95 / max |
| `systems` / `gpu_passes` | 每系统、每 GPU 通道的 p50 / p95 / max / total（µs） |
| `memory` | 进程 RSS、Lua 堆、GPU 贴图/网格、2D 顶点缓冲、回读缓冲、资源/场景/运行时实体数；取不到的项是 `null` |
| `gpu_available` / `gpu_note` | 设备不支持时间戳时为空 + 人读原因，不拿 0 冒充 |

编辑器采集走同一模型：Performance 面板的「开始采集」从当前 Play 预览收逐帧帧时间、
`FrameScheduleReport` 的逐系统耗时与 `gpu_pass_report()` 的逐通道耗时（600 帧上限），
「结束并导出」写 `<工程>/target/reports/editor-capture.json`；若内存里已有上一份采集，
同时写 `editor-capture-diff.json`。编辑器采集**不记录输入日志**，只用于同机前后对比，
不用于跨进程重放——真正的重放证据由下面的无头例子给出。

### 8.2 重放门

`engine/crates/engine/examples/wp0_capture_replay.rs` 用同一场景（5000 Sprite、1280×720、
60 Hz）跑两遍：

1. A 用定种子 xorshift 生成逐帧输入，跑 120 帧（预热 5 帧），落 `capture-a.json`；
2. B **读 A 的输入日志**（不重跑生成器）逐帧 `.replay()`，落 `capture-b.json`；
3. `capture-a.diff(&capture-b, 10%)` 写 `diff.json`；`verdict != stable` 时进程退出码为 1。

判定口径：场景描述（场景指纹/视口/dt/种子/帧数/预热/输入日志）一致、最终状态指纹逐位相同、
帧 p50 漂移 ≤ 阈值、所有**参与判定**的 system/GPU 通道 p50 不越界。p50 < 10 µs 的系统只记录、
不参与判定（本机计时分辨率约 100 ns，0.1–2 µs 的系统一次运行内就能翻倍）；p95 一并记录，
但判定只看 p50。这拒绝的是"系统本身回归"，不是计时噪声。

2026-10-23 的真实读数（`RUSTLUA_GIT_COMMIT=$(git rev-parse HEAD) cargo run --release -p engine
--example wp0_capture_replay -- --frames 120 --output target/reports/p3/capture-replay`）：

```
state_equal=true state=81b60d6a97ab033e input_entries=125 input_equal=true
baseline_p50_ms=1.507 replayed_p50_ms=1.434 frame_delta_pct=-4.812
systems=19 slowest=none threshold_pct=10.0 stable=true verdict=stable
```

同一门在同机重复运行时，帧 p50 差值曾出现 `+1.062%` 与 `-4.812%` 两种读数，都在 10% 容差内；
这正是不要求 bit-identical、只对 p50 设容差的原因。状态指纹两次都逐位相同。

### 8.3 差分语义

`CaptureDiff` 先比场景：`scene_hash` / `viewport` / `fixed_dt` / `seed` / `frames` /
`warmup_frames` / `input_log` 任一项不同，`scenario_match=false`，读数对比没有意义。
场景一致后逐项给 `stable / faster / slower / added / removed / no_baseline`，
`slowest` 是 p50 变慢最多的前 5 个系统，`added/removed` 列出增删的系统；
`threshold_pct` 可配置（默认 10），只作用于 p50。编辑器面板顶部显示上次导出的对比结论，
完整差分在 `editor-capture-diff.json`。

## 9. 内存

- **进程工作集**：Windows 真实 RSS（MiB），回答"编辑器 + 预览总共吃了多少"。
- **Lua 堆**：mlua `used_memory` 的真实 VM 堆字节（面板显示为 KiB/MiB）。它是 Lua 分配器
  统计的堆，不含 `InputSnapshot`、Rust 侧资源表等宿主内存。
- **GPU 贴图 / GPU 网格 / 2D 顶点缓冲 / 回读 CPU 缓冲**：已知缓存的分项，用来回答"哪一类在涨"。
- **已知 GPU 合计** = 贴图 + 网格 + 2D 顶点缓冲；不是完整显存占用，面板明确标注"估算"。
- 进程工作集按 `MEMORY_SAMPLE_INTERVAL = 250 ms` 节流，不是每个渲染帧都问系统。

## 10. 趋势窗口与交互

- 趋势窗口固定 240 帧（`RUNTIME_SAMPLE_CAPACITY`，约 4 秒 @60 FPS），旧样本自动淘汰；
  长会话不会持续吃内存。
- 图按 2 列排列：帧率、帧间隔、CPU 渲染、GPU 渲染、draw call、set pass、三角形、顶点、进程工作集。
  GPU 不可用时该格自动跳过。帧间隔图对 >20 ms 的样本画竖线并标「尖峰 N」（E06-4）。
- 逐通道 GPU 分组里的每一行带占比条（该通道 µs / 整帧 µs，E06-4）。
- **冻结采样**：保留最后一次快照与趋势，便于逐项核对；预览继续运行。
- **清空采样**：清空编辑器帧/面板/命令采样与运行时趋势，保留计数器、gauge 与当前快照。
- **复制报告**：编辑器 profiler 文本 + 运行时 `to_text()`（`frame:` / `render:` / `resources:` /
  `memory:` / `scene:` 五行）+ 调度系统完整清单（不截断），可直接归档为证据。
- Play 停止时快照与趋势清空，面板回到"未运行（点击 Play 开始实时采样）"，不显示上一局的过期数字。

## 12. 已知边界

- **编辑器只采 Play 预览**。非 Play 时编辑器的 3D Scene 视口也有离屏渲染器，但它的帧率/首帧
  语义与游戏运行时不同，未混进同一组读数；需要时可在后续版本单列"编辑器视口"目标。
- **GPU 时间依赖设备能力**。离屏预览复用 eframe 的 wgpu 设备；设备没有启用
  `TIMESTAMP_QUERY / TIMESTAMP_QUERY_INSIDE_ENCODERS` 时，整帧与逐通道都显示"不可用"，
  不会用 CPU 时间冒充。GPU timestamp 本身是异步回读，显示的可能是几帧前的值。
- **逐通道的拆分边界**：2D overlay 与 ScreenUI 共用一次 render pass，报告里只在
  `legacy_2d_overlay` 一项；`screen_ui` 要单列得等 inside-pass 时间戳能力。`pass_sum` 因此
  等于"被计时的通道之和"，不是"所有 GPU 工作之和"。
- **逐通道回读证据来自 WARP（软件光栅）**：真实独显/集显的绝对微秒数未在本机采集；
  一致性门（±5%）与 `supported` 语义与设备无关。
- **FPS 是预览提交帧率**，不是显示器刷新率；读回（非原生纹理）路径下，提交与上传可能相差一帧。
- **没有逐 draw 的帧调试器**：本面板给的是聚合账本；"哪一个 draw 慢"仍需 RenderDoc / 帧捕获。
- **CPU 细分的覆盖范围**：编辑器侧已拆到 panel/command，运行时已拆到逐 system；Lua `update()`、
  UI layout、render encode 在**编辑器内**仍是整段读数（无头例子记录了 script/extract，但编辑器
  的 trace 不记这两段）。
- **trace 是 top-N + 合成时间线，不是完整 flame**：面板没有 egui 自绘 flame chart；运行时
  system 的起止是顺序合成的（§6.2），不是真实交错时刻。环形缓冲只保留最近 8192 个 span，
  长捕获会丢最旧并计数。
- **Chrome/Perfetto 人工打开未验证**：目前只证明导出 JSON 能被解析器逐字段读出（§6.5），
  还没有在浏览器里实际打开目视。
- **编辑器采集不能跨进程重放**：编辑器没有把 Play 预览的逐帧输入边沿持久化，
  `editor-capture.json` 的 `input_log` 为空，`state_hash` 与场景内容指纹同源。
  它只回答"同一场景前后两次采集是否稳定"；跨进程重放与终态逐位一致由无头
  `wp0_capture_replay` 证明（§8.2）。
- **重放只判 p50，且跳过 <10 µs 的系统**：计时噪声不是回归；p95 记录但不参与 `stable`。
  阈值默认 10%，可用例子的 `--threshold` 或直接调用 `diff` 改。
- **输入日志有已知缺口**：鼠标/键盘/手柄按钮与模拟轴已记录，但手柄数字轴边沿
  （`axis_digital` 派生的 pressed/released axes）不在日志里；用到该路径的场景重放
  可能不同。无头例子不接手柄，门不覆盖这一项。
- **内存分项不含 CPU 侧资源解码缓冲与字体轮廓缓存**：Lua 堆已单列（§9），但解码中的
  临时缓冲没有插桩——不做全局分配器插桩是 release 开销约束下的取舍。
