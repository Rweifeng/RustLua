## 1. 结论先行

UI 子系统的评级从 **★★★☆☆**（锚点 + 九宫格 + 焦点导航，缺自动布局与完整裁剪）改为
**★★★★★**，判据不是"又加了几个控件"，而是五条主路径同时闭环：

1. **交互在生产路径上生效**：交互树从默认关改为默认开，hover/pressed/focus、捕获/冒泡、
   键盘与手柄空间导航、拖拽不再是没有消费者的内核（M80-01）。
2. **裁剪与组透明成对补齐**：`Mask` 按矩形裁剪子孙（对齐 Unity `RectMask2D`），
   `CanvasGroup` 提供乘法 alpha、`interactable`、`blocks_raycasts` 三个与 Unity 同名同义的字段（M80-02）。
3. **文本排版按 Unity `Text` 的语义落地**：对齐/垂直对齐、换行/截断/省略号、垂直溢出、
   富文本标签（M80-03）。
4. **可交互控件与作者面同时到位**：Toggle / Slider / Progress / Scrollbar 有运行时组件、`ui.*`
   取值面、spec 节点、v1 导出与编辑器新建入口（新建 Scrollbar 时自动补 `handle` 子节点，
   不让用户建出校验不过的形状）。编辑器补上多选、对齐/分布、12 锚点预设、数值布局行、
   6 px 吸附参考线与「导出为 UI 预设」（把选中子树连同它引用的样式/令牌/资产/绑定落成独立
   `prefab` 文档）（M80-04、M80-05、M80-07）。
5. **契约与交互语义收口**（M80-07）：`rich_text`、`scrollbar`、`list{virtualized}` 进 spec，
   `value_changed` / `drag` 进事件，状态过渡（`transition=时长:曲线`）复用已有轨道运行时；
   click 改为**抬起**触发（按下与抬起同一命中、未越过拖拽阈值才派发一次）。

边界：**三宿主证据已齐，但没有一个是在浏览器或真机上量的**。PC 是真实 `RuntimeScene`；
Web/微信是同一份 wasm 产物在 Node 里跑的无头 harness——不加载 canvas/WebGL，也不证明
WXWebAssembly 真机行为（[docs/32](32-webgl-浏览器平台验收.md) R1）。harness 不带工程资源，
文本回落内建位图图集另算一条 draw path，所以两份产物的原始顶点数高于 PC；`layout_rects`
与 `draw_order` 两项检查仍逐位相同。字形顶点在三个宿主都是 0（没有字体图集），
文字层次序仍未覆盖；"交互序列"门也还没有生产端。

## 3. 逐包变化

### 3.1 M80-01：交互路由默认开、空间导航、拖拽

**问题**：M76 落地的 `ui_interaction` 是一个"纯逻辑树 + 宿主接线"，但 `ui_interaction_enabled`
默认 false，生产路径仍走旧的 `process_ui_clicks`——hover/pressed、捕获/冒泡、键盘导航、
滚轮/拖拽全都只有测试在跑。

**当前语义**：

- **默认开**（`engine/crates/engine/src/host/runtime_scene/scene.rs:746`）。关闭后回到旧路径
  （所有重叠目标都收到 click），作为显式回滚档，行为逐字节不变。
- **捕获/冒泡**：命中从绘制序列末尾（最上层）向前取第一个可交互节点；事件先向下捕获、
  再向上冒泡，`stop_propagation` 在树内生效。hover / pressed / focus / disabled 四种状态
  由同一棵树维护。
- **空间导航**：方向键在可聚焦节点间按几何位置移动焦点，Enter 触发 `submit`；
  `set_ui_keyboard_nav(false)` 可单独关掉键盘/手柄抢焦点。
- **拖拽**：按住后位移超过 **8 px** 才进入拖拽，之后每次移动向按下目标派发 `drag`；
  未越过阈值时仍是 click 语义。ScrollView 的滚轮与拖拽也接在同一套输入上。
- **click 在抬起时派发**（M80-07，对齐 Unity `IPointerClickHandler`）：按下与抬起命中
  同一节点、且期间未进入拖拽，才派发一次；按下只负责按下态与捕获，所以"按下拖走再松手"
  不再被当成点击。旧行为（按下即派发）不再保留开关——它会让 UI 与场景拖拽互相触发。

**证据**：`cargo test -q -p engine --lib -- ui_` → **50 passed**（2026-10-28 连跑三次同数）。

### 3.2 M80-02：`Mask` 与 `CanvasGroup`

- **`Mask`**：组件串 `padding=left,top,right,bottom`（缺省 0，负值向外扩张，非有限值拒绝）。
  绘制与命中共用同一份裁剪矩形；与 `ScrollView` 的区别只有"内容是否可滚动"。
- **`CanvasGroup`**：`alpha`（0..1，沿父链乘法继承）、`interactable`（false 时整棵子树
  不参与命中）、`blocks_raycasts`（false 时命中穿过整棵子树）。三个字段与 Unity 同名同义。
- **贯通三层**：spec 节点（`UiNodeKind::Mask` / `CanvasGroup`）、预览器（裁剪矩形与 alpha
  合成）、运行时组件与 v1 导出。

**证据**：`ui_mask` 过滤 **3 passed**；预览侧的遮罩内缩与组透明度由
`mask_insets_the_clip_rect_for_the_subtree` 与 `canvas_group_alpha_hides_its_subtree` 钉住，
运行时侧由 `engine --lib -- ui_mask` 的 3 条测试钉住。

### 3.3 M80-03：文本排版

`Text` 组件新增并默认启用（对齐 Unity `Text` 默认值）：

| 字段 | 取值 | 说明 |
|---|---|---|
| `align` | `left` / `center` / `right` | 布局矩形内的水平对齐 |
| `valign` | `top` / `middle` / `bottom` | 布局矩形内的垂直对齐 |
| `overflow` | `overflow` / `wrap` / `truncate` / `ellipsis` | 默认 `wrap`；`ellipsis` 截断后加省略号 |
| `voverflow` | `overflow` / `truncate` | 垂直超出行高是否丢弃 |
| `rich_text` | `true` / `false` | 默认开；支持 `<b>` / `<color=#rrggbb>` / `<br/>` |

点尺寸（宽高都为 0）实体没有可换行的盒，行为与旧版一致。宿主侧排版在
`engine/crates/engine/src/host/runtime_scene/text.rs`，字形测量与绘制共用同一份样式解析。

**诚实边界**：`UiNodeKind::Text` 在 M80-07 补了 `rich_text` 字段，`Capabilities::core().rich_text`
已为真。需要注意两个默认值不同：**组件串**不写 `rich_text` 时运行时默认**开**（对齐 Unity
`Text`），而 **spec 字段**缺省是 `false`（与编辑器新建文本控件的默认一致），导出会显式写进
组件串。因此作者要在文档里用 `<b>`/`<color>` 时必须写 `"rich_text": true`，否则标签按字面显示。

**证据**：`ui_text_layout` 过滤 **5 passed**。

### 3.4 M80-04：运行时控件与 Lua 取值面

| 控件 | 组件串 | 语义要点 |
|---|---|---|
| `Toggle` | `on=true;group=Sound;checkmark=Checkmark` | 默认 `on=true`；`group` 非空是单选组，同组至多一个开，切换时关掉兄弟项；`checkmark` 是子实体名，开时铺满、关时收成零尺寸 |
| `Slider` | `min=0;max=1;value=0.5;direction=left_to_right;fill=Fill;handle=Handle` | `fill`/`handle` 子实体按当前值改写矩形；`whole_numbers` 整数吸附；四个方向共用同一份"指针位置 ↔ 值 ↔ 填充方向"换算 |
| `Progress` | `min=0;max=1;value=0;direction=left_to_right;fill=Fill` | 只读，不响应输入；与 `Slider` 分成两个组件，因为"能不能拖"是作者一眼要看到的属性 |
| `Scrollbar` | `value=0;size=0.2;direction=left_to_right;handle=Handle` | 滑块长度由 `size` 决定（Unity `Scrollbar.size`），不是保留子实体自身尺寸 |

Lua 侧新增四个同形函数：`ui.toggle(id [, value])`、`ui.slider(id [, value])`、
`ui.progress(id [, value])`、`ui.scrollbar(id [, value])`。不传值是读，传了是写，
返回值是**写完之后**的当前值；实体没有对应组件时读返回 `nil`、写报错。鼠标/键盘改值与脚本
写值走同一套 `set_*`（夹取/整数吸附），Toggle 的单选组走 `set_toggle_on`——不会出现
"鼠标点是单选、脚本写值是复选"的第二套语义。

v1 导出同步扩到 `toggle` / `slider` / `progress` / `scrollbar` / `list`，并由导出端重新解析
组件串做校验；`list{virtualized}` 目前只导出标记，场景侧窗口化尚未落地（`Capabilities::core().virtual_list`
仍为 `false`，见 §4）。

**证据**：`cargo test -q -p engine --lib -- ui_` → **50 passed**；API 面快照 **42 张表 / 313 个函数**
（M79-04 交付时为 309，M80-04 +4）；`cargo test -q -p rustlua-ui-scene-export` → **21 passed**，
其中 `interactive_controls_export_runtime_components` 断言 `Toggle on=true`、
`Slider min=0;max=10;value=3`、`Progress min=0;max=1;value=0.5`，`scrollbar_exports_runtime_component`
钉住 `Scrollbar value=0.25;size=0.4;direction=top_to_bottom;handle=knob`，
`unsupported_kind_is_an_error` 钉住"`virtualized=true` 的列表宁可报错也不降级成滚动容器"。

### 3.6 M80-07：状态过渡、抬起点击与 spec 字段

**状态过渡**（用户点 3）：样式定义里可写 `transition: {duration, easing}`，`easing` 取
`linear` / `smooth_step` / `step`。导出落成运行时已有的 `ButtonStates`——
`tint.<state>` + `transition=秒:曲线`——宿主再用 `rustlua_ui::ui_states` 的 `UiStateTransitions`
按帧推进底色。**没有新造动画内核**：过渡状态机、夹取、实体消失后的清理都复用该模块，
运行时新增的只是"每帧 `advance` 一次、取当前显示色"这条驱动。

**抬起点击**（用户点 4）：见 §3.1。`pointer_down` 只置按下态与捕获，click 在 `pointer_up`
时由交互树派发；拖拽阈值 8 px 之内才算点击。

**spec 字段**（用户点 2）：`text.rich_text`、`scrollbar` 节点（`value/size/direction/handle`）、
`value_changed`/`drag` 事件、`list{virtualized}` 均已进 `UiSpec` 与能力矩阵。边界：虚拟列表
运行时窗口化没落地，导出端对 `virtualized=true` **报错**而不是退化成普通滚动容器；
`core().virtual_list` 保持 `false`。

**证据**：`style_states_export_button_state_tints`（导出 `tint.hover`/`tint.pressed` 与
`transition=0.15:smooth_step`）、`hover_tint_ramps_over_the_authored_duration`（运行时按 0.15 s
推进而不是瞬间跳）、`rustlua-ui/src/ui_states.rs` 的单测共同钉住；`rustlua-ui-spec` 的
`core_is_honest_about_current_runtime` 钉住能力矩阵与运行时同义。

## 5. 三宿主宿主证据

**一份读数实现**：`engine/crates/rustlua-ui-host-evidence` 同时被 PC 的
`editor/examples/m76_ui_matrix.rs` 与 wasm harness 调用。parse → `export_ui_scene` →
`RuntimeScene::from_scene_edit` → `ui_rects_by_name` / `vertices` → 两项检查 → 产物与红项。
三宿主各写一份判定就会变成"同一份文档由三套标准说绿"，那正是证据要防的事。

矩阵本身是 `examples/game_api/ui/matrix.ui.json`（45 节点、零资产的形状矩阵：九锚点、
四边内缩、percent、四种流向、按钮三事件、rich_text、toggle/slider/progress/scrollbar、
mask、canvas_group、list，以及一份带 `states` + `transition` 的按钮）。PC 读数：

```text
cargo run -q -p editor --example m76_ui_matrix -- --print-only
m76_ui_matrix document=ui/matrix.ui.json revision=2927121506108137 entities=45
layout_compared=33 layout_unreconciled=12 layout_max_delta=0.0000
draw_rank_max_error=0.0006
m76_ui_matrix_ok checks=2
```

PC 产物：`blocks=44`、`vertices=264`、`sdf_vertices=0`、`segments=5`、
`monotonic_preorder=true`。

Web / 微信：

```text
powershell -NoProfile -File scripts/verify/ui-host-evidence.ps1 -Target both
```

它构建 `rustlua-ui-host-harness`（cdylib + wasm-bindgen），分别用 `--target web` 与
`--target no-modules` 胶水在 Node 里执行同一份 wasm，然后经
`scripts/verify/ui-host-evidence.mjs` 落产物、回写 `ui/hosts.json`。两份读数与 PC 的
`layout_rects` / `draw_order` 子树**逐位相同**（33 键、最大残差 0；44 块、单调），
原始计数不同：`vertices=612`、`segments=6`、`paths` 多一条 `__builtin_text_atlas__`——
harness 不带工程资源，文本回落内建位图图集，每段字多一批四边形。

口径与限制：

- **33 个键**逐键对拍（含 rich_text 文本、四个值控件与遮罩/组），最大残差 **0.0000 px**
  （容差 0.51 px）；
- **12 个键**不参与对账：流向容器的子项及其子树（预览与运行时的列宽/流内 percent 口径
  未对齐）、`Scrollbar` 的 `handle` 子项（宿主按 `value` 改写矩形）。对这些键只断言
  运行时**解出正尺寸**（防 0×0 塌陷），宿主矩形照记进 `unreconciled_rows`；
- `draw_order` 覆盖 **44 个图块**；三个宿主都没有字体图集，字形顶点为 0，所以
  **文字层次序未覆盖**；
- **Web/微信不是真机**：harness 不加载 canvas/WebGL，也不证明 WXWebAssembly 真机行为
  （[docs/32](32-webgl-浏览器平台验收.md) R1）；两项检查不含文本，文本差异只以原始计数摊开；
- `ui_asset_gate` 读数（2026-10-28）：`3 份 .ui.json · error 0 · warning 0 · 未测宿主 6`
  ——矩阵的 3 个宿主槽全测，剩余 6 个槽是 `blacksmith` / `mcp_smoke` 两份文档 × 3 宿主，
  没有伪造条目。

**这不是"三宿主逐字节一致"**：一致的只有两项检查的读数；原始顶点数因字体回落而不同，
真机行为与文字层次序仍未覆盖。

## 6. 性能基线

沿用已有的确定性滚动用例（1000 行 / 100 px 视口 / 20 px 行高，60 帧，debug 构建）：

```text
cargo test -q -p engine --lib -- thousand_row_scroll_frames_report_assembly_cost --nocapture
1000 项滚动列表：60 帧，峰值装配 7 图/7 文、30 顶点，平均 20.035656ms/帧（含布局解算）
```

读数口径：

- **峰值装配 7 图 / 7 文**：视口裁剪在装配趟就生效，屏幕外行不进候选集；7 = 满窗 5 行 +
  两侧压边各 1 行，压边行进装配但真实交集为空，写不出顶点；
- **30 顶点**：30 = 5 个可见图块 × 6 顶点；文字层在无头宿主里没有字形顶点。测试同时断言
  `images ≤ 40`、`texts ≤ 40`、`vertices ≤ 240`；
- **20.04 ms/帧是 debug 构建、单机单次读数，不设阈值**：它只用于同机前后对比，不能当
  发布性能承诺。release 读数与帧时间分布（p50/p95/p99）不在本批范围内。

## 7. 已知缺口与下一步

按"会不会让五颗星名不副实"排序：

1. **"交互序列"门没有生产端**：hover/press/click/drag/value_changed 的事件与状态序列
   目前只有单元测试，还没有跨宿主录制的 golden。
2. **流向层 12 个键未对账**：预览器的网格列宽、流内 `percent` 与 `Scrollbar.handle`
   改写口径与运行时不同；补齐后 `layout_compared` 才能从 33 提到 45。
3. **虚拟列表只有字段没有运行时**：`list{virtualized=true}` 在导出端显式报错
   （`core().virtual_list=false`）。滚动窗口化内核已经存在（`thousand_row_scroll_frames…`），
   缺的是把 spec 的 `virtualized` 接到它上面。
4. **Web/微信证据是无头 harness**，不含 canvas/WebGL 与 WXWebAssembly 真机行为；
   节点层与块序之外的真实绘制仍要靠平台验收（docs/52）。
5. **文字层绘制次序**：三个宿主都没有字体图集，`draw_order` 只证明图块层。
6. **编辑器可新建但 v1 导出会拒绝的节点**：`input` / `grid` / `tabs` / `modal` /
   `tooltip` / `spacer` / `safe_area`。这是 v1 桥"表达不了就报错"的既定策略，不是静默降级；
   在运行时闭环前，它们属于"先能排版、后能运行"的中间态。
