  [scripts/release/tools.json](../scripts/release/tools.json)

本文回答四个问题：**这棵树的依赖有没有已知问题？发布包里到底装了什么？发布是不是只有某台机器会做？

## 1. 威胁模型与边界

在范围内：

- 依赖漏洞、yanked 版本、许可证越界、依赖来源越界（非 crates.io / 非本仓 path）；
- 构建工具链漂移（`stable` 变成"今天能过、明天不能过"）；
- 发布产物来源不可追溯（无 SBOM、无 commit、无校验和）；
- 发布包被替换或损坏（Authenticode + SHA-256）；
- vendored fork 与上游的补丁漂移（补丁还在不在、离上游多远）。

不在范围内：

- **不修漏洞本身**。发现漏洞只登记、分级、给处置建议；升级 wgpu/egui 等大依赖不在本任务。
- **不做 WebGL / 微信小游戏自动发布**。两条链路依赖 zig、wasm-bindgen、正式 appid 与平台凭据，
  继续按 [docs/32](32-webgl-浏览器平台验收.md) / [docs/52](52-微信小游戏分包发布.md) 手工发布。
- **不做公证 / EV 证书采购 / HSM**。只接 Authenticode；证书由仓库 Secrets 提供。
- **不把"没跑"写成"通过"**。工具缺失、网络失败、无证书分别退 3（BLOCKED），
  只有真正跑完且无发现才退 0。

## 2. 工具与版本锁定

单一事实源是 [`scripts/release/tools.json`](../scripts/release/tools.json)：

| 工具 | 版本 | 用途 |
|---|---|---|
| Rust | `1.97.1` | 编译与 CI，精确版本，不用 `stable` |
| Node | `20` | SBOM / fork 报告的零依赖脚本 |
| cargo-audit | `0.22.2` | RustSec 漏洞与 yanked 检查 |
| cargo-deny | `0.20.2` | advisories / licenses / bans / sources |
| cargo-cyclonedx | `0.5.9` | 可选的交叉 SBOM（见 §5.3） |

`engine/rust-toolchain.toml` 的 `channel = "1.97.1"`，`profile = "minimal"`，保留 rustfmt/clippy。
所有 workflow 的 `dtolnay/rust-toolchain@...` 必须是同一个精确版本，`actions/setup-node` 必须是
`node-version: "20"`；由 [`check-toolchain-lock.ps1`](../scripts/verify/check-toolchain-lock.ps1) 判红：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify/check-toolchain-lock.ps1
# toolchain_lock_ok rust=1.97.1 node=20 tools=3
```

它同时断言 `tools.json` 里的三个安全工具是精确 semver，防止"CI 用 latest、本地用另一版"。
`verify.ps1` 的默认路径已包含这道门（`-MvpOnly` 也跑），所以工具链漂移不需要记得单独跑。

安装固定版本工具：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/release/install-security-tools.ps1
# security_tools_ok audit=0.22.2 deny=0.20.2 cyclonedx=0.5.9
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/release/install-security-tools.ps1 -Check
```

CI 用 `taiki-e/install-action` 下载预编译二进制，但 `tool:` 里的版本必须与 `tools.json` 一致，
并由 `check-toolchain-lock` 的"至少有一条工具版本"断言兜底。第三方 action 的风险是
**供应链的供应链**；它只负责装工具，不参与签名，也不接触证书。

## 3. 一个入口、三种退出码

本地与 CI 的入口都是 [`check-security.ps1`](../scripts/verify/check-security.ps1)：

```powershell
# 有网络：cargo-audit / cargo-deny 自己拉 advisory DB
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify/check-security.ps1 -RequireTools

# 离线：显式给本地 RustSec 快照（cargo-audit 要仓库本身，cargo-deny 要父目录）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify/check-security.ps1 `
  -AdvisoryDb artifacts\tmp\advisory-dbs -SbomPath artifacts\reports\rustlua.cdx.json
```

退出码契约：

| 退出码 | 含义 | 典型输出 |
|---:|---|---|
| 0 | 所有已跑的检查通过 | `security_ok audit=ok deny=ok fork=ok` |
| 1 | 有检查判红 | `security_failed`、`[FAIL] cargo-audit ...` |
| 3 | 环境受限（缺工具、DB 不可达、网络失败） | `security_blocked`、`[BLOCKED] cargo-audit -- advisory database unavailable (network)` |

`-RequireTools` 把"工具缺失"从 3 改成 1（CI 用），因为 CI 的 job 已经负责装工具；**本地默认不要求**，
让没有工具的机器得到显式的 BLOCKED，而不是假装通过。`-SkipAudit` / `-SkipDeny` / `-SkipForkSync`
只用于排障，跳过的项会在汇总里少一项，不会写成 PASS。

## 4. 依赖漏洞、许可证与来源

### 4.1 cargo-audit

配置在 [`engine/.cargo/audit.toml`](../engine/.cargo/audit.toml)：`[advisories] ignore = []`，
`[yanked] enabled = true`。**初始没有 ignore**：先看真实读数，再决定要不要登记例外。

```powershell
cd engine
cargo audit --file Cargo.lock --json
```

2026-10-20 初次实测：`vulns=0 warnings=5`（`paste`、`ttf-parser`、`zbus_names`、`zvariant`、
`zvariant_derive`）。同日收口后 **`warnings=1`**，只剩 `ttf-parser`（RUSTSEC-2026-0192）。
处置原则：能让上游换掉就换；不能换的写进 `deny.toml` 的 ignore，**必须带 `id` / `reason` /
复核日期**；不允许用 `ignore = ["RUSTSEC-..."]` 把整个 audit 静音。

具体处置：

- `paste`（RUSTSEC-2024-0436）：上游已归档，推荐的替代是 `pastey`。但 `egui_dock 0.18`、
  `simba 0.9.1`、`metal 0.32.0` 仍声明 `paste ^1.0`，而 Cargo 的 path patch 不能把**不同包名**
  的 crate 注入 `paste` 依赖。因此仓库在 [`engine/vendor/paste`](../engine/vendor/paste) 放了
  **pastey 0.2.3 的维护代码**，用兼容包名/版本 `paste 1.0.15` 暴露给这些依赖；源码不是归档的
  `paste`。`cargo-audit`/`cargo-deny` 对 path 包不产 advisory，所以该条不再出现；这是**替换**，
  不是把归档代码标成安全。等依赖方不再要求 `paste` 时删 shim，直接依赖 `pastey`。
- `zbus_names` / `zvariant` / `zvariant_derive`（RUSTSEC-2026-0370/0371/0372）：这 3 条来自
  eframe 默认启用的 `accesskit` -> Linux-only `accesskit_unix` -> `atspi` -> `zbus 5` 链。项目没有
  使用屏幕阅读器/accesskit API，因此 `eframe` 改为 `default-features = false`，保留
  `wgpu`/`glow`/`default_fonts`/`x11`/`wayland`，**关闭 accesskit**；锁文件里不再有
  `accesskit_unix`/`atspi`/`zbus_names`/`zvariant*`。若将来要恢复无障碍支持，必须整体升级到
  zbus 6 的 accesskit 栈，不能只打开默认特性。
- `ttf-parser`（RUSTSEC-2026-0192）：没有 patched 版本，也没有 drop-in 替代；`ab_glyph`/
  `epaint` 和 `rustlua-render` 都直接依赖它。保留 `deny.toml` 的 ignore（复核截止 2027-10-20），
  这是**唯一**的 unmaintained 例外。

> 本任务实际修掉的一条：`ruzstd 0.8.3` 的 **RUSTSEC-2026-0344**（解压炸弹）。
> 升级到 `ruzstd 0.9.1` 后 audit 归零；`rustlua-infra` 的 `StreamingDecoder` 调用点 API 兼容。

### 4.2 cargo-deny

配置在 [`engine/deny.toml`](../engine/deny.toml)：

- `advisories`：`version = 2`、`yanked = "deny"`、`unmaintained = "workspace"`；
- `licenses`：按实际依赖收敛的 allow 列表（MIT / Apache-2.0 / BSD / ISC / Zlib / 0BSD / BSL-1.0 /
  CC0-1.0 / Unlicense / Unicode-3.0 / OFL-1.1 / Ubuntu-font-1.0 / MPL-2.0 等），`confidence = 0.8`；
- `bans`：`multiple-versions = "warn"`、`wildcards = "warn"`、`allow-wildcard-paths = true`；
- `sources`：`unknown-registry = "deny"`、`unknown-git = "deny"`，只允许 crates.io。

为什么 wildcard 是 `warn` 而不是 `deny`：workspace 内部大量 `path` 依赖不写版本，cargo-deny 0.20
会把其中一部分公开 crate 的 path 依赖也报成 wildcard；直接 `deny` 会逼着给所有内部 crate 加
`publish = false`，改动面远大于收益。补偿是 `check-security.ps1` 里的 **registry wildcard 精确扫描**：
只扫 `engine/Cargo.toml` 与 `engine/crates/**/Cargo.toml`，跳过带 `path` / `git` 的行，
发现 registry 依赖写 `"*"` 即判红。cargo-deny 的 `wildcards = "warn"` 仍会把读数留在日志里。

`multiple-versions = "warn"` 同理：Rust 生态的多版本并存很常见，直接 deny 会变成"每加一个依赖
都要先做一次全图统一"，不适合作为发布阻断项；它作为报告项保留，SBOM 里能查到实际版本。

当前唯一的 advisories 例外：

```toml
{ id = "RUSTSEC-2026-0192", reason = "ttf-parser 无维护版本；替换评估见 docs/69 §4.2，复核截止 2027-10-20" }
```

`reason` 里带复核日期，是因为 cargo-deny 0.20 的 ignore 只接受 `id` / `reason` 两个键，
不接受单独的 `expiry` 字段；日期写进 reason 仍然可被人和脚本检索。

命令（`check-security` 已封装离线/临时配置，手工排查时）：

```powershell
cd engine
cargo deny --locked check
```

离线且 advisory DB 在本地时，`check-security` 会把 `[advisories] db-path` 注入临时配置并加
`--offline`；`db-path` 必须是包含 `advisory-db-<hash>` 子目录的**父目录**，因为 cargo-deny
按默认 URL 的哈希找子目录。cargo-audit 则相反：`--db` 直接指向 RustSec 仓库本身
（有 `crates/` 与 `rust/`，没有 `advisories/`）。

## 5. SBOM（CycloneDX 1.5）

### 5.1 生成

生成器是 [`scripts/release/gen-sbom.mjs`](../scripts/release/gen-sbom.mjs)（Node，零依赖）：

```powershell
node scripts/release/gen-sbom.mjs --output artifacts/reports/rustlua.cdx.json
node scripts/release/gen-sbom.mjs --check --output artifacts/reports/rustlua.cdx.json
# sbom_ok check=1
```

2026-10-20 清理后实测读数：**505 components / 474 有 SHA-256 / 506 dependency 边 / forks=7**。
每个 registry 包：

- `bom-ref` 与 `purl` 都是 `pkg:cargo/<name>@<version>`；
- `hashes` 取 `Cargo.lock` 的 `checksum`（SHA-256），**不重新下载 .crate**；
- `licenses` 优先 SPDX 表达式，复杂表达式保留 `expression`；
- fork 组件额外带 `cargo:source=vendored-fork`、`cargo:patched`、`cargo:fork-base-version` 三个
  property，方便下游区分"来自 crates.io"与"本仓 patch 过"。

`--check` 做四件事：每个 lock 包都在 SBOM 里、哈希一致、PURL 唯一、JSON 可解析；缺文件直接判红
（不是"没文件就跳过"）。**SBOM 不进 git**，发布时作为资产上传。

### 5.2 信任边界

SBOM 的哈希来自 `Cargo.lock`，它证明"发布时 lock 里写的是这个哈希"，不证明"这个 .crate 在当时
确实来自 crates.io"。后者要靠 cargo 的 checksum 校验与 HTTPS；SBOM 不是签名，不能替代 Authenticode。
发布页同时给 SBOM 与 `SHA256SUMS.txt`，二者一起看才有意义。

### 5.3 cargo-cyclonedx 交叉件

`cargo-cyclonedx 0.5.9` 可以按 crate 生成一份官方格式的 BOM 作为交叉参考：

```powershell
cd engine
cargo cyclonedx --manifest-path crates/game/Cargo.toml --format json --spec-version 1.5 --describe crate
# 产出 crates/game/game.cdx.json
```

它的范围是 `game` 这一棵依赖树，不是整个 workspace，所以**不作为发布门**，也不与 505 直接比数字；
用途是当本仓生成器的字段/许可证映射出现争议时，有一个独立实现可对照。CI 的 security job 只跑
本仓 `gen-sbom.mjs`，避免把一个可选交叉件变成新的红门。

## 6. vendored fork 上游同步报告

清单是 [`engine/vendor/FORKS.json`](../engine/vendor/FORKS.json)，报告器是
[`scripts/repo/fork-sync-report.mjs`](../scripts/repo/fork-sync-report.mjs)（Node，零依赖）：

```powershell
node scripts/repo/fork-sync-report.mjs --check --fetch-missing
# fork_sync_ok forks=7 patched=5

node scripts/repo/fork-sync-report.mjs --write artifacts/reports/fork-sync.md
node scripts/repo/fork-sync-report.mjs --online --write artifacts/reports/fork-sync-online.md
```

覆盖 7 条：`paste` 兼容 shim + `mlua` / `mlua-sys` / `lua-src` / `wasm-bindgen-macro` /
`wasm-bindgen-macro-support`（6 条在 `[patch.crates-io]`）与不 patch、且不在 `Cargo.lock` 的
`wasm-bindgen-cli`。其中 `patched=true` 的 5 条是 `paste` / `mlua` / `mlua-sys` / `lua-src` /
`wasm-bindgen-macro-support`；`wasm-bindgen-macro` 只在 `[patch]` 里、`patched=false`；
`wasm-bindgen-cli` 是外部工具，`inLock=false`。`paste` 的 `baseVersion` 是兼容版本 `1.0.15`，
真实上游是 pastey 0.2.3，报告里会显示这是 shim 而非归档 paste 源码。

离线模式读 `$CARGO_HOME/registry/src/*` 的同名同版本源码，逐文件 SHA-256 比对，输出
`added / modified / removed`；找不到上游源码时该 fork 标 `upstream_source=missing` 并让 `--check`
判红（不绿色）。在线模式查 crates.io 最新稳定版，网络失败标 `unknown` 并退 3。报告字段固定为：
fork 版本、上游仓库/引用、补丁文件清单、相对上游的增删改、核对日期、建议动作。

例外：`wasm-bindgen-cli` 是 `inLock=false`、`patched=false` 的工具源码，cargo 不会把它下载到
`registry/src`。要求它的上游源码会让干净的 CI 永远 BLOCKED，而它没有补丁足迹要证明；所以该条标
`upstream_source=not-applicable`、不做 diff，但仍校验 vendor 版本与清单一致。

干净 CI 的 `$CARGO_HOME` 还有一个更普遍的问题：被 `[patch.crates-io]` 替换掉的 crate，cargo
**不会**下载对应的注册表源码。`check-security.ps1 -FetchForkUpstream` 会按 `FORKS.json` 从
`static.crates.io` 下载缺失的 `.crate`，解到 `registry/src/fork-upstream/` 后再做 diff；
解压只接受普通文件和目录，拒绝绝对路径与 `..`。这些源码只给报告用，不参与构建；CI 的两个
security 入口都带这个开关。离线本机没有该开关时仍按"缺源码 = BLOCKED"处理。下载只走 HTTPS，
不校验 Cargo.lock checksum（`[patch]` 条目在 lock 里没有 checksum），所以它们不能作为构建输入。

`--check` 接在 `check-security.ps1` 的 `fork-sync` 项里；`--online` 只用于人工月度核对，
不进常规门，避免网络抖动把 PR 判红。

## 7. tag / release 自动化

### 7.1 本地打 tag

```powershell
# 默认 dry-run，只打印命令，不改仓库
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/repo/tag-release.ps1

# 校验通过后真正打本地 annotated tag
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/repo/tag-release.ps1 -Apply

# 打 tag 并推送，触发 release.yml
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/repo/tag-release.ps1 -Push
```

校验：`engine/Cargo.toml` 的 workspace version 必须是 semver、`-Version` 必须与它一致、
工作树必须干净（`-AllowDirty` 只能用于明确接受"不可复现"的紧急发布）、本地 tag 不存在。
CHANGELOG 没有对应版本段时**只告警**，发布说明会退到 `Unreleased` 并写明，不编造版本段。

### 7.2 release.yml

[`.github/workflows/release.yml`](../.github/workflows/release.yml) 触发：

- `push` tag `v*`；
- `workflow_dispatch`：输入 `tag` 与 `dry_run`（**默认 true**，避免手滑发版）。

一个 Windows job 串行做：固定工具链 → 构建 release 三件套 → 生成 SBOM → 安全门 → 反例自测 →
`package-engine.ps1 -SkipBuild` → `package.ps1 -SkipBuild` → 可选签名 → 强制签名策略 →
打 zip → `SHA256SUMS.txt` → release notes → 上传 Actions artifact → 创建 GitHub Release。

资产命名：

| 资产 | 内容 |
|---|---|
| `RustLua-<version>-win64.zip` | `examples/game_jhyt/builds/pc` 的全部内容（`game.exe` + `pack/`） |
| `RustLua-Engine-<version>-win64.zip` | 编辑器绿色版（`editor.exe` / `game.exe` / `assetc.exe` + 字体 + 样例） |
| `RustLua-<version>.cdx.json` | 整个 workspace 的 CycloneDX 1.5 SBOM |
| `SHA256SUMS.txt` | 上述三个文件的 SHA-256（`<hash>  <name>`，与 `sha256sum -c` 兼容） |
| `release-notes.md` | 构建证据 + 资产哈希 + CHANGELOG 段 |

`SHA256SUMS.txt` 在签名**之后**生成；如果先算哈希再签名，哈希会立刻过期。签名后不再改 zip 内容。
`release-notes.ps1` 的资产表也从最终文件重算哈希，和 `SHA256SUMS.txt` 是两条独立路径，
对不上就是流程有问题。

### 7.3 手动补发 / dry-run

`workflow_dispatch` 的 `dry_run=true` 会构建、签名、打包、上传 Actions artifact，但**不创建
GitHub Release**；最后一步打印资产清单与 notes 前 12 行。补发时给已存在的 tag，`gh release create`
会走 `--verify-tag`；tag 不存在时用 `--target $GITHUB_SHA` 在当前 commit 创建。

### 7.4 覆盖重发已发布版本（re-cut）

> 2026-10-21 已改用新 tag `v0.1.1` 发布（`v0.1.0` 保持原位）；下面的 `v0.1.0` re-cut 流程只适用于
> 必须覆盖同号的场景，不是本次发布路径。

`gh release create` 对已存在的同名 Release 直接失败，所以重发同一 tag 的正确顺序是：
**先删 Release（保留 tag），再推 tag 触发 workflow**，让 `release.yml` 重新创建。

```powershell
# 1) 把 tag 移到新提交（新构建的资产必须与 tag 指向的源码一致，仓库口径：可复现提交）
git tag -f -a v0.1.0 -m "v0.1.0 re-cut: security-clean build (unmaintained 5->1)"
# 2) 删 Release 但保留 tag
gh release delete v0.1.0 --yes
# 3) 强制推 tag，触发 release.yml（有网）
git push origin refs/tags/v0.1.0 --force
```

注意：`tag-release.ps1` 只负责**新** tag；覆盖已有 tag 必须用上面的手工流程。
已知的 re-cut 先决条件与详细步骤（含 Secrets 配置）见

## 8. Windows 代码签名

脚本：[`scripts/release/sign-windows.ps1`](../scripts/release/sign-windows.ps1)。

证书三选一：

1. `-PfxPath` + `-PfxPassword`（或环境变量 `RUSTLUA_SIGN_PFX_PASSWORD`）；
2. `-Thumbprint`：从 CurrentUser / LocalMachine 证书存储找；
3. `-Certificate`：PS 证书对象（测试用）。

优先 `signtool.exe`（PATH → Windows Kits 最新 x64），参数 `/fd SHA256 /tr <RFC3161> /td SHA256`；
找不到时回退 `Set-AuthenticodeSignature -TimestampServer`，并打印 `sign_tool=authenticode`。
时间戳默认 `http://timestamp.digicert.com`，可用 `-TimestampUrl` 换。

```powershell
# 无真实证书也能跑：自签证书签一个未签名 exe，验证通过 + 篡改必须检出
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/release/sign-windows.ps1 -SelfTest
# signing_selftest_ok signer=authenticode tamper=HashMismatch

# 验证已有签名
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/release/sign-windows.ps1 -Path foo.exe -VerifyOnly

# 要求签名（没有证书/签名失败 = exit 1）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/release/sign-windows.ps1 -Path foo.exe -RequireSignature
```

退出码：0 = 已签/验证通过；1 = 要求签名但失败；3 = 无证书/无 signtool 的显式跳过。
**无证书时 release 资产是未签名的**；如果仓库变量 `RUSTLUA_REQUIRE_SIGNING=1`，release.yml 会在
签名步骤之后用一个独立步骤判红，避免"跳过签名但发布成功"。

GitHub 配置：

| 名称 | 类型 | 用途 |
|---|---|---|
| `WINDOWS_CERT_PFX_BASE64` | Secret | PFX 的 Base64；workflow 解码到 `$RUNNER_TEMP`，结束删除 |
| `WINDOWS_CERT_PASSWORD` | Secret | PFX 密码；不打印 |
| `RUSTLUA_REQUIRE_SIGNING` | Variable | `1` = 没证书/签名失败即阻断发布；不设 = 允许未签名并告警 |

证书采购、EV/HSM、公证不在代码范围。签名只证明"这个 exe 由持有私钥的人签过"，不证明代码没有漏洞；
漏洞结论看 §4，来源结论看 §5/§7。

## 9. 门怎么跑（本地 / CI）

本地：

```powershell
# 总门 + 安全门（安全门需要工具与 advisory DB；缺了是 BLOCKED，不是绿）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify/verify.ps1 -Security -SkipClippy -SkipTests -SkipBuild

# 只跑安全门
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify/check-security.ps1 -RequireTools

# 安全门自己的反例：SBOM 篡改、坏 DB 路径、签名自测
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify/test-security-gates.ps1
# security_gates_selftest_ok
```

CI：

- `quality.yml` 的 `security` job（`needs: lint`）：工具链锁定 → 固定工具 →
  `cargo check --workspace --all-features` 解包 registry 源码 → 生成 SBOM →
  `check-security -RequireTools -FetchForkUpstream` → 反例自测 → 上传 SBOM/日志。
- `release.yml`：tag 触发，串行跑同一入口（同样带 `-FetchForkUpstream`）并产出可下载资产。
- `security-schedule.yml`：每周一 03:00 UTC + 手动触发，复跑 `check-toolchain-lock` / SBOM /
  `check-security -FetchForkUpstream` / 反例自测；`fork-sync --online` 作为报告步骤
  （`continue-on-error`），报告与安全日志随 artifact 上传。这样 advisory DB 与上游 fork 的漂移
  不再依赖"有人记得手动跑"。
- `check-toolchain-lock.ps1` 在 `verify.ps1` 的默认段，且 security job 显式先跑一次；
  改版本不改正则会先红在这道门。

`verify.ps1 -Security` 的语义：`check-security` 退 1 → 总门 throw；退 3 → 总门打印
`Quality gate PARTIAL: supply-chain security was BLOCKED` 并**以 3 退出**，不会打印
`Quality gate passed`。这是三态在总门里的落地。

## 10. 已知限制与未测边界

1. **真实 tag 发布已跑通，但真实证书签名仍未跑**：`v0.1.1` 已由 `release.yml` 在 Actions 上构建并
   发布（run `39553133515`，assets 4 个，`SHA256SUMS.txt` 3/3 复核；`game --pack pack --check`
   exit 0）。发布时仓库 Actions secrets 为 0，没有 `WINDOWS_CERT_PFX_BASE64` /
   `WINDOWS_CERT_PASSWORD`，所以签名步骤与 `RUSTLUA_REQUIRE_SIGNING` 强制策略都是 skipped，
   资产 `Status=NotSigned`，发布说明已如实写明。自签自测只证明签名/验证/篡改检测链路；
   "Windows 显示受信任发布者"仍未证明。配好 Secrets 后下一次 tag 才会生效。
2. **本机没有 `signtool.exe`**（Windows Kits 未装）；已走 `Set-AuthenticodeSignature` 回退，
   CI 的 windows-latest 通常带 signtool，但未在本机验证 `/tr` 参数路径。
3. **advisory DB 的时效**：`cargo audit` / `cargo deny` 默认从网络拉 DB；离线机器上的结论以最近一次
   在线日志为准。`-AdvisoryDb` 只解决"能不能跑"，不解决"DB 是不是最新"。仓库已有
   `security-schedule.yml` 每周一 03:00 UTC 复跑并上传报告；两次周检之间新披露的 advisory
   仍要等下一次周检或手动 `workflow_dispatch`。
4. **仅剩 1 条 unmaintained 警告**：`ttf-parser`（RUSTSEC-2026-0192）。`paste` 已用 pastey
   兼容 shim 替换；`zbus_names`/`zvariant`/`zvariant_derive` 已通过关闭 eframe 的 accesskit
   默认特性从依赖图移除。`ttf-parser` 没有 patched 版本/drop-in 替代，保留 deny 例外
   （复核截止 2027-10-20），这是当前唯一例外。
5. **wildcard / multiple-versions 是 warn**：补偿扫描只覆盖 registry 依赖的 `"*"`，
   不覆盖"同一个 crate 两个大版本"这类体积/维护问题；SBOM 能查到版本，但没有判红。
6. **cargo-cyclonedx 交叉件不是发布门**：它按 crate 生成，范围与整 workspace SBOM 不同；
   只作为独立实现的对照。
7. **fork 报告的上游源码**来自 `$CARGO_HOME/registry/src`；本地缓存缺失时离线报告只能标
   `upstream_source=missing` 并判红，逐行 diff 需要先 `cargo check` 解包或联网。
   唯一例外是 `wasm-bindgen-cli`（tool-only、未 patch，标 `not-applicable`，不做 diff）。
8. **WebGL / 微信小游戏未自动发布**；签名只覆盖 Windows PE，不覆盖网页/微信包。
9. **第三方 action 仍按可变 tag 固定**：`actions/checkout@v4`、`Swatinem/rust-cache@v2`、
   `taiki-e/install-action@v2`、`actions/setup-node@v4`、`actions/upload-artifact@v4` 等没有固定到
   commit SHA；它们不接触证书，但仍是供应链的一部分，升级需人工复核。固定 SHA 是后续独立项。
