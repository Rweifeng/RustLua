## Unreleased — 打包脚本按功能拆分：2,555 行入口 → 132 行编排 + 15 个阶段文件（2026-11-02）

- **为什么**：`scripts/build/package.ps1` 涨到 2,555 行 / 192 KB，改任何一处都要在整文件里翻；
  发布链的三个平台（pc/webgl/wechat-minigame）逻辑混在一条线性流程里，出问题只能靠 `==>` 阶段标记定位。
- **拆法**：入口只留 `param()` + 编排（**132 行**，其中参数块原样 79 行），阶段落在
  [scripts/build/package/](../build/package/)：`00-context` / `10-helpers` / `20-staging` / `30-build` /
  `40-assets` / `50-runner` / `60-settings` / `70-first-screen` / `72-subpackage` / `74-pack-export` /
  `76-code-rename` / `80-validate` / `82-manifest` / `84-swap` / `90-selftest`（见表
  [docs/26 §4](26-assetc-and-publish.md)）。
- **执行语义**：阶段被 dot-source，跑在入口的脚本作用域里——共享变量、`ErrorActionPreference`、
  `throw`/`return` 行为都与拆分前一致。**为什么不是函数文件**：主体共享约 200 个跨阶段变量，改成函数
  要么传巨型参数表、要么全改 `$script:` 前缀，两者都会让「逐字节等价」失去可验证性；这是本次刻意
  选择「先拆文件、不动语义」的理由，已写进入口注释。
- **验收（可复跑）**：
  1. **代码等价**：15 个阶段文件去掉 8 行头注释后，逐行等于原文件对应行区间（**2,452 行，0 差异**；
     唯一文本替换是 `$PSScriptRoot` → `$packageScriptRoot`，因为阶段文件不在 `scripts/build/` 下，
     共 17 处）。入口的 `param()` 与原文件 1–79 行逐字节相同，`catch`/`finally` 与原 2331–2350 行相同。
  2. **产物等价**：三平台各打一次包，产物逐文件 SHA256 与拆分前一致——pc 12 个文件、webgl 17 个、
     wechat 32 个，**唯一不同的文件是 `build-info.txt` 的 `build_time` 行**（时间戳，本来每次变）。
  3. **阶段标记等价**：`==>` 行序列与拆分前逐条一致（pc 8 条、webgl 9 条、wechat 23 条）——编辑器
     「发布项目」面板按这些标记映射进度，顺序不能变。
  4. `-SelfTest`：`Directory-isolation self test passed`（带空格路径 + 无源码 + 用户数据目录三条）。
  5. 门：`check-docs` → `check_docs_ok docs=71 links=440 ps1_bom_ok=76 ps1_parse_ok=76`（新增 15 个
     `.ps1` 全部带 BOM 且可解析）。
- **诚实边界**：这次只拆文件，没有把任何一段改写成函数，也没有做"阶段可单跑"；要单跑某段仍需
  先过前序阶段（它们靠共享变量传递状态）。若以后要函数化，得先把跨阶段状态收进一个显式上下文对象，
  那是一次独立改造。
- **回滚钩子**：把入口恢复成原文件即可（原文件在本次提交的父提交里）。

## Unreleased — 修掉 `rustlua-net` 的 TCP 收敛用例：帧数账依赖调度（80 vs 82）（2026-11-02）

- **现象**：本日一次完整 `verify.ps1` 在 `cargo test --workspace --all-features` 里红——
  `rustlua-net::tcp::tests::tcp_sessions_converge_over_a_real_socket`：
  `assertion left == right failed: client advanced every frame; left: 80, right: 82`。
  同一棵树前一轮刚全绿，看起来像"负载抖动"，实际是**测试自己的帧数账写错了**。
- **根因**（读代码即可定位）：`run_side` 的循环条件是 `log.len() < frames`（80），而
  `prime(Vec::new(), 2)` 先塞了 2 帧预热、这 2 帧同样会被放行 → 正确放行数是 **82**。
  旧实现在第 80 帧就退出，剩下两帧能不能进日志取决于"同一次 `try_advance` 是否恰好连取两帧"；
  排空阶段又只 `poll` 不 `try_advance`，于是同一份代码一会儿 82、一会儿 80。
- **修法**：`WARMUP` 提成常量并进循环条件（`expected = frames + WARMUP`），排空阶段也
  `try_advance` 收帧；断言仍是 82（行为不变，只是把"碰运气"变成"等够帧"）。
- **证据**：`cargo test -p rustlua-net --lib` → **18 passed**；连跑 **15 次 0 失败**；
  `--test-threads=1` 也绿；随后完整 `verify.ps1` 重跑 → exit 0（日志见
  [docs/34](../34-质量门与发布清单.md) §6 末行）。
- **诚实边界**：这是测试帧数账的错，不是网络栈行为变化；`scripts/verify/flaky-skips.json`
  仍是空的——**没有**为它登记"跳过"（跳过会把同一类账错藏起来，修掉才是正解）。
- **回滚钩子**：把循环条件改回 `log.len() < frames`。

## Unreleased — 3D 提取"可选组件快速否定"：试过、无可测收益、已回退（2026-11-02）

- **动机**：上一条归因显示 3D 提取占 10,000 网格档 CPU 帧的 46%，而提取里对
  `Visibility`/`Animation3D`/`LodGroup` 三个**可选**组件是逐实体 `get::<T>`——静态场景里
  一个都没有，等于每帧白付 30,000 次注定落空的"存活检查 + `TypeId` 哈希 + downcast"。
- **做法（已实施并测过，随后回退）**：给 `World` 加 `has_storage::<T>()`（每帧查一次），
  三个逐实体查表各自过一道快速否定；可见性那条**必须保留 `view_mask != 0` 的退化语义**
  （存储不存在时 `entity_visible_in` 等价于"遮罩非 0 即全可见"，漏掉它会把"遮罩 0 =
  什么都不画"悄悄变成"全画"）。
- **测量**（release、640×360、10,000 网格档、`--cycles 20`、每组 3 次）：

  | 版本 | 三次 `extract_us` | 中位数 |
  |---|---|---|
  | 无门（基线） | 4,258 / 4,524 / 4,386 | **4,386** |
  | 有门（首次） | 4,535 / 3,950 / 3,970 | 3,970 |
  | 有门（补可见性语义后） | 4,625 / 4,005 / 4,401 | **4,401** |

- **结论**：中位数从 4,386 到 4,401 µs——**差异落在跑次噪声里**（组内极差本身就有 600 µs），
  30,000 次落空查表**不是**这条路径的瓶颈（单 drawable 提取约 0.44 µs）。因此**回退**，
  不留下"看着更快"的代码；`World::has_storage` 一并未保留（不给符号面加无消费者的 API）。
- **教训（写进 docs/62）**：这台机器上 5 轮单次测量的极差可达 ±20%，判断 <10% 的改动必须
  **20 轮 × 3 次取中位数**；单次读数只能用来定"哪一段最大"，不能用来宣称收益。
- **证据**：`wp0_3d_stress --profile` 的 `extract_us` 字段；`cargo test -p rustlua-ecs --lib`
  162 passed、`-p engine --lib` 246 passed（试验版全绿后才回退，回退后同一批测试仍绿）。
- **回滚钩子**：本就是回退态；本条目只记录判据与读数。

## Unreleased — 3D 帧耗时归因：加 `--profile`，实测"下一步不是遮挡剔除"（2026-11-02）

- **为什么做**：`wp0_3d_stress` 只报一个 `cpu_frame_us`，于是"渲染侧下一步做 BVH/遮挡剔除"

- **release 档读数**（640×360、软件光栅、5 轮、`cargo run --release -p engine --example wp0_3d_stress -- --cycles 5 --profile`）：

  | 网格数 | 2D 顶点 | 3D 提取 | 渲染 | 合计 |
  |---|---|---|---|---|
  | 100 | 36 µs | 59 µs | 466 µs | 561 µs |
  | 1,000 | 185 µs | 397 µs | 549 µs | 1,131 µs |
  | **10,000** | 1,873 µs | **4,423 µs（46%）** | 2,910 µs（30%） | 9,206 µs |

- **结论（写进 [docs/62](../62-成熟引擎差距分析.md) §2.1 的注）**：最大单段是**3D 提取**

  剔除部分，上限很小**——下一步应做提取路径，那也正是 docs/53 "每帧分配" 的同一处代码。

  `--profile` 默认关闭，既有报告格式逐字不变（无 flag 时 `"profile":null`）。
- **回滚钩子**：删掉 `--profile` 分支与三个 `Instant` 采样即可（无行为影响）。

## Unreleased — 渲染侧：3D 合批键不再每帧克隆字符串（每帧分配 −19.6% @10k 网格）（2026-11-02）

- **一句话**：`frame_3d_draws` 的分组键从 `(String, usize, Option<String>)` 换成借用
  `(&str, usize, Option<&str>)`；WP0 的 10,000 网格阶梯里每轮分配 **153,238 → 123,238（−30,000，−19.6%）**，
  而 `draw_calls` / `instances` / 三角形读数一个都没变（仍是 `draw_calls=2 instances=10000`）。
- **为什么以前每帧都在分配**：3D 合批按 `(mesh 路径, primitive 序号, 材质覆盖路径)` 分组，
  原实现给每个 drawable 每帧 `clone()` 两个 `String` 当键——可这些键只需要活到本轮合批结束。
  10,000 个静态网格就是每帧两万次堆分配。
- **做法**：键借用 `scene.drawables`（`scene` 的生存期覆盖整个函数），`self` 在这段只被
  `&self` 读（网格缓存、模型缩放），借用键不与可变借用冲突；语义与字符串相等完全一致
  （同一路径仍合并成一批，`HashMap` 只多了哈希，不再分配）。
- **证据**：`cargo run -p engine --example wp0_3d_stress -- --cycles 3`（软件适配器、debug）
  三档分配数 **100 → 2,031 / 1,706（−16%）**、**1,000 → 15,777 / 12,763（−19%）**、
  **10,000 → 153,238 / 123,238（−19.6%）**；`cargo test -p rustlua-gpu --lib` → **151 passed**
  （含 3D 像素对拍与合批用例）。
- **诚实边界**：只削分配，**不削 draw 数**。帧时间在软件光栅上噪声大（10k 档 69,273 → 68,205 µs），
  不作为性能提升宣称。剩余每帧分配的大头在提取层（`runtime_scene/frame_data.rs` 每个 drawable
  `material.clone()`）与 `Scene3d` 的逐帧重建，要改 `Scene3dDrawable` 的字段类型（跨 crate），
  本轮没动。**"跨网格材质合批"的实测结论**见 [docs/62](../62-成熟引擎差距分析.md) §2.1 的注：
  现有数据下能省的 draw 是 0~3 个，下一档要共享顶点缓冲 + indirect draw，属独立项目。
- **回滚钩子**：把分组键改回拥有型 `String` 即可（无行为差异）。

## Unreleased — 渲染侧：3D 材质绑定组稳态复用（2026-11-02）

- **一句话**：3D 每个 draw 每帧一次的 `create_bind_group`，在布局不变的帧上降到 **0 次**；
  第一帧建、之后复用，画面逐字节不变（GPU 用例钉住）。
- **为什么以前省不掉**：材质绑定组把"材质 uniform 段 + 关节调色板段 + 实例矩阵段 + 5 张贴图"

- **做法**：环形缓冲加代次（扩容重建时自增），用 `MaterialBindKey`（代次 + 三段 offset/size +
  调色板档位 + 5 个贴图槽）按 draw 序位缓存绑定组；键相等直接 clone 复用，失配才新建。
  贴图记**槽位号**而不是视图指针：`albedo_textures`/`linear_textures` 只追加不替换，槽位号的
  视图一生不变。
- **验收口**：新增 GPU 用例
  `renderer::tests::material_bind_cache::material_bind_groups_are_reused_on_steady_frames`
  （软件适配器、连渲三帧）：首帧 `created == draws`，稳态两帧 `created == 0 && reused == draws`，
  第 2/3 帧像素**逐字节相同**，且画面有 13 种颜色（不是空帧——"全黑所以相等"不算证据）。
  `cargo test -p rustlua-gpu --lib` → 151 passed，含全部像素级用例（材质预览、HDR、IBL、纹理采样），
  说明复用没有改坏着色：预览用例正是"同一绑定组、换材质字节"的路径。
- **可观测性**：第 5 个带 3D draw 的帧（或首次全命中时）打一行
  `[render] material bind cache stats draws=… created=… reused=… warm=…`，浏览器/真机控制台可见。
  只在"全命中"时打是不够的：真机上一帧没命中的场景在日志里会和"缓存不存在"长得一模一样。
  本轮 WebGL 产物验收**没有**打出这一行（`draws=3 tris=2582` 的采样窗里没有 3D 材质 draw，
  日志里连 120 帧那行 3D 基线也没有），所以产物侧没有这条读数——证据以 GPU 用例为准。
- **诚实边界**：省的是 **CPU 侧创建开销**；绑定组数量本身没有减少（没改成 dynamic offset 或
  材质级共享绑定组），`draw_calls` / `set_pass_calls` / 三角形数都不变。透明与不透明 draw 的
  排序（"材质批量"）本轮没动。
- **回滚钩子**：删 `material_bind_cache` 字段与 `MaterialBindKey`，把 `material_bind_group` 的
  `index` 参数去掉、末尾新建后直接返回，即回到旧行为。

- **根因**（`rustlua-gameplay/src/net_lua.rs` 的 `net.status()` 绑定）：桌面分支
  `state.udp.as_ref().map(|udp| udp.stats())` 能把 `stats` 推成 `Option<UdpStats>`，wasm 分支
  只写 `let stats = None;`，后面 `if let Some(stats)` 里再访问字段时类型已无处可推 → `E0282`。
  这是**只在 wasm 目标下存在**的红，原生 `cargo check --workspace` 看不见。
- **修法**：wasm 分支显式写 `Option<rustlua_net::UdpStats>`（`UdpStats` 在 `rustlua-net` 里
  没有 cfg 门，wasm 上同样可命名）；`verify.ps1` 新增 `WASM platform compile
  (game_web -> wasm32-unknown-unknown)` 一步，插在 clippy 之后、rustdoc 之前，**不进 `-Quick`
  的跳过清单**——它不是重活（热缓存 2026-11-02 实测 10.5 s），而"这棵树红不红"必须包含平台分支。
  缺 `wasm32-unknown-unknown` 目标时打印 `[SKIP] …（不是通过）`，不判红。
- **验收口**：`cargo check -p game_web --target wasm32-unknown-unknown --locked` → 0；
  `verify.ps1 -Quick` → exit 0，且结尾跳过清单里**没有**这一步
  （日志 `artifacts/logs/quality/verify-20261102-125347.log`）。产物层同批复验：
  `package.ps1 -ProjectRoot examples/game_api -Platform webgl` → exit 0（16 个文件 / 8,905.9 KB，

## Unreleased — M76-07 收尾：虚拟列表运行时窗口化（2026-10-31）

- **一句话**：`list{virtualized=true}` 不再"导出即报错"——导出写出 `UiVirtualList`
  （`count/item_height/spacing/overscan`，typed 与 codec 表同步 21 → 22），宿主在每帧布局解算前

- **为什么**：spec 字段、校验、UI Studio 与窗口化内核（`thousand_row_scroll_frames…`）早已就位，
  只差"把 `virtualized` 接到运行时"这一格；背包/排行榜这类长列表是 UI 收口后的下一批真实需求。
- **三个机制**：
  - **行池**：在世行实体数 = 窗口大小（`VirtualList::window`），与数据行总数解耦；5,000 行数据
    只材料化可见行 ± 1 屏。
  - **滚动锚定**：行矩形是内容坐标（`y = stride × index`，左右贴列表宽），滚动位移走既有
    `ScrollView` 路径；滚动范围取 `UiVirtualList::total_height()`，不按已材料化行的包围盒算

## Unreleased — 桌面宿主：窗口遮挡/最小化不再停逻辑（画面停、固定步照跑）（2026-10-28）

- **一句话**：桌面 runner 不再把"窗口被遮挡或最小化"当作暂停——画面停、逻辑继续按 60 Hz 固定步推进
  （`about_to_wait` + `ControlFlow::WaitUntil`）。帧同步联机里一端被别的窗口盖住，不再把对端一起拖住。
- **为什么**：桌面宿主的固定步一直挂在 `RedrawRequested` 里（渲染帧驱动逻辑帧），而
  `update_pause_state` 在 `occluded || !has_renderable_size` 时把 lifecycle 打到 `Paused` ⇒
  渲染一停，逻辑跟着停。单人游戏只是省电（合理）；联机是错的：lockstep 两端按同一帧推进，
  一端最小化就不发输入、也不推进，对端只能等。
- **改法**（`engine/crates/game/src/game_app.rs`）：
  - 抽出 `advance_clock()`（查磁盘 Lua 热重载 → `FixedTimeStep::advance` → 丢步/统计日志 →

    的墙钟，两条路径互斥，同一段时间不会被跑两遍。
  - `about_to_wait` 只在「Running 且窗口不可渲染」时工作：睡到下一个固定步到期
    （`WaitUntil(now + max(剩余, 1ms))`），醒来只跑真正到期的那几步。0 步唤醒不跑管线——
    `run_script_steps` 即使 0 步也会跑一遍帧管线，被遮挡时一秒多跑几十次没有意义。
  - `update_pause_state` 换成 `sync_render_state`：只改"要不要出画"，恢复可见时立刻
    `request_redraw()`；`RedrawRequested` 的重申请也以可渲染为前提（被遮挡时不再空转请求）。
    `AppLifecycle::Paused` 与迁移表未动，只是宿主不再走它。
- **证据**（release `game.exe`，`--log-filter info,game=debug`）：

    `[window] renderable size` 立刻出现、帧计数接着走。
  - 双人联机（中继 `:8790`，房间 `occl`）把一端最小化 10.3 s：两端各记录 **618 次**
    `fixed update returned`（A `f=433→1050`、B `f=435→1052`，两端同步），A 期间 `[perf]` 0 条，
    中继 `checksum_matches=1359 desyncs=0`。
- **回滚档**：只有 `game_app.rs` 一个文件；把 `sync_render_state` 换回暂停语义、删掉
  `about_to_wait` 即回到旧行为。
- **边界**：被"别的窗口盖住"是否触发 `Occluded` 由平台决定（Windows 最小化实测走的是

## Unreleased — 玩法联网：自适应输入延迟（`net.now()` + ping/pong 控制器）（2026-10-28）
