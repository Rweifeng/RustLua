# RustLua 引擎 2D/3D 更彻底统一：方案、现状对比与实施计划

> 文档用途：汇总本轮关于“引擎如何进行更彻底的 2D 和 3D 统一”以及“根据当前 RustLua 引擎现状制定逐条优化计划”的全部结论，形成可执行的工程文档。
>
> 文档性质：现状复核、目标架构、差距分析、分阶段计划和验收契约。本文不替代 `docs/40-引擎全面重构计划.md`，而是把其中与 2D/3D 统一最直接相关的内容重新组织，并补充当前已完成项、剩余接线项和实施优先级。

---

## 1. 本轮讨论结论

### 1.1 核心判断

RustLua 不应把 2D 和 3D 继续发展为两套平行引擎，也不应为了“统一”而强迫所有底层算法、Shader 或物理求解器完全相同。

正确方向是：

> **统一上层数据模型、空间语义、相机描述、资源身份、动画属性、输入投影、编辑器和工具链；保留 2D/3D 在渲染管线、物理求解和批处理方面的专业实现。**

因此，统一的目标不是“所有东西都共用一份代码”，而是：

1. 同一个实体和场景模型可以表达 Sprite、Mesh、粒子、文字、相机和 UI；
2. 2D 是 3D 空间中的一种受约束表达，而不是独立世界；
3. 正交投影是 2D 的默认相机配置，不是另一种相机系统；
4. Sprite 是几何体、材质、纹理区域和排序/深度策略的组合，不是独立渲染世界；
5. 2D/3D 的差异主要由组件配置和渲染策略表达，而不是由互不兼容的类型层级表达；
6. 物理和渲染底层允许专门化，但对外使用统一的生命周期、同步、查询和诊断契约。

### 1.2 必须坚持的设计原则

- **统一抽象，不强行统一所有算法。**
- **不静默近似。** 无法无损表达的剪切、倾斜、空间压平、负缩放或非法数值必须报错或拒绝迁移。
- **先量化再重写。** 没有基准和 profile 证据，不全面替换 ECS、渲染器或调度器。
- **兼容迁移优先。** 旧场景、Lua、Prefab、编辑器和发布流程必须有边界适配和回滚路径。
- **3D 不回退。** 任何统一改造都必须通过纯 3D golden、投影、深度、阴影、材质、骨骼和编辑器回归。
- **UI 与世界空间分离。** Screen UI 不应被世界 Transform 或世界相机意外驱动。
- **排序层不等于深度。** 2D sorting layer/order 不能直接冒充 3D Z 或深度缓冲。

## 2. RustLua 当前事实盘点

> **本节与 §3 描述的是本轮工作开始时的现状快照，保留作为对照基线；最新达成进度与逐条缺口见 §10（滚动更新）。**

本节依据当前仓库源码、`docs/38`、`docs/39`、`docs/40`、`docs/45` 及 `tasks/plan` 下各工作包记录整理。

### 2.1 已具备的基础能力

RustLua 已经不是只有独立 2D 和独立 3D 原型，而是已经完成了一批重要收敛：

- `core/transform.rs` 已成为 2D/3D 变换的共同模块；原 `transform3d.rs` 已并入。
- 已提供 `Transform::to_3d()` 与 `Transform3D::to_2d()`，并采用“可无损才转换”的严格语义。
- `core/camera.rs` 已成为 2D/3D 相机逻辑的共同住处；2D 控制器也已迁入。
- 已有 `Projection::{Orthographic, Perspective}`、`RenderView`、`ClearPolicy`、`CameraSelection` 的核心描述。
- 已有 `spatial_transform.rs` 原型，包含 `LocalTransform`、`GlobalTransform`、父先序传播、换父保持世界位置、剪切/镜像拒绝和增量传播原型。
- 已有 `typed_scene.rs` 原型，覆盖实际源场景出现过的 17 类组件，并能对 26 个真实场景进行源/typed 对拍。
- 已有 `DenseStorage<T>` 原型和 ECS A/B 基准。
- 2D 已具备 Sprite、SpriteBatch、Tilemap、粒子、文字、WorldText、动画状态机、帧事件、输入 `screen_to_world`、2D 物理和 collider debug draw。
- 已完成大量 2D 提取、剔除、顶点单趟化和并行合批优化，并有 2D golden 与性能证据。
- 编辑器已经具备 2D/3D 场景视图、3D 透视视口、Gizmo、实时预览和统一 Transform Inspector 面板的部分能力。
- Lua 已有统一 `transform` 表，可按实体实际拥有的空间分派 2D/3D 变换操作，同时保留 `transform3d` 和 `camera` facade。
- WP0 基准、3D semantic golden、2D overlay golden 和 `verify.ps1 -Benchmarks` 已形成较完整的质量证据基础。

### 2.2 当前真正的架构状态

当前状态更准确地描述为：

> **核心类型和设计已经开始统一，但运行时接线、世界空间渲染、相机消费、物理 authority 和编辑器/迁移闭环仍未完全统一。**

当前仍存在以下事实：

1. `Transform` 仍保留 2D `Vec2 + rotation + Vec2 scale` 组件形式，`Transform3D` 仍是独立运行时组件语义；统一 TRS 原型尚未成为 RuntimeScene 的唯一真源。
2. `GlobalTransform` 传播原型目前主要是可验证的独立模块，生产提取器仍有按单实体 TRS 构造 model matrix 的路径。
3. 场景 `parent/children` 目前主要表达组织关系；不能自动把旧 v2 parent 解释为局部空间。
4. `RenderView` / `FrameViews` 已定义且**渲染器已消费**（清屏策略与视口由宿主声明，不再写死在 pass 里），但渲染器仍分别接收 3D 快照与 2D `SceneMesh`，两套提取路径尚未合成单一 RenderSnapshot。
5. 3D 相机仍保留 `position/target/up` 字段；姿态可由实体 `Transform3D` 提供（组件串 `pose=transform`，默认关闭）——"默认姿态来自 Transform"与 GlobalTransform 传播仍未接入。
6. 2D 默认仍主要走 3D 之后的无深度 overlay，Sprite 与 Mesh 尚未默认共享世界深度。
7. World2D 已接线（世界 Sprite 走带深度的独立通道，`set_world_sprite_depth` 可回滚）；Legacy2DOverlay 与 ScreenUI 的显式层描述仍是 overlay 一条通道内的顺序，尚未拆成类型化层。
8. Rapier2D 与 Rapier3D 保留两套是正确选择，但 `PhysicsAuthority` 和统一同步阶段尚未明确接入。
9. `DenseStorage` 已证明有效，但尚未替换生产 `World` 的热组件存储。
10. `scene_3d()` 仍有每帧克隆 mesh 路径；3D 当前规模较小，优先级低于 2D 收集和 ECS 查询。
11. Tilemap chunk 级脏重建、世界 Sprite nine-slice、完整迁移 CLI 与组件弃用告警仍未完成（**统一 Camera Inspector 与编辑器拾取投影已在本轮完成**；2D 连续碰撞配置 CCD 也已补上）。

## 3. 当前实现与彻底统一目标对比

| 领域 | 当前 RustLua | 目标状态 | 差距性质 |
|---|---|---|---|
| 实体模型 | 同一 World 可放多种组件，但 2D/3D 空间组件仍有分叉 | 一个 Entity + 统一 Transform/Renderable/Camera/Animator 等组件 | 运行时真源未收敛 |
| Transform | 2D `Vec2+角度`、3D `Vec3+Quat`；已有互转和统一原型 | 单一 LocalTransform + 派生 GlobalTransform | 原型未完全接入 |
| 层级 | parent/children 主要是组织关系 | 显式 SpatialParent，父先序传播、dirty/version、reparent | 产品语义仍需裁定 |
| 世界矩阵 | 生产路径仍有单实体 TRS 构造 | 所有渲染、拾取和世界空间逻辑消费 GlobalTransform | 提取路径需改造 |
| 相机 | 逻辑已集中，但 2D/3D 姿态与宿主消费仍分开 | Camera + Projection + Viewport + RenderView | RenderView 尚未全面消费 |
| 投影 | 2D/3D 投影语义已有基线 | 正交/透视都是统一 Projection，投影类型不等于渲染维度 | 接线和兼容尚未完成 |
| Sprite | 主要是 2D overlay quad | Sprite = Geometry + Material + TextureRegion + 深度/排序策略 | 需新增 World2D 路径 |
| Mesh | 3D mesh pipeline、深度、阴影、实例化已存在 | 与 World Sprite 在同一视图按材质、深度和 pass 协作 | 需共享 RenderWorld/RenderSnapshot |
| Renderer | 已消费 `FrameViews`（清屏/视口由声明决定），但仍分别接收 3D 快照与 2D overlay | 按 RenderView 组织 opaque、transparent、world sprite、UI 等 pass | 需要重构 frame/renderer 边界 |
| UI | Screen UI 与世界文字已有区分，但工具链仍有独立映射 | ScreenUI 明确独立于世界 Transform 和世界相机 | 需统一编辑器投影但保持 UI 隔离 |
| 资源 | ResourceDatabase、AssetId 原型和多种缓存已存在 | Sprite/Mesh/Material/Texture 统一 AssetId/Handle | 运行时消费仍有路径型结构 |
| 动画 | 2D clip/state/event 和 3D 骨骼动画分别存在 | 统一属性轨道；2D 帧动画是 Sprite region 轨道，3D 是骨骼轨道 | 需要统一抽象，不必统一采样器 |
| 物理 | Rapier2D/3D 分开，调试绘制与 CCD 已接入 | 后端专用，外部统一 authority、事件、查询和调试契约 | authority 未接线 |
| 输入 | 编辑器拾取与 Lua 已共用 `Camera2D` 投影；3D ray 已存在 | screen→viewport→ray/plane 的统一投影链，编辑器与 Lua 共用 | 3D 侧拾取链尚未统一 |
| ECS | HashMap/有序实体表为主，DenseStorage 已验证 | 热组件渐进 dense/sparse，冷组件保持抽象 | 尚未替换生产存储 |
| 可见性 | 2D 有视口剔除，3D 有 CPU bounds/culling | RenderSnapshot + 层级 bounds + 空间索引 | 仍是两条提取路径 |
| 编辑器 | Transform / Camera 面板与 2D 拾取投影已统一 | 同一 Scene 数据、2D/3D 只是观察/编辑模式 | 3D 拾取与迁移工具仍有分叉 |
| 迁移 | v2→typed 和层级迁移原型有报告 | dry-run、备份、原子写回、一键回滚、弃用期 | 需等待空间继承裁定 |
| 质量门 | 2D/3D golden、基准和 verify 门已存在 | 每个统一阶段都有旧新对拍、性能报告、3D 不回退和一键回滚 | 需要纳入统一阶段门 |

## 4. 目标架构

### 4.1 统一实体和空间

```text
Entity
├── LocalTransform
├── GlobalTransform       // 派生缓存，不作为磁盘真源
├── SpatialParent
├── Renderable            // Sprite/Quad/Mesh/Text/Particle
├── Material / AssetHandle
├── Camera / Light
├── PhysicsBody / Collider
├── Animator
├── Script
└── ScreenUI / UiLayout
```

2D 是 3D 空间中的受约束配置：`z=0`、绕 Z 旋转、`scale.z=1`、默认正交投影。约束属于工具和组件策略，不应形成第二套空间真源。

**现状（统一架构批 E 之后）**：

- `Script` **已经是实体组件**（`core/entity_script.rs` + `core/script.rs`）：场景写
  `Script  file=scripts/ai/patrol.lua`，实例化末尾就把文件读进来、每个实体调一次 `on_spawn(id)`，
  之后每步按实体 id 升序调 `on_update(id, dt)`。因此"哪个实体跑哪个行为"不再是工程级脚本里
  手工维护的分派表。
  - **一个文件一份 Lua 状态、实体是实例**：同文件的实体共享顶层局部变量，每实体状态写在以 `id`
    为键的表里；上万实体不会变成上万份 Lua 状态。
  - 钩子名与工程级脚本不重名（工程级仍是 `on_create/update/on_destroy`），因此同一个文件被两边
    加载也不会互相踩。
  - **路径限制在工程根内**：绝对路径与含 `..` 的路径在解析期报错——脚本是可执行代码，场景文件
    不该能把可执行代码指到工程外。
  - 文件缺失/编译失败在**加载期**报错；`enabled=false` 既不加载也不调用；
    `RuntimeScene::reload_scripts()` 一次处理工程级脚本与每实体脚本。

**现状（统一架构批 G 之后）**：

- **"旧 v2 `parent` 默认仍是组织关系"现在是运行时事实**（批 G）：此前 `RuntimeScene` 的继承开关
  默认是开的，判据只看"场景里有没有 `Parent` 组件"，于是任何一个带 `parent` 边的旧场景都会被
  自动按父子组合解释——正是这条要求要挡住的静默语义变化。现在默认值来自**场景自身的声明**
  （`meta spatial=local|organizational`，未声明 ⇒ 组织关系），宿主开关退化为覆盖（回滚档），
  `RuntimeScene::spatial_mode()` 让"为什么继承/不继承"有据可查；认不出的取值按默认处理并告警点名。
- **文档侧读同一份声明**：`scene_space::world_matrices` 在组织关系下返回局部矩阵，
  `parent_world_matrix` 返回 `None`（"在父之下保持世界矩阵"因此退化为"保持局部值"）。编辑器
  Gizmo、keep-world 换父与运行时由此不会一个按组合算、一个按局部值画（§8-⑦ 修掉的正是这类分裂）。
- **代价是显式**：迁移后的场景必须带 `spatial=local`；仓库里唯一带 `parent` 边的示例场景
  （`game_api/index.scene`）子实体局部变换为 0，两种解释数值等价，因此画面不变。

统一空间契约：

- `Global(child) = Global(parent) * Local(child)`；
- `GlobalTransform` 不序列化，由父先序传播产生；
- 旧 v2 `parent` 默认仍是组织关系，不自动解释为局部空间；
- reparent 提供 keep-world 语义；
- 剪切、镜像、退化缩放、非有限值和不可逆矩阵禁止静默近似；
- dirty/version 只有全量传播被证明为瓶颈后才接入生产。

### 4.2 统一 Camera、Projection 与 RenderView

```text
Camera
├── Projection: Orthographic | Perspective
├── Viewport
├── ClearPolicy
├── VisibilityMask
├── Order
└── Enabled
```

`RenderView` 应包含本帧 Renderer 所需的 view/projection/inverse、viewport、clear、visibility 和 render order。相机姿态来自实体 Transform/GlobalTransform；`look_at` 是修改姿态的方法，而不是第二份姿态真源。

Camera2D controller 继续负责 zoom、bounds、follow、dead-zone、平滑和抖动；Camera3D 继续负责透视、射线和视锥语义。

**现状（统一架构批 A 之后）**：`VisibilityMask` 与 `Enabled` 两项已接线，不再是蓝图里的空字段。

- `VisibilityMask`：`RenderView::visibility` 原本**没有任何消费者**。现在实体侧组件
  `Visibility { layers }`（`core/visibility.rs`）+ 视图侧遮罩共同决定本视图画不画它，判定是
  **相交**（`layers ∩ view != 0`）。缺组件 = 全可见，所以既有场景零改动；被遮掉的实体是
  "不存在于这个视图"（不产顶点、不占默认绘制层序号）。消费点覆盖世界精灵、3D Mesh 与
  `UiImage`/`UiText`（world / overlay 两个遮罩），按名字注册的画布 UI 不是实体、永远照画。
- `Enabled`：`Camera2D`/`Camera3D` 都有 `enabled`，`enabled=false` 的相机不参与选帧（不会成为初始
  2D 相机、不会被 `camera.set_active` 选中——选中已禁用相机时告警并回退到其它候选）。序列化只在
  禁用时写出 `;enabled=false`，启用时字段完全不出现，既有场景串逐字节不变。
- 仍未接线：`Order`（渲染顺序仍由 `RenderLayer` / overlay 排序表达）、`ClearPolicy`（仍有宿主持有）。

### 4.3 统一 Renderable、World2D 和 ScreenUI

Sprite 不要求使用和 Mesh 相同的 Shader，但必须进入相同的 RenderWorld 语义：

```text
Sprite = Quad Geometry + TextureRegion + Material + Transform + Depth/Sorting
Mesh   = Mesh Geometry + Material + Transform + Depth/Sorting
```

三种显式 2D 显示模式：

- `World2D`：使用世界相机，可选参与深度；
- `Legacy2DOverlay`：旧项目默认模式，保持旧排序和像素行为；
- `ScreenUI`：屏幕空间布局，不受世界相机和世界 Transform 影响。

目标渲染组织：

```text
RenderPlan
├── Shadow
├── Depth / Opaque
├── World Sprite / Billboard
├── Transparent
├── Legacy2DOverlay
├── ScreenUI
└── PostProcess
```

**现状（统一架构批 B 之后）**：`RenderPlan` 已经是**类型**且已被渲染器消费，不再是蓝图上的词。

- `core/render_plan.rs`：`RenderPass` 的**声明顺序就是规范执行顺序**（`Ord` 由此导出），
  `RenderPlan::for_frame(FrameFacts)` 是纯函数——输入只有一帧内容的计数与布尔（有多少世界精灵、
  有没有 3D 网格、三个 `RenderLayer` 桶各有多少 draw……），因此"本帧跑哪些通道、按什么顺序"
  可以在**不启动 GPU** 的单测里穷举断言。此前这些决策散在 `render_passes` 的一串 `if` 里，
  决策与执行混在一起，"顺序对不对"只能靠读代码。
- 渲染器**按计划执行**：每个通道的开关从就地判断改成 `plan.contains(...)`，执行完立刻与计划核对
  （`RenderPlan::mismatch`），不一致就 `tracing::warn!`；`Renderer::last_frame_plan()` 与
  `last_frame_passes()` 把"这一帧到底跑了哪些通道"变成可直接断言的事实（此前只能数 draw call 反推）。
  硬性质 `is_canonical()`（同一通道至多一次、严格规范顺序）对全部输入组合都成立。
- 与蓝图的**有意偏离**（都写进了类型的文档注释）：不透明世界 Sprite 排在 `Depth/Opaque` **之前**
  ——共用深度附件时"精灵遮挡网格"要求它先写深度；蓝图里的 `Transparent` 就是 `WorldSprite` 的
  半透明分段（与不透明段同管线同附件，只是深度写策略不同）；`Clear` 与 `VectorText` 是蓝图没单列的
  两条（清屏是附件操作；矢量文字轮廓是独立管线与独立缓冲），保留成通道是因为它们同样改变画面。
- `Legacy2DOverlay` 覆盖 `RenderLayer::{World2D, Overlay2D}` 两个桶，`ScreenUI` 独立成通道，两者共用
  一次 `begin_render_pass`（同一条管线，拆两个 pass 只多 CPU 开销、不写像素）；取桶用的
  `layer_indices` 与既有的 `layered_indices` 共用同一套"层怎么比"的规则。
- `PostProcess` 通道**已落地**（批 C）：宿主用 `Renderer::set_post_process(Some(settings))` 打开，
  场景先画进离屏颜色纹理，最后由全屏 pass 采样它写进目标附件；参数只有曝光 / 色调 / 暗角三个，
  非法值（非有限、负曝光、负色调、暗角越界）由 `PostProcess::new` **当场拒绝**而不是静默夹紧。
  `None`（默认）是回滚档：不创建离屏纹理、不产生额外 pass，像素与收敛前逐字节相同。开后处理时
  本帧**一定会清屏**（离屏附件上没有"上一帧内容"可叠），因此 `ClearPolicy::None` 会被显式改成
  默认清屏色并告警一次——静默改写比报错更难查。像素方向性有测试钉住（恒等参数不变、曝光压暗、
  色调 `[1,0,0]` 把绿蓝压到 0、暗角 1.0 时四角全黑而中心不变）。
- **一等 Quad 已落地**（批 D）：§4.3 那句 `Sprite = Quad Geometry + TextureRegion + Material +
  Transform + Depth/Sorting` 此前只是代码里的既成事实——`Sprite` 组件**必须**给贴图（缺 `texture=`
  直接报 `MissingTexture`），于是"一个纯色矩形"只能写 `texture=__white__` 这种只在渲染器内部有
  定义的哨兵，而几何（size/pivot）、材质（tint）与深度/排序又和贴图绑在同一个类型上分不开。
  现在 `Quad`（`core/quad.rs`）是**独立组件**：`size` 必填，`pivot`/`color`/`z`/`layer`/`order`/
  `flip` 可选，`texture` 可选（缺省即内置白纹理 ⇒ `color` 就是最终颜色）。它**不是第二条渲染
  通道**：提取阶段降级成与精灵完全相同的批处理项（`Quad::to_sprite` 给出几何 + 整张纹理区域），
  因此排序、剔除、深度、可见遮罩、世界/overlay 两条路径全部同源；`Quad` 组件本身**留在 ECS 里**
  （运行时可查可改、`quad.get/set` 可读写），不会被悄悄降级成 `Sprite`。刻意的边界：`Quad` 不
  参与 `Animation`——帧动画动的是 UV 区域，而矩形恰恰没有区域。
- **`Renderable` 与 `Material` 已是单一类型**（批 K）：`core/renderable.rs` 给出
  `Renderable::classify`（一个实体只有**一种**可绘制表达；挂了多种会被点名并按写下来的优先级只画
  一种——此前"Sprite + Quad 同挂"会画两遍）与 `Material`（精灵/Quad 的无光照参数与网格的 glTF PBR
  参数是同一个类型；渲染器 `GpuMaterial` 由它构造，因此"缺省材质"只有一处定义）。
  `Renderable` 是**分类视图**而不是第二份真源：它从组件推出来，不序列化、不参与渲染决策。
- **三种显式 2D 显示模式已是组件字段**（批 J）：`RenderMode`（`mode=world|overlay|screen`），
  未声明 = 跟随全局开关（回滚档），声明后由提取阶段路由到世界通道 / `Overlay2D` / `ScreenUI`。
- **`LocalTransform` 是运行时局部变换的规范表示**（批 L）：`RuntimeScene::local_transform_of` /
  `set_local_transform` 是跨空间读写局部变换的**唯一**入口（实体只有 2D `Transform` 时写非平面值
  **报错**，不悄悄压平）。**存储**仍是每个空间自己的边界格式（`Transform` / `Transform3D`）——
  这是有意的：它们是序列化格式，也是 2D 快路径（平面 f32 弧度比四元数便宜，10k 精灵档实测过），
  而 `Transform`/`Transform3D` 与 `LocalTransform` 之间的转换只有一处实现（`spatial_transform`），
  并且"文档侧与运行时侧对同一实体给出的 `LocalTransform` 必须一致"有逐实体的对拍门。
- 仍未达成：精灵的 tint 仍是顶点级烘焙（`Material` 统一的是**描述**，没有把 tint 搬成 bind group
  参数）。

### 4.4 统一资源、动画、物理和输入边界

运行时统一使用 `AssetId`/`Handle`；SpriteRegion、Mesh、Texture、Material、AnimationClip 和 Skeleton 共享资源身份系统。动画统一为属性轨道和事件轨道：2D 帧动画是 Sprite region 轨道，2D 骨骼动画是 Transform 轨道，3D 骨骼动画是 pose/palette 轨道，底层采样器可继续专用。

Rapier2D/3D 保留两个后端，但统一生命周期、layer/mask、query、事件、debug draw 和 authority。推荐更新顺序：

```text
Input → Script/Controller → Static/Kinematic Sync → Fixed Physics
→ Dynamic Writeback → GlobalTransform → RenderSnapshot → Render
```

输入统一为 `screen → viewport → camera ray → world plane/query`；运行时、Lua 和编辑器 picking 共用同一份投影数学。

**现状（统一架构批 F 之后）**：

- **运行时资源身份已落地**（批 F）：`core/asset_handle.rs` 的 `AssetStore<T>` 给出"`key（路径）→
  `AssetHandle`（下标 + 世代）"的注册表，`intern` 幂等 ⇒ **同一路径在进程内恒同句柄**；释放后
  世代前进 ⇒ **旧句柄失效**（`get` 返回 `None`），而不是拿到别人放在同一个下标上的资源。
  此前运行时侧**没有身份**：`RuntimeScene::texture_paths` 每帧清空重建，`texture = 下标`，
  同一个下标在相邻两帧可以指两个完全不同的资源。
- **身份有真实消费方**：`SceneMesh::path_handles` 与 `paths` 同序把身份交给渲染器，渲染器按句柄
  做贴图缓存查找（O(1)，此前是每 draw 一次线性路径扫描），并用
  `Renderer::texture_identity_stats()` 把命中/未命中变成可断言的事实；宿主手写 `SceneMesh`
  （没有身份）时回退到按路径解析，行为不变。
- 与 `core/resource_db` 的 `AssetId`（16 字节内容指纹，编辑器/assetc 的**工程身份**）刻意分开：
  那一层回答"这是哪个工程资源"，这一层回答"运行时这一帧引用的是哪个已加载资源"。
- 仍未达成：`AnimationClip` / `Skeleton` 仍以网格/贴图路径间接标识（没有独立的 clip 句柄）；
  输入边界的类型强制（`core::picking` 是共用实现，不是类型约束）。

**现状（统一架构批 I 之后，资源身份部分）**：

- **网格也走同一套身份**（`Scene3dDrawable::mesh_handle`）：3D 提取是 `&self`，因此运行时身份表
  改成 `RefCell`——同一网格跨帧恒同句柄，渲染器按句柄查网格缓存（O(1)），
  `Renderer::mesh_identity_stats()` / `cached_mesh_count()` 把"命中"与"同一网格只解析一次"变成
  可断言的事实。宿主手写 `Scene3d`（编辑器预览、测试夹具）时 `mesh_handle: None`，渲染器回退到
  按路径解析——行为与收敛前一致。
- **`Material` 的身份由网格身份派生**：glTF 的材质/贴图嵌在网格资产里（没有独立路径可 intern），
  因此运行时的材质身份是 `(网格句柄, primitive 下标)`，`CachedMesh::primitives` 就是它的载体。
  这比"另编一个材质路径键"更诚实：材质本来就随网格资产一起加载。
- **§4.4 列的六类资源现在都有说法**：Texture / 网格 → 运行时句柄；Material → 网格句柄 + primitive；
  SpriteRegion / AnimationClip / Skeleton → 统一轨道（批 H）。

**现状（统一架构批 H 之后，动画部分）**：

- **统一轨道抽象已落地**（`core/animation_track.rs`）："一条动画 = 若干条按时间采样的轨道"从文档
  说法变成类型——`PropertyTrack`（目标 + 关键帧 + 插值方式）与 `EventTrack`（按时间点触发的事件），
  合起来是 `AnimationTracks`。四类目标 `SpriteRegion` / `PlaneTransform` / `SpatialTransform` /
  `SkeletonPose` 都在同一套类型里；离散目标（region / pose）**只允许 Step 插值**——对 UV 区域插值
  没有意义，校验会拒绝而不是静默产生杂乱帧。
- **它是消费方，不是并列的第二套**：`AnimationClip::tracks()` 把帧动画表达成轨道，
  `AnimationStateMachine::current_frame_uv()` 采样这条 `SpriteRegion` 轨道，`advance()` 的帧事件
  触发改走 `EventTrack::events_in_interval`（`fired` 只负责"本圈已触发过"的去重）。于是
  "帧 → UV"与"事件落在哪一步"两条规则各自只有一处定义；3D 骨骼的 palette 采样器继续专用
  （§4.4 明确允许），但它的轨道形态已能表达进 `TrackValue::Pose`。
- **等价性有测试钉住**：`clip_tracks_agree_with_the_state_machine` 按 1/32 秒步长扫过两圈以上，
  逐步比对轨道采样与渲染真正用的 UV；`clip_tracks_carry_the_frame_events_in_order` 比对事件轨道的
  时刻/名称/序号与片段里的帧事件；既有的帧事件语义测试（每圈一次、单步跨多帧全触发、回绕再触发）
  一条未改而全过——这次收敛**没有改变行为**。
- 新增 Lua `animation.time(id)`（与 `animation3d.time` 同名同义）：轨道采样是"时刻 → 值"的函数，
  脚本按时间轴推理需要一个可读时钟。

## 5. 逐阶段优化计划

### 阶段 A：统一契约和基线

1. 清点 RuntimeScene、game、editor、game_web、assetc、Prefab、Lua 的空间/相机/渲染入口。
2. 固定 2D 约定：Y 向上、tile 第 0 行位于底部、pivot、像素 zoom、DPI、旋转、viewport offset 和负缩放规则。
3. 固定 3D 约定：右手系、+Y 上、-Z 前向、深度 0..1、FOV、near/far、ray、frustum。
4. 固定纯 2D、纯 3D、混合 Sprite/Mesh、ScreenUI 和编辑器 picking fixture。
5. 记录像素、顶点、draw、instance、triangle、CPU/GPU frame、分配和内存。

验收：同机重复误差 ≤5%；旧 2D/3D golden 可复现。失败只撤销测量接入。

### 阶段 B：统一 Local/Global Transform 接入

1. 定义生产版 LocalTransform、GlobalTransform、SpatialParent 和唯一关系来源。
2. 通过边界转换兼容旧 2D/3D 组件，不立即删除旧格式。
3. 使用 parent-first 求解，首版优先正确性；让渲染、拾取、编辑器预览和世界文字读取 GlobalTransform。
4. 接入 reparent keep-world、循环、missing parent、剪切和非法变换诊断。
5. 保持旧 v2 世界位置；新场景或显式迁移后才启用空间继承。
6. 只有基准证明需要时才启用 dirty/version。

验收：`Gchild = Gparent * Lchild`；深度 1/10/100 对拍；2D 屏幕矩形不漂移；3D 模型矩阵、骨骼 palette、物理回写不回退。

回滚：RuntimeScene 关闭空间继承，继续使用旧单实体提取。

### 阶段 C：Typed Runtime、资源句柄和热 ECS

1. v2 可读源格式只在加载边界编译为 TypedScene。
2. 运行时改用 ComponentId、AssetId、Handle、预计算父拓扑。
3. RenderSnapshot 禁止逐帧解析组件字符串和资源路径。
4. 先替换 Transform、Sprite、Velocity、PhysicsProxy 的存储为 dense/sparse。
5. 保留确定性有序遍历入口，热路径不重复克隆实体表。
6. 针对已量出的 5 万 Sprite 收集热点做 A/B；3D 低频组件不因形式统一而强制迁移。

验收：运行帧字符串解析为 0；typed/source 计数一致；旧新快照 hash 一致；10k/100k ECS 和 Sprite 收集有报告；3D 不回退。

回滚：按组件切回 HashMap，typed 编译失败保留诊断和解释路径。

### 阶段 D：统一 Camera/RenderView 接线

1. Renderer 接收 RenderView，不再分别读取 2D/3D 相机。
2. 统一 camera selection、viewport、DPI、resize、离屏目标和 clear policy。
3. 保留 Camera2D controller 的旧 zoom/bounds/follow 语义。
4. 将 Camera3D `position/target/up` 迁移为实体姿态；冲突必须诊断。
5. 编辑器 Scene View 使用同一投影函数；Lua 和旧 Camera facade 转发到统一描述。

验收：旧 2D 坐标转换、3D projection/ray/frustum、resize/DPI/离屏逐项等价；3D golden 不变。

回滚：使用旧相机构造路径，RenderView adapter 可关闭。

### 阶段 E：World2D、Legacy2DOverlay、ScreenUI

1. Sprite、Tilemap、Particle、WorldText 增加明确显示空间。
2. Legacy2DOverlay 保持旧项目默认行为。
3. 新增 World2D Sprite quad，可被正交或透视相机投影。
4. 不透明/裁切 Sprite 可深度写入；透明 Sprite 默认测深不写深度并稳定排序。
5. Mesh、World Sprite、粒子和世界文字共享 RenderView，但保留各自 pipeline。
6. ScreenUI 永远独立于世界深度和世界相机。
7. 增加 Sprite/Mesh 遮挡、透明边缘、HUD 隔离和离屏 golden。

验收：Sprite 与 Mesh 前后遮挡正确；Legacy Overlay 像素不变；HUD 不随相机移动；透明边缘无错误深度写入。

回滚：场景级关闭 World2D，回到 Legacy2DOverlay。

### 阶段 F：RenderSnapshot、可见性和批处理

1. 增加 World → RenderWorld/RenderSnapshot 的明确 Extract 阶段。
2. 快照包含 GlobalTransform、Renderable、材质/纹理句柄、bounds、视图和排序键。
3. 2D/3D 按 RenderView、pass、material、mesh/quad、depth policy 分组。
4. 保留现有 2D 视口剔除和 3D CPU bounds/culling，补层级 bounds 和轻量空间索引。
5. 1000×1000 等真实大地图出现前，不盲做 Tilemap chunk dirty rebuild。
6. 3D 先 profile，再决定 BVH、LOD、遮挡或 indirect；只有 profile 证明收益时才处理 `scene_3d()` mesh clone。

验收：Renderer 不解析场景字符串、不回查 ECS；10k/100k Sprite 和 10k Mesh 有阶梯报告；draw/instance/triangle/CPU/GPU 指标完整；透明、深度、阴影回归通过。

回滚：使用旧全量提取和旧 culling；indirect/遮挡默认关闭。

### 阶段 G：PhysicsAuthority、动画、输入和同步

1. 定义游戏驱动、运动学、物理驱动、动画驱动等 PhysicsAuthority。
2. 明确各阶段允许写入 LocalTransform 的组件和优先级。
3. 统一 2D/3D 静态、运动学、动态同步接口，后端仍使用各自 Rapier。
4. 固定步物理、显示插值、teleport、暂停恢复语义。
5. 统一属性轨道概念，但保留 2D 帧动画和 3D GPU 蒙皮专用数据。
6. 运行时拾取、编辑器 picking、Lua mouse world 共用同一投影/查询链。

验收：30/60/120 FPS 结果一致；同一实体不被多方重复驱动；物理事件、query、debug draw 和 3D Animation3D golden 通过。

回滚：保留旧同步模式和场景级 authority 开关。

### 阶段 H：编辑器、Lua、迁移和发布收口

1. 保持单一 Transform 面板，2D/3D 只是编辑模式。
2. 增加按 Projection 展示的统一 Camera 面板。
3. Scene View、Game View 和运行时共用空间与投影解析。
4. 统一 Gizmo、框选、picking、复制粘贴、批量编辑、Prefab override 和 Undo/Redo。
5. 完成 v2→typed/v3 迁移 CLI：dry-run、诊断、备份、原子写入、一键回滚。
6. 保留 `transform3d`、旧 `camera` 和旧组件名的兼容 facade 与弃用告警。
7. 剪切、负缩放、无法压平的数据必须保留源文件并明确报告。
8. 更新 Lua 文档、示例、模板、assetc、桌面、headless 和 Web 契约。

验收：旧项目可打开、运行、保存；迁移失败不覆盖源文件；Inspector/Gizmo/Prefab/Undo/Play 一致；工作区和发布质量门通过。

## 7. 通用验收门和红线

每个阶段至少提交：设计说明与不变量、旧新对拍、固定场景 p50/p95/p99、2D golden、纯 3D golden、迁移说明、feature flag、回滚说明、失败路径测试以及文档和 CHANGELOG 更新。

质量门：

```text
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace
cargo build --workspace
scripts/verify.ps1 -Benchmarks
```

红线：

- 固定场景 p95 比旧方案慢超过 5% 或 p99 慢超过 10%，默认不启用；
- 内存峰值增加超过 10% 需额外评审；
- 3D projection、ray、frustum、depth、shadow、material、skin、animation、scene load 或 editor preview 任一回退，阻塞合并；
- 不以规则固定步耗时冒充 GPU 帧时间；
- GPU 不支持 timestamp 时报告 `null` 和原因，不用 CPU 时间伪装。

## 8. 最终完成定义

只有以下条件全部满足，才能称为“2D/3D 更彻底统一”：

1. 同一场景和 Entity 模型可同时表达 Sprite、Mesh、正交/透视 Camera、粒子、文字和 UI。
2. 运行时只有一份权威 LocalTransform，GlobalTransform 由统一系统派生。
3. 2D/3D 相机都由 Camera/Projection/RenderView 描述，Renderer 消费同一契约。
4. Sprite 与 Mesh 可以在同一世界视图中按明确深度策略正确遮挡。
5. Legacy2DOverlay 和 ScreenUI 仍可保持旧项目和 UI 行为。
6. 物理后端可以不同，但 authority、同步阶段、查询、事件和调试契约统一。
7. Lua、Inspector、Gizmo、picking、Prefab、Undo/Redo 使用同一空间语义。
8. v2 项目可以通过报告、备份和回滚完成迁移。
9. 纯 2D、纯 3D、混合 2D/3D、编辑器和 Web 都有可重复质量证据。
10. 性能优化由基准证明，没有因统一抽象造成超过门槛的 3D 回退。

最终数据流：

```text
Source Scene / Editor
        ↓
Version Migration + Typed Compile + Asset Handles
        ↓
Logical World
(LocalTransform + Components + SpatialParent)
        ↓
GlobalTransform + Physics/Animation Sync
        ↓
Extract
        ↓
RenderWorld / RenderSnapshot
        ↓
RenderView
        ↓
2D Sprite/Tile/Particle + 3D Mesh + ScreenUI 专用 pipeline
```

一句话总结：

> **RustLua 的彻底 2D/3D 统一，应统一场景、空间、相机、资源、动画、输入、编辑器和快照，而不是强迫 2D 与 3D 共用所有算法；下一步应先把已有 Transform/Camera 原型接入运行时，再以 World2D 和 RenderSnapshot 完成真正的混合渲染闭环。**

### 本轮（§8-③ / §8-④）落了什么

1. `RenderView` 新增 `view_projection: Option<Mat4>`，三个构造器各自从相机求矩阵；渲染器把它作为
   3D pass 与世界 Sprite 通道的**唯一**矩阵来源（未声明才回退 `Scene3d.camera`）。
2. 世界 Sprite 通道的视图/深度决策收敛为纯函数 `resolve_world_sprite_view`：声明主视图 ⇒ 共用相机、
   视口与深度附件；只有 overlay ⇒ 用 overlay 的世界相机但深度独立；全未声明 ⇒ 回滚档。
3. `SpriteDrawBatch::depth_write`（由 `tint_is_opaque` 决定）：不透明段在网格 pass 之前写深度、
   半透明段在其后测深度不写深度。`build_world_into` 的分段键因此包含深度策略。
4. 瓦片（世界层）标为不透明分段、世界文字标为半透明分段；overlay 分段恒为"不写深度"。
5. 回滚档不变：`set_world_sprite_depth(false)`（默认）仍是纯 overlay；宿主不声明 `FrameViews` 时
   世界 Sprite 回到独立深度附件 + 显式矩阵 + 画家顺序，既有像素测试逐字节不变。

### 第二批（§8-⑨ / §8-⑩）落了什么

5. **缺口（下一批）**：`material` / `shadow` 仍无像素级正确性断言；`artifacts/` 仍被 gitignore，

### 第六批（§8-⑥）落了什么

1. **3D 有了权威与步前同步**：`PhysicsWorld3d::kinematic_positions`（只取动态刚体、位置取自
   **ECS**）与 `sync_kinematic_bodies_3d`；`RuntimeScene::physics_sync` 一次同步 2D+3D，
   `last_physics_sync()` 把"这一步同步了几个"暴露成可断言的事实。`PhysicsStageOrder::Legacy`
   从死开关变成真回滚档：`Legacy` 下不做统一同步、2D 回写留在 `physics2d_step`（收敛前的顺序）。
2. **2D 查询不再是"另一件事"**：`physics.raycast/overlap` 换成 Rapier 碰撞体查询（形状、偏移、
   sensor 都参与），与 `physics3d.*` 同义；原来的实体位置判定改名 `physics.positions_in_radius`
   并在文档里写明两者是两件事。`physics.get_velocity` 与 3D 同名同形（`{x=,y=}` + 数值下标）。
   受影响示例脚本 `examples/game_jhyt/scripts/systems/combat.lua` 已改到新名字。
3. **查询吃分组**：两侧 `raycast`/`overlap` 新增可选尾参 `{layer=, mask=}`（缺省全收、只给一侧
   另一侧取 `0xFF`、越界/负数/非整数**报错**），判定与碰撞体自身的 layer/mask 用同一套两位测试。
4. **2D 场景能写静态墙**：`Collider` 支持 `;dynamic=false`（与 `Collider3d` 同名同义）。此前写出来
   只会得到 "unknown field" 报错，静态墙只能靠 `Tilemap` 或代码表达。
5. **调试契约两侧对齐**：`ColliderDebugShape` 与新的 `ColliderDebugShape3d` 都报出世界姿态、
   `sensor`、是否动态；轮廓边只在形状类型上定义一次（`wireframe_edges` / `wireframe_segments`），
   宿主不再内联形状数学；动态绿、固定青、sensor 黄。3D 新增 `physics3d.debug_draw`，
   线框用本帧 3D pass 的相机投影到 overlay。
6. **对拍测试**：`core/physics_parity`（只在测试构建编译）用**同一个场景**在两个世界上跑，
   逐项断言停靠位置/碰撞事件/同步来源/查询命中/分组过滤/调试字段一致——这是"名字一样、语义
   不一样"这类漂移唯一能自动化抓住的地方。

### 第七批（§8-⑧）落了什么

1. **标记不再是第二步**：幂等标记写进场景自身的 `meta`（`meta\tspatial\tlocal`），与迁移后的
   组件数据**同一次原子写**落盘。此前"先写场景、再写标记文件"之间存在窗口：进程在中间死掉会
   留下"已迁移但没标记"的场景，下次运行二次施加，把子树又乘一遍父变换。回滚把 `.bak` 拷回去，
   标记随之消失。旧版旁路标记 `<scene>.spatial-local` 仍被认（已用旧命令迁过的工程不会被二次
   施加），并在回滚时清理。
2. **原子写 + 读回校验**：`write_scene_atomically` 用**唯一**临时名（带进程 id，`Scene::save` 的
   `<path>.tmp` 在并发迁移下会互相覆盖）→ 写 → `sync_all` → rename → 把文件读回来逐字节比对。
   写盘前还有一次"内容能被自己解析回来且再序列化逐字节一致"的自检。任何一步失败都放弃写回并
   报错，源文件保持原样（有测试钉住：把临时路径/备份路径先占成目录，断言源文件字节不变）。
3. **备份语义收紧**：`.bak` 存在但不是文件（例如目录）时**报错**，而不是当成"已有备份"继续——
   那会让用户以为有回滚点、其实没有。
4. **退出码门**：有实体无法无损迁移或有权处理失败时报告行变成 `spatial_migration_blocked` 并
   `exit 2`；报告照样完整打印/落盘，不是静默失败。
5. **报告 artifact**：`--migrate-report <路径>` 把终端报告原样落盘（自动建目录），
   `verify.ps1` 每次跑一遍示例工程的 dry-run 并断言 `spatial_migration_ok` / `refused=0` /
   `removed=0`，因此"迁移干净"是每次验证重新证明的事实。
6. **弃用告警**：迁移命令按 docs/30「已删除的旧设计」表扫描场景，逐条给出
   `removed\t<场景>\tentity=<id>\t<组件>.<旧字段>\t→ <现在写在哪>`。此前旧场景只会以
   `malformed field: x=5` 失败，作者看不出该把几何搬到 `UiLayout`。

### 统一架构批 A（§4.2 的 `VisibilityMask` 与 `Enabled`）落了什么

1. **`RenderView::visibility` 终于有了消费者**：此前 `u32` 字段从没有读者（"字段存在"被当成"能力
   存在"）。现在实体侧有 `Visibility { layers }` 组件（`core/visibility.rs`：十进制/`0x`/`0b` 都收，
   未知键/空串/非整数**报错**），视图侧遮罩仍由宿主声明，判定是**相交**而非相等。缺组件 = 全可见
   ⇒ 既有场景不用改一个字、像素不变。被遮掉 = 不存在于该视图（不产顶点、不占默认绘制层序号、
   不计入计数），每帧被遮掉的实体数记在 `RuntimeScene::view_filtered`，所以"东西没画出来"能一眼
   分清是遮罩拦的还是根本没提取到。
2. **遮罩只作用于有实体身份的内容**：世界精灵与 3D Mesh 吃 world 遮罩，`UiImage`/`UiText` 吃
   overlay 遮罩；按名字注册的画布 UI（面板/血条/调试网格）不是实体，永远照画。把非实体内容也塞进
   遮罩只会让"谁被谁挡住"更难查。测试 `view_visibility_mask_filters_world_sprites` /
   `..._3d_meshes` / `..._entity_backed_ui_only` 各自钉住一条边界。
3. **Lua 只读写实体侧**：`visibility.get/set/all`（`visibility.get` 对缺组件返回 `all()` 而不是 0，
   因为 0 是"什么都不画"的另一个含义）。视图侧遮罩属于宿主声明，脚本改不到——否则"脚本把东西藏起来"
   与"视图决定看哪些层"会演化成两件事。
4. **`Camera.enabled` 落地**：`Camera2D`/`Camera3D` 新增 `enabled`（默认 `true`，**启用时不写出字段**，
   因此既有场景串逐字节不变；禁用才写 `;enabled=false`）。禁用的相机不参与选帧：不会成为场景声明的
   初始 2D 相机、不会被 `camera.set_active` 选中（选中已禁用相机时 `tracing::warn!` 告警并回退到其它
   候选）；编辑器取景相机恒为启用。Inspector 面板补了复选框与"已禁用"摘要（否则用户会看到一台参数
   正常却完全不参与渲染的相机），`camera3d_enabled_round_trips` 钉住编解码不丢开关。
5. **本批仍未接线**：`Camera.Order` 与 `ClearPolicy` 仍是宿主持有（顺序由 `RenderLayer`/overlay 表达）；
   编辑器侧尚未给实体声明 `Visibility`（要先设置再提取，否则会有一帧延迟）。

### 统一架构批 B（§4.3 的 `RenderPlan`）落了什么

1. **"跑哪些通道"从渲染循环里搬进纯函数**：`core/render_plan.rs` 的 `RenderPlan::for_frame` 只吃
   一帧内容的事实（`FrameFacts`：清不清屏、有没有 3D 网格、世界精灵数、有没有不透明段、是否共用
   深度、三个 `RenderLayer` 桶各多少 draw、有没有矢量文字），输出规范顺序的通道列表。此前这些
   判断散在 `render_passes` 的 `if` 里，决策与执行混在一起 ⇒ 不启动 GPU 就没法断言。
2. **渲染器按计划执行并自检**：每个通道的开关改为 `plan.contains(...)`，执行完用
   `RenderPlan::mismatch` 与计划核对（不一致 `tracing::warn!`）。`Renderer::last_frame_plan()` /
   `last_frame_passes()` 把"这一帧实际跑了哪些通道"暴露成可断言的事实。
3. **规范顺序是类型的硬性质**：`RenderPass` 的声明顺序即执行顺序，`is_canonical()`（无重复、严格
   递增）对全部事实组合穷举成立；`mismatch` 自带"少一条 / 多一条 / 顺序颠倒"三条测试，防止
   "计划=执行"退化成恒真断言。
4. **与蓝图的偏离写进类型文档**：不透明世界 Sprite 排在 `Depth/Opaque` 之前（否则共用深度附件时
   精灵遮挡网格不成立）；`Transparent` = `WorldSprite` 的半透明分段；`Clear` / `VectorText` 是蓝图
   未单列的两条。
5. **零像素变化**：计划是派生的、只决定跑不跑与顺序，通道内部行为未改；`verify.ps1 -Benchmarks`
   的五个 golden（2D/3D/混合/HUD/光照）与结构性基线对比全绿。
6. **证据**：`core::render_plan` 五条单测 + `render_plan_matches_the_executed_passes_on_a_real_frame`
   （真实离屏帧上断言空帧只有 `Clear`、不清屏时连 `Clear` 都没有、2D 帧正好两条通道各一个 draw）；
   引擎 733 → 739。
7. **本批仍未达成**：`PostProcess` 通道还不存在（下一批）；`Renderable`/`Material` 仍不是单一类型；
   三种 2D 显示模式仍由宿主选择调用路径，而不是组件上的模式字段。

### 统一架构批 C（§4.3 的 `PostProcess`）落了什么

1. **后处理从"蓝图里的一行"变成真通道**：`core/post_process.rs` 定义参数（曝光 / 色调 / 暗角）与
   校验，`host/renderer.rs` 执行——场景先画进**离屏颜色纹理**，再由全屏三角形 pass 采样它写进
   目标附件（WGSL 顶点由 `@builtin(vertex_index)` 生成，不需要顶点缓冲）。
2. **回滚档是 `None`**：不创建离屏纹理、不产生额外 pass，本帧所有通道直接画进目标附件，像素与
   收敛前逐字节相同；`Some(identity)` **不是**回滚档（会多一次 8 位量化往返），文档与测试都写明了。
3. **非法参数当场拒绝**：非有限值、负曝光、负色调、暗角越界一律 `PostProcessError`，不静默夹紧
   ——"我调了参数但画面没变"是最难查的一类问题。
4. **`ClearPolicy::None` × 后处理的交互显式化**：离屏附件上没有"上一帧内容"可叠，因此开后处理时
   本帧强制用默认清屏色并 `tracing::warn!` 一次；计划函数也把"开后处理 ⇒ 一定有 Clear"编码成事实
   （`post_process_forces_a_clear_and_is_always_last`）。静默改写比报错更难查。
5. **"取出 → 用完放回"的借用策略**：离屏视图单独存进 `self.post_process_scene_view`，渲染时
   `take()` 成局部值、结束时放回，因此渲染循环不必同时持有 `&self` 与 `&mut self`。
6. **证据**：`post_process_pass_changes_pixels_in_the_documented_way`（真实离屏帧的读回像素：
   不开后处理时计划里没有 `PostProcess`；恒等参数不变；曝光 0.5 压暗；`tint=[1,0,0]` 把绿蓝压到
   ≤1；暗角 1.0 时角落是 `[0,0,0,255]` 而中心更亮）＋ `core::post_process` 三条单测。
7. **仍未达成**：`Renderable`/`Material` 仍不是单一类型；三种 2D 显示模式仍由宿主选择调用路径。
8. **验证口径（本批踩到的环境坑，记下来免得重复踩）**：`verify.ps1` 默认的
   `cargo test --workspace --all-features`（全并行）在这台机器上会**蓝屏重启**，崩溃点在**编译
   阶段**（多个 rustc + 链接器同时开），不是跑测试的时候。因此本批的门按"**限并行度**"跑：
   `cargo test --workspace --all-features -j 3 -- --test-threads=3` 与
   `verify.ps1 -Benchmarks -SkipTests`（`-SkipTests` 只跳过门里那条全并行测试步骤，其余步骤一条
   不少；release 构建用 `CARGO_BUILD_JOBS=3` 限制并行度）。两条合起来仍然覆盖门的全部内容
   （fmt / clippy / test / 构建 / golden / 基线对比 / 迁移 dry-run / 文档），只是把并行度降到硬件
   能承受的范围。**`verify.ps1` 与门本身未做任何改动**。
9. **另有一处由我自己造成的假失败**：门运行期间用 `Get-Content` 读它正在写的
   `artifacts/logs/quality/verify-*.log` 会与 `Add-Content` 抢文件锁，门会以 exit 1 中止。看门
   的进度要等它自己结束（或用不会持锁的方式），不要边跑边读那个日志文件。

### 统一架构批 D（§4.3 的一等 Quad）落了什么

1. **`Quad` 成为独立组件**（`core/quad.rs`）：`size` 必填，`pivot`/`color`/`z`/`layer`/`order`/
   `flip_x`/`flip_y` 可选，`texture` **可选**——缺省即内置 1×1 白纹理，`color` 就是最终颜色。
   §4.3 的 `Sprite = Quad Geometry + TextureRegion + Material + Transform + Depth/Sorting`
   因此第一次有了独立的几何/材质类型，而不是"必须给贴图的 Sprite"。
2. **不再是内部哨兵**：纯色矩形此前只能写 `texture=__white__`，而那个字符串只在渲染器内部有定义；
   现在它是 `Quad` 的缺省值，文档与 Lua 读回都给出实际采样到的路径。
3. **不是第二条渲染通道**：提取阶段 `Quad::to_sprite()` 给出几何 + 整张纹理区域，随后走与精灵
   **完全相同**的 `SpriteBatchItem` 路径（同一套排序、剔除、深度、可见遮罩、世界/overlay 两通道）。
   分段按层升序绘制，未写 `layer`/`order` 时用与精灵同一套"按场景顺序"的默认层。
4. **组件留在 ECS 里**：`Quad` 不被降级成 `Sprite`（测试断言 `get::<Sprite>` 为 `None`，否则会画
   两遍），因此运行时可查可改；Lua 新增 `quad.get/set`（与场景组件串同一套语法，非法值报错）。
5. **刻意的边界**：`Quad` **不参与 `Animation`**——帧动画动的是 UV 区域，矩形没有区域；需要帧动画
   就用 `Sprite`。这条写进 docs/16 与类型文档，而不是靠"反正动画查询拿不到 Sprite 就跳过"。
6. **证据**：`core::quad` 四条单测（逐字段解析与回写、默认值不写进串、非法串逐条拒绝、降级出的
   `Sprite` 区域取整张贴图）；`quad_is_a_first_class_renderable_sharing_the_sprite_path`（真实场景
   提取：两个 Quad 各 6 顶点、无贴图者解析到白纹理、`Quad` 仍在 ECS 且没有 `Sprite`、层序按
   升序分段）；`lua_quad_round_trips_and_validates`；`unified.scene` 增补第 9 个实体
   `HealthBar`（`Transform` + `Quad`），`one_scene_expresses_every_renderable_category` 把
   `ComponentId::Quad` 列入必需集合，因此"一份场景表达全部渲染类别"现在包含矩形。引擎 744 → 750。
7. **仍未达成**：`Renderable`/`Material` 仍不是单一类型；三种 2D 显示模式仍由宿主选择调用路径。

### 统一架构批 E（§4.1 的 per-entity `Script`）落了什么

1. **脚本归属从"工程级一份"下放到实体**：新增 `Script` 组件（`core/entity_script.rs`）：
   `file=<相对工程根路径>` 必填，可选 `enabled=false`（启用时不写出字段）。场景因此可以直接声明
   "这个实体跑哪个脚本文件"，不必再在 `scripts/main.lua` 里遍历实体、按名字查、自己维护分派表。
2. **一个文件一份 Lua 状态、实体是实例**（`LuaRuntime::sync_entity_scripts` /
   `call_entity_scripts`）：同文件的实体共享顶层局部变量，脚本用收到的实体 `id` 区分自己；
   上万实体不会变成上万份 Lua 状态。钩子名与工程级脚本**不重名**（`on_spawn(id)` /
   `on_update(id, dt)` vs `on_create/update/on_destroy`），因此同一个文件被两边加载也不会互相踩。
3. **加载期就报错**：场景实例化末尾就读入脚本并调用 `on_spawn(id)`，文件缺失、编译失败、以及
   "有脚本却没有工程根"都在**加载期**报错——否则"脚本没跑"会变成没有线索的谜题。运行时新生成的
   实体下一帧自动补上 `on_spawn`/`on_update`（`call_entity_scripts` 每次都先同步一次）。
4. **路径限制在工程根内**：绝对路径与含 `..` 的路径在解析期报错。脚本是可执行代码，场景文件能让
   它去读工程外的任何文件就不是"配置"而是漏洞。四条非法路径各有用例。
5. **进流水线**：新增内建 step 系统 `entity_scripts`（`ScheduleStage::Script`，依赖
   `ui_click_dispatch`），因此每实体脚本与工程级脚本共享同一套脚本侧状态与阶段顺序；调用顺序
   确定（按实体 id 升序），`RuntimeScene::last_entity_script_calls()` 把它变成可断言的事实。
   内建系统名单（`builtin_pipeline_preserves_legacy_stage_order`）已同步更新。
6. **热重载不再只覆盖工程级脚本**：`RuntimeScene::reload_scripts()` 一次处理两者并返回
   `(工程级状态, 重载的实体脚本文件数)`——工程级没变而实体脚本改了时前者是 `Unchanged`、后者
   `> 0`，两个数字分开报。已生成过的实体不会因重载重复触发 `on_spawn`。
7. **证据**：`core::entity_script` 三条单测（解析与回写、非法字段、工程根外路径逐条拒绝）；
   `entity_script_component_drives_its_own_entity`（加载/调用/`enabled=false` 不加载/热重载改逻辑
   后按新逻辑移动）；`entity_script_reports_missing_files_and_missing_project_root`；
   `entity_script_component_runs_inside_the_step_pipeline`（固定步流水线里真的动了实体，且
   `last_entity_script_calls() == 1`）；`typed_scene` 的来源组件集合把 `ComponentId::Script`
   列入。引擎 750 → 756。
8. **仍未达成**：`LocalTransform` 作为唯一运行时局部变换存储（`Transform`/`Transform3D` 仍是
   边界格式）、v2 `parent` 的组织语义、运行时 `AssetId`/`Handle`、统一动画轨道抽象、以及
   §4.4 的输入边界收口。

### 统一架构批 F（§4.4 的运行时 `AssetId`/`Handle`）落了什么

1. **运行时第一次有了资源身份**（`core/asset_handle.rs`）：`AssetHandle` 是 `(下标, 世代)`，
   `AssetStore<T>` 是 `key（路径）→ 句柄` 的注册表。`intern` 幂等 ⇒ 同一路径在进程内恒同句柄；
   释放后世代前进 ⇒ **旧句柄失效**（`get` 返回 `None`）。此前 `RuntimeScene::texture_paths`
   每帧清空重建、`texture = 下标`，同一个下标在相邻两帧可以指两个完全不同的资源——
   "这一帧的 draw 引用的是哪个资源"跨帧不可比，资源释放也不可能被察觉。
2. **身份有真实消费方，不是"字段存在"**：`SceneMesh::path_handles`（与 `paths` 同序）把身份交给
   渲染器；渲染器按句柄查贴图缓存（O(1)，此前每 draw 一次线性路径扫描），
   `Renderer::texture_identity_stats()` 与 `loaded_texture_count()` 把命中/未命中与"同一资源只
   加载一次"变成可断言的事实。宿主**手写** `SceneMesh`（没有身份）时回退到按路径解析，行为与
   收敛前一致——这条回退路径本身也有测试。
3. **两张表各司其职**：`assets`（跨帧、不清空）是身份；`texture_paths` + `texture_lookup`
   （每帧重建）是本帧的注册顺序与去重。两者都是 O(1) 哈希，批量精灵档不会因为引入身份而多出
   任何线性扫描（`core/quad`/精灵/瓦片/粒子四条产出路径都改到同一入口 `texture_id_of`）。
4. **与工程身份分开**：`core::resource_db` 的 `AssetId` 是 16 字节内容指纹（编辑器/assetc 的
   工程身份），运行时句柄回答"这一帧引用的是哪个已加载资源"。两者都不是对方的副本。
5. **证据**：`core::asset_handle` 四条单测（幂等、释放后失效且**复用下标也不会别名**、重复释放
   no-op、顺序稳定）；`texture_identity_is_stable_across_frames`（真实场景两帧同句柄、不同资源不同
   句柄、身份表记录的就是路径与 `ResourceKind`）；
   `texture_identity_cache_is_hit_on_the_second_frame`（第一帧未命中、第二帧命中、同一资源只加载
   一次、没有身份时统计不动）。引擎 756 → 762。
6. **仍未达成**：Mesh / Material / AnimationClip / Skeleton 仍以路径字符串为运行时身份；动画的
   统一轨道抽象未落地；输入边界已由 `core/picking` 统一但不是类型强制的。

### 统一架构批 G（§4.1 的 v2 `parent` 组织语义）落了什么

1. **默认语义从"宿主猜"改成"场景说"**：`core/scene_space.rs` 新增 `SpatialMode`
   （`Organizational` / `Inherit`）与 `spatial_mode(scene)` / `spatial_mode_issue(scene)`，
   读取场景元数据 `meta spatial=...`。**未声明 ⇒ 组织关系**（v2 历史语义），`spatial=local` ⇒
   父子参与空间组合（迁移工具写入的就是它）。`scene_migration::MIGRATION_META_KEY` 改成引用同一个
   常量，写入方与读取方不会再各自漂移。
2. **修掉一处真实的静默语义变化**：此前 `RuntimeScene` 的继承开关默认是**开**的，判据只看"场景里
   有没有 `Parent` 组件"——任何带 `parent` 边的旧场景都会被自动按父子组合解释。现在
   `RuntimeScene::init` 从场景声明取默认值，宿主 `set_spatial_inheritance` 退化为覆盖（回滚档），
   并且 `RuntimeScene::spatial_mode()` 把"场景自己说的是什么"暴露出来。
3. **文档侧与运行时同一份声明**：`scene_space::world_matrices` 在组织关系下返回各实体的局部矩阵，
   `parent_world_matrix` 返回 `None`（于是"在父之下保持世界矩阵"自然退化为"保持局部值"）。编辑器
   Gizmo / keep-world 换父 / 运行时因此不会一个按组合算、一个按局部值画。
4. **非法声明被点名**：认不出的 `spatial=` 取值按 v2 默认处理，但 `spatial_mode_issue` 会给出
   可读原因，`RuntimeScene::init` 记一条 warn——不静默吞掉。
5. **代价是显式**：断言父子组合的测试与文档必须显式声明 `spatial=local`（本批改了 4 处测试夹具：
   文档/运行时/Lua 三向对拍、编辑器拾取、开关切换、编辑器转发）。仓库里唯一带 `parent` 边的示例
   场景（`game_api/index.scene`）子实体局部变换为 0，两种解释数值等价，因此画面不变。
6. **证据**：`unmarked_v2_scenes_treat_parent_as_organizational_only`（未声明 ⇒ 不组合、子实体世界
   值 = 局部值、但 `Parent` 边仍在 ECS 里）、`explicit_and_invalid_spatial_declarations_are_reported`、
   `organizational_mode_ignores_parents_on_both_sides`（文档侧也不组合）、
   `spatial_inheritance_switches_between_local_and_world_positions`（声明后默认开、关掉回滚、
   再开一致）。引擎 762 → 765，编辑器 170+111、assetc 19、game 13 全绿。
7. **仍未达成**：`LocalTransform` 作为唯一运行时局部变换存储（`Transform`/`Transform3D` 仍是
   边界格式与 2D 快路径）；Mesh/Material/AnimationClip/Skeleton 的运行时身份。

### 统一架构批 H（§4.4 的统一动画轨道抽象）落了什么

1. **"一条动画 = 若干条按时间采样的轨道"从说法变成类型**（`core/animation_track.rs`）：
   `PropertyTrack { target, interpolation, keyframes }` + `EventTrack { events }`，合起来
   `AnimationTracks`（可查询、可校验）。四类目标 `SpriteRegion` / `PlaneTransform` /
   `SpatialTransform` / `SkeletonPose` 在同一套类型里，`TrackValue::matches` 保证"值属于目标"。
2. **离散目标只允许 Step**：对 UV 区域或骨骼 pose 做"插值"没有意义，`validate()` 直接报
   `InterpolationNotAllowed`——静默允许会让美术看到中间的杂乱帧，而画面看起来只是"糊了一下"。
   连续目标（Transform）支持 `Linear`：位置/缩放线性、旋转按**最短弧**（nlerp + 归一化，点积为负
   先取反），结果保证是单位四元数。
3. **事件不写"第几帧"**：帧只是 Sprite region 轨道上的一种量化，写在事件上会让别的轨道类型无法
   复用，因此 `EventMarker` 带 `time` + 源数据序号 `order`（供"每圈只触发一次"去重）。
   `events_in_interval` 的区间是闭区间，`looped && to >= duration` 时按"两段都到达过"处理。
4. **抽象是消费方，不是并列的第二套**：`AnimationClip::tracks()` 生成轨道，
   `current_frame_uv()` 采样 `SpriteRegion` 轨道（`Cow` 借用，帧动画热路径不克隆），`advance()`
   的帧事件改走 `EventTrack::events_in_interval`（`fired` 只负责去重）。3D 骨骼的 palette 采样器
   继续专用（§4.4 允许），但形态已能表达进 `TrackValue::Pose`。
5. **新增 Lua `animation.time(id)`**：与 `animation3d.time` 同名同义（缺组件报错而不是返回 0）。
   轨道采样是"时刻 → 值"的函数，脚本按时间轴推理需要可读时钟。
6. **证据（等价性优先）**：`clip_tracks_agree_with_the_state_machine`（1/32 秒步长扫过 80 步、
   跨两圈以上，逐步比对轨道采样与渲染真正用的 UV）；`clip_tracks_carry_the_frame_events_in_order`；
   `core::animation_track` 六条单测（Step 保持/夹取、平面线性、3D 最短弧、事件区间与回绕、
   校验四类错误、Step 采样是借用）。**既有的帧事件语义测试一条未改而全过**——这次收敛没有改变
   行为。引擎 765 → 773，编辑器 170+111、assetc 19、game 13 全绿。
7. **仍未达成**：Mesh/Material/AnimationClip/Skeleton 仍以路径字符串为运行时身份（轨道抽象只是
   把"动画是什么"统一了，"它是哪个资源"还没统一）；`LocalTransform` 作为唯一运行时局部变换存储。

### 统一架构批 I（§4.4 的网格/材质运行时身份）落了什么

1. **网格也走同一套身份**：`Scene3dDrawable` 新增 `mesh_handle`，`scene_3d_with_camera` 在提取时
   把网格路径 intern 进同一张身份表（`ResourceKind::Model`）。3D 提取是 `&self`，所以运行时身份表
   改成 `RefCell`——这也是"身份表要能被只读提取路径写入"的唯一原因，`asset_entries()` 因此返回
   克隆（借用作用域没法延长到调用方）。
2. **渲染器按句柄查网格缓存**：`cached_mesh(handle, path)` 先查身份表（O(1)），未命中才按路径加载
   并记下映射；`mesh_identity_stats()` / `cached_mesh_count()` 把"命中"与"同一网格只解析一次"
   变成可断言的事实。**路径键的 `mesh_cache` 保持不变**，因此"同一网格被两个路径引用"也不会加载
   两遍；宿主手写 `Scene3d`（`mesh_handle: None`）时回退到按路径解析，行为与收敛前一致。
3. **材质身份由网格身份派生**（`(网格句柄, primitive 下标)`，载体是 `CachedMesh::primitives`）：
   glTF 的材质与底图嵌在网格资产里，没有独立路径可 intern；另编一个材质路径键会变成第二套假身份。
4. **§4.4 的六类资源现在都有说法**：Texture/网格 → 运行时句柄；Material → 网格句柄 + primitive；
   SpriteRegion/AnimationClip/Skeleton → 统一轨道（批 H）。
5. **证据**：`mesh_identity_is_stable_across_frames`（真实场景两帧同句柄、不同网格不同句柄、
   身份表的 `ResourceKind` 是 `Model`）；`mesh_identity_cache_is_hit_on_the_second_frame`（真实离屏
   帧：第一帧未命中、第二帧命中、同一网格只解析一次、`mesh_handle: None` 时统计不动）。引擎
   773 → 775，编辑器 170+111、assetc 19、game 13 全绿。
6. **`AnimationClip` / `Skeleton` 也有了运行时身份**（批 N）：片段身份是**内容签名**
   （`AnimationClip::resource_key` = 贴图 + 帧数 + 帧率位模式 + 循环 + 事件；`Animation3D::resource_key(mesh)`
   = 网格 + 片段名），在推进动画时 intern 进与贴图/网格同一张身份表（`ResourceKind::Animation`）。
   同一片段在进程内恒同句柄，"这份动画是哪一个"因此跨帧可比。**同批修掉一个真实性能回归**：批 H 把
   "帧 → UV"与帧事件改成走轨道视图，但每次调用都现算一遍（`cols` 个关键帧 + 事件 Vec），对一群动画
   实体就是**每帧每实体一次分配**——而 WP0 基准场景恰好都是静态精灵，性能门没抓到。现在轨道视图与
   身份键按片段缓存（换片段才重建），`advance` 在片段没有事件时直接跳过事件采样，
   `clip_track_cache_is_reused_across_frames` 用**数据指针**证明缓存真的在复用。
   `LocalTransform` 作为唯一运行时局部变换存储；§4.3 的三种显式 2D 显示模式与
   `Renderable`/`Material` 单一类型。

### 统一架构批 J（§4.3 的三种显式 2D 显示模式）落了什么

1. **显示模式从"宿主选路径"下放到实体**（`core/render_mode.rs`）：`RenderMode` 组件
   `mode=world|overlay|screen`。此前"这段几何走哪条路"是**全局开关**
   （`RuntimeScene::set_world_sprite_depth`）决定的：整帧要么全走世界通道、要么全走 NDC overlay，
   同一场景里没法混——"3D 场景里挂一个不受相机影响的 HUD 精灵"只能靠另开 UI 通道或干脆不做。
2. **语义**：未声明 = 跟随全局开关（既有场景一字不改、像素不变，这是回滚档）；
   `overlay` / `screen` = **退出世界通道**（屏幕空间，分别落 `Overlay2D` / `ScreenUI` 桶，因此画在
   世界内容之上且 ScreenUI 不被其它 2D 内容盖住）；`world` = **请求世界通道**（通道是帧级的，
   默认实体也跟着进——这条写进 docs/16，免得变成意外）。
3. **未知取值报错**：`mode=wrold` 被静默当成 overlay，会让"我写了 world 却没进世界通道"变成没有
   线索的问题。
4. **顺带修掉一个真实缺陷**：`merge_adjacent_draws` 的合并条件是"纹理相同 + 顶点连续"，**漏了
   `render_layer`**——相邻两段纹理相同、顶点连续时会被并成一段并沿用前一段的层，于是 ScreenUI 的
   几何悄悄变成 Overlay2D：几何还在、层却变了，§8-⑤ 的 HUD 隔离门在有显式显示模式之后就会失效。
   现在层一起比，并加了回归测试（跨层不许合并、同层连续才合并）。
5. **证据**：`explicit_render_modes_route_geometry_to_the_right_channel`（真实场景：默认实体进
   世界通道 6 顶点、`mode=overlay`/`mode=screen` 分别落 Overlay2D/ScreenUI 桶、路由计数
   `(0,1,1)`；宿主开关关着但声明了 `mode=world` 时这一帧照样走世界通道）；
   `merging_adjacent_draws_never_crosses_render_layers`；`core::render_mode` 两条单测。
   引擎 775 → 779，编辑器 170+111、assetc 19、game 13 全绿。
6. **仍未达成**：`Renderable`/`Material` 仍不是单一类型（§4.3 剩下的那一条）；
   `LocalTransform` 作为唯一运行时局部变换存储。

### 统一架构批 K（§4.3 的单一 Renderable / Material）落了什么

1. **`Renderable` 是单一的**（`core/renderable.rs`）：`RenderableKind` 覆盖 Sprite / Quad / Mesh /
   WorldText / Text / Image / Particle，`Renderable::classify` 从一个实体的组件名集合给出
   `Single` / `None` / `Conflict`。冲突带**优先级**（`Sprite → Quad → Mesh → 文字 → 图片 → 粒子`），
   因此"两者都挂时画哪一个"是可预测、可断言的，而不是取决于收集循环的先后。
2. **冲突被点名两次**：加载期收集进 `scene_renderable_conflicts`
   （`RuntimeScene::renderable_conflicts()` 读回并记一条 warn），提取阶段按优先级只画一种。此前
   "`Sprite` + `Quad` 同挂"会**画两遍**——既没有诊断也没有优先级。
3. **`Material` 是单一的**：`Material { base_color, texture, metallic, roughness, unlit }`，
   精灵/Quad 用 `unlit(...)`、网格用 glTF `pbr(...)`；渲染器 `CachedPrimitive` 直接持有它，
   `GpuMaterial` 由 `from_material` 构造——"缺省材质"（基色/金属度/粗糙度）从此只有一处定义。
4. **刻意的边界**：`Renderable` 是**分类视图**，不是第二份真源（不序列化、不参与渲染决策）；
   精灵的 tint 仍在顶点里烘焙（批处理路径就是性能所在），`Material` 统一的是**描述**而非 bind group
   参数。
5. **证据**：`core::renderable` 三条单测（分类与非可绘制组件无关、冲突按文档优先级消解且与参数顺序
   无关、材质校验与缺省）；`conflicting_renderables_are_reported_and_only_one_draws`（真实场景：
   冲突被点名、只画精灵那 6 个顶点）。引擎 779 → 783，编辑器 170+111、assetc 19、game 13 全绿。
6. **仍未达成**：`LocalTransform` 作为唯一运行时局部变换存储；精灵 tint 的材质化。

### 统一架构批 L（§4.1 的 `LocalTransform` 规范表示）落了什么

1. **读：一个入口**——`RuntimeScene::local_transform_of(scene_id)` 把 ECS 里的 `Transform` /
   `Transform3D` 统一转成 `LocalTransform`（3D 优先，因为它是超集空间；与"两份局部真源会被点名、
   矩阵按 3D 取"的既有规则同源）。跨空间、跨系统要"一个局部变换"时不再各写一次转换。
2. **写：一个入口**——`RuntimeScene::set_local_transform(scene_id, value)` 写回实体**自己的**空间：
   有 `Transform3D` 就原样写；只有 2D `Transform` 时**只在真能无损压平时**才写，否则**报错**并保持
   原值不变（手抄 XY 会丢掉旋转与缩放，docs/54 §1.2）；两种组件都没有则 `Ok(false)`。
3. **表示层对拍门**：`runtime_and_document_agree_on_the_canonical_local_transform` 对真实场景
   逐实体比对运行时导出的 `LocalTransform` 与 `scene_space::local_transforms`（文档侧解析）——这正是
   "两份真源"最容易被引入的地方，现在任何一处改口径都会在门里失败；写回 round-trip 也一并断言。
4. **非平面值被拒绝**：`non_planar_local_transform_is_refused_for_2d_entities` 断言 2D 实体收到带 z
   位移的值时报错、且**不留半写状态**（原值仍在）。
5. **存储的边界是刻意的**：运行时 ECS 仍按空间存 `Transform` / `Transform3D`——它们是序列化边界格式
   与 2D 快路径；`LocalTransform` 是**规范表示**（组合/反解/换父/迁移都基于它，docs/40 WP2、
   §8-②）。这条差别写进文档而不是含糊过去：把 2D 也换成四元数存储会牺牲已量过的快路径，而
   "唯一真源"由转换只有一处 + 上面那条对拍门保证。
6. **证据**：上述两条新测试 + 既有 `scene_ambiguous_transforms` / `scene_space::local_transform_truth`
   的仓库级门（56 份示例场景逐份断言"局部变换真源唯一"）。引擎 783 → 785，编辑器 170+111、
   assetc 19、game 13 全绿。

### 统一架构批 N（§4.4 的动画片段身份 + 轨道缓存）落了什么

1. **`AnimationClip` / `Skeleton` 有了运行时身份**：片段没有文件路径，身份因此是**内容签名**——
   `AnimationClip::resource_key()` = 贴图 + 帧数 + 帧率**位模式** + 循环 + 帧事件；
   `Animation3D::resource_key(mesh_path)` = 网格 + 当前片段名（3D 片段来自 glTF mesh 资产，
   `Animation3D` 自己不存路径，路径在实体的 `MeshRenderer` 上）。推进动画时把它们 intern 进与贴图/
   网格同一张身份表，kind 为 `ResourceKind::Animation`（新增的家族）。热路径上先 `handle_of` 再
   `intern`，因此每帧只有一次哈希查找、不分配字符串。
2. **同批修掉批 H 引入的性能回归**：轨道视图是 `(clip)` 的纯函数，但批 H 的 `advance` 与
   `current_frame_uv` 每次调用都现算一遍（`cols` 个关键帧 + 事件 Vec）——对一群动画实体就是每帧每
   实体一次分配。WP0 的基准场景恰好都是静态精灵，所以性能门没抓到；这次是**读代码时发现的**，不是
   门发现的（这条差别也说明：门只覆盖它跑过的场景）。现在：
   - 轨道视图与身份键**按片段缓存**，只在当前片段变化时重建（`set_state` 是唯一的变更点，已接）；
   - `advance` 在片段**没有帧事件**时直接跳过事件采样，省掉每帧一次 Vec 分配；
   - `current_frame_uv` 采样缓存（帧 → UV 这条规则仍只有一处定义）。
3. **证据**：`clip_track_cache_is_reused_across_frames`（用关键帧切片的**数据指针**证明缓存复用；
   换状态后指针与身份键都变，切回去又回到原键）；`clip_resource_key_is_content_addressed`
   （名字不参与身份；帧数/帧率/循环/贴图/事件任一不同即不同键）；
   `animation_clip_identity_is_stable_across_frames`（真实场景：推进动画后身份已登记、kind 是
   `Animation`、相邻两步同句柄、第二帧不重复登记）。引擎 785 → 788，编辑器 170+111、assetc 19、
   game 13 全绿。
4. **仍未达成**：精灵 tint 仍是顶点级烘焙——这条**不是缺口而是刻意的**：tint 放顶点里才能让
   "同贴图不同 tint"的精灵合进同一个 draw，搬进 bind group 就得按 tint 拆批（见批 K 的边界说明）。

### 统一架构批 O（动画分配门 + 本批自己引入的浪费）落了什么

1. **补上"门覆盖不到动画路径"这个洞**：批 N 的性能回归是**读代码发现的**，不是门发现的——WP0 的
   阶梯里没有动画实体。现在 `wp0_scene_frame` 单列一档**动画精灵阶梯**（500 / 5,000 个实体，同一
   片段），报告 `alloc_count_p50` 与"每实体脚本分配"，`verify.ps1` 判红两件事：
   ① 两档实体数相差 10 倍时每帧分配次数之差 ≤ 20（**每帧分配不许随实体数增长**）；
   ② 最大 `alloc_count_p50` ≤ 200（两档一起退化也判红——5000 实体若每实体一次分配就是 5000）。
   实测：500 实体 79 次 / 5,000 实体 80 次（每实体 0.116 → 0.0116），**平面**。
2. **修掉批 N 自己引入的浪费**：登记片段身份时先收集 `Vec<String>` 再逐条查表 = 每帧每实体一次
   `String` 分配。改成**就地**先 `handle_of` 再 `intern`（命中路径零分配），并在片段没有帧事件时
   跳过事件采样。3D 骨骼那条刻意保留"每帧组合一次键"：骨骼实体数量少，而 `Animation3D` 不知道网格
   路径、没有可缓存的完整键——这条差异写进了代码注释与 docs/53。
3. **门是同一份报告的两个读者**：`animation_alloc_p50` 由 `verify.ps1` 从报告 JSON 直接读，不另算
   一遍；`wp0_scene_frame_ok` 行也带上 `animation_stairs=2 animation_alloc_p50_max=80` 便于人工速查。
4. **证据**：`verify.ps1 -Benchmarks -SkipTests` 全绿（含新断言）；`docs/53` 新增 §3.4b 记录两档实测
   数字与门槛理由。引擎 788、编辑器 170+111、assetc 19、game 13 全绿。

### 统一架构批 P（传播成本的实测阶梯）落了什么

1. **把一条"判断"变成"证据"**：§11.1 此前把 dirty/version 增量传播登记成"有意未实施（未被证明是
   瓶颈）"——那是我自己的判断，不是测量。批 P 在 `wp0_scene_frame` 里加了一档**层级帧阶梯**
   （`spatial=local` 的场景，1,000 / 10,000 个实体按深度 8 组成父链 + 精灵），从每帧的调度报告里
   取 `spatial_propagate` 那一格的耗时，报出它与整帧的占比。
2. **测出来的结论与判断相反**：
   | 实体 | 链数（深度 8） | 帧 p50 | 传播 p50 | **传播占比** | 每帧分配次数 |
   |---:|---:|---:|---:|---:|---:|
   | 1,000 | 125 | 4,252 µs | 1,228 µs | **28.6%** | 4,602 |
   | 10,000 | 1,250 | 44,835 µs | 14,131 µs | **31.5%** | 44,951 |
   即：**传播占一帧约三成，且每实体每帧约 4.5 次分配**——它是真瓶颈，不是"没被证明是瓶颈"。分配
   来源在读代码时定位：`collect_hierarchy` 与 `parent_first_plan` 各用 `BTreeSet`/`BTreeMap` 逐实体
   插树节点。
3. **门只判"测量是活的"**：`verify.ps1` 断言层级阶梯恰为 2 档、`spatial_propagate_us > 0`、占比落在
   `0..100`；**时间阈值不进门**（跨机不可比，与 `compare-baseline -GeometryOnly` 同一口径）。
4. **下一步（批 Q）**：先修分配与索引结构（排序 `Vec` + 二分取代 `BTreeSet`/`BTreeMap`、链上暂存
   复用），再按修后的占比决定是否需要 dirty/version 增量。修前/修后的数字都记在 docs/53 §3.4c。

### 统一架构批 Q（传播路径的索引与分配）落了什么

1. **按批 P 的定位修掉真瓶颈**：`collect_hierarchy` 与 `parent_first_plan` 各用 `BTreeSet`/`BTreeMap`
   逐实体插树节点（每节点一次分配），外加"每条链一个 `Vec`"。现在：排序 `Vec` + 与下标一一对应的
   `state: Vec<u8>` + `binary_search` 定位；链上暂存整趟复用。**语义与顺序都不变**（`BTreeSet` 本就是
   按 id 升序，`ordered`/`problems`/诊断顺序因此不变），既有的传播/环/悬空父/歧义局部变换测试一条
   未改而全过。
2. **实测（1,000 / 10,000 实体、深度 8 的父链）**：

   | 实体 | 帧 p50 | 传播 p50 | 传播占比 | 每帧分配次数 |
   |---:|---:|---:|---:|---:|
   | 1,000 | 4,252 → **3,045 µs** | 1,228 → **801 µs** | 28.6% → **26.2%** | 4,602 → **138** |
   | 10,000 | 44,835 → **31,525 µs** | 14,131 → **9,283 µs** | 31.5% → **29.4%** | 44,951 → **155** |

   分配从"每实体 4.5 次"降到**与实体数无关的 155 次/帧**（1 万档 300 倍），传播快 35%，整帧快约 30%。
3. **占比几乎没变，这是信息而不是失败**：省掉的是分配的固定开销，剩下的三成是真实工作——每实体
   3 次组件查找（`Parent`/`Transform`/`Transform3D`）+ 矩阵组合 + `GlobalTransform` 写入。因此
   §11.1 的状态更新为"分配已修、增量待定"，并留待批 R 按"静态层级场景里传播占比"决定是否接
   dirty/version。
4. **门收紧**：层级档新增两条断言——`alloc_count_p50` ≤ 400、两档之差 ≤ 100（**分配不许随实体数
   增长**）；时间阈值仍不进门。
5. **证据**：`verify.ps1 -Benchmarks -SkipTests` 全绿（含新断言）；引擎 788、编辑器 170+111、
   assetc 19、game 13 全绿；docs/53 §3.4d 记修前/修后对照。
