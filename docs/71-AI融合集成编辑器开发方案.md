## 1. 背景与目标

RustLua 是单人/小团队、全 Rust、强门文化（`scripts/verify/verify.ps1` + MVP 回归 + 黄金对账）的
2D/3D 引擎，脚本层是 Lua（vendored 补丁版 mlua）。编辑器是 egui/eframe，已具备商业引擎对标的
类型化命令总线、事务/撤销、schema 驱动 Inspector、插件注册表与 GUI 证据 harness（见
[docs/55 编辑器商业引擎对标重构计划](55-编辑器商业引擎对标重构计划.md)、
[docs/58 阶段 0-3 收口](58-编辑器重构阶段0-3收口与验收.md)）。

**目标**：把 AI（大模型）接入编辑器**授权侧**工作流——让 AI 能读场景/组件/控制台/Lua API、
能经确认与撤销安全地改场景与写 Lua 脚本、能跑无头自测，且全程可审计、可回放、可进门。

**非目标（本期）**：游戏内运行时推理（智能 NPC 等）、生成式美术资产管线、绑定单一云厂商。

## 2. 市场方案对标与取舍

2025–2026 年主流引擎的 AI 融合已收敛：**授权侧统一到 MCP（Model Context Protocol）**，
运行时侧各家自造推理引擎。

| 引擎 | 授权侧（AI 驱动编辑器） | 运行时侧（游戏内推理） | 对 RustLua 的启示 |
|---|---|---|---|
| Unity AI（原 Muse） | Assistant（代理式动作：解控制台错误、批量重命名、造 NPC 变体、摆物件）+ Generators（Sprite/Texture/Animation/Sound）+ 官方 MCP Server | Inference Engine（原 Sentis，端侧推理） | 代理式动作 + MCP 是主形态；生成式资产后置 |
| Unreal | Epic 官方实验性 Unreal MCP 插件（进程内起 server） | 第三方为主 | 进程内 MCP server 的范式 |
| Godot | 社区 Godot-MCP（C# addon 暴露编辑器操作为 tools） | 弱 | 小引擎靠 MCP 也能补齐 |
| Unity-MCP（CoplayDev，MIT，47 tool） | 建场景/GameObject、改脚本、管资源、跑测试、构建 | — | **tool 粒度与清单的最佳参照** |
| BlenderMCP | 提示词驱动建模 | — | 生成式资产管线参照 |

**统一架构范式（三层，边界必须分离）**：

```
AI 客户端(Claude/Qoder/Cursor)  ──MCP(JSON-RPC over stdio/TCP)──►  MCP Server
      ──本地Socket──►  引擎桥接层(进程内)  ──Editor API──►  编辑器
```

**取舍结论**：
1. **主轴选授权侧**，运行时推理（Track B）暂缓——它对 wasm/微信体积极不友好，重投入低紧迫。
2. **走 MCP，不自造协议、不绑厂商**——模型无关，Qoder/Claude Code/Cursor/本地 LLM 皆可直连。
3. **RustLua 的结构性优势：单语言单进程**。Unity/Unreal 之所以要"MCP Server(Python) + 引擎桥接(C#/C++)"
   两进程，是因为跨语言；RustLua 全 Rust，可把 MCP server 直接嵌进编辑器进程，省掉进程跳与序列化桥，
   延迟更低、崩溃域可控（已有 `PluginRegistry` 的 panic 隔离，见
   `engine/crates/rustlua-infra/src/editor_plugins.rs:7`，`PLUGIN_API_VERSION=1`）。

## 3. 两条集成轴

| 轴 | 含义 | 市场对应 | 本期 |
|---|---|---|---|
| **Track A 授权侧** | AI 帮开发者在编辑器里造游戏 | Unity Assistant / MCP | ✅ 本方案主体 |
| **Track B 运行时侧** | AI 推理跑在发布的游戏里（智能 NPC） | Unity Inference Engine / Sentis | ⏸ 暂缓，单独立项 |

Track B 的前置门槛（必须先论证再开工）：ONNX/端侧推理进 Lua 的**体积账**（微信主包上限、
`noextern` heap type 那类真机坑，见项目记忆）、wasm 目标可行性。未过论证不排期。

### 3.1 M75-06 论证结论（2026-10-22，只出结论、不开工）

**结论：Track B 不立项。** 依据与账：

- **体积账（微信）**：`docs/52` 的口径是主包 ≤ 4 MB、单个普通分包不限、总量 ≤ 20 MB（无内购保守取
  20 MB）。`metrics/history/2026-10.jsonl` 的 package 读数：`wechat|subpackage|main` 主包
  493,011 B（约 481 KB）、分包 5,175,946 B、总量 5,668,957 B（约 5.4 MiB），总量只剩约 14.3 MB
  余量。ONNX Runtime Web 的上游 wasm 产物在数 MB 到十余 MB 量级（**未在本仓实测**，需立项探针才能
  钉死），加上模型权重，即使自定义裁剪也会吃掉剩余余量的相当部分；一旦超 20 MB，只能继续拆分包或
  改远端推理。
- **wasm 宿主可行性**：现有 `game_web.wasm` 为 9,074,177 B（gzip 9 后 2,862,792 B），再加推理
  运行时与权重会显著抬高首包下载；微信侧还受上传器 ECMA 2019 解析档位与真机内存约束
  （见 `docs/52`、项目记忆 `project-wechat-publish-quota-hazard`）。
- **桌面宿主**：原生 `ort` 可行，但这与 M75 的"编辑器授权侧 AI"不同轴——它是**发布包内的游戏 AI**，
  需要独立的产品需求、模型训练与内容管线，不属于本批"接线"工作。
- **替代路径**：智能 NPC 先用 Lua 行为树/规则 + 远端推理（不占包体）；若出现"必须离线端侧推理"的
  产品需求，重开条件须同时满足：① 有具体玩法需求与可接受的质量基线；② 自定义运行时 + 模型能在
  分包内压到可接受体积（以真机 PoC 实测，不用上游整包估算）；③ 桌面/WebGL/微信至少各有一台真机
  验证。
- **买不到的部分**：本条没有实测 ONNX 运行时字节，也没有真机帧率/内存读数；因此结论是
  "**当前不立项**"而非"永久排除"，重开前必须先补这三项探针。

## 4. 关键裁定：MCP 先行，能力层建一次双客户端复用

"用 MCP，还是把 AI 直接集成进编辑器？"——**这不是二选一，两者不在同一层。**

- **MCP 模式** = 编辑器只当"工具提供方"，LLM 活在外面（Qoder/Claude Code）。编辑器不含大模型。
- **直接集成** = 编辑器内做 Assistant 面板，自己调 LLM API、自己驱动动作（像 Unity 内置 Assistant）。

**核心认知**：只要把"能力面（typed command → tool）"这一层建一次，两种交付方式都复用它。
MCP 只是传输层，内置面板不过是同一套 tool 的另一个客户端。

| 维度 | MCP 模式 | 直接集成 |
|---|---|---|
| 模型绑定 | 无关，任意客户端 | 需自建 Provider 抽象（易锁厂商） |
| 开发量 | 小（协议面窄） | 大（LLM 客户端+流式 UI+上下文+密钥/成本） |
| 可测/进门 | **可确定性回放**，LLM 在环外 | LLM 在环内 → CI flaky、吃 token，难进门 |
| UX | 有摩擦（外部客户端、切窗口） | 丝滑（编辑器内聊天、拖实体入 prompt） |
| 维护成本 | 低 | 高（模型/UI 长期自养） |

**裁定：MCP 先行（P1/P2 建能力层），内置面板（P3）作为同层薄客户端后加，返工近零。**
只有当目标用户是不会跑 Claude Code 的非技术策划、或要做带品牌的成品特性时，才把内置面板提到首要交付——
但即便如此，它仍坐落在这同一套 tool 层之上，不另起炉灶。

> **2026-10-22 更新**：P3 已按用户要求重开并交付（§9、§12.4）。实现验证了上述判断——面板没有
> 改动工具层，只新增 Provider 适配与 UI，写路径与外部 MCP 客户端完全相同。

## 5. RustLua 的适配优势（现有钩子盘点）

现有架构几乎为 AI 集成预留好，绝大部分工作是"接线"而非"造轮子"：

| 现有能力 | 位置 | 在 AI 方案里的角色 |
|---|---|---|
| 类型化命令总线 `EditorCommand` → `dispatch` | `engine/crates/editor/src/command_router.rs:37` | AI 的**写动作面**——每个 tool 落一条 typed command，受架构棘轮测试约束 |
| 事务 + 撤销 + 补丁历史 | `src/actions/`、`src/history.rs`、`src/patch_history.rs` | AI 每个动作**可回滚、可审计** |
| 插件系统 `EditorPlugin`/`PluginRegistry`（panic 隔离、版本校验） | `rustlua-infra/src/editor_plugins.rs:7` | 曾评估为 AI 桥挂载点；M75 实际未用（接口无逐帧钩子），见 §6/§11 |
| Lua 运行时 `LuaRuntime::eval_json`（求值 Lua 返回 JSON） | `rustlua-scripting/src/script/mod.rs:738` | AI 的**运行时读/探针面** |
| API 面快照门 `lua_api_surface.json` + 运行时探针 | `rustlua-scripting/src/api_surface_snapshot/` | 喂 LLM 的 **ground-truth API 契约**，可确定性校验 |
| 自动生成的 Lua API 文档桩 | `scripts/docgen/gen-lua-api-docs.js` → `engine::lua_api::*` | 作为 **MCP resources** 注入，压制幻觉（见 [docs/61](61-rustdoc站点发布与lua_api文档桩.md)） |
| 组件注册表 `COMPONENT_REGISTRY: &[ComponentDescriptor{name,category}]` | `engine/crates/editor/src/panels/inspector.rs:57` | `add_component` 取值域 + `list_components` tool |
| schema 驱动字段编辑 | `src/panels/schema_inspector.rs` + `rustlua-ecs/src/component_schema.rs` | `get_inspector_schema` 的字段级 ground-truth |
| 人类可读场景格式 `.scene`（packed text） | `rustlua-scene/src/scene.rs`（见 [docs/16](16-scene-format.md)） | AI 可读可写的场景文本 |

| 只读 Lua 探针面板 | `src/panels/runtime_debug.rs` | 运行时调试 tool 的原型 |
| 门文化 verify.ps1 / MVP / 黄金对账 | `scripts/verify/verify.ps1`（见 [docs/34](34-质量门与发布清单.md)） | AI tool 面可像 `lua_api_surface` 一样被快照门锁死 |

## 6. 总体架构（分层，单一能力层 + 双客户端）

```
┌── 交付层（clients，只说自然语言/调 tool，绝不含引擎逻辑）────────────────┐
│  外部 MCP 客户端                        内置 Assistant 面板 (P3)         │
│  Qoder / Claude Code / Cursor           egui dock tab                    │
│  （已有，当天可连）                      ← 本身就是"进程内 MCP 客户端"     │
└───────────▲───────────────────────────────────────▲─────────────────────┘
    MCP stdio/本地TCP                        进程内直连(同一 registry)
┌───────────┴───────────────────────────────────────┴─────────────────────┐
│  传输层  MCP Server (rmcp / JSON-RPC 2.0)  —— 仅翻译意图，不含业务         │
├──────────────────────────────────────────────────────────────────────────┤
│  ★能力层（地基，只建一次，两种交付共用）  crate: rustlua-editor-ai          │
│    • Tool Registry:  读tool / 写tool / 运行时探针tool                     │
│    • Resource Provider: lua_api_surface + doc桩 / scene schema / project  │
│    • 确认·事务网关:  写动作一律 confirm → transaction（对两客户端同等生效） │
│    • AiBridge: EditorApp 直接持有（主线程 pump；宿主调用 catch_unwind 隔离）│
├───────────────────────────────┬──────────────────────────────────────────┤
│  引擎执行层（已存在，直接接线）                                             │
│   command_router               │  LuaRuntime                              │
│   typed EditorCommand          │  eval_json (受 ScriptGuard 预算/沙箱)     │
│   + transaction/undo           │  + api_surface 探针                       │
│   + patch_history (逐字段审计)  │  + gui_evidence (让 AI "看见")            │
└───────────────────────────────┴──────────────────────────────────────────┘
   门: ai_tool_surface.json 快照门(先红后刷)  +  确定性回放门(LLM 剥离到环外)
   feature gate: 仅 editor 原生构建启用，永不进 wasm/game/微信包
```

**三条设计红线**：
1. **协议归协议、引擎归引擎、AI 归 AI**：MCP server 只翻译意图，不塞业务；引擎侧不理解自然语言。
2. **写动作一律经 `EditorCommand` + 事务 + 撤销**：AI 绝不直接改 `ProjectDocument`，受既有架构棘轮测试保护。
3. **人在回路**：所有写 tool 默认需编辑器内确认（可配置自动批处理白名单）。

| `list_components` | `COMPONENT_REGISTRY`（`inspector.rs:57`），类别 Spatial/Gameplay/Rendering/ThreeD/Ui | `add_component` 取值域 + LLM 上下文 |
| `get_inspector_schema` | `schema_inspector.rs` + `rustlua-ecs/component_schema.rs` | 字段级编辑的 ground-truth |
| `get_scene_tree` | `SceneTreeState` / `.scene` | 场景层级 |
| `get_selection` | `SelectionModel`（唯一事实源） | 选区相对命令的前置校验 |
| `read_console` | `console` LogSink | 复刻 Unity"解控制台错误" |
| `list_lua_api` / `get_lua_api` | `lua_api_surface.json` + 生成文档桩 | LLM 的 API 真签名 |
| `eval_lua_readonly` | `LuaRuntime::eval_json`（`mod.rs:738`），受 `ScriptGuard` 预算约束 | 运行时结构化探针 |
| `capture_screenshot` | `gui_evidence.rs` | 让 AI"看见"编辑器（无真实窗口时返回 `Unavailable`）|
| `get_project_config` | `project.toml` + 工程根 | 读取工程配置 |

### 7.4 扫描结论

- **33 命令 → 23 写 tool + 1 个 Lua 闭环写入口（`write_lua_script`）+ 10 读 tool = 34 个**，
  量级与 Unity-MCP（47）相当（对方多覆盖 assets/build/test）。
- **AI 友好度已很高**：多数命令显式携带 `entity`/`name`（`RenameSelection`、`AddComponent`、`SetComponentField`），
  不偷读面板缓冲——接线成本低。
- **4 个必须处理的坑**：① `NewScene` 清 Undo 栈；② `OpenDocument` 脏文档挂起（无头会 pend）；
  ③ 4 个**选区相对**命令（Duplicate/Delete/Reparent/OnSelection）对 AI 脆弱，建议显式 `entities[]` 化；
  ④ `AddCollider3d` 依赖 Inspector 缓冲、`PasteComponents` 依赖剪贴板——**无头不可用**，不暴露或改走通用命令。
- **2 个跨文件副作用**（`SavePrefabToSource`、`UnpackPrefab`）定 T2，永远确认。

## 8. 安全、可审计与确定性（门集成）

这是让方案"能进门"而非"能跑就行"的关键，贴合既有门纪律：

1. **tool 面快照门**：新增 `ai_tool_surface.json`，仿 `lua_api_surface` 的探针+diff 机制。tool 契约漂移
   （新增/删除/改签名）必须先红后刷，防止 LLM 依赖的接口静默变更。
2. **确定性回放门**：把 AI 一次 tool 调用序列录成 fixture（命令 + 期望 patch），CI 里**无 LLM 重放**，
   只验引擎侧执行确定性。AI 功能因此能进 `verify.ps1` 且不吃 token、不 flaky。
3. **`eval_lua` 护栏**：复用现有 `ScriptGuard`（回调预算、错误策略，见
   [docs/64 Lua 脚本错误处置策略](64-Lua脚本错误处置策略.md)）；默认只读；写需确认；超时/死循环熔断。
4. **撤销即安全网**：所有写动作进 `edit_transaction`，一键 `undo`；`patch_history` 提供逐字段审计。
5. **隐私/成本**：LLM Provider 抽象支持本地（Ollama）优先；上下文注入前脱敏；不上传 `.env`/密钥。
6. **feature gate 隔离**：`rustlua-editor-ai` 及可选依赖仅 editor 原生构建启用，
   **绝不进 wasm/game/微信包**（体积与真机兼容零关联）。

## 10. 关键技术选型与风险

- **MCP SDK**：**已裁定自实现最小 JSON-RPC 2.0（stdio），不引 `rmcp`**（2026-10-22）。协议面只覆盖
  `initialize` / `tools/list` / `tools/call` / `resources/list` / `resources/read` / `ping` 与
  notification，依赖只有 `serde`/`serde_json`；editor 增量构建与离线 vendored 生态零新增负担。
  stdio 纯度由"`--mcp-stdio` 时日志改走 stderr"保证。真实进程 smoke 见 M75-00 §11。
- **不做的事**：不自造 AI 协议、不绑单一 LLM 厂商、P1–P4 不碰运行时推理、不让 AI 绕过 typed command 直改文档。
- **主要风险与压制**：
  1. LLM 生成 Lua 幻觉 API → resources 注入真签名 + API 面探针 + `eval_json` 校验，三重压制。
  2. wasm/微信体积污染 → feature gate 硬隔离，AI crate 永不进发布包。
  3. tool 契约漂移 → `ai_tool_surface.json` 快照门。
  4. 非确定性难进 CI → 回放 fixture 把"LLM 环节"从门里剥离。
  5. 自实现协议的兼容性风险 → 真实 MCP 进程 smoke + 快照门兜底；只追稳定协议面，不追新版本特性。

## 11. 与现有工程纪律的契合

- **架构棘轮测试**（`src/panels/architecture_tests.rs`，"面板只发类型化动作"）天然覆盖 AI：AI 只发
  `EditorCommand`，与面板同源，不需要为 AI 开特例。
- **崩溃隔离**：桥接层对每次宿主调用做 `catch_unwind`，tool panic 变成带 `panic：…` 的 tool error，
  不穿透 UI 线程。**未用 `EditorPlugin`/`PluginRegistry`**：现有插件接口只有 `on_load`/`on_unload`，
  没有逐帧钩子也没有宿主访问，承载不了"每帧 pump + 主线程执行"的桥；因此 `AiBridge` 由 `EditorApp`
  直接持有。若未来插件接口扩展逐帧钩子，再评估迁移。
- **门文化**：`ai_tool_surface.json` 快照门与确定性回放门按 `lua_api_surface` / 黄金对账的"先红后刷"范式接入
  `verify.ps1`（见 [docs/34](34-质量门与发布清单.md)、[docs/70](70-性能与测试度量.md)）。
- **文档门**：本文与新计划文件受 `scripts/verify/check-docs.ps1` 约束（编号唯一、单 H1、索引可达、链接可解析）。

## 12. 已裁定项（2026-10-22 回写）

1. **MCP SDK 选型 → 自实现最小 JSON-RPC 2.0（stdio）**。协议面窄（initialize/tools/resources/ping），
   自实现只依赖 `serde`/`serde_json`，不新增 editor 增量构建负担，也不碰离线 vendored 生态；
   `rmcp` 的协议新特性暂不需要。详见 §10 与 M75-00 §11 的真实进程 smoke。
2. **选区相对命令显式化 → P2 内联完成**（不改 `EditorCommand` 本身，在 tool 层加显式入口）：
   `delete_entity` 强制 `entities[]`；`set_component_fields` 用 `entities[]`（缺省才回落选区）；
   `duplicate_entity` 可给 `entity`；`reparent_entity` 强制 `entity`。AI 不再依赖"先改选区"的隐式前置。
3. **自动批处理默认边界 → 默认全部确认**。`GatePolicy::interactive(auto_t1)` 默认 `false`；
   editor 内确认窗可勾选"自动批准 T1"；无头 `HEADLESS` 自动放行 T1、对 T2/T3 返回
   `NeedsConfirmation` 错误而不是等待（不会挂死）。白名单暂不按 tool 名细化——先保证可审计。
4. **内置面板（P3）→ 原裁定不立项，同日按用户要求重开并交付（2026-10-22）**。原裁定的理由仍成立：
   面板要自建聊天/Provider/密钥管理，成本集中在这一层。用户明确要求内置助手后，实现严格按原基线
   落地——`DockTab::Assistant` 作为同一 registry 的薄客户端，写动作仍走 `execute_tool` +
   `EditorAiHost`，没有第二套写路径；Provider 支持 OpenAI 兼容 / Anthropic / 本地 Ollama，密钥只存
   内存、不落布局/日志/模型上下文；GUI 证据与 egui 几何门均已纳入新面板（读数见 M75-00 §11.4）。
   面板默认与属性同标签组（属性保持活动），可从 View 菜单隐藏/恢复。
5. **Track B（运行时推理）→ 不立项**。体积、wasm/微信宿主与产品需求三项均未过门，详见 §3.1；
   重开触发条件写在该节。
