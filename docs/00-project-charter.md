## 1. 项目定位

本项目是一套面向独立开发者的游戏引擎，核心使用 Rust，游戏玩法使用 Lua，优先支持 Windows 桌面平台，先完成 2D 能力，再逐步扩展轻量 3D。

项目采用 AI 驱动开发模式：AI 负责调研、设计、编码、测试、文档和问题排查；项目负责人负责产品方向、范围决策、视觉结果和里程碑最终验收。

## 2. 第一阶段目标

- Windows 桌面运行能力；
- Rust 运行时核心；
- Lua 游戏脚本执行和错误报告；
- 2D 渲染、精灵、摄像机和基础输入；
- 场景保存/加载；
- 资源导入和基础缓存；
- 编辑器 MVP；
- 可运行的 2D 样板游戏；
- Debug 和 Release 构建及发布流程。

## 3. 成功标准

1. 能创建、编辑、保存和运行场景；
2. Lua 能实现玩家、敌人、UI、任务和存档逻辑；
3. 原始资源可以被导入、缓存并打包；
4. 常见错误可以通过日志、调用栈和测试定位；
5. 有明确的性能基线和回归测试；
6. 第一款样板游戏可以在 Release 版本中完整玩通。

## 4. 产品范围

### 4.1 当前版本包含

- Rapier 物理适配；

## 5. 技术基线

```text
语言：Rust stable
脚本：Lua 5.4，通过 mlua 接入
图形：wgpu
窗口/输入：winit 或 SDL3，最终以技术决策记录为准
ECS：bevy_ecs、hecs 或最小自研实现，需通过基准测试决定
物理：Rapier
编辑器 UI：egui 起步
资源/场景序列化：Serde + RON/JSON，发布资源可使用二进制缓存
模型：GLTF/GLB
音频：Kira 或 rodio
日志：tracing
性能分析：Tracy、RenderDoc 及平台工具
目标平台：Windows first
开发顺序：2D first，轻量 3D second
```

所有依赖必须锁定版本，并通过适配层接入。业务代码不得无必要地直接依赖第三方库的内部细节。

## 6. 架构原则

1. 编辑器与运行时分层；
2. 编辑器使用易用的场景/实体树，运行时使用数据导向系统；
3. 资源使用 UUID 引用，运行时对象使用带 generation 的句柄；
4. Lua 只访问稳定的命令、事件和句柄 API；
5. 不让 Lua 持有 Rust 内部可变引用；
6. 先使用成熟中间件，不重复实现物理、音频解码和模型解析；
7. 先做垂直切片，再抽象通用引擎能力；
8. 每项功能必须有测试、Demo 或可重复验收步骤；
9. 从第一天记录日志、性能和资源生命周期；
10. 任何公共格式变更必须有版本号和迁移策略。

## 7. 第一款样板游戏

默认样板游戏为俯视角 2D 动作 Roguelite，范围限制为：

- 1–3 个核心玩法；
- 一张小型地图或 10–30 个关卡；
- 至少两种敌人；
- 玩家移动、攻击、受伤、死亡；
- 拾取物、UI、音效、胜负条件和存档；
- 单机运行，不做联网；
- 所有主要玩法逻辑由 Lua 实现。

如后续变更游戏类型，必须记录技术影响和范围变化。

## 9. AI 开发规则

本章是 AI 驱动开发模式的操作规范；与它冲突的旧表述以本章为准。

### 9.1 任务生命周期

每个任务按五阶段推进，每阶段产物必须显式输出，禁止跳过"方案声明"直接动手：

| 阶段 | 输入 | 必须输出 |
|---|---|---|
| 接收/拆分 | 需求或里程碑目标 | 任务清单、影响文件、风险、验收方式 |
| 方案声明 | 上文输入 | 先报告方案、影响范围、风险与验收方式，获确认后再实现 |
| 实现 | 确认后的方案 | 最小改动 + 测试或可复现 Demo |
| 自检 | 实现产物 | fmt/clippy/test/build 全绿 |
| 验收与归档 | 自检证据 | 见 §10 验收门，并记录失败原因、已知限制、文档更新 |

### 9.2 开始前必读清单

按优先级读取：项目章程 → 当前任务文件（`tasks/plan/` 中的待做任务，或 `tasks/done/` 中的已归档任务）→ 相关能力文档（`docs/`）→ 相关技术决策（`docs/02-technical-decisions.md`）。当前阶段以 CHANGELOG 为准，不依赖章程中的历史快照。

### 9.3 AI 必须做

- 开始任务前读取 9.2 的必读清单；
- 只能从 `tasks/plan/` 认领待做任务，认领后将任务状态更新为进行中；
- 先报告方案、影响文件、风险和验收方式；
- 只修改当前任务所需范围；
- 新增或修改代码时遵守 §9.7 注释规范；
- 添加测试或可重复 Demo；
- 执行格式检查、静态检查、测试和构建；
- 记录失败原因，不隐瞒未完成项；
- 更新任务状态、文档和验收证据。

### 9.4 AI 不得擅自做

- 删除用户文件或资产；
- 更换核心技术选型；
- 大规模重写公共 API；
- 修改资源/场景格式而没有迁移方案；
- 以删除测试、降低标准或屏蔽错误的方式通过验收；
- 无说明新增 unsafe、全局可变状态或复杂并发；
- 将未验证的代码描述为已完成。

### 9.5 任务规模

单个任务建议 0.5–2 个工作日，最大不超过 5 个工作日。任务涉及多个未稳定模块时必须拆分。

### 9.6 结果上报模板

任务收尾必须用统一格式上报，不隐瞒未完成项：

```text
[状态] 目标
完成度：<已实现项>
未完成项及原因：<逐条说明，不允许留空后仍描述为"已完成">
风险 / 已知限制：<逐条说明>
验收证据：<测试/Demo/命令输出，附运行命令>
```

### 9.7 代码与注释规范

代码注释一律使用**精简的中文**：说清"为什么"与不显然的约束，不复述代码已经表达的内容。Rust 与 Lua 代码、脚本与工程配置同此要求。

- **中文书写**：注释正文用中文；代码标识符、API 名、标准库/第三方名称、`TODO`/`FIXME`/`SAFETY` 等既有标记保持原文。
- **精简优先**：单行注释优于多行段落；只写非显然的信息，逐行翻译代码的注释不要写。
- **必写处**：数值口径与设计依据、非显然的算法或状态机、与外部工具/文档/数据的一致性约束（例如 Lua 常量须与生成脚本一致这类"两处必须同步"的事实）、"为什么不能那样写"的踩坑结论、公共 API 的边界与错误语义。
- **不写处**：复述下一行代码的注释、与实现已经不符的过期注释、被注释掉的死代码（直接删除，历史交给 git）。
- **资产保护**：现有中文注释是工程的重要资产，重构、搬迁、改接口时必须随代码迁移或改写，不得顺手删除；发现过期注释应当修正而非保留错误信息。

## 10. 验收门

验收分两级，避免"每次改动都跑 release"的浪费：

**任务级验收（日常引擎/编辑器改动）**：

- 代码实现完成；
- 相关测试通过（`cargo test -p <crate>` 或全量）；
- `cargo fmt --all -- --check` 通过；
- `cargo clippy --workspace --all-targets --all-features -- -D warnings` 无新增告警；
- Debug 构建通过（日常 `cargo build -p editor` 即可，具体以改动涉及的 crate 为准）；
- Demo 或手工步骤可复现；
- 文档和已知限制已更新。

Release 构建不纳入日常验收，由负责人需要时手动执行。

**里程碑级验收**：

- 通过本地 `scripts/verify.ps1`（含全量测试与 Debug 构建；Release 由负责人手动确认）；
- 没有未解决的 P0/P1 问题；
- 回归测试通过；
- 至少一个可运行的里程碑 Demo；
- 验收证据已归档至 `tasks/done/`；
- 项目负责人确认进入下一阶段。

## 11. 问题分级

- P0：无法启动、数据损坏、发布包不可运行；
- P1：核心玩法或核心编辑流程不可用；
- P2：重要功能异常但有替代方案；
- P3：体验、性能或文档问题。

P0/P1 未解决时不得通过里程碑。
