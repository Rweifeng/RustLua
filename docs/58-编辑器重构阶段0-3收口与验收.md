### 2.2 GUI smoke：为什么是"合成输入 + 整帧"

`EditorApp::draw_frame(&egui::Context)` 从 `eframe::App::update` 里抽了出来
（`engine/crates/editor/src/main.rs`）。抽它的理由是可测性：`update` 需要真实的
`eframe::Frame`，而它无法在测试里构造，于是"整帧"在自动化里一直不可达，只能逐个面板调用。
现在合成帧能把**所有面板**按生产路径跑一遍，并且输入是真实的 `RawInput.events`
（指针按下/抬起/移动、键盘、文本），走的是与真人操作完全相同的
`Response` → 面板处理器路径。

29 个用例分组：
| 分组 | 覆盖 |
|---|---|
| `hierarchy/*` | 点击单选、Ctrl 加选、普通点击替换、Shift 范围选、空白画布拖动清空 |
| `keyboard/*` | Q/W/E/R 工具切换、Ctrl+D 复制、Delete 删除、Ctrl+Z 撤销 |
| `scene_view/*` | 真实指针拖动 = 恰好一条 Undo、拖动中不写历史、松手回到 Idle、Undo 精确还原 |
| `modal/*` | 未保存保护：挂起而非执行、跨帧保持、取消后文档与选择不变 |
| `focus/*` | **输入焦点**：点进搜索框 → 键入 Q/W/E/R 快捷键**不抢键** → 文本真的缩窄了树 |
| `dnd/*` | **拖放**：注入拖放载荷并在画布释放 → 新增实体 + 恰好一条 Undo + 新实体成为选中 |
| `dock/*` | **停靠**：收起控制台后画布真的变高、`Ctrl+Shift+L` 落盘布局、恢复后画布回到原量级 |
| `dpi/*` | 1.0/1.5/2.0 × 4 种窗口尺寸：画布矩形真实存在、行内容 ≤ 行高、层级仍虚拟化 |
| `resize/*` | 连续 resize 后选中状态不变、画布跟随新窗口 |

这九组正好覆盖 `docs/55 §8` 质量门第 3 条枚举的全部项目：**DPI、resize、拖放、停靠、
输入焦点、多选、弹窗**。

**这一层当场抓到三个真实缺陷**（都已修，且都由用例钉住）：

1. **小尺寸精灵拖不动**：`egui` 的 `drag_started` 在指针已经移出点击阈值那一帧才置位，而
   命中测试用的是**移动之后**的位置。设计分辨率缩放到画布后一个 32×32 的精灵只有约 11 点宽，
   "按在中心拖 12 点"就会落到包围框之外——表现是"抓着精灵拖，结果变成了框选"。
   修法：拖动起点改用 `press_origin`（`scene_view.rs::drag_start_pos`）。
2. **中心把手无法命中**：Gizmo 命中改成"点到线段距离"之后，三条臂都从锚点出发，
   24×24 的中心区域必然同时落在所有臂上，于是"自由拖动"和"锁定实体不响应"两条语义都失效。
   修法：中心把手优先判定（`gizmo.rs::pick_gizmo_axis`）。
3. **拖放创建的实体没有成为选中**：其余创建入口（层级面板 `+`、`Ctrl+D`、Inspector 添加组件）
   都会把新实体设为选中，只有"把资源拖进 Scene 视图"这条路径漏了——拖完资源 Inspector 还停在
   旧对象上，得再去层级面板点一次。修法：`scene_ops.rs::spawn_sprite_from_drop` 提交后
   `selection.set_single` + `sync_inspector`，并给出状态栏提示。

| 报告 | `summary.txt`（含每张图的实测 DPI、非黑像素比例、进程工作集、面板/命令耗时）+ `manifest.json` |

**两条自证约束**（避免"标签与内容不一致的证据"）：

* **实测 DPI 必须等于请求 DPI**。第一版只记请求值，结果 200% 那一档的图其实是 150% 渲染的
  （`InnerSize` 由 eframe 按**当时**的 `pixels_per_point` 换算成物理像素，而 DPI 覆盖要到下一次
  pass 才生效）。现在报告同时记 `req_ppi` 与 `act_ppi`，不一致直接判失败。
* **图不能是黑的**：每张图都算非黑像素比例，低于 0.2 判失败。

采集前还有一段**准备阶段**：打开默认场景 + 等启动资源导入跑完（首帧之后才发起导入，
所以退出条件除"空闲"外还要求至少 45 帧）。第一版没等，归档的是"导入资源 86%"的弹窗盖住工作台，
而不是编辑器界面。

### 2.4 长会话与 Play/Stop

`RUSTLUA_EDITOR_SOAK=<秒>` 打开真实窗口 soak：循环 Play（默认 2 秒）/ Stop + 定时采样
（工作集、**egui 纹理账**、帧数、实体数、历史深度、日志行数），每 12 个采样增量落盘一次
（中途快照带 `complete=false`，长档被外部打断也留下可分析数据），结束时写 `soak.txt` / `soak.json`。
M27-03 起再加三个开关，把"被测那期改动的路径"塞进每一轮：
`_CHURN_SECONDS`（每轮间隔，走 `dock::churn` 真重排树）、`_DROP_EVERY`（每几轮做一次外部文件拖放导入，
默认每轮）、`_DROP_SOURCE`（拖放源文件；不填则在**工程外**自动找一个纹理）。导入的实体会立刻 Undo、
入库副本在下一轮开头删除，于是重复 200 遍的是**同一份工作**而不是"越来越大的资产目录"。
报告头与 `soak.json` 带 `rounds / dock_churns / drop_imports / drop_cleanups / skipped`，
**`skipped>0` 表示有轮次在空转**（Play 锁定或树被表面借走），不能读成"重排过这么多遍"。
判定仍然只由 `scripts/analyze-soak.ps1` 给（它自己现在有 `scripts/test-analyze-soak.ps1` 兜底，

#### 判据：看**谷值趋势**，不看均值差

第一版的报告只给"首尾各 10% 采样的均值差"，这在一个真实的长会话里是**会误导**的：
进程工作集是锯齿状的（缓存涨落、分配器保留页、Windows 主动 trim working set），
均值差 100% 取决于取到锯齿的哪一相位。30 分钟那一档就同时出现了
"均值 -258 MiB"与"谷值 +55 MiB"两个相反的结论。

现在报告与复算脚本都给三样东西：

1. 整段按时长切 8 段的 **min / p50 / max**；
2. **谷值趋势**：预热之后（后半段窗口）首末谷值之差；
3. **幅度**：窗口内 max−min，用来判断"谷值差"是不是被噪声淹没。

复算脚本 `scripts/analyze-soak.ps1 -Path <soak.json> [-Windows N]` 直接读归档 JSON，
因此任何一次 soak 都能事后按同一口径重算（含把它切成更多窗口）。判据是
`tail_growth > max(15% × 后半段首谷值, 10 MiB)`，否则输出 `soak_verdict=no_sustained_growth`。

> 脚本的第一版判据**当场误报过**：它拿"第一个窗口的谷值"当基准，而那个窗口还包含启动预热
> （加载工程 + 导入 706 个资源 + 建字体图集），于是 30 分钟那一档被算成 `+54.9 MiB`
> 的"持续增长"。现在基准只取**后半段**，同一份数据变成 `+4.7 MiB`（阈值 37 MiB）
> → `no_sustained_growth`。**自动化判据里把启动成本算进增长，是这份报告最容易犯的错。**

**30 分钟那一档的实测**（`playstop-30min/`）：

* 1800 秒 / **128,573 帧** / **178 次 Play-Stop 循环** / 346 个采样；
* 帧耗时 p50 5.21 ms、p95 7.54 ms、p99 8.44 ms；全程超过 16.7 ms 预算的帧 **207 个（0.16%）**；
* 工作集：0-460 秒 498→510 MiB（Play 预热 + 资源导入 + 字体图集），460-672 秒回落到 243 MiB；
* **预热后谷值 +4.7 MiB**（窗口 5→8：246.6 → 251.2 MiB），窗口内幅度最大 45 MiB
  —— 即"锯齿存在、谷值不动"，判为 `no_sustained_growth`；
* 控制台行数稳定停在 **500**（`LogSink` 上限），实体数恒为 17，历史深度恒为 0。

**8 小时那一档**：**按用户决定暂缓**（本轮不等待跑满），命令与复算口径见 §9。

#### 两次长档中途失败的真实原因（必须写清楚，否则会被误读）

我在等待期**同时**跑了两档长 soak（8 小时档 + 90 分钟"归因档"）做对照——这个设置本身是错的：

| 观察 | 数据 |
|---|---|
| 两个进程都在启动后 ~6-13 分钟开始工作集暴涨 | 8 小时档 2806 s 到 **2240 MiB**；归因档 366 s 到 **1808 MiB**、最后一窗峰值 **2561 MiB** |
| 两个进程随后都退出 | 归因档 `exit=101`（Rust panic）；8 小时档窗口被关闭（`exit=0`，报告为 `complete=false` 中途快照） |
| 崩溃现场（`_bin/crash.log`） | `Failed to create staging buffer for index data … Required 80724. Actual size 147408` @ `egui-wgpu-0.33.3/src/renderer.rs:958`；紧邻的日志是 `WARN egui_wgpu: Dropped frame with error: Acquiring a texture failed with a generic error` |
| **egui 纹理账**（本轮新加的量尺） | 整段恒为 **1 个纹理 / 1.0 MiB**——**排除**"egui 管理的纹理在涨" |
| 单实例对照 | 30 分钟档（178 次 Play/Stop，无并发）谷值 +4.7 MiB，判为 `no_sustained_growth` |

综合起来：Play/Stop 每轮会重新加载约 10 MB 贴图（`title_bg_pixel` 1280×720、`ui_menu_vignette`
1280×720 等），**两个编辑器同时这样churn** 会把 2 GB 显存（GT 1030）压到边界；WDDM 在显存不足时
会把 GPU 分配回退到系统内存，于是**进程工作集暴涨**，随后某次分配失败
（`Acquiring a texture failed`），egui-wgpu 在 staging buffer 拿不到时**直接 panic**，编辑器随之退出。

因此正确的结论是两句话：

1. **单实例长会话在现有证据（30 分钟）里没有持续增长**；两次失败来自我自己的并发设置，
   不能读成"编辑器跑 49 分钟必崩"；
2. 但它确实暴露一个**真实的健壮性缺口**：**GPU 分配失败会以 panic 收场**（egui-wgpu 上游行为，
   我们没有兜底），这与计划 §8 质量门里"GPU 实机：设备丢失或初始化失败"那条相关，
   已登记进 §9。**离线/自包含**的依赖策略下无法就地给 egui-wgpu 打补丁，
   可行的做法是后续把"GPU 失败"纳入会话级诊断并在 panic 前落盘现场。

## 3. 服务依赖图（`docs/55 §4` 逐点对照）

```text
EditorShell（main.rs: EditorApp）
  -> CommandRouter / Shortcut / Layout / Notification
       command_router.rs（dispatch 唯一编排点）
       menu.rs / panels/toolbar.rs（快捷键与菜单只发 typed action）
       layout.rs（可保存布局 + 容错加载 + 100 次往返门）
  -> WorkspaceController
       DocumentService        services.rs::WorkspaceService + document.rs
       SelectionService       services.rs::SelectionService（选择唯一事实源）
       CommandService/History services.rs::CommandService + history.rs（预算 200）
       AssetService/ImportJob resource_refresh.rs（worker + 代际）、import.rs、file_watcher.rs
       SceneViewController    panels/scene_view.rs + scene_drag.rs + scene_ops.rs + gizmo.rs
       InspectorRegistry      panels/schema_inspector.rs + schema_fields.rs（schema 驱动）
       PlayController         play_control.rs + preview_session.rs
       DiagnosticsService     services.rs::DiagnosticBuffer + diagnostics.rs
       Profiler               profiler.rs（有界采样 + 百分位 + 计数器/gauge）
       BuildService           publish.rs + panels/publish.rs + assetc
  -> Infrastructure
       Scene/Prefab Serializer scene.rs / prefab.rs（文本确定性 + 原子保存）
       ResourceDatabase/Watcher resource_db.rs（稳定 AssetId）+ file_watcher.rs
       RuntimeScene/Renderer   engine::host
       Lua Runtime             script.rs
```

边界规则的落实方式（`docs/55 §4.1`）：

| 规则 | 落实与守卫 |
|---|---|
| View 只发 typed action | `panels/architecture_tests.rs` 源级棘轮：`panels/` 下所有文件的直接写入计数为 **0**，新增一处即判红 |
| 持久修改经 Command/Serializer | `EditorApp::dispatch` 是唯一编排点；`scene_drag.rs` / `hierarchy_ops.rs` / `scene_ops.rs` 承载提交边界 |
| Selection 单一事实源 | `EditorApp.selection: SelectionService`；面板不再保留第二套业务选择 |
| PreviewService 独占运行时/GPU/字体 | `preview_session.rs`（readback slot 有界，指标可读） |
| 后台任务只返回不可变结果 | `resource_refresh.rs::RefreshResult` + `RefreshPoll::{Pending,Stale,Ready}` |
| 稳定 ID，路径只作展示/边界 | `resource_db::AssetId`（`from_seed` 确定性）+ 实体 ID 不随重命名变化 |
| 每个服务有取消/失败/恢复/telemetry 契约 | `CancellationToken`、`JobReport`、`DiagnosticBuffer`、`EditorProfiler` |

### 5.1 patch 原型：把"历史内存不可控"从论断变成数字

`docs/55 §1` 的来源清单第 4 条是：**"Undo 主要保存完整文档快照，大场景和长编辑会话的内存成本
不可控"**。阶段 1 的"历史内存预算"只给了上界（200 条，超出丢最旧并计数）——上界有了，
但每条历史的成本仍然是 O(文档)。

`patch_history.rs` 是 ER-03 要求的**原型**（不是替代品，生产历史仍是 `CommandService`）：
把一次编辑表达成补丁（`FieldChange::{Component, Name}`，带 before/after），
undo/redo 只回放补丁而不克隆文档。范围写清楚：**只覆盖字段级编辑**
（Inspector 改字段、批量改属性、重命名——长会话里占比最高的操作）；
**不覆盖**结构变更（新建/删除/换父），那些需要单独的补丁形态，原型不假装支持。

`--perf-baseline` 的 `patch_history_memory_1k_edits` 场景给出实测（1,000 实体场景、1,000 次字段编辑）：

| 指标 | 值 |
|---|---|
| 单份文档序列化 | 198,945 字节（约 194 KiB） |
| 补丁历史保留 | 216,000 字节（1,000 条，约 211 KiB） |
| 快照历史保留（下界：每条 before+after） | 397,890,000 字节（约 379 MiB） |
| **比值** | **0.054%（约 1,840×）** |
| 单条补丁 p95 | 0.005 ms |
| 应用后文档逐字节相同 / 全部撤销回起点 / 全部重做回终态 | **三项全部成立** |

最后一行才是这条原型的意义所在：`docs/55 §8` 的硬门槛里"Undo 不等价"是**直接阻断**项，
所以"省内存"必须在等价性成立的前提下才有讨论价值。等价性由两条路径跑**同一串编辑**、
逐字节比较文档文本来证明，不是"看起来差不多"。

> 第一版这条场景判红过一次：预算设成 200 而编辑有 1,000 次，两条历史各丢了 800 条，
> 于是谁都撤不回起点——`undo_equivalent=false`。那是在测预算，不是在测补丁。
> 预算上限现在分别由 `history_budget_500_edits`（快照）与
> `patch_history::tests::adjacent_transforms_merge_and_budget_drops_the_oldest`（补丁）钉住。

### 6.1 本轮补齐的两处缺口

**① 3D Gizmo 多选。** 过去手柄只作用于"首个选中实体"（`selected_entity = entities3d.iter().find(...)`），
多选之后拖拽只动一个；`commit_gizmo_drag3d` 也只取 `preview` 的第一条。现在：

* 拖拽目标 = 整个选中集合（锁定实体排除，全锁则不给拖拽集合，不制造空 Undo）；
* 锚点：`Pivot` 模式 = 主实体原点，`Center` 模式 = **选中集合并集包围盒中心**；

* 提交时**整批**世界→局部反解，任何一个反解失败就整批拒绝（写一半会让"多选拖拽"变成
  "部分实体留在原地"的静默错误）。

**② 精确命中。** 命中从"点到端点圆"改为"点到线段距离"，并把中心把手提到最前判定。
这样"看到一整条臂就能抓整条臂"，同时中心区域仍然是自由拖动/原地旋转的把手。
旋转手柄画的是**整圈**（半径 = 臂长），判定于是也覆盖整圈
（`rotation_ring_is_grabbable_all_around`）——"画了一整圈、只有一点能抓"和"臂只能抓端点"
是同一类问题。

### 7.3 本轮补齐：外部改动不再被静默覆盖

`docs/55 §8` 把"**数据损坏**"列为直接阻断项，而"保存时静默覆盖外部改动"正是最典型的一类
数据损坏路径：`scenes/` 与 `scripts/` 本来就是外部工具会写的目录（生成器、git checkout、
另一个编辑器），`file_watcher.rs` 的模块注释里就写明这一点——但保存路径过去是**无条件覆盖**，
用户的 Ctrl+S 会悄悄吃掉别人的改动，**且没有任何提示**。

现在：

* `SceneDocument.disk_signature: Option<FileSignature>`：加载成功、保存成功后各记一次
  （长度 + mtime，与观察器同一套判据，**不读内容**），不参与 `PartialEq`（磁盘状态不是文档内容，
  与 `revision` 同理），因此不会干扰历史的 no-op 判定；
* `SceneDocument::disk_status() -> DiskStatus::{Untracked, Unchanged, Modified, Removed}`：
  未命名/无基准（崩溃恢复出来的文档）恒为 `Untracked`——**宁可保守放行，也不要在没有基准时
  把用户挡在门外**；
* `EditorApp::save_scene()` 在 `Modified`/`Removed` 时**拒绝写入**并给出可执行的下一步
  （状态栏 + Scene View 诊断 + 控制台提示），文档保持 dirty，`false` 返回值沿用 E06
  「保存并继续」的既有语义（停留在当前文档）；
* 显式出口 `save_scene_force()` + 菜单「强制保存（覆盖外部修改）」，用户不会被卡死；
* 观察器一旦发现外部改动**命中当前打开的文档**就立刻提示（不必等到按 Ctrl+S 才知道）。

由 `actions::tests::save_refuses_to_overwrite_an_externally_modified_scene` 钉住五个环节：
干净状态保存必须成功（不制造假冲突）→ 外部写入被识别为 `Modified` → 普通保存被拒绝
**且磁盘内容原样保留**（关键：拒绝不是提示，而是不写）→ 强制保存真的覆盖 →
覆盖后签名刷新，再保存不再报冲突（否则用户会陷在"永远冲突"里）。
`unnamed_document_never_reports_a_disk_conflict` 钉住未命名文档不被误判。

### 7.5 本轮补齐：Prefab 往返 hash 门

`--perf-baseline` 新增场景 `prefab_roundtrip_hash`，把验收条款拆成四个可判定的不变量：

1. `to_text` → `from_text` → `to_text` **逐字节相同**（序列化定点，不会每次多/少一个字段）；
2. 写盘 → 读回 → 再写盘的字节与首次相同（磁盘往返不引入漂移）；
3. 实例化 → 落盘场景 → 重新打开之后，实例上的**逐字段覆盖**逐字保持
   （`Quad.size` 读回 `99.000000,88.000000`）；
4. 把"实例 vs 源 Prefab"重新 diff 出来的覆盖集合与写入前完全相同（幂等，不会越用越多）。

这条门**当场抓到过一个错误**：第一版先做了一次无覆盖的 `instantiate`，再带覆盖做第二次，
于是场景里有两个同名实例，断言取到的是没被覆盖的那个——正是"用名字找实例"这类脆弱写法的典型
翻车方式（现在按 `source_to_instance` 映射取实体）。

   egui-wgpu 在 `Queue::write_buffer_with` 返回 `None` 时直接 panic（上游行为），
   编辑器随之退出，**没有降级、没有把现场落到崩溃日志之外的诊断里**。
   计划 §8 的 GPU 实机门里"设备丢失或初始化失败"正是这一类；仓库的离线自包含策略下
   无法就地给 egui-wgpu 打补丁，因此本轮只登记现状与复现方式，
   后续做法应是"把 GPU 失败纳入会话级诊断 + 退出前落盘现场"。
3. **GUI smoke 是合成帧，不是真实窗口的自动化**：它没有 GPU 后备缓冲，也没有真实窗口的重绘节奏。
   真实窗口那一半靠 `--gui-evidence` 的截图与 soak 数字，但目前**还是脚本化的采样式验证**，
   不是"点击真实窗口并断言"的端到端自动化（无头浏览器 / UI 自动化框架不在本仓库依赖里）。
4. **DPI 覆盖是 egui 层的 `pixels_per_point`，不是改操作系统缩放**：几何等价（点空间布局相同、
   物理像素按倍数放大），但字体光栅化细节与系统级缩放仍有差异。
5. **停靠布局是轻量版**：可保存/恢复/重置的是面板宽度、可见性、工作台标签、视图模式、工具、
   Gizmo 空间与轴心、缩放、预览分辨率、密度。**不是**可任意拖拽重排的商业引擎停靠系统
   ——计划 §2.2 明确"不用自研 Docking 替代成熟库"。
6. **外部 `.scene` 的改动不再被静默覆盖**（§7.3），但**仍没有三向比较/合并对话框**：
   编辑器现在是"拒绝 + 提示 + 显式强制覆盖"，不是"把外部版本与内存版本合起来看"。
   真要做合并，需要一方为基准的三方 diff，属于独立一轮。
7. **诊断跳转没有内置源码查看器**：能解析 `路径:行号` 并做三级降级跳转，
   但仍需外部编辑器打开源码行。
8. **Undo 仍是快照历史 + 内存预算**：`patch_history.rs` 已把 ER-03 要的**原型**做出来并给出
   实测（0.054% / Undo 等价，见 §5.1），但**生产路径仍是快照历史**——把 `CommandService`
   切到补丁需要对全部 `history.execute` 调用点改成"声明补丁"，且要先解决结构变更
   （新建/删除/换父）的补丁形态，属于独立一轮，本轮不假装完成。
9. **Prefab 嵌套展开与 Variant 未做**：计划把"完整 Prefab 变体"排在阶段 3 之后且要求
   "前三项稳定前不启动"，本轮遵守该次序；嵌套只有检测与拒绝，没有运行时展开。
10. **Gizmo 旋转手柄没有"点到圆环"的解析判定，但已按整圈命中**：判定用"到中心的距离 ≈ 臂长"
    近似整圈（`rotation_ring_is_grabbable_all_around`），足够"看到哪里点哪里"；
    仍是近似（没有考虑圆环在透视下退化成椭圆的情形）。
11. **Widget 模式的工具只到"选择/移动"**：完整 Widget Designer（阶段 4）未启动。
