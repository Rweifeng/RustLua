本文把前期架构、性能、包体、跨平台和易用性分析整理成一份可执行的治理总方案，但不是产品实现提交，也不是新的技术决策记录。

## 2. 先校正分析口径

### 2.1 事实、推断和建议分开

| 类型 | 写法 | 证据要求 |

| 已有事实 | 已有、当前代码实现、当前产物显示 | 路径、符号或可复现命令；工作树状态须注明 |

工作树、已提交内容、构建产物和运行期读数是四个不同层次。文档引用某一层时必须注明层次，不能用工作树中的未跟踪文件证明已入库，也不能用历史产物证明当前产物。

### 2.2 性能基线不是从零建立

项目已经有 WP0 基准、统一统计字段和每帧分配入口，覆盖场景装载、typed 编译、运行时帧和部分渲染工作负载。后续工作不是再建一套平行量具，而是：

1. 复测既有基线，确认命令和当前代码仍能运行；
2. 补齐端到端、冷启动、跨宿主和真实发布产物维度；
3. 将观测开销与被测工作负载分开；
4. 在基线批准后再讨论预算和质量门。

### 2.3 当前包体数只代表本次目录快照

2026-10-16 对现存目录做了只读字节统计。口径是递归文件 `stat().st_size` 之和，不是磁盘簇、网络传输量、解压后内存或微信平台最终计费量：

| 目录 | 文件数 | 总字节 | 字体字节 | `game_web_bg.wasm` |
|---|---:|---:|---:|---:|
| `examples/game_jhyt/builds/webgl` | 1,381 | 28,687,444 | 18,061,608 | 5,436,214 |
| `examples/game_jhyt/builds/wechat-minigame/launcher` | 1,387 | 11,101,589 | 288,364 | 5,441,803 |

微信目录按 `game.json` 的分包根计算，主包为总量减分包：主包 2,347,320 字节，分包 8,754,269 字节。WebGL 字体中，`NotoSansSC-VF.ttf` 为 17,773,244 字节；它是当前快照中最显著的字体项。

这些数字只用于本方案的起点，不替代正式的 `verify-webgl-bundle.ps1`、`verify-wechat-minigame.ps1`、网络压缩统计和真机下载统计。两个目录的修改时间接近，也不能证明它们由同一源码和同一参数生成。

复现命令（仓库根目录、Git Bash，Python 3；只读；产物不存在会显式报出，不把缺目录记成零字节）：

```bash
python - <<'PY'
from pathlib import Path
import json

roots = {
    'webgl': Path('examples/game_jhyt/builds/webgl'),
    'wechat': Path('examples/game_jhyt/builds/wechat-minigame/launcher'),
}
for name, root in roots.items():
    if not root.is_dir():
        print(name, 'NOT_BUILT', root.as_posix())
        continue
    files = [p for p in root.rglob('*') if p.is_file()]
    sizes = {p: p.stat().st_size for p in files}
    total = sum(sizes.values())
    fonts = sum(n for p, n in sizes.items() if p.suffix.lower() in ('.ttf', '.otf'))
    print(name, 'files=', len(files), 'total_bytes=', total, 'font_bytes=', fonts)
    for p, n in sorted(sizes.items()):
        if p.name == 'game_web_bg.wasm':
            print('wasm', p.relative_to(root).as_posix(), 'bytes=', n)
    if name == 'wechat':
        config = json.loads((root / 'game.json').read_text(encoding='utf-8-sig'))
        packages = config.get('subpackages', config.get('subPackages', []))
        prefixes = [entry['root'].strip('/') + '/' for entry in packages]
        sub = sum(n for p, n in sizes.items()
                  if any(p.relative_to(root).as_posix().startswith(s) for s in prefixes))
        print('main_bytes=', total - sub, 'subpackage_bytes=', sub)
PY
```

上表保留编制时快照，后续重打包导致变化时新增日期和差异原因，不无声覆盖历史。此前将旧包接近上限的余量沿用为“当前状态”的说法在本方案中撤回：当前目录读数如上，正式平台配额结论仍须重跑平台门。

## 3. 治理目标

治理目标按“先证明，再优化；先收口所有权，再删重复路径；先保护可回滚，再扩大范围”排列：

1. **正确性优先**：输入、时间、场景、存档、资源和发布身份在各宿主中有一致且可解释的语义。
2. **单一所有权**：同一运行期职责只有一个生产者；平台差异留在平台边界，不能由旧 JS 世界和 Rust 宿主同时猜测。
3. **可测性能**：CPU、GPU、内存、分配、启动和传输分别量化，不能用单一 FPS 代替所有指标。
4. **可控包体**：区分主包、分包、Web 总包、压缩传输、首屏读取和解码后内存，资源变更有来源和归因。
5. **易用性可回归**：编辑器的 Play/Stop、保存、热重载、诊断、发布和错误恢复都有可操作的验证路径。
6. **跨平台诚实**：假宿主、浏览器、开发者工具和真机分别标注证明范围；一个环境通过不外推到另一个环境。
7. **渐进收口**：每个阶段都能独立验证和回滚，不以长期双跑、永久兼容层或放宽判据换取绿色。

## 4. 总体阶段与排序

这里使用 G0–G4 表示治理阶段，避免与项目章程中的 P0–P3 缺陷严重度混用。G 阶段不是排期承诺；进入下一阶段的条件是证据满足，而不是经过了固定天数。

| 阶段 | 目标 | 主要交付 | 进入条件 | 退出证据 |
|---|---|---|---|---|
| G0 事实收口 | 让当前状态可重复读取 | 复测表、产物身份表、风险清单 | 命令、源码、产物口径已分开 | 同一命令在干净入口可复现 |
| G1 正确性与所有权 | 收口输入、时间、存档和宿主所有权 | 失败注入、跨宿主对照、M73 分账结果 | G0 基线可用 | 核心场景和负面用例逐宿主通过 |
| G2 端到端性能 | 找出真实热路径和启动瓶颈 | CPU/GPU/分配/启动/内存报告 | G1 不再有未解释的所有权冲突 | 结论带 workload、宿主和样本数 |
| G3 资源与发布治理 | 控制包体、首屏和发布身份 | 依赖闭包、字体、分包、appid、产物审计 | G0 产物统计稳定 | 变更可归因，正式发布门不依赖手工改产物 |
| G4 易用性与长期维护 | 将引擎能力转成编辑器可操作流程 | UX 回归、诊断入口、文档和任务拆分 | G1/G2 的稳定边界已知 | 新用户路径、错误恢复和回滚都有证据 |

建议按 G0 → G1 → G2/G3 并行 → G4 推进。G2 的性能优化不能绕过 G1 的所有权收口；G3 的体积优化不能通过删除尚未证明为非运行依赖的资源完成。

## 5. G0：事实、产物和证据基线

### 5.1 建立单次复测记录

每次基线记录至少包含：

- git 提交、工作树是否干净、未跟踪文件是否参与；
- Rust 工具链、Node/Python/PowerShell 版本；
- 平台、浏览器或开发者工具版本；
- 命令完整参数、环境变量和输入工程；
- 产物根目录、生成时间、文件数、总字节和关键文件哈希；
- 通过、失败、跳过和环境阻塞的区别；
- 原始日志的位置以及可脱离临时日志复核的摘要。

一次性探针和临时日志可以留在 `.temp/`，但正式结论不能只依赖无法提交的临时文件。需要长期复测的内容应转成脚本、门或文档中的稳定命令。

### 5.2 统一产物身份

发布验证必须同时回答三个问题：

1. 这个目录由哪个源码、参数和工具链生成？
2. 它是否包含目标平台需要的宿主、WASM、资源和配置？
3. 这个产物是否曾被手工改写过？

特别是微信小游戏的 appid：`touristappid` 只能表示占位身份，不能证明开发者工具可编译、上传或真机可运行。工程配置、打包脚本和编辑器发布入口应在实施阶段统一来源和优先级；不能靠打包后手改 `project.config.json` 证明发布链路正确，也不能把真实标识写入 shell 历史作为默认做法。

### 5.3 风险登记格式

每条风险使用以下字段：

```text
编号：Gx-Rn
现象：用户或门实际看到什么
当前证据：静态、假宿主、浏览器、开发者工具、真机中的哪一层
未测边界：还缺什么证据
影响：P0/P1/P2/P3（按项目章程）
建议动作：最小可回滚动作
验收：命令、输入、期望读数和反面用例
```

## 6. G1：正确性、宿主所有权与发布可靠性

### 6.1 输入和时间线

Rust 侧已有 RLFI 批量 ABI、固定模拟步、帧时钟和输入快照。下一步不是再造输入抽象，而是确认以下不变量在所有宿主一致：

- 一帧输入只由一个明确生产者写入；
- 按键边沿只在规定的第一模拟步消费一次；
- 零步帧、多步帧、失焦恢复和转场期间不会重复消费或丢失状态；
- 键盘、轴、鼠标、手柄和修饰键在 ABI 中的索引和符号一致；
- 浏览器 DOM 采集、微信宿主输入和脚本回放属于不同测试通道，不能互相冒充。

验收优先使用同一输入脚本在浏览器、受限微信假宿主和开发者工具中逐方向对拍；真机结论单独登记。移动距离不能直接跨刷新率比较，必须同时记录显示帧、模拟步、丢帧和实际时间。

### 6.2 Rust 宿主与旧 JS 世界

M73 已经把“删除旧 JS 世界”的工作拆成删除面和分账，本文不另起一套竞争性迁移计划。实施时遵循：

- Rust 宿主负责统一帧推进、场景输入、时间和状态镜像；
- WebGL/微信的必要平台后端继续保留在平台边界；
- 旧 JS 只作为隔离对照或明确的兼容路径，不能与新宿主双写生产状态；
- 每个待删除状态镜像先列出唯一生产者、读取者、平台后端和负面用例；
- 删除前先获得新宿主等价证据，删除后再跑静态门和运行期门。

`engine/crates/game_web/src/engine_core.rs`、`engine_host.rs`、`frame_input.rs` 和两个平台插件是后续实施的事实入口；不应仅凭 `docs/65` 首段的旧描述判断当前状态。

### 6.3 存档、设置和平台错误语义

现有 Web `LocalStorageSlot::write` 把 `web_sys::Storage::set_item` 抛出的异常转为 `Err`；微信适配层的 `localStorage.setItem` 则在捕获 `wx.setStorageSync` 异常后返回 `false`。这里存在具体的契约风险：标准 Storage 写入接口不通过布尔返回值报告失败，因此 shim 的 `false` 未必能进入 Rust 的错误链。本轮仅核查源码，尚未通过故障注入证明玩家实际遇到的失败表现。实施时优先核查标准 Storage 异常语义和所有调用者，再决定最小修法，不能把“返回了 false”写成“失败已经传到存档 API”。

建议按以下顺序验证：

1. 注入写入失败、读取失败、删除失败和存储不可用；
2. 检查 Rust 存档 API、Lua provider、微信 shim 和浏览器 shim 的错误语义是否一致；
3. 确认 UI 是否显示失败、是否错误地提示已保存；
4. 只对已确认不兼容的调用者做最小修复；
5. 用重启、覆盖写、空值、损坏数据和容量不足做回归。

设置持久化继续复用现有输入设置路径和原子写入能力，除非基线证明需要新的跨平台槽，不预先泛化存储框架。

### 6.4 场景和物理回归

游戏回归需要把“逻辑能走”和“出生点几何正确”分开。出生点、碰撞盒偏移、实心格、门洞和地图旅行属于场景内容/物理边界，不应由输入修复掩盖。

核心回归至少包括：

- 出生点四向余量和碰撞盒实际位置；
- WASD、方向键、轴输入逐方向同号；
- 场景切换前后输入和时间不重复；
- 读档、重启和发布目录隔离；
- 固定步在不同显示刷新率下的位移、帧数和丢步解释。

### 6.5 架构边界：先审计依赖，再做拆分

当前工程已经有 `rustlua-*` 能力 crate、脚本子模块、RuntimeScene 和 Web EngineCore/EngineHost。架构治理不再从“拆单体 script.rs”或“重建 dense ECS”起步，也不预设换用另一个 ECS、脚本语言或渲染引擎。

建议的边界约束如下；这是目标约束，不是对所有依赖边已满足的声明：

| 边界 | 应拥有的职责 | 应避免的耦合 | 实施前核查入口 |
|---|---|---|---|
| 基础能力 crate | 数学、资源标识、输入值、帧线格式等稳定能力 | 反向依赖编辑器、具体游戏或 JS 宿主 | 各 `Cargo.toml`、`cargo metadata` |
| ECS/调度 | 实体存储、查询、系统依赖与执行顺序 | 把平台事件和游戏规则塞进通用存储 | `rustlua-ecs/src/world.rs`、`scheduler.rs` |
| 脚本运行时 | Lua 绑定、脚本状态、请求、诊断和热重载 | 直接拥有平台窗口或另一套世界时钟 | `rustlua-scripting/src/script/` |
| RuntimeScene | 场景、脚本、物理和提取阶段的编排 | 依赖编辑器 UI 或复制平台后端 | `engine/src/host/runtime_scene/` |
| Web 核心/宿主 | 共享场景、帧推进、GPU/资源桥接 | 浏览器和微信各复制一套玩法状态 | `game_web/src/engine_core.rs`、`engine_host.rs` |
| 平台适配 | 输入采集、文件/存储/音频/生命周期实现 | 平台壳重新解释游戏世界 | `plugins/webgl/`、`plugins/wechat-minigame/` |
| 编辑器 | 文档、撤销、资源索引、PlaySession 和工作流 | 编辑态与运行态共享可变实体而没有边界 | `editor/src/document.rs`、`actions.rs` |
| 游戏脚本 | 内容、玩法、UI 组合和存档 schema | 用平台分支绕过引擎能力契约 | `examples/game_jhyt/scripts/` |

执行步骤：

1. 用 `cargo metadata --manifest-path engine/Cargo.toml --no-deps --format-version 1` 导出依赖事实，标注宿主相关模块；不以 crate 数量衡量架构质量。
2. 针对实际变更频繁或有性能证据的边界列出读写者、数据生命周期、错误通道和测试入口。
3. `Rc<RefCell<ScriptState>>` 先审计借用范围、回调重入和请求队列，不为“多线程化”盲目改成锁；脚本子状态已拆分，继续拆分必须有具体收益。
4. 只有发现逆向依赖、重复所有权或无法独立测试时，才提取最小接口或移动职责；不引入全局 service locator 或万能平台接口。
5. 改公开 API/格式前记录 ADR，调用点同批迁移；若确需兼容，写明消费者、期限和退出条件，不能永久叠加旧入口。

验收以依赖方向、功能等价、错误可解释和测试独立性为准，不以文件行数下降作为成功。

### 6.6 ABI、Lua API 与格式契约

- RLFI 当前线格式和旧格式兼容分支需要分别有长度、版本、字段和非法输入测试；不能只因看到旧长度就删除消费者兼容。
- Lua API 复用既有运行期 API 面基线和文档桩生成链。函数存在不等于平台能力可用，应补查返回值、错误、状态生命周期和平台后端。
- 场景、prefab、资源清单和存档 schema 的变更，先提供旧数据读取、迁移失败和重新保存的验证，再切换默认写法。
- 禁止平台用空成功替代不支持；不支持应能被 Lua、编辑器和测试明确识别。已接通的能力不能被重新列作占位。

## 7. G2：性能、内存和启动治理

### 7.1 性能量具分层

继续使用 [WP0 增量基准](53-WP0增量场景帧基准与每帧分配.md) 的统计字段和入口，补充四类缺口：

| 层次 | 需要回答的问题 | 最小证据 |
|---|---|---|
| 微基准 | 某个容器、查询或转换是否有额外成本 | 固定输入、重复次数、p50/p95/p99、分配数 |
| 场景帧 | 一帧脚本、顶点、UI、3D 和析构成本如何组成 | `wp0-v4` 及其前后对照 |
| 端到端 | 从启动到首屏、持续运行和场景切换哪里变慢 | 冷/热启动、首屏、稳定段、转场 |
| 跨宿主 | 浏览器、假宿主、开发者工具和真机差异是什么 | 同 workload、同版本、逐宿主报告 |

不在没有 profile 的情况下把 ECS 有序索引、Scheduler 计时、Lua 查询缓存、Sprite overlay、字体预热或整图上传直接判为瓶颈。它们是候选测点，只有在负载和采样方式明确后才能进入优化任务。

### 7.2 优先测量的候选点

按“测量成本低、可能影响热路径、容易回滚”排序：

1. Scheduler 的拓扑缓存复制、system 名称 clone、计时采样和 `catch_unwind` 路径；
2. ECS 有序实体遍历中的 order→dense 回查和查询过滤；
3. Lua 请求缓存命中后仍进行的扫描与逐实体调用；
4. `RuntimeScene` 每步输入 clone、UI revision 和 pending input 生命周期；
5. Sprite overlay 整理、排序、九宫格生成和批次合并；
6. 字体预热、图集变化和纹理上传；
7. 资源依赖选择、WASM 启动和首屏等待。

每个候选点必须先有前后对照。若观测本身引入显著开销，增加采样档或编译时诊断入口，但不能把生产路径改成“为了测量而常驻计时”。

### 7.3 内存与分配

内存报告要区分：

- Rust 堆分配和释放；
- Lua VM、脚本对象和字符串；
- GPU buffer/texture；
- 解码后图像、字体和音频；
- 发布目录字节、压缩传输和首屏读取。

先建立启动峰值、稳定运行、场景切换、读档和退出五个窗口。只有确认归属后，才考虑复用 buffer、减少 clone、改变缓存生命周期或延迟加载。不要以“缓存存在”推断“整帧零分配”，也不要为了减少分配破坏错误隔离或生命周期清晰度。

### 7.4 启动与首屏

Web 启动已有依赖索引选择和保守完整清单回退。治理重点是验证索引选择是否正确、首屏依赖是否过宽、失败是否可诊断，而不是简单改成始终全量预载或始终懒加载。

首屏报告至少包含：宿主初始化、WASM 下载/解码、资源依赖选择、脚本编译、场景装载、首个可见帧和首个可交互帧。每个阶段记录墙钟时间、资源字节和是否阻塞主线程。

## 8. G3：资源、字体和包体治理

### 8.1 资源依赖闭包

发布目录治理采用“声明依赖 + 运行期引用 + 平台入口 + 回退清单”四面交叉，而不是只看资源是否在目录里。对每个资源分类：

- 必须随主包进入；
- 可进入分包或按需读取；
- 仅编辑器/预览使用；
- 测试、备份或临时产物；
- 未知，必须先找引用者。

任何删除或迁移前，先跑资源引用、manifest、Lua/场景/prefab、平台配置和发布产物对照。备份目录不得因为“看起来不像运行资源”直接删除；先登记来源、去留负责人和回滚位置。

### 8.2 字体治理

当前 Web 目录快照中，字体占总字节的大部分，优先调查：

- 实际覆盖字符集与 UI/剧情/存档文本的联合需求；
- 变量字体是否可以按目标平台拆分或子集化；
- 首屏必需字体与后续语言/内容字体是否应分层；
- 子集生成是否可复现、是否保留 fallback；
- 字体解码后内存是否比文件体积更敏感。

字体优化必须同时做显示回归、缺字回归、中文标点/数字/符号回归和发布目录复核。不能只以文件字节下降作为成功。

### 8.3 微信主包、分包和身份

微信包体治理必须使用正式门的口径，单次报告同时给出主包、分包、总包、文件数和超限原因。历史上曾出现“绿色但压着别包在制品/备份资源”的情况，因此每次包体报告要附：

- 资源来源和工作树状态；
- 是否包含未跟踪目录；
- appid 来源和产物配置；
- `assetc` 文件计数与关键资源列表；
- 主包/分包边界和首屏依赖。

超过上限时，先归因到资源、WASM、字体、脚本、配置或重复文件，再决定迁移或重压缩。不能靠删门、改产物 JSON 或放宽阈值解决。

## 9. G4：编辑器和开发者体验

### 9.1 复用已有能力，不重复立项

项目已经有 Lua 热重载、候选 VM 原子替换、脚本诊断记录、路径/阶段/行号/栈/次数、过滤和去重。后续治理先审核编辑器入口和当前可用性，再决定是否需要补齐：

- 诊断列表到源文件行的跳转；
- Play/Stop 后错误清理和上下文关联；
- 热重载失败时保留旧 VM 的可视反馈；
- 运行期脚本错误与场景/实体的关联；
- 发布、保存和外部文件变化的冲突提示。

不能把“没有完整断点调试器”扩大成“没有脚本诊断能力”，也不能把历史示例命令直接当作当前验收命令。

### 9.2 最小 UX 回归集

编辑器实施项应至少覆盖：

1. 新建/打开工程，资源和场景索引可用；
2. 打开场景、修改、保存、撤销/重做和外部变更提示；
3. Play/Stop 多次往返，运行态不污染编辑态；
4. Lua 错误可定位、可过滤、重复错误不会无限刷屏；
5. 热重载成功和失败各有可见结果；
6. 发布配置、平台选择、appid 来源和失败信息明确；
7. 关闭/重启后用户数据和编辑器状态按预期恢复。

这些是行为验收项，不要求每一项都先抽象成新的编辑器框架。

## 10. 跨平台与依赖治理

### 10.1 平台分层

平台治理把共性和变体明确分开：

- 共性：EngineCore、EngineHost、场景、脚本、输入 ABI、资源语义和错误模型；
- WebGL 变体：浏览器 canvas、WebGL2、DOM/浏览器事件和发布壳；
- 微信变体：受限宿主、WXWebAssembly、开发者工具、分包和真机 API；
- 桌面/编辑器变体：窗口、GPU 能力、文件系统和调试工具。

共享 Rust/WASM 不等于最终产物字节必须相同。微信 EH、WXWebAssembly、wasm-bindgen fork、Zig/Binaryen 和浏览器 WebGL 的约束必须按平台验收，不以“统一字节”为目标替代运行正确性。

### 10.2 工具链和依赖升级

依赖升级按风险分组：

1. 先记录当前 Rust、wasm-bindgen、Zig、Binaryen、wgpu 和平台工具版本；
2. 对共享 wasm crate、WebGL、微信分别建立构建和运行对照；
3. 先做可回滚的单依赖实验，不在同一提交叠加架构迁移；
4. 对发布大小、异常处理、输入、音频、存档和启动做反向回归；
5. 只有在跨平台证据齐全后才更新技术决策和锁文件。

`game_web` 的 `gpu2d` 默认特性与 WebGL/微信验证门存在联动。本轮核查工作树时，`Cargo.toml` 实际已是 `default = ["gpu2d"]`，而相邻长注释仍描述默认关和曾撤回的历史；应先复核 M73 的门改造状态并校正注释，不能把“再打开 gpu2d”重复立项。今后若改变默认档，默认开关、bundle-summary 引擎证据和 CI 断言必须按依赖顺序一起处理。

### 10.3 CI 触发和质量门

当前质量工作流已拆成 lint、build/test、gates 和 web-evidence 等职责，但特定 workflow 的路径过滤未覆盖所有平台插件目录。治理动作是先审计所有 workflow 的触发面，再决定是否补路径；本方案不直接改 CI。

质量门应区分：

- 代码质量：fmt、clippy、test、rustdoc；
- 文档质量：编号、H1、索引、链接、编码、历史路径、PowerShell BOM/解析；
- 产物质量：WebGL/微信包、GPU/宿主证据、依赖闭包和配额；
- 运行质量：浏览器、受限假宿主、开发者工具、真机；
- 体验质量：编辑器和示例游戏的人工或半自动回归。

环境不可用时标记 BLOCKED/NOT RUN，不以删除判据或换成更弱环境伪造通过。

## 11. 建议的任务拆分

实际开工时，每个任务只承担一个可验证闭环：

| 任务类别 | 首个最小任务 | 不包含的内容 |
|---|---|---|
| G0 | 复测当前产物、工具链和工作树口径 | 不改代码、不重写历史数字 |
| G1 | 输入/时间/宿主所有权逐宿主对拍 | 不顺手删除旧 JS |
| G1 | 存档故障注入与错误语义审计 | 不先建新存储框架 |
| G1 | 出生点和碰撞盒场景回归 | 不把场景内容修复伪装成输入修复 |
| G2 | WP0 复测并补一个端到端 workload | 不先定硬 FPS/分配预算 |
| G2 | 一个候选热路径的 profile 与最小优化 | 不同时重构 ECS、Scheduler、Lua |
| G3 | 字体依赖闭包和显示回归 | 不凭文件大小删除字体 |
| G3 | 微信产物身份、appid 和包体来源审计 | 不手改产物 JSON 作为验收 |
| G4 | 编辑器诊断/热重载/Play-Stop UX 回归 | 不把断点调试器作为前置条件 |
| M73 衔接 | 按现有删除面和分账继续收口旧 JS | 不另建第二套迁移计划 |

每个任务完成后都要回写：影响文件、证据命令、未测边界、回滚方式和是否需要 ADR。未完成项留在任务或残项登记中，不通过移动目录或改状态词隐藏。

## 12. 建议指标与批准规则

以下指标是建议观察字段，不是本次直接批准的发布硬阈值：

- 启动：WASM、资源、脚本、场景、首屏、首个可交互帧的墙钟时间；
- 帧性能：CPU/GPU 分位数、模拟步、丢步、稳定段和转场段；
- 分配：每帧、场景切换、读档、退出的分配次数和字节；
- 内存：启动峰值、稳定峰值、场景切换峰值、字体/纹理解码后占用；
- 包体：主包、分包、总包、文件数、字体、WASM、重复文件和首屏依赖；
- 正确性：逐方向输入、存档故障注入、负面用例、宿主所有权和场景回归；
- 易用性：从打开工程到 Play、错误定位、热重载、保存和发布的步骤与失败恢复。

将观察值升级为硬门前，需要同时批准：

1. 测量口径和 workload；
2. 机器、宿主和工具链范围；
3. 样本数、重复策略和波动处理；
4. 失败后的用户影响与回滚方式；
5. 对主包、分包、WebGL 和真机是否分别设门。

本节约束的是新增预算。现有 WP0 和质量门中已经批准的断言继续有效，不能借本方案降级或移除。新建议尚未满足批准条件时，只能作为观察值；回归判断仍按现有门、同 workload 对照及统计证据执行。

## 13. Definition of Done

一项治理任务只有在以下条件全部满足时才可标记完成：

- 现象、影响和证据层次明确；
- 代码/配置/任务/文档变更范围最小且可回滚；
- 正向用例和至少一个反面用例已执行；
- 假宿主、浏览器、开发者工具和真机的结论没有互相外推；
- 性能和包体数字带命令、日期、单位和统计口径；
- 失败、跳过、环境阻塞和未测项没有被写成通过；
- 需要时更新 ADR、能力文档、质量门或 CHANGELOG；
- `scripts/check-docs.ps1`、相关代码质量门和目标平台门按影响范围执行；
- 共享台账中的别包改动没有被误暂存或覆盖。

## 14. 当前明确不纳入本方案实施的事项

以下事项保留为后续任务或外部验收，不在本文落地时直接修改：

- 真机微信输入、画面和包体验收；
- 所有旧 JS 世界删除面；
- 出生点卡门洞的场景内容修复；
- 松手后短距离惯性的成因和玩家感知判定；
- 备份美术资源的最终去留和统一质感阈值；
- WebGL/微信默认宿主开关及其质量门改造；
- CI 触发路径、GPU 门和发布硬阈值的调整；
- Rust/ECS/Scheduler/Lua 的无 profile 重构；
- 任何依赖升级、格式迁移和公开 API 变更。

这些事项不是被否定，而是需要各自的证据、授权和回滚边界。本文的作用是提供统一治理框架，避免多个专项重复测量、相互覆盖或把局部绿灯当成全平台完成。
